1.1 Translating business problems into Claude solutions

ต้นฉบับ: CertSafari 1.1

อ่านจบแล้วควรทำได้
  • ไล่ดู process ทางธุรกิจที่มีอยู่ หาว่าขั้นไหนเจ็บจริง แล้วแตกงานใหญ่ออกเป็น task ย่อยที่วัดผลแยกกันได้
  • ตัดสินได้ว่าขั้นไหนควรให้ Claude ทำ ขั้นไหนควรปล่อยเป็นโค้ดหรือระบบเดิม และขั้นไหนต้องมี retrieval / tool / คนตรวจ
  • เลือกรูปร่างโซลูชันที่ง่ายที่สุด (augmented LLM, workflow, agent) และเลือกทางสร้าง (Messages API, Agent SDK, Managed Agents, Claude Code, Claude apps)
  • จับคู่ model tier (Haiku, Sonnet, Opus, Fable) กับแต่ละงาน และรู้ว่า effort เป็นคันโยกอีกตัวที่ถูกกว่าการเปลี่ยนโมเดล
  • ผูก task metric เข้ากับ business metric ที่เจ้าของ process สนใจจริง
แนวคิดหลัก: เริ่มจาก process ไม่ใช่เริ่มจากโมเดล

ออกแบบโดย ดู process ก่อน: วาดว่างานทุกวันนี้ทำกันยังไง หาจุดที่เจ็บ แล้วยกให้ Claude เฉพาะขั้นที่ช่วยได้ชัดๆ หลังจากนั้นค่อยเลือกรูปร่างที่ง่ายที่สุด ทางสร้าง และโมเดล ไม่ใช่เริ่มจาก "เราจะใช้ Opus ทำ agent" แล้วค่อยหางานมาใส่

1. วาด process ทางธุรกิจก่อนเลือกโมเดล

โจทย์ที่ทีมธุรกิจยื่นมามักมาในรูปของ "อาการ" เช่น "ticket ไปผิดทีมบ่อย" หรือ "ลูกค้ารอนาน" งานแรกของสถาปนิกคือย้อนจากอาการไปหาว่า ขั้นไหนใน process เป็นต้นเหตุ เหมือนหมอที่ไม่จ่ายยาจากอาการไข้อย่างเดียว แต่ต้องหาว่าติดเชื้อที่ไหน

คำถามที่ควรถามตอนวาด process (ยกตัวอย่างจากงาน ticket routing):

  • ทุกวันนี้ route ticket กันยังไง ใช้คน ใช้ keyword rule หรือใช้ ML ตัวเก่า
  • อะไรเป็นตัวกำหนด SLA ของแต่ละ ticket
  • การ route คือเลือก ระดับ ซัพพอร์ต (tier 1/2/3) หรือเลือก ผู้เชี่ยวชาญ ตามผลิตภัณฑ์
  • rule หรือ workflow เดิม พังตรงไหน และคนแก้เคสขอบ (edge case) ด้วยมือยังไง

จุดที่คนต้องแก้มือคือทองคำ เพราะมัน วัดเป็นต้นทุนได้ ตัวอย่างคลาสสิก: rule เขียนว่า "ticket ไหนมีคำว่า payment ส่งไป billing" ผลคือบั๊กของหน้า payment ที่ควรไปทีม engineering กลับไปโผล่ที่ billing แล้วต้องมีคนมาย้ายเองทีละใบ

แตกงานใหญ่เป็น task ย่อย

อย่ามอง "แชทบอทซัพพอร์ต" เป็นก้อนเดียว ลองนึกถึงบอทของบริษัทประกันรถ จริงๆ มันทำหลายงานปนกัน:

  • ทักทายและรับเรื่อง
  • ตอบข้อมูลผลิตภัณฑ์ (ความคุ้มครอง เงื่อนไข)
  • คุมบทสนทนาให้อยู่ในเรื่อง ไม่หลุดไปคุยเรื่องอื่น
  • ออกใบเสนอราคา (quote) ผ่าน API

แต่ละงานควรมี prompt ของตัวเองและ evaluation ของตัวเอง เพราะถ้ารวมเป็นคะแนนเดียว งานออกใบเสนอราคาอาจพังเงียบๆ ในขณะที่คะแนนรวมยังดูดีเพราะการทักทายทำได้ดีมาก

เข้าใจผิดบ่อย

"แชทบอทซัพพอร์ตคือ task เดียว ใช้ prompt เดียว วัดด้วยคะแนนเดียว" ไม่ใช่ ต้องแยกเป็นหลาย task แต่ละอันมี prompt และ eval ของตัวเอง คะแนนรวมก้อนเดียวจะซ่อนจุดที่พังไว้

สรุปสั้นๆ

เริ่มจากอาการ → หาขั้นที่เป็นต้นเหตุ → ดูว่าคนแก้มือตรงไหน (นั่นคือต้นทุนที่วัดได้) → แตกงานใหญ่เป็น task ย่อยที่มี prompt และ eval แยกกัน

Checkpoint 1

โรงพยาบาลเอกชนอยากได้ LINE bot ที่ทำได้ทั้ง ทักทาย ตอบคำถามแพ็กเกจตรวจสุขภาพ จองคิวผ่าน API ของระบบนัดหมาย และกันไม่ให้บอทตอบคำถามวินิจฉัยโรค ทีมเสนอให้เขียน prompt ใหญ่ prompt เดียวแล้ววัดด้วยคะแนนความพึงพอใจหลังแชท ควรแนะนำอะไร?

  1. ใช้ prompt เดียวเหมือนเดิม แต่เปลี่ยนไปใช้โมเดลที่เก่งที่สุด
  2. ใช้ prompt เดียว แต่เพิ่มแบบสอบถามความพึงพอใจให้ละเอียดขึ้น
  3. เปลี่ยนเป็น agent อิสระให้มันตัดสินใจเองว่าจะทำอะไร
  4. แยกเป็น task (ทักทาย, ข้อมูลแพ็กเกจ, จองคิว, คุมขอบเขตเรื่อง) แต่ละ task มี prompt และชุดทดสอบของตัวเอง
ดูเฉลย

D งานจองคิวกับงานคุมขอบเขตเรื่องการวินิจฉัยมีเกณฑ์ผ่านคนละแบบ ต้องวัดแยก A และ B ยังคงเป็นคะแนนก้อนเดียวที่ซ่อนจุดพัง ส่วน C เพิ่มความซับซ้อนโดยไม่มีเหตุผล

2. ตัดสินว่าขั้นไหนควรให้ Claude ทำ

Claude เก่งกับขั้นที่เกี่ยวกับ ภาษา การใช้วิจารณญาณ และความหลากหลายของ input สัญญาณที่บอกว่า Claude น่าจะดีกว่า ML แบบดั้งเดิม (เช่น classifier ที่ต้องเทรนเอง):

  • ข้อมูลที่ติด label มีน้อย (Claude ใช้ตัวอย่างแค่ไม่กี่สิบตัวใน prompt ก็จัดหมวดได้)
  • หมวดหมู่เปลี่ยนบ่อย แก้ prompt ง่ายกว่าเทรนโมเดลใหม่
  • input ไม่มีโครงสร้าง หรือหมวดถูกนิยามด้วยเงื่อนไขที่เป็นภาษาคน
  • ต้องอธิบายได้ว่าทำไมตัดสินแบบนั้น (explainable)
  • ต้องรองรับหลายภาษาด้วยโมเดลตัวเดียว

ข้อจำกัดที่ต้องออกแบบรองรับ

โมเดลสร้างข้อความที่ "น่าจะเป็น" ที่สุด ไม่ได้ค้นข้อเท็จจริงจากฐานข้อมูล จึงอาจแต่งอ้างอิง ตัวเลข หรือข้อมูลเฉพาะของบริษัทขึ้นมาได้ ดังนั้น:

  • ขั้นที่ต้องการข้อมูล ปัจจุบัน หรือ ข้อมูลภายในบริษัท ต้องมี retrieval, search หรือ tool ป้อนข้อมูลให้
  • output ที่ตรวจไม่ได้ด้วยตัวมันเอง ต้องมีคนตรวจ หรือมีการตรวจด้วยโค้ด
  • ขั้นที่เป็น deterministic และทำงานดีอยู่แล้ว (เช่น lookup SLA จากตาราง) ไม่ต้องเอา LLM ไปแตะ
ในข้อสอบ

มองหาคำตอบที่ แก้เฉพาะขั้นที่เจ็บ และปล่อยขั้นที่ทำงานดีไว้เหมือนเดิม คำตอบประเภท "รื้อทั้ง process แล้วสร้างใหม่รอบ LLM" แทบไม่เคยถูก

ลองทำกับงานจริง: หยิบ process ที่คุ้นเคย เช่น การอนุมัติใบแจ้งหนี้ การ onboard พนักงานใหม่ หรือการคัดแยก incident แล้วหาขั้นที่ต้องแก้มือบ่อยที่สุด ถามต่อว่าการแก้นั้นเป็น "การใช้วิจารณญาณ" (Claude ช่วยได้) หรือเป็น "การค้นข้อมูล" (ต้องมี tool หรือ retrieval)

สรุปสั้นๆ

ให้ Claude ทำขั้นที่ต้องใช้ภาษาและวิจารณญาณ ป้อนข้อเท็จจริงด้วย retrieval/tool ตรวจ output ที่ตรวจตัวเองไม่ได้ และอย่าไปยุ่งกับขั้น deterministic ที่ดีอยู่แล้ว

Checkpoint 2

ระบบรับเรื่องร้องเรียนของบริษัทขนส่งมี 3 ขั้น: (1) ใช้ keyword rule จัดหมวดเรื่อง (2) เปิดตาราง SLA ตามหมวดและระดับลูกค้า (3) ส่งเข้าคิวทีม ข้อมูลบอกว่าเรื่องที่เขียนกำกวม เช่น "ของมาช้าแถมกล่องบุบ" ถูกจัดหมวดผิดและต้องมีคนย้ายเองทุกวัน ควรเริ่มที่ตรงไหน?

  1. ให้ Claude ทำขั้นที่ 2 แทนตาราง SLA
  2. ไม่ต้องแก้อะไร เพราะยังมีคนคอยแก้ให้อยู่แล้ว
  3. รื้อทั้ง 3 ขั้นให้โมเดลตัวเดียวทำตั้งแต่ต้นจนจบ
  4. เอา Claude มาแทนเฉพาะขั้นที่ 1 ที่เป็นต้นเหตุของการแก้มือ ส่วนขั้น 2 และ 3 เก็บไว้
ดูเฉลย

D ขั้นจัดหมวดคือจุดที่เจ็บและต้องการการตีความภาษา A ไปแตะขั้น deterministic ที่ทำงานดีอยู่ C รื้อเกินจำเป็น B มองข้ามต้นทุนการแก้มือที่วัดได้ชัดๆ

3. เลือกรูปร่างโซลูชันที่ง่ายที่สุด

มี 3 รูปร่างพื้นฐาน เรียงจากง่ายไปซับซ้อน:

รูปร่างคืออะไรเหมาะกับ
Augmented LLMเรียกโมเดลครั้งเดียว เสริมด้วย retrieval, tool หรือ memoryงานที่นิยามชัด เช่น จัดหมวด ticket
WorkflowLLM และ tool ถูกเรียงต่อกันตามเส้นทางที่โค้ดกำหนดไว้งานที่ขั้นตอนตายตัว เช่น จัดหมวดแล้วส่งเข้า prompt เฉพาะทาง
Agentโมเดลเลือกขั้นตอนและ tool เองตอนรันงานที่ขั้นตอนขึ้นกับ input เช่น แก้โค้ดที่ไม่รู้ล่วงหน้าว่าต้องแตะไฟล์ไหน

กฎคือ เพิ่มความซับซ้อนเมื่อมีหลักฐานว่าต้องใช้เท่านั้น เพราะ agent เพิ่มทั้ง latency และค่าใช้จ่าย

ลองเดา: ต้องสรุปเอกสารกฎหมายลงฟิลด์ตายตัว โดยใช้นิยามศัพท์จาก glossary ของบริษัท รูปร่างเริ่มต้นที่ดีที่สุดคือ? คำตอบคือ เรียก Claude ครั้งเดียว ใส่ entry ของ glossary ที่เกี่ยวข้องและตัวอย่างไม่กี่ตัว ไม่ต้องมี orchestrator หรือ agent อิสระ

เข้าใจผิดบ่อย

"process ที่ต้องแตะหลายระบบต้องใช้ agent อิสระ" ไม่ใช่ จำนวนระบบไม่ได้เป็นตัวตัดสิน ถ้าขั้นตอนตายตัวก็ใช้ workflow ใช้ agent เมื่อขั้นตอนขึ้นกับ input เท่านั้น

สรุปสั้นๆ

Augmented LLM → workflow → agent ขยับขึ้นทีละขั้นเมื่อมีหลักฐานว่าขั้นที่ต่ำกว่าไม่พอ

Checkpoint 3 (จับคู่)

จับคู่งานกับรูปร่างที่เหมาะที่สุด (A = Augmented LLM, B = Workflow, C = Agent):

  1. ติดแท็กอารมณ์ (บวก/ลบ/กลาง) ให้รีวิวสินค้าทีละรายการ
  2. รับเรื่อง → จัดประเภท → ส่งเข้า prompt ที่จูนมาเฉพาะประเภทนั้น ทุกครั้งเหมือนกัน
  3. ย้าย config จากระบบเก่าไประบบใหม่ ซึ่งแต่ละ repo มีโครงสร้างต่างกันและไม่รู้ล่วงหน้าว่าต้องแก้ไฟล์ไหน
ดูเฉลย

1-A, 2-B, 3-C งานจัดหมวดเดี่ยวๆ เรียกครั้งเดียวพอ งานที่ลำดับตายตัวเป็น workflow ส่วนงานที่ไฟล์ที่ต้องแตะขึ้นกับ input ต้องให้โมเดลเลือกเอง

4. จับคู่รูปร่างกับทางสร้าง (build path)

พอรู้รูปร่างแล้ว ต้องเลือกว่าจะสร้างบนอะไร ตัวแบ่งหลักคือ ใครเป็นคนรัน loop และ runtime:

ทางสร้างได้อะไรเหมาะเมื่อ
Messages API (Client SDK)เข้าถึง API ตรงๆ เขียน tool loop เอง หรือใช้ tool runner (beta)ต้องการควบคุมเต็มที่ และเห็น prompt/response ทุกตัว
Agent SDKtool ในตัวของ Claude Code, permissions, sessions, hooks, subagents มาในรูป library รันใน process ของเราเองอยากฝัง agent ที่มี tool อ่านไฟล์ / shell / เว็บ ไว้ใน service ของตัวเอง
Managed AgentsAnthropic host ทั้ง loop, การรัน tool และ runtime โดย session รันใน sandbox ที่ Anthropic จัดการ หรือ self-hosted sandbox บน infra ของเรางานยาวเป็นนาทีหรือชั่วโมงที่มี tool call เยอะ และไม่อยากดูแล infra ของ loop เอง
Claude Code CLIเครื่องมือใน terminalงานแบบ interactive ที่นักพัฒนานั่งทำเอง
Claude apps (artifacts)สร้างเครื่องมือเล็กๆ แบบไม่ต้องเขียนโค้ดtool ภายในง่ายๆ

Self-hosted sandbox ของ Managed Agents มีไว้สำหรับกรณีที่ต้องทำตาม compliance หรือข้อกำหนดเรื่องที่เก็บข้อมูล (data residency) ให้ทำงานจริงบน infra ของเราได้ แม้ loop จะยังเป็นของ Anthropic

เข้าใจผิดบ่อย

"Managed Agents ก็คือ Agent SDK ที่เปลี่ยนชื่อ" ไม่ใช่ ต่างกันที่ว่าใครดูแล runtime: Agent SDK รันใน process ที่ เรา ดูแล ส่วน Managed Agents Anthropic เป็นคน host loop และการรัน tool

สรุปสั้นๆ

อยากเห็นทุกอย่างเอง → Messages API · อยากได้ agent สำเร็จรูปใน process ตัวเอง → Agent SDK · อยากให้ Anthropic รันงานยาวให้ → Managed Agents

Checkpoint 4 (จับคู่)

จับคู่ความต้องการกับทางสร้าง (A = Messages API, B = Agent SDK, C = Managed Agents):

  1. ทีม data อยากให้ agent วิเคราะห์ dataset ใหญ่ทีละหลายชั่วโมงใน sandbox โดยไม่ต้องเขียนและดูแล loop เอง
  2. ทีม backend อยากฝัง agent ที่อ่านไฟล์ รัน shell และค้นเว็บได้ ไว้ใน microservice ที่ตัวเองดูแล
  3. ทีม fintech มี flow สั้นๆ 2 ขั้น และต้อง log ทุก prompt กับ response ให้ auditor ดูได้ทั้งหมด
ดูเฉลย

1-C, 2-B, 3-A จับผิดคู่เมื่อไหร่ จะได้อย่างใดอย่างหนึ่ง: ต้องดูแล infra ที่ไม่ได้อยากดูแล หรือ loop ถูกซ่อนในจุดที่ต้องมองเห็น

Claude Sonnet 5.5ค่าเริ่มต้นสำหรับงานทั่วไปเขียนโค้ดประจำวัน วิเคราะห์ข้อมูล ร่างเนื้อหา งาน agent ที่ใช้ tool และงาน enterprise
Claude Opus 5.5ทำงานอิสระต่อเนื่องได้นานcoding agent ที่รันหลายชั่วโมง refactor ขนาดใหญ่ งานระบบซับซ้อน computer use
Claude Fable 5.1tier ที่ความสามารถสูงสุดagent session ยาวมากๆ และ deep research ที่หนักที่สุด

Effort: คันโยกที่ถูกกว่าการเปลี่ยนโมเดล

ค่า effort ปรับความลึกของการคิดภายในโมเดลตัวเดียวกัน แลกกับ latency และค่าใช้จ่าย หลายครั้งการลดหรือเพิ่ม effort ได้ผลพอโดยไม่ต้องย้ายไปอีก tier เหมือนปรับเกียร์รถแทนที่จะเปลี่ยนรถทั้งคัน

สองกลยุทธ์เริ่มต้น

  • Cost-first: เริ่มจากโมเดลเล็ก แล้วอัปเกรดเฉพาะเมื่อพิสูจน์ได้ว่ามีช่องว่างด้านความสามารถ
  • Capability-first: เริ่มจากโมเดลใหญ่เพื่อให้ได้คุณภาพก่อน แล้วค่อยลดลงมาเพื่อประหยัด

ในระบบจริงมักผสมกัน เช่น Haiku คัดแยก แล้ว Sonnet หรือ Opus รับงานยากต่อ

เข้าใจผิดบ่อย

"งานที่ต้อง reasoning หลายเทิร์นต้องใช้ Sonnet หรือ Opus เสมอ" ไม่ใช่ Haiku ถูกสร้างมาสำหรับงาน real-time ปริมาณสูงที่ยังต้องคิดเป็น ให้เริ่มจาก Haiku แล้วอัปเกรดเมื่อเจอช่องว่างที่ระบุได้ชัด

"context ใหญ่ขึ้น = คิดเก่งขึ้น" ไม่ใช่ ขนาด context กับความลึกของ reasoning เป็นคนละเรื่องกัน

สรุปสั้นๆ

Haiku = เร็ว/ถูก/ปริมาณมาก · Sonnet = ค่าเริ่มต้นงานทั่วไป · Opus = งานอิสระยาวหลายชั่วโมง · Fable = หนักที่สุด ลองปรับ effort ก่อนเปลี่ยน tier

Checkpoint 5

เว็บขายตั๋วคอนเสิร์ตต้องมีแชทตอบคำถามช่วงเปิดขาย คนเข้าพร้อมกันหลายหมื่น ต้องตอบภายในไม่กี่ร้อยมิลลิวินาที งบต่อข้อความต่ำมาก คำถามส่วนใหญ่ต้องคิดนิดหน่อย เช่น เทียบโซนที่นั่ง ควรเริ่มที่ tier ไหน?

  1. Sonnet เพราะงานไหนต้องคิดก็ควรใช้อย่างน้อย Sonnet
  2. Fable แต่ตั้ง effort ต่ำสุด
  3. Opus แล้วไปขอผ่อนเงื่อนไขเรื่อง latency กับงบ
  4. Haiku แล้วทดสอบให้ละเอียด อัปเกรดเฉพาะเมื่อเจอช่องว่างที่ระบุได้
ดูเฉลย

D โจทย์ตรงกับจุดแข็งของ Haiku A อิงความเชื่อผิดว่างานคิดต้องใช้ tier ใหญ่ C ไปเปลี่ยนข้อจำกัดที่ตายตัว B แม้ลด effort แล้ว Fable ก็ยังเป็น tier ราคาพรีเมียมที่ไม่ได้ออกแบบมาสำหรับแชทเร็วราคาถูก

Checkpoint 6

ทีมแพลตฟอร์มต้องการ agent ที่ย้าย monolith ไปเป็นหลาย service โดยรันอิสระต่อเนื่องหลายชั่วโมง แตะหลายร้อยไฟล์ ควรเลือก tier ไหน?

  1. Haiku รันหลายๆ ตัวขนานกันแทน เพราะถูกกว่า
  2. Haiku แต่ให้ context ใหญ่ขึ้น
  3. Sonnet เพราะเป็นค่าเริ่มต้น
  4. Opus
ดูเฉลย

D งานอิสระหลายชั่วโมงและ refactor ขนาดใหญ่คือโจทย์ของ Opus A คิดว่าลองถูกๆ หลายครั้งแทน reasoning ต่อเนื่องได้ B สับสนระหว่างขนาด context กับความลึกของการคิด C ใช้ได้แต่ไม่ใช่ตัวเลือกแรกสำหรับงานอิสระระดับนี้

Checkpoint 7

บริษัทจะเปิดให้ทุกแผนกใช้ Claude ผ่านเครื่องมือภายใน งานปนกันทั้งร่างอีเมล วิเคราะห์ spreadsheet และเขียน script เล็กๆ ต้องเลือกโมเดล default ตัวเดียว ควรเลือก?

  1. Opus เพราะเก่งที่สุดในกลุ่มงานโค้ด
  2. Fable เพราะ tier สูงสุดจะตอบได้ทุกงาน
  3. Haiku เพราะถูกที่สุด
  4. Sonnet
ดูเฉลย

D Sonnet คือค่าเริ่มต้นสำหรับงานประจำวันที่หลากหลาย Opus และ Fable แพงเกินไปสำหรับงานทั่วไป Haiku อ่อนเกินไปสำหรับงานผสมข้ามแผนก

6. ผูก success criteria เข้ากับผลทางธุรกิจ

Metric มี 2 ชั้น:

  • Task metric วัดงานของโมเดล เช่น ความแม่นในการจัดหมวด ความถูกต้องของใบเสนอราคา
  • Business metric วัดผลที่ธุรกิจจ่ายเงินเพื่อให้ได้ เช่น deflection rate (สัดส่วนเรื่องที่จบโดยไม่ต้องถึงคน), CSAT, เวลาจัดการต่อเรื่อง, escalation rate, ต้นทุนต่อ ticket

ทุก task metric ต้องอธิบายได้ว่า มันขยับ business metric ตัวไหน และเป้าหมายควรตั้งร่วมกับทีมที่เป็นเจ้าของ process ไม่ใช่ทีม engineering ตั้งเอง

ตัวอย่างงานTask metricBusiness metric (ตัวเลขอ้างอิงในบทเรียน)
Support chatความแม่นในการจับ intent 95% ขึ้นไป, ใบเสนอราคาถูก 100%deflection 70–80%, CSAT 4 จาก 5 ขึ้นไป, เวลาจัดการเฉลี่ยต่ำกว่าคน
Ticket routingrouting accuracyticket ที่ปิดได้ต่อ agent เพิ่ม 10–20%, escalation ต่ำกว่า 20%, ต้นทุนต่อ ticket ลด 10–15%
สรุปสั้นๆ

รายงาน task metric คู่กับ business metric เสมอ และตกลงเป้ากับเจ้าของ process ความแม่น 99% ไม่มีความหมายถ้าต้นทุนต่อ ticket ไม่ลด

Checkpoint 8

ทีมส่งรายงานว่าระบบจัดหมวดอีเมลลูกค้าแม่น 93% ผู้บริหารฝ่ายบริการลูกค้าถามว่า "แล้วมันช่วยอะไรเรา" ควรปรับรายงานยังไง?

  1. เพิ่ม metric ฝั่ง engineering อีก เช่น latency p99 และ token ต่อคำขอ
  2. ตั้งเป้าความแม่นใหม่เป็น 99%
  3. ตัดความแม่นทิ้ง แล้วรายงานแค่ CSAT
  4. รายงานความแม่นคู่กับ escalation rate และต้นทุนต่อเรื่อง โดยตั้งเป้าร่วมกับทีมบริการลูกค้า
ดูเฉลย

D ต้องโยง task metric เข้ากับผลทางธุรกิจ A ยังไม่ผูกกับธุรกิจ B ความแม่นไม่ใช่สิ่งที่ธุรกิจจ่ายเงินซื้อ C ตัด task metric ทิ้งจนไม่รู้ว่าโมเดลทำงานดีแค่ไหน

Checkpoint 9

ข้อไหน ไม่ใช่ สัญญาณที่บอกว่า Claude น่าจะเหมาะกว่า classifier แบบเทรนเอง?

  1. มีข้อมูลติด label แค่ไม่กี่สิบตัว
  2. หมวดหมู่ถูกปรับทุกไตรมาส
  3. ต้องอธิบายเหตุผลการตัดสินให้ฝ่าย compliance อ่าน
  4. input เป็นรหัสสินค้าแบบตายตัวที่ map ไปหมวดได้ด้วยตาราง lookup
ดูเฉลย

D ถ้า map ได้ด้วยตาราง ก็เป็นงาน deterministic ที่โค้ดธรรมดาทำได้ดีกว่า ข้ออื่นเป็นสัญญาณคลาสสิกที่ Claude ได้เปรียบ
