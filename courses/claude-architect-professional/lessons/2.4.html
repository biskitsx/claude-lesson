2.4 Context window budgeting: what counts and how to measure it

ต้นฉบับ: CertSafari 2.4

อ่านจบแล้วควรทำได้
  • นับทุกส่วนของ request รวมเป็นยอดเดียว และรู้ว่าส่วนไหนนับใน context window บ้าง
  • ทำนายได้ว่า API จะทำอะไรเมื่อ input อย่างเดียว เกิน window กับเมื่อ input + max_tokens เกิน window
  • อธิบายได้ว่า thinking block จากรอบก่อนๆ กระทบ context และค่าใช้จ่ายอย่างไร ซึ่งต่างกันตามรุ่นโมเดล
  • วัด context ได้ทั้งก่อนส่ง (token counting) และหลังได้ผล (usage)
  • จับคู่ต้นทุนของ agent ที่ใช้ tool เยอะ กับเทคนิคที่ลดต้นทุนนั้นได้ตรงจุด
แนวคิดหลัก: งบก้อนเดียว ใช้ร่วมกันทุกอย่าง

Context window คือจำนวน token สูงสุดที่โมเดลรับได้ในหนึ่ง request ให้คิดว่าเป็น งบประมาณก้อนเดียว ที่ system prompt, tool definitions, ประวัติข้อความ (รวม tool result) และ output ของรอบนี้ (รวม thinking) ต้องหารกันใช้ Caching ทำให้ token ที่ cache ไว้ ถูกลง แต่ ยังกินพื้นที่ ใน window เท่าเดิม

1. อะไรบ้างที่อยู่ใน window

เปรียบเหมือนกระเป๋าเดินทางใบเดียวที่มีน้ำหนักจำกัด ของทุกชิ้นนับน้ำหนักหมด ไม่ว่าจะซื้อมาแพงหรือได้ส่วนลด (cache) ก็หนักเท่ากัน

ส่วนของ requestนับไหมหมายเหตุ
System promptนับส่งไปทุก request
Tool definitionsนับอยู่ในทุกรอบ แม้รอบนั้นจะไม่ได้เรียก tool เลย
Messages (รวม tool result, รูปภาพ, เอกสาร)นับโตขึ้นทุกรอบ เพราะรอบก่อนๆ ถูกส่งไปเต็มๆ
Output รวม extended thinkingนับถูกจำกัดด้วย max_tokens สูงสุด 128k ในรุ่นที่มี window 1M
Cached prefix (cache_read_input_tokens, cache_creation_input_tokens)นับcache เปลี่ยนแค่ราคา ไม่ได้เปลี่ยนว่านับหรือไม่

ขนาด window ของแต่ละรุ่น

  • Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.1 และอีกหลายรุ่น: window 1M token output สูงสุด 128k ต่อ request
  • Sonnet 4.5 (deprecated แล้ว): window 200k
  • รุ่น 1M ใช้ window เต็มได้เป็นค่าเริ่มต้นในราคามาตรฐาน ยกเว้น Haiku 5.5 ที่คิดราคาสูงขึ้นเมื่อ prompt เกิน 100,000 token
  • ใหญ่ไม่ได้แปลว่าดีเสมอ ความแม่นและการดึงข้อมูลกลับมาใช้ (recall) แย่ลงเมื่อ context ยาวขึ้น (ดูบท 5.2) จึงควรวางงบให้ต่ำกว่าเพดานไว้เยอะๆ
เข้าใจผิดบ่อย

"ส่วนที่ cache ไว้แล้วไม่นับใน context window" ผิด caching เปลี่ยนแค่ราคา token ยังนั่งอยู่ใน window ครบทุกตัว

สรุปสั้นๆ

ทุกอย่างนับ: system, tools (แม้ไม่ได้เรียก), ประวัติทั้งหมด, output และ thinking รวมถึงส่วนที่ cache ไว้ window 1M ไม่ได้แปลว่าควรใช้ให้เต็ม

Checkpoint 1

agent วิเคราะห์สัญญา cache system prompt + tool catalogue ไว้ 25,000 token รอบถัดมา usage แสดง cache_read_input_tokens = 25,000 และ input_tokens = 3,000 โดยรอบนี้ไม่มีการเรียก tool เลย input ของรอบนี้ใช้ context window ไปเท่าไร?

  1. 5,500 เพราะส่วนที่ cache นับแค่ 10% ตามราคา hit
  2. 3,000 + system prompt เท่านั้น เพราะไม่ได้เรียก tool รอบนี้ tool definitions จึงไม่นับ
  3. 25,000 เพราะ input_tokens เป็นส่วนหนึ่งของ cache read อยู่แล้ว
  4. 28,000
ดูเฉลย

D ทั้งส่วน cache และไม่ cache นับใน window เต็มจำนวน (ราคาถูกลงไม่ได้แปลว่ากินที่น้อยลง) สองช่องนี้แยกกัน ไม่ซ้อนกัน และ tool definitions นับทุกรอบแม้ไม่มีการเรียก tool

2. ชนเพดานแล้วเกิดอะไรขึ้น

มี 2 กรณีที่ต้องแยกให้ออก:

กรณีผลลัพธ์
Input อย่างเดียวก็เกิน window แล้วทุกรุ่นตอบ 400 invalid_request_error (ข้อความทำนอง "prompt is too long") ไม่เริ่ม generate เลย
Input พอดี แต่ input + max_tokens เกิน บน Claude 4.5 ขึ้นไปรับ request ปกติ ถ้า generate จนชนเพดานจริง จะหยุดพร้อม stop_reason: "model_context_window_exceeded"
กรณีเดียวกันบนรุ่นก่อน 4.5ได้ validation error เว้นแต่จะ opt-in ด้วย beta header model-context-window-exceeded-2025-08-26

อีกเรื่องที่ต้องจำ: API เปล่าๆ ไม่เคยทิ้งรอบเก่าให้เรา และไม่ขยาย window ชั่วคราวให้ด้วย แอปแชตอย่าง claude.ai อาจตัดประวัติเก่าแบบเข้าก่อนออกก่อน (FIFO) ให้ แต่ถ้าเรียก API ตรง ประวัติทุกรอบจะถูกส่งไปเต็มๆ แอปของเราต้องจัดการการโตของ context เอง

และต้อง เช็ก stop_reason ทุกครั้ง ถ้าโค้ดไม่สนใจค่านี้ คำตอบที่ถูกตัดกลางคันจะดูเหมือนคำตอบที่จบสมบูรณ์

resp = client.messages.create(...)
if resp.stop_reason == "model_context_window_exceeded":
    # คำตอบไม่ครบ: ย่อประวัติ/ตัด tool result เก่า แล้วลองใหม่
    ...
elif resp.stop_reason == "max_tokens":
    # ชน max_tokens ที่เราตั้งเอง
    ...
เข้าใจผิดบ่อย

"ถ้า input + max_tokens เกิน window ก็โดน 400 เหมือน input ใหญ่เกิน" ไม่ใช่ บนรุ่นใหม่ เฉพาะ input ที่ใหญ่เกินเท่านั้นที่ถูกปฏิเสธล่วงหน้า

สรุปสั้นๆ

Input เกิน = 400 ทันที. Input พอดีแต่บวก max_tokens เกิน = รุ่น 4.5+ รับ แล้วหยุดด้วย model_context_window_exceeded ถ้าชนจริง API ไม่ตัดประวัติให้ ต้องเช็ก stop_reason เอง

ลองเดาก่อน

บน Sonnet 5.5 คุณส่ง input ขนาด 900k token พร้อม max_tokens = 128k (รวมเกิน 1M) จะเกิดอะไรขึ้น?

  1. โดน 400 ทันทีก่อนเริ่ม generate
  2. API ลด max_tokens ให้เหลือ 100k เองแล้วจบด้วย end_turn
  3. รับ request ถ้า output ยาวจนชนเพดานจะหยุดด้วย model_context_window_exceeded
ดูเฉลย

C input 900k ยังอยู่ใน window รุ่น 4.5 ขึ้นไปรับ request และหยุดเมื่อชนเพดานจริงเท่านั้น

Checkpoint 2

สตาร์ทอัปเคยต้นแบบผู้ช่วยด้วยการคุยใน claude.ai แล้วย้ายมาเขียนแอปที่เรียก Messages API ตรง โดยเชื่อว่าบทสนทนายาวๆ จะถูกตัดรอบเก่าออกให้เองเหมือนเดิม จริงๆ แล้วเกิดอะไรขึ้น?

  1. ทุกรอบก่อนหน้าถูกส่งไปเต็มๆ แอปต้องจัดการการโตของ context เอง
  2. SDK จะตัดประวัติให้เองถ้าตั้ง max_tokens ไว้ต่ำ
  3. API ตัดรอบเก่าแบบ FIFO เหมือน claude.ai
  4. รอบที่ cache ไว้แล้วไม่ทำให้ window โตขึ้น จึงไม่ต้องห่วงเรื่องนี้
ดูเฉลย

A การตัดประวัติเป็นพฤติกรรมของแอปแชต ไม่ใช่ของ API (C) max_tokens คุมแค่ความยาว output ไม่ได้ตัด input (B) และส่วนที่ cache ก็ยังนับใน window (D) การจัดการ context เป็นหน้าที่ของแอปเรา

Checkpoint 3

ระบบสรุปเอกสารบน Opus 5.5 ส่ง input ที่ยังอยู่ใน window แต่ input + max_tokens เกิน window คาดว่าจะเกิดอะไรขึ้น?

  1. ได้ 400 ก่อนเริ่ม generate
  2. request เข้าคิวรอจนกว่าจะมี window ว่างพอ
  3. ต้องใส่ beta header ก่อนเสมอ ไม่งั้นได้ validation error
  4. รับ request และถ้าชนเพดานระหว่าง generate จะหยุดด้วย model_context_window_exceeded
ดูเฉลย

D 400 ล่วงหน้าเกิดเฉพาะเมื่อ input อย่างเดียวเกิน (A) ไม่มีระบบคิวแบบ B และ beta header จำเป็นแค่กับรุ่นก่อน 4.5 ไม่ใช่ Opus 5.5 (C)

3. Thinking token ข้ามรอบ

Thinking นับใน max_tokens คิดเงินเป็น output และนับใน rate limit ด้วย ถ้าใช้ adaptive thinking ปริมาณจะแตกต่างกันไปทุก request คำถามสำคัญคือ thinking block ของรอบ ก่อนๆ ที่เราส่งกลับไปพร้อมประวัติ เกิดอะไรขึ้นกับมัน?

รุ่นthinking block รอบก่อนผลต่อ window/บิล
Opus 4.5 ขึ้นไป, Sonnet 4.6 ขึ้นไป, Haiku 5.5, Fable, Mythosเก็บไว้ เป็นค่าเริ่มต้นนับใน window และคิดเงินเป็น input ใน request ถัดๆ ไป
Opus/Sonnet รุ่นก่อนหน้านั้น, Haiku ถึง 4.5ถูกตัดทิ้ง อัตโนมัติเมื่อส่งกลับไปไม่นับ และเราไม่ต้องตัดเอง

จ่ายสองต่อ: บนรุ่นที่เก็บ thinking ไว้ block หนึ่งถูกคิดเงินเป็น output ตอนที่สร้าง แล้วถูกคิดเงินเป็น input อีกทุกครั้ง ที่ส่งกลับไปในรอบถัดๆ ไป ในเซสชันยาวๆ (เช่น 40 รอบ) ยอดนี้พอกพูนเร็วมาก ฟีเจอร์ thinking block clearing (อยู่ในบท context editing) ปรับค่าเริ่มต้นนี้ได้ทั้งสองทาง

กฎตอนใช้ tool

เมื่อส่ง tool result กลับไป ต้องแนบ thinking block ของ assistant turn นั้นไปด้วยแบบครบ ไม่แก้ไข และมี signature นี่เป็นกรณีเดียวที่บังคับให้ส่ง thinking กลับ API จะตรวจ signature และ error ถ้า block ถูกแก้ พอจบรอบ tool แล้วเริ่ม user turn ใหม่ block นั้นไม่จำเป็นต้องอยู่ใน context อีก

Context awareness

  • รุ่นที่มี: Sonnet 5, Sonnet 4.6, Sonnet 4.5, Haiku 4.5 API จะใส่ขนาด window ทั้งหมดไว้ใน tag <budget:token_budget> และส่งคำเตือนว่าเหลือพื้นที่เท่าไรหลังการเรียก tool แต่ละครั้ง
  • รุ่นที่ไม่มี: Opus 4.7 ขึ้นไป, Sonnet 5.5, Haiku 5.5, Fable, Mythos ถ้าต้องการให้โมเดลรู้งบ ให้ตั้งงบชัดๆ ผ่าน task budgets (beta)
สรุปสั้นๆ

รุ่นใหม่เก็บ thinking เก่าไว้ = กิน window และโดนคิดเงินเป็น input ซ้ำทุกรอบ รุ่นเก่าตัดทิ้งให้เอง ตอนส่ง tool result ต้องแนบ thinking block เดิมแบบไม่แก้ไขพร้อม signature เสมอ

Checkpoint 4

ทีมย้าย agent จาก Sonnet 4.5 ไปเป็น Opus 5.5 โดยไม่แก้โค้ด client ส่ง thinking block กลับไปกับประวัติทุกรอบเหมือนเดิม แล้วพบว่า input token ต่อรอบโตเร็วกว่าเดิมมาก สาเหตุน่าจะเป็นอะไร?

  1. thinking เก่าถูกคิดเงินเป็น output ซ้ำทุกรอบ
  2. Opus 5.5 ใส่ tool definitions ซ้ำเพิ่มอีกหนึ่งชุดในประวัติทุกรอบ
  3. รุ่นใหม่เก็บ thinking block รอบก่อนไว้เป็นค่าเริ่มต้น จึงนับใน window และคิดเป็น input ซ้ำ ขณะที่รุ่นเดิมตัดทิ้งให้
  4. signature ของ thinking block มีขนาดใหญ่กว่าตัว thinking หลายเท่า
ดูเฉลย

C Opus 4.5 ขึ้นไปเก็บ thinking เก่า ส่วน Sonnet 4.5 อยู่ในกลุ่มที่ถูกตัดทิ้ง (Sonnet ที่เก็บต้อง 4.6 ขึ้นไป) A ผิดเพราะ thinking เก่าถูกคิดเป็น input ไม่ใช่ output ส่วน B และ D ไม่มีพฤติกรรมแบบนั้น

4. วัด token ก่อนและหลัง request

  • ก่อนส่ง: ใช้ token counting endpoint ซึ่งรับ input โครงสร้างเดียวกับ Messages request (system, tools, รูป, PDF) แล้วคืนจำนวน input token โดยไม่รันโมเดล
  • หลังส่ง: ดูจาก usage ใน response ซึ่งเป็นตัวเลขจริง
import anthropic

client = anthropic.Anthropic()
count = client.messages.count_tokens(
    model="claude-opus-5-5",
    system="คุณคือผู้ช่วยตอบคำถามเรื่องภาษี",
    messages=[{"role": "user", "content": "สวัสดี"}],
)
print(count.input_tokens)   # เช่น 21
ข้อเท็จจริงสำคัญ

เมื่อใช้ caching input จะแตกเป็น 3 ช่อง: input_tokens, cache_read_input_tokens, cache_creation_input_tokens ทั้งสามนับใน window dashboard ที่รวมแค่ input_tokens จะรายงานต่ำกว่าจริงมาก

u = resp.usage
total_input = (u.input_tokens
               + u.cache_read_input_tokens
               + u.cache_creation_input_tokens)

ข้อจำกัดของการนับล่วงหน้า

  • ตอบ invalid_request_error ถ้า request มี server tool (เช่น web search, code execution), MCP connector หรือรูป/เอกสารที่อ้างผ่าน URL หรือ file source ให้ส่งรูปและ PDF แบบ base64 แทน ส่วน request ที่ใช้ server tool ให้อ่าน usage จาก response จริง
  • เป็นค่าประมาณที่ ไม่มี logic ของ caching ใส่ cache_control ได้แต่ไม่มีผลอะไร
  • ใช้ tokenizer ของรุ่นที่ระบุ Fable และ Mythos ใช้ tokenizer ที่มากับ Opus 4.7 ซึ่งได้จำนวน token มากกว่ารุ่นก่อน 4.7 ราว 30% ข้อความเดียวกันจึงนับไม่เท่ากัน ควรนับเทียบทั้งสองรุ่นก่อนย้าย
  • ใช้ฟรี แต่จำกัดจำนวน request ต่อนาทีตาม usage tier (เช่น 5,000 RPM ที่ tier Start)
เข้าใจผิดบ่อย

"count_tokens ใช้ได้กับทุก request" ไม่ใช่ server tool, MCP connector และรูป/เอกสารแบบ URL หรือ file source ใช้ไม่ได้

สรุปสั้นๆ

ก่อนส่งใช้ count_tokens (ไม่รองรับ server tool/MCP/URL source ไม่รู้เรื่อง cache) หลังส่งใช้ usage และรวมทั้ง 3 ช่อง input เสมอ

Checkpoint 5 (เติมคำ)

อยากรู้จำนวน input token ของ request ก่อนส่งจริง โดยไม่ให้โมเดลรัน ต้องเรียก client.messages.____(...)

  1. create
  2. preview
  3. count_tokens
  4. measure_input
ดูเฉลย

C create คือการส่ง request จริงซึ่งรันโมเดลและเสียเงิน อีกสองชื่อไม่มีอยู่จริง

Checkpoint 6

agent ช่วยเขียนโค้ดใช้ code execution (server tool) และ cache system prompt ไว้ ทีม FinOps อยากบันทึกจำนวน input token จริงของทุก request วิธีไหนถูกต้อง?

  1. ประมาณจากจำนวนตัวอักษรหาร 4 แล้วบวกขนาด system prompt
  2. อ่าน usage.input_tokens จาก response อย่างเดียว
  3. เรียก count_tokens แค่ครั้งแรกของเซสชัน แล้วคูณด้วยจำนวนรอบ
  4. อ่าน usage จาก response แล้วรวม input_tokens + cache_read_input_tokens + cache_creation_input_tokens
ดูเฉลย

D ตัวเลขจริงอยู่ใน usage และต้องรวมทั้ง 3 ช่อง B ขาดส่วนที่ cache ไป A เป็นการเดา และ C ใช้ไม่ได้ทั้งเพราะ count_tokens ไม่รองรับ server tool และเพราะประวัติโตขึ้นทุกรอบ

5. ลดต้นทุนจาก tool ใน context

ใน agent ส่วนใหญ่ของ window ถูกใช้ไปกับ tool: definitions ถูกส่งทุก request และการเรียกแต่ละครั้งเพิ่ม tool_result เข้าไปในประวัติ ต้องดูว่าแรงกดดันมาจากไหน แล้วเลือกเทคนิคให้ตรง

เทคนิคลดอะไรเหมาะกับ
Tool searchdefinitions ที่โหลดไว้ล่วงหน้ามี tool 20+ ตัว แต่แต่ละรอบใช้ไม่กี่ตัว
Programmatic tool callingtool_result ไป-กลับระหว่างทางการเรียกต่อกันเป็นสายที่รวมเป็น script เดียวได้
Prompt cachingราคาของ definitions ที่ส่งซ้ำ (พื้นที่ใน window เท่าเดิม)ชุด tool คงที่ ใช้ข้าม request จำนวนมาก
Context editingtool_result เก่าในประวัติบทสนทนายาวที่ผลช่วงต้นไม่สำคัญแล้ว
  • Tool search: ส่งไปแค่ tool ชื่อ tool_search ตัวเดียว Claude ค้นหา tool อื่นเมื่อต้องใช้ แลกกับ latency เพิ่มหนึ่งรอบ
  • Programmatic tool calling: Claude เขียนโค้ดหนึ่งก้อนที่เรียก tool เล็กๆ หลายตัวต่อกันใน sandbox ผลระหว่างทางไม่ย้อนกลับเข้าบทสนทนา ได้กลับมาแค่ผลสุดท้าย
  • Prompt caching: definitions ที่ส่งซ้ำถูกลง แต่ยังกินพื้นที่

สิ่งที่ไม่ช่วย: ย้ายไปรุ่น 1M, เพิ่ม max_tokens หรือย่อชื่อ tool พวกนี้ไม่ลดภาระ definitions ไม่ลดรอบไป-กลับ และไม่ลดราคาที่จ่ายซ้ำ window ที่ใหญ่ขึ้นแต่เต็มไปด้วย tool ชุดเดิมก็ยังเจอ context rot (คุณภาพตกเมื่อ context ยาว)

ทางแก้เชิงโครงสร้าง: โยนงานสำรวจที่ verbose ไปให้ subagent ที่มี window ของตัวเอง แล้วส่งกลับมาแค่ผลที่ย่อแล้ว (ดูบท 1.4)

สรุปสั้นๆ

Definitions เยอะ → tool search. เรียกต่อกันเป็นสาย → programmatic tool calling. Definitions ซ้ำแพง → caching (ไม่คืนพื้นที่). ผลเก่าค้าง → context editing. Window ใหญ่ขึ้นไม่ใช่คำตอบ

Checkpoint 7 (จับคู่)

จับคู่เทคนิคกับแรงกดดันที่มันลด:

  1. Tool search
  2. Programmatic tool calling
  3. Prompt caching
  4. Context editing

A = ผลระหว่างทางจากการเรียก tool ต่อกันเป็นสาย · B = schema ที่ถูกโหลดล่วงหน้าทุก request · C = tool_result เก่าที่ค้างในประวัติ · D = ราคาของ definitions ที่ส่งซ้ำ (พื้นที่ไม่ลด)

ดูเฉลย

1-B, 2-A, 3-D, 4-C caching เป็นตัวเดียวที่ลดแค่ราคา ไม่คืนพื้นที่ใน window

Checkpoint 8 (เลือก 3 ข้อ)

agent ฝ่ายปฏิบัติการมี tool 60 ตัว ปัญหาคือ (1) schema ที่ไม่ได้ใช้ถูกโหลดทุก request (2) เรียก tool เล็กๆ ต่อกันหลายครั้ง ผลระหว่างทางค้างอยู่ในประวัติ (3) definitions ชุดเดิมถูกคิดราคาเต็มทุก request ข้อไหนแก้ได้ตรงจุด?

  1. ย้ายไปรุ่น 1M โดยไม่แตะชุด tool
  2. เปิด prompt caching ให้ definitions
  3. เขียนใน system prompt ว่า "ใช้ tool ให้น้อยที่สุด"
  4. ใช้ tool search
  5. ส่ง tool definitions ซ้ำสองชุดเพื่อให้ cache hit ง่ายขึ้น
  6. ใช้ programmatic tool calling
ดูเฉลย

B, D, F แต่ละข้อแก้ปัญหาหนึ่งข้อ: tool search → (1), programmatic → (2), caching → (3) ข้อ A แค่เพิ่มที่ว่างแต่ไม่ลดต้นเหตุ C ไม่ได้เอา definitions ออกจาก context E ยิ่งเพิ่ม token เป็นสองเท่า
