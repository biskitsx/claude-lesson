4.5 ลดต้นทุนและ latency ของ Claude: free wins, batching และ budget

ต้นฉบับ: CertSafari 4.5

อ่านจบแล้วควรทำได้
  • แยก "free wins" (ประหยัดโดยไม่เสียคุณภาพ) ออกจาก "trade-offs" (ประหยัดแลกกับอะไรบางอย่าง)
  • อธิบายได้ว่าทำไม prompt caching คือตัวคุมต้นทุนหลักของ agent loop และอ่านค่า cache hit ได้
  • เลือกระหว่าง cache 5 นาทีกับ 1 ชั่วโมงจากรูปแบบช่วงเวลาระหว่าง request
  • รู้ว่า Message Batches เหมาะกับงานแบบไหน และมีข้อจำกัดอะไร
  • ตั้งขอบเขตการใช้จ่ายด้วย max_tokens, session budget, spend limit และนโยบาย re-run
แนวคิดหลัก: เก็บของฟรีก่อน แล้วค่อยต่อรอง

คันโยกลดต้นทุนมีสองกลุ่ม กลุ่มแรก ฟรี คือประหยัดได้โดยคุณภาพเท่าเดิม กลุ่มสอง trade-off คือได้ส่วนลดแต่ต้องแลกกับคุณภาพ ความเร็ว หรือความสำเร็จของ task ให้ใช้กลุ่มแรกให้หมดก่อน และทุกคันโยกต้องวัดผลกับ workload ของเราเอง

Checkpoint 1 (จัดกลุ่ม)

จัดคันโยกต่อไปนี้ว่าเป็น free win (F) หรือ trade-off (T):

  1. ใส่ cache_control บน system prompt ยาว
  2. ลด effort จาก high เป็น low

ดูเฉลย

1-F, 2-T, 3-F, 4-T, 5-T batching ยอมรอแต่ไม่เสียคุณภาพ ส่วน effort, รุ่น และ cap แลกกับความสามารถหรือ run ที่ไม่จบ

2. ทำไม caching คุมต้นทุนของ agent loop

ใน agent loop ทุกรอบต้องส่ง history ทั้งหมดกลับไปใหม่ รอบที่ 10 ส่ง 10 รอบก่อนหน้า รอบที่ 20 ส่ง 20 รอบ ต้นทุนรวมจึงโตประมาณ กำลังสองของจำนวนรอบ caching ไม่ได้หยุดการส่งซ้ำ แต่ทำให้ส่วนที่ส่งซ้ำ ราคาถูกลงมาก

รายการราคาเทียบกับ input ปกติ
Cache read (โมเดลส่วนใหญ่)ประมาณ 1/10
Cache read บน Claude Opus 5.5 และ Sonnet 5.51/20
Cache read บน Claude Fable 5.1 และ Mythos 5.11/40
Cache write (5 นาที)1.25x

ผลวัดจริงของต้นทุนเมื่อ ไม่ใช้ caching เทียบกับใช้:

Workloadไม่ cache แพงกว่า
SWE-bench Pro บน Opus 5.53.3x
SWE-bench Pro บน Sonnet 5.53.1x
Managed Agents session สั้นบน Haiku 5.51.7x
agent คัดแยก bug ขนาดเล็กบน Sonnet 5.57.3x
ตัวเลขสุขภาพ

agent loop ที่ปกติอ่าน input จาก cache ได้ค่ามัธยฐาน 84% ถ้าต่ำกว่าราว 80% แปลว่ามีอะไรบางอย่างทำให้ prefix ไม่ตรงกัน เช่น timestamp ใน system prompt, ลำดับ tool ที่สลับไปมา หรือเนื้อหาที่หมุนเวียน

หัวใจคือ prefix ต้องตรงกันทุก byte ดังนั้นวางของที่นิ่งไว้ข้างหน้า แล้ววาง breakpoint cache_control ไว้หลังส่วนที่นิ่ง:

system = [
    {"type": "text",
     "text": PRODUCT_MANUAL,                     # ~30,000 token ไม่เปลี่ยน
     "cache_control": {"type": "ephemeral"}},
]
messages = [{"role": "user", "content": question}]   # ส่วนที่เปลี่ยนทุกครั้งอยู่หลัง breakpoint

สิ่งที่ ไม่ช่วย: ย้ายคู่มือไปไว้หลังเนื้อหาที่เปลี่ยน (prefix จะไม่ตรงทุกครั้ง), หมุนเวียนชิ้นส่วนของ prompt, หรือลด max_tokens (คุมแค่ output ไม่ได้ลดการประมวลผล input)

เข้าใจผิดบ่อย

"cache hit ต่ำ เพราะ cache หมดอายุ" ถ้าแต่ละรอบห่างกันแค่ไม่กี่วินาที อายุ cache ไม่ใช่ปัญหา ให้หาสิ่งที่ทำให้ prefix เปลี่ยน

สรุปสั้นๆ

agent loop ต้นทุนโตแบบกำลังสอง caching ทำให้ส่วนซ้ำถูกลง 10–40 เท่า · hit ปกติ ~84% ต่ำกว่า 80% = prefix พัง · ของนิ่งไว้หน้า + cache_control

Checkpoint 2

agent เขียนโค้ดของทีมอ่าน input จาก cache ได้แค่ 58% ทั้งที่แต่ละรอบห่างกันไม่กี่วินาที ควรสืบอะไรก่อน?

  1. เปลี่ยนเป็น cache 1 ชั่วโมง
  2. หาสิ่งที่ทำให้ prefix เปลี่ยนระหว่างรอบ เช่น timestamp หรือลำดับ tool ที่ไม่คงที่
  3. ลด max_tokens
  4. ปิด caching เพราะไม่คุ้ม
ดูเฉลย

B รอบห่างกันไม่กี่วินาที cache ไม่ได้หมดอายุ hit rate ต่ำกว่า 80% ชี้ว่า prefix ไม่ตรงกัน ส่วน max_tokens ไม่เกี่ยวกับ cache

Checkpoint 3

bot ซัพพอร์ตแนบคู่มือนโยบาย 25,000 token ที่ไม่เปลี่ยนเลยไปกับทุกคำถาม วิธีไหนลดต้นทุน input ได้จริง?

  1. วาง breakpoint cache_control แบบ ephemeral หลังคู่มือ ให้ request ถัดไปอ่านจาก cache
  2. แบ่งคู่มือเป็น 5 ชิ้นแล้วสุ่มส่งชิ้นละครั้ง
  3. ย้ายคู่มือไปไว้หลังคำถามของผู้ใช้
  4. ลด max_tokens เหลือ 300
ดูเฉลย

A B ทำให้ prefix เปลี่ยนตลอดและเสียข้อมูล C ทำให้ prefix ต่างกันทุกคำถาม D ไม่ได้ลดการประมวลผล input

3. เลือก cache 5 นาที หรือ 1 ชั่วโมง

  • ค่า default 5 นาที และนาฬิกาจะรีเฟรชฟรีทุกครั้งที่มีการอ่าน
  • แบบ 1 ชั่วโมง ตั้งด้วย "ttl": "1h" ค่าเขียนแพงขึ้นเป็น 2x ของ input (จาก 1.25x)
  • ถ้า miss ไม่ว่าแบบไหน จะโดนคิด prefix ทั้งก้อนในราคา write
{"type": "text", "text": KNOWLEDGE_BASE,
 "cache_control": {"type": "ephemeral", "ttl": "1h"}}

เลือกจาก รูปแบบช่องว่างระหว่าง request ไม่ใช่ความยาวของ session:

สถานการณ์ผลที่วัดได้
ราว 1 ใน 20 ของช่องว่างยาว 5 นาที–1 ชั่วโมงcache 1 ชั่วโมงคุ้ม (จุดคุ้มทุนที่วัดได้ราว 1 ใน 30)
1 ใน 10 ของช่องว่างยาว 5 นาที–1 ชั่วโมงถ้ายังใช้ 5 นาที แพงกว่าถึง 54%
ทุกรอบห่างกันไม่กี่วินาที5 นาทีถูกกว่า 1 ชั่วโมงราว 19% (บน Sonnet 5.5)

ทางเลือก: keep-alive

แทนที่จะจ่าย 1 ชั่วโมง อาจส่ง request เดิมซ้ำเพื่อต่ออายุ cache โดยตั้ง max_tokens: 0 ไม่ใช้ stream prefix ตรงเดิมทุก byte และ header เดิม ส่งภายใน 4 นาที และทุก 4 นาทีหลังจากนั้น

แต่จะถูก ปฏิเสธ ถ้า request ใช้ thinking.type: "enabled", structured outputs, forced tool choice หรือ compaction ระดับบนสุด

keepalive = {**last_request, "max_tokens": 0}   # prefix และ header เดิมทุกอย่าง
keepalive.pop("stream", None)
# ส่งภายใน 4 นาที แล้วทุก 4 นาที
เข้าใจผิดบ่อย

"session ยาวหลายชั่วโมง ต้องใช้ cache 1 ชั่วโมง" ไม่ใช่ สิ่งที่ตัดสินคือช่องว่างระหว่าง request ถ้าทุกรอบห่างกันไม่กี่วินาที 5 นาทีก็รีเฟรชตัวเองตลอดและถูกกว่า

สรุปสั้นๆ

5 นาที: write 1.25x รีเฟรชฟรีเมื่ออ่าน · 1 ชม.: write 2x · ดูสัดส่วนช่องว่าง 5 นาที–1 ชม. (คุ้มเมื่อเกินราว 1 ใน 30) · keep-alive ด้วย max_tokens: 0 ทุก 4 นาที มีข้อห้ามหลายข้อ

Checkpoint 4

agent วิเคราะห์ข้อมูลรันต่อเนื่อง 3 ชั่วโมง แต่ละรอบห่างกัน 5–20 วินาที ไม่เคยหยุดนานกว่านั้น ควรใช้ cache แบบไหน?

  1. คงค่า default 5 นาที
  2. เปลี่ยนเป็น 1 ชั่วโมง เพราะ session ยาวกว่า 1 ชั่วโมง
  3. ปิด cache แล้วใช้ keep-alive แทน
  4. ใช้ 1 ชั่วโมงแล้วส่ง keep-alive ทุก 4 นาทีด้วย
ดูเฉลย

4. Token hygiene

ตัดคำสั่งที่ซ้ำซ้อนและ output ที่เยิ่นเย้อ Claude จะ ไม่เดาเติม คำสั่งที่ไม่ชัด ดังนั้นให้เขียนชัดแต่กระชับ และ audit prompt ที่เขียนไว้สำหรับรุ่นเก่าใหม่ทุกครั้งที่ย้ายรุ่น

การตัด input: ย่อขนาดรูปภาพ และเลื่อนการโหลด tool definition ด้วย tool search (ไม่ต้องแนบทุก tool ตั้งแต่แรก) ลดต้นทุนได้ 26% (run 20 issue) และ 21% (run ที่ยาวกว่า) เพิ่มเติมจาก caching

คันโยกสำหรับ session ยาว

คันโยกทำอะไรตัวอย่างค่าที่ใช้
Context editingล้างผลของ tool เก่าๆ ทิ้งเมื่อเกิน thresholdเมื่อ prompt เกิน 20,000 token ให้ล้างอย่างน้อย 2,000 token โดยเก็บ tool use ล่าสุด 3 ครั้ง
Compactionย่อ history ให้สั้นลงtrigger ที่ 50,000 input token ในงานหนึ่ง
Memory toolเก็บ state ที่ต้องอยู่รอดหลังการล้าง/ย่อบันทึกความคืบหน้าลงไฟล์
ข้อควรระวัง: context editing ไม่ได้ฟรีเสมอ

ใน run ที่ Anthropic วัดไว้ context editing แพงกว่าที่ประหยัดได้ เพราะการล้างเนื้อหาทำให้ prompt เปลี่ยน cache ตั้งแต่จุดนั้นเป็นต้นไปจึงใช้ไม่ได้ ต้องวัด ต้นทุนต่อ task ทั้งแบบเปิดและปิดก่อนตัดสินใจ

เข้าใจผิดบ่อย

"ลด effort แล้ว context จะไม่เต็ม" ไม่ใช่ effort ไม่ได้หยุดการสะสมของ history

"ย้าย session ยาวไป Batches ช่วยเรื่อง context" ไม่ใช่ batch ไม่ได้ถือ session ที่โต้ตอบสดๆ

สรุปสั้นๆ

คำสั่งชัดแต่สั้น · ย่อรูป + tool search ลดได้อีก 21–26% บนยอด caching · session ยาวใช้ context editing / compaction / memory tool แต่ context editing ทำ cache พัง ต้องวัดต้นทุนต่อ task

Checkpoint 5

ทีมเปิด context editing ใน agent ที่ใช้ caching หนัก แล้วอยากรู้ว่าคุ้มไหม ควรทำอะไร?

  1. ดูว่า context window เต็มช้าลงไหม ถ้าใช่ก็คุ้ม
  2. วัดต้นทุนต่อ task ทั้งแบบเปิดและปิด context editing แล้วเทียบกัน
  3. เปิดไว้เสมอ เพราะ token น้อยลงย่อมถูกลง
  4. ลด effort ควบคู่ไปด้วย
ดูเฉลย

B การล้างเนื้อหาทำให้ cache หลังจุดนั้นใช้ไม่ได้ ต้นทุนรวมอาจสูงขึ้น ต้องวัดจริงด้วยต้นทุนต่อ task

agent รีวิวโค้ดทำงานยาวหลายชั่วโมงจน context ใกล้เต็ม เครื่องมือไหนช่วยจัดการ context ที่โตขึ้นได้ (เลือกทุกข้อที่ถูก)

  1. Server-side compaction
  2. Context editing
  3. Memory tool

5. Message Batches สำหรับงานที่รอได้

Batches API คิดราคา 50% ของราคาปกติ ส่ง request เป็นชุด แต่ละตัวมี custom_id แล้ว poll ดูผล

หัวข้อรายละเอียด
เวลาส่วนใหญ่เสร็จภายใน 1 ชั่วโมง รับประกันภายใน 24 ชั่วโมง
เก็บผล29 วัน
ขนาดต่อ batchสูงสุด 100,000 request หรือ 256 MB
ไม่รองรับstream: true และ Fast mode (speed)
max_tokensต้องอย่างน้อย 1 จึงใช้ max_tokens: 0 pre-warm cache ไม่ได้
Spend limitอาจเกินไปเล็กน้อย
client.messages.batches.create(requests=[
    {"custom_id": f"ticket-{t.id}",
     "params": {"model": MODEL, "max_tokens": 512,
                "messages": [{"role": "user", "content": t.text}]}}
    for t in archived_tickets
])

งานที่เหมาะ: ให้คะแนน ticket เก่า 50,000 ใบตอนกลางคืนโดยไม่มีใครนั่งรอ งานที่ไม่เหมาะ: แชตสด หรืออะไรที่ผู้ใช้รอคำตอบ

เข้าใจผิดบ่อย

"Batch เร็วกว่าเพราะประมวลผลพร้อมกัน" ไม่ใช่ batch แลก latency กับราคา ไม่ได้เร็วขึ้น

สรุปสั้นๆ

ลด 50% · ส่วนใหญ่ < 1 ชม. รับประกัน 24 ชม. · ผลเก็บ 29 วัน · 100,000 request / 256 MB · ห้าม stream, Fast mode, max_tokens: 0

Checkpoint 7

ข้อไหน ถูกต้อง เกี่ยวกับ Message Batches? (เลือกทุกข้อที่ถูก)

  1. request ที่ตั้ง stream: true จะถูกปฏิเสธ
  2. ผลอาจใช้เวลาถึง 24 ชั่วโมง
  3. ใช้ max_tokens: 0 เพื่อ pre-warm cache ได้
  4. Fast mode (speed) ใช้ร่วมกับ batch ไม่ได้
  5. batch เร็วกว่าเรียก API ปกติ
ดูเฉลย

A, B, D max_tokens ใน batch ต้องอย่างน้อย 1 (C ผิด) และ batch แลกความเร็วกับราคา (E ผิด)

ทุกคืนทีมต้องจัดหมวดรีวิวสินค้า 80,000 รายการเพื่อใช้ในรายงานตอนเช้า ไม่มีใครรอผลแบบ real-time วิธีไหนประหยัดที่สุดโดยไม่เสียคุณภาพ?

  1. ส่งผ่าน Message Batches API
  2. ใช้ Fast mode เพื่อให้เสร็จเร็ว
  3. ลด effort เป็น low ทุก request
  4. เปลี่ยนไปใช้รุ่นเล็กที่สุดโดยไม่ทดสอบ
ดูเฉลย

A งานรอได้ ปริมาณอยู่ในขีดจำกัด ได้ส่วนลด 50% โดยคุณภาพเท่าเดิม C และ D เป็น trade-off ที่ยังไม่ได้วัด B ยิ่งแพงขึ้น

6. คันโยกแบบ trade-off: effort และรุ่นโมเดล

เมื่อเก็บ free wins หมดแล้ว ค่อยลอง ลด effort ตัวอย่างบน DRACO: Opus 5.5 ที่ effort low ใช้เวลาน้อยกว่า medium ถึง 84% แต่คะแนนต่ำลง 13.3 จุด ถ้าลดแล้วคุณภาพตก ให้คืน effort ก่อนลองวิธีอื่น

สำหรับ รุ่นโมเดล:

  • เทียบด้วย ต้นทุนต่อ task ที่ทำสำเร็จ ไม่ใช่ราคาต่อ token รุ่นถูกที่ต้อง retry บ่อยอาจแพงกว่า
  • งานปริมาณสูงที่ตรวจผลได้ ลอง Haiku 5.5 ก่อน
  • การอัปเกรดเป็นรุ่นใหม่กว่า แทบไม่มีต้นทุนเพิ่ม ในการวัดของ Anthropic ถ้ายังไม่ได้อยู่รุ่นล่าสุด ควรอัปเกรด
สรุปสั้นๆ

effort low เร็วขึ้นมากแต่คะแนนลด (DRACO: −84% เวลา, −13.3 จุด) · คุณภาพตก → คืน effort · เทียบต้นทุนต่อ task สำเร็จ · งานตรวจได้ปริมาณสูง → Haiku 5.5 · อยู่รุ่นเก่า → อัปเกรด

Checkpoint 9 (จับคู่)

จับคู่สถานการณ์กับการกระทำที่ถูก:

  1. ลด effort ไปเมื่อสัปดาห์ก่อน แล้วอัตรางานผ่านตกลง
  2. รุ่น A ราคาต่อ token ถูกกว่ารุ่น B ครึ่งหนึ่ง แต่ต้อง retry บ่อยกว่ามาก
  3. งานแท็กภาษาของข้อความหลายล้านรายการต่อวัน ตรวจผลด้วยโค้ดได้
  4. ระบบยังใช้รุ่นที่ออกมาก่อนรุ่นปัจจุบันหนึ่งรุ่น

ตัวเลือก: A) ลอง Haiku 5.5 พร้อม eval · B) อัปเกรดเป็นรุ่นล่าสุด · C) คืน effort เดิม · D) เทียบด้วยต้นทุนต่อ task ที่สำเร็จ

ดูเฉลย

1-C, 2-D, 3-A, 4-B

7. ตั้งขอบเขตการใช้จ่าย

max_tokens คือ เพดานแข็ง ของ thinking + ข้อความตอบรวมกัน ไม่ใช่เป้าที่โมเดลพยายามเขียนให้ถึง ถ้าตั้งต่ำเกิน run จะถูกตัดกลางคันและเสียเงินฟรี คำแนะนำคือ ตั้งไว้ที่ 64,000: ในการทดสอบของ Anthropic มีเพียง 2 จากราว 14,000 turn ที่เกินค่านี้ และต้นทุนต่อ task ที่สำเร็จแทบไม่เปลี่ยน

การคุมการใช้จ่ายของ agent ราคาแพงมีหลายชั้น:

  • Session budget ของ Managed Agents จำกัดต่อ session
  • Workspace spend limit เป็นตาข่ายรองรับระดับบัญชี
  • Task budget (beta) สำหรับโมเดลรุ่นใหม่
  • บอกเวลาที่ผ่านไปให้โมเดลรู้ ลดเวลารันได้ 7%–47% แลกกับคะแนนลดลงไม่กี่จุด

นโยบาย re-run: low ก่อน แล้ว re-run ที่ high

รันทุก task ที่ effort low ก่อน แล้วเอาเฉพาะตัวที่ fail ไปรันใหม่ที่ high ใช้ได้ก็ต่อเมื่อมีการตรวจอัตโนมัติ (เทสต์ หรือ verifier) บอกได้ว่าตัวไหน fail

นโยบายอัตราสำเร็จต้นทุนต่อ task
Low + re-run ตัวที่ fail ที่ high~97%~$0.17
High ทุกตัว95.3%$0.29
Medium + re-run ตัวที่ fail ที่ high~97%~$0.24
results = {t.id: run(t, effort="low") for t in tasks}
failed = [t for t in tasks if not tests_pass(results[t.id])]   # ต้องมีตัวตรวจอัตโนมัติ
for t in failed:
    results[t.id] = run(t, effort="high")

งานปลายเปิดอย่างการเขียนข้อความการตลาดไม่มีตัวตรวจอัตโนมัติ นโยบายนี้จึงใช้ไม่ได้

เข้าใจผิดบ่อย

"ตั้ง max_tokens ต่ำๆ ไว้ ประหยัดเงิน" ไม่ใช่ มันเป็นเพดาน ไม่ใช่เป้า ตั้งต่ำเกินทำให้ run ถูกตัดและต้องรันใหม่ ตั้ง 64,000 แล้วต้นทุนต่อ task แทบเท่าเดิม

"re-run ที่ high ใช้ได้กับทุกงาน" ไม่ใช่ ต้องมีตัวตรวจอัตโนมัติชี้ว่าอะไร fail

สรุปสั้นๆ

max_tokens = เพดาน ตั้ง 64,000 · คุมด้วย session budget, spend limit, task budget, บอกเวลาที่ผ่านไป · low + re-run fail ที่ high ถูกและดีกว่า high ทั้งหมด แต่ต้องมีตัวตรวจอัตโนมัติ

Checkpoint 10

agent แก้ bug ของทีมตั้ง max_tokens: 4096 พบว่าหลาย run ถูกตัดกลางทางขณะกำลัง thinking ต้องรันใหม่บ่อย ควรทำอะไร?

  1. เพิ่ม max_tokens เป็น 64,000
  2. ลด max_tokens ลงอีกเพื่อบังคับให้คิดสั้น
  3. ปิด thinking ทั้งหมด
  4. ย้ายไป Batches API
ดูเฉลย

A max_tokens เป็นเพดานของ thinking + คำตอบ การตั้งต่ำทำให้ run เสียเปล่า ที่ 64,000 แทบไม่มี turn เกิน และต้นทุนต่อ task สำเร็จใกล้เดิม

  1. ทั้งสองงาน
  2. เฉพาะงานแก้ bug เพราะมีเทสต์บอกว่าตัวไหน fail
  3. เฉพาะงานคำโปรย เพราะงานสร้างสรรค์ต้องใช้ effort สูง
  4. ไม่ได้ทั้งคู่ ต้องรัน high ทั้งหมดเสมอ
