1.3 Workflow, agent and augmented LLM patterns for Claude

ต้นฉบับ: CertSafari 1.3

อ่านจบแล้วควรทำได้
  • อธิบายได้ว่า augmented LLM คือหน่วยพื้นฐานที่ทุก pattern เอามาต่อกัน
  • แยก workflow กับ agent ด้วยคำถามเดียว: ใครเป็นคนตัดสินขั้นต่อไป
  • เริ่มจากการเรียกครั้งเดียวที่จูนดีแล้ว และเพิ่มความซับซ้อนเมื่อวัดได้ว่าไม่พอ
  • เลือกระหว่าง prompt chaining, routing, parallelization (sectioning / voting) และ orchestrator-workers
  • รู้ว่าเมื่อไหร่ evaluator-optimizer คุ้ม และเมื่อไหร่ควรใช้ programmatic gate แทน
แนวคิดหลัก: ใครคุมขั้นต่อไป

ใน workflow โค้ดของเรากำหนดเส้นทางไว้ตายตัว ใน agent โมเดลเลือก action ถัดไปเองตอนรัน โดยดูจากผลของ tool

1. Augmented LLM: อิฐก้อนพื้นฐาน

ทุก pattern ในบทนี้สร้างจากหน่วยเดียวกัน คือ การเรียกโมเดลหนึ่งครั้งที่เสริมด้วย retrieval, tools และ memory ตัวโมเดลเป็นคนเขียน search query เอง เลือก tool เอง และตัดสินว่าข้อมูลไหนควรเก็บไว้ pattern ต่างๆ แค่เอาอิฐพวกนี้มาเรียงต่อกัน ไม่ได้มาแทนที่มัน

หลักการเสริมความสามารถ:

  • ตรงกับ use case: ผู้ช่วยซัพพอร์ตต้องการ tool ค้นคำสั่งซื้อ ไม่ใช่ web crawler
  • Interface ชัดและมีเอกสารดี: ชื่อ tool คำอธิบาย และ parameter ต้องอ่านแล้วรู้ว่าใช้ตอนไหน
สรุปสั้นๆ

Augmented LLM = LLM + retrieval + tools + memory ที่โมเดลใช้เองได้ ให้เฉพาะความสามารถที่งานต้องใช้ พร้อม interface ที่ชัด

Checkpoint 1

ทีมทำผู้ช่วยตอบคำถามเรื่องสวัสดิการพนักงาน ต้องอ้างอิงคู่มือสวัสดิการ 300 หน้าที่อัปเดตทุกปี วิธีไหนเหมาะที่สุด?

  1. ไม่ต้องเสริมอะไร ปล่อยให้ pattern workflow จัดการเอง
  2. ให้โค้ดค้นคู่มือด้วยคำถามผู้ใช้ตรงๆ แล้วแปะผลลง prompt ทุกครั้ง
  3. ต่อทุก tool ที่บริษัทมีเข้าไป เผื่อได้ใช้
  4. ให้โมเดลมี tool ค้นคู่มือที่มีคำอธิบายชัดเจน แล้วให้โมเดลเขียน query เอง
ดูเฉลย

D A: pattern ไม่ได้ให้ความสามารถเสริมมาเอง B: ตัดโอกาสที่โมเดลจะเขียน query ที่ดีกว่าเอง C: ไม่ได้เลือกให้ตรงกับ use case

2. Workflow กับ agent: ใครตัดสินขั้นต่อไป

การมี tool หรือการเรียก LLM หลายครั้ง ไม่ได้ทำให้ระบบเป็น agent สิ่งที่ตัดสินคือใครเลือกขั้นถัดไป

Agent loop ของ Agent SDK: Claude ขอ tool → SDK รัน tool → ผลกลับไปให้ Claude → วนจน Claude ตอบโดยไม่มี tool call เพื่อให้ agent ยังอยู่ในการควบคุม ต้องมี stopping condition เช่นจำนวนรอบสูงสุด

คุณสมบัติWorkflowAgent
ใครตัดสินขั้นต่อไปเส้นทางที่โค้ดกำหนดไว้โมเดล ตอนรัน ตามผลของ tool
ความคาดเดาได้สูง สำหรับงานที่นิยามชัดต่ำกว่า จำนวน turn แปรผัน
ต้นทุนและความเสี่ยงจำกัดอยู่ที่จำนวนครั้งที่เราเขียนไว้สูงกว่า และ error อาจสะสมทบต้น (compounding)
ชนะเมื่อรู้ขั้นตอนล่วงหน้าปัญหาปลายเปิดที่ขั้นตอนเดาไม่ได้

ตัวอย่าง agent: งานแก้บั๊กที่รันเทสต์ อ่านไฟล์ แก้ แล้วรันเทสต์ใหม่จนผ่าน หรือโจทย์แบบ SWE-bench ที่ต้องแก้หลายไฟล์ ตัวอย่าง workflow: ดึงข้อมูลใบแจ้งหนี้ → ตรวจ → ร่างอีเมล ตามลำดับเดิมทุกครั้ง

ลองเดา: ระบบเรียก LLM 3 ครั้งและมี tool ค้นหา เป็น agent หรือไม่? ยังตอบไม่ได้จนกว่าจะรู้ว่า ใคร เลือกขั้นต่อไป ถ้าโค้ดเรียง 3 ครั้งไว้แล้วก็เป็น workflow

สรุปสั้นๆ

นับ tool หรือนับจำนวนครั้งที่เรียก LLM ไม่ได้ช่วยตัดสิน ให้ดูว่าเส้นทางอยู่ในโค้ดหรืออยู่ในมือโมเดล

Checkpoint 2

ระบบรับใบสมัครงาน: LLM ดึงข้อมูลจาก resume → LLM เทียบกับ requirement โดยเรียก tool ดูตำแหน่งงาน → LLM ร่างอีเมลตอบ ทุกใบผ่าน 3 ขั้นนี้ตามลำดับเดิม และมีเพดาน 5 รอบต่อขั้น ระบบนี้คืออะไร?

  1. Agent เพราะเรียก LLM 3 ครั้ง
  2. Agent เพราะมีการใช้ tool
  3. Agent ที่คาดเดาได้ เพราะมีเพดานจำนวนรอบ
  4. Workflow เพราะลำดับขั้นถูกโค้ดกำหนดไว้
ดูเฉลย

D จำนวนครั้งที่เรียก การมี tool หรือการมี stopping condition ไม่มีข้อไหนทำให้เส้นทางกลายเป็นทางเลือกของโมเดล

3. เริ่มง่ายๆ แล้วเพิ่มความซับซ้อนเมื่อคุ้ม

  1. เริ่มจาก การเรียกครั้งเดียวที่ปรับดีแล้ว (มี retrieval และตัวอย่างใน prompt)
  2. เพิ่ม workflow เมื่อวัดได้ว่าการเรียกครั้งเดียวไม่พอ ในงานที่นิยามชัด
  3. ใช้ agent เมื่องานต้องการความยืดหยุ่นและให้โมเดลตัดสินเอง

ระวัง framework: บางตัวซ่อน prompt และ response จริงจนดีบักยาก หลาย pattern เขียนได้ในไม่กี่บรรทัดบน API ตรงๆ

ลองกับงานตัวเอง: นึกถึงฟีเจอร์ LLM หลายขั้นที่เคยเห็น แล้วถามว่าต้องวัดอะไร ถึงจะรู้ว่าแค่เรียกครั้งเดียวพร้อม retrieval ก็พอแล้ว

เข้าใจผิดบ่อย

"Agent เก่งกว่า workflow ดังนั้นตั้ง default เป็น agent ไปเลย" ไม่ใช่ agent แลก latency และค่าใช้จ่ายกับประสิทธิภาพ workflow ให้ความคาดเดาได้ และหลายครั้งเรียกครั้งเดียวก็พอ

สรุปสั้นๆ

เรียกครั้งเดียว → workflow → agent ขยับเมื่อมีตัวเลขยืนยัน ไม่ใช่เพราะดูทันสมัย

Checkpoint 3 (จับคู่)

จับคู่สถานการณ์กับการออกแบบ (A = เรียกครั้งเดียวที่ปรับดีแล้ว, B = Workflow, C = Agent):

  1. โปรเจกต์ใหม่ ยังไม่มีข้อมูลว่าวิธีไหนพอ
  2. งานนิยามชัด แต่วัดแล้วว่าการเรียกครั้งเดียวคุณภาพไม่ถึงเป้า
  3. งานต้องยืดหยุ่นและให้โมเดลตัดสินขั้นตอนเอง
ดูเฉลย

1-A, 2-B, 3-C การเรียกครั้งเดียวคือ default แล้วค่อยขยับตามหลักฐาน

4. Prompt chaining และ routing

คำถามช่วยเลือก pattern: ขั้นตอนตายตัวไหม? input แบ่งเป็นหมวดชัดๆ ได้ไหม? งานแยกทำขนานได้ไหม? รู้งานย่อยก่อนเห็น input ไหม? มีเกณฑ์วัดคุณภาพชัดไหม?

ถ้างาน…ใช้
แบ่งเป็นงานย่อยต่อกันเป็นลำดับตายตัวPrompt chaining
input แบ่งเป็นหมวดที่ต่างกันชัดRouting
มีชิ้นงานอิสระ หรือต้องลองหลายครั้งParallelization (sectioning หรือ voting)
งานย่อยขึ้นกับ input แต่ละตัวOrchestrator-workers
มีเกณฑ์ประเมินชัด และดีขึ้นเมื่อได้ feedbackEvaluator-optimizer

Prompt chaining

แต่ละการเรียกรับ output ของขั้นก่อนไปทำต่อ แลก latency กับความแม่น ระหว่างขั้นใส่ programmatic gate ได้ เช่น จำกัดความยาว ตรวจ schema ตรวจว่ามี field ที่ต้องมีครบ chain ที่ชัดเจนยังช่วยให้ log และส่องผลระหว่างทางได้ง่าย

copy = llm("เขียนคำโฆษณาสินค้า", brief)
for lang in ["th", "en", "ja"]:
    text = llm(f"แปลเป็น {lang}", copy)
    if len(text) > 60:                      # gate ด้วยโค้ด ไม่ใช่ LLM
        text = llm("ย่อให้ไม่เกิน 60 ตัวอักษร", text)

Routing

จัดหมวดก่อน แล้วส่งไป prompt, ชุด tool หรือ process ที่เฉพาะทางสำหรับหมวดนั้น ใช้ส่งคำถามง่ายไปโมเดลที่ถูกกว่าได้ด้วย

ในข้อสอบ

Routing ดีได้แค่เท่ากับหมวดหมู่ของมัน ก่อนเลือก routing ให้ยืนยันว่าหมวดนิยามชัด และการจัดหมวดเชื่อถือได้

เข้าใจผิดบ่อย

"มีการตรวจคุณภาพ = ต้องเป็น evaluator-optimizer" ไม่ใช่ การตรวจตามกฎ (เช่น ความยาว) ใช้ programmatic gate ระหว่างขั้นของ chain ส่วน evaluator-optimizer เหมาะกับเกณฑ์ที่ LLM วิจารณ์ได้และดีขึ้นเมื่อวนแก้

สรุปสั้นๆ

ขั้นตายตัวต่อกัน = chaining (+ gate ด้วยโค้ด) · หมวดชัดแยกทาง = routing

Checkpoint 4 (จับคู่)

จับคู่สถานการณ์กับ pattern (A = Chaining + code gate, B = Routing, C = Orchestrator-workers, D = Evaluator-optimizer):

  1. คำถามลูกค้าธนาคาร แบ่งเป็น บัตรเครดิต / สินเชื่อ / แจ้งทุจริต แต่ละหมวดมี prompt ที่จูนไว้
  2. เขียนสคริปต์วิดีโอ แล้วตัดให้ยาวไม่เกิน 90 วินาทีตามกฎตายตัว
  3. แปลบทกวี แล้วให้ LLM อีกตัววิจารณ์จังหวะและน้ำเสียงจนผ่าน
  4. คำขอแก้ระบบที่ไม่รู้ว่าจะกระทบไฟล์ไหนจนกว่าจะอ่านคำขอ
ดูเฉลย

1-B, 2-A, 3-D, 4-C กฎความยาวเป็นการตรวจตายตัว ใช้โค้ด ส่วนน้ำเสียงต้องใช้วิจารณญาณ จึงเป็น evaluator

  1. Evaluator-optimizer ให้ LLM ตรวจความยาว
  2. Routing แยกตามภาษา
  3. Orchestrator-workers ให้ LLM ตัวกลางเลือกภาษา

ดูเฉลย

5. Parallelization และ orchestrator-workers: งานย่อยรู้ก่อน vs เกิดตอนรัน

Parallelization มี 2 แบบ:

  • Sectioning: งานย่อย คนละอย่าง ที่อิสระต่อกัน รันพร้อมกันแล้วรวมผล เช่น ตัวหนึ่งตรวจช่องโหว่ในโค้ด อีกตัวตรวจปัญหา license แล้วรวมเป็นรายงานเดียว guardrail ก็เป็นตัวอย่างคลาสสิก: ตัวหนึ่งตอบผู้ใช้ อีกตัวคัดกรองว่าคำถามไม่เหมาะสมหรือเปล่า
  • Voting: งาน เดียวกัน รันหลายครั้งเพื่อให้ได้ผลหลากหลาย เช่น ให้หลาย prompt รีวิวโค้ดชุดเดียวกันหาช่องโหว่ ถ้าตัวไหนเจอก็ flag

Orchestrator-workers: LLM ตัวกลางตัดสินงานย่อยตอนรันจาก input นั้นๆ จุดต่างจาก sectioning คืองานย่อย ไม่ได้ถูกกำหนดไว้ก่อน เลี่ยงใช้เมื่อ latency สำคัญมาก งานง่าย หรืองานย่อยคาดเดาได้

async def investigate(question):
    angles = await lead.plan_angles(question)          # หัวหน้าคิดงานย่อยจาก input นี้
    results = await asyncio.gather(
        *[worker(a) for a in angles])                  # ลูกทีมทำพร้อมกัน
    return await lead.combine(results)                 # หัวหน้ารวมผล

บรรทัดที่ทำให้นี่เป็น orchestrator-workers คือบรรทัดแรก: รายการงานย่อยถูกสร้างตอนรันสำหรับแต่ละคำถาม ถ้ารายการนี้เป็นค่าคงที่ ก็จะกลายเป็น sectioning

ลองเดา: prompt รีวิว 5 ตัวที่กำหนดไว้แล้วรันพร้อมกัน เป็น pattern ไหน? คำตอบคือ sectioning ไม่ใช่ orchestrator-workers เพราะงานย่อยตายตัว

เข้าใจผิดบ่อย

"งานที่มีหลายงานย่อยต้องใช้ orchestrator-workers" ไม่ใช่ ถ้ารู้งานย่อยล่วงหน้า ใช้ parallelization แบบ sectioning ที่ง่ายกว่า

"รันการตรวจ 2 แบบที่ต่างกันพร้อมกัน = voting" ไม่ใช่ นั่นคือ sectioning voting คือทำงานเดียวกันซ้ำ

สรุปสั้นๆ

งานต่างกัน รู้ก่อน = sectioning · งานเดียวกันซ้ำ = voting · งานย่อยเกิดตอนรัน = orchestrator-workers

  4. Parallelization แบบ sectioning

D สองงานต่างกันและอิสระต่อกัน voting คือทำงานเดิมซ้ำ ไม่มีการวิจารณ์วนแก้ (ไม่ใช่ C) และไม่ได้ส่ง output ต่อกัน (ไม่ใช่ A)

6. Evaluator-optimizer loop

การเรียกหนึ่งสร้างงาน อีกการเรียกวิจารณ์เทียบเกณฑ์ แล้ววนจนผ่าน เหมือนนักเขียนกับบรรณาธิการ

เงื่อนไขที่ทำให้คุ้ม:

  • มีเกณฑ์ประเมินที่ชัด
  • การแก้ตาม feedback ทำให้ผลดีขึ้นอย่างวัดได้
  • ถ้าคนให้ feedback แล้วงานดีขึ้นจริง และ LLM ให้ feedback แบบเดียวกันได้ ก็เป็นสัญญาณที่ดี

ตัวอย่างที่เหมาะ: แปลวรรณกรรมที่ต้องการความละเอียดของภาษา, การค้นหาซับซ้อนที่ evaluator ตัดสินว่าต้องค้นอีกรอบไหม

ชนิดการตรวจใช้อะไรตัวอย่าง
ตามกฎ ตรวจด้วยโค้ดได้Programmatic gateJSON valid ไหม, ชื่อไม่เกิน 60 ตัวอักษร
ต้องใช้วิจารณญาณLLM evaluatorน้ำเสียง ความละเอียดอ่อน ความครบถ้วน

ลองเดา: ชื่อบทความต้องเป็น JSON ที่ valid และยาวไม่เกิน 60 ตัวอักษร ใช้อะไรตรวจ? ใช้โค้ด ไม่ใช่ LLM evaluator

ทุกรอบเพิ่มจำนวนการเรียก จึงต้องมีเงื่อนไขผ่านเพื่อหยุด ถ้าคะแนนเริ่มแบนราบ เช่น loop แปล 4 รอบแต่ดีขึ้นแค่ถึงรอบที่ 2 แปลว่าการวนไม่ได้เพิ่มคุณค่าแล้ว ให้ตั้งเพดานรอบ หรือทำเกณฑ์ให้คมขึ้น

สรุปสั้นๆ

ใช้ evaluator-optimizer เมื่อเกณฑ์ชัดและ feedback ทำให้ดีขึ้นจริง กฎตายตัวใช้ gate ด้วยโค้ด และต้องมีจุดหยุดเสมอ

Checkpoint 9

ทีมทดลอง evaluator-optimizer กับการเขียนบทสรุปรายงานการเงิน ผลการทดลองข้อไหนบอกว่า pattern นี้ ไม่ เหมาะ?

  1. นักวิเคราะห์เขียนเกณฑ์ผ่าน/ไม่ผ่านได้ชัดเจน
  2. LLM เขียนคำวิจารณ์ได้ใกล้เคียงกับที่นักวิเคราะห์เขียน
  3. ผู้ตรวจที่เป็นคนเห็นด้วยกับคำวิจารณ์ของ LLM ส่วนใหญ่
  4. แม้นักวิเคราะห์จะให้ feedback ละเอียด ร่างรอบถัดไปก็ไม่ได้ดีขึ้น
