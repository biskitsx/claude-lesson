3.6 Retrieval strategies matched to data shape and query pattern

ต้นฉบับ: CertSafari 3.6

อ่านจบแล้วควรทำได้
  • ตัดสินได้ว่าคลังข้อมูล (corpus) ชุดนี้ ยัดลง prompt ทั้งก้อน ได้เลย หรือจำเป็นต้องมีระบบ retrieval
  • เลือกระหว่าง embeddings, BM25 หรือใช้คู่กัน (hybrid) จาก หน้าตาของคำถาม ที่ผู้ใช้ส่งมาจริง
  • อธิบาย pipeline ของ hybrid search และรู้ว่าจะจูนน้ำหนัก fusion ไปทางไหนเมื่อเจออาการพลาด
  • เลือก stack ที่เหมาะกับงบและ latency: contextual embeddings, hybrid, reranking
  • รู้ว่าเมื่อไหร่ควรใช้ just-in-time retrieval, tool search และ server-side compaction แทนการ index ล่วงหน้า
แนวคิดหลัก: ดูรูปร่างข้อมูลกับรูปร่างคำถามก่อนเลือกเครื่องมือ

ไม่มี retrieval แบบไหนดีที่สุดในทุกกรณี คำถามแรกคือ ข้อมูลใหญ่แค่ไหน และเปลี่ยนเร็วแค่ไหน คำถามที่สองคือ ผู้ใช้ถามด้วยรหัสเป๊ะๆ หรือถามด้วยภาษาของตัวเอง คำตอบของสองข้อนี้จะบอกเองว่าควรใส่ทั้งก้อน ใช้ BM25 ใช้ embeddings ผสมกัน หรือให้ agent ไปค้นเองตอนต้องใช้

1. ข้อมูลใส่ลง prompt ได้ทั้งก้อนไหม

หลายทีมกระโดดไปทำ RAG pipeline (ตัด chunk, ทำ index, ตั้ง vector DB) ทันทีที่ได้ยินคำว่า "knowledge base" ทั้งที่ข้อมูลอาจเล็กพอจะใส่ลง prompt ตรงๆ ได้เลย

  • ถ้า corpus เล็กกว่าประมาณ 200,000 token (ราวๆ 500 หน้า) ใส่ทั้งหมดลง prompt ได้ ไม่ต้อง chunk ไม่ต้องมี index
  • ทำให้คุ้มด้วย prompt caching: ส่วนที่ซ้ำทุก request ถูก cache ไว้ ต้นฉบับอ้างว่า latency ลดลง มากกว่า 2 เท่า และค่าใช้จ่ายลด ได้ถึง 90%
  • แต่ "ใส่ได้พอดี window" คือ เพดาน ไม่ใช่เป้าหมาย ยิ่ง token เยอะ ความแม่นและความสามารถดึงข้อมูลกลับมาใช้ (recall) ยิ่งตก อาการนี้เรียกว่า context rot
  • ถ้าข้อมูลใหญ่เกินนั้น หรือกำลังโตจนจะเกิน ต้องมีวิธี retrieval ที่ scale ได้

เปรียบเหมือนสมุดคู่มือพนักงานเล่มบาง ยื่นให้อ่านทั้งเล่มเลยง่ายกว่าทำสารบัญดัชนี แต่ถ้าเป็นห้องสมุดทั้งตึก ยังไงก็ต้องมีระบบค้นหา

เข้าใจผิดบ่อย

"มี knowledge base สำหรับ grounding เมื่อไหร่ ต้องทำ RAG pipeline เสมอ" ไม่จริง ถ้า corpus ต่ำกว่าราว 200K token ใส่ลง prompt แล้ว cache ไว้ เป็นทางที่ง่ายและมักถูกกว่า

สรุปสั้นๆ

ข้อมูลเล็กกว่า ~200K token: ใส่ทั้งก้อน + prompt caching ข้อมูลใหญ่หรือกำลังจะใหญ่: วางแผน retrieval ที่ scale ได้ และอย่าลืมว่าใส่เยอะเกินไปก็เจอ context rot

ลองเดาก่อน

ทีม HR มีคู่มือนโยบายบริษัทราว 300 หน้า แก้ปีละครั้ง อยากทำแชตบอตตอบคำถามพนักงาน ทางไหนเหมาะที่สุดตอนนี้?

  1. ใส่คู่มือทั้งเล่มลง prompt และเปิด prompt caching
  2. ตัด chunk แล้วทำ vector index พร้อม reranker
  3. Fine-tune โมเดลด้วยคู่มือ
  4. ให้ agent ใช้ grep ค้นทีละหน้า
ดูเฉลย

A 300 หน้าอยู่ต่ำกว่าราว 500 หน้า / 200K token ใส่ทั้งก้อนได้ และเนื้อหาแทบไม่เปลี่ยน caching จึงคุ้มมาก ระบบ index เป็นภาระที่ยังไม่จำเป็น

Checkpoint 1

สตาร์ตอัปมีเอกสาร API ตอนนี้ 120 หน้า แต่แผนงานบอกว่าจะเพิ่มเป็นราว 2,500 หน้าภายในปีหน้า ควรวางแผนยังไง?

  1. สร้าง hybrid search + reranking ตั้งแต่วันแรก เพราะสุดท้ายก็ต้องใช้
  2. ใส่ทั้งหมดลง prompt ตลอดไป เพราะ context window จะใหญ่ขึ้นเรื่อยๆ
  3. ใส่ทั้งหมดลง prompt พร้อม caching ไปก่อน แล้วค่อยเพิ่ม retrieval ที่ scale ได้เมื่อ corpus เลยราว 200K token
  4. ใช้ BM25 อย่างเดียวตั้งแต่วันแรก
ดูเฉลย

C วันนี้ข้อมูลเล็ก ทางง่ายที่สุดก็พอแล้ว แต่ต้องรู้ว่าจุดเปลี่ยนอยู่ตรงไหน B ผิดเพราะต่อให้ใส่ได้ก็เจอ context rot และ 2,500 หน้าเกินเพดานแน่นอน

2. Embeddings กับ BM25: จับ "ความหมาย" หรือจับ "คำ"

Retriever สองตระกูลหลักจับคนละอย่าง:

  • Embeddings แปลงข้อความเป็นเวกเตอร์แล้ววัดความใกล้ของ ความหมาย เก่งกับคำถามที่ใช้คำไม่ตรงกับเอกสาร (paraphrase) เช่นถาม "ลาคลอดได้กี่วัน" แต่เอกสารเขียน "สิทธิ์ลาเพื่อดูแลบุตรแรกเกิด" แต่ อาจพลาดสตริงเป๊ะๆ อย่างรหัส error ERR-4021 หรือเลขชิ้นส่วน
  • BM25 เป็นวิธีจัดอันดับแบบ lexical (ดูตัวคำ) ต่อยอดจาก TF-IDF โดยเพิ่มสองอย่าง: document-length normalization (เอกสารยาวไม่ได้เปรียบแค่เพราะมีคำเยอะ) และ term-frequency saturation (คำเดิมซ้ำ 50 ครั้งไม่ได้คะแนนมากกว่า 5 ครั้งเป็นสิบเท่า) เก่งเรื่องจับคำตรงตัว แต่ไม่เข้าใจคำพ้องความหมาย

รหัสเฉพาะ เช่น error code, SKU, ชื่อฟังก์ชันBM25ต้องการตัวอักษรตรงกันเป๊ะ
คำถามเชิงแนวคิด พิมพ์ด้วยภาษาของผู้ใช้เองEmbeddingsคำอาจไม่ตรงกับเอกสารเลย แต่ความหมายตรง
ปนกันทั้งสองแบบใช้ร่วมกัน (hybrid)แต่ละตัวอุดจุดอ่อนของอีกตัว

ตั้ง input_type ให้ถูกตอนเรียก embedding

ตอนเรียก embedding model ต้องบอกว่าข้อความนี้เป็นอะไร: ใช้ input_type="query" กับคำถามของผู้ใช้ และ input_type="document" กับเนื้อหาใน corpus อย่าปล่อยว่างหรือตั้งเป็น None เพราะโมเดลจะเติม prefix ต่างกันให้แต่ละฝั่งเพื่อให้จับคู่กันได้ดีขึ้น

doc_vecs = vo.embed(chunks, model="voyage-3", input_type="document").embeddings
q_vec    = vo.embed([question], model="voyage-3", input_type="query").embeddings[0]
เข้าใจผิดบ่อย

"Embeddings ดีๆ หา identifier ตรงตัวได้แม่นพอๆ กับหา paraphrase" ไม่จริง embeddings มองความหมาย สตริงอย่าง PN-88213-B กับ PN-88213-C อาจได้เวกเตอร์ใกล้กันมากจนแยกไม่ออก งานแบบนี้ BM25 เป็นตัวอุด

สรุปสั้นๆ

Embeddings = ความหมาย, BM25 = ตัวคำ ดู traffic จริงว่าคนถามแบบไหน แล้วเลือกตาม ถ้าปนกันก็ใช้คู่กัน และอย่าลืมตั้ง input_type

Checkpoint 2 (จับคู่)

จับคู่ระบบค้นหากับ retriever ที่เหมาะ (BM25 / Embeddings / ใช้ร่วมกัน):

  1. ช่างซ่อมพิมพ์รหัสอะไหล่อย่าง VX-2290 เพื่อหาคู่มือ
  2. ลูกค้าพิมพ์ว่า "เครื่องดังแก๊กๆ ตอนปั่นหมาด" แต่เอกสารเขียนว่า "เสียงผิดปกติขณะรอบ spin"
  3. พอร์ทัลซัพพอร์ตที่บางคนแปะ error code บางคนเล่าอาการเป็นภาษาพูด
ดูเฉลย

1-BM25, 2-Embeddings, 3-ใช้ร่วมกัน รหัสต้องการตัวคำตรง คำบรรยายอาการไม่มีคำซ้ำกับเอกสารเลยต้องใช้ความหมาย ส่วน traffic ปนกันต้องใช้ทั้งสอง

3. Hybrid search และการจูน fusion

Pipeline ของ hybrid search แบบที่ Anthropic ใช้อ้างอิงมีขั้นตอนดังนี้:

  1. ตัด corpus เป็น chunk
  2. encode แต่ละ chunk ทั้งแบบ TF-IDF (สำหรับ BM25) และแบบ embeddings
  3. ดึง chunk อันดับต้นๆ จาก retriever แต่ละตัว (reference implementation ใช้ ตัวละ 150 candidate)
  4. รวมผลด้วย rank fusion (ใช้ weighted Reciprocal Rank Fusion หรือ RRF)
  5. ตัดตัวซ้ำออก (deduplicate)
  6. เอา top-K chunk ใส่ prompt

RRF ไม่ได้สนใจคะแนนดิบของแต่ละ retriever (ซึ่งคนละสเกลกัน) แต่ใช้ อันดับ แทน chunk ที่ติดอันดับต้นในทั้งสองรายการจะได้คะแนนรวมสูง ส่วน "weighted" หมายถึงให้น้ำหนักแต่ละ retriever ไม่เท่ากันได้

def weighted_rrf(sem_ranks, bm25_ranks, w_sem=0.8, w_bm25=0.2, k=60):
    score = {}
    for rank, cid in enumerate(sem_ranks):
        score[cid] = score.get(cid, 0) + w_sem / (k + rank + 1)
    for rank, cid in enumerate(bm25_ranks):
        score[cid] = score.get(cid, 0) + w_bm25 / (k + rank + 1)
    return sorted(score, key=score.get, reverse=True)
  • ค่าเริ่มต้นใน reference คือ semantic 80% / BM25 20% และ ปรับได้ ถ้า corpus อัดแน่นไปด้วยรหัสและ identifier แล้วผู้ใช้หารหัสไม่เจอ ให้ เพิ่มน้ำหนัก BM25
  • อย่าคิดว่า 20% แปลว่า BM25 แทบไม่มีบทบาท ในการทดสอบกับ codebase พบว่าหลัง fusion แล้ว BM25 ยังเป็นแหล่งของผลลัพธ์สุดท้ายราว 39–45%
  • ก่อนจะเพิ่ม retriever ตัวที่สอง ให้ดูก่อนว่ามี embedding model เฉพาะโดเมน ไหม เช่น voyage-code-4 (โค้ด), voyage-law-2 (กฎหมาย), voyage-finance-2 (การเงิน) บางทีเปลี่ยนโมเดลอย่างเดียวก็แก้ปัญหาได้
สรุปสั้นๆ

Hybrid = ดึงจากสอง retriever (ตัวละ 150) → รวมด้วย weighted RRF (เริ่ม 80/20) → dedupe → top-K หารหัสไม่เจอให้เพิ่มน้ำหนัก BM25 และลองโมเดลเฉพาะโดเมนก่อนเพิ่มของ

Checkpoint 3

ระบบค้นเอกสารของโรงงานใช้ hybrid search ที่น้ำหนัก 80/20 (semantic/BM25) วิศวกรบ่นว่าพิมพ์รหัสแม่พิมพ์ MD-7731 แล้วผลที่ได้เป็นแม่พิมพ์รุ่นคล้ายๆ กันแต่ไม่ใช่ตัวนั้น ควรแก้ที่ไหนก่อน?

  1. เพิ่มน้ำหนัก BM25 ใน fusion เพราะ corpus นี้เต็มไปด้วยรหัส
  2. ตัด BM25 ออกเพื่อลดสัญญาณรบกวน
  3. เพิ่มขนาด chunk เป็นสองเท่า
  4. เปลี่ยน input_type ของ query เป็น document
ดูเฉลย

A อาการคือ semantic ดึง "ของที่ความหมายใกล้" มาแทน "ของที่ตรงเป๊ะ" corpus ที่หนักไปทาง identifier ควรให้ BM25 มีเสียงมากขึ้น D ทำให้แย่ลงเพราะ query ต้องใช้ query

4. เลือก stack ให้ครบ: contextual embeddings, hybrid, reranking

นอกจาก retriever ยังมีอีกสองชั้นที่ซ้อนเพิ่มได้ แต่ละชั้นมีต้นทุนต่างกัน

  • Contextual embeddings: ก่อน index ให้ Claude เขียนบริบทสั้นๆ ของ chunk นั้น (เช่น "ข้อความนี้มาจากรายงานไตรมาส 2 ของบริษัท X ส่วนรายได้") แล้วแปะไว้หน้า chunk ก่อน embed จ่ายครั้งเดียวตอน ingest ราว $1.02 ต่อล้าน token ของเอกสาร (ชุดข้อมูล codebase ใช้ราว $3) เหมาะที่สุดกับ chunk ที่ หลุดบริบทแล้วอ่านไม่รู้เรื่อง เช่นย่อหน้าในเอกสาร SEC ที่เขียนว่า "รายได้เพิ่มขึ้น 3%" โดยไม่บอกว่าของบริษัทไหน ไตรมาสไหน
  • Hybrid search: ต้องรันและดูแล Elasticsearch (หรือ engine BM25 อื่น) เพิ่มเข้ามา เป็นภาระด้าน ops
  • Reranking: เอา candidate จาก retrieval ไปให้โมเดล rerank จัดอันดับใหม่ เพิ่ม latency ราว 100–200 ms และราว $0.002 ต่อ query ตัว rerank-3 แม่นที่สุด ส่วน rerank-3-lite เน้นเร็วและถูก ยิ่งส่ง candidate ไป rerank มาก ยิ่งแม่น แต่ก็ยิ่งช้าและแพง

ผลการทดสอบกับ codebase (248 query) วัดด้วย Pass@k คือสัดส่วน query ที่ chunk ที่ถูกต้องติดอยู่ใน k อันดับแรก:

D จ่ายครั้งเดียวตอน ingest ไม่มีค่าต่อ query ได้ Pass@10 ราว 92% พอดีเป้า reranking จะเพิ่มค่าใช้จ่ายและ latency ทุก query ซึ่งที่สเกลนี้หนักมาก

5. Just-in-time retrieval: ไม่ index ล่วงหน้า ให้ agent ไปหยิบเอง

อีกแนวคิดหนึ่งคือไม่ต้องดึงข้อมูลมาเตรียมไว้เลย agent ถือแค่ reference เบาๆ เช่น path ของไฟล์, query ที่บันทึกไว้, ลิงก์ แล้วใช้ tool โหลดข้อมูลจริงเฉพาะตอนต้องใช้ Claude Code ทำแบบนี้อยู่แล้ว ด้วย glob, grep และ head/tail

  • เหมาะที่สุด เมื่อข้อมูลเปลี่ยนเร็วกว่าที่จะ rebuild index ทัน เช่น monorepo ที่มีคน rename ฟังก์ชันทุกชั่วโมง index ที่สร้างตอนกลางคืนจะเก่าตั้งแต่ออกแบบ
  • โครงสร้างโฟลเดอร์และการตั้งชื่อไฟล์ก็เป็นสัญญาณช่วย agent ตัดสินว่าจะเปิดอะไรต่อ (ไฟล์ชื่อ test_payment.py บอกอะไรได้เยอะโดยไม่ต้องเปิด)
  • ราคาที่ต้องจ่าย: ช้ากว่าการดึงจากที่คำนวณไว้แล้ว, ต้องมี tool ดีๆ และคำแนะนำที่ชัด, และเสี่ยงเอาของไม่เกี่ยวมาเติม context จนรก

แบบผสม (hybrid): โหลดของที่นิ่งไว้ล่วงหน้า เช่นไฟล์ CLAUDE.md หรือเอกสารหลักด้านกฎหมาย/การเงินที่ไม่ค่อยเปลี่ยน แล้วให้ agent สำรวจส่วนที่เหลือตามต้องการ

สรุปสั้นๆ

ข้อมูลเปลี่ยนเร็วกว่า index = ให้ agent ค้นเองตอนต้องใช้ ของนิ่งโหลดไว้ก่อน ของเยอะและเปลี่ยนบ่อยค่อยสำรวจ

Checkpoint 5

Agent ช่วยรีวิวโค้ดใน monorepo ที่มีคน merge วันละหลายร้อย PR ระบบใช้ vector index ที่ rebuild ทุกตีสอง ผลคือ agent ชอบอ้างถึงคลาสที่ถูกลบไปแล้วเมื่อบ่าย ควรแก้ยังไง?

  1. Rebuild index ทุก 6 ชั่วโมงแทน
  2. ให้ agent มี tool ค้นไฟล์ (เช่น glob/grep) เพื่อดูโค้ดปัจจุบันตอนต้องใช้
  3. เพิ่ม reranking
  4. ใส่โค้ดทั้ง repo ลง prompt
ดูเฉลย

B ปัญหาคือ index เก่าโดยธรรมชาติ ถี่ขึ้นก็ยังเก่า reranking จัดอันดับของเก่าให้ดีขึ้นเท่านั้น ส่วน repo ใหญ่ขนาดนี้ใส่ prompt ไม่ได้ just-in-time ดูของจริง ณ ตอนนั้นเสมอ

Checkpoint 6

Agent ด้านภาษีมีชุดประมวลกฎหมายหลัก (ไม่ค่อยเปลี่ยน ใช้แทบทุกคำถาม) กับคลังคำวินิจฉัยเก่าหลายหมื่นฉบับ (ใช้บ้างไม่ใช้บ้าง) ควรจัดยังไง?

  1. ใส่ทั้งสองส่วนลง prompt
  2. ให้ agent ค้นทั้งสองส่วนเองทุกครั้ง
  3. โหลดประมวลกฎหมายหลักไว้ล่วงหน้า แล้วให้ agent ใช้ tool สำรวจคลังคำวินิจฉัยเมื่อจำเป็น
  4. Fine-tune ด้วยคำวินิจฉัย
ดูเฉลย

C นี่คือแบบผสม: ของนิ่งและใช้บ่อยโหลดก่อน ของเยอะที่ใช้เป็นครั้งคราวค่อยไปหยิบ

6. เมื่อสิ่งที่ต้อง "ค้น" คือ tool และเมื่อ session ยาวมาก

หลักคิดเดียวกันใช้กับ tool definition ได้ด้วย ถ้ามี tool เยอะ ไม่ต้องโหลดนิยามทั้งหมดตั้งแต่แรก (รายละเอียดเต็มในบท 3.8)

  • Tool search: ใส่ defer_loading: true ให้ tool ที่ไม่ต้องโหลดทันที นิยามจะเข้า context เมื่อถูกค้นเจอ มี built-in สองแบบ: tool_search_tool_regex_20251119 และ tool_search_tool_bm25_20251119
  • คุ้มเมื่อ context ที่ประหยัดได้และความแม่นที่เพิ่มขึ้นมากกว่า latency ของขั้นค้นหาที่เพิ่มมา สัญญาณคือ นิยาม tool รวมเกินราว 10K token หรือ มีมากกว่า 10 tool
  • เก็บ 3–5 tool ที่ใช้บ่อยที่สุดไว้แบบไม่ defer ส่วนชุดเล็กที่ใช้บ่อยอยู่แล้ว โหลดตรงๆ ทั้งหมดไปเลย
  • ถ้าอยากค้น tool ด้วย ความหมาย (embeddings) ให้สร้าง custom search tool ที่คืน block แบบ tool_reference โดย tool ทุกตัวที่ถูกอ้างถึงยังต้องอยู่ใน array tools ระดับบนสุด (ปกติตั้ง defer_loading: true)
{"type": "tool_result", "tool_use_id": "toolu_01...",
 "content": [{"type": "tool_reference", "tool_name": "refund_order"}]}

Session ยาวหลายชั่วโมง

เมื่อ session ที่ดึงข้อมูลเยอะใกล้ชน context window วิธีหลักคือ server-side compaction (ให้ฝั่ง server ย่อประวัติเก่าลง) ไม่ใช่ทางเหล่านี้:

  • เพิ่ม max_tokens: เป็นการจองที่ให้ output มากขึ้น เหลือที่ให้ประวัติน้อยลง ทำให้แย่กว่าเดิม
  • อัปโหลดเอกสารซ้ำทุก turn: เติม window เร็วขึ้นอีก
เข้าใจผิดบ่อย

"Tool search ประหยัด context เสมอ ก็ defer ทุก tool ไปเลย" ไม่ใช่ ทุกครั้งที่จะเรียก tool ที่ถูก defer ต้องเพิ่มขั้นค้นหาก่อน tool ที่ใช้บ่อยควรโหลดไว้ และชุดเล็กๆ ที่ใช้บ่อยควรโหลดตรงทั้งหมด

"Tool search แบบ BM25 ที่ built-in มาก็เหมือน semantic search" ไม่ใช่ BM25 ดูตัวคำ ถ้าต้องการค้นด้วยความหมายจริง ต้องเขียน custom tool ที่ใช้ embeddings แล้วคืน tool_reference

สรุปสั้นๆ

Tool เกิน 10 ตัวหรือเกิน ~10K token: พิจารณา tool search แต่เก็บ 3–5 ตัวยอดฮิตไว้ ค้นด้วยความหมายต้องทำ custom tool session ยาวใช้ server-side compaction

Checkpoint 7

Agent ฝ่าย IT มี tool 6 ตัว (รีเซ็ตรหัส, ปลดล็อกบัญชี, เช็กสถานะ VPN ฯลฯ) นิยามรวมราว 900 token และแทบทุก request ใช้ 2–3 ตัวในนี้ ควรทำยังไง?

  1. โหลดทั้ง 6 ตัวตรงๆ ไม่ต้องใช้ tool search
  2. เปิด tool search แล้ว defer ทั้ง 6 ตัว
  3. เปิด tool search แบบ regex แล้ว defer 3 ตัว
  4. สร้าง custom embeddings search tool
ดูเฉลย

A ชุดเล็ก ใช้บ่อย ต่ำกว่าเกณฑ์ทั้งเรื่องจำนวนและ token การเพิ่มขั้นค้นหามีแต่เพิ่ม latency

Checkpoint 8

Agent วิเคราะห์ตลาดทำงานต่อเนื่อง 4 ชั่วโมง ดึงรายงานเข้ามาเรื่อยๆ จน context ใกล้เต็ม ข้อไหนเหมาะที่สุด?

  1. เปิด server-side compaction
  2. เพิ่ม max_tokens เป็นค่าสูงสุด
  3. ส่งรายงานทั้งหมดซ้ำทุก turn เพื่อไม่ให้ลืม
  4. เริ่ม session ใหม่ทุก 30 นาทีโดยไม่ส่งอะไรต่อ
ดูเฉลย

A compaction เป็นกลยุทธ์หลักสำหรับ session ยาว B ลดที่ว่างของประวัติ C เติม window เร็วขึ้น D ทิ้งงานที่ทำมาทั้งหมด

Checkpoint 9

แพลตฟอร์มมี tool 400 ตัว ผู้ใช้ชอบขอด้วยคำที่ไม่ตรงกับชื่อ tool (เช่นพิมพ์ "ยกเลิกแพ็กเกจ" แต่ tool ชื่อ terminate_subscription) และ built-in BM25 tool search หาไม่เจอบ่อย ควรทำยังไง?

  1. สร้าง custom search tool ที่ใช้ embeddings แล้วคืน tool_reference โดยทุก tool ยังอยู่ใน tools พร้อม defer_loading: true
  2. เปลี่ยนไปใช้ regex variant
  3. เลิก defer แล้วโหลดทั้ง 400 ตัว
  4. ให้ custom tool คืนนิยาม tool เต็มเป็นข้อความ แล้วเอา tool ออกจาก tools
ดูเฉลย

A ปัญหาคือการจับคู่ความหมาย ซึ่ง BM25 และ regex ทำไม่ได้ D ผิดเพราะ tool ที่ถูกอ้างถึงต้องมีนิยามอยู่ใน tools ระดับบนสุดเสมอ
