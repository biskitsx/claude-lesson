1.4 Multi-agent design: when to split and how to brief subagents

ต้นฉบับ: CertSafari 1.4

อ่านจบแล้วควรทำได้
  • ตัดสินได้ว่างานไหนคุ้มที่จะใช้หลาย agent พร้อมบอกเหตุผลที่จับต้องได้และต้นทุน token
  • อธิบายว่า coordinator ส่งงานให้ subagent ที่มี context แยกยังไง และได้อะไรกลับมา
  • ขีดเส้นแบ่ง agent ตาม context ไม่ใช่ตาม บทบาท
  • เขียน brief ให้ subagent ที่ครบในตัว: objective, output format, tools, boundaries
แนวคิดหลัก: subagent มองไม่เห็น context ของเรา

Subagent ทำงานในบทสนทนาของตัวเอง ไฟล์ที่มันอ่านและ tool call ที่มันทำอยู่ในนั้นทั้งหมด coordinator ได้กลับมาแค่ ข้อความสุดท้าย และในทางกลับกัน subagent ก็ไม่เห็นสิ่งที่ coordinator คุยมาก่อน ดังนั้น brief ต้องครบในตัว

1. เริ่มจาก agent ตัวเดียว แยกเมื่อมีเหตุผลที่จับต้องได้

Multi-agent ไม่ฟรี การทดสอบของ Anthropic พบว่าระบบหลาย agent มักใช้ token ประมาณ 3–10 เท่า ของ agent ตัวเดียวในงานเดียวกัน และเวลารวมก็มักนานขึ้นด้วย สิ่งที่การรันขนานซื้อได้คือ ความครอบคลุม ไม่ใช่ความเร็ว

ลองเดา: งานที่ agent ตัวเดียวทำ 10 นาที ถ้าแบ่งให้ subagent 5 ตัวรันขนาน จะเป็นยังไง? ส่วนใหญ่ใช้ token มากขึ้น และเวลารวมมักนานขึ้น ไม่ใช่เหลือ 2 นาที

มีแค่ 3 เหตุผลที่คุ้มจะแยก:

เหตุผลสัญญาณใน agent ตัวเดียวต้นทุนหลัก
Context pollutionงานย่อยดึงข้อมูลเข้ามาเกินประมาณ 1,000 token ที่งานหลักแทบไม่ได้ใช้ส่งต่องานแล้วรายละเอียดหายได้ ถ้าไม่บอกชัดว่าต้องดึงอะไรกลับมา
Parallel breadthงานแตกเป็นมุมที่อิสระต่อกัน เช่น ค้นข้อมูลจากหลายแหล่งtoken เพิ่มมาก และเวลารวมมักนานขึ้น
Specialisationtool 20+ ตัว, tool คนละโดเมนที่ไม่เกี่ยวกัน, หรือโหมดพฤติกรรมที่ขัดกันความซับซ้อนของการ route ถ้าส่งผิดตัว ผลก็แย่

ตัวอย่าง context pollution: ให้ subagent ไปดึงประวัติคำสั่งซื้อหลายพัน token แล้วส่งกลับมาแค่สรุป 50–100 token ที่งานหลักต้องใช้จริง

ถ้าไม่มีสัญญาณไหนในสามข้อนี้ ให้เก็บ agent ตัวเดียวไว้ แล้วไปปรับ prompt ให้ดีขึ้นแทน

ขีดเส้นตาม context ไม่ใช่ตามบทบาท

การแบ่งเป็น planner / implementer / tester / reviewer ดูเป็นระเบียบเหมือนผังองค์กร แต่ได้ผลเหมือน เกมกระซิบต่อกัน: ส่งต่อทีละทอด รายละเอียดหายทีละนิด agent ที่สร้างฟีเจอร์ควรเป็นคนเขียนเทสต์ของมันเองด้วย เพราะมันรู้ว่าตัวเองตัดสินใจอะไรไปบ้าง

เส้นแบ่งที่ดีเส้นแบ่งที่แย่
เส้นทางรีเสิร์ชที่อิสระต่อกันช่วงต่อเนื่องของฟีเจอร์เดียวกัน (วางแผน → ทำ → เทสต์)
component ที่มี API contract ชัดเจนcomponent ที่ผูกกันแน่น
การตรวจแบบ black-box (ตรวจผลจากภายนอกโดยไม่ต้องรู้ไส้ใน)งานที่แชร์ state ที่แก้ไขได้ร่วมกัน
ในข้อสอบ

ตัวเลือกที่แบ่ง agent ตามบทบาท (planner, implementer, tester, reviewer) มักเป็นคำตอบผิด ให้แยกเฉพาะจุดที่ context แยกขาดจากกันได้จริง

ลองกับงานตัวเอง: ดู subagent ที่คุณมีอยู่ มันอิสระต่อกันจริง หรือเป็นแค่ช่วงต่อเนื่องของงานเดียวที่ควรอยู่ใน agent ตัวเดียว?

เข้าใจผิดบ่อย

"แบ่งให้หลาย agent ขนานกันแล้วจะเสร็จเร็วกว่าและถูกกว่า" ไม่ใช่ มักใช้ token มากกว่าและเวลารวมนานกว่า สิ่งที่ได้คือความละเอียดครอบคลุม

"ให้งานแต่ละประเภทมี agent ของตัวเอง" ไม่ใช่ แบ่งตามบทบาททำให้ context หายทุกครั้งที่ส่งต่อ ให้แบ่งตามขอบเขต context

สรุปสั้นๆ

แยกเมื่อเจอ context pollution, parallel breadth หรือ specialisation เท่านั้น จ่าย token 3–10 เท่า และขีดเส้นตาม context ไม่ใช่ตามตำแหน่งงาน

Checkpoint 1 (จับคู่)

จับคู่สัญญาณกับการตัดสินใจ (A = แยกเพราะ context pollution, B = แยกเพราะ parallel breadth, C = แยกเพราะ specialisation, D = เก็บ agent ตัวเดียว แล้วปรับ prompt):

  1. agent ซัพพอร์ตมี tool 28 ตัว ครอบทั้ง HR, การเงิน และ IT แล้วเริ่มเรียก tool ผิดโดเมน
  2. ต้องสรุปกฎหมายคุ้มครองข้อมูลของ 8 ประเทศ แต่ละประเทศค้นแยกกันได้
  3. ก่อนตอบ agent ต้องอ่าน log 15,000 token แต่ใช้จริงแค่บรรทัด error ไม่กี่บรรทัด
  4. agent ตอบคำถามสินค้าได้ช้านิดหน่อย แต่ไม่มีอาการข้างบนเลย
ดูเฉลย

1-C, 2-B, 3-A, 4-D มีแค่สามสัญญาณนี้ที่คุ้มกับต้นทุนที่เพิ่ม ถ้าไม่มีเลยให้ปรับ agent ตัวเดียว

Checkpoint 2

ทีมออกแบบระบบสร้างฟีเจอร์ "ระบบคูปองส่วนลด" ด้วย 4 agent: planner → implementer → tester → reviewer ผลคือเทสต์ไม่ครอบเงื่อนไขที่ implementer ตั้งใจไว้ ควรแนะนำอะไร?

  1. รวม planner กับ reviewer เป็นตัวเดียว เหลือ 3 agent
  2. ให้ทั้ง 4 agent รันขนานกันเพื่อลดเวลา
  3. คง 4 agent ไว้ แต่ให้ส่งต่อบ่อยขึ้น
  4. ให้ agent ตัวเดียวสร้างและเขียนเทสต์ของฟีเจอร์ แยกเฉพาะงานที่อิสระจริง เช่น ตัวตรวจแบบ black-box
ดูเฉลย

D A ยังแบ่งตามบทบาทอยู่ C คือเกมกระซิบเหมือนเดิม B ยังแบ่งตามบทบาทและเพิ่มต้นทุน

2. Coordinator pattern และ context ที่แยกขาด

Coordinator วางแผน แบ่งชิ้นงานให้ subagent แล้วรวมผล subagent แต่ละตัวเริ่มจาก context ว่างเปล่า และมีแค่ข้อความสุดท้ายที่กลับไปหาตัวแม่

แยกแค่บทสนทนา ไม่ได้แยกสภาพแวดล้อม

ใน Managed Agents agent ตัวหนึ่งสามารถประสาน agent ตัวอื่นภายใน session เดียวกันได้ โดย:

  • ทุก agent ใน session แชร์ sandbox, filesystem และ vault credentials เดียวกัน
  • แต่ละ agent มี session thread ของตัวเอง ซึ่งเป็น event stream ที่ context แยกขาดจากกัน
  • thread ของ subagent ยังเปิดอยู่หลังจบงาน coordinator ถามต่อได้ และ subagent จำสิ่งที่ทำไปก่อนหน้าได้

ผลที่ตามมา: ถ้า subagent เขียนผลละเอียดลงไฟล์ เช่น findings.md coordinator จะเห็นแค่สรุปในข้อความ แต่เปิดไฟล์นั้นอ่านเองได้เพราะ filesystem เป็นของกลาง

Subagent vs agent team vs workflow

กลไกคืออะไรเหมาะกับ
Subagentทำงานข้างเคียงหนึ่งชิ้นใน context ของตัวเอง ส่งกลับแค่ข้อความสุดท้ายซ่อนงานสืบค้นหนึ่งชิ้นไม่ให้รกบทสนทนาหลัก
Agent teamหลาย session ที่ประสานกัน แชร์ task list และส่งข้อความหากันได้ มี lead คอยจัดการ (ยังเป็น experimental และปิดไว้โดย default)ให้ worker หลายตัวทำงานสอดคล้องกันแบบเพื่อนร่วมทีม
Workflow (scripted)สคริปต์ที่รันหลาย agent เบื้องหลังแล้วรวมผล มี session budget คุมค่าใช้จ่ายรวมงานใหญ่เกินกว่า subagent ไม่กี่ตัวจะรับไหว

การ "ส่งกลับแค่สรุป" เป็นคุณสมบัติของ subagent เอง ไม่ใช่สิ่งที่ hook หรือ workflow ทำให้ภายหลัง

สรุปสั้นๆ

Context แยก แต่ไฟล์ร่วม subagent ส่งสรุป ไฟล์ละเอียดยังอ่านได้ และถามต่อใน thread เดิมได้

Checkpoint 3

ใน session ของ Managed Agents coordinator ส่ง subagent ไปวิเคราะห์ไฟล์ metrics 60 ไฟล์ subagent เขียนผลละเอียดลง analysis.md แล้วตอบกลับเป็นสรุป 5 บรรทัด ข้อไหนถูก?

  1. Coordinator ได้เนื้อหาทั้ง 60 ไฟล์เข้ามาใน context ด้วย
  2. Thread ของ subagent ปิดทันทีที่ส่งสรุป ถามต่อไม่ได้
  3. Subagent มี sandbox แยกของตัวเอง coordinator จึงเปิดไฟล์นั้นไม่ได้
  4. Coordinator เห็นแค่สรุป แต่เปิด analysis.md อ่านได้เพราะ filesystem แชร์กัน และถาม subagent ต่อได้
ดูเฉลย

D แยกแค่บทสนทนา sandbox และไฟล์ใช้ร่วมกัน และ thread ของ subagent ยังเปิดให้ถามต่อ

Checkpoint 4

คุณกำลังคุยกับ agent หลักเรื่องออกแบบ API แล้วต้องไล่หาสาเหตุ memory leak ที่ต้องอ่านไฟล์และ heap dump เยอะมาก แต่ไม่อยากให้ของพวกนั้นรก context หลัก ใช้อะไร?

  1. Subagent ที่ทำงานใน context ของตัวเองและส่งกลับแค่ข้อสรุป
  2. Agent team ให้หลายตัวช่วยกันคุย
  3. Hook PostToolUse เพื่อย้ายผล tool ออกไป
  4. Workflow script
ดูเฉลย

A B เหมาะกับการร่วมงานแบบเพื่อน ไม่ใช่งานสืบค้นชิ้นเดียว C hook สังเกตหรือบล็อก tool call ได้ แต่ไม่ได้ย้ายผลไป context อื่น D ไม่ใช่กลไกแยก context และไม่ได้เข้าถึง filesystem โดยตรง

3. Fan-out subagent ที่อิสระต่อกันแบบขนาน

Subagent ที่ไม่พึ่งกันรันพร้อมกันได้ ทั้งชุดจะเสร็จในเวลาประมาณ เท่ากับตัวที่ช้าที่สุด เงื่อนไขคือ coordinator ต้อง เรียกทุกตัวใน turn เดียวกัน

  • เรียกทีละตัว (ตัวที่สองรอผลตัวแรก) = เสียความขนาน เวลารวมเท่ากับผลบวกของทุกตัว
  • รวมเป็น subagent ตัวเดียวที่ทำทุกอย่าง = เสียทั้งความขนานและคำสั่งที่โฟกัสเฉพาะทาง

เหมือนสั่งอาหารในร้าน: บอกพนักงานทีเดียวทั้ง 3 จาน ครัวทำพร้อมกัน ได้ครบเมื่อจานที่ช้าที่สุดเสร็จ แต่ถ้าสั่งทีละจานหลังกินจานก่อนหมด ก็รอนานเป็นสามเท่า

สรุปสั้นๆ

อยากได้เวลาเท่าตัวที่ช้าสุด ต้องเรียกทุก subagent ใน turn เดียว

Checkpoint 5

Coordinator มี subagent รีวิวเอกสาร 3 ตัว (ไวยากรณ์ / ความถูกต้องทางเทคนิค / ลิงก์เสีย) ตอนนี้ส่งผลของตัวแรกไปให้ตัวที่สอง แล้วต่อไปตัวที่สาม อยากให้เสร็จในเวลาเท่าตัวที่ช้าสุด ต้องทำยังไง?

  1. เรียกทั้ง 3 ตัวใน turn เดียวกันเพื่อให้รันพร้อมกัน
  2. ให้ส่งผลต่อกันเหมือนเดิม แต่ตั้ง timeout สั้นลง
  3. รวมทั้ง 3 งานเป็น subagent ตัวเดียว
  4. ยกเลิก subagent แล้วให้ agent ตัวเดียวทำ เพราะเร็วกว่าเสมอ
ดูเฉลย

A C เสียความขนานและความเฉพาะทาง B ยังเป็นลำดับต่อกัน D agent ตัวเดียวไม่ได้เร็วกว่าเสมอ

Checkpoint 6

ระบบตรวจ pull request มี subagent ตรวจ performance, accessibility และ i18n ต้องการให้ทั้ง 3 รันพร้อมกัน ข้อไหนถูก?

  1. Coordinator เรียกทั้ง 3 subagent ใน turn เดียว
  2. เรียกทีละตัว พอตัวหนึ่งเสร็จค่อยเรียกตัวถัดไป
  3. รวมเป็น reviewer ตัวเดียวที่ตรวจครบ 3 เรื่อง
  4. ใช้ agent ตัวเดียว แต่สลับโมเดลในแต่ละรอบตรวจ
ดูเฉลย

A B เวลารวมเป็นผลบวก C เสียความขนานและผสมความเชี่ยวชาญคนละด้าน D การสลับโมเดลยังเป็นลำดับต่อกันอยู่ดี

4. เขียน brief ให้ subagent ที่มองไม่เห็น context ของเรา

นึกภาพว่าคุณส่งงานให้ฟรีแลนซ์ที่ไม่เคยเข้าประชุมกับทีมเลย brief ที่ครบในตัวมี 4 ส่วน:

  1. Objective: งานที่ต้องทำแบบเจาะจง รวมข้อเท็จจริงจาก context ของ coordinator ที่ subagent ต้องรู้
  2. Output format: ระบุว่าต้องส่งอะไรกลับมาเป๊ะๆ เพราะข้อความสุดท้ายคือทั้งหมดที่ coordinator จะเห็น
  3. Tools: ชุด tool น้อยที่สุดที่จำเป็น ตั้งไว้ในนิยามของ subagent
  4. Boundaries: อะไรห้ามแตะ และเมื่อไหร่ควรหยุด

Brief ที่แย่ กับ brief ที่ดี

# แย่
"หาสาเหตุให้หน่อย"

# ดี
"เป้าหมาย: หาสาเหตุที่ webhook ส่งซ้ำ 2 ครั้งหลังจ่ายเงินสำเร็จ
 อาการ: เกิดเฉพาะเมื่อ gateway ตอบช้ากว่า 5 วินาที
 ตัดออกแล้ว: payment_client.py, queue_worker.py (ตรวจแล้วปกติ)
 ดูที่: โมดูล retry ใน webhooks/
 เครื่องมือ: อ่านอย่างเดียว ห้ามแก้ไฟล์
 ส่งกลับ: สาเหตุ 1 ประโยค พร้อมชื่อไฟล์และเลขบรรทัด"

Brief แบบแรกทำให้ subagent เริ่มจากศูนย์ ไม่รู้ว่าบั๊กคืออะไร ไม่รู้ว่าไฟล์ไหนตรวจแล้ว อาจไล่ทั้ง codebase ใหม่ แล้วส่งกลับมาในรูปแบบที่เอาไปใช้ต่อไม่ได้

Field ในนิยาม subagent (AgentDefinition)

  • description: coordinator ใช้อ่านเพื่อตัดสินว่าจะเรียก subagent ตัวนี้เมื่อไหร่ ถ้าเขียนกว้างๆ จะ route ผิด
  • prompt: system prompt ของ subagent
  • tools: allowlist ของชื่อ tool ถ้าไม่ใส่ subagent จะได้ทุก tool ที่ subagent ใช้ได้
agents = {
  "doc-reviewer": AgentDefinition(
    description="ตรวจความถูกต้องของเอกสาร API เทียบกับโค้ด ไม่แก้ไฟล์",
    prompt="คุณคือผู้ตรวจเอกสาร ...",
    tools=["Read", "Grep"],      # อ่านกับค้นเท่านั้น ไม่มี Edit/Write/Bash
  )
}

การเขียนใน prompt ว่า "ห้ามแก้ไฟล์" แค่ ขอร้อง ส่วนการตัด tool ออกจาก tools คือ ถอดความสามารถ ทิ้งจากต้นทาง

เข้าใจผิดบ่อย

"ไม่ใส่ field tools แปลว่า subagent ถูกจำกัด" ไม่ใช่ มันจะได้ทุก tool ที่ subagent ใช้ได้ รวม Edit, Write, Bash ถ้าต้องการ read-only ต้องระบุแค่ Read และ Grep

"subagent อ่าน CLAUDE.md แล้วจะรู้ว่าเราคุยอะไรกันมา" ไม่ใช่ CLAUDE.md ไม่ได้พกบทสนทนาของ coordinator ไปด้วย ต้องใส่ข้อมูลที่จำเป็นไว้ใน brief

สรุปสั้นๆ

Brief = objective + output format + tools + boundaries เขียน description ให้ชัด และจำกัด tools เสมอ

Checkpoint 7

หลังคุยกับผู้ใช้เรื่องคู่มือ 3 ฉบับ coordinator ส่ง subagent ด้วย brief ว่า "ช่วยรีวิวเอกสารที่เราคุยกันหน่อย ห้ามแก้ไฟล์นะ" และนิยาม subagent ไม่มี field tools ประเมินยังไง?

  1. ใช้ได้ เพราะ subagent อ่าน CLAUDE.md และคำว่า "ห้ามแก้ไฟล์" ก็กันได้แล้ว
  2. ใช้ได้ เพราะไม่ใส่ tools แปลว่า read-only
  3. ใช้ได้ เพราะ subagent เห็นบทสนทนาก่อนหน้าของ coordinator และ tool ถูกปิดไว้โดย default
  4. Brief กว้างเกิน subagent ไม่รู้ว่าเอกสารไหน และการไม่ใส่ tools ให้ทุก tool ควรระบุแค่ Read และ Grep
ดูเฉลย

D Subagent ไม่เห็นบทสนทนาก่อนหน้า CLAUDE.md ไม่ได้พกมันไป คำขอใน prompt แค่ลดโอกาสแก้ไฟล์ และการไม่ใส่ tools คือได้ทุก tool

Checkpoint 8

ต้องการ subagent ตรวจ changelog ที่อ่านและค้นไฟล์ได้ แต่ห้ามแก้ไฟล์และห้ามรันคำสั่งใดๆ ควรตั้งค่ายังไง?

  1. ตั้ง tools เป็น ["Read", "Grep"]
  2. ไม่ใส่ tools เลย
  3. ให้ Edit และ Write แล้วใช้ hook บล็อกทีหลัง
  4. ตั้ง tools เป็น ["Read", "Grep", "Bash"] เพื่อให้ค้นได้เร็วขึ้น
ดูเฉลย

A ถอดความสามารถเขียนและรันออกตั้งแต่ต้นทาง B ได้ทุก tool รวม Edit/Write/Bash C เปราะกว่าการไม่ให้ตั้งแต่แรก D Bash รันคำสั่งอะไรก็ได้ ขัดกับข้อกำหนด
