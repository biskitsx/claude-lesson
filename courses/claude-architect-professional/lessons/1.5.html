1.5 Task decomposition patterns: chaining, routing, parallelization และ orchestrator-workers

ต้นฉบับ: CertSafari 1.5

อ่านจบแล้วควรทำได้
  • เลือกได้ว่าจะใช้ chaining, routing, parallelization หรือ orchestrator-workers โดยดูว่า รู้ subtask ล่วงหน้าได้หรือไม่
  • จับคู่โมเดลกับแต่ละ subtask ตามความยากและความถี่ของงาน
  • แตกงานที่ต้องดูหลายมิติออกเป็น subagent ใน Agent SDK ที่มี tool และ description ของตัวเอง
  • รู้ว่าเมื่อไหร่ควรย้ายลูปเรียก tool ถี่ๆ ไปไว้ในโค้ดด้วย programmatic tool calling
แนวคิดหลัก: ใครเป็นคนกำหนด subtask

Task decomposition คือการหั่นงานยากหนึ่งชิ้นเป็นงานย่อย (subtask) ให้แต่ละชิ้นมี model call, prompt, ชุด tool หรือแม้แต่โมเดลของตัวเอง คำถามที่แยก pattern ทั้งหมดออกจากกันมีข้อเดียว: subtask ถูกกำหนดโดยคนออกแบบตอนสร้างระบบ หรือโดยโมเดลตอนรันจริง

1. ทำไมแตกงานแล้วผลดีขึ้น

ถ้าสั่ง LLM ครั้งเดียวให้ทำหลายเรื่องพร้อมกัน ความสนใจของโมเดลก็ถูกแบ่งไปทุกเรื่อง แต่ละเรื่องเลยได้น้อยลง พอแยกให้ call หนึ่งรับผิดชอบเรื่องเดียว เช่น call หนึ่งตอบลูกค้า อีก call ตรวจว่าคำถามมีเนื้อหาไม่เหมาะสมไหม ทั้งสองงานมักออกมาดีกว่าการยัดรวมกันใน prompt เดียว วิธีนี้เหมาะกับงานที่มีงานย่อยหลายอันแต่รับใช้เป้าหมายเดียวกัน

เปรียบเหมือนครัวร้านอาหาร ถ้าให้เชฟคนเดียวทั้งหั่นผัก ทอด จัดจาน และล้างจาน งานทุกอย่างจะออกมาพอใช้ แต่ถ้าแบ่งสถานี แต่ละคนโฟกัสงานของตัวเอง คุณภาพจะดีขึ้น แลกกับการที่ต้องส่งของระหว่างสถานี

ราคาที่ต้องจ่ายมี 3 อย่าง:

  • Latency เพิ่ม เพราะมีหลาย call
  • Token เพิ่ม เพราะแต่ละ call ต้องมี prompt และ context ของตัวเอง
  • Context อาจหล่นหาย ทุกครั้งที่ส่งงานต่อจาก call หนึ่งไปอีก call

กฎง่ายๆ: ถ้าเขียนรายการ subtask ได้ตั้งแต่ตอนออกแบบ ให้เขียนลงในโค้ด (chaining, routing, parallelization) ถ้า subtask ขึ้นอยู่กับ input แต่ละครั้ง ให้โมเดลเป็นคนวางแผน (orchestrator-workers)

สรุปสั้นๆ

แตกงานเพื่อให้แต่ละ call โฟกัสเรื่องเดียว แต่ต้องยอมจ่ายเวลา token และความเสี่ยงที่ context หล่นระหว่างทาง

Checkpoint 1

ทีมทำแชตบอตตอบคำถามเรื่องประกันสุขภาพ เดิมใช้ prompt เดียวให้ทั้ง "ตรวจว่าคำถามขอคำวินิจฉัยทางการแพทย์หรือเปล่า" และ "ตอบคำถาม" ตอนนี้แยกเป็น 2 call ข้อได้เปรียบหลักของการแยกคืออะไร?

  1. แต่ละ call โฟกัสงานเดียวเต็มที่ ทั้งการคัดกรองและการตอบจึงแม่นขึ้น
  2. ใช้ token รวมน้อยลง เพราะ prompt แต่ละตัวสั้นลง
  3. ระบบรวมตอบเร็วขึ้น เพราะ call แต่ละตัวสั้นลง
  4. โมเดลจะเลือกเองตอนรันว่าต้องตรวจเรื่องอะไรบ้าง
ดูเฉลย

A การแยกซื้อความแม่นยำด้วยความสนใจเต็มที่ต่องาน ส่วน C กับ B กลับด้าน เพราะ call ที่เพิ่มขึ้นทำให้ช้าลงและใช้ token มากขึ้น ข้อ D เป็นลักษณะของ orchestrator-workers ไม่ใช่การแยก call แบบกำหนดไว้ล่วงหน้า

2. Prompt chaining: ต่อกันเป็นสายพาน

Prompt chaining คือแบ่งงานเป็นขั้นตอนตายตัวเรียงกัน output ของ call ก่อนหน้ากลายเป็น input ของ call ถัดไป ระหว่างขั้นใส่ gate ได้ คือด่านตรวจที่เป็นโค้ดธรรมดา เช็คว่างานยังอยู่ในเส้นทาง ถ้าไม่ผ่านก็หยุดหรือแก้ก่อนที่ความผิดพลาดจะไหลต่อไปขั้นถัดไป

ตัวอย่างการใช้งาน: เขียนข้อความโฆษณาแล้วค่อยแปล หรือเขียน outline → ตรวจ outline ตามเกณฑ์ → ค่อยเขียนเอกสารเต็มจาก outline

เป้าหมายของ chaining คือ ยอมแลก latency เพื่อความแม่นยำ เพราะแต่ละ call มีงานง่ายลง เหมาะเมื่องานแบ่งเป็นขั้นตายตัวได้สะอาด

ตัวอย่าง: แปลงรายงานยอดขายเป็นตาราง

สมมติต้องเอารายงานไตรมาสที่เป็นข้อความยาวมาทำเป็นตาราง markdown แบ่งได้ 4 call:

  1. ดึงชื่อ metric และค่าออกมา
  2. แปลงค่าทั้งหมดให้อยู่ในรูปแบบเดียวกัน (เช่น หน่วยเดียวกัน)
  3. เรียงจากมากไปน้อย
  4. จัดเป็นตาราง markdown

หลังขั้นที่ 1 ใส่โค้ดเช็คว่าได้ metric ครบหรือยัง ถ้าขาด ก็หยุดตรงนั้น ไม่ปล่อยให้ข้อมูลไม่ครบไปถึงตาราง

Claude Code workflow ใช้ pattern เดียวกัน

ใน dynamic workflow ของ Claude Code เราเรียก agent() ครั้งแรกให้คืนรายการไฟล์ตามรูปแบบที่ประกาศไว้ผ่าน option schema แล้วเอารายการนั้นไปขับขั้นต่อไปที่ทำงานทีละไฟล์ ตัวอย่างนี้หา endpoint ที่ลืมเช็คสิทธิ์:

const found = await agent("หาไฟล์ .ts ทั้งหมดใต้ src/api/", {
  schema: {
    type: "object",
    properties: { files: { type: "array", items: { type: "string" } } },
    required: ["files"]
  }
});

const reports = await pipeline(found.files, f =>
  agent(`ตรวจ ${f} ว่ามี route ไหนไม่เช็ค permission`, { label: f })
);
return reports.filter(Boolean);
  • schema บังคับให้ output ของ call แรกเป็น object ที่มี files เป็น array ของ string ขั้นถัดไปจึงวนได้แน่นอน
  • label แค่ตั้งชื่อ agent แต่ละตัวให้อ่านง่าย ไม่ได้คุมรูปแบบ output
  • filter(Boolean) ตัดผลที่ว่างทิ้ง
ลองเดาก่อน

ถ้าเปลี่ยน prompt สกัดข้อมูลตัวเดียวเป็น chain 4 ขั้น จะเกิดอะไร? คำตอบคือ ช้าลงแต่แม่นขึ้น เพราะ chain รันทีละ call ต่อกัน ไม่มีการทำงานซ้อนกัน แต่ละ call ทำงานที่ง่ายลง

เข้าใจผิดบ่อย

"แบ่งเป็น chain แล้วเร็วขึ้น เพราะแต่ละ call เล็กลง" ไม่ใช่ chain รันตามลำดับ เวลารวมคือผลบวกของทุกขั้น จึงช้ากว่า call เดียว

สรุปสั้นๆ

Chaining = ขั้นตอนตายตัวต่อกัน มี gate ตรวจด้วยโค้ดคั่น แลกเวลาเพื่อความแม่นยำ ใน Claude Code ใช้ schema ทำให้ output ของขั้นแรกมีรูปแบบแน่นอน

Checkpoint 2

ใน workflow ของ Claude Code คุณอยากให้ call แรกคืน { "tickets": [...] } ในรูปแบบที่ประกาศไว้ เพื่อให้ขั้นถัดไปวนลูปได้โดยไม่ต้อง parse ข้อความเอง ต้องใส่ option ไหน?

  1. label
  2. tools
  3. context
  4. schema
ดูเฉลย

D schema กำหนดโครงสร้าง output ส่วน label แค่ตั้งชื่อ agent และ tools กำหนดเครื่องมือที่ใช้ได้ ไม่เกี่ยวกับรูปแบบ output

3. Routing: คัดแยกก่อน แล้วส่งให้ผู้เชี่ยวชาญ

Routing คือจัดประเภท input ก่อน แล้วส่งต่อไปยังขั้นเฉพาะทางที่มี prompt, tool หรือโมเดลของตัวเอง เหมือนพนักงานต้อนรับโรงพยาบาลที่ดูอาการแล้วส่งไปแผนกที่ถูก

เหตุผลที่ต้องแยกคือปัญหา interference: ถ้าใช้ prompt เดียวรับทุกประเภท พอจูนให้เก่งเรื่องหนึ่ง เรื่องอื่นมักแย่ลง ตัวอย่างคลาสสิกคือ customer service ที่แยกเป็น 3 ทาง: คำถามทั่วไป, ขอคืนเงิน และปัญหาเทคนิค

Routing ใช้ได้ดีเมื่อ หมวดหมู่แยกกันชัด และ จัดประเภทได้แม่น (ใช้ LLM หรือ classifier แบบดั้งเดิมก็ได้) ถ้าจัดผิดบ่อย ผู้เชี่ยวชาญแต่ละทางจะได้งานที่ไม่ได้ถูกออกแบบมาให้รับ

Routing คือจุดที่เลือกโมเดลให้แต่ละงาน

งานง่ายและเกิดบ่อยใช้โมเดลเล็กราคาถูก งานยากหรือแปลกใหม่ใช้โมเดลที่เก่งกว่า ตัวอย่าง pipeline ซัพพอร์ต: ขั้นจัดประเภท ticket (ปริมาณมาก) ใช้ Haiku ส่วนขั้นร่างแผนแก้ปัญหา (หลายขั้นตอน เป็นปัญหาใหม่) ใช้ Opus

  • ใช้โมเดลใหญ่ทุกขั้น = จ่ายแพงกับงานจัดประเภทธรรมดาทุกวัน
  • ใช้ Haiku ทุกขั้น = ผลักงานยากให้โมเดลที่ทำไม่ไหวอย่างน่าเชื่อถือ
  • สุ่มโมเดล ไม่ใช่ routing เพราะไม่มีอะไรใน input เป็นตัวตัดสินว่าจะไปทางไหน
Model classเหมาะกับ
Haikuงานความถี่สูงที่ latency และต้นทุนสำคัญ เช่น classification, extraction ง่ายๆ
Sonnetงานทั่วไปในชีวิตประจำวัน รวมถึงเป็น subagent ปริมาณมากในระบบ multi-agent
Class ที่เก่งกว่า เช่น Opusงานช้า หลายขั้นตอน หรือปัญหาที่ยังไม่เคยแก้มาก่อน

ใน Agent SDK นิยามของ subagent แต่ละตัวมี field model (ไม่บังคับใส่) ทำให้ classifier ราคาถูกกับตัวร่างงานราคาแพงอยู่ในระบบเดียวกันได้ และเมื่อเป็นระบบ agent การ routing ก็คือการส่งงานไปหา specialist agent แทนที่จะเป็น specialist prompt

สรุปสั้นๆ

Routing ได้ผลก็ต่อเมื่อ classifier แม่น ถ้าส่งผิดทางบ่อย ให้แก้ที่ขั้นจัดประเภทก่อน และใช้ routing เป็นจุดจับคู่โมเดลกับความยากของงาน

Checkpoint 3

ระบบ HR แยกคำถามพนักงานเป็น "เรื่องวันลา" กับ "เรื่องเงินเดือน" แล้วส่งให้ prompt เฉพาะทาง แต่ log พบว่าคำถามเรื่องหักเงินเพราะลาเกินมักไปตกที่ฝั่งวันลา ซึ่งตอบเรื่องเงินไม่ได้ ควรแก้อะไรเป็นอย่างแรก?

  1. ปรับขั้นจัดประเภทให้แยกเคสแบบนี้ได้แม่นขึ้น
  2. เปลี่ยน prompt ฝั่งวันลาให้ใช้โมเดลที่ใหญ่ขึ้น
  3. รวมทั้งสองฝั่งกลับเป็น prompt เดียว
  4. เพิ่มหมวดใหม่อีก 3 หมวด
ดูเฉลย

A ต้นเหตุคือการจัดประเภทผิด โมเดลใหญ่ขึ้นที่ปลายทางไม่ทำให้งานถูกส่งมาถูกที่ การรวมกลับเป็น prompt เดียวทำให้ปัญหา interference กลับมา และเพิ่มหมวดก็ไม่ได้แก้ที่ classifier

Checkpoint 4

ระบบตรวจรีวิวสินค้ามี 2 ขั้น: (1) ติดป้ายรีวิวหลายแสนรายการต่อวันว่าเป็นบวก/ลบ/ร้องเรียน และ (2) สำหรับรีวิวร้องเรียนที่ซับซ้อน ร่างแผนแก้ปัญหาข้ามหลายแผนก ควรจัดโมเดลอย่างไร?

  1. Opus ทั้งสองขั้น แต่ตั้ง effort ต่ำในขั้นแรก
  2. Haiku ทั้งสองขั้น แล้วเขียน prompt ขั้นที่ 2 ให้ยาวและละเอียดมาก
  3. สุ่มโมเดลแต่ละ request เพื่อเฉลี่ยต้นทุน
  4. Haiku สำหรับขั้นติดป้าย และ Opus สำหรับขั้นร่างแผน
ดูเฉลย

D จับคู่โมเดลกับความยากและความถี่ของแต่ละงาน ข้อ A ยังใช้โมเดลแพงกับงานง่ายปริมาณมาก ข้อ B prompt ยาวชดเชยความสามารถที่ไม่พอไม่ได้ ข้อ C ไม่ใช่ routing เพราะไม่ได้ดูจาก input เลย

4. Parallelization: sectioning กับ voting

Parallelization คือรันหลาย model call พร้อมกัน แล้วใช้โค้ดรวมผล มี 2 แบบ:

  • Sectioning แบ่งเป็นงานย่อยที่ไม่พึ่งกันแล้วรันคู่กัน เช่น call หนึ่งตอบผู้ใช้ อีก call คัดกรองเนื้อหาไม่เหมาะสม ซึ่งมักดีกว่าให้ call เดียวทำทั้งสองอย่าง หรือ eval อัตโนมัติที่ให้แต่ละ call ให้คะแนนคนละด้านของคำตอบ
  • Voting รันงานเดียวกันหลายครั้งแล้วรวมคำตอบเพื่อให้มั่นใจขึ้น เช่น ใช้หลาย prompt ตรวจช่องโหว่ในโค้ดชุดเดียวกัน ถ้าตัวไหนเจอปัญหาก็ flag หรืองาน moderation ที่ปรับ threshold ของจำนวนเสียงโหวตเพื่อถ่วงดุลระหว่าง false positive กับ false negative

จำง่ายๆ: sectioning = คนละงาน ทำพร้อมกัน, voting = งานเดียวกัน ทำหลายรอบ

ลองเดาก่อน

ถ้าระบบกระจายคำถามไปให้ subagent 5 ตัวทำพร้อมกัน สิ่งที่ได้หลักๆ คืออะไร? คำตอบคือ ความครอบคลุมที่ละเอียดขึ้น โดยมักใช้ token มากขึ้น และเวลารวมอาจนานขึ้นด้วย

แยกเรื่องความเร็วกับต้นทุนออกจากกัน

  • งานย่อยที่รันพร้อมกันจะเสร็จตามเวลาของ ตัวที่ช้าที่สุด ไม่ใช่ผลรวมของทุกตัว
  • แต่ทั้งระบบ multi-agent มักใช้ token มากกว่า agent ตัวเดียวประมาณ 3–10 เท่า และเวลารวมมักนานกว่าด้วย
  • ดังนั้นเลือก parallelization เพื่อ ความครอบคลุมหรือความมั่นใจ และต้องยอมรับค่าใช้จ่ายที่สูงขึ้น

"รัน agent แบบขนานเพื่อให้งานเสร็จเร็วและถูกลง" ไม่ใช่ การรันขนานไม่ได้ลดต้นทุน และไม่รับประกันว่าจะเร็วขึ้น สิ่งที่ซื้อได้คือความครอบคลุม

สรุปสั้นๆ

Sectioning แบ่งงานต่างกันไปทำพร้อมกัน, voting ทำงานเดียวกันซ้ำเพื่อความมั่นใจ ทั้งสองแบบได้ความละเอียด ไม่ใช่ความถูก

  2. Sectioning
  3. Prompt chaining
  4. Orchestrator-workers
ดูเฉลย

A งานเดียวกันรันหลายรอบแล้วรวมผลด้วย threshold คือ voting ถ้าเป็น sectioning แต่ละ call ต้องตรวจคนละเรื่อง chaining รันต่อกันเป็นลำดับ และ orchestrator-workers ต้องมีโมเดลคิด subtask ตอนรัน

5. Orchestrator-workers: ให้โมเดลวางแผนงานย่อยเอง

ใน orchestrator-workers มีโมเดลตัวกลาง (orchestrator) อ่านงาน ตัดสินว่าต้องทำ subtask อะไรบ้าง ส่งให้ worker ทำ แล้วรวมผล หน้าตาคล้าย sectioning แต่ต่างตรงที่ subtask ไม่ได้ถูกกำหนดไว้ล่วงหน้า orchestrator คิดให้ใหม่ตาม input ทุกครั้ง ตัวอย่างคลาสสิกคืองานแก้โค้ดที่ไม่รู้ล่วงหน้าว่าจะต้องแตะกี่ไฟล์หรือแก้อะไร

async def investigate(incident):
    angles = await lead.plan(incident)          # lead แตกปัญหาเป็นมุมที่ต้องสืบ
    jobs = [worker(a) for a in angles]          # worker หนึ่งตัวต่อหนึ่งมุม
    findings = await asyncio.gather(*jobs)      # รันพร้อมกัน
    return await lead.summarize(findings)       # lead รวมผล

จำนวน worker ในโค้ดนี้ขึ้นกับรายการ angles ที่ lead สร้างขึ้นตอนรัน ไม่ได้เขียนตายตัว

ข้อจำกัดและวิธีลดต้นทุน

  • ใช้ N+1 call ต่อการรันหนึ่งครั้ง (orchestrator 1 + worker N)
  • คุณภาพทั้งหมดขึ้นกับแผนของ orchestrator จึงต้องลงแรงกับ prompt ของ orchestrator มากที่สุด
  • ลดต้นทุนด้วยการแบ่งโมเดล: ใช้โมเดลเก่งอย่าง Opus วางแผน และโมเดลถูกอย่าง Haiku เป็น worker

ไม่ควรใช้เมื่อ: งานง่ายที่ได้ output ชิ้นเดียว, เส้นทางที่ latency สำคัญมาก, หรือ subtask เหมือนเดิมทุกครั้ง (กรณีหลังใช้ parallelization ที่กำหนดไว้ล่วงหน้าจะง่ายกว่า)

Managed Agents: dynamic workflows

Managed Agents มีความสามารถนี้ในชื่อ dynamic workflows: agent เขียน "workflow" ขึ้นมาเป็นโปรแกรมที่รัน agent จำนวนมากเป็นเฟสๆ แล้วรวมผล ตัว server รันให้ใน background งานที่ใช้บ่อยคือ audit, migration, deep research และการตรวจไขว้ (cross-checking) เนื่องจาก agent ทุกตัวในการรันกิน token จึงควรตั้ง session budget เพื่อคุมค่าใช้จ่ายรวม

Patternใครกำหนด subtaskใช้เมื่อ
Prompt chainingคนออกแบบ เป็นลำดับตายตัวงานแบ่งเป็นขั้นตายตัวได้ และความแม่นสำคัญกว่าความเร็ว
Routingคนออกแบบ เป็นชุดหมวดหมู่input แบ่งเป็นหมวดชัดเจนและจัดประเภทได้แม่น
Parallelization: sectioningคนออกแบบ เป็นชิ้นที่ไม่พึ่งกันแต่ละด้านควรได้ call ที่โฟกัสของตัวเอง
Parallelization: votingคนออกแบบ เป็นการทำซ้ำต้องการความมั่นใจจากหลายรอบหรือหลายมุมมอง
Orchestrator-workersโมเดล orchestrator ตอนรัน ต่อ inputเดา subtask ล่วงหน้าไม่ได้
เข้าใจผิดบ่อย

"งานไหนมีหลาย subtask ให้ใช้ orchestrator-workers เป็นค่าเริ่มต้น" ไม่ใช่ คุณค่าของมันคือการเลือก subtask ตอนรัน ถ้า subtask คาดเดาได้อยู่แล้ว parallelization แบบกำหนดล่วงหน้าง่ายและถูกกว่า

สรุปสั้นๆ

Orchestrator-workers = โมเดลคิดงานย่อยตาม input จ่าย N+1 call, ลงแรงที่ prompt ของ orchestrator, ใช้โมเดลเก่งวางแผนและโมเดลถูกทำงาน และตั้ง session budget เมื่อใช้ dynamic workflows

6. แตกงานเป็น subagent ใน Agent SDK

ใน Agent SDK การแตกงานทำผ่าน subagent นิยามได้ 2 ทาง: ผ่าน option agents ในโค้ด หรือเป็นไฟล์ markdown ในโฟลเดอร์ .claude/agents/ แล้ว agent หลักเรียกใช้ผ่าน Agent tool

subagent แต่ละตัวมีบทสนทนาของตัวเอง tool call ระหว่างทางอยู่ในนั้น มีแค่ข้อความสุดท้ายที่ส่งกลับไปให้ตัวแม่ บางครั้งเหตุผลที่แยกก็แค่ไม่อยากให้ output ยาวเหยียดของ tool ไหลเข้า context ของ agent หลัก แม้จะไม่ได้รันขนานเลยก็ตาม

Field ของ AgentDefinitionบังคับ?หน้าที่
descriptionบังคับบอกว่าควรใช้ agent นี้เมื่อไหร่ orchestrator อ่านอันนี้เพื่อตัดสินว่าจะส่งงานไหนให้ใคร
promptบังคับsystem prompt ของผู้เชี่ยวชาญตัวนั้น
toolsไม่บังคับรายชื่อ tool ที่อนุญาต ถ้าไม่ใส่ จะได้ทุก tool ที่ subagent ใช้ได้ อยากจำกัดต้องใส่เอง
disallowedToolsไม่บังคับรายชื่อ tool ที่ห้าม
modelไม่บังคับใช้โมเดลอื่นแทนค่าเริ่มต้นสำหรับ agent ตัวนี้

ตัวอย่าง: ตรวจ codebase 3 มิติ

สมมติต้อง audit codebase ใหญ่ใน 3 ด้าน: ช่องโหว่ความปลอดภัย, คุณภาพโค้ด และ test coverage แต่ละด้านใช้ tool และโฟกัสต่างกัน ทางที่ดีคือ orchestrator หนึ่งตัวกับ subagent 3 ตัว แต่ละตัวมี description และชุด tool ตรงกับด้านของตัวเอง scanner, style checker และ coverage checker ก็รันพร้อมกันได้

agents = {
    "security": AgentDefinition(
        description="ใช้เมื่อต้องหาช่องโหว่ความปลอดภัย",
        prompt="คุณคือผู้เชี่ยวชาญ AppSec ...",
        tools=["Read", "Grep", "Bash"],
    ),
    "coverage": AgentDefinition(
        description="ใช้เมื่อต้องวัด test coverage",
        prompt="คุณดูแลคุณภาพ test ...",
        tools=["Read", "Bash"],
        model="haiku",
    ),
    # "quality": ...
}

ทางเลือกที่ดูดีแต่ไม่แก้ปัญหา:

  • Prompt เดียวให้ agent หลักทำทั้ง 3 ด้านตามลำดับ: output ทุกด้านกองอยู่ใน context เดียว คุณภาพตกลงเมื่อ context โตขึ้น
  • MCP server ตัวเดียวเปิดทุกการตรวจเป็น tool: ไม่ได้แยกอะไรเลย agent เดียวยังต้องถือ tool หลายโดเมน และเมื่อมี tool ราว 20 ตัวขึ้นไปจะเริ่มเลือกผิด
  • ใช้ context window ใหญ่ขึ้น + extended thinking: แค่เพิ่มที่ให้ขยะกองมากขึ้น คุณภาพยังตกเมื่อ context ยาว
สรุปสั้นๆ

Subagent = context แยก, ส่งกลับแค่ข้อความสุดท้าย, มี description ให้ orchestrator ใช้ตัดสินใจ และต้องใส่ tools เองถ้าอยากจำกัด tool

  2. subagent ใช้ tool ไม่ได้เลย

7. ย้ายลูปเรียก tool ถี่ๆ ไปไว้ในโค้ด: programmatic tool calling

บางครั้งปัญหาไม่ได้อยู่ที่ subtask แต่อยู่ที่ tool call เล็กๆ จำนวนมากในขั้นเดียว การเรียก tool แบบปกติทุกครั้งต้องวิ่งกลับผ่านโมเดล (round trip) และผลของแต่ละครั้งก็ถูกเพิ่มเข้า context

Programmatic tool calling ให้ Claude เขียนโค้ดที่เรียก tool ของเราภายใน code execution container ลูปจึงไปรันใน container แทนที่จะวนผ่านโมเดลทุก call และโค้ดกรองผลก่อน ทำให้ข้อมูลก้อนใหญ่ไม่เข้า context เลย ประหยัดทั้ง latency และ token ต้องใช้ code execution tool เวอร์ชัน code_execution_20260120 ขึ้นไป

ตัวอย่าง: ตรวจว่าร้านสาขาไหนสต็อกต่ำกว่าเกณฑ์ใน 30 สาขา แบบปกติคือ 30 round trip และดึงรายการสินค้าหลายพันบรรทัดเข้า context แบบ programmatic คือ script เดียวเรียก lookup 30 ครั้ง กรองแล้วคืนแค่สาขาที่ต่ำกว่าเกณฑ์ Claude ได้คิดบนข้อมูลไม่กี่บรรทัด

ทางเลือกที่ดูคล้ายแต่ไม่ช่วย

  • Message Batches API ทำงานแบบ async และแต่ละ request อิสระจากกัน เหมาะกับงานปริมาณมากที่ไม่มีใครรอ (ส่วนใหญ่เสร็จภายในชั่วโมง) แต่ เอาผลของ request หนึ่งไปป้อนขั้นถัดไปของลูปที่กำลังรันสดไม่ได้
  • Subagent หนึ่งตัวต่อหนึ่ง tool call ช่วยให้ context ของ orchestrator สะอาดก็จริง แต่เพิ่ม agent ทั้งตัวต่อการเรียกหนึ่งครั้ง และ multi-agent ใช้ token ราว 3–10 เท่า overhead จึงยิ่งแย่
ในข้อสอบ: จับคู่ปัญหากับวิธีแก้
  • overhead มาจาก tool call เล็กๆ จำนวนมากในขั้นเดียว → programmatic tool calling
  • งานที่ไม่เกี่ยวกันกองรวมใน context เดียว → subagents
  • งานปริมาณมากที่ไม่มีใครรอคำตอบ → batches
เข้าใจผิดบ่อย

"เอาลูป tool call เล็กๆ ไปใส่ใน Message Batches จะลด overhead" ไม่ใช่ batch เป็น async และแต่ละ request อิสระ ผลของ call หนึ่งไปขับ call ถัดไปไม่ได้ ส่วน programmatic tool calling รันลูปในโค้ดและตัด round trip ผ่านโมเดลออก

"เพิ่ม effort แล้วลูปจะเร็วขึ้น" ไม่ใช่ effort เพิ่มความลึกในการคิดต่อ turn แต่ไม่ลดจำนวน turn

สรุปสั้นๆ

ลูป tool ถี่ๆ ให้ Claude เขียนโค้ดรันใน container แล้วกรองผลก่อนเข้า context ไม่ใช่ batch และไม่ใช่ subagent ต่อ call

Checkpoint 10

Workflow ตรวจราคาคู่แข่งต้องเรียก tool ดึงราคาหลายร้อยครั้งในลูปเดียว ทุก tool-use turn ทำให้ latency และ token พุ่ง วิธีไหนแก้ตรงจุดที่สุด?

  1. ส่งแต่ละการดึงราคาเป็น request ใน Message Batches API
  2. เพิ่ม effort ให้โมเดลวางแผนลูปให้ดีขึ้น
  3. สร้าง subagent แยกต่อการดึงราคาแต่ละครั้ง
  4. ใช้ programmatic tool calling ให้ Claude เรียก tool จากโค้ดใน code execution container
