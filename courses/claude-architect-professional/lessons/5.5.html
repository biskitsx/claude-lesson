5.5 Bias, fairness and honest outputs in Claude builds

ต้นฉบับ: CertSafari 5.5

อ่านจบแล้วควรทำได้
  • ชี้ได้ว่า bias เข้ามาในระบบที่สร้างบน Claude ได้ทางไหนบ้าง: training data, prompt และตัวอย่าง, retrieval corpus และ evaluation set
  • วัด fairness ด้วยการเทียบผลลัพธ์รายกลุ่ม แทนที่จะสันนิษฐานเอาว่ายุติธรรมแล้ว
  • ทำให้คำอธิบายของระบบสม่ำเสมอไม่ว่าผู้ใช้จะถามด้วยถ้อยคำแบบไหน แล้วทดสอบซ้ำ
  • แยก output ที่ calibrated และไม่ชี้นำ ออกจาก output ที่มั่นใจเกินจริง เข้าข้างเกินไป หรือดันผู้ใช้ไปทางใดทางหนึ่ง
  • มองภาษา accessibility และช่องทางเป็น design decision ที่กำหนดว่าระบบจะทิ้งใครไว้ข้างหลัง
แนวคิดหลัก: ระบบจะลอกสิ่งที่ input ของมันถือว่า "ปกติ"

ระบบที่สร้างบน Claude จะทำซ้ำสิ่งที่ input ทั้งหมดของมันมองว่าเป็นค่าปกติ ทั้ง training data, ตัวอย่างใน prompt, เอกสารที่ retrieve มา และ test case ดังนั้น bias เป็นเรื่องของ architecture ไม่ใช่แค่เรื่อง policy และ fairness มีอยู่จริงเฉพาะในกลุ่มที่มีคนวัดไว้แล้ว เท่านั้น

1. Bias เข้ามาในระบบได้ทางไหน

ลองนึกก่อนอ่านต่อ: ผู้ช่วยคัดกรองผู้สมัครงานเขียนเหตุผลที่เอียงเข้าหากลุ่มหนึ่งตลอด เราควรไปหาสาเหตุที่ไหน? ถ้าตอบว่า "ที่โมเดล" อย่างเดียว ยังไม่พอ สาเหตุอาจซ่อนอยู่ได้ 4 ที่ และถ้าเช็กแค่ที่เดียวก็พลาดอีกสามที่

ทางเข้าที่ 1: Training data

โมเดลรู้เท่าที่มันเคยเห็น เรื่องที่พบบ่อยและข้อมูลสอดคล้องกันจะครอบคลุมดี ส่วนเรื่องที่หายาก เฉพาะท้องถิ่น เฉพาะกลุ่ม หรือยังถกเถียงกันอยู่ จะอ่อนกว่า และภาพ "ปกติ" ในหัวโมเดลจะสะท้อนสิ่งที่มีมากที่สุดใน training เช่น ถามเรื่องขั้นตอนราชการของเทศบาลเล็กๆ ในต่างจังหวัด อาจได้คำตอบที่ฟังดูมั่นใจแต่อิงขั้นตอนของกรุงเทพฯ

ทางเข้าที่ 2: Prompt และ few-shot examples

ถ้าตัวอย่าง "ผู้สมัครที่ดี" ใน prompt ทุกตัวเดินเส้นทางอาชีพแบบเดียวกัน (เช่น จบมหาวิทยาลัยดัง แล้วเข้าบริษัทใหญ่) โมเดลจะยึดเส้นทางนั้นเป็นแม่แบบ คนที่มาทางอื่นจะได้คะแนนน้อยลงโดยไม่มีใครตั้งใจ ข้อดีคือ ตัวอย่างเป็นแหล่ง bias ที่ เราคุมเองได้ 100%

ทางเข้าที่ 3: Retrieval corpus

เอกสารที่เราป้อนผ่าน retrieval กลายเป็นส่วนหนึ่งของสิ่งที่โมเดล "รู้" สำหรับงานนั้น ถ้าคลังนโยบายมีแต่ขั้นตอนของสำนักงานใหญ่ พนักงานสำนักงานใหญ่จะได้คำตอบที่มีหลักฐานชัด ส่วนพนักงานสาขาต่างจังหวัดได้คำตอบบางๆ หรือคำตอบที่ไม่ตรงกับบริบทของตัวเอง

ทางเข้าที่ 4: Evaluation set

ถ้า test set มีแต่เคสทั่วไป ระบบที่พังกับบางกลุ่มก็ยังสอบผ่านได้ เพราะกลุ่มนั้นไม่เคยถูกทดสอบเลย ตัวเลขดูสวยไม่ได้แปลว่ายุติธรรม แปลว่า "ยุติธรรมกับกลุ่มที่อยู่ใน test set"

ทางเข้าอาการที่เห็นจับได้ตรงไหน
Training dataความครอบคลุมไม่เท่ากัน บางกลุ่มหรือบางพื้นที่ถูกมองเป็น "นอกค่าปกติ"ทดสอบเคสที่หายาก เฉพาะท้องถิ่น และเป็นประเด็นถกเถียง ไม่ใช่แค่เคสที่พบบ่อย
Prompt และ few-shot examplesตัวอย่างสอนให้โปรไฟล์เดียวเป็นแม่แบบของ "ดี"รีวิวตัวอย่างว่าทิ้งใครไว้ข้างนอกบ้าง
Retrieval corpusกลุ่มที่มีเอกสารเยอะได้คำตอบมีหลักฐาน กลุ่มอื่นได้คำตอบบางaudit ว่า corpus ครอบคลุมอะไรจริงๆ
Evaluation setmetric ดูดีเพราะกลุ่มที่ขาดไม่เคยถูกทดสอบเพิ่มเคสและแยก segment ให้ครบทุกกลุ่มที่ได้รับผลกระทบ
เข้าใจผิดบ่อย

"bias มาจาก training data ของโมเดลเท่านั้น" ผิด prompt, เอกสารที่ retrieve มา และ test set ก็ใส่ bias เข้าระบบได้ และสามอย่างหลังนี้เป็นของที่ทีมเราคุมเองทั้งหมด

สรุปสั้นๆ

bias มี 4 ทางเข้า: training data, prompt/ตัวอย่าง, retrieval corpus, evaluation set เวลาเจออาการเอียง ให้ไล่เช็กครบทั้งสี่ ไม่ใช่โทษโมเดลอย่างเดียว

Checkpoint 1 (จับคู่)

จับคู่อาการกับทางเข้าของ bias (A = Training data, B = Prompt/ตัวอย่าง, C = Retrieval corpus, D = Evaluation set)

  1. แชตบอตสหกรณ์ตอบเรื่องสินเชื่อของสาขาในเมืองได้ละเอียด แต่สาขาอำเภอได้คำตอบกว้างๆ เพราะคู่มือที่อัปโหลดมีแต่ของสาขาในเมือง
  2. ระบบผ่าน eval ด้วยคะแนน 94% แต่ไม่มีเคสของผู้ใช้สูงอายุอยู่ใน test set เลย และกลุ่มนี้ร้องเรียนเยอะ
  3. ผู้ช่วยแนะนำอาหารเข้าใจอาหารพื้นบ้านของชนกลุ่มน้อยน้อยมาก แม้ prompt และเอกสารจะไม่ได้เกี่ยวข้อง
  4. ตัวอย่าง "รีวิวพนักงานดีเด่น" ใน prompt เป็นพนักงานขายทั้งหมด พนักงานฝ่ายสนับสนุนเลยได้คะแนนต่ำกว่า
ดูเฉลย

1-C, 2-D, 3-A, 4-B คู่มือที่ป้อนเข้า = corpus, กลุ่มที่ไม่อยู่ใน test = evaluation set, ความรู้พื้นฐานของโมเดลที่บาง = training data, แม่แบบจากตัวอย่าง = prompt

2. วัด fairness ข้ามกลุ่ม และข้ามสำนวนการถาม

Fairness ต้อง วัด ไม่ใช่ สันนิษฐาน การลบชื่อกลุ่ม (เพศ เชื้อชาติ ศาสนา) ออกจาก prompt ไม่ได้ทำให้ output ยุติธรรมโดยอัตโนมัติ เพราะสัญญาณของกลุ่มยังรั่วผ่านข้อมูลอื่นได้ เช่น ที่อยู่ ชื่อโรงเรียน หรือสำนวนภาษา

วิธีวัดคือเอา outcome metric มาเทียบกัน ราย segment เช่น

  • อัตราการอนุมัติ (approval rate)
  • อัตราการได้เข้ารอบ (shortlist rate)
  • อัตราความผิดพลาด (error rate)

ตัวเลข accuracy รวมตัวเดียวซ่อนปัญหาได้ง่ายมาก ระบบอาจแม่น 95% โดยรวม แต่ error เกือบทั้งหมดไปกองอยู่ที่กลุ่มเล็กกลุ่มเดียว

สำนวนการพิมพ์ก็เป็น "กลุ่ม" แบบหนึ่ง

ตัวอย่างจากผู้ช่วยตรวจคุณสมบัติสินเชื่อ: ผู้สมัครสองคนมีข้อมูลเหมือนกันทุกอย่าง คนที่พิมพ์ภาษาทางการได้เหตุผลการปฏิเสธที่ละเอียด ส่วนคนที่พิมพ์ภาษาพูดได้คำตอบคลุมเครือ ผลคือ คนที่สื่อสารเก่งอยู่แล้วได้รับการปฏิบัติที่ดีกว่า ซึ่งเป็นความไม่เป็นธรรมที่ไม่ต้องมีชื่อกลุ่มใดๆ อยู่ใน prompt เลย

วิธีแก้ที่ถูก มีสองท่อนต้องทำคู่กัน:

  1. กำหนด decision factor ชุดมาตรฐาน ที่ทุกคำอธิบายต้องอ้างถึง (เช่น รายได้ ภาระหนี้ ประวัติชำระ อายุงาน)
  2. ทดสอบซ้ำ ด้วยคำถามหลายสำนวนที่ขอข้อมูลชุดเดียวกัน แล้วเทียบว่าคำอธิบายครบเท่ากันไหม
ทุกครั้งที่ปฏิเสธใบสมัคร ให้อธิบายครบทั้ง 4 หมวดเสมอ:
1) รายได้ต่อเดือนเทียบเกณฑ์  2) สัดส่วนภาระหนี้
3) ประวัติการชำระ           4) อายุงาน
ใช้ระดับรายละเอียดเท่ากัน ไม่ว่าผู้สมัครจะพิมพ์มาแบบไหน

ทางลัดที่ดูดีแต่ไม่แก้

ทางลัดทำไมไม่ผ่าน
ตัดคำอธิบายทิ้งทั้งหมดเสีย transparency ผู้ถูกปฏิเสธไม่มีอะไรให้เข้าใจหรือโต้แย้ง
ให้รายละเอียดเฉพาะคนที่ขอฝังความไม่เท่าเทียมลงไปใน policy เลย คนที่กล้าถามได้มากกว่า
แปะ disclaimer ว่า "คำอธิบายอาจแตกต่างกัน"แค่บรรยายปัญหา พฤติกรรมของ prompt ที่เป็นต้นเหตุยังอยู่เหมือนเดิม
ในข้อสอบ

ให้เลือกคำตอบที่ แก้ prompt คู่กับ re-test คำตอบที่แค่ประกาศ (disclose) ระงับ (suppress) หรือจำกัดการให้ (ration) output ล้วนทิ้งต้นเหตุไว้ที่เดิม

เข้าใจผิดบ่อย

"ใส่ disclaimer แล้วถือว่าจัดการเรื่อง fairness แล้ว" ผิด disclaimer ไม่ได้เปลี่ยนพฤติกรรมที่ทำให้ผลไม่สม่ำเสมอ

สรุปสั้นๆ

เทียบ outcome metric ราย segment อย่าเชื่อตัวเลขรวม มองสำนวนการพิมพ์เป็นมิติหนึ่งของกลุ่ม แก้ด้วย decision factor มาตรฐาน + re-test หลายสำนวน

Checkpoint 2

ผู้ช่วยตอบเรื่องสิทธิประกันสังคมให้คำอธิบายละเอียดกับคนที่พิมพ์ภาษาทางการ แต่ตอบสั้นห้วนกับคนที่พิมพ์ภาษาพูดหรือสะกดผิด ทั้งที่กรณีเหมือนกัน ทีมควรทำอะไร?

  1. เพิ่มปุ่ม "ขอรายละเอียดเพิ่ม" ให้คนที่อยากรู้ลึกกดเอง
  2. เขียน prompt ให้ทุกคำตอบต้องครอบคลุมหมวดเงื่อนไขชุดเดียวกัน แล้วทดสอบซ้ำด้วยคำถามหลายสำนวนที่ถามเรื่องเดียวกัน
  3. ให้ระบบตอบแค่ "มีสิทธิ์/ไม่มีสิทธิ์" โดยไม่อธิบาย เพื่อให้ทุกคนได้เท่ากัน
  4. เพิ่มข้อความใต้คำตอบว่า "ระดับรายละเอียดอาจต่างกันตามคำถาม"
ดูเฉลย

B แก้ต้นเหตุที่ prompt แล้วยืนยันด้วย re-test A ทำให้คนที่ไม่รู้ว่าต้องกดเสียเปรียบ C ตัด transparency ทิ้ง D แค่ประกาศปัญหา

Checkpoint 3

ทีม red-team ของธนาคารรายงานว่า ผู้ช่วยอธิบายผลประเมินบัตรเครดิตให้รายละเอียดต่างกันตามความสละสลวยของคำถาม ผู้บริหารถามว่าจะปิดประเด็นนี้ยังไง ข้อไหนเหมาะที่สุด?

  1. ปิดฟีเจอร์คำอธิบายจนกว่าจะมีโมเดลรุ่นใหม่
  2. ทำให้ prompt คำอธิบายเป็นมาตรฐานเดียว อ้าง decision factor ชุดเดียวกันทุกครั้ง แล้ว re-test ด้วยหลายสำนวน
  3. ให้รายละเอียดเต็มเฉพาะลูกค้าที่โทรเข้าคอลเซ็นเตอร์ขอเพิ่ม
  4. คง prompt เดิมไว้ แต่เพิ่ม disclaimer ในหน้าเว็บ
ดูเฉลย

B จับคู่การแก้ prompt กับ re-test A เอา transparency ออก C สร้างความต่างด้านการเข้าถึงใหม่ D เปิดเผยแต่ไม่แก้

3. ความมั่นใจที่ซื่อตรง และพื้นที่ให้ผู้ใช้คิดเอง

ความซื่อตรงของ output มีสองด้าน: calibration (ความมั่นใจที่แสดงออกตรงกับน้ำหนักของหลักฐาน) และ non-steering (ไม่ดันผู้ใช้ไปสู่ข้อสรุปที่ระบบเลือกไว้แล้ว)

Calibration สำคัญที่สุดเมื่อหลักฐานก้ำกึ่ง

ตัวอย่าง: ระบบช่วยคัดผู้สมัครเจอเคสที่หลักฐานปนกัน เช่น ทักษะตรงแต่ประสบการณ์สั้น และมีช่วงว่างงานที่ไม่มีคำอธิบาย คำอธิบายที่ดีควร

  • บอกตรงๆ ว่าหลักฐาน ผสมกัน
  • อธิบายว่า ทำไม ถึงผสม (อะไรสนับสนุน อะไรค้าน)
  • ระบุจุดที่ ข้อมูลไม่พอ จะตัดสิน

ไม่ควรฟันธงแบบมั่นใจ และไม่ควรเลือกอ่านแบบที่เข้าข้างผู้สมัครมากที่สุด

เทคนิคที่ช่วยได้: อนุญาตใน prompt ให้โมเดลบอกได้ว่าข้อมูลไม่พอ วิธีนี้ลดการพูดเรื่องผิดแบบมั่นใจ แต่ต้องแยกให้ออกจากการ "ไม่ตอบอะไรเลย" เมื่อไฟล์ไม่ครบ การส่งช่องว่างกลับไปไม่บอกอะไรผู้ใช้ ส่วนการบอกว่า "ไม่แน่ใจเรื่อง X เพราะขาดเอกสาร Y" บอก recruiter ว่าต้องไปดูตรงไหนต่อ

อีกทางที่ดูปลอดภัยแต่ไม่ใช่ calibration คือ บังคับให้ตอบแต่คำพูดที่ยกมาจากเรซูเม่ตรงๆ เพราะมันซ่อน judgement ที่ผู้ใช้ต้องการไว้ชั่งน้ำหนัก ทั้งที่การสังเคราะห์คือเหตุผลที่ tool นี้มีอยู่

ถ้าหลักฐานในไฟล์ขัดกันหรือไม่พอ ให้บอกตรงๆ ว่าหลักฐานก้ำกึ่ง
อธิบายว่าส่วนไหนสนับสนุน ส่วนไหนค้าน และระบุข้อมูลที่ขาด
ห้ามเดาเพื่อให้คำตอบดูมั่นใจ

Non-steering และ epistemic autonomy

Epistemic autonomy คือสิทธิ์ของผู้ใช้ที่จะไปถึงข้อสรุปด้วยการคิดของตัวเอง ตัวอย่าง: tool ให้ feedback เรียงความที่คอยดันนักเรียนไปเข้าข้างหนึ่งของประเด็นถกเถียงทุกครั้ง แม้คำแนะนำแต่ละครั้งจะดูมีเหตุผล แต่รวมกันแล้วกัดกร่อนความสามารถในการคิดเองของนักเรียน

แนวทางที่ Claude ถูกออกแบบไว้:

  • ระมัดระวังในการแสดง ความเห็นส่วนตัวในประเด็นที่ถกเถียงกัน และอาจเลือกไม่แสดงเพื่อไม่ให้ไปมีอิทธิพลกับผู้คน
  • เสนอ มุมมองทางเลือก ให้ผู้ใช้คิดต่อเอง
  • ถ้าผู้ใช้ขอ "เหตุผลที่แข็งที่สุดของฝั่งหนึ่ง" นั่นคือคำขอให้ทำ case นั้น ไม่ใช่ การถามความเห็นของ Claude การทำให้จึงไม่ขัดหลักนี้
ลองใช้กับงานจริง

ใน tool ที่คุณสร้างหรือรีวิว หา output ที่ ตัดสินตัวบุคคล แล้วถามว่า คนอ่านรู้ไหมว่าการตัดสินนั้นมั่นใจแค่ไหน?

เข้าใจผิดบ่อย

"เคสก้ำกึ่งปลอดภัยที่สุดคือไม่ตอบ หรือตีความในทางที่ดีที่สุดไว้ก่อน" ผิด ทั้งสองทางบิดภาพความจริง calibration คือการบอกความไม่แน่นอนอย่างถูกต้อง

สรุปสั้นๆ

ความมั่นใจต้องเท่ากับหลักฐาน บอกได้ว่าไม่รู้ (แต่ไม่ใช่เงียบ) อย่าซ่อน judgement ด้วยการยกคำพูดอย่างเดียว และอย่าดันผู้ใช้ไปทางใดทางหนึ่งในเรื่องที่ถกเถียง

Checkpoint 4

ระบบช่วย HR คัดผู้สมัครเจอเรซูเม่ที่ทักษะตรงตำแหน่ง แต่ไม่มีเอกสารยืนยันประสบการณ์บริหารที่อ้างไว้ คำอธิบายแบบไหนดีที่สุด?

  1. "เหมาะสมมาก แนะนำให้เข้ารอบ" เพราะทักษะตรง
  2. ช่องเหตุผลว่างไว้ เพราะไฟล์ไม่ครบ
  3. "หลักฐานก้ำกึ่ง: ทักษะเทคนิคตรงตามที่ต้องการ แต่ประสบการณ์บริหารยังไม่มีเอกสารยืนยัน ควรถามเพิ่มในสัมภาษณ์"
  4. ยกประโยคจากเรซูเม่มา 5 ประโยคโดยไม่สรุป
ดูเฉลย

C บอกว่าหลักฐานผสม อธิบายเหตุผล และชี้จุดที่ข้อมูลไม่พอ A มั่นใจเกินหลักฐาน B ไม่บอกอะไร D ซ่อน judgement

Checkpoint 5

ฝ่ายกฎหมายถามว่า "เราจะมั่นใจได้ยังไงว่าระบบไม่พูดเกินจริงเวลาข้อมูลไม่ชัด" คำตอบไหนตรงกับหลักการออกแบบของ Claude ที่สุด?

  1. เราตั้งให้ระบบเลือกการตีความที่เป็นประโยชน์ต่อผู้ใช้ที่สุดทุกครั้ง
  2. Claude ถูก train ให้ calibrated คือแสดงความไม่แน่นอนตามจริง และ prompt ของเราอนุญาตให้บอกว่าข้อมูลไม่พอ
  3. ถ้าข้อมูลขาด ระบบจะไม่แสดงผลอะไรเลย
  4. ระบบแสดงเฉพาะข้อความที่ยกมาจากเอกสารต้นทางคำต่อคำ
ดูเฉลย

B calibration คือกลไกที่ตอบคำถามนี้ตรงๆ A คือ miscalibration แบบหนึ่ง C เป็นเรื่องการตัดสินใจว่าจะแสดงผลหรือไม่ ไม่ใช่ calibration D ตัดการสังเคราะห์ที่ tool ควรให้ทิ้ง

Checkpoint 6

ครูพบว่าแชตบอตช่วยติวโต้วาทีคอยแนะนำให้นักเรียนทุกคนเปลี่ยนจุดยืนไปฝั่งเดียวกันในญัตติเรื่องโทษประหารชีวิต หลักการไหนถูกละเมิดชัดที่สุด?

  1. Epistemic autonomy สิทธิ์ของนักเรียนที่จะไปถึงข้อสรุปด้วยการคิดของตัวเอง
  2. การปฏิบัติตามคำสั่งของ operator
  3. การประเมิน counterfactual impact ของคำตอบ
  4. การกระตุ้นให้นักเรียนแก้งานหลายรอบที่สุด
ดูเฉลย

A การดันความเห็นในประเด็นถกเถียงกระทบความสามารถคิดเองของผู้ใช้ B ไม่ได้พูดถึงการยัดเยียดความเห็น C เกี่ยวกับการคำนวณความเสียหาย D ยิ่งทำให้แย่เพราะเน้นปริมาณ

4. การเข้าถึงคือ design decision

ทุกระบบทิ้งใครสักคนไว้ข้างหลังเสมอ คำถามคือเราเลือกเองอย่างรู้ตัวหรือเปล่า ตัวอย่างการตัดสินใจที่กำหนดว่าใครจะได้ใช้:

  • ภาษา รองรับภาษาเดียว คนที่ใช้ภาษาอื่นก็ใช้ไม่ได้
  • Accessibility ของ interface หน้าแชตที่ screen reader อ่านยาก ทำให้ผู้พิการทางสายตาใช้ไม่ได้
  • ช่องทาง มีแต่เว็บ ขณะที่ผู้ใช้จำนวนมากใช้มือถือหรือโทรศัพท์เป็นหลัก

ตัดสินใจเรื่องเหล่านี้อย่างตั้งใจ และ บันทึกเป็นเอกสาร ว่าเลือกอะไรและทิ้งใครไว้

อีกชั้นที่ซ้อนอยู่คือ ความครอบคลุมของโมเดล: ต่อให้ interface ใช้ได้ ผู้ใช้ที่ถามเรื่องท้องถิ่นหรือเรื่องของกลุ่มที่มีข้อมูลน้อยก็ยังได้คำตอบที่อ่อนกว่า (ย้อนไปที่ทางเข้าที่ 1 ในหัวข้อแรก)

ก่อน ship ให้ถามตรงๆ ว่า "ระบบนี้ไม่ได้ให้บริการใครได้ดี?" แล้วตั้ง feedback loop หลัง launch ไว้จับความผิดพลาดที่ test ไม่เห็น

ตัวอย่างระบบบอกเวลารอคิวคลินิก: นอกจาก test ผ่านแล้ว ให้เช็กผู้ใช้ภาษาอื่น ผู้ใช้ assistive technology และคนที่ไม่มีอุปกรณ์หรือช่องทางที่เราคาดไว้ รวมถึง edge case อย่างคลินิกปิด ไม่มีข้อมูล หรือเวลารอเป็นศูนย์

สรุปสั้นๆ

ภาษา accessibility และช่องทางคือการเลือกว่าระบบจะให้บริการใคร ตัดสินใจอย่างตั้งใจ จดไว้ เช็กความครอบคลุมของโมเดลกับคำถามของกลุ่มที่เสี่ยง และตั้ง feedback loop หลัง launch

Checkpoint 7

อบต. แห่งหนึ่งจะเปิดผู้ช่วยตอบเรื่องเบี้ยยังชีพผู้สูงอายุ รองรับเฉพาะภาษาไทยกลางผ่านเว็บ test ผ่านหมด คะแนนพึงพอใจจากการทดลองใช้ภายในสูง ก่อนเปิดจริงควรทำอะไร?

  1. เปิดได้เลย เพราะโมเดลถูก train มาอย่างกว้างขวางแล้ว
  2. เปิดได้เลย เพราะ test ผ่านและคะแนนความพึงพอใจดี
  3. เพิ่มข้อความแจ้งว่า "บริการนี้รองรับเฉพาะภาษาไทยกลางผ่านเว็บ" แล้วเปิด
  4. บันทึกว่าการเลือกภาษาไทยกลางและเว็บอย่างเดียวทิ้งใครไว้ (เช่น ผู้สูงอายุที่ใช้ภาษาถิ่นหรือไม่มีสมาร์ตโฟน) เช็กคุณภาพคำตอบกับคำถามเฉพาะท้องถิ่น และตั้งช่องทาง feedback หลังเปิด
ดูเฉลย

D ทำให้การกีดกันมองเห็นได้ ตรวจช่องว่างความครอบคลุม และมีระบบจับปัญหาหลัง launch A ไม่สนใจ coverage gap B คะแนนรวมซ่อนผู้ใช้ที่ถูกทิ้ง C แค่บอกว่ากีดกันแต่ไม่ได้จัดการ
