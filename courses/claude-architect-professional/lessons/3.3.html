3.3 Accuracy-latency trade-offs: effort, fast mode, streaming และการเลือก config ที่อธิบายได้

ต้นฉบับ: CertSafari 3.3

อ่านจบแล้วควรทำได้
  • บอกได้ว่าคันโยกแต่ละตัว (รุ่นโมเดล, effort, max_tokens, streaming, fast mode) ขยับ "นาฬิกา" latency ตัวไหน และต้องแลกกับอะไร
  • เลือกจุดเริ่มต้นระหว่างแนวทาง cost-first กับ capability-first ได้ตามโจทย์
  • ตั้งค่า effort ผ่าน output_config.effort ให้เหมาะกับงาน และรู้ว่า effort ไม่ได้คุมความยาวคำตอบ
  • ใช้ fast mode และ display: "omitted" ได้ถูกที่ โดยไม่ลดความแม่นยำ
  • ให้เหตุผลกับ config ด้วยการ sweep บน eval ของตัวเอง และเทียบด้วย ต้นทุนต่องานที่สำเร็จ ไม่ใช่ต้นทุนต่อ token
แนวคิดหลัก: "ช้า" มีหลายความหมาย

Latency ไม่ได้มีตัวเลขเดียว มีอย่างน้อย 3 นาฬิกา: เวลาจนเห็น token แรก (TTFT), เวลาจนคำตอบเสร็จ และ เวลารวมทั้งหมดของ agent ที่วิ่งหลาย turn คันโยกแต่ละตัวขยับนาฬิกาไม่เหมือนกัน และบางตัวแลกด้วยความแม่นยำ บางตัวแลกด้วยเงิน บางตัวไม่ต้องแลกอะไรเลย

1. คันโยกแต่ละตัวขยับนาฬิกาไหน

คันโยกนาฬิกาที่ขยับสิ่งที่ต้องแลก
ใช้รุ่นเล็กลง (เช่น Haiku 5.5)เวลารวม และค่าใช้จ่ายความสามารถในงานยาก
ลด effortเวลารวม (token ของ thinking, tool call และข้อความลดลง)ความสามารถบางส่วน
prompt/output สั้นลง และตั้ง max_tokensเวลารวมถ้าตั้ง cap แน่นเกินไป output จะถูกตัดกลางทาง
Streamingเวลาจนเห็น output แรกเท่านั้นไม่เสียอะไร แต่เวลารวมก็ไม่เปลี่ยน
Fast mode (speed: "fast")จำนวน output token ต่อวินาที (ไม่ใช่ TTFT)ราคาแพงขึ้น แต่ความฉลาดเท่าเดิม

จัดกลุ่มได้ 3 แบบ:

  • ไม่กระทบคุณภาพ: streaming, ตัด token ที่ไม่จำเป็นใน prompt/output
  • แลกการคิดกับความเร็ว: รุ่นเล็กลง, effort ต่ำลง, cap ที่แน่น
  • แลกเงินกับความเร็ว: fast mode ความแม่นยำเท่าเดิม แต่จ่ายแพงขึ้น

เปรียบเหมือนส่งของ: streaming คือส่งชิ้นแรกให้ลูกค้าเห็นก่อน (ของทั้งหมดถึงเวลาเดิม), ลด effort คือให้พนักงานเช็กของน้อยลง, ส่วน fast mode คือจ้างรถด่วนที่ขับเร็วกว่า คนขับเดิม ของเดิม แต่ค่าส่งแพงกว่า

เข้าใจผิดบ่อย

"เปิด streaming แล้วงานจะเสร็จเร็วขึ้น" ไม่ใช่ streaming ทำให้รู้สึกเร็ว เพราะเห็นข้อความแรกเร็วขึ้น แต่เวลาสร้างคำตอบทั้งหมดเท่าเดิม

"Fast mode คือโมเดลตัวเล็กที่ฉลาดน้อยกว่า" ไม่ใช่ fast mode รันโมเดลเดิม weights เดิม แค่ส่ง output เร็วขึ้นในราคาที่สูงขึ้น

สรุปสั้นๆ

ก่อนเลือกคันโยก ถามว่า "ช้า" ที่ผู้ใช้บ่นคือนาฬิกาไหน แล้วถามต่อว่ายอมแลกอะไรได้: ความแม่นยำ เงิน หรือไม่ยอมแลกอะไรเลย

Checkpoint 1 (จับคู่)

จับคู่คันโยกกับผลที่มันทำ:

  1. Streaming
  2. Fast mode
  3. ลด effort
  4. เปลี่ยนเป็นรุ่นเล็ก
  1. ความแม่นยำเท่าเดิม จ่ายแพงขึ้นเพื่อให้ output ไหลเร็วขึ้น
  2. ผู้ใช้เห็นข้อความแรกเร็วขึ้น แต่เวลารวมไม่เปลี่ยน
  3. ใช้ thinking/tool/text token น้อยลงในโมเดลตัวเดิม แลกกับความสามารถบางส่วน
  4. ถูกลงและเร็วขึ้น แต่สู้งานยากได้น้อยลง
ดูเฉลย

1-B, 2-A, 3-C, 4-D streaming ขยับแค่นาฬิกาแรก, fast mode แลกเงิน, effort กับรุ่นเล็กแลกความสามารถ (effort ยังอยู่บนโมเดลเดิม)

2. เริ่มจากรุ่นที่เร็วที่สุดที่ยังแม่นพอ

มีแนวทางเลือกโมเดล 2 ทาง:

แนวทางเริ่มที่เหมาะกับ
Cost-firstรุ่นที่เร็วและถูกที่สุด (Claude Haiku 5.5) แล้วอัปเกรดเฉพาะจุดที่ความสามารถไม่พอlatency ตึง, งบตึง, งานง่ายปริมาณมาก
Capability-firstClaude Opus แล้วค่อยลดลงมางาน reasoning ซับซ้อนที่ความแม่นยำสำคัญกว่าค่าใช้จ่าย

อีกข้อที่ต้องจำ: ปรับ effort มักดีกว่าย้ายรุ่น เพราะเราได้ใช้โมเดลตัวเดิมที่ prompt ถูกจูนมาแล้ว การย้ายรุ่นหมายถึงต้องเทสต์ prompt ใหม่ทั้งชุด

สรุปสั้นๆ

งานง่าย ปริมาณมาก งบน้อย → เริ่มที่ Haiku แล้วอัปเกรดเฉพาะช่องว่างที่เจอจริง งานยากที่พลาดไม่ได้ → เริ่มที่ Opus แล้วไล่ลง

Checkpoint 2

ทีมต้องติดแท็กหมวดหมู่ให้ข้อความแชทลูกค้าวันละหลายล้านข้อความแบบ real-time งบจำกัดมาก หมวดมีแค่ 12 หมวดที่ชัดเจน ควรเริ่มยังไง?

  1. เริ่มที่ Opus effort max เพื่อความชัวร์ แล้วค่อยลดถ้างบเกิน
  2. ใช้ Opus กับ fast mode เพื่อให้ทัน real-time
  3. เริ่มที่ Haiku 5.5 วัดผลบน eval แล้วอัปเกรดเฉพาะหมวดที่พลาดจริง
  4. ใช้ Sonnet effort xhigh เพราะเป็นตัวกลาง
ดูเฉลย

C เป็นโจทย์ cost-first ชัดเจน: ง่าย ปริมาณมาก latency และงบตึง Haiku คือรุ่นที่เร็วและประหยัดที่สุด ตัวเลือกอื่นจ่ายแพงเกินโดยไม่จำเป็น

3. Effort: ปุ่มหมุนภายในโมเดลตัวเดียว

Effort ตั้งที่ output_config.effort และมีผลกับ output token ทุกประเภท: thinking, การเรียก tool และ argument ของ tool, และข้อความที่ตอบ ใช้ได้ทั้งตอนเปิดและไม่เปิด thinking

client.messages.create(
    model="claude-opus-5-5",
    max_tokens=4096,
    output_config={"effort": "low"},   # subagent ที่แค่ค้นข้อมูลง่ายๆ
    messages=[{"role": "user", "content": "หา SKU ของสินค้า A-102"}],
)
ระดับพฤติกรรมใช้เมื่อ
maxคิดง่ายที่สุด ลึกที่สุด ไม่จำกัดความยาวการคิดไม่ค่อยคุ้ม มักจ่ายแพงเพื่อผลที่ดีขึ้นนิดเดียว และไม่ได้รับประกันว่าผลจะดีขึ้น
xhighลึกกว่า highงาน agentic และงานเขียนโค้ดที่วิ่งยาว
highคิดในเกือบทุก request ที่ได้ประโยชน์จากการคิดค่า default ของโมเดลส่วนใหญ่
mediumคิดปานกลาง อาจข้ามการคิดในคำถามง่ายค่า default ของ Opus 5.5 และ Haiku 5.5
lowคิดน้อยที่สุด ข้ามการคิดในงานง่ายsubagent ที่ทำ lookup ง่ายๆ

ข้อควรรู้เรื่อง effort

  • Effort คุมปริมาณการคิด ไม่ได้คุมความยาวคำตอบที่มองเห็น ถ้าบน Opus 5 คำตอบยาวเกินไป ให้เขียนใน prompt ว่าต้องการความยาวแค่ไหน
  • Effort กับ prompt cache: ค่า effort ที่ใช้จริงถูกเขียนลงไปใน prompt ดังนั้นถ้าเปลี่ยน effort ระหว่าง request ใน conversation เดียว cache breakpoint จะใช้ไม่ได้ ให้ใช้ระดับเดียวตลอด conversation หรือใช้ per-message effort (beta) บนโมเดลที่รองรับ ซึ่งไม่ทำให้ cache หลุด
  • Effort เป็นคำแนะนำแบบ soft ไม่ใช่การรับประกัน
  • ถ้าโจทย์ยากแล้วโมเดลคิดตื้นไป ให้เพิ่ม effort อย่าพยายามเขียน prompt เพื่ออ้อมข้อจำกัดของ effort ที่ตั้งไว้ต่ำ
เข้าใจผิดบ่อย

"ตั้ง max แล้วจะได้การคิดที่ลึกที่สุด ไม่มีทางได้ผลไม่ครบ" ไม่ใช่ effort เป็นแนวทางแบบ soft, max เพิ่มค่าใช้จ่ายมากเพื่อผลที่ดีขึ้นนิดเดียว และงาน subagent ง่ายๆ เหมาะกับ low มากกว่า

"ลด effort แล้วคำตอบจะสั้นลง" ไม่ใช่ effort คุมปริมาณการคิด อยากให้สั้นต้องบอกใน prompt

สรุปสั้นๆ

Effort ครอบคลุม thinking + tool + text มี 5 ระดับ ค่า default ของ Opus 5.5/Haiku 5.5 คือ medium ใช้ระดับเดียวต่อ conversation เพื่อรักษา cache และอย่าใช้มันคุมความยาวคำตอบ

Checkpoint 3

Orchestrator ปล่อย subagent 10 ตัวพร้อมกันเพื่อดึงราคาสินค้าจาก API ภายใน (งาน lookup ตรงไปตรงมา) ต้องการลดทั้ง latency และค่าใช้จ่าย ควรตั้ง effort ของ subagent เป็นเท่าไหร่?

  1. max
  2. xhigh
  3. high
  4. low
ดูเฉลย

D low ออกแบบมาสำหรับ subagent ที่ทำงานง่าย ระดับสูงกว่านั้นเพิ่ม token และเวลาโดยไม่ได้อะไรเพิ่มในงาน lookup

Checkpoint 4

แชตบอตบน Opus 5 ตอบยาวเกินไป วิศวกรคนหนึ่งเสนอให้สลับ effort ไปมาระหว่าง low กับ high ในแต่ละข้อความของบทสนทนาเพื่อให้คำตอบสั้นลง ข้อไหนถูกต้อง?

  1. ดีแล้ว เพราะ low ทำให้คำตอบสั้นลงโดยตรง
  2. ควรย้ายไปใช้ fast mode
  3. ควรตั้ง max_tokens ให้ต่ำมากๆ แทน
  4. ควรกำหนดความยาวใน prompt และใช้ effort ระดับเดียวตลอด conversation เพราะ effort ไม่ได้คุมความยาว และการสลับไปมาทำให้ cache หลุด
ดูเฉลย

D effort คุมการคิด ไม่ใช่ความยาว และค่าที่เปลี่ยนจะ invalidate cache breakpoint C เสี่ยงคำตอบถูกตัดกลางประโยค B แค่ส่ง token เร็วขึ้น

4. Streaming, fast mode และการซ่อน thinking

Streaming

ช่วยเรื่อง perceived latency (ความเร็วที่ผู้ใช้รู้สึก) ไม่ใช่เวลาสร้างทั้งหมด เหมาะกับคำบ่นว่า "หน้าจอค้าง ไม่มีอะไรขึ้นเลย" แต่ไม่ช่วยงาน batch ที่ไม่มีใครนั่งดู

Fast mode

  • รันโมเดลเดิม weights เดิม แต่ได้ output token ต่อวินาทีสูงถึง 2.5 เท่า
  • คิดราคาเป็นตัวคูณจากราคามาตรฐาน (ราคา premium) บทเรียนไม่ได้ระบุตัวเลขตัวคูณ
  • รองรับบน Claude Opus 5.5, Opus 5 และ Opus 4.8
  • เปิดด้วย speed="fast" คู่กับ beta header fast-mode-2026-02-01
  • ไม่ได้ลด TTFT สิ่งที่เร็วขึ้นคือความเร็วการไหลของ output
client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    speed="fast",
    betas=["fast-mode-2026-02-01"],
    messages=[...],
)

ซ่อน thinking ด้วย display: "omitted"

  • โมเดลยังคิดเต็มเหมือนเดิม แต่ thinking block ที่ส่งกลับมามี field thinking ว่างเปล่า
  • field signature ยังเก็บ thinking ที่เข้ารหัสไว้ เพื่อให้ multi-turn ต่อเนื่องได้
  • ประโยชน์หลักคือเวลาเห็น text token แรก เร็วขึ้นตอน streaming (ไม่ต้องรอ stream thinking ออกมาก่อน)
เข้าใจผิดบ่อย

"อยากให้เร็ว ก็ปิด thinking หรือตั้ง budget_tokens ให้น้อยๆ คงที่ทุก request" วิธีนี้ทำให้ความแม่นยำในโจทย์ยากแย่ลง และกลับกัน การเพิ่ม budget ก็ไม่ได้ทำให้ latency ลดลงเช่นกัน ถ้าต้องรักษาความแม่นยำ ให้คงการคิดไว้แล้วใช้ display: "omitted" หรือ fast mode

สรุปสั้นๆ

ผู้ใช้รอดูหน้าจอ → streaming, output ยาวแต่ต้องแม่นเท่าเดิม → fast mode, อยากเห็นคำตอบเร็วแต่ยังให้คิดเต็ม → display: "omitted" อย่าตัด thinking เพื่อแลกความเร็วในงานยาก

Checkpoint 5

งาน batch ตอนกลางคืนให้ Opus 5.5 เขียนรายงานยาวหลายพัน token ต่อชิ้น ช้าจนไม่ทันเช้า ความแม่นยำห้ามลด งบเพิ่มได้ ควรทำอะไร?

  1. เปิด fast mode (speed="fast") บนโมเดลเดิม
  2. เปิด streaming
  3. เปลี่ยนเป็น Haiku 5.5
  4. ลด effort เป็น low
ดูเฉลย

A output ยาวได้ประโยชน์จาก token/วินาทีที่สูงขึ้น และความฉลาดเท่าเดิม streaming ไม่ช่วยเพราะไม่มีใครดูหน้าจอและเวลารวมไม่เปลี่ยน C และ D ลดความแม่นยำ

Checkpoint 6

เครื่องมือวิเคราะห์สัญญาเงินกู้ใช้ extended thinking ผู้ใช้บ่นว่ากว่าจะเห็นคำตอบแรกนานมาก แต่ทีมกฎหมายยืนยันว่าความแม่นยำลดไม่ได้ ควรทำอะไร?

  1. ตั้ง budget_tokens ให้ต่ำคงที่ทุก request
  2. ปิด thinking
  3. คง thinking budget เดิม แล้วตั้ง display เป็น "omitted"
  4. เพิ่ม budget_tokens ให้สูงขึ้นเพื่อให้คิดเสร็จเร็วขึ้น
ดูเฉลย

C thinking ยังทำงานเต็ม ความแม่นยำคงเดิม แต่ไม่ต้อง stream thinking ออกมาก่อน text แรกจึงขึ้นเร็วขึ้น A และ B ทำร้ายความแม่นยำ D ไม่ลด latency

5. ให้เหตุผลกับ config ด้วยการ sweep บน "ต้นทุนต่องานที่สำเร็จ"

อย่าเอาค่า effort ที่เคยใช้กับโมเดลรุ่นเก่ามาใช้ต่อเลย ให้ sweep ใหม่บน eval ของตัวเอง และเปรียบเทียบด้วยต้นทุนต่องานที่สำเร็จ (cost per completed task) ไม่ใช่ราคาต่อ token

วิธีคิด: ต้นทุนต่องานที่ผ่าน = ต้นทุนต่อครั้ง ÷ pass rate (ตัวเลขคอลัมน์สุดท้ายที่ไม่ใช่ medium/xhigh คำนวณเองจากสูตรนี้) จากตาราง Opus 5.5 ที่ medium ใช้ราว $0.97 ต่องานที่สำเร็จ ส่วน xhigh ราว $4.51 ได้ pass rate เพิ่มอีก 4.5 จุด จะคุ้มหรือไม่ขึ้นกับว่างานที่ไม่สำเร็จหนึ่งงานทำให้ธุรกิจเสียเท่าไหร่ ไม่มีคำตอบสากล

เทคนิคลดต้นทุนที่ยังรักษา pass rate

  • Low ก่อน แล้ว high เฉพาะที่พลาด: ถ้าตรวจผลอัตโนมัติได้ (มี test หรือ verifier) ให้รันทุกงานที่ low แล้วรันซ้ำที่ high เฉพาะงานที่ไม่ผ่าน การทดสอบภายในของ Anthropic รายงานว่าต้นทุนต่ำกว่ารันทุกงานที่ high ราว 40% ที่ pass rate เท่ากัน และ latency ดีขึ้นเพราะงานส่วนใหญ่จบในรอบแรก ตัวเลขนี้เป็นแค่ทิศทาง ต้องวัดกับงานของตัวเอง
  • บอกเวลาที่ผ่านไปให้โมเดลรู้: บอกว่าเวลาสำคัญและแสดงเวลาที่ใช้ไปแล้ว ลด run time ได้ 7% ถึง 47% ในการทดสอบของ Anthropic แลกกับคะแนนที่ลดลงไม่กี่จุด agent ที่วิ่งยาวควรมีขอบเขตเวลาด้วย เช่น output cap และ session budget
  • ระวัง multi-model setup: การเพิ่มการเรียกโมเดล frontier อีก 1–2 ครั้งต่องานจะอยู่บน critical path และเพิ่ม latency
def solve(task):
    out = run(task, effort="low")
    if verify(out):            # มี test/verifier ตรวจได้
        return out
    return run(task, effort="high")   # จ่ายแพงเฉพาะงานที่ยาก

สรุปสั้นๆ
