4.4 วินิจฉัยความล้มเหลวของระบบ Claude: hallucination, prompt, tool และ model

ต้นฉบับ: CertSafari 4.4

อ่านจบแล้วควรทำได้
  • แยกได้ว่า output ที่ผิดมาจากชั้นไหน: grounding, prompt, tools หรือ model
  • ยืนยันว่าเป็น hallucination จริงด้วยวิธีที่ไม่หลงเชื่อความลื่นไหลของคำตอบ
  • อ่านอาการของ prompt failure และ tool misuse แล้วชี้จุดแก้ได้ตรง
  • บอกได้ว่าโมเดลใหญ่เกินหรือเล็กเกินงาน และควรเช็กอะไรก่อนเปลี่ยนรุ่น
แนวคิดหลัก: output ผิดคืออาการ ไม่ใช่โรค

ก่อนลงมือแก้ ต้องหาให้เจอว่าต้นเหตุอยู่ชั้นไหนในสี่ชั้น: grounding, prompt, tools, model ถ้ายาไปผิดชั้น อาการอาจดูดีขึ้นชั่วคราว แต่ต้นเหตุยังอยู่ครบ เหมือนกินยาแก้ปวดหัวทั้งที่ปัญหาคือสายตาสั้น

1. สี่ชั้นของความล้มเหลว

ชั้นหน้าตาของปัญหาคำถามวินิจฉัย
Groundingโมเดลพูดสิ่งที่ input ไม่ได้รองรับ (hallucination)ข้อความนี้มีหลักฐานในเอกสารที่ให้ไปไหม?
Promptโมเดลทำตามคำสั่ง แต่คำสั่งไม่ได้สื่อสิ่งที่คนเขียนตั้งใจถ้าอ่านคำสั่งตามตัวอักษร ผลนี้ถือว่าทำตามไหม?
Toolsdescription หรือ schema ทำให้โมเดลต้องเดาว่าจะเรียก tool ไหน หรือเรียกยังไงถ้าเป็นคนอ่านแค่ description จะเลือกถูกไหม?
Modelโมเดลอ่อนเกินงาน หรือใหญ่ (และแพง) เกินงานprompt และ tool ชัดแล้ว แต่ยังพลาด/ยังช้าและแพงเกินไหม?

ตัวอย่างชั้น tools: Claude เรียก get_invoice ทั้งที่ควรเรียก get_payment_status เพราะ description ของทั้งสองตัวเขียนคล้ายกันจนแยกไม่ออก ทางแก้คือเขียน description ให้ชัดว่าแต่ละตัวใช้ เมื่อไหร่ การเปลี่ยนชื่ออย่างเดียวหรือเปลี่ยนไปใช้โมเดลใหญ่กว่าไม่ได้แก้ที่ต้นเหตุ

สรุปสั้นๆ

ถามทีละชั้น: มีหลักฐานไหม (grounding) → คำสั่งสื่อถูกไหม (prompt) → tool ชัดไหม (tools) → โมเดลเหมาะกับงานไหม (model)

Checkpoint 1

agent ร้านค้ามี tool check_stock และ check_delivery ผู้ใช้ถาม "ของจะมาถึงเมื่อไหร่" แต่ Claude เรียก check_stock บ่อยครั้ง เมื่อเปิดดูพบว่า description ทั้งคู่เขียนว่า "ตรวจสอบสถานะสินค้า" ต้นเหตุและวิธีแก้คืออะไร?

  1. ชั้น model: เปลี่ยนไปใช้โมเดลที่ใหญ่กว่า
  2. ชั้น tools: เขียน description ให้แยกชัดว่าแต่ละตัวใช้ในสถานการณ์ไหน
  3. ชั้น tools: เปลี่ยนชื่อเป็น stock_v2 และ delivery_v2
  4. ชั้น grounding: บังคับให้ quote เอกสารก่อนตอบ
ดูเฉลย

B description กำกวมเป็นต้นเหตุ ต้องแก้ที่ description การเปลี่ยนชื่ออย่างเดียวยังทิ้ง description ที่เหมือนกันไว้ และนี่ไม่ใช่ปัญหาความสามารถของโมเดลหรือ grounding

2. ยืนยันว่าเป็น hallucination จริง

คำตอบที่ฟังดูมั่นใจและลื่นไหล ไม่ได้แปลว่าถูก ต้องใช้วิธีตรวจที่ไม่ขึ้นกับความลื่นไหล:

  • Quote first ให้ Claude ดึงข้อความที่รองรับแบบคำต่อคำออกมาก่อน แล้วค่อยตอบจาก quote เหล่านั้น
  • Cross-sample consistency รัน prompt เดิมหลายรอบ ข้อเท็จจริงที่เปลี่ยนไปมาระหว่างรอบ มักเป็นสิ่งที่โมเดลแต่งขึ้น ไม่ได้ดึงมาจากแหล่งจริง
  • Cite or retract หลังร่างเสร็จ ให้ Claude หา quote รองรับแต่ละข้อความ ข้อไหนหาไม่เจอให้ลบออก การเว้นวงเล็บว่าง [] ไว้ตรงจุดที่ไม่มีหลักฐาน ช่วยให้คนรีวิวเห็นช่องโหว่ชัดๆ
  • ดู reasoning ถ้าเปิด extended thinking ไว้ reasoning แบบสรุปอาจเผยสมมติฐานผิดที่ทำให้คำตอบเพี้ยน
<instructions>
1. จาก <policy> ด้านล่าง ดึงประโยคที่เกี่ยวกับคำถามแบบคำต่อคำ ใส่ใน <quotes>
2. ตอบโดยใช้เฉพาะสิ่งที่อยู่ใน <quotes>
3. ถ้าไม่มี quote ที่ตอบคำถามได้ ให้ตอบว่า "ไม่พบในเอกสารนโยบาย"
</instructions>

สาเหตุที่พบบ่อยและวิธีแก้

สาเหตุอาการวิธีแก้
ขาด groundingตอบจากความรู้ทั่วไปแทนเอกสารจำกัดให้ตอบจากเอกสารที่ให้เท่านั้น และบังคับ quote
ถูกบังคับให้ต้องตอบไม่มีข้อมูล แต่ก็ยังให้ตัวเลขมาอนุญาตให้บอกว่า "ไม่รู้" อย่างชัดเจน
ข้อความจริงปนกับข้อความไม่มีหลักฐานส่วนใหญ่ถูก แต่มีบางข้อแต่งขึ้นเพิ่มรอบ cite-or-retract
เข้าใจผิดบ่อย

"เอกสารไม่ครบ ก็ให้โมเดลเติมช่องว่างด้วยความรู้ทั่วไป" ไม่ใช่ นี่คือ สาเหตุ ของตัวเลขที่ไม่มีที่มา ไม่ใช่วิธีแก้

"คำตอบละเอียดและมั่นใจ น่าจะถูก" ไม่ใช่ ความลื่นไหลไม่ใช่หลักฐาน ต้องตรวจด้วย quote หรือความสม่ำเสมอข้ามหลายรอบ

สรุปสั้นๆ

ตรวจ: quote first, รันหลายรอบดูความนิ่ง, cite-or-retract, อ่าน reasoning · แก้: จำกัดแหล่ง + บังคับ quote, อนุญาตให้ไม่รู้, ตัดข้อที่ไม่มีหลักฐาน

Checkpoint 2 (จับคู่)

จับคู่สาเหตุของ hallucination กับวิธีแก้:

  1. bot ตอบคำถามสัญญาเช่าด้วยกฎหมายทั่วไป แทนที่จะอ่านจากสัญญาที่แนบมา
  2. prompt เขียนว่า "ต้องให้ตัวเลขค่าปรับเสมอ" แม้สัญญาบางฉบับไม่มีค่าปรับ
  3. สรุปสัญญาถูกเกือบทุกข้อ แต่มีบางเงื่อนไขที่สัญญาไม่ได้เขียนไว้

ตัวเลือก: A) อนุญาตให้ตอบว่าไม่มีข้อมูล · B) รอบ cite-or-retract · C) จำกัดให้ตอบจากเอกสารและบังคับ quote

ดูเฉลย

1-C, 2-A, 3-B ขาด grounding → quote first · ถูกบังคับให้ตอบ → อนุญาตให้ไม่รู้ · ข้อความจริงปนแต่ง → cite-or-retract

Checkpoint 3

assistant ตอบคำถามสวัสดิการพนักงาน บอกว่า "ค่ารักษาพยาบาลเบิกได้ปีละ 35,000 บาท" ทั้งที่เอกสารสวัสดิการไม่มีตัวเลขนี้ วิธีแก้ไหนดีที่สุด?

  1. บังคับให้ quote ข้อความจากเอกสารสวัสดิการก่อนตอบ และอนุญาตให้บอกว่าไม่พบข้อมูล
  2. สั่งให้ใช้ความรู้เรื่องสวัสดิการทั่วไปของบริษัทในไทยเมื่อเอกสารไม่ครอบคลุม
  3. สั่งให้ตอบเป็นตัวเลขทุกครั้งเพื่อความชัดเจน
  4. ขยาย max_tokens ให้โมเดลอธิบายได้ยาวขึ้น
ดูเฉลย

A B คือสาเหตุของปัญหาเอง C บังคับให้ต้องแต่งเมื่อไม่มีข้อมูล D ไม่เกี่ยวกับ grounding

3. Prompt failure: ทำตามคำสั่ง แต่ไม่ใช่สิ่งที่ตั้งใจ

ลักษณะเฉพาะของ prompt failure คือ ไม่มีอะไรถูกแต่งขึ้น และไม่มี tool ไหนทำงานผิด โมเดลทำตามที่เขียนไว้ตรงๆ แต่สิ่งที่เขียนไว้ไม่ใช่สิ่งที่ต้องการ วิธีเทสต์ prompt ง่ายๆ: ลองให้คนที่แทบไม่มี context อ่านแล้วทำตาม ถ้าเขาทำผิด Claude ก็จะทำผิดเหมือนกัน

Pattern ที่ต้องรู้

  • Format ไม่ชัด (underspecified format): input หน้าตาคล้ายกันและสะอาดดี แต่โครงสร้าง JSON ที่ออกมากลับไม่เหมือนกันทุกครั้ง แปลว่า prompt ไม่ได้ล็อก format แก้ด้วยการระบุ field และการซ้อน (nesting) ให้ชัด พร้อมแนบตัวอย่าง response และห่อตัวอย่างด้วย tag เพื่อแยกตัวอย่างออกจากคำสั่ง
  • กฎที่ไม่มีเหตุผล (rules without reasons): กฎโดดๆ อย่าง "ห้ามใช้ ..." จะถูกใช้ทุกที่ ถ้าบอกเหตุผลด้วย โมเดลจะรู้ว่ากฎนี้ควรใช้ตรงไหนและไม่ควรใช้ตรงไหน
  • ตีความตามตัวอักษรเกินไป และคำสั่งเก่าค้าง: คำสั่งที่ขัดกันเองหรือล้าสมัยทำให้โมเดลสืบค้นเกินจำเป็น เรียก tool เกิน และเปลืองเงิน ลบคำสั่งเหล่านั้นออกแล้วความแม่นกลับมา
ตอบเป็น JSON ตามโครงสร้างนี้เท่านั้น:
<example>
{"order_id": "A-1029",
 "items": [{"sku": "TS-01", "qty": 2}],
 "shipping": {"method": "express", "eta_days": 2}}
</example>

ตัวอย่างกฎที่ใส่เหตุผล:

ไม่ใช้อักษรย่อทางการแพทย์ในคำตอบ
เพราะผู้อ่านเป็นคนไข้ทั่วไปที่อาจไม่รู้ความหมาย
(ในส่วนบันทึกภายในสำหรับแพทย์ ใช้ได้ตามปกติ)
เข้าใจผิดบ่อย

"JSON ออกมาโครงสร้างไม่เหมือนกันทั้งที่ input สะอาด = hallucination" ไม่ใช่ ไม่มีข้อเท็จจริงไหนถูกแต่ง นี่คือ prompt ที่ระบุ format ไม่ชัด

"โมเดลใช้กฎกว้างเกิน ก็เขียนกฎซ้ำให้แรงขึ้น ตัวใหญ่ขึ้น" ไม่ใช่ ยิ่งเน้นยิ่งถูกใช้กว้างขึ้น ให้อธิบายจุดประสงค์ของกฎแทน

สรุปสั้นๆ

prompt failure = ทำตามตัวอักษรแต่ผิดเจตนา · format เพี้ยน → ระบุ field + ตัวอย่างใน tag · กฎกว้างเกิน → ใส่เหตุผล · คำสั่งเก่า/ขัดกัน → ลบออก

Checkpoint 4

system prompt ของ bot ธนาคารมีกฎ "ห้ามเปิดเผยเลขบัญชี" ผลคือ bot ปฏิเสธที่จะบอกลูกค้าว่าเลขบัญชีสำหรับโอนค่างวดของธนาคารคืออะไร ทั้งที่เป็นข้อมูลสาธารณะ วิธีแก้ที่ดีที่สุดคืออะไร?

  1. เขียนกฎซ้ำด้วยตัวพิมพ์ใหญ่และคำว่า "สำคัญมาก"
  2. ใส่เหตุผลของกฎ: ปกป้องเลขบัญชีส่วนตัวของลูกค้า ส่วนเลขบัญชีรับชำระของธนาคารเป็นข้อมูลสาธารณะ
  3. เปลี่ยนไปใช้โมเดลที่ใหญ่กว่า
  4. ลบกฎนี้ทิ้งทั้งหมด
ดูเฉลย

B เมื่อรู้จุดประสงค์ โมเดลจะจำกัดขอบเขตของกฎได้เอง A ทำให้ใช้กว้างกว่าเดิม C ไม่ได้แก้ที่ prompt D ทิ้งการป้องกันที่จำเป็น

Checkpoint 5

ระบบสกัดข้อมูลใบสมัครงาน input เป็นฟอร์ม PDF แบบเดียวกันทั้งหมด แต่ output JSON บางครั้งใส่ education เป็น array บางครั้งเป็น object และบางครั้งชื่อ field เป็น edu ต้นเหตุคือ?

  1. prompt ระบุ format ไม่ชัด แก้ด้วยการกำหนด field และ nesting ตายตัวพร้อมตัวอย่าง response
  2. hallucination แก้ด้วยการบังคับ quote
  3. โมเดลเล็กเกินไป ต้องอัปเกรด
  4. tool schema ผิด ต้องเพิ่ม strict: true ให้ tool ค้นหา
ดูเฉลย

A input เสถียรแต่โครงสร้างแกว่ง คือสัญญาณของ format ที่ไม่ได้ระบุ ไม่มีข้อเท็จจริงถูกแต่ง และไม่เกี่ยวกับ tool

4. Tool misuse: อาการบอกจุดที่ต้องแก้

อาการของ tool แต่ละแบบชี้ไปที่ส่วนเฉพาะของ tool definition:

อาการสาเหตุที่น่าจะเป็นวิธีแก้
เรียก tool A ทั้งที่ควรเรียก Bdescription กำกวมเขียน description ให้คม แยกว่าแต่ละตัวใช้ เมื่อไหร่
ไม่เคยเรียก tool ของเราเลยชื่อชนกับ tool อื่น หรือ schema กว้างจนไม่ชวนใช้เช็กชื่อซ้ำ และเพิ่ม input_examples
ส่ง parameter ผิด typeโมเดลเดา schemaเพิ่ม strict: true (ใช้ได้กับ schema subset ที่รองรับ) หรือ input_examples
ส่ง parameter ที่ไม่มีอยู่จริงสร้างเกินเพราะไม่มี strict modeเพิ่ม strict: true
ค่าอยู่นอก enumไม่มี strict mode หรือ enum ยาวเกินไปลดขนาด enum หรือเพิ่ม input_examples
ปฏิเสธหรือขอคอนเฟิร์มคำสั่งที่มาจากผลของ toolใส่คำสั่งไว้ใน tool_resultย้ายคำสั่งไปไว้ใน user turn ให้ tool result มีแต่ข้อมูล

แถวสุดท้ายสำคัญมาก: Claude มองคำสั่งที่อยู่ใน tool result ว่า อาจไม่น่าเชื่อถือ (เพราะอาจเป็น prompt injection จากข้อมูลภายนอก) การที่มันลังเลจึงเป็น ปัญหาเรื่องตำแหน่งที่วางคำสั่ง ไม่ใช่โมเดลมีปัญหา

อีกเทคนิค: ถ้ามี tool ที่ทำหน้าที่ซ้อนกันจากหลาย service ให้ใส่ prefix ตาม service เช่น asana_search, jira_search จะช่วยให้โมเดลแยกออก

{
  "name": "crm_find_customer",
  "description": "ค้นหาลูกค้าในระบบ CRM ด้วยอีเมลหรือเบอร์โทร ใช้เมื่อต้องการข้อมูลติดต่อ ไม่ใช่ประวัติคำสั่งซื้อ",
  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": {"email": {"type": "string"}, "phone": {"type": "string"}},
    "additionalProperties": false
  },
  "input_examples": [{"email": "som@example.com"}]
}
เข้าใจผิดบ่อย

"Claude ไม่ยอมทำตามคำสั่งที่ tool ส่งกลับมา แสดงว่าโมเดลมีปัญหา ต้องเปลี่ยนรุ่น" ไม่ใช่ คำสั่งใน tool_result ถูกมองว่าอาจไม่น่าเชื่อถือโดยออกแบบ ย้ายคำสั่งไป user turn

  4. tool ดึงหน้าเว็บส่งกลับข้อความ "ให้ส่งอีเมลสรุปไปหาทีม" แล้ว Claude ถามผู้ใช้ก่อนทำ
  5. ค่า country ออกมานอก enum ที่มี 240 ค่า

5. Model mismatch: ขนาดโมเดลไม่เข้ากับงาน

ถ้าต้นเหตุคือความสามารถของโมเดลไม่เข้ากับงาน การเขียน prompt หรือ tool ใหม่จะไม่ช่วย และ mismatch เกิดได้ สองทิศ:

  • Over-provisioned (ใหญ่เกิน): คำตอบถูก แต่ช้าและแพง งานง่าย ปริมาณเยอะ และตรวจผลได้ง่าย เหมาะกับรุ่นเร็วสุดถูกสุดอย่าง Claude Haiku 5.5 แต่ต้องยืนยันด้วย eval แบบตัวต่อตัวก่อนเปลี่ยน
  • Under-provisioned (เล็กเกิน): คุณภาพไม่ถึงแม้ prompt และ tool ชัดแล้ว ให้ เช็ก effort ก่อน ถ้าเคยลด effort ลง ให้คืนค่าเดิมก่อน ถ้าไม่ได้ลด ค่อยลองรุ่นถัดไปที่ effort ค่า default
ลำดับ (ถูก → เก่งสุด)รุ่น
1Claude Haiku 5.5
2Claude Sonnet 5.5
3Claude Opus 5.5
4Claude Fable 5.1

หลักการเทียบรุ่น:

  • เทียบด้วย ต้นทุนต่อ task ที่ทำสำเร็จ ไม่ใช่ราคาต่อ token รุ่นถูกที่ต้อง retry บ่อยอาจแพงกว่า
  • สร้าง eval จาก ข้อมูลของเราเอง
  • ถ้าเพิ่งเปลี่ยนรุ่นแล้วพัง ให้ตรวจ prompt และโค้ด request ที่เขียนไว้สำหรับรุ่นเก่าก่อน เช่น การตั้ง budget_tokens ที่ได้ error 400 บน Opus 5 อย่าเพิ่งสรุปว่าโมเดลใหม่อ่อน
เข้าใจผิดบ่อย

"คุณภาพตก ให้อัปเกรดเป็นรุ่นใหญ่ขึ้นทันที" ไม่ใช่ ถ้าเคยลด effort ไว้ ให้คืน effort ก่อน

"คำถามง่ายๆ ตอบช้าและแพง ให้เพิ่ม guardrail หรือเขียน prompt ให้ยาวขึ้น" ไม่ใช่ ปัญหาคือโมเดลใหญ่เกินงาน prompt ที่ยาวขึ้นยิ่งเพิ่มต้นทุน

สรุปสั้นๆ

ใหญ่เกิน → ลอง Haiku 5.5 พร้อม eval เทียบ · เล็กเกิน → คืน effort ก่อน แล้วค่อยขึ้นรุ่น · เทียบด้วยต้นทุนต่อ task ที่สำเร็จ · พังหลังย้ายรุ่น → ตรวจ prompt/โค้ดเก่าก่อน

Checkpoint 7

ทีมลด effort ของ Sonnet 5.5 เพื่อประหยัด แล้วคุณภาพการสรุปเคสลูกค้าตกจากเดิม prompt และ tool ไม่ได้เปลี่ยน ควรทำอะไรก่อน?

  1. เปลี่ยนไปใช้ Opus 5.5 ทันที
  2. คืนค่า effort เดิมแล้วรัน eval ซ้ำ
  3. เขียน prompt ให้ยาวและละเอียดขึ้น
  4. เพิ่มตัวอย่าง few-shot อีก 20 ตัว
ดูเฉลย

B ตัวแปรที่เปลี่ยนคือ effort ก็คืนค่านั้นก่อน การกระโดดขึ้นรุ่นหรือแก้ prompt คือแก้ผิดจุด

Checkpoint 8

widget ตอบคำถาม "ร้านเปิดกี่โมง / ที่จอดรถอยู่ไหน" รันบน Opus 5.5 คำตอบถูกทุกข้อแต่ใช้เวลาหลายวินาทีและบิลสูง ควรทำอย่างไร?

  1. เพิ่ม guardrail ให้ตอบสั้นลง
  2. ระบุว่าเป็น model mismatch แบบใหญ่เกิน แล้ว eval Haiku 5.5 เทียบกับ baseline ปัจจุบัน
  3. เปลี่ยนไปใช้ Fable 5.1 เพื่อความแม่น
  4. เพิ่ม system prompt ให้ละเอียดขึ้น
ดูเฉลย

B งานง่าย ปริมาณเยอะ ตรวจได้ง่าย เหมาะกับรุ่นเล็ก แต่ต้องยืนยันด้วย eval ก่อน A และ D เพิ่มงานให้โมเดลที่ใหญ่เกินอยู่แล้ว C ไปผิดทิศ

Checkpoint 9

ทีมย้ายจากรุ่นเก่ามาใช้ Opus 5 แล้ว request บางตัวได้ HTTP 400 ทันที ในโค้ดยังส่งค่า thinking แบบ budget_tokens ที่ตั้งไว้สำหรับรุ่นเก่า ควรสรุปว่าอย่างไร?

  1. รุ่นใหม่ความสามารถไม่พอ ต้องถอยกลับรุ่นเก่า
  2. ปัญหาน่าจะอยู่ที่โค้ด request ที่เขียนสำหรับรุ่นเก่า ต้องตรวจและปรับก่อนสรุปเรื่องความสามารถ
  3. เป็น hallucination ต้องบังคับ quote
  4. เป็น tool misuse ต้องเพิ่ม strict: true
ดูเฉลย

B ความล้มเหลวทันทีหลังย้ายรุ่นมักมาจาก prompt หรือ parameter ที่ผูกกับรุ่นเก่า error 400 คือ request ไม่ถูกต้อง ไม่ใช่โมเดลอ่อน
