3.1 Capability bloat in agent tool configurations

ต้นฉบับ: CertSafari 3.1

อ่านจบแล้วควรทำได้
  • อธิบายได้ว่า tool ที่มากเกินกระทบ context, attention และความแม่นในการเลือก tool อย่างไร
  • ชี้ tool ที่ซ้ำซ้อน ไม่ได้ใช้ อธิบายไม่ชัด หรือ MCP server ที่ต่อเกินมา จาก config และ transcript ได้
  • รวม tool ที่ทับกันให้เป็น tool ระดับงาน (task-level) และตั้ง namespace ให้ตัวที่เหลือ
  • จำกัด tool ของแต่ละ agent/subagent ตามบทบาทด้วย tools, disallowedTools, mcpServers และ permission mode
  • เลือกระหว่าง consolidation, scoping, tool search, prompt caching และ context editing ตามต้นตอของปัญหา
แนวคิดหลัก: tool เยอะ ≠ เก่งขึ้น

Capability bloat คือ agent มี tool มากกว่าที่งานต้องใช้ ไม่ว่าจะเป็น tool ที่ทับกัน ไม่เคยถูกเรียก อธิบายคลุมเครือ หรือมาจาก MCP server ที่ไม่เคยใช้ ทุก definition กิน context และเป็นตัวเลือกอีกหนึ่งตัวที่ Claude ต้องตัดทิ้ง ผลคือ agent เลือก tool แม่นน้อยลง ไม่ใช่เก่งขึ้น

1. tool ที่มากเกินทำให้ agent เสียอะไร

นึกภาพช่างซ่อมที่แบกกล่องเครื่องมือ 200 ชิ้นขึ้นบันได ทุกครั้งที่จะขันน็อตต้องคุ้ยหาไขควงตัวที่ใช่ แถมกล่องหนักจนเหลือแรงน้อยลง agent ก็เป็นแบบนั้น ต้นทุนมี 3 ด้าน:

  • Context: ชื่อ description และ input schema ของทุก tool อยู่ใน context ทุกรอบ ก่อนจะได้อ่านคำขอของผู้ใช้ด้วยซ้ำ tool ราว 50 ตัว อาจกินราว 10–20K token และ setup หลาย server (GitHub, Slack, Sentry, Grafana, Splunk) อาจกินราว 55K token ก่อนเริ่มงานจริง
  • Attention: definitions ใช้พื้นที่เดียวกับไฟล์ tool result และการคิด context ทำตัวเหมือน "งบความสนใจ" token ส่วนเกินทำให้ recall และคุณภาพการคิดลดลง แม้ tool นั้นแทบไม่ถูกใช้ ใน agent ที่รันนาน definitions ยังต้องแย่งที่กับ tool_result ที่สะสมขึ้นเรื่อยๆ จน agent อาจหมดที่ก่อนงานเสร็จ
  • ความแม่นในการเลือก: ลดลงเมื่อโหลด tool พร้อมกันราว 30–50 ตัว ขึ้นไป และ tool ที่ทับกันทำให้เลือกผิดได้ ทุกขนาด: เลือก tool ผิด ใช้ tool ถูกแต่ parameter ผิด หรืออ้อมโลก

การเรียกผิดไม่ได้แค่เปลืองรอบ แต่ยังใส่ผลลัพธ์ที่ชวนเข้าใจผิดเข้ามาใน context และบางครั้งทำสิ่งที่ไม่ควรทำ (เช่น ลบหรือส่งข้อความ) bloat จึงเป็น เรื่องความปลอดภัย ด้วย ไม่ใช่แค่เรื่องประสิทธิภาพ

สรุปสั้นๆ

ทุก tool จ่ายค่า context ทุกรอบ แย่งความสนใจ และทำให้เลือกผิดง่ายขึ้นเมื่อเกิน ~30–50 ตัวหรือเมื่อทับกัน การเรียกผิดอาจกลายเป็นการกระทำที่ไม่ต้องการ

ลองเดาก่อน

agent ฝ่ายการเงินมี tool อยู่ 28 ตัว ทีมจะต่อ MCP server ใหม่ที่เพิ่มอีก 30 ตัว "เผื่อได้ใช้" ผลต่อการเลือก tool น่าจะเป็นอย่างไร?

  1. แม่นน้อยลง เพราะ tool ที่ไม่เกี่ยวยังกิน context และเพิ่มตัวเลือกให้แย่งกัน
  2. แม่นขึ้น เพราะมีตัวเลือกมากขึ้น
  3. เท่าเดิม เพราะ tool ที่ไม่ถูกเรียกไม่มีต้นทุน
ดูเฉลย

A รวมแล้วเกือบ 60 ตัว เกินช่วงที่ความแม่นเริ่มตก และ definitions ทุกตัวอยู่ใน context ไม่ว่าจะถูกเรียกหรือไม่

Checkpoint 1

agent DevOps ที่ต่อ MCP server 4 ตัว ทำงานสั้นๆ ได้ดี แต่พอสืบ incident ยาวๆ ที่เรียก tool หลายสิบครั้ง กลับ context เต็มก่อนสรุปได้ สาเหตุหลักคือ?

  1. MCP server ทั้ง 4 ตัวใช้ connection ร่วมกัน จึงตันเมื่อเรียกถี่
  2. เมื่องานยาว ระบบสลับไปใช้โมเดลรุ่นเล็กที่ window เล็กกว่าเอง
  3. tool definitions อยู่ใน context ทุกรอบ และแย่งพื้นที่กับ tool_result ที่สะสมขึ้นเรื่อยๆ
  4. context window ไม่นับ tool definitions
ดูเฉลย

C definitions ใช้ window เดียวกับ tool result ยิ่งงานยาว result ยิ่งสะสม จนพื้นที่ไม่พอ D ผิดเพราะ definitions นับเสมอ ส่วน A และ B ไม่ใช่พฤติกรรมที่มีอยู่จริง

2. วินิจฉัย bloat จาก config

คำถามหลักที่ต้องถามกับทุกรายการ: "ถ้าเอาตัวนี้ออก อะไรจะพัง?" ถ้าตอบไม่ได้ ก็น่าจะไม่จำเป็น ปัญหาที่เจอบ่อยมี 4 แบบ:

  • Tool ทับกัน: เช่น tool แบบ list กับแบบ search ของ resource เดียวกัน หรือ get-by-ID กับ list ที่ถูกเรียกคู่กันเสมอ
  • Tool ที่ไม่ได้ใช้: ไม่เคยถูกเรียกในงานจริง บ่อยครั้งเป็นทั้ง MCP server ที่ต่อไว้ "เผื่อ"
  • Description คลุมเครือ: Claude แยกไม่ออกว่าตัวไหนทำอะไร หรือใช้ parameter ผิดซ้ำๆ
  • MCP server ที่ต่อเกินมา: มาจากไฟล์ของโปรเจกต์ user settings plugin หรือ connector ขององค์กร โดยที่เราไม่ได้ตั้งใจ

หลักฐานดีกว่าการนั่งอ่าน config: เก็บจำนวนการเรียก tool, token และ error ต่องาน และอ่าน tool call ดิบใน transcript ไม่ใช่สรุปที่ agent เล่าเอง

สิ่งที่เห็นใน transcriptน่าจะเป็นแก้ด้วยอะไรก่อน
tool 3 ตัวเดิมถูกเรียกเรียงกันทุกครั้งแบ่ง tool ละเอียดเกินไปรวมเป็น tool เดียวระดับงาน
error parameter ไม่ถูกต้องบ่อยdescription หรือ schema ไม่ชัดเขียน description ใหม่ ใส่ตัวอย่าง
สลับไปมาระหว่าง tool 2 ตัวที่คล้ายกันหน้าที่ทับกันหรือคลุมเครือรวม หรือตั้ง namespace ให้เส้นแบ่งชัด
tool ของ server หนึ่งไม่เคยโผล่ใน transcriptความสามารถที่ไม่ได้ใช้ตัดการเชื่อมต่อ หรือ deny tool ของมัน

MCP server มาจากไหนบ้าง

ใน Agent SDK ถ้าตั้ง strict_mcp_config เป็น true ระบบจะใช้แค่ server ที่ระบุใน mcp_servers และไม่สนใจ .mcp.json ของโปรเจกต์ user settings server จาก plugin และ connector ของ claude.ai ดังนั้นถ้าเห็น server ที่ไม่ได้ระบุไว้แต่โผล่มา แปลว่ามาจากช่องทางใดช่องทางหนึ่งในนี้

options = ClaudeAgentOptions(
    mcp_servers={"jira": jira_cfg, "github": gh_cfg},
    strict_mcp_config=True,   # ใช้แค่ 2 server นี้ ไม่ดึงจากแหล่งอื่น
)
สรุปสั้นๆ

ถาม "เอาออกแล้วอะไรพัง" กับทุก tool ดูหลักฐานจาก transcript และ metric แล้วจับอาการเข้ากับวิธีแก้: เรียกเป็นชุด → รวม, parameter ผิด → แก้ description, สลับไปมา → รวม/namespace, ไม่เคยใช้ → ตัดออก

Checkpoint 2 (จับคู่)

จับคู่สิ่งที่เห็นใน transcript กับวิธีแก้แรก:

  1. get_order, get_shipment, get_refund_status ถูกเรียกเรียงกันทุกครั้งที่ลูกค้าถามสถานะ
  2. tool ของ server analytics ไม่เคยโผล่ใน transcript 3 เดือน
  3. agent ส่ง date ผิดรูปแบบให้ create_booking ซ้ำๆ
  4. agent สลับไปมาระหว่าง find_user กับ lookup_member

A = เขียน description/schema ใหม่ พร้อมตัวอย่าง · B = รวมเป็น tool เดียว · C = รวม หรือ namespace ให้เส้นแบ่งชัด · D = ตัดการเชื่อมต่อ หรือ deny tool

ดูเฉลย

1-B, 2-D, 3-A, 4-C แต่ละอาการชี้ไปที่ปัญหาคนละแบบ จึงแก้คนละทาง

3. รวม tool และตั้ง namespace

Consolidation: ออกแบบ tool ตาม งาน ไม่ใช่ห่อ API endpoint ทีละตัวแบบหนึ่งต่อหนึ่ง ถ้าห่อ endpoint ตรงๆ agent ต้องเรียกต่อกันเองและอ่านผลระหว่างทางทุกตัว แต่ tool ระดับงานทำหลายขั้นข้างในแล้วคืนเฉพาะสิ่งที่ต้องใช้

tool ระดับ endpointtool ระดับงาน
list_users, list_events, create_eventschedule_event (หาเวลาว่างแล้วจองให้)
read_logssearch_logs (คืนเฉพาะบรรทัดที่เกี่ยวข้อง)
get_customer_by_id, list_transactions, list_notesget_customer_context
list_contactssearch_contacts หรือ message_contact

ได้ 2 อย่าง: definitions น้อยลง (ช่วยให้อยู่ต่ำกว่าช่วง 30–50) และ agent ต้องคิดน้อยลง tool แต่ละตัวควรมีหน้าที่ชัดเจนหนึ่งเดียว และแบ่งงานแบบที่คนที่มีทรัพยากรเดียวกันจะแบ่ง

Namespacing

tool ที่เหลือให้ตั้งชื่อนำหน้าตาม service (เช่น asana_search, jira_search) และตาม resource ภายใน service (เช่น asana_projects_search, asana_users_search) การวางแบบ prefix หรือ suffix มีผลต่อคะแนน eval จริง และ ผลต่างกันไปตามโมเดล ให้ตัดสินจากการทดสอบกับ setup ของเราเอง ไม่ใช่ความเคยชินหรือค่า default ของ client

ลองใช้กับงานตัวเอง

เลือก agent ที่เคยสร้างหรือรีวิว หา tool 2 ตัวที่แทบจะถูกเรียกคู่กันเสมอ แล้วลองตั้งชื่อ tool ระดับงานตัวเดียวที่ทำแทนได้

สรุปสั้นๆ

ออกแบบ tool ตามงาน ไม่ใช่ตาม endpoint ตัวที่เหลือตั้ง namespace ตาม service และ resource ส่วน prefix หรือ suffix ให้วัดจาก eval ของเราเอง

Checkpoint 3

ทีมแพลตฟอร์มเถียงกันว่าจะตั้งชื่อ github_issues_search (prefix) หรือ search_issues_github (suffix) ดี ควรตัดสินอย่างไร?

  1. เลือกแบบที่ทำให้ชื่อสั้นที่สุด เพราะชื่อสั้นช่วยประหยัด token ได้มาก
  2. ให้ทีมโหวตครั้งเดียว แล้วใช้แบบนั้นกับทุกโมเดลตลอดไป
  3. ไม่ต้องสนใจ ตำแหน่งไม่มีผลต่อการเลือก tool
  4. รัน tool-use eval ของตัวเองกับโมเดลที่ใช้จริง เพราะผลต่างกันไปตามโมเดล
ดูเฉลย

D ตำแหน่งของ namespace มีผลจริงและต่างกันตามโมเดล จึงต้องวัดเอง C ผิดเพราะมีผลจริง A ผิดเพราะชื่อที่สั้นลงประหยัดได้น้อยมาก B ผิดเพราะผลเปลี่ยนเมื่อเปลี่ยนโมเดล

4. จำกัด tool ตามบทบาทของแต่ละ agent

field tools ของ subagent

ใน AgentDefinition ของ subagent field tools กำหนดว่าตัวนั้นใช้ tool อะไรได้บ้าง ถ้าไม่ใส่ subagent จะได้ทุก tool ที่เปิดให้ subagent ใช้ ไม่ใช่ได้ชุดย่อยของ parent โดยอัตโนมัติ และโน้ตใน CLAUDE.md หรือ permission mode ของ parent ก็ไม่ได้เปลี่ยนเรื่องนี้

agents: {
  "doc-auditor": {
    description: "ตรวจเอกสารโดยไม่แก้ไข",
    prompt: "คุณคือผู้ตรวจเอกสาร ...",
    tools: ["Read", "Grep", "Glob"],   // อ่านและค้นได้อย่างเดียว ไม่ว่า parent จะมีอะไร
    model: "sonnet"                    // override รุ่นเฉพาะ subagent นี้
  }
}

disallowedTools และ mcpServers

  • disallowedTools รับ pattern ของ MCP ได้: mcp__server หรือ mcp__server__* ตัด tool ทุกตัวของ server นั้น ส่วน mcp__* ตัด MCP tool ทุกตัวจากทุก server ตัวอย่าง mcp__legacy__* ตัด server เก่าออกจาก agent ตัวเดียว ขณะที่ agent อื่นยังใช้ได้
  • mcpServers ในนิยาม agent ระบุ server เพียงชุดเดียว ที่ agent ตัวนั้นได้ ส่วน server ที่ไม่มี agent ไหนต้องใช้ ควรตัดการเชื่อมต่อทิ้งไปเลย

อนุมัติ (approve) ≠ จำกัด (scope)

allowedTools แค่ อนุมัติล่วงหน้า ให้ tool ที่ระบุรันได้โดยไม่ต้องถาม แต่ ไม่ได้ปิด tool อื่น tool ที่ไม่อยู่ในรายการยังมีอยู่และถูกเรียกได้ แค่ไปตกที่ permission mode แทน ในโหมด default การเรียกที่ต้องขออนุมัติและไม่ตรง allow rule จะไปที่ callback canUseTool ซึ่งในงาน headless (เช่น CI) ไม่มีใครมาตอบ

ถ้าต้องการพื้นผิวแบบปิดสำหรับ headless ให้ใช้ allowlist คู่กับ permissionMode: "dontAsk": tool ในรายการรันได้ ส่วนอะไรที่ปกติจะต้องถาม จะถูก ปฏิเสธทันที โดยไม่เรียก canUseTool

const options = {
  allowedTools: ["Read", "Glob", "Grep"],
  permissionMode: "dontAsk",   // อะไรที่ต้องถาม = ปฏิเสธ
};
การตั้งค่าผลต่อ tool ที่ไม่อยู่ใน allowlist
defaultส่งไปถาม canUseTool
dontAskถูกปฏิเสธ (ปิดพื้นผิว)
bypassPermissionsรันได้โดยไม่ถาม (ยกเว้น action ที่ไม่มีโหมดไหนอนุมัติอัตโนมัติ) ถ้าใช้คู่กับ denylist แล้วลืมใส่ตัวไหน ตัวนั้นรันได้เลย = fail open
acceptEditsอนุมัติการแก้ไฟล์และการทำงานกับ filesystem อัตโนมัติ ไม่เหมาะกับ agent อ่านอย่างเดียว
allowedTools: ["*"]ไม่ได้ลดพื้นผิวลงเลย
planเป็นโหมดระดับเซสชัน ใช้จำกัด subagent ตัวเดียวแบบเลือกเจาะจงไม่ได้

Skills ก็เป็นพื้นผิวเหมือนกัน

Skill คือโฟลเดอร์ skills/<name>/ ที่มี SKILL.md โดย frontmatter มี name, description และ when_to_use (ไม่บังคับ) ตอนเริ่มเซสชันจะโหลดแค่รายการสั้นๆ ของแต่ละ Skill คำสั่งเต็มโหลดเมื่อถูกเรียก ไม่ว่าจะโดย Claude (เมื่อ description ตรง) หรือผู้ใช้พิมพ์ /name

  • ทุก Skill เพิ่มรายการหนึ่งบรรทัดใน listing และใน Claude Code ข้อความ description + when_to_use รวมกันจะถูกตัดที่ 1,536 ตัวอักษร (คนละเรื่องกับเพดาน 1,024 ตัวอักษรของ field description ใน frontmatter ฝั่ง API ที่เรียนในบท 2.5)
  • Skill ที่มีผลข้างเคียง (เช่น deploy, ส่งอีเมล) และควรให้คนเป็นผู้สั่ง ให้ใส่ disable-model-invocation: true Claude จะไม่โหลดเองและไม่ preload ให้ subagent จะรันก็ต่อเมื่อผู้ใช้พิมพ์ /name
ในข้อสอบ

มีแค่ การตั้งค่า ที่ลดพื้นผิวได้จริง: ตัด server, pattern ใน disallowedTools, tools ที่แคบลง, mcpServers ในนิยาม agent, dontAsk คู่ allowlist และ disable-model-invocation บน Skill ส่วนโน้ตใน CLAUDE.md ที่ขอให้ "อย่าใช้ tool นี้" ไม่ได้เอา definition ออก tool ยังโหลดอยู่และถูกเรียกได้

เข้าใจผิดบ่อย

"ใส่ tool ใน allowedTools แล้ว agent ใช้ได้แค่นั้น" ผิด มันแค่อนุมัติล่วงหน้า ต้องปิดด้วย dontAsk หรือบล็อกด้วย disallowedTools

"subagent ได้ชุดย่อยของ tool ของ parent เอง" ผิด ถ้าไม่มี field tools จะได้ทุก tool ที่เปิดให้ subagent ต้องจำกัดในนิยามของมันเอง

สรุปสั้นๆ

จำกัดด้วย config ไม่ใช่ด้วยคำขอร้อง: tools ต่อ subagent, disallowedTools pattern, mcpServers, allowlist + dontAsk และ disable-model-invocation สำหรับ Skill ที่มีผลข้างเคียง

ลองเดาก่อน

job ใน pipeline ตั้ง allowedTools: ["Read", "Glob", "Grep"] ไว้อย่างเดียว ไม่ได้ตั้งอะไรอื่น ระหว่างรัน Claude พยายามเรียก Write จะเกิดอะไรขึ้น?

  1. ไม่ได้อนุมัติล่วงหน้า จึงตกไปที่ permission mode และ canUseTool ซึ่งใน pipeline ไม่มีใครตอบ
  2. ถูกบล็อกทันที เพราะไม่อยู่ใน allowedTools
  3. pipeline เปลี่ยนไปใช้ bypassPermissions ให้อัตโนมัติเมื่อไม่มีคนตอบ
ดูเฉลย

A allowedTools ไม่ได้ปิด tool อื่น การเรียกที่ไม่อยู่ในรายการจะไปตามเส้นทาง permission mode ปกติ

  4. ให้ lead agent ตรวจผลหลัง subagent ทำเสร็จ แล้ว revert ถ้าพบการแก้ไฟล์

C subagent ไม่ได้ชุดย่อยอัตโนมัติ (A) รุ่นของโมเดลไม่เกี่ยวกับสิทธิ์ใช้ tool (B) และการตามแก้ทีหลังไม่ใช่การป้องกัน เพราะการแก้เกิดขึ้นไปแล้ว (D)

  3. เปลี่ยนชื่อ tool ของ billing ให้ขึ้นต้นด้วย zz_ จะได้อยู่ท้ายรายการ
  4. ตัดการเชื่อมต่อ MCP server marketing ที่ไม่เคยถูกใช้
  5. เพิ่ม max_tokens ให้ agent มีที่คิดมากขึ้น
  6. ใส่ disallowedTools: ["mcp__oldcrm__*"] ให้ agent ตัวนี้
ดูเฉลย

B, D, F ทั้งสามเป็นการตั้งค่าที่ตัดหรือปิดความสามารถจริง A เป็นแค่คำแนะนำ tool ยังโหลดอยู่ C แค่เปลี่ยนชื่อ จำนวน tool เท่าเดิม E เกี่ยวกับความยาว output ไม่ได้เอา tool ออก

5. เลือกวิธีแก้ให้ตรงต้นตอ

การรวม การตั้ง namespace และการ scope เปลี่ยนชุดของ tool ส่วนเทคนิคด้าน context ไม่แตะชุด tool แต่เปลี่ยนว่า token ไปอยู่ตรงไหน

ต้นตอวิธีแก้ผล
tool ทับกันหรือคลุมเครือรวม + namespaceตัวเลือกน้อยลงและชัดขึ้น
บทบาทหนึ่งถือ tool ของอีกบทบาทscope ด้วย tools, disallowedTools, mcpServersแต่ละ agent ได้แค่ของตัวเอง
ชุด tool ใหญ่ (20+) แต่แต่ละรอบใช้ไม่กี่ตัวTool searchdefinitions โหลดเมื่อถูกค้นเท่านั้น
ชุด tool ใหญ่คงที่ ใช้ข้าม request จำนวนมากPrompt cachingถูกลง แต่จำนวน token เท่าเดิม
tool_result เก่าค้างเยอะContext editingตัดผลเก่าที่หมดประโยชน์
เรียก tool เล็กๆ ต่อกันเป็นสายที่รวมเป็น script ได้Programmatic tool callingผลระหว่างทางไม่เข้าประวัติ
  • Programmatic tool calling: แทนที่จะไป-กลับ 5 รอบ Claude เขียน script เดียวที่เรียกทั้ง 5 ฟังก์ชันใน sandbox ได้กลับมาแค่ผลสุดท้าย เหมาะกับงาน batch ซ้ำๆ แต่ไม่ช่วยเรื่องชุด tool ที่ใหญ่เกิน
  • Tool search: เก็บ definitions ไว้นอก context จนกว่า Claude จะค้นหา เสียหนึ่งรอบเพื่อ lookup แต่ประหยัด context พื้นฐานได้มาก เหมาะกับ catalogue ใหญ่ที่แต่ละคำขอใช้ไม่กี่ตัว แต่ไม่แก้ tool ที่ทับกัน เพราะการค้นอาจคืนทั้งสองตัวที่ชวนสับสนมาพร้อมกัน
  • Prompt caching: ลดราคาของ definitions ที่ส่งซ้ำ แต่ไม่ลดพื้นที่ใน context และไม่ลดผลต่อการเลือก tool ใช้แก้ปัญหาเรื่องเงิน ไม่ใช่เรื่องความแม่นหรือพื้นที่

ลำดับที่แนะนำสำหรับ agent ที่มีปริมาณงานสูง

  1. รวมและ scope ก่อน เพราะ tool ที่ถูกเอาออกไม่ต้องเสียค่า defer, cache หรือ trim อะไรเลย
  2. cache definitions ตั้งแต่เนิ่นๆ
  3. เพิ่ม tool search เมื่อชุด tool เกินราว 20 ตัว หรือ context พื้นฐานเริ่มเห็นผล
  4. เพิ่ม context editing เมื่อบทสนทนายาว

ตัวอย่างเคส: agent HR มี tool 10 ตัว definitions คงที่ แต่เรียก find_employee แทน search_staff ผิดบ่อย tool search ไม่ช่วยเพราะ tool มีน้อยอยู่แล้ว ปัญหาคือการทับกัน ต้องรวมหรือตั้ง namespace และเขียน description ให้คมขึ้น

เข้าใจผิดบ่อย

"Tool search แก้ปัญหาเลือกผิดระหว่าง tool ที่คล้ายกัน" ไม่ใช่ มันแค่ลด definitions ที่โหลด การทับกันต้องแก้ด้วยการรวมและ namespace

"Prompt caching แก้ context bloat" ไม่ใช่ ลดแค่ราคา definitions ยังกินพื้นที่และความสนใจเท่าเดิม

สรุปสั้นๆ

ตัดและรวมก่อนเสมอ แล้วค่อยใช้เทคนิคด้าน context ให้ตรงต้นตอ: เยอะแต่ใช้น้อย → tool search, แพง → caching, ผลเก่าค้าง → context editing, เรียกเป็นสาย → programmatic, ทับกัน → รวม/namespace
