6.5 AI solution lifecycle: ตั้งแต่ discovery จนถึง retirement

ต้นฉบับ: CertSafari 6.5

อ่านจบแล้วควรทำได้
  • เรียก 6 phase ของ lifecycle ได้ และบอกได้ว่าแต่ละ phase ต้องส่งอะไรให้ phase ถัดไป
  • แยกได้ว่างานไหนเป็นของ discovery และงานไหนยังไม่ถึงเวลา
  • เลือก build surface (Client SDK, Agent SDK, Managed Agents) จากคำถามว่า "ใครดูแล agent loop และ runtime"
  • เขียน acceptance test ที่คนไม่มี context ก็ตัดสินผ่าน/ไม่ผ่านได้
  • อ่าน usage และตั้ง budget ของ Managed Agents ได้ถูกจังหวะ และตัดสิน ship / fix / stop จากผล eval
  • วางแผน retire ทั้งงานของเราเองและโมเดลที่เราใช้ รวมถึงรู้ว่าอะไรหายไปเมื่อลบ session
แนวคิดหลัก: ทุก phase ส่งมอบของที่จับต้องได้

Solution หนึ่งตัวเดินผ่าน 6 phase: discovery, design, handoff, monitoring, iteration และ retirement แต่ละ phase ต้องส่ง artifact ที่เป็นรูปธรรม ให้ phase ถัดไป และสถาปนิกเป็นเจ้าของผลลัพธ์ตลอดทุก phase ไม่ใช่แค่ช่วงออกแบบ

1. หก phase และสิ่งที่ส่งต่อกัน

Phaseคำถามหลักส่งอะไรให้ phase ถัดไป
Discoveryแก้ปัญหาอะไร ให้ใคร และแบบไหนเรียกว่าสำเร็จsuccess criteria, acceptance tests, evaluation set
Designarchitecture และ build surface แบบไหนทำให้ผ่านเกณฑ์design ที่พฤติกรรมตรวจได้ด้วย test
Handoffทีมวิศวกรสร้างและแก้ไขได้อย่างปลอดภัยไหมtest ที่นิยามคำว่า "เสร็จ" + design
Monitoringใช้ได้จริงกับผู้ใช้จริงในต้นทุนที่รับได้ไหมผลที่วัดได้ เทียบกับ criteria
Iterationship, fix หรือ stopเวอร์ชันใหม่ หรือการตัดสินใจ retire
Retirementจะปิดงานของเรา หรือย้ายออกจากโมเดลที่ใช้อยู่ยังไงmigration ไปสู่ตัวแทน พร้อมเก็บบันทึกไว้

Phase เหล่านี้ เป็นวงวน ไม่ใช่เส้นตรง iteration แต่ละรอบวนกลับไปที่ design และ handoff ของเวอร์ชันใหม่ ส่วน monitoring ทำต่อเนื่องตลอดที่ระบบยังใช้งาน และ retirement อาจถูกกระตุ้นจาก ภายนอก ได้ด้วย เช่น โมเดลที่เราใช้ถูกประกาศวัน retire

เรื่องที่เกี่ยวกับการ ship อย่าง migration, versioning, rate limit และ feature flag ต้องถูกวางแผนอย่างตั้งใจไว้ใน phase ที่เป็นเจ้าของเรื่องนั้น ไม่ใช่ปล่อยให้โผล่มาเองตอนจะขึ้น production

สรุปสั้นๆ

Discovery → Design → Handoff → Monitoring → Iteration → (วนกลับ หรือ) Retirement ทุกขั้นส่ง artifact ที่ตรวจได้ และ retirement มาจากนอกวงได้

Checkpoint 1 (จับคู่)

โปรเจกต์ผู้ช่วยตอบคำถามประกันภัย จับคู่ artifact กับ phase ที่ผลิตมัน:

  1. "ต้องตอบถูก ≥ 90% บนชุดคำถาม 500 ข้อ และมีคำถามกำกวม 50 ข้อในชุด"
  2. แผนภาพระบบที่บอกว่าแต่ละขั้นตรวจด้วย test ไหนได้
  3. dashboard สัปดาห์นี้: ความแม่น 87%, ต้นทุนต่อคำถามเกินเป้า 15%
  4. มติประชุม: "แก้ retrieval ก่อน ship เวอร์ชันถัดไป"
  5. แผนย้ายไปโมเดลรุ่นใหม่ พร้อม export log เก่าเก็บไว้

ตัวเลือก: (a) Discovery (b) Design (c) Monitoring (d) Iteration (e) Retirement

ดูเฉลย

1-a, 2-b, 3-c, 4-d, 5-e สังเกตว่า monitoring กับ iteration ใช้เกณฑ์จาก discovery เป็นตัวเทียบ

2. Discovery: ตกลงกันว่า "สำเร็จ" หน้าตาเป็นยังไง

  • Success criteria ต้องเป็นตัวเลข ไม่ใช่ "ตอบได้ดี" ตัวอย่างในบท: F1 อย่างน้อย 0.85 บน held-out set ขนาด 10,000 โพสต์ และ 95% ของคำตอบต้องกลับมาภายใน 200 ms
  • Evaluation set ต้องสะท้อนการกระจายของงานจริง รวมถึง edge case อย่าง input ว่าง หรือ input ยาวมาก
  • Eval set ที่เป็นรูปธรรมช่วย ยุติข้อถกเถียงเรื่อง edge case ตั้งแต่ต้น ก่อนที่วิศวกรแต่ละคนจะเขียนโค้ดตามความเข้าใจของตัวเองจนเข้ากันไม่ได้

เปรียบง่ายๆ discovery คือการตกลงว่าข้อสอบมีข้ออะไรบ้างและได้กี่คะแนนถึงผ่าน ก่อนจะเริ่มติวเลือกว่าจะอ่านหนังสือเล่มไหน

ในข้อสอบ

Discovery = use case, เกณฑ์ที่วัดได้ และ eval set เท่านั้น การเลือกโมเดลและ prompt เป็นงาน design caching และ batching เป็นการ จูนต้นทุน ของ design ที่มีอยู่แล้ว ส่วน runbook เป็นงาน handoff

เข้าใจผิดบ่อย

"สัปดาห์แรกของ discovery ให้ตั้ง caching และเขียน runbook ไว้ก่อนเลย" ไม่ใช่ ของพวกนี้ขึ้นกับ design ที่ยังไม่มี

สรุปสั้นๆ

Discovery ส่งมอบเกณฑ์เป็นตัวเลข + eval set ที่มี edge case เรื่องโมเดล, caching, runbook ยังไม่ถึงคิว

Checkpoint 2

สัปดาห์แรกของโปรเจกต์คัดกรองใบสมัครงานอัตโนมัติ ผู้จัดการถามว่าทีมควรส่งมอบอะไรเมื่อจบสัปดาห์?

  1. เลือกโมเดลและล็อก prompt สุดท้าย
  2. เกณฑ์ความสำเร็จที่เป็นตัวเลข พร้อม eval set ที่รวมเคสยาก เช่น ใบสมัครว่างเปล่าหรือยาวผิดปกติ
  3. Runbook สำหรับทีม on-call
  4. แผน caching และ batching เพื่อลดค่าใช้จ่าย
ดูเฉลย

B A เป็นงาน design ที่ต้องมีเกณฑ์ก่อน C เป็นงาน handoff และ D เป็นการจูนต้นทุนของ design ที่ยังไม่มี

Checkpoint 3

ข้อใดเป็นกิจกรรมของ discovery?

  1. นิยาม use case, ตั้งเกณฑ์ที่วัดได้ และสร้าง eval set
  2. เลือกโมเดลและ prompt ให้เสร็จก่อนคุย requirement
  3. ตั้งค่า prompt caching
  4. เขียนขั้นตอนรับมือเหตุขัดข้องให้ทีม support
ดูเฉลย

A B ข้าม discovery ไปเลย C เป็นงานหลังมี solution แล้ว และ D เป็นงาน handoff

3. Design: เลือก build surface

หลายครั้ง constraint ที่ได้จาก discovery ก็ตัดสิน build surface ให้แล้ว คำถามที่ชี้ขาดคือ ใครเป็นคนดูแล agent loop และ runtime

Surfaceได้อะไรใครดูแล loop และ runtimeเลือกเมื่อ
Client SDK (Messages API)เข้าถึง API ตรงๆ เราเขียน tool loop เองเราทั้งหมดต้องการ loop แบบ custom และคุมละเอียด
Agent SDKlibrary ที่รัน Claude Code binary มี built-in tool (ไฟล์, คำสั่ง, ค้นหา), permissions, sessions และ hooksเรา ใน process ที่เราดูแลอยากได้ tool อ่านไฟล์/รันคำสั่ง/ค้นหาโดยไม่ต้องเขียน loop
Managed Agentsharness ที่ host ไว้รัน agent loop ให้ sandbox เป็นแบบ Anthropic ดูแลบน cloud หรือ self-hosted บน infrastructure ของเราก็ได้Anthropic host ตัว harnessงานยาวแบบ async และไม่อยากดูแล agent infrastructure เอง

จุดที่ต้องจำ: Agent SDK ยังรันบนเซิร์ฟเวอร์ของเรา ดังนั้นถ้า requirement คือ "ไม่ต้องดูแล infrastructure" คำตอบคือ Managed Agents และถ้าต้องการให้ข้อมูลของ tool อยู่ในบ้าน แต่ก็ไม่อยากดูแล loop ให้ใช้ Managed Agents กับ self-hosted sandbox

ลองเดาก่อน

ลูกค้าอยากรันงานสืบสวนยาวๆ แบบ async และไม่อยากดูแล infrastructure เลย เลือกอะไร? Managed Agents เพราะ Agent SDK ยังรันใน process ที่ลูกค้าต้องดูแล และ Client SDK ต้องเขียน loop เอง

เข้าใจผิดบ่อย

"ลูกค้าไม่อยากดูแล infra ก็ใช้ Agent SDK สิ เพราะมี loop ให้แล้ว" Agent SDK มี loop ให้จริง แต่ยังรันใน process ที่ลูกค้าต้องดูแล คำตอบที่ถูกคือ Managed Agents

สรุปสั้นๆ

เขียน loop เอง = Client SDK / มี tool และ loop ให้แต่รันบนเครื่องเรา = Agent SDK / ไม่อยากรัน infra = Managed Agents (sandbox บน cloud หรือ self-hosted)

Checkpoint 4

โรงพยาบาลต้องการ agent ที่จับคู่ใบแจ้งหนี้กับเวชระเบียน ทีม IT ไม่อยากดูแล agent loop เอง แต่ข้อมูลที่ tool เข้าถึงต้องอยู่บนเครื่องของโรงพยาบาลเท่านั้น ควรเลือกอะไร?

  1. Managed Agents กับ sandbox ที่ Anthropic ดูแลบน cloud
  2. Managed Agents กับ self-hosted sandbox บน infrastructure ของโรงพยาบาล
  3. Agent SDK รันใน process ของโรงพยาบาล
  4. Client SDK แล้วเขียน loop เอง เพราะเป็นทางเดียวที่ข้อมูลอยู่ในบ้าน
ดูเฉลย

B A ทำให้ tool รันนอกโรงพยาบาล C และ D ทำให้ทีม IT ต้องดูแล loop/runtime เอง และไม่มีอะไรบอกว่า Messages API เป็นทางเดียวที่เก็บข้อมูลในบ้านได้

Checkpoint 5

สตาร์ทอัพอยากให้ agent ไล่วิเคราะห์ incident ย้อนหลังครั้งละหลายชั่วโมงแบบ async โดยไม่มีทีม ops มาดูแล runtime ควรเลือกอะไร?

  1. Messages API กับ loop ที่เขียนเอง
  2. Agent SDK บนเซิร์ฟเวอร์ของสตาร์ทอัพ
  3. Managed Agents
  4. Files API ร่วมกับ prompt caching
ดูเฉลย

C Anthropic รัน loop และ sandbox ให้ A ต้องสร้างและดูแล orchestration เอง B ต้องมีคนดูแล runtime และ D จัดการเอกสารกับต้นทุน ไม่ใช่ orchestration

Checkpoint 6

ทีม platform อยากได้ agent ภายในที่อ่านไฟล์ใน repo, รัน test และแก้โค้ดได้ โดยไม่ต้องเขียน tool loop เอง และไม่ติดที่จะรันบนเซิร์ฟเวอร์ตัวเอง ควรเลือกอะไร?

  1. Agent SDK
  2. Client SDK
  3. เรียก Messages API ครั้งเดียวต่อไฟล์
  4. Usage and Cost Admin API
ดูเฉลย

A มี built-in tool, loop และการจัดการ context ให้ B ต้องเขียน loop เอง C ทำงานแบบอิสระหลายขั้นไม่ได้ และ D แค่รายงานการใช้งานและค่าใช้จ่าย ไม่ได้รัน tool

4. Handoff: ส่งมอบให้ทีมวิศวกรแบบที่ "เสร็จ" มีความหมายเดียว

  • Acceptance test ต้องชัดพอที่คนไม่มี context ก็ตัดสินได้ ว่าผ่านหรือไม่ผ่าน "ตอบสุภาพ" ตรวจไม่ได้ แต่ "เมื่อลูกค้าพิมพ์ X ระบบต้องตอบ Y และถ้าขาดข้อมูล Z ต้องถามกลับ" ตรวจได้
  • Test พวกนี้ ปกป้องระบบต่อหลัง launch ทำให้การแก้ไขภายหลังปลอดภัย
  • ถ้าไม่มี test ตั้งแต่ตอนส่งมอบ วิศวกรแต่ละคนจะนิยามคำว่า "เสร็จ" ไม่เหมือนกัน
Given ลูกค้ามีนัดพรุ่งนี้ 10:00 และมีเบอร์โทรในระบบ
When  ถึงเวลา 18:00 ของวันนี้
Then  ส่ง SMS เตือนนัด 1 ข้อความ ระบุวัน เวลา สาขา

Given ลูกค้ามีนัดพรุ่งนี้ แต่ไม่มีเบอร์โทร
Then  ไม่ส่ง SMS และสร้างงานให้เจ้าหน้าที่โทรตามแทน

Checkpoint 7

ข้อใดเป็น acceptance test ที่พร้อมส่งมอบให้ทีมวิศวกร?

  1. "bot ต้องให้ความรู้สึกเป็นกันเองกับลูกค้า"
  2. "ยังไม่ต้องเขียน test ให้แต่ละคนตกลงกันเองหลัง sprint แรก"
  3. "เมื่อพัสดุเลยกำหนดส่ง 3 วัน ระบบส่งข้อความขอโทษพร้อมเลขติดตาม ถ้าไม่มีเลขติดตามให้ส่งต่อเจ้าหน้าที่"
  4. "ระบบต้องเสถียรและใช้ง่าย"
ดูเฉลย

C มี trigger ชัด ผลที่คาดชัด และมี edge case ข้อมูลขาด A และ D ตรวจไม่ได้ ส่วน B ทำให้แต่ละคนนิยามคำว่าเสร็จต่างกัน

5. Monitoring: วัดของจริงกับผู้ใช้จริง

Usage ของ Managed Agents

แต่ละ session มี usage object ที่ สะสม ไปเรื่อยๆ และจะ เป็นค่าสุดท้ายเมื่อ session เข้าสถานะ idle field ที่มี:

  • input_tokens, output_tokens
  • cache_read_input_tokens
  • cache_creation ซึ่งแยกเป็น ephemeral_5m_input_tokens และ ephemeral_1h_input_tokens
  • list_cost มี amount และ currency คิดตามราคา list สาธารณะ หน่วยเป็น เซนต์
  • active_seconds
สถานะ sessionความหมายสำหรับ usage
runningตัวเลขยังขึ้นอยู่
idleตัวเลขเป็นค่าสุดท้าย ให้อ่านตอนนี้
terminatedsession จบแล้ว

Budget เป็นเพดานแข็ง

Session budget คือ hard cap เมื่อ list cost ถึงเพดาน platform จะ หยุดแต่ละ thread ไว้ก่อนการเรียกโมเดลครั้งถัดไป อย่าไปเขียนระบบ poll usage แล้วสั่งหยุด session เอง เพราะมันช้ากว่าและพลาดได้

สัญญาณที่ต้องเฝ้า

Webhook eventความหมาย
session.status_idledsession เข้า idle เช่น รอการอนุมัติ
session.budget_reachedsession ชน budget
session.status_terminatedsession จบ
deployment_run.failedscheduled run เริ่ม session ไม่สำเร็จ

  • Webhook อาจหลุดได้ จึงต้อง list session ตามรอบเวลา ควบคู่ไปด้วย
  • จะรีวิว session events แบบ offline เพื่อหาพฤติกรรมที่เกินสิทธิ์ที่ให้ไว้ก็ได้ (ไม่บังคับ)
  • การรีวิว transcript เจอปัญหาได้ หลังจาก call เกิดไปแล้วเท่านั้น การป้องกันจริงต้องมาจาก limit ที่ตั้งไว้ตอน design
สรุปสั้นๆ

อ่าน usage ตอน idle, list_cost หน่วยเซนต์, budget เป็น hard cap ที่ platform บังคับให้ เฝ้า webhook แต่ list session สำรองด้วย และป้องกันด้วย limit ตั้งแต่ design

Checkpoint 8

ระบบ billing ภายในอยากบันทึกต้นทุนของแต่ละ session ของ Managed Agents ให้เป็นตัวเลขสุดท้าย ควรอ่าน usage เมื่อ session อยู่ในสถานะไหน?

  1. running
  2. idle
  3. budget_reached
  4. ทุกๆ 5 วินาทีระหว่างทำงาน แล้วเอาค่าสูงสุด
ดูเฉลย

B ตอน running ตัวเลขยังขึ้นอยู่ budget_reached เป็นชื่อ event ไม่ใช่สถานะ และการ poll เองไม่จำเป็นเพราะ usage สะสมและเป็นค่าสุดท้ายตอน idle

6. Iteration: ship, fix หรือ stop

การตัดสินเมื่อไหร่
Ship itเวอร์ชันนี้ผ่านเกณฑ์ และรักษาเกณฑ์ไว้ได้ใน production
Fix itมีช่องว่างที่วัดได้ชัด และแก้ได้ด้วยการปรับงาน (rollback ก็นับเป็น fix แบบเร็ว)
Stop itsolution ไม่คุ้มที่จะเก็บไว้แล้ว ส่งไป retirement

Capability eval กับ regression eval

  • Capability eval เริ่มต้นด้วย pass rate ต่ำ บอกว่าควรพัฒนาอะไรต่อ
  • Regression eval ควรผ่านเกือบ 100% เสมอ ถ้าตกเมื่อไหร่ แปลว่ามีอะไรพัง
  • เมื่อ capability eval ตัวไหนผ่านได้สม่ำเสมอแล้ว ให้ ย้ายเข้า regression suite และรันต่อเนื่อง ไม่ใช่ทิ้งหรือขยับเกณฑ์ขึ้น เพราะจะมองไม่เห็น drift
  • ถ้า regression ตก ต้อง fix แม้ capability จะดีขึ้นก็ตาม

หลักคิด: prototype ได้อิสระ แต่ ship อย่างเลือกสรร

เข้าใจผิดบ่อย

"capability eval ผ่านหมดแล้ว ลบทิ้งได้" ไม่ใช่ ย้ายเข้า regression suite

"capability ขึ้นเยอะ regression ตกนิดหน่อย ship ไปก่อนแล้วตั้ง baseline ใหม่" เท่ากับซ่อนสิ่งที่พัง

สรุปสั้นๆ

Ship = ผ่านและคงอยู่ใน prod, Fix = gap ที่วัดได้ (รวม rollback), Stop = ไม่คุ้ม regression ตกเมื่อไหร่ = fix capability eval ที่อิ่มตัวย้ายเข้า regression

Checkpoint 9

เวอร์ชันใหม่ของ agent จองห้องประชุม: capability eval ขึ้นจาก 35% เป็น 70% แต่ regression eval ตกจาก 99% เหลือ 92% และผู้บริหารชอบ demo มาก ควรตัดสินอย่างไร?

  1. Ship แล้วตั้ง 92% เป็น baseline ใหม่
  2. Ship เพราะ capability ที่เพิ่มขึ้นคุ้มกว่า
  3. Fix: regression ที่ตกบอกว่ามีของพัง ต้องแก้ก่อน ship
  4. Stop แล้วส่งไป retirement
ดูเฉลย

C A ซ่อนสิ่งที่พัง B ให้ demo ชนะข้อมูล และ D ใช้กับ solution ที่ไม่คุ้มเก็บแล้ว ไม่ใช่ gap ที่แก้ได้

7. Retirement: ปิดงานของเรา หรือย้ายออกจากโมเดล

Retirement มีสองแบบ: ปิดงานของเราเอง (ผลจากการตัดสิน stop it) และ โมเดลที่เราใช้ถูก retire ซึ่งเป็นไปตามปฏิทินของผู้ให้บริการ เมื่อโมเดล retire แล้ว request ไปหาโมเดลนั้นจะล้มเหลว ต้อง migrate ให้เสร็จก่อนวัน retire

"integration เดิมยังใช้ได้หลังโมเดล retire" ไม่ใช่ request จะล้มเหลว ต้อง migrate ให้เสร็จก่อนวัน retire

สรุปสั้นๆ

Retirement = stop it ของเราเอง หรือปฏิทินโมเดลของผู้ให้บริการ migrate ก่อนวัน retire ก่อนลบ session ให้ export events และดาวน์โหลดไฟล์ที่สร้างขึ้น และอย่าลืมลบ uploaded files / memory stores / vaults แยก

Checkpoint 10 (จับคู่)

ทีมกำลังปิดโปรเจกต์ agent วิเคราะห์สัญญาบน Managed Agents และจะลบ session ทั้งหมด จับคู่ข้อมูลกับสิ่งที่ต้องทำ:

  1. ลำดับ event ของการวิเคราะห์ที่ฝ่ายกฎหมายต้องเก็บ 7 ปี
  2. รายงาน PDF ที่ agent สร้างไว้ใน session
  3. สัญญาต้นฉบับที่ทีมอัปโหลดเข้าไป
  4. memory store ที่เก็บข้อสรุปจากหลาย session

ตัวเลือก: (a) export ผ่าน events API ก่อนลบ เพราะจะหายไปกับ session (b) ดาวน์โหลดก่อนลบ เพราะจะหายไปกับ session (c) ไม่หายไปกับ session ต้องลบแยกเอง
