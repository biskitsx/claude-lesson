2.5 Prompt reuse with caching, modular prompts and Agent Skills

ต้นฉบับ: CertSafari 2.5

อ่านจบแล้วควรทำได้
  • อธิบายได้ว่า prompt caching เก็บอะไร อายุเท่าไร และคิดเงินยังไง พร้อมคำนวณความคุ้มได้
  • ใช้ automatic caching กับ explicit cache_control breakpoint ร่วมกันได้ถูก และรู้ข้อจำกัด 4 breakpoint
  • วินิจฉัย cache miss ที่เกิดจาก lookback 20 block และแก้ได้
  • จัดลำดับ prompt แบบ modular: ส่วนคงที่ไว้ก่อน ส่วนที่เปลี่ยนไว้ท้าย และรู้ว่าการเปลี่ยนอะไรทำ cache ส่วนไหนพัง
  • เขียน SKILL.md ให้ผ่านกฎ รู้ว่า Skill อยู่ที่ไหนและใครใช้ได้ และอธิบาย progressive disclosure 3 ระดับ
แนวคิดหลัก: ต้นเหมือนกันเป๊ะ ถึงจะ reuse ได้

Caching ได้ผลเฉพาะเมื่อ ส่วนต้นของ request เหมือนกับครั้งก่อนทุกตัวอักษร การจัด prompt แบบ modular ช่วยให้ส่วนต้น (prefix) นิ่ง โดยเอาของที่เปลี่ยนบ่อยไว้ท้ายสุด ส่วน Agent Skills ดึงคำสั่งที่ใช้ซ้ำออกจาก prefix ไปเลย แล้วค่อยโหลดเข้ามาเมื่องานต้องใช้จริง

1. Prompt caching เก็บอะไร และต้องจ่ายเท่าไร

Caching เก็บ prefix ของ request ไว้จนถึงจุดที่เรียกว่า breakpoint request ถัดไปที่ขึ้นต้นเหมือนกันจะข้ามการประมวลผลส่วนนั้นไปได้ เปรียบเหมือนร้านกาแฟที่ต้มน้ำเชื่อมไว้หม้อใหญ่ แก้วต่อไปตักใช้ได้เลยไม่ต้องเคี่ยวใหม่ ของที่เหมาะจะ cache: system prompt ยาว ตัวอย่างจำนวนมาก เอกสารอ้างอิงขนาดใหญ่ งานซ้ำๆ และบทสนทนาหลายรอบที่ยาว

อายุของ cache

  • ค่าเริ่มต้นอยู่ได้ 5 นาที และทุกครั้งที่ถูกใช้ อายุจะต่อใหม่ ฟรี
  • เลือก TTL 1 ชั่วโมง ได้ ค่าเขียนแพงขึ้นเป็น 2 เท่า ของราคา input ปกติ
  • นาฬิกาเริ่มนับ ตอนที่ request ที่เขียนหรืออ่าน cache เริ่มต้น ไม่ใช่ตอน response จบ ดังนั้นถ้า response stream นานๆ เวลาที่เหลือก็หดลง เช่น stream 4 นาที จะเหลือราว 1 นาทีให้ request ถัดไปมาใช้

ราคา (ต่อ 1 ล้าน token)

  • breakpoint ไม่มีค่าใช้จ่าย เราจ่ายแค่ 3 อย่าง: การเขียน cache, การอ่าน cache และ input ที่ไม่ได้ cache
  • ลองคิดเลข: system prompt 50,000 token บน Opus 5.5 ถ้าไม่ cache = $0.20 ต่อ request เขียน cache ครั้งแรก = $0.25 แล้วแต่ละ hit = $0.01 ส่วนเกินตอนเขียน ($0.05) คืนทุนตั้งแต่ใช้ซ้ำครั้งแรก
  • prefix ที่สั้นกว่า ความยาวขั้นต่ำ ของรุ่นนั้นจะไม่ถูก cache เลย แม้ใส่ cache_control ไว้ ขั้นต่ำคือ 512 token ในรุ่นปัจจุบัน และสูงสุดถึง 4,096 ในบางรุ่นเก่า เช่น Haiku 4.5
เข้าใจผิดบ่อย

"5 นาทีเริ่มนับหลัง response จบ" ไม่ใช่ เริ่มนับตอน request เริ่ม การ generate นานๆ กินเวลาในหน้าต่างนั้นไป

"ยิ่งใส่ breakpoint เยอะ ยิ่งเสียเงินเพิ่ม" ไม่ใช่ breakpoint ฟรี จ่ายแค่ write, read และ input ที่ไม่ได้ cache

สรุปสั้นๆ

Cache = เก็บ prefix ที่เหมือนกันเป๊ะ อยู่ 5 นาที (ต่ออายุฟรีเมื่อใช้) หรือ 1 ชม. ที่ค่าเขียน 2 เท่า นับเวลาจากตอนเริ่ม request hit ถูกมาก breakpoint ฟรี และต้องยาวถึงขั้นต่ำก่อนถึงจะ cache

Checkpoint 1

แชตบอตกฎหมาย cache system prompt ไว้ด้วย TTL ค่าเริ่มต้น คำถามหนึ่งทำให้ response stream ยาว 4 นาที ผู้ใช้อยากถามต่อโดยใช้ cache เดิม ข้อไหนถูก?

  1. มีเวลาอีก 5 นาทีเต็มหลัง response จบ
  2. cache ถูกลบทันทีเมื่อ response ใดๆ stream นานเกิน 3 นาที
  3. ใช้ cache ต่อได้เฉพาะเมื่อ request ถัดไปส่งผ่าน connection เดิม
  4. request ถัดไปต้องเริ่มภายในราว 1 นาทีหลัง response จบ
ดูเฉลย

D 5 นาทีนับจากตอน request เริ่ม stream 4 นาทีจึงเหลือราว 1 นาที A นับผิดจุด ส่วน B และ C เป็นกฎที่ไม่มีอยู่จริง

2. Automatic caching กับ explicit cache_control breakpoint

  • Automatic caching: ใส่ field cache_control ที่ระดับบนสุดของ request แค่ที่เดียว ระบบจะวาง breakpoint ไว้ที่ block สุดท้ายที่ cache ได้ และเลื่อนตามไปเองเมื่อบทสนทนายาวขึ้น
  • Explicit breakpoint: ใส่ cache_control ที่ content block แต่ละตัว ใช้เมื่ออยากคุมละเอียด เช่น cache ส่วนที่เปลี่ยนไม่บ่อยแยกจากส่วนที่เปลี่ยนบ่อย
{
  "model": "claude-opus-5-5",
  "max_tokens": 1024,
  "cache_control": {"type": "ephemeral"},
  "system": [
    {"type": "text",
     "text": "คู่มือนโยบายบริษัท ... (ยาวมาก)",
     "cache_control": {"type": "ephemeral"}}
  ],
  "messages": [{"role": "user", "content": "สรุปนโยบายการลาให้หน่อย"}]
}

ตัวอย่างนี้เป็น setup ที่นิยม: explicit breakpoint บน system prompt + automatic caching ตามท้ายบทสนทนา ถ้าอยากได้อายุ 1 ชั่วโมง ใส่ "ttl": "1h" ไว้ใน object เดียวกัน เช่น {"type": "ephemeral", "ttl": "1h"}

กฎ 4 breakpoint

  • หนึ่ง request มี breakpoint ได้ สูงสุด 4 จุด automatic caching ใช้ไป 1 ช่อง
  • ถ้ามี explicit breakpoint ระดับ block ครบ 4 จุดแล้วยังเปิด automatic ด้วย → 400
  • ถ้า block สุดท้ายมี explicit marker ที่ TTL ต่างจาก automatic caching ของ request → 400 เช่นกัน
  • ทั้งสองวิธีใช้ราคา ความยาวขั้นต่ำ กฎลำดับ และ lookback 20 block แบบเดียวกัน
สรุปสั้นๆ

Automatic = cache_control ระดับบนสุด เลื่อนตามบทสนทนาเอง. Explicit = cache_control ราย block. รวมกันได้ไม่เกิน 4 จุด และ TTL ต้องไม่ขัดกัน

Checkpoint 2 (เติมคำ)

request มี explicit breakpoint บน system prompt แล้ว และต้องการเปิด automatic caching ให้บทสนทนาด้วย field ระดับบนสุดที่หายไปคืออะไร?

ดูเฉลย

C automatic caching ใช้ชื่อ field เดียวกับ explicit breakpoint เพียงแต่วางไว้ที่ระดับบนสุด ชื่ออื่นไม่มีอยู่จริง

3. Lookback หา cache เก่าอย่างไร

Breakpoint คือ "ปลายของ prefix ที่จะเอาไปค้น" ถ้าไม่เจอ entry ที่ตรงตำแหน่งนั้นพอดี ระบบจะ เดินถอยหลังทีละ block หา prefix ที่ยาวที่สุดที่ request ก่อนหน้าเคยเขียนไว้ แต่เดินได้แค่ 20 ตำแหน่ง เท่านั้น breakpoint ที่ block N จะค้นแค่ block N ถึง N−19

ไล่ดูตัวอย่าง (ใช้ breakpoint เดียวท้ายบทสนทนา):

  1. รอบแรก มี 8 block → เขียน cache ที่ block 8
  2. รอบสอง มี 12 block → ค้น 12 ลงไป ชน entry ที่ block 8 = hit แล้วเขียนใหม่ที่ block 12
  3. agent วน tool loop จนรอบสามมี 34 block → ค้นได้แค่ 34 ถึง 15 ไม่ถึง block 12 = miss

สังเกตว่า entry ที่ block 12 ยังอยู่ ไม่ได้หมดอายุหรือถูกลบ แค่อยู่นอกระยะค้นหา

ทางแก้: เพิ่ม explicit breakpoint ไว้ใกล้ๆ จุดที่เขียนล่าสุด เพราะ แต่ละ breakpoint มีหน้าต่างค้นหา 20 ตำแหน่งของตัวเอง การย้าย breakpoint เดียวไปไว้ block แรกไม่ช่วย และเปลี่ยนไปใช้ automatic caching อย่างเดียวก็ไม่ช่วย เพราะใช้ lookback 20 block แบบเดียวกัน

ในข้อสอบ

เจอ cache miss ในบทสนทนายาว ทั้งที่ส่วนต้นไม่เปลี่ยนเลย → สงสัย lookback window ก่อน ไม่ใช่การหมดอายุหรือการลบ แก้ด้วย explicit breakpoint ที่ใกล้จุดเขียนล่าสุด

สรุปสั้นๆ

Breakpoint ค้นย้อนได้ 20 block ถ้า entry เก่าอยู่ไกลกว่านั้นก็ miss ทั้งที่ยังอยู่ แก้โดยเพิ่ม breakpoint ใกล้จุดเขียนล่าสุด

ลองเดาก่อน

มี cache entry ที่ block 8 ต่อมา request ยาวขึ้นเป็น 30 block โดย block 1–8 ไม่เปลี่ยนเลย และมี breakpoint เดียวที่ block 30 ผลคือ?

  1. Miss เพราะการค้นครอบคลุมแค่ block 30 ถึง 11
  2. Hit ที่ block 8
  3. Miss เพราะ entry หมดอายุแล้ว
ดูเฉลย

A 30 − 19 = 11 การค้นจึงไปไม่ถึง block 8 ทั้งที่ entry ยังอยู่

Checkpoint 3

agent วิเคราะห์ log มี explicit breakpoint ตัวเดียวที่ block สุดท้าย หลังวน tool loop เพิ่มอีกราว 25 block ก็เริ่ม miss เพื่อนร่วมทีมเสนอให้เปลี่ยนเป็น automatic caching แทน คุณควรตอบว่าอะไร?

  1. เห็นด้วย automatic caching หา entry เก่าเจอเสมอไม่ว่าห่างแค่ไหน
  2. ลดจำนวน tool ให้ต่ำกว่า 20 ตัว lookback จะได้ครอบคลุม
  3. ปิด caching ระหว่าง tool loop แล้วค่อยเปิดใหม่หลังจบ loop
  4. ไม่ช่วย automatic caching ใช้ lookback 20 block แบบเดียวกัน ต้องเพิ่ม explicit breakpoint ใกล้จุดเขียนล่าสุด
ดูเฉลย

D ทั้งสองวิธีมี lookback 20 block เท่ากัน อาการ miss หลังเพิ่มหลาย block ทั้งที่ต้นไม่เปลี่ยนชี้ไปที่ระยะค้นหา C ทำให้เสียประโยชน์ของ cache ไปเลย B สับสนระหว่างจำนวน tool กับจำนวน block

Checkpoint 4

cache entry อยู่ที่ block 9 breakpoint อยู่ที่ block 33 ส่วนต้นไม่เปลี่ยน แต่ miss ตลอด สาเหตุและทางแก้คืออะไร?

  1. lookback ค้นไปข้างหน้าจาก breakpoint ไม่ใช่ถอยหลัง จึงไม่เจอ block 9
  2. ต้องเรียก count_tokens ก่อนทุก request เพื่อลงทะเบียน prefix
  3. breakpoint ควรอยู่ที่ block แรกเสมอ ให้ย้ายไปที่ block 1
  4. block 9 ห่างจาก block 33 อยู่ 24 ตำแหน่ง เกินหน้าต่าง 20 ให้เพิ่ม explicit breakpoint ระหว่างทาง
ดูเฉลย

D การค้นจาก 33 ถอยไปได้ถึง 14 เท่านั้น A ผิดทิศ (lookback ถอยหลัง) B ไม่เกี่ยวกับ caching เลย (count_tokens ไม่มี logic ของ cache) C ผิดเพราะ breakpoint ควรอยู่ที่ block คงที่ตัวสุดท้าย ไม่ใช่ตัวแรก

4. Modular prompt layout: ของนิ่งไว้ก่อน ตัวแปรไว้ท้าย

เรียง module จาก เปลี่ยนน้อยที่สุด → เปลี่ยนบ่อยที่สุด:

  1. Tool definitions
  2. System instructions
  3. Reference context และ examples
  4. Conversation
  5. ค่าที่เปลี่ยนทุก request ไว้ท้ายสุด (ข้อความ template ที่คงที่ต้องอยู่ก่อนช่องตัวแปรทุกช่อง)

ลำดับชั้นของ cache คือ tools → system → messages การเปลี่ยนที่ชั้นไหนจะทำให้ชั้นนั้นและ ทุกชั้นหลังจากนั้น ใช้ไม่ได้ เหมือนโดมิโนที่ล้มไปข้างหน้าอย่างเดียว

สิ่งที่เปลี่ยนcache ส่วนที่ใช้ไม่ได้
แก้ tool definitionsทั้งหมด
เปิด/ปิด web search หรือ citationssystem และ messages
เปลี่ยน tool_choicemessages เท่านั้น
เปลี่ยน disable_parallel_tool_usemessages เท่านั้น
มี/ไม่มีรูปภาพmessages เท่านั้น
เปลี่ยนพารามิเตอร์ thinkingmessages เสมอ และ tools กับ system ด้วยในรุ่นที่ render การตั้งค่า thinking ไว้ก่อนส่วนนั้น

Deferred tools (tool ที่ใช้กับ tool search) ไม่อยู่ใน prefix ของ system prompt เมื่อ tool search ค้นเจอ definition จะถูก ต่อท้าย ประวัติบทสนทนา หลัง prefix ที่ cache ไว้ cache จึงยัง hit ต่อได้

พลาดบ่อย: timestamp อยู่ตรง breakpoint

# ผิด: ค่าเปลี่ยนทุก request อยู่ใน block ที่มี breakpoint
system = [
  {"type": "text", "text": RULES},
  {"type": "text", "text": f"เวลาปัจจุบัน: {now()}",
   "cache_control": {"type": "ephemeral"}},
]

# ถูก: breakpoint อยู่ท้ายส่วนคงที่ ตัวแปรอยู่หลังจากนั้น
system = [
  {"type": "text", "text": RULES, "cache_control": {"type": "ephemeral"}},
  {"type": "text", "text": f"เวลาปัจจุบัน: {now()}"},
]

แบบผิด hash ของ prefix เปลี่ยนทุก request ไม่มีอะไรถูกเขียนที่ prefix เดิมซ้ำ การ lookback จึงหาอะไรไม่เจอเลย

เข้าใจผิดบ่อย

"เปลี่ยน tool_choice แล้ว cache พังหมด" ไม่ใช่ กระทบแค่ messages มีแค่การแก้ tool definitions ที่ล้างทั้งหมด

สรุปสั้นๆ

เรียง tools → system → reference/examples → conversation → ตัวแปร การเปลี่ยนล้มไปข้างหน้าตามลำดับชั้น breakpoint ต้องอยู่ท้ายส่วนคงที่ ไม่ใช่บน timestamp

Checkpoint 5 (จับคู่)

จับคู่การเปลี่ยนแปลงกับผลต่อ cache:

  1. แก้ข้อความ description ของ tool ตัวหนึ่ง
  2. เปิด citations
  3. เปลี่ยน disable_parallel_tool_use
  4. tool search ต่อท้าย definition ของ deferred tool

A = system และ messages · B = ไม่กระทบ prefix ที่ cache ไว้ · C = ทั้งหมด · D = messages เท่านั้น

ดูเฉลย

1-C, 2-A, 3-D, 4-B การเปลี่ยนล้มไปข้างหน้าตาม tools → system → messages ส่วน deferred definition ถูกต่อท้ายหลัง prefix

Checkpoint 6

agent มี tool 20 ตัวและ system prompt ที่ cache ไว้ ประวัติยาวขึ้นเรื่อยๆ รอบนี้เปลี่ยนแค่ disable_parallel_tool_use เป็น true อย่างเดียว ผลคือ?

  1. cache ทั้งหมดใช้ไม่ได้ เพราะเกี่ยวกับ tool
  2. tools กับ messages ใช้ไม่ได้ แต่ system ยังใช้ได้
  3. tools และ system ยังใช้ cache ได้ มีแค่ messages ที่ใช้ไม่ได้
  4. ต้องรอ 5 นาทีให้ cache เดิมหมดอายุก่อน ถึงจะเขียน cache ใหม่ได้
ดูเฉลย

C field นี้อยู่ในกลุ่มเดียวกับ tool_choice คือกระทบแค่ messages A สับสนกับการแก้ definitions B เป็นไปไม่ได้เพราะการพังล้มไปข้างหน้าเท่านั้น ถ้า tools พัง system ก็ต้องพังด้วย D ไม่มีกฎแบบนั้น

5. Agent Skills: แพ็กคำสั่งที่ใช้ซ้ำเป็น SKILL.md

Skill คือ directory ที่มีคำสั่ง metadata และไฟล์ประกอบ (ถ้ามี) Claude หยิบมาใช้เองเมื่อคำขอเกี่ยวข้อง ต่างจาก prompt ตรงที่ prompt เป็นคำสั่งเฉพาะบทสนทนาเดียว แต่ Skill โหลดเมื่อต้องใช้และใช้ได้ข้ามบทสนทนา Anthropic มี Skill สำเร็จรูปสำหรับ PowerPoint, Excel, Word และ PDF ส่วน custom Skill ใช้แพ็กขั้นตอนงานขององค์กรเราเอง

Frontmatter ของ SKILL.md

ไฟล์ขึ้นต้นด้วย YAML frontmatter ที่มี field บังคับ 2 ตัว:

  • name: ไม่เกิน 64 ตัวอักษร ใช้ได้แค่ตัวพิมพ์เล็ก ตัวเลข และขีด (-) ห้ามมี XML tag และ ห้ามมีคำสงวน "anthropic" หรือ "claude" ไม่ต้องมี version suffix
  • description: ห้ามว่าง ไม่เกิน 1,024 ตัวอักษร ห้ามมี XML tag ไม่มีความยาวขั้นต่ำ ควรบอกทั้ง ทำอะไร และ ใช้เมื่อไหร่ โดยใช้คำที่ผู้ใช้น่าจะพิมพ์จริง เพราะ Claude อาจต้องเลือกจาก Skill 100+ ตัวโดยดูจาก description นี้
---
name: reconciling-invoices
description: กระทบยอดใบแจ้งหนี้กับรายการเดินบัญชี หารายการที่ไม่ตรงกัน และสรุปส่วนต่าง ใช้เมื่อผู้ใช้พูดถึงการกระทบยอด reconcile ใบแจ้งหนี้ หรือ statement ธนาคาร
---
  • ชื่อที่แนะนำเป็นแบบ gerund (คำกริยา -ing) เช่น processing-pdfs, analyzing-spreadsheets และเลี่ยงชื่อกว้างๆ อย่าง helper หรือ utils
  • ตัวอย่างชื่อที่ผิด: มีคำสงวน (anthropic-report-tool), มีขีดล่าง (report_tool), มีตัวพิมพ์ใหญ่ (Report-Tool)

Custom Skill อยู่ที่ไหน ใครใช้ได้

ที่อยู่เพิ่มยังไงใครใช้ได้
Claude APIอัปโหลดผ่าน Skills API (/v1/skills) ใช้คู่กับ skill_id และ code execution toolทุกคนใน workspace
Claude Codeโฟลเดอร์ที่มี SKILL.md ใน ~/.claude/skills/ หรือ .claude/skills/~/.claude/skills/ = ส่วนตัว, .claude/skills/ = ทุกคนในโปรเจกต์
claude.aiอัปโหลด zip ที่ Settings > Featuresเฉพาะคนที่อัปโหลด ไม่ใช่ทั้งองค์กร admin จัดการรวมศูนย์ไม่ได้

ความปลอดภัย: Skill มีโค้ดและคำสั่งที่สั่งให้เรียก tool ได้ ใช้เฉพาะจากแหล่งที่เชื่อถือได้ และตรวจทุกไฟล์ที่แนบมาก่อนแชร์

เข้าใจผิดบ่อย

"ชื่อรูปแบบถูกแล้ว (ตัวเล็ก + ขีด) ใส่คำว่า claude ก็ได้" ไม่ได้ คำสงวนห้ามอยู่ตรงไหนของชื่อก็ตาม

"อัปโหลด Skill ใน claude.ai แล้วทั้งองค์กรใช้ได้" ไม่ใช่ ใช้ได้เฉพาะคนอัปโหลด การแชร์ทั้ง workspace เป็นเรื่องของ API

ลองใช้กับงานตัวเอง

หาขั้นตอนที่ทีมพิมพ์ซ้ำใน prompt บ่อยๆ แล้วแยกให้ได้ว่า อะไรควรอยู่ใน description (ทำอะไร + ใช้เมื่อไหร่) อะไรควรอยู่ใน body ของ SKILL.md (คำสั่งหลัก) และอะไรเปลี่ยนเป็น script ได้ เพราะ Claude ต้องการแค่ผลลัพธ์ของมัน

สรุปสั้นๆ

SKILL.md ต้องมี name (≤64, ตัวเล็ก/ตัวเลข/ขีด, ห้าม anthropic/claude) และ description (≤1,024, บอกทำอะไร+ใช้เมื่อไหร่) API แชร์ทั้ง workspace, Claude Code แบ่งส่วนตัว/โปรเจกต์, claude.ai เฉพาะคนอัปโหลด

Checkpoint 7 (จับคู่)

จับคู่ที่อยู่ของ custom Skill กับคนที่ใช้ได้:

  1. อัปโหลดผ่าน /v1/skills แล้วอ้างด้วย skill_id
  2. .claude/skills/ ใน repo
  3. zip ที่อัปโหลดใน claude.ai
  4. ~/.claude/skills/

A = เฉพาะนักพัฒนาคนนั้นบนเครื่องตัวเอง · B = ทุกคนใน workspace · C = เฉพาะคนที่อัปโหลด · D = ทุกคนที่ทำงานในโปรเจกต์นั้น

ดูเฉลย

1-B, 2-D, 3-C, 4-A แต่ละช่องทางมีขอบเขตการแชร์ต่างกัน claude.ai ไม่ใช่ทั้งองค์กร

Checkpoint 8

ทีมสร้าง Skill ชื่อ excel-claude-tools description คือ "ช่วยทำงาน Excel" แต่อัปโหลดไม่ผ่าน เพราะอะไร?

  1. ชื่อต้องขึ้นต้นด้วยคำกริยารูปปกติ เช่น build-
  2. description ต้องระบุนามสกุลไฟล์ที่รองรับ เช่น .xlsx
  3. ชื่อมีคำสงวน "claude"
  4. ชื่อห้ามมีขีด
ดูเฉลย

C "claude" เป็นคำสงวน ห้ามอยู่ในชื่อ ชื่อแบบ gerund เป็นแค่คำแนะนำ ไม่ใช่กฎบังคับ description ไม่มีข้อบังคับเรื่องนามสกุลไฟล์ และขีดใช้ได้ (แต่ description นี้ควรปรับให้บอก "ใช้เมื่อไหร่" ด้วย)

6. Progressive disclosure: Skill โหลด 3 ระดับ

ระดับโหลดเมื่อไหร่ต้นทุนโดยประมาณเนื้อหา
1. Metadataตลอด ตั้งแต่เริ่มเซสชันราว 100 token ต่อ Skillname และ description
2. Instructionsเมื่อ Skill ถูก triggerต่ำกว่าราว 5k tokenbody ของ SKILL.md
3+. Resourcesเมื่อต้องใช้ศูนย์จนกว่าจะถูกเปิดไฟล์แนบ ส่วน script รันผ่าน bash และมีแค่ output ที่เข้า context ไม่ใช่ตัวโค้ด

เหมือนห้องสมุด: ระดับ 1 คือบัตรรายการหนังสือที่วางไว้ให้ดูตลอด ระดับ 2 คือหยิบเล่มที่ตรงเรื่องมาเปิดอ่าน ระดับ 3 คือภาคผนวกที่เปิดเฉพาะหน้าที่ต้องใช้

แนวทางเขียน

  • มอง SKILL.md เป็น สารบัญ body ไม่เกิน 500 บรรทัด ย้ายรายละเอียดไปไฟล์ลิงก์ เช่น FORMS.md, REFERENCE.md, examples.md
  • reference หลายโดเมน ให้แยกไฟล์ตามโดเมน
  • reference ทุกไฟล์ต้องลิงก์จาก SKILL.md ลึกแค่ชั้นเดียว ถ้าซ้อนหลายชั้น Claude อาจอ่านแค่บางส่วน (เช่นอ่านแค่ head -100) แล้วพลาดข้อมูล
  • ไฟล์ reference ที่ยาวเกิน 100 บรรทัด ให้มีสารบัญไว้ด้านบน
  • script ถูกกว่าและให้ผลสม่ำเสมอกว่าการให้ Claude เขียนโค้ดเทียบเท่าขึ้นใหม่ เพราะมีแค่ output ที่เข้า context
สรุปสั้นๆ

Metadata (~100 token) อยู่เสมอ → body (<5k) โหลดเมื่อ trigger → ไฟล์ประกอบโหลดเมื่อใช้ SKILL.md ≤500 บรรทัด, reference ลึกชั้นเดียว, ไฟล์ยาวเกิน 100 บรรทัดมีสารบัญ

Checkpoint 9 (เรียงลำดับ)

ผู้ใช้ติดตั้ง Skill reconciling-invoices ที่มี MATCHING_RULES.md และ TAX_CODES.md แล้วขอให้ "กระทบยอดใบแจ้งหนี้เดือนนี้กับ statement" (ไม่เกี่ยวกับภาษี) เรียงสิ่งที่เกิดขึ้น:

  1. คำขอตรงกับ description จึงโหลด body ของ SKILL.md
  2. ตอนเริ่มเซสชัน name และ description อยู่ใน context แล้ว
  3. Claude ทำงานเสร็จด้วยคำสั่งที่โหลดมา
  4. Claude เปิด MATCHING_RULES.md เพราะต้องใช้ ส่วน TAX_CODES.md ไม่ถูกเปิดเลย
ดูเฉลย

2 → 1 → 4 → 3 metadata มาก่อนเสมอ body โหลดเมื่อ trigger ไฟล์ประกอบโหลดเฉพาะที่ต้องใช้ ไฟล์ที่ไม่เกี่ยวไม่กิน token เลย
