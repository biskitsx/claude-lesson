6.4 Architecture documentation สำหรับ Claude solutions

ต้นฉบับ: CertSafari 6.4

อ่านจบแล้วควรทำได้
  • บอกได้ว่าเอกสาร architecture ต้องระบุ 5 อย่าง: components, data flows, models, tools และ boundaries
  • แนะนำได้ว่า agent loop ควรรันที่ไหน (Agent SDK ใน process ของเรา หรือ Managed Agents) และ tool ควรต่อเข้ามาทางไหน
  • บันทึกเหตุผลของแต่ละ layer ไว้ เพื่อไม่ให้ทีมรุ่นหลังลบของที่จำเป็นทิ้ง หรือสร้างของซ้ำ
  • ระบุสิ่งที่ต้องเปลี่ยนเพื่อยก prototype ขึ้นเป็น service จริง: การ serve, configuration, error handling และการ deploy
แนวคิดหลัก: เอกสารที่ดีบอกทั้ง "อะไร" และ "ทำไม"

เอกสาร architecture ต้องบอกวิศวกรว่า ชิ้นส่วนหลักมีอะไรบ้าง คุยกันยังไง แต่ละชิ้นใช้โมเดลและ tool อะไร และเส้นแบ่งอยู่ตรงไหน และที่ขาดไม่ได้คือ เหตุผลที่แต่ละชิ้นมีอยู่ ถ้าไม่มีส่วนนี้ ทีมถัดไปจะเดาเอง

1. เอกสารต้องตอกหมุดอะไรบ้าง

ใช้ตัวอย่างเดียวตลอดบท: customer support agent ที่มี intent classifier คอยดูว่าคำถามลูกค้าเป็นเรื่องอะไร แล้วส่งต่อไปยัง "บทสนทนาเฉพาะทาง" (specialized conversation) ที่แต่ละตัวมี tool และ system prompt ของตัวเอง

เอกสารต้องตอบให้ครบ 5 เรื่อง:

องค์ประกอบคำถามที่ต้องตอบในตัวอย่าง support agent
Componentsมีชิ้นส่วนอะไรบ้างintent classifier, บทสนทนาเฉพาะทาง, API wrapper, web interface
Data flowsข้อมูลไหลจากไหนไปไหนคำถามลูกค้า → classifier → บทสนทนาเฉพาะทาง → คำตอบ stream กลับผ่าน Server-Sent Events
Modelsใช้โมเดลอะไร หนึ่ง request เรียก Claude กี่ครั้งclassifier เพิ่มการเรียก Claude อีก 1 ครั้งก่อนบทสนทนาเริ่ม
Toolsแต่ละชิ้นใช้ tool อะไรบทสนทนาเฉพาะทางแต่ละตัวมี tool และ system prompt ของตัวเอง
Boundariesส่วนไหนเราดูแล ส่วนไหนเป็นของภายนอกHTTP service ที่ทีมรันเอง กับ Claude API ที่ service ไปเรียก

ข้อ Models มักถูกลืม ทั้งที่สำคัญมาก ถ้าเอกสารไม่บอกว่าหนึ่ง request เรียก Claude 2 ครั้ง คนที่มาประเมิน latency หรือค่าใช้จ่ายทีหลังจะคำนวณผิดทันที

สรุปสั้นๆ

Components, data flows, models (รวมจำนวน call ต่อ request), tools และ boundaries ต้องอยู่ในเอกสารครบทุกตัว

Checkpoint 1 (จับคู่)

ทีมทำระบบตอบคำถามพนักงานเรื่อง HR: มี router แยกคำถามเป็น "วันลา" กับ "สวัสดิการ" แต่ละสายมี prompt และ tool ของตัวเอง จับคู่ประโยคในเอกสารกับองค์ประกอบ:

  1. "router, ผู้ช่วยวันลา, ผู้ช่วยสวัสดิการ, หน้าเว็บ Slack bot"
  2. "คำถาม → router → ผู้ช่วยที่ตรงเรื่อง → คำตอบ stream กลับไปที่ Slack"
  3. "router เรียก Claude 1 ครั้ง แล้วผู้ช่วยเรียกอีกอย่างน้อย 1 ครั้ง"
  4. "ผู้ช่วยวันลาใช้ tool ดึงยอดวันลาคงเหลือได้อย่างเดียว"
  5. "service ของเรารันบน k8s ของบริษัท ส่วน Claude API กับระบบ HRIS เป็นของภายนอก"

2. Agent loop รันอยู่ที่ไหน

Agent SDK กับ Managed Agents ใช้แนวคิดเดียวกัน (agent, tool, session) แต่ รันคนละที่:

  • Agent SDK รันใน process ที่เราดูแลเอง
  • Managed Agents รันบน infrastructure ของ Anthropic

เอกสารต้องระบุให้ชัดว่าใช้ตัวไหน เพราะมันกำหนดว่า ใครถือ filesystem ใครเป็นคนรัน tool และอะไรต้องข้าม network

เรื่องAgent SDKManaged Agents
รันที่ไหนprocess ที่เราดูแลinfrastructure ของ Anthropic
ตั้งค่า agentสร้าง ClaudeAgentOptions(...) ใหม่ทุกครั้งที่รันเรียก client.beta.agents.create(...) ครั้งเดียว เก็บไว้และมี version ฝั่ง server
Custom toolsฟังก์ชันที่ประกาศด้วย @tool SDK dispatch ให้อัตโนมัติประกาศไว้บน Agent แล้ว client ของเราต้องตอบ event agent.custom_tool_use เอง
Built-in toolsรันใน process ของเรา กับ filesystem ของเรารันใน sandbox ที่ Anthropic ดูแล
ลองเดาก่อน

ถ้า agent ที่สร้างด้วย Agent SDK ใช้ built-in tool อ่านไฟล์ การอ่านเกิดที่ไหน? คำตอบ: ใน process ของเรา กับ filesystem ของเรา ไม่ใช่ใน sandbox ของ Anthropic และไม่ใช่ผ่าน MCP server ระยะไกล

ตัวอย่างการตัดสินใจ: ทีมต้องการให้ทุกอย่างอยู่บนเครื่องของบริษัท ทำงานกับ git checkout บนดิสก์ และมี custom tool ที่รันใน process เดียวกัน คำตอบคือ ฝัง Agent SDK เป็น library ใน service ของตัวเอง เหตุผลแต่ละทาง:

  • Managed Agents ไม่เข้า เพราะ sandbox อยู่ฝั่ง Anthropic และ custom tool จะกลายเป็น event ที่ client ต้องตอบเอง
  • เขียน tool loop เองด้วย Messages API ก็ได้ แต่เท่ากับสร้างกลไก dispatch ที่ SDK มีให้แล้วขึ้นมาใหม่
  • MCP connector อย่างเดียวไม่ได้ให้ agent loop ไม่ได้ให้เข้าถึง filesystem และไม่มี custom tool แบบ in-process
from claude_agent_sdk import tool, ClaudeAgentOptions

@tool("lookup_order", "ดึงสถานะคำสั่งซื้อจาก DB ภายใน", {"order_id": str})
async def lookup_order(args):
    ...  # รันใน process ของเรา SDK เรียกให้อัตโนมัติ

options = ClaudeAgentOptions(...)  # สร้างใหม่ทุกครั้งที่รัน
เข้าใจผิดบ่อย

"service ของเราเป็นคนสั่ง Managed Agents ดังนั้นมันก็รันบน infrastructure ของเรา" ไม่ใช่ ทั้ง agent loop และ sandbox ของ Managed Agents อยู่บน infrastructure ของ Anthropic มีแค่ Agent SDK ที่รัน loop และ tool ใน process ที่เราดูแล

สรุปสั้นๆ

Agent SDK = loop และ tool อยู่ใน process เรา, custom tool ใช้ @tool / Managed Agents = loop และ sandbox อยู่ที่ Anthropic, custom tool มาเป็น event agent.custom_tool_use เขียนให้ชัดในเอกสารว่าใช้ตัวไหน

Checkpoint 2

ทีม compliance ของธนาคารต้องการ agent ที่อ่าน log จากดิสก์ของเซิร์ฟเวอร์ภายใน เรียกฟังก์ชัน Python ภายในเพื่อ mask ข้อมูล และห้ามให้ไฟล์ออกนอกเครือข่าย ทีมไม่อยากเขียน tool loop เอง ควรเลือกอะไร?

  1. Client SDK (Messages API) แล้วเขียน loop จัดการ tool_use เอง
  2. ฝัง Agent SDK เป็น library ใน service ภายใน แล้วประกาศฟังก์ชัน mask เป็น @tool
  3. Managed Agents แล้วอัปโหลด log เข้า sandbox
  4. ใช้ MCP connector ของ Messages API อย่างเดียว
ดูเฉลย

B A ต้องเขียน loop เอง ซึ่งทีมไม่อยากทำ C ทำให้ไฟล์ไปอยู่ใน sandbox ของ Anthropic และ D ไม่มี agent loop ไม่มี filesystem และไม่มี custom tool แบบ in-process

3. บันทึกว่า tool ต่อเข้ามายังไง

ใน Claude Code การต่อ agent เข้ากับ issue tracker, ระบบ monitoring หรือ database ทำผ่าน MCP server และเอกสารควรใส่ คำสั่งลงทะเบียนแบบเป๊ะๆ ไว้ ไม่ใช่แค่เขียนว่า "ต่อ Jira ไว้"

Transport บอกว่าใครเป็นคนรัน server

  • Hosted server คือ URL ที่มีคนรันไว้แล้ว เพิ่มด้วย --transport http
  • Local server คือโปรแกรมที่ agent สั่งรันบนเครื่องตัวเอง ไม่ต้องใส่ transport flag เพราะ local server ใช้ stdio เป็นค่าเริ่มต้น

ตัวอย่างลงทะเบียน local stdio server (ทุกอย่างหลัง -- คือคำสั่งที่ Claude Code จะรัน):

claude mcp add playwright -- npx -y @playwright/mcp@latest

ส่วน hosted server ก็ใส่ transport กับ URL แทน เช่น claude mcp add --transport http tracker https://mcp.example.com/mcp

ถ้ามี connector โอเพนซอร์สของ Confluence หรือ Jira อยู่แล้ว ที่ agent สั่งรันบนเครื่องได้ ให้บันทึกเป็น stdio MCP server ไปเลย การเขียน API call เดิมใหม่เป็น custom tool เท่ากับทิ้ง connector ที่ใช้งานได้อยู่แล้ว

Scope ของ MCP server

Scopeใครได้ใช้เก็บที่ไหน
localคนเดียว ในโปรเจกต์เดียวconfig ส่วนตัว
userคนเดียว ทุกโปรเจกต์config ส่วนตัว
projectทุกคนที่ clone repo.mcp.json ที่ root ของโปรเจกต์

คำแนะนำสำหรับทั้งทีมมักต้องใช้ scope project เพราะทุกคนที่ clone ได้ config ชุดเดียวกัน

สรุปสั้นๆ

Hosted = --transport http + URL, local = stdio ไม่ต้องใส่ flag ใส่คำสั่ง claude mcp add เป๊ะๆ ในเอกสาร เลือก scope ให้ถูก (ทีม = project / .mcp.json) และใช้ connector ที่มีอยู่แทนการเขียนใหม่

Checkpoint 3

บริษัทมี MCP connector สำหรับระบบ ticket ภายในที่ทีม platform ดูแลอยู่แล้ว และอยากให้ coding agent ของทุกทีมใช้ได้ เอกสารควรแนะนำอะไร?

  1. เขียน tool loop ใหม่ด้วย Messages API ที่เรียก REST ของระบบ ticket ตรงๆ
  2. ลงทะเบียน connector เดิมเป็น MCP server และใส่คำสั่งลงทะเบียนที่ใช้ได้จริงไว้ในเอกสาร
  3. ประกาศเป็น custom tool บน Managed Agent
  4. เขียน API call ของ connector ใหม่เป็นฟังก์ชัน @tool ใน Agent SDK
ดูเฉลย

B A และ D สร้างของที่มีอยู่แล้วขึ้นใหม่และทิ้ง connector ที่ใช้ได้ ส่วน C เป็นกลไกผิดที่ ไม่ใช่วิธีต่อ connector เข้ากับ coding agent

Checkpoint 4

ทีมต้องการให้ agent อ่านหน้า wiki ภายในผ่าน connector โอเพนซอร์ส แต่บริษัทไม่อนุญาตให้เปิด network endpoint ใหม่ ควรทำแบบไหน?

  1. ติดตั้ง connector เป็น MCP server ที่ agent สั่งรันบนเครื่องเองผ่าน stdio
  2. เขียน integration ใหม่ใน prompt ให้โมเดลเรียก REST ตรงๆ โดยไม่ผ่าน MCP
  3. เปิด extended thinking ให้โมเดลวางแผนการเรียก wiki
  4. อัปโหลดหน้า wiki ทั้งหมดผ่าน Files API
ดูเฉลย

A stdio ไม่ต้องเปิด endpoint ทาง network เลย B ทำซ้ำของเดิมและข้าม MCP server C เป็นเรื่องการคิด ไม่ใช่การเรียกระบบภายนอก และ D ใช้กับเอกสารที่อัปโหลด ไม่ได้ให้เข้าถึงข้อมูลสด

4. บันทึกการเลือกโมเดล

ทุกจุดที่เรียกโมเดลต้องเขียนว่า ใช้โมเดลอะไร และเพราะอะไร เพื่อให้ตรวจสอบใหม่ได้เมื่อมีโมเดลใหม่ออกมา

ตัวอย่าง: งานคัดแยก ticket ปริมาณสูง ที่มีงบ latency และค่าใช้จ่ายตึง แต่ยังต้องใช้ reasoning จริง คำแนะนำในบทคือ Claude Haiku 4.5 เพราะเป็น class ที่ถูกและเร็วที่สุด ออกแบบมาสำหรับงาน real-time ปริมาณมากที่อ่อนไหวเรื่องต้นทุนแต่ยังต้องคิดเป็น ส่วน Opus ถูกวางไว้สำหรับงาน enterprise ที่ต้อง reasoning หนัก ซึ่งเกินความจำเป็นของการจัดประเภท ticket ทีละใบ

บันทึกในเอกสารอาจหน้าตาแบบนี้:

call: intent_classifier
model: claude-haiku-4-5
why: เรียกทุกคำถาม (ปริมาณสูง), งบ latency ตึง, ต้องการ reasoning พอแยก intent
recheck: เมื่อมีโมเดลเล็กรุ่นใหม่ หรือ eval การแยก intent ตกต่ำกว่าเป้า
ในข้อสอบ

effort ไม่ใช่ตัวช่วยประหยัดเงินหรือเวลา มันแลกระหว่างความละเอียดถี่ถ้วนกับประสิทธิภาพ การเพิ่ม effort ทำให้ละเอียดขึ้น (และใช้เวลามากขึ้น) ถ้าเป้าคือต้นทุนและ latency ให้เลือก model class ที่เล็กกว่า ส่วน fast mode เป็น research preview ที่คิดราคา premium ไม่ใช่ฟีเจอร์ GA ที่ช่วยลดต้นทุน

เข้าใจผิดบ่อย

"เพิ่ม effort เพื่อลด latency และค่าใช้จ่าย" ผิดทิศ effort ที่สูงขึ้นซื้อความละเอียด ไม่ใช่ความเร็ว

"ใช้ Opus แล้วลด effort ลงก็ได้ผลเหมือนโมเดลเล็ก" ยังเป็น class สำหรับ reasoning หนักอยู่ดี เกินความจำเป็นของงานจัดประเภท

สรุปสั้นๆ

เขียนโมเดล + เหตุผล ของทุก call งานปริมาณสูง งบตึง แต่ต้องคิด → Haiku 4.5 ไม่ใช่ปรับ effort หรือเปิด fast mode

Checkpoint 5

ใน support agent ตัวอย่าง classifier เพิ่มการเรียก Claude 1 ครั้งต่อทุกคำถาม และงบ latency ของทั้ง request ตึงมาก classifier ควรใช้อะไร?

  1. Opus รุ่นล่าสุด เพื่อให้แยก intent แม่นที่สุด
  2. Claude Haiku 4.5
  3. โมเดลเดียวกับบทสนทนาหลัก แต่เพิ่ม effort
  4. Opus แล้วลด effort ให้ต่ำสุด
ดูเฉลย

B A ให้ความสามารถเกินงาน C เพิ่ม effort ไม่ได้ลดเวลา และ D ยังเป็น class reasoning หนักที่เกินกว่างานจัดประเภทต้องการ

Checkpoint 6

ระบบจัดหมวดอีเมลเข้าวันละหลายแสนฉบับ ต้องตอบใน 1 วินาทีและคุมต้นทุนต่อฉบับให้ต่ำ ข้อใดเหมาะที่สุด?

  1. Claude Haiku 4.5
  2. Opus 4.8 เพราะเป็นรุ่นสำหรับงาน enterprise
  3. Sonnet 5 ที่ effort ระดับ xhigh
  4. Opus 4.8 เปิด fast mode
ดูเฉลย

A Opus 4.8 วางไว้สำหรับงาน agentic coding และวิศวกรรมระดับ enterprise effort xhigh ยิ่งทำให้ตอบช้า และ fast mode เป็น research preview ราคา premium ไม่ได้ลดต้นทุน

5. บันทึกว่าทำไมแต่ละ layer ถึงมีอยู่

ทุก layer ต้องมีเหตุผลกำกับ พร้อมบอกว่าลองทางที่ถูกกว่าอะไรมาก่อนแล้ว ถ้าไม่มีบันทึกนี้ จะเกิดสองแบบ: ทีมใหม่ลบ layer ที่จำเป็นทิ้งเพราะคิดว่าเกิน หรือสร้าง layer ซ้ำเพราะไม่รู้ว่ามีอยู่แล้ว

ลำดับที่แนะนำก่อนจะเพิ่ม layer ใหม่:

  1. รีดประสิทธิภาพจาก prompt ให้สุดก่อน (prompt engineering)
  2. เพิ่ม tool หรือทำ prompt chain
  3. ถ้ายังไม่พอ ค่อยเพิ่ม intent classifier แยกออกมา

Classifier คุ้มค่าเมื่อ bot ต้องรับงานที่หลากหลายมาก แต่มันเพิ่ม Claude call อีก 1 ครั้ง ซึ่งเพิ่ม latency ได้

บันทึกของแต่ละ layer ควรมี 4 ส่วน:

หัวข้อตัวอย่างสำหรับ intent classifier
ปัญหาที่แก้คำถามหลากหลายเกินกว่า prompt และชุด tool เดียวจะรับไหว
ทางเลือกที่ลองก่อน และทำไมไม่พอปรับ prompt แล้ว และเพิ่ม tool/chain แล้ว แต่ยังเลือก tool ผิดในบางหมวด
ต้นทุนที่เพิ่มClaude call เพิ่ม 1 ครั้งต่อคำถาม latency สูงขึ้น
เงื่อนไขที่ถอดออกได้เมื่อบทสนทนาเดียวรับคำถามได้ครบทุกแบบอีกครั้ง
สรุปสั้นๆ

prompt → tool/chain → classifier ทุก layer บันทึก: แก้อะไร, ลองอะไรมาก่อน, เพิ่มต้นทุนเท่าไหร่, ถอดออกได้เมื่อไหร่

Checkpoint 7 (เรียงลำดับ)

ผู้ช่วยตอบคำถามร้านค้าออนไลน์เริ่มตอบผิดหมวดเมื่อคำถามหลากหลายขึ้น เรียงสิ่งที่ควรลองจากก่อนไปหลัง:

  1. แยก intent classifier ออกมาเป็นอีก call
  2. ปรับ prompt ให้ชัดขึ้น ใส่ตัวอย่าง
  3. เพิ่ม tool หรือแตกงานเป็น prompt chain
ดูเฉลย

b → c → a classifier มาท้ายสุด เพราะเพิ่มทั้ง call และ latency

6. จาก prototype สู่ service ที่ deploy ได้

Prototype ของ support agent ตัวอย่างเป็นฟังก์ชัน Python ที่รันใน Streamlit ซึ่งใช้ demo ได้ แต่แชตบอต real-time ต้องเป็น API service เอกสารต้องบอกการเปลี่ยนแปลง 4 ด้าน:

Serving

  • ห่อฟังก์ชันหลักด้วย web framework อย่าง Flask หรือ FastAPI
  • Stream คำตอบด้วย Server-Sent Events
  • Cache คำตอบเพื่อลด API call ที่ไม่จำเป็น
  • เก็บ context ของบทสนทนา ไว้ ให้ผู้ใช้ออกไปแล้วกลับมาคุยต่อได้

Configuration

  • เขียนทุกขั้นตอนที่ checkout ใหม่ต้องทำ เช่น copy .env.example เป็น .env ถ้าข้ามขั้นนี้ test และ dev server จะพัง
  • HTTPS_PROXY ใช้ส่ง traffic ผ่าน proxy ขององค์กร (เรื่อง network/security)
  • กลุ่มตัวแปร ANTHROPIC_BASE_URL ใช้ชี้ไปที่ LLM gateway เพื่อติดตามการใช้งานแบบรวมศูนย์ ตั้ง rate limit ตั้งงบ หรือจัดการ authentication

Error handling

  • ทุก response ของ Messages API บอกเหตุผลที่หยุด generate ใน field stop_reason
  • Tool loop ต้องเช็กค่านี้ end_turn คือจบปกติ ส่วน refusal เป็นอีกค่าที่ service ต้องจัดการแยกให้ชัด
  • แยก configuration error ออกจาก transient failure เช่น บน Claude Haiku 4.5 ถ้าตั้งทั้ง temperature และ top_p จะได้ 400 กลับมา retry เท่าไหร่ก็ไม่หาย ต้องแก้ config
resp = client.messages.create(...)
if resp.stop_reason == "end_turn":
    return render(resp)
elif resp.stop_reason == "refusal":
    return handoff_to_human(resp)   # อย่าให้ตกไปเป็น error ทั่วไป

Deployment

ทดสอบใน development environment ก่อนขึ้น production เสมอ

เข้าใจผิดบ่อย

"อยากคุมงบรวมทุกทีม ตั้ง HTTPS_PROXY ก็พอ" ไม่ใช่ proxy เป็นเรื่อง network ส่วนการติดตามการใช้งาน limit และงบแบบรวมศูนย์ต้องชี้ ANTHROPIC_BASE_URL ไปที่ LLM gateway

สรุปสั้นๆ

Serving (Flask/FastAPI, SSE, cache, เก็บ context), Config (.env, HTTPS_PROXY, ANTHROPIC_BASE_URL → gateway), Error (stop_reason, refusal, แยก 400 จาก config ออกจาก error ชั่วคราว), Deploy (dev ก่อน prod)

Checkpoint 8

CFO อยากเห็นยอดการใช้ Claude ของทุกทีมในที่เดียว ตั้ง rate limit ต่อทีม และตั้งงบรายเดือนได้ สถาปนิกควรแนะนำอะไร?

  1. ตั้ง HTTPS_PROXY ไปที่ proxy ขององค์กร
  2. ลด effort ของทุก call
  3. ชี้กลุ่มตัวแปร ANTHROPIC_BASE_URL ไปที่ LLM gateway
  4. เปิด caching คำตอบทุก service
ดูเฉลย

C proxy เป็นเรื่องความปลอดภัยของ network การลด effort มีผลแค่ราย call และ caching ลดจำนวน call ได้แต่ไม่ได้ให้การติดตามหรือ limit แบบรวมศูนย์
