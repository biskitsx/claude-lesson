4.6 OpenTelemetry สำหรับ Claude Code และ Agent SDK: signals, traces และ content gates

ต้นฉบับ: CertSafari 4.6

อ่านจบแล้วควรทำได้
  • บอกได้ว่า metrics, log events และ traces ตอบคำถามคนละแบบ และแต่ละตัวต้องมี exporter ของตัวเอง
  • ตั้งค่า OTLP ให้ข้อมูลออกจาก process จริงๆ (exporter + protocol + endpoint + headers) ทั้งใน Claude Code และ Agent SDK
  • คุม cardinality ของ metrics ด้วยตัวแปร OTEL_METRICS_INCLUDE_* แทนการไปยืด export interval
  • อ่าน trace ของ agent ที่มี subagent ได้ ว่าเวลาหายไปที่ model, tool หรือคนที่กดอนุมัติ
  • รู้ว่า content gate ตัวไหนเปิดเผยข้อมูลอะไร และ gate ไหน "ลากตัวอื่นมาด้วย" โดยไม่ตั้งใจ
แนวคิดหลัก: เปิด telemetry ≠ ส่งข้อมูลออก

Claude Code และ Agent SDK ปล่อย OpenTelemetry ได้ 3 signal คือ metrics, log events และ traces ทั้งหมดเป็นแบบ opt-in และ แต่ละ signal มี exporter แยกกัน signal ไหนไม่ได้เลือก exporter ข้อมูลก็วนอยู่ใน process ไม่ไปไหน ต่อให้เปิดสวิตช์ telemetry หลักไว้แล้วก็ตาม

1. Metrics, log events และ traces ตอบคำถามคนละข้อ

ลองนึกถึงร้านอาหาร: metrics คือยอดขายรายวันกับต้นทุนวัตถุดิบ, log events คือใบสั่งอาหารแต่ละใบว่าใครสั่งอะไร, traces คือการจับเวลาว่าจานนี้รอที่ครัวกี่นาที รอเสิร์ฟกี่นาที สามอย่างนี้แทนกันไม่ได้

  • Metrics เป็น counter ที่นับ token, ค่าใช้จ่าย (cost), จำนวน session, จำนวนบรรทัดโค้ด และการตัดสินใจเรื่อง tool (ยอมรับ/ปฏิเสธ) ใช้ตอบว่า ใช้ไปเท่าไหร่ เสียเงินเท่าไหร่
  • Log events เป็น record แบบมีโครงสร้าง หนึ่งรายการต่อหนึ่งเหตุการณ์ เช่น prompt หนึ่งครั้ง, API request หนึ่งครั้ง, API error หนึ่งครั้ง หรือผลของ tool หนึ่งครั้ง (มี event อย่าง user_prompt และ assistant_response) ใช้ตอบว่า เกิดอะไรขึ้นบ้าง
  • Traces (beta) เป็น span ที่มีเวลาเริ่ม/จบ ครอบ interaction, การเรียก model, การเรียก tool และ hook ใช้ตอบว่า เวลาไปหมดที่ไหน
Signalตัวแปรเลือก exporterค่าที่ใส่ได้backend ที่เหมาะ
MetricsOTEL_METRICS_EXPORTERotlp, prometheus, console, nonetime-series DB, หรือ columnar store ถ้าต้องนับ unique user
Log eventsOTEL_LOGS_EXPORTERotlp, console, noneระบบรวม log ที่ค้น full-text ได้ หรือ columnar store
Traces (beta)OTEL_TRACES_EXPORTER + CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1ตาม exporter ที่เลือกระบบ distributed tracing

ตั้งค่าให้ข้อมูลออกไปจริง

  • CLAUDE_CODE_ENABLE_TELEMETRY=1 แค่ เปิดการเก็บ ไม่ได้เลือกว่าจะส่งไปทางไหน
  • ถ้าเลือก otlp ต้องบอก protocol ด้วย OTEL_EXPORTER_OTLP_PROTOCOL (เช่น grpc) และ ปลายทาง ด้วย OTEL_EXPORTER_OTLP_ENDPOINT Claude Code ไม่มี protocol ค่า default ให้
  • OTEL_EXPORTER_OTLP_HEADERS ใช้ใส่ credential ของ collector ของเรา (เช่น bearer token) ไม่ใช่ Anthropic API key
  • flag beta มีผลกับ traces อย่างเดียว ส่วน exporter แบบ console มีไว้ debug ดูบนจอ ไม่ใช่ของที่ต้องมีก่อน
  • รอบการ flush ค่า default: metrics ทุก 60 วินาที (OTEL_METRIC_EXPORT_INTERVAL หน่วยเป็น ms คือ 60000) และ logs ทุก 5 วินาที

ตัวอย่าง env block ในไฟล์ settings ที่ทำให้ metrics กับ logs ออกไปที่ collector ภายในบริษัท:

{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "grpc",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://otel.internal.example:4317",
    "OTEL_EXPORTER_OTLP_HEADERS": "Authorization=Bearer <collector-token>"
  }
}

Agent SDK: ระวังเรื่อง env

ใน production ให้ตั้งตัวแปรพวกนี้ไว้ที่ environment ของ process เลย ถ้าจะส่งผ่าน ClaudeAgentOptions.env ทีละ call ต้องรู้ว่าสอง SDK ทำงานไม่เหมือนกัน:

  • Python เอา env ที่ส่งมา merge ทับ environment ที่สืบทอดมา ตัวแปรอื่นยังอยู่ครบ
  • TypeScript เอา env ไป แทนที่ทั้งก้อน ถ้าลืม spread process.env เข้าไป ตัวแปรอื่น (PATH, key ต่างๆ) จะหายหมด
// TypeScript: ต้อง spread ของเดิมเข้าไปเอง
const options = {
  env: {
    ...process.env,
    CLAUDE_CODE_ENABLE_TELEMETRY: "1",
    OTEL_TRACES_EXPORTER: "otlp",
    CLAUDE_CODE_ENHANCED_TELEMETRY_BETA: "1",
  },
};
เข้าใจผิดบ่อย

"ตั้ง CLAUDE_CODE_ENABLE_TELEMETRY=1 แล้วข้อมูลจะไหลเข้า dashboard เอง" ไม่ใช่ ต้องเลือก exporter ให้ทีละ signal และถ้าเป็น otlp ต้องมีทั้ง protocol และ endpoint ด้วย

"ต้องใส่ Anthropic API key ใน OTLP headers" ไม่ใช่ headers เป็น credential ของ collector ปลายทาง

สรุปสั้นๆ

Metrics = เท่าไหร่, logs = เกิดอะไร, traces = เวลาไปไหน สวิตช์หลักแค่เปิดการเก็บ แต่ละ signal ต้องมี exporter ของตัวเอง และ otlp ต้องมี protocol + endpoint เสมอ

ดูเฉลย

2. คุมว่า metrics พก attribute อะไรไปบ้าง

ต้นทุนของ metrics backend ขึ้นกับ cardinality คือจำนวนชุดค่า attribute ที่ไม่ซ้ำกัน ทุกชุดค่าใหม่กลายเป็น time series ใหม่หนึ่งเส้น ปัญหาคือ session.id เปิดอยู่เป็นค่า default ถ้ามี CI job สั้นๆ วันละหลายพันรอบ ทุกรอบก็เป็น session ใหม่ = series ใหม่ งอกขึ้นเป็นพันเส้นต่อวัน

เหมือนการแยกถังขยะ ถ้าแยกถังตามประเภทขยะก็มีไม่กี่ถัง แต่ถ้าแยกถังตามบ้านเลขที่ทุกหลัง จำนวนถังจะระเบิด การ "เก็บขยะห่างขึ้น" (ยืด interval) ไม่ได้ทำให้จำนวนถังลดลงเลย

ตัวแปรเพิ่ม attribute อะไรค่า default
OTEL_METRICS_INCLUDE_SESSION_IDsession.id (และ ccr.session.id สำหรับ cloud session)true
OTEL_METRICS_INCLUDE_ACCOUNT_UUIDuser.account_uuid, user.account_idtrue
OTEL_METRICS_INCLUDE_RESOURCE_ATTRIBUTESkey ต่างๆ ที่ตั้งไว้ใน OTEL_RESOURCE_ATTRIBUTEStrue
OTEL_METRICS_INCLUDE_VERSIONapp.versionfalse
OTEL_METRICS_INCLUDE_ENTRYPOINTapp.entrypointfalse
  • อยากแยกดูตาม service หรือลูกค้า ให้ใช้ OTEL_SERVICE_NAME และ OTEL_RESOURCE_ATTRIBUTES เช่น deployment.environment=prod,tenant.id=acme ค่าพวกนี้มีจำนวนจำกัด จึงไม่ทำให้ series ระเบิด
  • แต่ถ้าเอา ID รายผู้ใช้ไปใส่เป็น attribute ก็เจอปัญหา cardinality แบบเดียวกับ session ID
  • metrics ใช้ delta temporality เป็นค่า default (ส่งเฉพาะส่วนที่เพิ่มในแต่ละรอบ) ถ้า backend ต้องการค่าสะสม ให้ตั้ง OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=cumulative ซึ่งเป็นเรื่องรูปแบบตัวเลข ไม่เกี่ยวกับจำนวน series
เข้าใจผิดบ่อย

"series เยอะเกินไป ยืด export interval จาก 60 วินาทีเป็น 5 นาทีก็หาย" ไม่ใช่ interval แค่ลดความถี่การ flush จำนวน series มาจาก attribute ต้องปิด OTEL_METRICS_INCLUDE_SESSION_ID

"ปิด resource attributes ไปเลยจะได้ลด series" ได้ผลแต่เสียของที่ต้องการ เช่น breakdown ตาม deployment.environment ตัวต้นเหตุจริงคือ session ID

สรุปสั้นๆ

series = ชุดค่า attribute ที่ไม่ซ้ำ ต้นเหตุคลาสสิกคือ session.id ที่เปิดเป็น default ปิดตัวนั้น แล้วแยกมิติที่มีค่าจำกัดผ่าน OTEL_RESOURCE_ATTRIBUTES

3. อ่าน trace: span ตลอดหนึ่งรอบ รวมถึง subagent

โครงสร้าง span ของ Claude Code เรียงเป็นต้นไม้แบบนี้:

claude_code.interaction            ← root: ตั้งแต่ prompt ถึงคำตอบ
├─ claude_code.llm_request         ← การเรียก Claude API แต่ละครั้ง
├─ claude_code.tool                ← การเรียก tool แต่ละครั้ง
│  ├─ claude_code.tool.blocked_on_user   ← รอคนกดอนุมัติ permission
│  └─ claude_code.tool.execution         ← เวลาที่ tool ทำงานจริง
└─ claude_code.tool (Agent)        ← subagent
   └─ claude_code.llm_request (agent_id=..., parent_agent_id=...)

span claude_code.llm_request มี attribute สำคัญ:

Attributeใช้ดูอะไร
duration_ms, ttft_msเวลาทั้งหมด และเวลาจนได้ token แรก (time to first token)
attempt, error_classครั้งที่เท่าไหร่ของการ retry และประเภท error
input_tokens, output_tokenstoken เข้า/ออก
cache_read_tokens, cache_creation_tokenstoken ที่อ่านจาก/เขียนลง prompt cache
agent_id, parent_agent_idเป็นของ subagent ตัวไหน และใครเป็นแม่
query_source_safeแหล่งที่มาของ query
stop_reasonเหตุผลที่ model หยุด
  • span ของ subagent จะ ซ้อนอยู่ใต้ span ของ Agent tool ที่สร้างมันขึ้นมา ส่วน session หลักจะ ไม่มี agent_id
  • span claude_code.hook จะโผล่มาเฉพาะโหมด detailed beta tracing (ENABLE_BETA_TRACING_DETAILED=1 + BETA_TRACING_ENDPOINT) และในโหมดนี้ logs กับ traces จะถูกส่งไปที่ BETA_TRACING_ENDPOINT แทน exporter ที่ตั้งไว้
สูตรอ่าน trace ที่ใช้บ่อย
  • หา subagent ที่แพงที่สุด: รวม token แยกตาม agent_id
  • ขนาด input จริงทั้งหมด: input_tokens + cache_read_tokens (ส่วนที่อ่านจาก cache ไม่ได้รวมอยู่ใน input_tokens)
  • attempt สูงพร้อม duration_ms ยาว: กำลังโดน retry
  • stop_reason = max_tokens: output ถูกตัดกลางทาง
  • tool.blocked_on_user ยาว แต่ tool.execution สั้น: tool ไม่ได้ช้า คนกดอนุมัติช้า
สรุปสั้นๆ

interaction → llm_request / tool → (blocked_on_user, execution) subagent ซ้อนใต้ Agent tool และระบุตัวด้วย agent_id อยากเห็น hook ต้องใช้ detailed beta tracing

4. Content gates: ค่า default คือปิดเนื้อหา

โดย default telemetry เก็บแค่ ความยาว ไม่เก็บ เนื้อหา prompt และ response ถูกย่อเหลือแค่จำนวนตัวอักษร และ event user_prompt จะแสดงเป็น <REDACTED> ข้อมูลไปแค่ endpoint ที่เราตั้งเอง แต่ต้องคิดให้ดีว่าถ้าเปิด gate แล้ว collector ของเราจะกลายเป็นที่เก็บ source code และ secret ของทั้งบริษัท

ข้อยกเว้นหนึ่งที่ต้องจำ: ถ้า login ด้วย OAuth ค่า user.email จะติดไปด้วย โดยไม่มี gate คุม

ตัวแปรเปิดเผยอะไร
OTEL_LOG_USER_PROMPTS=1ข้อความ prompt ใน event user_prompt (field prompt และ prompt_text) และบน interaction span
OTEL_LOG_ASSISTANT_RESPONSES=1ข้อความคำตอบใน event assistant_response ถ้าไม่ตั้ง จะสืบทอดค่าจาก gate ของ prompts
OTEL_LOG_TOOL_DETAILS=1input ของ tool: คำสั่ง Bash, path ไฟล์, URL, ชื่อ MCP และ skill
OTEL_LOG_TOOL_CONTENT=1span event tool.output ที่มีเนื้อไฟล์และ output ของคำสั่ง (ต้องเปิด tracing)
OTEL_LOG_RAW_API_BODIESJSON ของ Messages API ทั้งก้อน รวมประวัติบทสนทนา (1 = inline, file:<dir> = เขียนลงไฟล์แบบไม่ตัด)
  • เนื้อหาแบบ inline ถูกตัดที่ CLAUDE_CODE_OTEL_CONTENT_MAX_LENGTH ค่า default 61440 UTF-16 code units (ประมาณ 60 KB)
  • ในโหมด detailed beta tracing ค่า response.model_output บน llm_request span ตาม gate ของ prompts ไม่ได้ตาม gate ของ responses
  • การเปิด raw API bodies เท่ากับยินยอมให้เห็นทุกอย่างที่ gate อื่นเปิดเผยอยู่แล้ว เพราะ body ดิบมีทั้ง prompt, response และผล tool อยู่ในตัว เป็น gate ที่กว้างที่สุด

Managed settings กับ endpoint

ถ้าแอดมินตั้ง OTEL_EXPORTER_OTLP_ENDPOINT ผ่าน managed settings (ค่าที่ deploy บังคับให้ผู้ใช้ทุกคน) endpoint แยกราย signal ที่ developer ตั้งเองจะถูกเอาออก dev จึงชี้ signal ใดไป collector อื่นไม่ได้ แต่ตัวเลือก exporter (OTEL_*_EXPORTER) ยังเป็นไปตามลำดับ precedence ปกติทีละ key แปลว่า developer ยังสลับ signal ไปเป็น none หรือ console ได้ เว้นแต่ managed settings จะตั้งตัวเลือก exporter ไว้ด้วย

เข้าใจผิดบ่อย

"เปิดแค่ OTEL_LOG_USER_PROMPTS=1 ก็จะได้เฉพาะ prompt ส่วนคำตอบยังปิดอยู่" ไม่ใช่ gate ของ responses สืบทอดค่าจาก prompts เมื่อไม่ได้ตั้ง ถ้าอยากได้แค่ prompt ต้องตั้ง OTEL_LOG_ASSISTANT_RESPONSES=0 ชัดๆ

"แอดมินตั้ง endpoint ใน managed settings แล้ว dev ปิด telemetry ไม่ได้แน่นอน" ยังได้ ถ้า managed settings ไม่ได้ล็อก exporter selector ไว้ด้วย

สรุปสั้นๆ

default = เก็บแค่ความยาว gate แต่ละตัวเปิดเนื้อหาคนละชั้น: prompt, response (สืบทอดจาก prompt), tool input, tool output (ต้อง tracing), และ raw body ที่กว้างสุด อย่าลืม user.email ที่ไม่มี gate ใน OAuth

ลองเดาก่อน

ทีม compliance ขอเก็บข้อความที่พนักงานพิมพ์ถามเพื่อ audit แต่ห้ามเก็บคำตอบของ Claude เพราะอาจมีโค้ดลับ ถ้าตั้งแค่ OTEL_LOG_USER_PROMPTS=1 จะเกิดอะไร?

  1. เก็บแค่ prompt ตามที่ต้องการ
  2. เก็บทั้ง prompt และ response เพราะ response gate สืบทอดค่ามา
  3. ไม่เก็บอะไรเลยจนกว่าจะเปิด tracing
ดูเฉลย

B ต้องตั้ง OTEL_LOG_ASSISTANT_RESPONSES=0 เพิ่มเพื่อกันไม่ให้คำตอบหลุดไปด้วย

Checkpoint 7 (จับคู่)

จับคู่ความต้องการกับ content gate:

  1. อยากเห็นว่า agent รันคำสั่ง Bash อะไร และแตะไฟล์ path ไหน
  2. อยากเห็นผลลัพธ์ที่คำสั่งพิมพ์ออกมาและเนื้อไฟล์ที่อ่าน (ใช้ tracing อยู่แล้ว)
  3. อยากได้ request/response ของ Messages API แบบดิบทั้งก้อนไว้ replay
  4. อยากเห็นข้อความที่ผู้ใช้พิมพ์
ดูเฉลย

1-OTEL_LOG_TOOL_DETAILS, 2-OTEL_LOG_TOOL_CONTENT, 3-OTEL_LOG_RAW_API_BODIES, 4-OTEL_LOG_USER_PROMPTS tool details = input, tool content = output (ต้องมี tracing), raw bodies = กว้างที่สุดและครอบ gate อื่นทั้งหมด

Checkpoint 8

แอดมินตั้ง OTEL_EXPORTER_OTLP_ENDPOINT ใน managed settings อย่างเดียว developer คนหนึ่งตั้ง OTEL_LOGS_EXPORTER=none ในเครื่องตัวเอง ผลคืออะไร?

  1. log ยังถูกส่งไป endpoint ของบริษัท เพราะ managed settings ชนะทุกอย่าง
  2. log ของ dev คนนั้นไม่ถูกส่ง เพราะ selector ยังตาม precedence ปกติ และ managed settings ไม่ได้ล็อก selector ไว้
  3. log ถูกส่งไป endpoint ที่ dev ตั้งเองแทน
  4. Claude Code ไม่ยอมเริ่มทำงาน
ดูเฉลย

B managed endpoint ลบแค่ endpoint ราย signal ของ dev แต่ exporter selector ยังเปลี่ยนได้ ถ้าจะบังคับจริงต้องตั้ง selector ใน managed settings ด้วย C ผิดเพราะ dev ชี้ไป endpoint อื่นไม่ได้แล้ว
