6.3 Stakeholder expectations: SLAs, limits และ pilot feedback

ต้นฉบับ: CertSafari 6.3

อ่านจบแล้วควรทำได้
  • อธิบายให้ฝั่งธุรกิจเข้าใจว่า service tier แต่ละแบบ (Standard, Priority Tier, Batch) สัญญาอะไรไว้ และ ไม่ได้ สัญญาอะไร
  • แยกได้ว่า rate limit กับ spend cap เป็น "เพดาน" ไม่ใช่ "ความจุที่จองไว้" และอ่าน error 429 / 400 แต่ละแบบออกว่าต้องทำอะไรต่อ
  • ระบุเกณฑ์ที่ stakeholder ต้องเซ็นรับก่อนจะคุยเรื่อง SLA และรู้ว่าเกณฑ์นั้นต้องเปิดคุยใหม่เมื่อไหร่
  • วางช่องทางสื่อสารตอนระบบล่มและตอนโมเดลถูก retire ได้ถูกที่
  • ออกแบบ feedback loop ของ pilot และไล่สาเหตุเวลามีคนบ่นว่า "คุณภาพตก" อย่างเป็นระบบ
แนวคิดหลัก: สัญญาได้แค่เพดานกับเป้า ไม่ใช่การรับประกัน

สิ่งที่สถาปนิกบอก stakeholder ได้ต้องยืนอยู่บน ตัวเลขที่เป็นเพดาน (ceiling) และเป้าหมาย (target) เท่านั้น rate limit กับ spend cap คือค่าสูงสุดที่ใช้ได้ ไม่ใช่ขั้นต่ำที่การันตี และในบรรดา tier ทั้งหมด มีแค่ Priority Tier ที่มีตัวเลข uptime เป็นเป้า

1. Service tier: แต่ละแบบสัญญาอะไรไว้

ก่อนจะรับปากใครว่า "ระบบจะพร้อมใช้ 99.x%" ต้องรู้ก่อนว่าคำขอของเราวิ่งอยู่บน tier ไหน เพราะแต่ละ tier ให้คำมั่นต่างกันมาก

  • Standard เป็นค่าเริ่มต้นของทุก request ให้บริการแบบ best effort ไม่มีตัวเลข uptime ใดๆ ช่วงคนใช้เยอะอาจเจอ overload error ได้ เป็นเรื่องปกติของ tier นี้
  • Priority Tier ต้องทำ capacity commitment (ผูกปริมาณใช้งานล่วงหน้า) แลกกับเป้า uptime 99.5% แต่เป้านี้ครอบคลุมแค่ ปริมาณที่ commit ไว้ บนโมเดลเวอร์ชันที่ระบุ เท่านั้น ส่วนที่เกินจาก commitment จะไหลกลับไปเป็น Standard
  • Batch สำหรับงานแบบ asynchronous ที่รอได้ ไม่เหมาะกับเส้นทางที่ผู้ใช้นั่งรอคำตอบ (latency-sensitive)

Commitment ของ Priority Tier ประกอบด้วย 3 อย่าง:

  • จำนวน token ต่อนาที แยก input กับ output
  • ระยะเวลา 1, 3, 6 หรือ 12 เดือน
  • โมเดลเวอร์ชันเดียว ที่ระบุชื่อ

Cache read และ cache write ก็นับเข้า capacity ของ Priority Tier ด้วย โดยมีน้ำหนัก (weighting) ของตัวเอง และที่ต้องจำคือ Priority Tier ไม่รองรับ หลายโมเดลรุ่นปัจจุบัน ได้แก่ Claude Fable 5.1, Claude Opus 5.5, Claude Sonnet 5.5 และ Claude Haiku 5.5 ถ้าลูกค้าอยากได้เป้า uptime บนโมเดลพวกนี้ ต้องบอกตรงๆ ว่า Priority Tier ช่วยไม่ได้

เปรียบง่ายๆ Priority Tier เหมือนจองโต๊ะร้านอาหารไว้ 10 ที่ ถ้ามา 10 คนได้นั่งแน่ (ตามเป้า) แต่ถ้ามา 14 คน อีก 4 คนต้องไปต่อคิวเหมือนลูกค้า walk-in ปกติ

Tierคำมั่นเรื่องความพร้อมใช้เหมาะกับ
StandardBest effort ไม่มีตัวเลข uptimeค่าเริ่มต้นของทุกงาน
Priority Tier (ในส่วนที่ commit)เป้า 99.5% เฉพาะโมเดลเวอร์ชันที่ commitเส้นทางสำคัญที่ต้องมีตัวเลขไปคุยกับธุรกิจ
Priority Tier (ส่วนที่เกิน)กลับไปเป็น Standardไม่ได้ออกแบบมาให้พึ่งพา
Batchไม่เน้นความเร็ว ประมวลผลแบบ asyncงานรอได้ เช่น ประมวลผลเอกสารข้ามคืน
เข้าใจผิดบ่อย

"ซื้อ Priority Tier แล้วได้ 99.5% กับ traffic ทั้งหมด ทุกโมเดล" ไม่ใช่ เป้า 99.5% ครอบคลุมแค่ capacity ที่ commit บนโมเดลเวอร์ชันที่รองรับ ส่วนที่ล้นเป็น Standard และบางโมเดลไม่รองรับ Priority Tier เลย

สรุปสั้นๆ

Standard = best effort, Priority Tier = เป้า 99.5% เฉพาะส่วนที่ commit บนโมเดลเดียว, Batch = งานที่รอได้ อย่าเอาตัวเลขของ tier หนึ่งไปสัญญากับ traffic ที่วิ่งอยู่อีก tier

Checkpoint 1 (จับคู่)

ทีมมี traffic 4 แบบ จับคู่กับสิ่งที่ฝั่ง Claude สัญญาไว้:

  1. แชตบอตภายในที่ไม่ได้ทำ commitment อะไรเลย
  2. ระบบตอบลูกค้าที่ commit token ต่อนาทีไว้ 6 เดือนบนโมเดลที่รองรับ และใช้ไม่เกินที่ commit
  3. ช่วงแคมเปญที่ traffic ของระบบข้อ 2 พุ่งเกิน commitment ไปเกือบเท่าตัว
  4. งานสรุปรายงานประจำวันที่รันตอนตีสองและพรุ่งนี้เช้าค่อยมีคนอ่าน

ตัวเลือก: (a) เป้า uptime 99.5% (b) best effort ไม่มีตัวเลข uptime (c) ส่วนเกินถูกให้บริการแบบ Standard (d) Batch เหมาะสุด

ดูเฉลย

1-b, 2-a, 3-c, 4-d ข้อ 3 คือกับดักที่เจอบ่อย ส่วนที่ล้นจาก commitment ไม่ได้รับเป้า 99.5% แต่กลับไปอยู่ใน Standard

2. Rate limit กับ spend cap: เพดาน ไม่ใช่ความจุที่จองไว้

ทุกองค์กรถูกจัดอยู่ใน usage tier ซึ่งขยับขึ้นเองอัตโนมัติตามประวัติการใช้งาน องค์กรใหม่อาจเริ่มที่ Evaluation tier ที่ limit ต่ำกว่า นอกจากนี้ admin ยังตั้ง limit ของแต่ละ workspace ให้ต่ำกว่าขององค์กรได้ ซึ่งมีประโยชน์มากตอนทำ pilot เพราะกันไม่ให้ทีมหนึ่งใช้ headroom ของอีกทีมจนหมด

Rate limit วัดยังไง

  • วัดแยกตาม model class เป็น 3 ตัว: RPM (requests per minute), ITPM (input tokens per minute) และ OTPM (output tokens per minute)
  • ทุกตัวเป็น ค่าสูงสุด ไม่ใช่ขั้นต่ำที่รับประกัน
  • บังคับใช้จริงใน ช่วงเวลาที่สั้นกว่าหนึ่งนาที ดังนั้นถ้ายิงกระจุก (burst) อาจโดน limit ได้ทั้งที่ยอดรวมทั้งนาทียังไม่ถึง
  • ในโมเดลส่วนใหญ่ เฉพาะ input token ที่ไม่ได้มาจาก cache เท่านั้นที่นับเข้า ITPM แปลว่าใช้ prompt caching ดีๆ จะได้ ITPM ที่ใช้งานได้จริงสูงขึ้น
  • ขอเพิ่ม limit ได้ใน Console เมื่อใช้ไปแล้ว อย่างน้อย 50% ของ limit ปัจจุบัน และการเพิ่ม limit ก็แค่ยกเพดานขึ้น ไม่ได้จองความจุให้

Spend cap รายเดือนตาม tier

TierSpend cap ต่อเดือน

Customไม่มี cap (ตกลงกับ account team)

อ่าน error ให้ออกว่าต้องทำอะไรต่อ

ตรงนี้คือจุดที่ runbook มักเขียนผิด เพราะ 429 ไม่ได้มีความหมายเดียว

สาเหตุHTTP / typeสัญญาณที่แยกได้ต้องทำอะไร
ชน rate limit429 rate_limit_errorมี header retry-afterรอตามเวลาที่บอก แล้ว retry
ชน spend cap ของ tier429 rate_limit_error + enforced_spend_limit_reachedไม่มี retry-afterรอถึง 00:00 UTC วันที่ 1 ของเดือนถัดไป หรือขยับไป tier ที่สูงกว่า
ชน spend limit ที่องค์กรตั้งเอง400 invalid_request_errorข้อความขึ้นต้นด้วย "You have reached your specified API usage limits"เพิ่มหรือเอา limit ที่ตั้งไว้ออก

ตัวอย่าง logic แยกเคสใน client:

if status == 429 and "retry-after" in headers:
    sleep(int(headers["retry-after"])); retry()
elif status == 429 and code == "enforced_spend_limit_reached":
    alert_finance("ชน spend cap ของ tier: retry ไม่ช่วย")
elif status == 400 and msg.startswith("You have reached your specified API usage limits"):
    alert_admin("ชน limit ที่เราตั้งเอง: ปรับใน Console")
ลองเดาก่อน

ถ้าใช้ SDK ที่ retry 429 ให้อัตโนมัติ แล้วไปชน spend cap ของ tier จะเกิดอะไร? คำตอบ: retry กี่รอบก็ไม่ผ่าน เพราะ 429 แบบนี้ไม่มี retry-after และจะค้างอยู่อย่างนั้นจนกว่าจะถึงรอบรีเซ็ตต้นเดือน หรือจนกว่าจะเปลี่ยน tier

เข้าใจผิดบ่อย

"Rate limit คือความจุขั้นต่ำที่เราได้แน่ๆ" ไม่ใช่ เป็นเพดานบน Standard ยังเป็น best effort อยู่ดี

"429 ทุกตัว retry แล้วเดี๋ยวก็หาย" ไม่ใช่ 429 จาก spend cap ของ tier ไม่หายด้วยการ retry

สรุปสั้นๆ

Limit วัดเป็น RPM/ITPM/OTPM ต่อ model class บังคับในหน้าต่างสั้น และเป็นเพดานทั้งหมด แยก 429 แบบมี retry-after (รอแล้วลองใหม่) ออกจาก 429 spend cap (รอเดือนใหม่/เปลี่ยน tier) และ 400 จาก limit ที่ตั้งเอง

Checkpoint 2

ผู้บริหารถามว่า "เราได้ ITPM limit เพิ่มเป็นสองเท่าแล้ว แปลว่าตอนช่วงพีกระบบเราจะไม่ช้าหรือ error แน่นอนใช่ไหม" ทีมใช้ Standard tier อยู่ ควรตอบแบบไหน?

  1. ใช่ เพราะ limit ใหม่คือความจุที่ Anthropic จองไว้ให้เรา
  2. ไม่ใช่ limit ที่เพิ่มแค่ยกเพดาน บน Standard ยังเป็น best effort และอาจเจอ overload ช่วงพีกได้
  3. ใช่ ตราบใดที่ยอดรวมต่อนาทีไม่เกิน limit จะไม่มี error เลย
  4. ไม่ใช่ เพราะ limit จะกลับลงมาเองทุกต้นเดือน
ดูเฉลย

B limit ไม่ใช่ความจุที่จอง (A ผิด) และถึงยอดรวมต่อนาทีไม่เกิน การยิงกระจุกก็โดน limit ได้เพราะบังคับในหน้าต่างที่สั้นกว่าหนึ่งนาที (C ผิด) ส่วน D ไม่มีกลไกแบบนั้น

3. เกณฑ์ที่ stakeholder ต้องเซ็นรับก่อนคุย SLA

ก่อนจะคุยเรื่อง uptime หรือ response time ต้องตกลงเกณฑ์เลือกโมเดลกับฝั่งธุรกิจให้ได้ก่อน โดยถาม 3 คำถาม:

  1. ต้องการความสามารถอะไร (capabilities) งานนี้ต้องใช้ reasoning ลึกแค่ไหน
  2. ต้องเร็วแค่ไหน รวมถึงยอมจ่ายราคา premium ของ fast mode หรือไม่ (fast mode บน Opus 5.5, Opus 5 และ Opus 4.8 ให้ความเร็ว output สูงขึ้นได้ถึง 2.5 เท่า ในราคา premium การยอมจ่ายหรือไม่เป็นการตัดสินใจทางธุรกิจ ไม่ใช่ทางเทคนิค)
  3. งบเท่าไหร่ แยกทั้งช่วง development และ production

สิ่งที่ ไม่ใช่ เกณฑ์เลือก: จำนวน parameter ของโมเดล หรือที่ตั้งของ data center ข้อมูลพวกนี้ไม่ได้ถูกเผยแพร่เป็นเกณฑ์ในเอกสาร ใครถามมาให้ดึงกลับไปที่ความสามารถ ความเร็ว และงบ

ส่วน uptime กับ response time ควรอยู่ในเอกสารที่เซ็นด้วย แต่ต้องเขียนเป็น เป้า (target) ที่ตรงกับ tier ที่ซื้อจริง ถ้าอยู่บน Standard ก็ห้ามเขียนตัวเลข uptime ที่ Standard ไม่ได้ให้

เกณฑ์ที่เซ็นแล้วไม่ได้ตายตัว

หลัง launch เกณฑ์ต้องถูกเปิดคุยใหม่เป็นระยะ เพราะโมเดลใหม่อาจเปลี่ยนสมการ เช่น โมเดลถูกลงหรือเก่งขึ้นจนสลับ trade-off เดิม สิ่งที่ทำให้การคุยใหม่มีหลักฐานคือ eval suite ที่วัดตามเกณฑ์เดิม เวลาย้ายไปโมเดลใหม่ให้:

  • รัน eval suite เทียบกับเกณฑ์ที่เซ็นไว้ ไม่ใช่รอให้มีคนบ่นก่อน
  • ทบทวน prompt และ guardrail ที่เขียนไว้ให้โมเดลเก่า เพราะอาจไปจำกัดโมเดลที่เก่งกว่า
  • ไม่สมมติว่าโมเดลใหม่จะดีกว่าเสมอโดยไม่ทดสอบ
สรุปสั้นๆ

เซ็นเกณฑ์ 3 ข้อ: ความสามารถ, ความเร็ว (รวม fast mode), งบ dev/prod ตัวเลข uptime/latency เป็นเป้าตาม tier จริง และเปิดคุยใหม่ด้วย eval suite ทุกครั้งที่เปลี่ยนโมเดล

Checkpoint 3

ระบบสรุปสัญญาเช่าผ่านเกณฑ์ที่เซ็นไว้มา 8 เดือน ทีมวางแผนย้ายไปโมเดลรุ่นใหม่ที่เก่งกว่า ควรทำอะไรเป็นอันดับแรก?

  1. ย้ายเลย แล้วรอดูว่ามีผู้ใช้ร้องเรียนไหม
  2. ย้ายโดยคง prompt และ guardrail เดิมไว้ทุกตัว เพื่อไม่ให้พฤติกรรมเปลี่ยน
  3. รัน eval suite บนโมเดลใหม่เทียบกับเกณฑ์ที่เซ็นไว้ และทบทวน prompt/guardrail ที่อาจไปจำกัดโมเดลใหม่
  4. ไม่ต้องทดสอบ เพราะโมเดลใหม่ทำได้ดีกว่าโมเดลเก่าเสมอ
ดูเฉลย

C A เป็นการตั้งรับ B อาจกดโมเดลที่เก่งกว่าไว้ด้วยข้อจำกัดที่เขียนไว้ให้รุ่นเก่า และ D ไม่มีอะไรรับประกันได้ถ้าไม่วัด

Checkpoint 4 (เลือก 3 ข้อ)

เวิร์กชอปเลือกโมเดลกับฝ่ายปฏิบัติการ ข้อไหนเป็นเกณฑ์ที่ควรให้ stakeholder เซ็นรับ?

  1. ความสามารถที่งานต้องการ เช่น ต้องเข้าใจตารางในเอกสารสแกน
  2. จำนวน parameter ของโมเดลแต่ละตัว
  3. เวลาตอบที่รับได้ และยอมจ่ายราคา premium ของ fast mode หรือไม่
  4. ประเทศที่ตั้ง data center ที่ประมวลผลคำขอ
  5. งบประมาณช่วงพัฒนาและช่วง production
ดูเฉลย

A, C, E จำนวน parameter และที่ตั้ง data center ไม่ใช่เกณฑ์เลือกที่มีการเผยแพร่ไว้ในเอกสาร

4. สื่อสารตอนระบบล่มและตอนโมเดลถูก retire

  • คำถามเรื่องบัญชีและ billing ไปที่ Support ผ่านไอคอนข้อความใน Help Center หรือปุ่ม "Get help" ใน Console
  • เขียนสองช่องทางนี้แยกกันใน runbook อย่าให้ทีม on-call ไปเปิด ticket หา Support ทั้งที่ควรดู status page หรือกลับกัน

สิ่งที่คนพลาดบ่อย: capacity constraint ช่วงที่ความต้องการสูง เป็นการจัดการโหลดปกติ ไม่ขึ้นบน status page และ 429 หมายถึงองค์กรเราชน limit ของตัวเอง ไม่ใช่ incident ของ Anthropic ส่วน system card เป็นเอกสารอธิบายพฤติกรรมโมเดล ไม่ใช่ช่องทางแจ้งเหตุขัดข้อง

การ retire โมเดล

  • Anthropic แจ้งล่วงหน้า อย่างน้อย 60 วัน ก่อน retire โมเดลที่เปิดให้ใช้สาธารณะ ผ่านอีเมลถึงลูกค้าที่ได้รับผลกระทบและในเอกสาร
  • Deprecated = ยังใช้ได้ แต่มีตัวแทนที่แนะนำและมีวัน retire แล้ว
  • Retired = ทุก request ล้มเหลว (ไม่ใช่แค่ปิดใน Console แต่ปิด API inference ด้วย)
  • หา API key ที่ยังเรียกโมเดลเก่าอยู่ได้จากหน้า Usage ใน Console โดย export เป็น CSV แยกตาม API key และโมเดล
ลองเดาก่อน: วัน retire ใช้กับทุก platform ไหม?

วัน retire ที่ Anthropic ประกาศใช้กับ platform ที่ Anthropic ดูแลเอง คือ Claude API, Claude Platform on AWS และ Microsoft Foundry ส่วน Amazon Bedrock และ Google Cloud กำหนดตารางของตัวเอง และไม่มี platform ไหนยกเว้นให้ traffic ที่ใช้อยู่เดิม (ไม่ใช่ว่าห้ามแค่ลูกค้าใหม่)

เข้าใจผิดบ่อย

"ข้อความแจ้ง capacity constraint แปลว่า Claude ล่ม เดี๋ยวเช็ก status page ได้" ไม่ใช่ capacity constraint เป็นการจัดการโหลดปกติ และไม่ขึ้นบน status page

สรุปสั้นๆ

Incident ดูที่ status.claude.com, บัญชี/billing ไปที่ Support, overload/429 ไม่ใช่ incident โมเดล retire แจ้งล่วงหน้า ≥60 วัน ใช้กับ platform ของ Anthropic ส่วน Bedrock/Google Cloud มีตารางของตัวเอง

Checkpoint 5

ช่วงบ่ายวันจันทร์ ระบบบน Standard tier เจอ overload error เป็นพักๆ ราว 20 นาทีแล้วหายไป หัวหน้าทีมขายอยากส่งอีเมลแจ้งลูกค้าว่า "ผู้ให้บริการ AI ล่ม" ควรแนะนำอะไร?

  1. ส่งได้เลย overload error คือหลักฐานว่า Anthropic มี incident
  2. เปิด ticket กับ Support ให้ยืนยัน incident ก่อนส่ง
  3. ยังไม่ควรบอกว่าล่ม overload บน Standard ช่วงพีกเป็นการจัดการโหลดปกติ ไม่ใช่ incident ที่ยืนยันแล้ว และจะไม่ขึ้นบน status page
  4. ดู system card ของโมเดลเพื่อยืนยันเหตุขัดข้อง
ดูเฉลย

C overload บน Standard เป็นพฤติกรรมที่คาดได้ของ best effort Support ไม่ใช่ช่องทางยืนยัน incident และ system card ไม่ได้รายงานสถานะแบบ real-time

Checkpoint 6

บริษัทใช้โมเดลรุ่นหนึ่งผ่าน Claude API โดยตรงในระบบหลัก และใช้รุ่นเดียวกันผ่าน Amazon Bedrock ในอีกระบบ Anthropic ประกาศวัน retire ของรุ่นนั้นแล้ว ข้อใดถูก?

  1. Traffic เดิมใช้ต่อได้ การ retire มีผลกับลูกค้าที่สมัครใหม่เท่านั้น
  2. ระบบที่ใช้ Claude API ต้องย้ายก่อนวัน retire ส่วนระบบบน Bedrock ให้ตรวจตารางของ Bedrock เอง
  3. ทั้งสองระบบหยุดวันเดียวกัน เพราะวัน retire ใช้กับทุก platform
  4. การ retire ปิดแค่การเข้าถึงใน Console แต่ API ยังเรียกได้
ดูเฉลย

B วัน retire ของ Anthropic ใช้กับ platform ที่ Anthropic ดูแล ส่วน Bedrock และ Google Cloud กำหนดเอง ไม่มีการยกเว้น traffic เดิม และโมเดลที่ retire แล้วทุก request จะล้มเหลว

Checkpoint 7

ทีม on-call กำลังเขียน runbook ว่า "ถ้าสงสัยว่าฝั่ง Claude มีปัญหา ให้ดูที่ไหนเป็นอันดับแรก" ควรเขียนว่าอะไร?

  1. status.claude.com สำหรับ incident แบบ real-time และแยกให้คำถามเรื่องบัญชีไปที่ Help Center/Support
  2. System card ของโมเดลล่าสุด
  3. ไม่ต้องดูที่ไหน เพราะ Anthropic ไม่มีหน้าแสดงสถานะ ให้ถือว่า 429 คือ incident ทุกครั้ง
  4. ส่งอีเมลถาม account team ทุกครั้ง
ดูเฉลย

A Anthropic มี status page ที่เป็นแหล่งอ้างอิงหลัก system card ไม่ใช่ช่องทาง incident และ 429 อาจมาจากการที่องค์กรเราชน limit เอง

5. สร้าง feedback loop ไว้ใน pilot ตั้งแต่วันแรก

Pilot ที่ไม่มีช่องทางรับ feedback ที่ชัดเจน จะจบด้วยความรู้สึกมากกว่าข้อมูล ให้วาง loop 4 ขั้นนี้:

ขั้นทำอะไรได้อะไร
Collectเปิดช่องทางเฉพาะ มี เจ้าของที่ระบุชื่อ คอยเฝ้าช่วง 48 ชั่วโมงแรก และตอบแบบเปิดเผยให้ทุกคนเห็นคำถามช่วงแรกได้คำตอบเร็ว คนอื่นเห็นคำตอบด้วย
Promptส่งคำถามประจำสัปดาห์ เช่น "สัปดาห์นี้เครื่องมือช่วยอะไรคุณได้บ้าง" ให้ตอบด้วย screenshot หรือสองสามประโยคfeedback ไหลเข้ามาต่อเนื่อง ไม่เงียบหายหลังสัปดาห์แรก
Observeดู usage analytics: active users, sessions, spendเห็นการใช้งานที่ลดลง ซึ่งอาจเป็นสัญญาณว่ามีจุดติดขัด
Report backสรุปรายสัปดาห์ว่า feedback นำไปสู่การตัดสินใจอะไรบ้างผู้ใช้เห็นว่าเสียงของตัวเองเปลี่ยนอะไรได้จริง เลยให้ feedback ต่อ

แต่ละเรื่องที่เข้ามาให้คัดแยก (triage) เป็น 4 ประเภท:

  • ช่องว่างด้านความสามารถ (capability gap) โมเดลหรือระบบยังทำสิ่งนี้ไม่ได้
  • ปัญหา limit หรือ quota
  • ปรับได้ด้วย prompt หรือ configuration
  • คำบ่นเรื่องคุณภาพ ที่ต้องเอาไปตรวจกับ eval

ตอนชวนคนเข้า pilot ให้บอกเหตุผลว่าทำไมเลือกเขา และ input ของเขาจะเปลี่ยนอะไร คนที่รู้ว่าความเห็นตัวเองมีผล จะให้ feedback ที่ใช้ได้มากกว่า

สรุปสั้นๆ

Collect (ช่องทาง + เจ้าของ 48 ชม.แรก) → Prompt (ถามทุกสัปดาห์) → Observe (analytics) → Report back (สรุปว่าทำอะไรจาก feedback) แล้ว triage เป็น capability / limit / config / คุณภาพ

Checkpoint 8 (จับคู่)

จับคู่ปัญหาที่เจอใน pilot กับขั้นของ feedback loop ที่แก้ได้:

  1. สัปดาห์แรกมีคำถามซ้ำๆ แต่ไม่มีใครตอบ คนเลยเลิกถาม
  2. หลังสัปดาห์ที่สอง ไม่มีใครส่ง feedback อีกเลย
  3. ทีมบัญชีเลิกใช้ไปเงียบๆ โดยไม่มีใครบ่น
  4. ผู้ใช้รู้สึกว่าส่ง feedback ไปก็เหมือนโยนลงหลุมดำ

ตัวเลือก: (a) Collect (b) Prompt (c) Observe (d) Report back

ดูเฉลย

1-a, 2-b, 3-c, 4-d ข้อ 3 จะเห็นได้จาก analytics ที่การใช้งานตกลง ไม่ใช่จากคำบ่น

6. แยก "คุณภาพตกจริง" ออกจาก "ความแปรปรวนปกติ"

โมเดลให้คำตอบต่างกันได้แม้ input ใกล้เคียงกัน ดังนั้นมีคนเจอคำตอบแย่ไม่กี่ครั้ง ยังไม่ได้พิสูจน์ว่าเกิด regression และถ้าไม่มี eval ทีมก็ได้แต่ debug แบบตามแก้ทีละเคส

เวลามีคนบอกว่า "ช่วงนี้คุณภาพแย่ลง" ให้ไล่ตามลำดับนี้ เริ่มจากสิ่งที่เช็กง่ายที่สุดก่อน:

  1. มี incident ยืนยันไหม เปิด status.claude.com
  2. เป็นเรื่อง capacity หรือ limit ไหม error ที่เห็นเป็น overload หรือ 429 หรือเปล่า ซึ่งทั้งคู่ไม่ใช่ปัญหาคุณภาพ
  3. มี regression ที่วัดได้ไหม รัน eval suite บน build ปัจจุบัน ถ้าคะแนน ต่ำกว่า baseline เท่านั้นถึงจะมีเหตุผลพอให้ rollback หรือแก้ prompt
  4. เป็นความแปรปรวนปกติ เอาเคสที่ถูกรายงานไปเพิ่มใน eval set แล้วแจ้ง stakeholder ว่าวัดอะไรไปและผลเป็นยังไง

เพื่อให้คำบ่นมีมาตรฐานให้เทียบ ควรเขียน ความคาดหวังเรื่องความสม่ำเสมอ ไว้ในเกณฑ์ที่เซ็นตั้งแต่ต้น เช่น "ยอมรับคำตอบที่สำนวนต่างกันได้ ตราบที่ข้อมูลตัวเลขถูกต้อง"

เข้าใจผิดบ่อย

"มีคนร้องเรียนหลายคน และเราทำซ้ำได้ 1 เคส ก็ rollback ได้เลย" ไม่พอ คำร้องเรียนและเคสที่ทำซ้ำด้วยมือแยก regression ออกจาก noise ไม่ได้ ต้องเทียบ eval กับ baseline

สรุปสั้นๆ

ไล่ 4 ขั้น: incident → capacity/limit → regression ที่วัดด้วย eval → ความแปรปรวนปกติ rollback ได้ก็ต่อเมื่อ eval ต่ำกว่า baseline เท่านั้น

Checkpoint 9

หลัง deploy prompt เวอร์ชันใหม่ ผู้จัดการ 3 คนบ่นว่าสรุปประชุม "ห้วนลง" และวิศวกรลองทำซ้ำเองได้ 1 เคส status page ไม่มี incident และไม่มี 429 ข้อใดเป็นเหตุผลที่เพียงพอให้ rollback?

  1. มีผู้บริหารร้องเรียนเกิน 2 คน
  2. วิศวกรทำซ้ำได้ด้วยมือ 1 เคส
  3. เปิดเคสกับ Support แล้ว
  4. รัน eval suite บน build ปัจจุบันแล้วคะแนนต่ำกว่า baseline
ดูเฉลย

D มีแค่การเทียบ eval กับ baseline ที่แยก regression จริงออกจากความแปรปรวนปกติได้ ถ้าคะแนนไม่ตก ให้เพิ่มเคสที่ถูกรายงานเข้า eval set แล้วรายงานผลการวัดกลับไป
