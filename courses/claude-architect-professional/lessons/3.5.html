3.5 RAG ingestion: chunking, embeddings และ contextual indexing

ต้นฉบับ: CertSafari 3.5

อ่านจบแล้วควรทำได้
  • ตัดสินได้ว่า knowledge base ต้องใช้ RAG หรือใส่ทั้งก้อนลง prompt ได้เลย
  • อธิบายได้ว่าขนาด chunk, จุดตัด (boundary) และ overlap กระทบ retrieval ยังไง และทำไม chunk ที่ถูกตัดออกมาเดี่ยวๆ ถึงเสีย context ของเอกสาร
  • เลือก embedding model ของ Voyage ได้ และตั้ง input_type ถูกทั้งฝั่งเอกสารและฝั่ง query
  • สร้าง contextual embeddings และ contextual BM25 index จาก context ชุดเดียวกัน โดยใช้ prompt caching คุมต้นทุน
แนวคิดหลัก: contextual retrieval

ก่อน index ให้ Claude เขียนคำอธิบายสั้นๆ ว่า chunk นี้อยู่ตรงไหนของเอกสารต้นทาง แล้วเอาข้อความนั้นแปะไว้หน้า chunk ก่อนทั้งการทำ embedding และการทำ BM25 index ทั้งสอง index จะจับคู่ chunk ที่ถ้าอ่านเดี่ยวๆ แล้วไม่รู้เรื่องได้

เปรียบเหมือนฉีกหน้าหนังสือออกมาหน้าเดียว ถ้าไม่เขียนกำกับมุมกระดาษว่า "บทที่ 3 ของคู่มือพนักงานสาขาเนเธอร์แลนด์" คนที่หยิบขึ้นมาทีหลังก็ไม่รู้ว่ามันพูดถึงใคร

1. ขนาด chunk, จุดตัด และ context ที่หายไป

RAG จำเป็นจริงไหม

ลองเดาก่อน

Knowledge base ขนาดราว 150,000 token อัปเดตเดือนละครั้ง ดีไซน์ที่ง่ายที่สุดที่ใช้ได้คืออะไร? คำตอบ: ใส่ทั้งก้อนลงใน prompt แล้วใช้ prompt caching ไม่ต้องมี vector database ไม่ต้อง fine-tune embedding model

  • ถ้า corpus เล็กกว่าประมาณ 200,000 token (ราว 500 หน้า) ใส่ทั้งหมดใน prompt ได้ caching ทำให้การส่งซ้ำเร็วและถูก
  • RAG คือการค้นหา passage ที่เกี่ยวข้องแล้วเติมลง prompt มันคุ้มกับความซับซ้อนที่เพิ่มขึ้นก็ต่อเมื่อ corpus ใหญ่จนใส่ไม่ลง

ขั้นตอน ingestion

  1. หั่น corpus เป็น chunk (ปกติไม่เกินไม่กี่ร้อย token)
  2. ทำ embedding ของแต่ละ chunk
  3. เก็บ vector ลง vector database
  4. ตอน query หา chunk ที่ใกล้ที่สุดแล้วใส่ลง prompt ของ Claude

3 ค่าที่ปรับได้

ค่าผลที่ต้องรู้
ขนาด chunk (size)เล็ก = แม่นแต่ขาดบริบท ใหญ่ = บริบทเยอะแต่เจือจาง แต่ไม่ว่าขนาดไหนก็มีปัญหา context หาย
จุดตัด (boundary)ตัดตาม heading ทำให้หัวข้อย่อยไม่ขาดกลาง ส่วน character splitter แบบง่ายจะตัดตรงไหนก็ได้ที่ตัวนับหมด
Overlapการตัด overlap ออกเพื่อให้ index เร็วขึ้นจะเปลี่ยนผล retrieval ต้องวัดก่อนตัดสินใจ

ปัญหา context loss

ตัวอย่างคลาสสิก: chunk จากรายงาน SEC เขียนว่า "รายได้เติบโต 3% จากไตรมาสก่อน" แต่ไม่ได้บอกว่าบริษัทไหน ไตรมาสไหน ถ้าผู้ใช้ถามโดยระบุชื่อบริษัทและไตรมาส chunk นี้แทบไม่มีอะไรให้จับคู่ การเปลี่ยนขนาด chunk ไม่ได้แก้ปัญหานี้

ทางแก้มี 2 ทาง:

  1. Contextual retrieval: เขียน context ลงไปในแต่ละ chunk ก่อน index (หัวข้อ 3)
  2. Contextualized chunk embedding model เช่น voyage-context-4 เรียกด้วย contextualized_embed() แทน embed() โมเดลจะใส่บริบทของทั้งเอกสารลงใน vector ของ chunk ให้เอง
สรุปสั้นๆ

ต่ำกว่า ~200K token ใส่ทั้งก้อน + cache ก่อน ถ้าต้อง RAG ให้ระวังว่า chunk ทุกขนาดเสีย context ของเอกสาร แก้ด้วย contextual retrieval หรือ contextualized embedding model

Checkpoint 1

ระบบถามตอบนโยบายบริษัทมีเอกสาร "สวัสดิการพนักงาน สาขาสิงคโปร์" ซึ่งมี chunk หนึ่งเขียนว่า "ได้รับเงินช่วยเหลือค่าเดินทาง 200 ต่อเดือน" ชื่อประเทศอยู่แค่ในชื่อเอกสาร เมื่อพนักงานถามว่า "สาขาสิงคโปร์ได้ค่าเดินทางเท่าไหร่" ระบบหา chunk นี้ไม่เจอ สาเหตุและทางแก้คือ?

  1. chunk เสีย context ของเอกสาร ให้เติม context ลงในแต่ละ chunk ก่อน index หรือใช้ contextualized embedding model อย่าง voyage-context-4
  2. chunk ใหญ่เกินไป ให้หั่นเล็กลง
  3. ต้อง fine-tune embedding model ให้รู้จักคำว่าสิงคโปร์
  4. overlap ทำให้เกิด chunk ซ้ำ ให้ปิด overlap
ดูเฉลย

A ไม่มีอะไรใน chunk บอกว่าเป็นของสาขาไหน ไม่ว่าจะหั่นขนาดไหนก็ยังขาดข้อมูลนี้ การ fine-tune หรือแก้ overlap ไม่ได้คืน context ที่หายไป

2. เลือกและเรียก embedding model

Anthropic ไม่มี embedding model ของตัวเอง บทเรียนใช้ Voyage AI เป็นตัวอย่าง และแนะนำให้เทียบ vendor จาก 3 เรื่อง: ข้อมูลที่ใช้เทรน, ประสิทธิภาพตอน inference (ความเร็วในการค้นและ latency ตลอดเส้นทาง) และความสามารถในการ customize

Context length สำคัญขึ้นเมื่อเราเติม context ให้ chunk ถ้าหลังเติม context แล้ว retrieval แย่ลง อาจเป็นเพราะข้อความยาวเกิน input limit แล้วถูกตัดทิ้ง การเปลี่ยนไปใช้โมเดลที่รับ input ได้ยาวกว่าแก้ได้ สังเกตว่า voyage-law-2 รับ input ได้แค่ครึ่งหนึ่งของโมเดลทั่วไป

input_type: บอกโมเดลว่าเป็นเอกสารหรือคำถาม

  • ตั้ง "document" ให้ chunk และ "query" ให้คำถามของผู้ใช้
  • อย่าละไว้หรือส่ง None
  • เหตุผล: Voyage จะเติม instruction สำหรับ retrieval ที่ต่างกันไว้หน้าแต่ละประเภท ทำให้ได้ vector ที่ค้นหาได้ดีกว่า
import voyageai
vo = voyageai.Client()

doc_vecs = vo.embed(chunks, model="voyage-4", input_type="document").embeddings
q_vec    = vo.embed([question], model="voyage-4", input_type="query").embeddings[0]

Metric ไม่ค่อยสำคัญ เพราะ vector ยาว 1

Vector ของ Voyage ถูก normalize ให้ยาวเท่ากับ 1 (unit length) ดังนั้น cosine similarity กับ dot product จัดอันดับเหมือนกันทุกประการ และ Euclidean distance ก็ให้อันดับเดียวกันด้วย การเปลี่ยน metric จึงไม่เปลี่ยนผล

ลดขนาดและต้นทุนของ index

ค่าตัวเลือกผล
output_dtypefloat (default)ความละเอียดสูงสุด
int8 / uint8ลดพื้นที่เก็บ 4 เท่า
binary / ubinaryลดพื้นที่เก็บ 32 เท่า
output_dimensionเช่น 256 แทน 1024 (Matryoshka)vector สั้นลง และ vector ที่เก็บไว้แล้วตัดเหลือมิติแรกๆ แล้ว renormalize ได้

สองค่านี้ช่วยลดขนาดและค่าใช้จ่าย แต่ไม่ได้ช่วยหา chunk ที่เกี่ยวข้องแต่หาไม่เจอ

เข้าใจผิดบ่อย

"ไม่ต้องใส่ input_type ก็ได้ เพราะ query กับ chunk อยู่ใน vector space เดียวกันอยู่แล้ว" ไม่ใช่ การระบุว่าเป็น document หรือ query ทำให้ได้ vector ที่ค้นหาได้ดีกว่า

"retrieval พลาดเพราะใช้ cosine ลองเปลี่ยนเป็น dot product" ไม่ช่วย กับ vector ที่ยาว 1 ทั้งสองจัดอันดับเหมือนกัน

สรุปสั้นๆ

เลือกโมเดลตามโดเมนและ context length, ใส่ input_type ทุกครั้ง, ไม่ต้องกังวลเรื่อง metric และใช้ dtype/dimension ลดต้นทุน ไม่ใช่แก้คุณภาพ

Checkpoint 3

เพื่อนร่วมทีมลบ input_type ออกจากทุกการเรียก embed ให้โค้ดสั้นลง โดยบอกว่า "ยังไง query กับเอกสารก็ไปอยู่ใน space เดียวกัน" ควรตอบว่าอะไร?

  4. ห้ามใส่ เพราะจะทำให้ query กับ chunk ไปอยู่คนละ space ที่เทียบกันไม่ได้

3. Contextual embeddings และ contextual BM25

สำหรับแต่ละ chunk ให้ Claude อ่านเอกสารทั้งฉบับคู่กับ chunk นั้น แล้วเขียน context สั้นๆ (ปกติ 50–100 token) ที่บอกว่า chunk นี้อยู่ตรงไหนของเอกสาร จากนั้นแปะไว้หน้า chunk ในตัวอย่าง SEC context จะบอกชื่อบริษัท ไตรมาส และรายได้ของไตรมาสก่อน

Prompt สำหรับ contextualizer ที่ Anthropic ใช้ (ทดลองกับ Claude 3 Haiku) มีโครงคร่าวๆ คือ ใส่เอกสารทั้งฉบับในช่อง {{WHOLE_DOCUMENT}}, ใส่ chunk, ขอให้เขียน context สั้นๆ เพื่อช่วยการค้นหา และให้ตอบแค่ context เท่านั้น ตัวอย่างที่เขียนเองตามแนวคิดนี้:

<document>
{{WHOLE_DOCUMENT}}
</document>
นี่คือ chunk ที่ต้องการวางตำแหน่งในเอกสารข้างบน:
<chunk>
{{CHUNK_CONTENT}}
</chunk>
เขียนบริบทสั้นๆ ที่บอกว่า chunk นี้อยู่ส่วนไหนของเอกสาร เพื่อช่วยให้ค้นหาเจอ
ตอบเฉพาะบริบทเท่านั้น

Hybrid indexing: chunk ที่มี context ป้อนเข้าทั้งสอง index

  • Contextual embeddings: แปะ context ก่อนทำ embedding
  • Contextual BM25: แปะ context ก่อน tokenize สำหรับ BM25 (การค้นแบบ lexical ที่จับคู่คำตรงตัว) ข้อความเดิมยังอยู่ครบ ดังนั้น string ตรงตัวอย่าง error code TS-999 ยังจับคู่ได้ และคำที่ปรากฏแค่ที่อื่นในเอกสาร (เช่น ชื่อบริษัท) ก็จับคู่ได้ด้วย
for chunk in chunks:
    ctx = contextualize(whole_doc, chunk)       # 50-100 token
    text = ctx + "\n\n" + chunk
    vector_index.add(embed(text, input_type="document"))
    bm25_index.add(tokenize(text))              # ใช้ข้อความเดียวกัน

ผลลัพธ์ (top-20 retrieval failure rate)

ทดสอบบน codebase, นิยาย, ArXiv และเปเปอร์วิทยาศาสตร์:

วิธีFailure rateลดลง
Embedding ปกติ5.7%-
Contextual embeddings อย่างเดียว3.7%35%
Contextual embeddings + contextual BM252.9%49%
  • embedding model ทุกตัวดีขึ้น โดย Gemini และ Voyage ได้ประโยชน์มากที่สุด
  • context ต้องเฉพาะเจาะจงกับแต่ละ chunk การแปะสรุปเอกสารแบบเดียวกันทุก chunk ได้ผลน้อยมาก
  • prompt ที่ปรับให้เข้ากับโดเมน (เช่น ใส่ glossary ที่นิยามไว้ในเอกสารอื่น) อาจได้ผลดีกว่าเดิม

คุมต้นทุนด้วย prompt caching

  • วางเอกสารทั้งฉบับไว้ต้น prompt แล้วใส่ cache_control ที่ท้ายเอกสาร
  • chunk แรกเขียน cache, chunk ถัดๆ ไปของเอกสารเดียวกันอ่าน cache ได้ส่วนลด 90%
  • cache อยู่ได้ 5 นาที จึงควรประมวลผล chunk ของเอกสารเดียวกันต่อเนื่องกันจนหมด ค่อยไปเอกสารถัดไป

ตัวเลขต้นทุน: chunk 800 token, เอกสาร 8k token, context 100 token ต่อ chunk ใช้ราว $1.02 ต่อ document token หนึ่งล้าน token เป็นต้นทุนครั้งเดียวตอน ingest บน codebase ที่มี 737 chunk การ cache ลดค่า input จากราว $9.20 เหลือ $2.85

เข้าใจผิดบ่อย

"เติม context ให้ฝั่ง embedding ก็พอ ส่วน BM25 ใช้ chunk ดิบ" ไม่ใช่ ทั้งสอง index ควรได้ข้อความที่มี context ชุดเดียวกัน ตัวเลข 49% มาจากการทำทั้งคู่

"แปะสรุปเอกสารชุดเดียวกันให้ทุก chunk ก็ได้ผลเท่ากัน" ไม่ใช่ ผลมาจาก context ที่เฉพาะกับแต่ละ chunk สรุปทั่วไปให้ผลน้อยมาก

สรุปสั้นๆ

Claude อ่านทั้งเอกสาร + chunk → เขียน context 50–100 token → แปะหน้า chunk → ป้อนทั้ง embedding และ BM25 ใช้ cache ต่อเอกสารและทำทีละเอกสารเพื่อให้อยู่ใน 5 นาที

Checkpoint 4

ทีมทำ knowledge base ของ log error ผู้ใช้มักค้นด้วยรหัสตรงตัวอย่าง ERR-4012 วิศวกรอยากให้ BM25 ยังจับรหัสพวกนี้ได้แม่นเหมือนเดิม แต่ embedding ได้ context เพิ่ม ดีไซน์ไหนถูกต้อง?

  1. เติม context เฉพาะฝั่ง embedding เพราะ context จะทำให้ BM25 จับรหัสพลาด
  2. เติม context ตอน query แทนตอน index
  3. แปะ context ชุดเดียวกันไว้หน้า chunk ก่อนทั้ง embedding และ tokenize BM25 ข้อความเดิมยังอยู่ รหัสจึงยังจับคู่ได้
  4. เติม context ให้ BM25 อย่างเดียว ส่วน embedding ใช้ chunk ดิบ

C context ถูกเพิ่มเข้าไป ไม่ได้แทนที่ข้อความเดิม BM25 ยังจับรหัสได้และยังได้คำจากส่วนอื่นของเอกสารเพิ่ม ตัวเลือกอื่นทำแค่ครึ่งเดียวหรือผิดจังหวะ

Checkpoint 5

ใน contextualizer prompt ช่องสำหรับเอกสาร ควรใส่อะไร?

  1. คำถามของผู้ใช้
  2. chunk ก่อนหน้า
  3. เอกสารทั้งฉบับ ({{WHOLE_DOCUMENT}})
  4. สรุปเอกสารสั้นๆ ที่ทำไว้ล่วงหน้า
ดูเฉลย

C โมเดลต้องเห็นทั้งเอกสารถึงจะเขียน context ที่เฉพาะกับ chunk นั้นได้ คำถามผู้ใช้ยังไม่มีตอน index และสรุปเอกสารให้ผลน้อยตามที่ทดลองไว้

Checkpoint 6

ทีม support ต้องการให้ lexical index ยังจับ SKU และข้อความ error ได้ตรงตัว แต่ให้แต่ละ chunk รู้ว่ามาจากคู่มือสินค้ารุ่นไหน ควรทำอย่างไร?

  1. แปะ context เฉพาะ chunk ชุดเดียวกับที่ใช้ทำ embedding ไว้หน้า chunk ก่อน tokenize BM25
  2. เลิกใช้ BM25 แล้วสร้าง embedding index ตัวที่สองแทน
  3. ลดน้ำหนัก term frequency ของ BM25 ลง
  4. index แค่ชื่อเอกสารและหัวข้อ
ดูเฉลย

A B ทิ้งการจับคู่ตรงตัว, C ทำให้ lexical matching อ่อนลง, D ทิ้งเนื้อหาที่การจับคู่ตรงตัวต้องใช้

Checkpoint 7

ทีม ingest เอกสาร 2,000 ฉบับด้วย contextual retrieval โดยสุ่มลำดับ chunk จากทุกเอกสารปนกันเพื่อกระจายโหลด ค่าใช้จ่ายสูงกว่าที่คาดมาก สาเหตุที่น่าจะเป็นที่สุดคือ?

  1. ไม่ได้ใช้ input_type="document"
  2. context ยาวเกิน 100 token
  3. ใช้ output_dtype="float"
  4. chunk ของเอกสารเดียวกันไม่ได้ถูกประมวลผลต่อเนื่องกัน cache ที่อยู่ได้ 5 นาทีจึงหมดอายุก่อนถูกอ่านซ้ำ
ดูเฉลย

D ส่วนลด 90% ได้เมื่ออ่าน cache ของเอกสารเดิมภายใน 5 นาที ถ้าสลับเอกสารไปมา cache หมดอายุและต้องเขียนใหม่ทุกครั้ง A และ C ไม่กระทบค่า Claude
