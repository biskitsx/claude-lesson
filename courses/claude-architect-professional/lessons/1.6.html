1.6 Business value pillars สำหรับ Claude solution

ต้นฉบับ: CertSafari 1.6

อ่านจบแล้วควรทำได้
  • เขียน business case บน 5 pillars (efficiency, transformation, productivity, cost, performance SLAs) โดยผูกแต่ละ pillar กับตัวเลขที่ sponsor ติดตามอยู่แล้ว
  • บอก lever หลักและ headline metric ของแต่ละ pillar และบอกได้ว่า design decision แต่ละข้อขยับ pillar ไหน
  • เลือก model class และ configuration ที่ผ่าน latency SLA ด้วยต้นทุนที่ยั่งยืน และอธิบายได้ว่าทำไม fast mode, batch และการยัด context ก้อนใหญ่ถึงไม่ผ่านโจทย์นั้น
  • แยก productivity ออกจาก transformation ได้
แนวคิดหลัก: ทุกการตัดสินใจต้องชี้ไปที่ pillar และ metric

Business value pillars คือผลลัพธ์ 5 ด้านที่ใช้ตัดสินว่า Claude solution คุ้มค่าไหม ทุก architectural decision ต้องตอบได้ว่า ขยับ pillar ไหน และตัวเลขอะไรพิสูจน์ว่าขยับจริง

1. Five pillars คือโครงของ business case

คนที่อนุมัติงบ (sponsor) ไม่ได้ซื้อสถาปัตยกรรม เขาซื้อ ผลลัพธ์ สถาปนิกจึงต้องแปลงงานออกแบบให้เป็นภาษา 5 ด้านนี้:

  • Cost: ผลลัพธ์หนึ่งชิ้นมีต้นทุนเท่าไหร่
  • Efficiency: งานหนึ่งหน่วยใช้ทรัพยากรไปเท่าไหร่
  • Performance SLAs: latency และ availability ที่ระบบต้องรักษาให้ได้
  • Productivity: งานที่เสร็จและใช้ได้จริงต่อ run หรือต่อ person-hour
  • Transformation: งานที่เมื่อก่อนทำไม่ได้เลย

ทุก pillar ต้องจบที่ ตัวเลขที่ sponsor มีอยู่แล้ว เช่น ระบบสรุปเอกสารอาจผูก 4 pillar กับ 4 ตัวเลข: ต้นทุนต่อสรุปที่เสร็จ, p95 response time, จำนวนสรุปที่ analyst รับไปใช้โดยไม่ต้องแก้ต่อสัปดาห์ และรายงานประเภทใหม่ที่ไม่เคยทำได้มาก่อน

PillarHeadline metricLever หลัก

Efficiencyสัดส่วน input ที่อ่านจาก cache; token ต่อ taskPrompt caching, ตัด token ส่วนเกิน, batch สำหรับงานที่รอได้

TransformationOutput หรือ workflow ใหม่ที่กระบวนการเดิมทำไม่ได้เลือกโมเดลตาม capability ในงานที่เครื่องมือปัจจุบันล้มเหลว

อะไรที่ไม่ใช่ value metric

  • ขนาด context window, token throughput, rate limits เป็นคุณสมบัติของ platform ไม่ใช่ผลลัพธ์ทางธุรกิจ
  • จำนวน prompt template ที่เขียน, จำนวน tool ที่ integrate เป็นชิ้นงานระหว่างทางของ implementation ไม่ใช่ value ที่ส่งมอบ
  • คะแนนความพอใจของ developer หลัง launch วัดความรู้สึกของทีมที่สร้าง ไม่ใช่สิ่งที่ส่งมอบ และมาช้าเกินไปสำหรับการตัดสินใจลงทุน
สรุปสั้นๆ

5 pillars = cost, efficiency, performance SLAs, productivity, transformation แต่ละอันต้องมีตัวเลขที่ sponsor ใช้อยู่แล้ว สเปกโมเดลและจำนวนงานที่ทีมทำไม่นับเป็น value

  1. Cost
  2. Efficiency
  3. Performance SLAs
  4. Productivity
  5. Transformation

  2. ค่าใช้จ่ายรวมหารด้วยจำนวนอีเมลที่ส่งออกไปจริง
  3. เปิดบริการตอบลูกค้าเป็นภาษาท้องถิ่น 12 ภาษา ซึ่งทีมเดิมไม่มีคนทำได้

Checkpoint 2

คุณต้องเขียน business case ขอทุนผู้บริหารก่อนเริ่มโปรเจกต์ โครงไหนเหมาะที่สุด?

  1. Cost, efficiency, performance SLAs, productivity และ transformation โดยแต่ละข้อผูกกับตัวเลขที่ผู้บริหารติดตามอยู่แล้ว
  2. จำนวน prompt template และ integration ที่ทีมจะสร้าง
  3. ขนาด context window, throughput และ rate limit ของโมเดลที่เลือก
  4. ผลสำรวจความพอใจของทีมพัฒนาหลังเปิดใช้งาน
ดูเฉลย

A C เป็นสเปกของ platform B เป็นกิจกรรมระหว่างทาง D เป็นสัญญาณรองที่ได้มาหลัง launch ใช้ตัดสินใจลงทุนล่วงหน้าไม่ได้

2. Cost: คิดราคาที่ผลลัพธ์ และเก็บของฟรีก่อน

ตัวเลขหลักคือ ต้นทุนต่อ outcome ไม่ใช่ราคาต่อ token สูตรคือ ค่าใช้จ่ายทั้งหมด ÷ จำนวน task ที่สำเร็จ ใน business case เขียนเป็น "บาทต่อ ticket ที่แก้ได้" หรือ "บาทต่อสรุปที่ถูกรับไปใช้"

โมเดลที่ราคา token แพงกว่าอาจชนะได้ ถ้ามันใช้ turn และ thinking น้อยกว่าในการทำงานให้เสร็จ เหมือนจ้างช่างฝีมือดีค่าแรงแพงกว่า แต่ซ่อมเสร็จในรอบเดียว ไม่ต้องเรียกมาซ้ำ

  4. ค่าใช้จ่ายรวมหารด้วยจำนวนการจองที่สำเร็จ ของแต่ละโมเดล

3. Efficiency: caching คือรายการแรก

Efficiency คือทรัพยากรที่ใช้ต่องานหนึ่งหน่วย เช่น token ที่จ่ายราคาเต็ม การคำนวณซ้ำ หรือการรอ synchronous call ที่ไม่จำเป็น มันทับซ้อนกับ cost แต่ไม่ใช่เรื่องเดียวกัน ระบบอาจ efficient มากแต่ยังแพงได้ ถ้างานนั้นต้องใช้ frontier model

Prompt caching เป็น lever ใหญ่ที่สุดสำหรับ agent loop เพราะทุก turn ต้องส่งบทสนทนาที่ยาวขึ้นเรื่อยๆ ซ้ำ งาน 40 turn ส่ง turn แรกซ้ำ 40 ครั้ง ต้นทุนจึงโตประมาณ กำลังสองของจำนวน turn ถ้าไม่มี cache

  • Metric ที่จับต้องได้คือ cache-read share (สัดส่วน input ที่อ่านจาก cache)
  • จากการวัด traffic จริงหนึ่งวันของ Anthropic เอง agent loop ค่า median อ่าน input จาก cache 84%
  • loop ที่ต่ำกว่าราว 80% น่าจะมีจุดที่ทำ cache แตกอยู่
  • เมื่อคิดราคา benchmark run ราวกับปิด caching งานยาวๆ (coding task ใน SWE-bench Pro และ agent คัดแยกบั๊ก) แพงขึ้น 3.1–7.3 เท่า
  • Anthropic ย้ำว่าเป็นตัวเลขภายในและบอกแค่ทิศทาง ทีมควรวัดของตัวเอง

Batch: รายการที่สอง แต่ไม่ใช่ของฟรีสำหรับทุกงาน

Message Batches API คิดราคาทุก usage ที่ 50% ของราคาปกติ batch ส่วนใหญ่เสร็จภายใน 1 ชั่วโมง และมีเพดาน 24 ชั่วโมง เหมาะกับ nightly evaluation, สร้างเนื้อหาจำนวนมาก, งานวิเคราะห์หลังบ้าน แต่ ไม่เหมาะกับงานที่มีคนรออยู่ เพราะ batch แลก latency กับส่วนลด

ระวังตัวเลขหลอกตา: ถ้าทีมรายงานว่า "จำนวน API call ลดลง 30%" นั่นเป็นแค่ input measure ต้องถามต่อว่า cache-read share เป็นเท่าไหร่ ต้นทุนต่อ task ที่สำเร็จเปลี่ยนไหม และจำนวน output ที่ใช้ได้ยังเท่าเดิมหรือเปล่า

เข้าใจผิดบ่อย

"Batch ลด 50% ฟรีๆ ควรใส่ในทุกแผน efficiency" ไม่ใช่ batch แลก latency ใช้ได้แค่กับงานที่ไม่ต้องตอบทันที

สรุปสั้นๆ

วัด efficiency ด้วย cache-read share (median 84%, ต่ำกว่า ~80% น่าสงสัย) และ token ต่อ task ใช้ batch ลด 50% เฉพาะงานที่รอได้ถึง 24 ชั่วโมง

Checkpoint 4

แผนลดต้นทุนเสนอย้าย 4 งานไป Message Batches API งานไหนต้องถอดออกจากแผน?

  3. ชุด regression eval ที่รันทุกคืน
  4. ผู้ช่วยกรอกแบบฟอร์มในแอปมือถือที่ต้องตอบภายใน p95 1.5 วินาที
ดูเฉลย

4. Performance SLAs: latency และ availability ที่ต้องทำได้จริง

SLA คือคำมั่น ไม่ใช่ความหวัง สถาปนิกต้องแปลงสัญญาของ product เป็นเป้าเชิงปฏิบัติการ เช่น "95% ของ response ต้องเสร็จใน 200 ms" และ uptime เป็นเปอร์เซ็นต์ ถ้าระบบ stream คำตอบ time to first token (TTFT) ต้องวัดแยก เพราะผู้ใช้ตัดสินความเร็วจากตอนที่ตัวหนังสือเริ่มขึ้น

Leverผลต่อความเร็วข้อควรรู้

  2. Fable 5.1 แล้วโหลดฐานข้อมูลคำถามทั้งหมดเข้า context ทุก request เพราะ context ใหญ่พอ
  3. Sonnet 5.5 แล้วปิด thinking
  4. Haiku 5.5 แล้วจูน effort
ดูเฉลย

D class ที่เร็วและถูกที่สุดตอบทั้ง latency และ cost A ซื้อความเร็วด้วยราคาพรีเมียมบนโมเดลที่แพงอยู่แล้ว B ช้าและแพงทั้งจากโมเดลและ token ที่บวม C การปิด thinking ไม่ใช่ lever ที่เอกสารแนะนำ

5. Productivity: นับงานที่เสร็จ ไม่ใช่ token

Productivity นับงานที่เสร็จ ใช้ได้ และผ่านการตรวจ ต่อ agent run หรือต่อ person-hour ส่วน token, call และ turn เป็นแค่ input ตัวอย่าง: agent ที่ใช้ 1 ล้าน token แล้วได้ pull request ที่ถูกต้องพร้อม merge 1 ชิ้น ดีกว่า agent ที่ใช้ 1 แสน token แล้วได้ร่างครึ่งๆ กลางๆ ที่ต้องเขียนใหม่

  • หน่วยนับคือ deliverable: ticket ที่ปิดได้, สรุปที่ถูกรับไปใช้, งานวิเคราะห์ที่ไปจบเป็นเอกสาร สเปรดชีต หรือ deck ที่เสร็จ
  • Task completion rate เป็นสัญญาณทางอ้อมจากผู้ใช้ ว่างานใช้ได้เลยโดยไม่ต้องทำซ้ำไหม
  • ต่อ person-hour: analyst ปิดงานได้กี่ชิ้นเมื่อให้ Claude ร่างแล้ว analyst ตรวจ เทียบกับเขียนเองทั้งหมด
  • โมเดลที่ฉลาดกว่ามักใช้ turn และ thinking น้อยกว่า จึงอาจเพิ่ม productivity ได้แม้ตัวเลข token ดูแย่กว่า

Agentic system มักแลก latency และต้นทุนกับผลงานที่ดีขึ้น การเพิ่ม agent loop จึงคุ้มก็ต่อเมื่อ เพิ่มงานที่เสร็จมากพอจะจ่ายค่า turn ที่เพิ่ม ถ้า call เดียวที่ออกแบบดีให้งานที่เสร็จอยู่แล้ว multi-step agent ก็แค่เพิ่ม spend โดยไม่เพิ่ม deliverable

สรุปสั้นๆ

Productivity = ชิ้นงานที่ใช้ได้ต่อ run หรือต่อชั่วโมงคน agent ที่ซับซ้อนขึ้นต้องพิสูจน์ว่าได้งานเพิ่มคุ้มกับเวลาและเงินที่เพิ่ม

Checkpoint 7

ทีมแปลเอกสารใช้ call เดียวแปลคู่มือ ผู้ตรวจรับไปใช้ได้ราว 88% มีคนเสนอเปลี่ยนเป็น agent หลายขั้น (แปล → ตรวจศัพท์ → ขัดเกลา) ควรใช้อะไรตัดสินว่าคุ้มด้าน productivity?

  1. agent ใช้ token รวมน้อยกว่าหรือไม่
  2. agent ใช้จำนวน turn มากกว่าหรือไม่ ซึ่งแปลว่างานละเอียดกว่า
  3. การเป็น agent ทำให้โปรเจกต์นับเป็น transformation หรือไม่
  4. จำนวนเอกสารที่ผู้ตรวจรับไปใช้ได้ต่อ run หรือต่อชั่วโมงผู้ตรวจ เพิ่มขึ้นมากพอจะคุ้มกับ latency และต้นทุนที่เพิ่มหรือไม่
ดูเฉลย

D productivity วัดที่งานที่ถูกรับไปใช้ token และ turn เป็น input ไม่ใช่ผลลัพธ์ และการเป็น agent ไม่ได้ทำให้กลายเป็น transformation

6. Transformation: งานที่เมื่อก่อนทำไม่ได้

ลองเดาก่อน

ทีมกฎหมายให้ paralegal อ่านและติดแท็กสัญญาหลายพันฉบับต่อเดือน ผู้บริหารวางแผนให้โมเดลติดแท็กแทน แล้วให้ paralegal ดูแค่เคสผิดปกติและไปใช้เวลาเจรจาเงื่อนไข ผู้บริหารกำลังอ้าง pillar ไหน? คำตอบคือ Transformation เพราะ workflow และบทบาทของคนถูกจัดใหม่รอบความสามารถใหม่

  • Productivity = กระบวนการเดิม ได้งานเสร็จมากขึ้น
  • Transformation = ความสามารถใหม่ที่เปลี่ยนรูปร่างของกระบวนการ บทบาทคนย้ายไปทำงานอื่น หรือองค์กรผลิตสิ่งที่ไม่เคยทำได้ เช่น ตรวจสัญญา ทุกฉบับ แทนการสุ่มตรวจ
คำถามทดสอบ

"ถ้าเพิ่มคนหรือเวลาให้กระบวนการเดิม จะได้ผลลัพธ์นี้ไหม?" ถ้าไม่ได้ = transformation ถ้าเป็น workflow เดิมที่เร็วขึ้นด้วยบทบาทเดิม = productivity ถ้าชั่วโมงที่คิดเงินต่อรายการลดลง = cost ถ้าอ้างคำมั่นเรื่อง turnaround = performance SLA

Frontier model class เหมาะกับงาน agent ระยะยาวและปัญหาที่ AI ยังทำไม่ได้อย่างน่าเชื่อถือมาก่อน และเศรษฐศาสตร์ก็เปลี่ยนได้ด้วย agent ที่เคยแพงเกินกว่าจะรัน อาจรันได้ในสเกลใหญ่ จาก pilot กลายเป็น workflow ถาวร

วัด transformation อย่างไรเมื่อไม่มี baseline

เพราะไม่มีตัวเลขเดิมให้เทียบ ต้องสร้างหลักฐานเอง: ทำ evaluation set ที่ดึงจาก production ใส่งานยากที่เครื่องมือปัจจุบันทำไม่ได้ และ กำหนด success criteria ไว้ล่วงหน้า แล้วรายงาน pass rate บนงานที่กระบวนการเดิมทำไม่ได้เลย นั่นคือ metric ของ transformation

เข้าใจผิดบ่อย

"พนักงานทำงานเดิมเสร็จเร็วขึ้น = transformation" ไม่ใช่ นั่นคือ productivity

สรุปสั้นๆ

Transformation คือ workflow หรือ output ใหม่ที่เพิ่มคนก็ทำไม่ได้ พิสูจน์ด้วย eval set จาก production ที่มีงานยากและเกณฑ์กำหนดล่วงหน้า แล้วรายงาน pass rate

Checkpoint 8

ทีม compliance เสนอให้ Claude ตรวจรายการธุรกรรม ทุกรายการ แทนการสุ่มตรวจ 2% แบบเดิม ผู้บริหารขอหลักฐานด้าน transformation ควรเสนออะไร?

  1. ผลสำรวจความพอใจของทีม compliance หลังใช้ระบบ 3 เดือน
  2. p95 เวลาที่ใช้ตรวจต่อรายการ
  3. ชั่วโมงงานของเจ้าหน้าที่ต่อรายการที่ลดลง
  4. Eval set จากธุรกรรมจริง ที่รวมเคสยากซึ่งเครื่องมือเดิมจับไม่ได้ กำหนดเกณฑ์ผ่านไว้ก่อน แล้วรายงาน pass rate

Checkpoint 9

โรงพยาบาลปรับขั้นตอนรับผู้ป่วยนอก ให้ Claude สรุปประวัติและคัดกรองล่วงหน้า พยาบาลคัดกรองจึงเปลี่ยนไปดูแลเฉพาะเคสเสี่ยงสูงและให้คำปรึกษา การเปลี่ยนนี้อยู่ใน pillar ไหน?

  1. Transformation
  2. Cost
  3. Productivity
  4. Performance SLAs
