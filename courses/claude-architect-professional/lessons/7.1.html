7.1 Claude Code settings: scopes, precedence และ permission rules

ต้นฉบับ: CertSafari 7.1

อ่านจบแล้วควรทำได้
  • เลือกไฟล์ settings ให้ถูกกับกฎแต่ละแบบ: กฎของทีม กฎส่วนตัว หรือนโยบายที่องค์กรบังคับ
  • ทำนายได้ว่าเมื่อ key เดียวกันถูกตั้งหลาย scope ค่าไหนชนะ และทำไม permission list ถึง merge กัน
  • เขียน rule แบบ allow / ask / deny และทำนายผลเมื่อ deny กว้างกับ allow แคบ match พร้อมกัน
  • ตัดสินได้ว่าข้อตกลงของทีมควรอยู่ใน CLAUDE.md หรือใน settings
แนวคิดหลัก: scope กำหนดว่าใครโดน และมีน้ำหนักแค่ไหน

ไฟล์ settings แต่ละไฟล์มี scope ที่บอกว่ากฎในนั้นไปถึงใคร และมีน้ำหนักเท่าไหร่ managed settings อยู่บนสุด เหนือทุกอย่างที่นักพัฒนาแก้ได้ ถัดลงมาคือไฟล์ project ที่ commit ไว้ ไฟล์ project ส่วนตัว (local) และไฟล์ของ user

1. Settings 4 scope

Scopeไฟล์มีผลกับใครใช้กับอะไร
Managedmanaged-settings.json และแหล่ง managed อื่นๆทุกคนที่องค์กร deploy ให้นโยบายความปลอดภัยและ compliance
Shared project.claude/settings.jsonทุกคนที่ทำงานในโฟลเดอร์นี้ (commit ไว้ให้เพื่อนร่วมทีมได้ด้วย)permission ของทีม, hooks, plugins, environment variable ของโปรเจกต์

User~/.claude/settings.jsonเราคนเดียว ทุกโปรเจกต์บนเครื่องนี้ความชอบส่วนตัว เช่น theme, editor mode, default model

รายละเอียดที่ต้องรู้ของแต่ละไฟล์

  • Shared project คือไฟล์สำคัญที่สุดสำหรับทีม platform การเปลี่ยนแปลงผ่าน code review และไปถึงทุก clone เมื่อ pull
  • User กฎในไฟล์นี้ไม่เคยออกจากเครื่องเรา เพื่อนในทีมไม่ได้รับ
  • Managed สำหรับนโยบายที่นักพัฒนาแก้ไม่ได้ นักพัฒนาไม่ได้สร้างหรือแก้ไฟล์นี้ มันจึง ไม่ผ่าน code review ของ repo เลยไม่ใช่ที่สำหรับข้อตกลงของทีม
  • Project local เป็นไฟล์ที่ไม่ถูก track เมื่อ Claude Code สร้างไฟล์นี้ใน git repo มันจะเพิ่มไฟล์เข้า global git excludes ให้เอง ถ้าเราสร้างเองด้วยมือ ต้องใส่ใน .gitignore เอง
  • เวลากด "Yes, and don't ask again" ใน prompt ของ Bash ระบบจะเขียน allow rule ลงไฟล์ local นี้
  • Allow rule ในไฟล์ local ที่ไม่ถูก track มีผลโดยไม่ต้องผ่านขั้น workspace trust (ต่างจากไฟล์ที่ commit ซึ่งต้องผ่าน) ตราบใดที่ไฟล์ยังไม่ถูก track
ในข้อสอบ

กฎของทีมที่ต้องผ่าน review → ไฟล์ project ที่ commit (.claude/settings.json) / override ส่วนตัวที่ต้องอยู่บนเครื่อง → ไฟล์ local / นโยบายองค์กร → managed settings

เข้าใจผิดบ่อย

"กฎที่ทีมใช้ร่วมกันใส่ใน managed-settings.json จะได้มั่นใจว่าทุกคนได้" ไม่ใช่ managed settings เป็นนโยบายที่ IT deploy และนักพัฒนาไม่ได้แก้ ข้อตกลงของทีมที่ต้องผ่าน code review ควรอยู่ในไฟล์ project ที่ commit

2. ค่าไหนชนะเมื่อ scope ขัดกัน

Key ที่มีค่าเดียว: scope ที่สูงกว่าชนะ

สำหรับ key ที่เป็นค่าเดี่ยว เช่น model ค่าจาก scope ที่สูงกว่าชนะไปเลย ลำดับจากสูงไปต่ำ:

  1. Managed settings
  2. Flag --settings (มีผลแค่ session นั้น)
  3. Project local (.claude/settings.local.json)
  4. Shared project (.claude/settings.json)
  5. User (~/.claude/settings.json)

--settings ตั้งได้ทุกอย่างที่ไฟล์ user ตั้งได้ แต่ ตั้ง key ที่เป็น managed ไม่ได้

Array: merge กัน ไม่ได้แทนที่

สำหรับค่าที่เป็น array รวมถึง permission rules ข้าม scope ที่ไม่ใช่ managed จะ merge รวมกัน ไม่ใช่ scope สูงแทนที่ scope ต่ำ ผลคือ allow rule ใน local ไม่ได้ลบ deny rule ใน project ทั้งคู่อยู่ในชุดกฎที่มีผลจริง

เปรียบง่ายๆ key ค่าเดี่ยวเหมือนตำแหน่งหัวหน้า ใครยศสูงกว่าได้ไป ส่วน array เหมือนรายชื่อแขกงานเลี้ยง ทุกฝ่ายเพิ่มชื่อเข้ามาในรายชื่อเดียวกัน

ข้อยกเว้น

  • fallbackModel เป็น chain ที่มีลำดับ จึงเอา ทั้งค่า จากไฟล์ที่สูงที่สุดที่กำหนดไว้ ไม่ merge
  • ถ้า managed settings กำหนด availableModels ลิสต์นั้นใช้ตามที่เขียนเลย รายการที่ scope ล่างเพิ่มเข้ามาจะถูกเพิกเฉย
สรุปสั้นๆ

ค่าเดี่ยว: managed > --settings > local > project > user / array (รวม permissions): merge ข้าม scope ที่ไม่ใช่ managed / ยกเว้น fallbackModel (เอาทั้งก้อนจากไฟล์บนสุด) และ availableModels ใน managed (ใช้ตามนั้น)

Checkpoint 3

ไฟล์ .claude/settings.json ของโปรเจกต์มี deny rule Bash(docker push *) นักพัฒนาคนหนึ่งเพิ่ม allow rule Bash(docker push *) ใน .claude/settings.local.json ชุดกฎที่มีผลจริงเป็นยังไง?

  1. ไฟล์ local แทนที่ array ของ project ทั้งหมด เหลือแค่ allow
  2. มีทั้ง deny จาก project และ allow จาก local อยู่ในชุดกฎ
  3. ไฟล์ project ที่ commit ไว้ชนะ allow จาก local ถูกทิ้ง
  4. rule ที่เจาะจงกว่าจะแทนที่ rule ที่กว้างกว่า
ดูเฉลย

B permission array merge ข้าม scope ที่ไม่ใช่ managed ไม่มีใครแทนที่ใคร local ไม่ได้ลบ array ของ project ไฟล์ commit ไม่ได้ทิ้งของ local และความเจาะจงไม่ใช่กลไกแทนที่

3. เขียน rule แบบ allow, ask, deny

Rule หนึ่งตัวคือ ชื่อ tool และอาจมี specifier ในวงเล็บ ต่อท้าย:

Rulematch อะไร
Bashทุกคำสั่ง Bash
Bash(npm run build)คำสั่งนี้คำสั่งเดียวแบบเป๊ะ
Read(./.env)ไฟล์ .env นี้
WebFetch(domain:example.com)โดเมนนี้โดเมนเดียว

Rule หนึ่งตัวระบุได้ หนึ่ง parameter ถ้าอยากคุมสอง parameter ต้องเขียนสอง rule

Rule ใส่ไว้ใน 3 list:

  • permissions.allow ใช้ tool ได้เลยโดยไม่ถาม
  • permissions.ask ถามทุกครั้ง
  • permissions.deny บล็อกเลย
{
  "permissions": {
    "allow": ["Bash(pnpm lint)", "Bash(pnpm test *)"],
    "deny":  ["Read(./secrets.json)", "Read(./config/*.pem)"]
  }
}

Deny ชนะเสมอ

  • Allow rule แค่ ตัด prompt ออก แต่ไม่เคย override deny
  • Deny ถูกประเมินก่อน allow และ ความเจาะจง (specificity) ไม่เปลี่ยนลำดับนี้
  • เพราะ rule merge ข้าม scope allow แคบๆ ใน local จึง เจาะข้อยกเว้น ออกจาก deny กว้างๆ ของ project ไม่ได้

ความไม่สมมาตรของ path pattern

Patternอยู่ใน allowอยู่ใน deny หรือ ask
Edit(src/**)match เฉพาะ src/ ใน directory ปัจจุบันmatch src ที่ความลึกระดับไหนก็ได้
Edit(**/src/**)match src ที่ความลึกระดับไหนก็ได้match src ที่ความลึกระดับไหนก็ได้

ความไม่สมมาตรนี้ออกแบบมาให้ปลอดภัย: deny ครอบคลุมกว้าง ส่วน allow แคบ ถ้าอยาก allow ชื่อ directory นั้นทุกระดับ ต้องเขียน **/ นำหน้าเอง

ลองเดาก่อน

กด "don't ask again" ให้คำสั่ง Bash แล้วการอนุมัตินั้นไปอยู่ที่ไหน อยู่นานแค่ไหน? คำตอบ: ถูกเขียนเป็น allow rule ในไฟล์ local ของ project และ อยู่ถาวร สำหรับ repo และคำสั่งนั้น ส่วนการอนุมัติ แก้ไฟล์ อยู่แค่จนจบ session

เข้าใจผิดบ่อย

"ใส่ allow Bash(kubectl get pods) แล้วจะได้ข้อยกเว้นจาก deny Bash(kubectl *)" ไม่ได้ deny บล็อกคำสั่งนั้น ส่วน allow แค่ตัด prompt ซึ่งไม่มีผลเมื่อโดน deny แล้ว

สรุปสั้นๆ

Rule = Tool(specifier) หนึ่ง parameter ต่อ rule allow ตัด prompt, ask ถามเสมอ, deny บล็อก deny ชนะทุกครั้งไม่ว่า allow จะเจาะจงแค่ไหนหรืออยู่ scope ไหน และระวัง path ใน allow แคบกว่าใน deny

Checkpoint 4

ไฟล์ project มี deny Bash(git push *) เพื่อนร่วมทีมใส่ allow Bash(git push origin feature-x) ในไฟล์ local แล้วให้ Claude รัน git push origin feature-x จะเกิดอะไร?

  1. รันได้ เพราะ allow เจาะจงกว่า
  2. Claude Code ถามผู้ใช้ เพราะกฎขัดกัน
  3. ถูกบล็อก ทั้งสอง rule มีผล และ deny ชนะ
  4. รันได้ เพราะไฟล์ local อยู่ scope สูงกว่าไฟล์ project
ดูเฉลย

C allow ที่เจาะจงไม่ได้เจาะข้อยกเว้นจาก deny กฎที่ขัดกันไม่ได้กลายเป็น prompt และแม้ local จะสูงกว่าสำหรับค่าเดี่ยว แต่ permission merge กันและ deny ชนะ

Checkpoint 5

หัวหน้าฝ่ายความปลอดภัยใส่ deny Bash(terraform *) ไว้ในไฟล์ project นักพัฒนาคนหนึ่งเพิ่ม allow Bash(terraform plan) ใน .claude/settings.local.json ของตัวเอง แล้วสั่งให้ Claude รัน terraform plan ผลคืออะไร และเพราะอะไร?

  1. ถูกบล็อก เพราะ deny ถูกประเมินก่อน allow และความเจาะจงไม่เปลี่ยนลำดับนี้
  2. รันได้ เพราะ rule ที่เจาะจงที่สุดชนะ
  3. เปลี่ยนเป็น ask เพราะ rule สองตัวที่ merge กันทำให้ต้องยืนยัน
  4. รันได้ เพราะไฟล์ local ของผู้ใช้ override deny จาก scope อื่นได้
ดูเฉลย

A ไม่มีกลไก "เจาะจงสุดชนะ" ไม่มีการ merge ที่เปลี่ยนเป็น ask และไฟล์ local ให้ข้อยกเว้นจาก deny ของ scope อื่นไม่ได้

4. คำแนะนำที่แชร์ (CLAUDE.md) กับการบังคับ (settings)

CLAUDE.md มีการซ้อนชั้นคล้ายกับ settings แต่ทำหน้าที่ แนะนำ Claude ไม่ได้ บังคับ

ไฟล์ขอบเขต
CLAUDE.md ของ project (หรือ .claude/CLAUDE.md)แชร์กับทีมผ่าน source control
~/.claude/CLAUDE.mdความชอบส่วนตัว ทุกโปรเจกต์
CLAUDE.local.mdโน้ตส่วนตัว เฉพาะโปรเจกต์นี้
Managed policy CLAUDE.md ที่ path นโยบายของ OS (เช่น /etc/claude-code/CLAUDE.md บน Linux)ทั้งองค์กร โหลดทุก session และ exclude ไม่ได้

หัวใจของหัวข้อนี้: คำสั่ง (instruction) ไม่ใช่การควบคุม (control) Claude อาจทำตาม CLAUDE.md หรือไม่ก็ได้ และถ้ามีคำสั่งขัดกัน ผลอาจออกไปทางไหนก็ได้ ซึ่งยอมรับได้สำหรับเรื่อง style แต่ยอมรับไม่ได้สำหรับเรื่องความปลอดภัย

เรื่องที่ต้องการตั้งไว้ที่
บล็อก tool, คำสั่ง หรือ path ไฟล์บางตัวManaged settings: permissions.deny
บังคับ sandbox isolationManaged settings: sandbox.enabled
วิธี login และจำกัดองค์กรManaged settings: forceLoginMethod, forceLoginOrgUUID
แนวทาง code style และคุณภาพManaged CLAUDE.md
คำแนะนำพฤติกรรมของ ClaudeManaged CLAUDE.md
เข้าใจผิดบ่อย

"เขียนใน CLAUDE.md ว่า 'ห้ามอ่านไฟล์ secret' ก็กันได้แล้ว" ไม่ได้ CLAUDE.md เป็นคำแนะนำ การเขียนซ้ำให้ดังขึ้นในหลายชั้นก็ยังไม่ใช่การบังคับ ต้องใช้ deny rule ใน settings

สรุปสั้นๆ

อยาก "แนะนำ" ใช้ CLAUDE.md อยาก "บังคับ" ใช้ settings ถ้าเป็นนโยบายความปลอดภัยขององค์กรที่ห้ามใครปิด ใช้ deny rule ใน managed settings

Checkpoint 6

CISO สั่งว่า Claude Code บนทุกเครื่องของบริษัทต้องไม่อ่านไฟล์ .env ได้เลย และนักพัฒนาต้องปิดกฎนี้เองไม่ได้ ควรทำอย่างไร?

  1. เพิ่มบรรทัด "ห้ามอ่านไฟล์ .env" ใน CLAUDE.md ของทุก repo
  2. ใส่ Read(./.env) ใน permissions.deny ของ managed settings
  3. เขียนคำสั่งเดียวกันทั้งใน managed CLAUDE.md และ ~/.claude/CLAUDE.md เพื่อให้หนักแน่นขึ้น
  4. ใส่ deny rule ใน .claude/settings.local.json ของแต่ละคน
ดูเฉลย

B A และ C เป็นคำแนะนำที่ Claude อาจไม่ทำตาม เขียนหลายชั้นก็ไม่กลายเป็นการบังคับ D นักพัฒนาแก้เองได้ มีแค่ deny rule ใน managed settings ที่บล็อกทุกครั้งและ override ไม่ได้
