2.1 เลือกโมเดล Claude: lineup, จุดเริ่มต้น และต้นทุนต่องาน

ต้นฉบับ: CertSafari 2.1

อ่านจบแล้วควรทำได้
  • เทียบ Fable 5.1, Opus 5.5, Sonnet 5.5 และ Haiku 5.5 ได้ในด้าน capability, latency, ราคา, context และ default effort
  • เลือกระหว่างเริ่มจากโมเดลเล็ก (small first) กับเริ่มจากโมเดลเก่ง (capability first) ได้ตามลักษณะงาน
  • เทียบโมเดลด้วย ต้นทุนต่องานที่สำเร็จ แทนราคาต่อ token และเลือก billing mode ที่เหมาะกับงาน bulk
  • ออกแบบระบบหลายโมเดลที่ใช้ token ราคา frontier เฉพาะจุดที่เปลี่ยนผลลัพธ์
แนวคิดหลัก: cost per solved task

ต้นทุนต่องานที่สำเร็จ คือเงินทั้งหมดที่จ่ายไปจนงานเสร็จถูกต้อง รวม token ที่ใช้ รอบที่ล้มเหลว และการ retry โมเดลที่ token แพงกว่าอาจถูกกว่าต่องาน ถ้ามันใช้แรงน้อยกว่าในการทำให้สำเร็จ

1. Lineup ปัจจุบัน และอะไรที่ทำให้ต่างกัน

Fast mode

Fast mode (research preview) มีบน Opus 5.5, Opus 5 และ Opus 4.8 เท่านั้น เป็นโมเดลตัวเดิม weights เดิม คุณภาพเดิม แต่รันบน inference setup ที่เร็วกว่า ได้ output tokens per second สูงขึ้นถึง 2.5 เท่า แลกกับราคาพรีเมียม (บน Opus 5.5 คือ $8 input / $40 output ต่อ MTok)

มันเร่ง ความเร็วในการพ่น output ไม่ได้ลด time to first token จึงเห็นผลชัดเมื่อใช้ streaming เหมือนรถคันเดิมที่วิ่งบนทางด่วน ไม่ได้เปลี่ยนเป็นรถเล็ก แต่ต้องจ่ายค่าผ่านทาง

client = anthropic.Anthropic()
resp = client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=2048,
    speed="fast",
    betas=["fast-mode-2026-02-01"],
    messages=[{"role": "user", "content": "ร่างแผน migration ..."}],
)

ต้องใส่ทั้ง speed="fast" และ beta header fast-mode-2026-02-01 ผ่าน betas

Models API: อย่า hardcode ตาราง

ระบบที่เลือกโมเดลตอน runtime ควรอ่านข้อมูลจาก Models API แทนการฝังตารางไว้ในโค้ด response มี:

  • max_input_tokens และ max_tokens
  • object capabilities บอกเช่น ปิด thinking ด้วย thinking: {type: "disabled"} ได้ไหม และรองรับ server tool อย่าง web search หรือ code execution ไหม
  • field line บอกตระกูลโมเดล เช่น opus ให้อ่าน field นี้แทนการแกะจาก model ID

2. เลือกโมเดลเริ่มต้น: ก้าวลง หรือก้าวขึ้น

ถ้าไม่มีเหตุผลพิเศษ ค่าเริ่มต้นคือ Opus 5.5 ใช้ Fable 5.1 เมื่องาน reasoning ยากมากหรือเป็นงาน agent ระยะยาว หรือเมื่อ Opus 5.5 ที่ effort สูง (xhigh / max) ยังไม่ผ่าน eval ระดับ effort ที่มีคือ low, medium, high, xhigh, max

ปรับ effort ก่อนเปลี่ยนโมเดล

Effort คือปุ่มปรับ accuracy กับ latency ภายในโมเดลเดียว (รายละเอียดในบท 3.3) ลำดับที่ถูก:

  • แพงไปแต่คุณภาพโอเค → ลด effort บนโมเดลเดิมก่อน
  • คุณภาพต่ำ → คืน effort ที่เคยลดไปก่อน แล้วค่อยลองโมเดลขั้นถัดไปที่ default effort ของมัน
  • อย่ายกค่า effort ข้ามโมเดล เพราะ default ต่างกัน เช่น Opus 5.5 default เป็น medium แต่ Opus 5 เป็น high request ที่ไม่ได้ระบุ effort ตอนย้ายจาก Opus 5 มา Opus 5.5 จะรันต่ำลงหนึ่งระดับโดยไม่รู้ตัว

ตัดสินใจด้วย eval set ของ use case ตัวเอง (prompt และข้อมูลจริง) เทียบความแม่น คุณภาพคำตอบ และ edge case (วิธีเทียบอยู่ในบท 4.3) public benchmark ช่วยได้น้อยที่ระดับบนสุด เพราะ Opus กับ Fable ทำคะแนนเกือบเต็มแล้ว

เข้าใจผิดบ่อย

"แพงเกินงบ ให้เปลี่ยนไปโมเดลที่ถูกกว่าก่อน" ไม่ใช่ ลด effort บนโมเดลปัจจุบันก่อน การเปลี่ยน tier มาหลังจากทำ effort sweep กับ eval แล้ว

สรุปสั้นๆ

Default คือ Opus 5.5 งานง่าย/ต้องเร็ว/ปริมาณมากเริ่มเล็ก งานยาก/ต้องแม่นเริ่มใหญ่ ปรับ effort ก่อนสลับโมเดล และไม่ยก effort ข้ามโมเดล

  1. เริ่มที่ Opus 5.5 จูน prompt ให้ดี แล้วค่อยลด effort หรือย้ายลงโมเดลเล็กทีหลัง

  3. เริ่มที่ Fable 5.1 เพราะ public benchmark แยกโมเดลระดับบนได้ชัดที่สุด
  4. เริ่มที่ Sonnet 5.5 เพราะโมเดลกลางๆ ช่วยแยกปัญหา setup ได้ดีที่สุด

A งานซับซ้อนที่ความแม่นสำคัญใช้ capability first การเริ่มเล็ก (B, D) ทำให้แยกสาเหตุยาก ส่วน C ผิดทั้งสองส่วน public benchmark แยกระดับบนได้น้อย และ Fable ไม่ใช่จุดเริ่มต้น ใช้เมื่อ Opus ที่ effort สูงยังไม่พอ

Checkpoint 5 (เลือก 3 ข้อ)

หัวหน้าทีมถามว่าทำไมเราสร้าง prototype ระบบติดแท็กอีเมลด้วย Haiku 5.5 แทนที่จะเริ่มที่ Opus 5.5 ซึ่งเก่งกว่า เหตุผลไหนถูกต้อง?

  1. โมเดลเร็วและถูกทำให้วนรอบแก้และทดลองได้เร็วในช่วง prototype
  2. ต้องเริ่มที่ Haiku ก่อน เพราะจะเข้าถึง Opus ได้ต่อเมื่อผ่าน benchmark ของ prototype
  3. ระบบนี้ต้องตอบเร็ว latency ต่ำ
  4. Haiku 5.5 รับประกันความแม่นเท่า Opus 5.5 ทุกงาน
  5. งานนี้ปริมาณมาก ตรงไปตรงมา และต้องคุมต้นทุน
ดูเฉลย

3. เทียบโมเดลด้วยต้นทุนต่องานที่สำเร็จ

ราคาต่อ token บอกได้แค่ request เดียว โมเดลที่ฉลาดกว่ามักใช้ turn และ thinking น้อยกว่า จึงอาจชดเชยราคาพรีเมียมได้ ส่วนโมเดลถูกที่ทำงานพลาดก็ยังเก็บเงินทุก token บวกค่า retry และความเสียหายปลายทาง

ลองเดาก่อน

Opus 5.5 ราคา token เป็น 2 เท่าของ Sonnet 5.5 ใน coding benchmark Opus 5.5 ที่ effort low แก้งานได้ใกล้กับ Sonnet 5.5 ที่ default effort ต้นทุนต่องานที่สำเร็จต่างกันเท่าไหร่? คำตอบคือ Opus แพงกว่าแค่ราว 7% เพราะที่ effort ต่ำ Opus ทำงานน้อยลงต่อ task จนกลบส่วนต่างราคาไปเกือบหมด

ตัวเลขจาก SWE-bench Pro subset ใช้ดูทิศทางเท่านั้น ไม่ใช่การรับประกัน สิ่งที่ควรเก็บ:

  • Opus 5.5 ที่ default ได้ผลพอๆ กับ Fable 5.1 (อยู่ในช่วง noise ระหว่างรอบ) ในราคาราว 1 ใน 5 ต่องาน จึงเป็นจุดเริ่มต้นยอดนิยม
  • บน GPQA Diamond, Haiku 5.5 ได้ 85% เทียบกับ 91% ของ Opus 5.5 และ Sonnet 5.5 แต่ต้นทุนต่อคำตอบที่ถูกราว 1 ใน 20 ของ Opus 5.5 เหมาะกับงานปริมาณมากที่ตรวจผลได้
  • อันดับอาจกลับด้านได้ เช่น research loop ยาวๆ ที่ Fable 5.1 อาจทำได้มากกว่าและแพงกว่าต่องาน
  • วัดที่ task ยากสุด 10% ไม่ใช่ task ทั่วไป บิลถูกขับโดยงานที่โมเดลถูกทำพลาด ในการรัน 20 ข้อครั้งหนึ่ง แค่ 2 ข้อกินไป 43% ของค่าใช้จ่าย

ของฟรีที่ต้องเก็บก่อนตัดสินเรื่องโมเดล

  • Message Batches API: ประมวลผลแบบ async ลด 50% แลกกับ latency ปกติเสร็จในชั่วโมงเดียว แต่ควรเผื่อถึง 24 ชั่วโมง ทุก active model รองรับ ไม่ผูกกับ tier
  • Prompt caching: ในการทดลองของ Anthropic มักเป็นก้อนประหยัดที่ใหญ่ที่สุดก้อนเดียว
  • อย่าใช้ synchronous call ที่ effort max กับงานที่รอได้ และอย่าปิด caching เพื่อประหยัด
เข้าใจผิดบ่อย

"โมเดลที่ token ถูกสุดคือวิธีที่ถูกที่สุด" ไม่ใช่ โมเดลที่ฉลาดกว่าอาจทำงานเสร็จด้วยแรงน้อยกว่าและพลาดน้อยกว่า จึงถูกกว่าต่องานที่สำเร็จ

"ส่วนลด batch ใช้ได้กับบางโมเดลเท่านั้น" ไม่ใช่ ทุก active model ได้ส่วนลด 50% เลือกโมเดลจากคุณภาพและต้นทุนต่องาน ไม่ใช่จากสิทธิ์ batch

สรุปสั้นๆ

เทียบด้วย cost per solved task บน eval ของตัวเอง ดูงานยากสุด เก็บ batch (−50%) และ caching ก่อนแตะเรื่องโมเดล

Checkpoint 6

ทุกคืนระบบต้องสกัดข้อมูลจากใบแจ้งหนี้หลายแสนใบ ไม่มีใครรอผลจนเช้า Sonnet 5.5 ที่ default effort แม่นพอแล้ว จะลดค่าใช้จ่ายอย่างไรโดยคุณภาพไม่ลด?

  1. ส่งผ่าน Message Batches API กับ Sonnet 5.5 แล้วเปิด prompt caching ไว้
  2. ปิด prompt caching เพื่อเลี่ยงค่าเขียน cache
  3. ย้ายไป Haiku 5.5 เพราะมีแค่โมเดลเล็กสุดที่ได้ส่วนลด batch
  4. ใช้ synchronous call ที่ effort max ให้เสร็จเร็วๆ
ดูเฉลย

A งานรอได้จึงได้ส่วนลด 50% โดยโมเดลและคุณภาพเหมือนเดิม และ caching เป็นของฟรีที่ไม่ควรปิด C ผิดเพราะทุก active model ได้ส่วนลด batch D แพงขึ้นโดยไม่จำเป็น

Checkpoint 7

ทีม data ต้องจัดหมวดหมู่และสรุปบันทึกการโทร call center ย้อนหลัง 25 ล้านรายการภายในสุดสัปดาห์ ไม่มีผู้ใช้รอ อยากลดค่า API รวมให้มากที่สุดโดยคุณภาพยังดีพอ ทางไหนเหมาะที่สุด?

  1. ใช้ Message Batches API ซึ่งราคาราวครึ่งหนึ่งของ synchronous
  2. ใช้ synchronous call ที่ effort max เพราะไม่มีข้อจำกัดเรื่องเวลา
  3. ใช้ Batch API กับ Fable 5.1 เท่านั้น เพราะส่วนลดมีเฉพาะ tier บนสุด
  4. ใช้ synchronous และปิด prompt caching เพื่อเลี่ยงค่า storage
ดูเฉลย

A งาน bulk ที่ไม่มีคนรอคือที่ของ batch B เพิ่ม token โดยไม่ได้อะไรกับงานตรงไปตรงมา C ผิดเพราะส่วนลดใช้ได้ทุกโมเดล และใช้โมเดลบนสุดกับงานจัดหมวดก็เปลืองเปล่า D ทิ้งเงินที่ประหยัดได้

4. ใช้หลายโมเดลในระบบเดียว (tiering)

ใช้โมเดลเดียวกับทุก request หมายความว่าจะจ่ายราคา frontier กับงานง่าย หรือได้คุณภาพโมเดลเล็กกับงานยาก ระบบหลายโมเดลส่งเฉพาะ การตัดสินใจที่ต้องใช้สมองแพง ไปให้โมเดลแพง token ส่วนใหญ่จึงถูกคิดในราคาที่ต่ำกว่า

Patternทำงานอย่างไรเหมาะเมื่อ / ข้อควรระวัง
Executor with an advisorโมเดลถูกทำงานหลัก แล้วปรึกษาโมเดล frontier ให้ตรวจแผนหรือรีวิว output ตอนเจอจุดยากเหมาะเมื่อโมเดลถูกติดแค่บางจุด advisor ช่วยได้เฉพาะตอนถูกเรียก จึงต้อง วัด consult rate ก่อน (เริ่มทดสอบ executor ที่ effort low) Haiku 5.5 เป็น advisor ไม่ได้
Orchestrator with workersโมเดลเก่งวางแผน แล้วกระจายงานส่วนใหญ่ให้ worker ราคาถูกเหมาะกับงานที่ใหญ่เกิน context window เดียว Sonnet เป็น worker ยอดนิยมเพราะสมดุลความเร็ว/ราคา และ Haiku ถูกวางไว้สำหรับงาน sub-agent
Routing (บท 1.5)classifier คัดแยกก่อนเริ่มงาน งานง่ายไปโมเดลเล็ก งานยากไปโมเดลใหญ่ประหยัดได้ก็ต่อเมื่อ classifier เชื่อถือได้ งานยากที่หลงไปโมเดลเล็กจะกลายเป็นงานล้มเหลวและดันบิลขึ้น

ตัวอย่างผลวัดของ advisor: Sonnet 5 ที่มี Fable 5 เป็น advisor ได้คะแนน SWE-bench Pro ห่างจาก Fable 5 ตัวเดียวไม่เกิน 10% ในราคา 63% ของการรัน Fable 5 อย่างเดียว

ไม่ว่าจะใช้ pattern ไหน ต้องวัดด้วย ต้นทุนต่องานที่สำเร็จบน eval set ของตัวเอง ไม่ใช่แค่ดูว่าใช้ token ของโมเดล frontier น้อยลงไหม

ลองใช้กับงานของคุณ

นึกถึง workflow ที่คุณรู้จักดี ขั้นไหนต้องการการตัดสินใจระดับ frontier จริงๆ ขั้นไหนโมเดลเล็กทำได้ถ้ามีอะไรตรวจ output แล้ว pattern ไหนเหมาะ: advisor, orchestrator หรือ router

สรุปสั้นๆ

Advisor = ตัวถูกทำ ตัวแพงช่วยตอนยาก, orchestrator = ตัวแพงวางแผน ตัวถูกลงมือ, routing = แยกก่อนเริ่ม ทั้งหมดต้องพิสูจน์ด้วย cost per solved task

  2. Opus 5.5 แตกงานแปลเอกสาร 3,000 หน้าเป็นชุดๆ แล้วส่งให้ Haiku 5.5 หลายตัวแปล
  3. classifier ดูคำถามลูกค้าก่อน ถ้าเป็นเรื่องเช็คสถานะส่งไป Haiku ถ้าเป็นข้อพิพาทส่งไป Opus
  1. Routing
