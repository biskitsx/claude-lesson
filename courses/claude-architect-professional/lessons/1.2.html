1.2 End-to-end agent architecture: the loop, tool execution and feedback

ต้นฉบับ: CertSafari 1.2

อ่านจบแล้วควรทำได้
  • ไล่ request หนึ่งตัวผ่าน agent loop ตั้งแต่ input ที่ประกอบเสร็จจนได้ผลลัพธ์สุดท้าย และบอกได้ว่าอะไรคือเงื่อนไขที่ทำให้ loop หยุด
  • แยกได้ว่า tool แต่ละตัว โค้ดของเรา หรือ Anthropic เป็นคนรัน และมันเปลี่ยนหน้าที่ของ loop เรายังไง
  • ตัดสินได้ว่าเมื่อไหร่ควรใส่ tool, MCP หรือโมเดลที่แรงขึ้นในขั้น processing
  • ออกแบบ feedback (tool result, hook, graded outcome) ให้ระบบแก้ตัวเองระหว่างรันได้
แนวคิดหลัก: loop ที่วนจนไม่มี tool call

Agent loop คือ: ประกอบ input → Claude ตอบเป็นข้อความหรือขอเรียก tool → รัน tool → ส่งผลกลับเข้าไป แล้ววนซ้ำ จนกว่า Claude จะตอบโดยไม่ขอ tool อีก คำตอบสุดท้ายนั้นคือ output ของระบบ

1. Agent loop ตั้งแต่ input จนถึง output

Input ไม่ได้มีแค่ข้อความของผู้ใช้ แต่รวมถึง system prompt, นิยาม tool ทั้งหมด และประวัติบทสนทนา ใน Agent SDK การรันจะเริ่มด้วย SystemMessage ที่มี subtype init ซึ่งพก metadata ของ session มาด้วย

Processing ทำงานเป็น turn แต่ละ turn คือรอบ "ประเมินแล้วลงมือ" หนึ่งรอบ งานหนึ่งอาจใช้หลาย turn

Output คือคำตอบที่ไม่มี tool call ใน Agent SDK ข้อความสุดท้ายมาเป็น AssistantMessage ตามด้วย ResultMessage ที่บรรจุข้อความสุดท้าย, token usage, ค่าใช้จ่าย และ session ID ต้องเช็ก field subtype ทุกครั้ง เพราะการรันอาจจบเพราะชน limit ไม่ได้จบเพราะสำเร็จ

ตัวอย่าง: แก้เทสต์ที่พัง

  1. Turn 1: Claude ขอรันเทสต์ผ่าน Bash เห็นว่าเทสต์ไหนพัง
  2. Turn 2: อ่านไฟล์ที่เกี่ยวข้อง
  3. Turn 3: แก้ไฟล์แล้วรันเทสต์ซ้ำ
  4. Turn สุดท้าย: ตอบเป็นข้อความสรุปโดยไม่มี tool call → loop จบ

ทุกขั้น Claude เลือกเองจากผลของขั้นก่อนหน้า ไม่มีใครเขียนลำดับนี้ไว้ในโค้ด

ถ้าเขียน loop เองบน Messages API

เราต้องเขียน while loop ที่ตัดสินจาก stop_reason:

while True:
    resp = client.messages.create(model=MODEL, tools=TOOLS, messages=msgs)
    msgs.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason == "tool_use":
        msgs.append({"role": "user", "content": run_client_tools(resp)})
    elif resp.stop_reason == "pause_turn":
        continue                      # ส่งบทสนทนา (รวม response ที่ pause) กลับไปใหม่
    else:
        break                         # end_turn หรือหยุดด้วยเหตุผลอื่น
stop_reasonความหมายโค้ดเราต้องทำอะไรต่อ
tool_useมี tool ที่ต้องรันรัน tool, ส่ง block tool_result กลับ, เรียก API อีกรอบ
end_turnคำตอบสุดท้ายออกจาก loop แล้วส่งผลให้ผู้ใช้
max_tokens, stop_sequence, refusalหยุดด้วยเหตุผลอื่น ไม่ใช่งานเสร็จออกจาก loop และจัดการกรณีนั้นแบบชัดเจน
pause_turnloop ของ server tool ชนเพดานจำนวนรอบส่งบทสนทนากลับไปใหม่ โดยรวม response ที่ถูก pause ไว้ด้วย

เลือกที่ host: Messages API เหมาะเมื่อต้องการ loop แบบ custom ที่ควบคุมละเอียด ส่วน Claude Managed Agents ให้ harness สำเร็จรูป (loop + การรัน tool + runtime) เหมาะกับงานยาวแบบ asynchronous

สรุปสั้นๆ

มีแค่ tool_use ที่ทำให้ loop ฝั่ง client วนต่อ end_turn คือเสร็จ ค่าอื่นคือหยุดก่อนเวลาที่ต้องจัดการ และ pause_turn คืองานฝั่ง server ยังไม่จบ

Checkpoint 1 (จับคู่)

จับคู่ stop_reason กับสิ่งที่โค้ดควรทำ:

  1. pause_turn
  2. tool_use
  3. max_tokens
  4. end_turn

A. ส่งผลให้ผู้ใช้ได้เลย · B. รัน tool แล้วส่ง tool_result พร้อมเรียกอีกรอบ · C. ส่งบทสนทนาเดิมรวม response ที่ค้างกลับไปให้ทำต่อ · D. ถือว่ายังไม่ใช่คำตอบสมบูรณ์ ต้องจัดการกรณีถูกตัดเอง

ดูเฉลย

1-C, 2-B, 3-D, 4-A จำไว้ว่า max_tokens ไม่ได้แปลว่างานเสร็จ และ pause_turn ไม่ใช่คำตอบสุดท้าย

2. ใครเป็นคนรัน tool: client tool กับ server tool

Claude ไม่เคยรัน tool เอง มันแค่ปล่อย request แบบมีโครงสร้างออกมา แล้วมีอะไรสักอย่างข้างนอกรันให้ ผลค่อยกลับเข้าบทสนทนา คำถามสำคัญคือ "โค้ดรันที่ไหน" เพราะมันกำหนดว่าแอปเราต้องรับผิดชอบอะไร

ชนิด toolตัวอย่างใครรันหน้าที่ของ loop เรา
User-defined client tooltool ที่เราเขียน schema เอง เช่น get_invoiceแอปของเรารัน, ส่ง tool_result, ขับ loop เอง Claude ไม่เห็น implementation
Anthropic-schema client toolmemory, bash, text_editor, computer, browserแอปของเราเหมือนข้างบน แต่ Claude ถูกเทรนกับ signature พวกนี้มา เลยเรียกแม่นกว่าและฟื้นจาก error ได้ดีกว่า
Server toolweb_search, web_fetch, code_execution, tool_searchAnthropicเปิดใช้ใน request, อ่านผล, ส่งใหม่เมื่อเจอ pause_turn ไม่ต้องสร้าง tool_result เอง

ผลต่อ latency:

  • Client tool เพิ่ม round trip ทุกครั้งที่เรียก เพราะโมเดลต้องถาม แล้วเราต้องตอบ
  • Server tool รันค้นหาหรือรันโค้ดหลายครั้งได้ภายใน request เดียว ผลกลับมาพร้อม block server_tool_use ที่มีผลแล้ว

สองทางออกที่ต้องออกแบบรองรับ

  • ถ้า loop ฝั่ง server ชนเพดานจำนวนรอบ จะได้ pause_turn ให้ส่งบทสนทนา (รวม response ที่ถูก pause) กลับไป โมเดลจะทำต่อจากเดิม
  • ถ้าการเรียกแบบขนานกลุ่มเดียวกัน ผสม server tool กับ client tool response จะเป็น tool_use และมี block server_tool_use ที่ยังไม่มีผล API จะรัน server tool นั้นต่อก็ต่อเมื่อเราส่งผลของ client tool กลับไปแล้ว

ลองเดา: bash ใครรัน? คำตอบคือแอปของเรา เพราะมันเป็น Anthropic-schema client tool Anthropic แค่กำหนด schema ให้

เข้าใจผิดบ่อย

"Anthropic เป็นคนรัน bash, text_editor, computer เพราะเป็น tool ของ Anthropic" ไม่ใช่ พวกนี้เป็น client tool โค้ดเราต้องรันเอง มีแค่ server tool ที่รันฝั่ง Anthropic

"pause_turn คือ response ที่เสร็จแล้ว" ไม่ใช่ มันแปลว่า loop ฝั่ง server ชนเพดาน ต้องส่งกลับไปให้ทำต่อ

สรุปสั้นๆ

Schema เป็นของใครไม่สำคัญ สำคัญที่ว่าโค้ดรันที่ไหน client tool = เรารันและตอบ tool_result, server tool = Anthropic รันให้

Checkpoint 2

Agent ของร้านค้าออนไลน์เปิดใช้ tool 4 ตัว ตัวไหนที่แอปของเรา ไม่ต้อง รันและไม่ต้องส่ง tool_result กลับเอง?

  1. text_editor
  2. check_stock ที่ทีมเขียน schema เอง
  3. memory
  4. web_search
ดูเฉลย

D web_search เป็น server tool ที่ Anthropic รัน ส่วน text_editor กับ memory เป็น Anthropic-schema client tool และ check_stock เป็น user-defined client tool ซึ่งแอปเราต้องรันทั้งหมด

3. เมื่อไหร่ควรมี tool ในงานออกแบบ

ใส่ tool เฉพาะเมื่อ ข้อความอย่างเดียวทำงานนั้นไม่ได้ มี 4 กรณีหลัก:

  • ต้องทำ action ที่มีผลข้างเคียง เช่น ส่งอีเมล อัปเดต record
  • ต้องใช้ข้อมูลสดหรือข้อมูลภายนอก
  • output ต้องมีโครงสร้างที่ บังคับ ได้
  • ต้องเรียกระบบที่มีอยู่ เช่น internal API, database, filesystem

งานสรุป แปล หรือถามตอบทั่วไปไม่ต้องมี tool และถ้างานเล็กมาก latency ของ tool อาจนานกว่าตัวงานเองด้วยซ้ำ

กลิ่นของการออกแบบผิด

ถ้าคุณกำลังเขียน regex เพื่อดึง "การตัดสินใจ" ออกจากข้อความของโมเดล นั่นแปลว่าการตัดสินใจนั้นควรเป็น tool call ตั้งแต่แรก ให้ schema เป็นตัวบังคับโครงสร้าง แทนการ parse ข้อความอิสระ

เชื่อมหลายระบบ: MCP

ถ้าต้องเชื่อม wiki, database, chat ฯลฯ การเขียน handler เองแปลว่าต้องดูแล integration ทีละระบบ MCP server เปิดแต่ละระบบผ่าน protocol มาตรฐานเดียว และ Claude ยังเป็นคนเลือกว่าจะเรียกเมื่อไหร่ ใน Managed Agents MCP server ถูกประกาศไว้บนตัว agent ส่วน credential ส่งเข้ามาตอนเริ่มแต่ละ session (การเทียบ protocol แบบละเอียดอยู่ในบท 3.7)

ทางลัดสองแบบที่ ใช้ไม่ได้:

  • แปะข้อมูลจากระบบลงใน prompt: ข้อมูลเก่า และทำ action ไม่ได้
  • ทำ decision tree ตายตัวไม่มีโมเดล: ตัดความสามารถของโมเดลในการเลือกขั้นต่อไปทิ้ง
สรุปสั้นๆ

Tool สำหรับ action, ข้อมูลสด, โครงสร้างที่ต้องบังคับ, และระบบเดิม หลายระบบใช้ MCP อย่าใช้ regex parse การตัดสินใจ

Checkpoint 3

Agent ตรวจคำขอเบิกค่าใช้จ่ายตอบเป็นข้อความยาว แล้วโค้ดใช้ regex หาคำว่า "APPROVE" หรือ "REJECT" ซึ่งพังบ่อยเมื่อโมเดลเขียนว่า "ไม่ควร approve" วิธีแก้ที่ถูกต้องคือ?

  1. เขียน prompt ให้ย้ำว่าต้องพิมพ์ APPROVE/REJECT ตัวใหญ่บรรทัดสุดท้าย แล้วใช้ regex เดิม
  2. เปลี่ยนเป็น decision tree ตามยอดเงินโดยไม่ใช้โมเดล
  3. แปะนโยบายการเบิกทั้งหมดลงใน prompt
  4. ให้ agent เรียก tool submit_decision ที่มี field decision เป็น enum approve/reject
ดูเฉลย

D ให้ schema บังคับโครงสร้าง A ยังคง parse ข้อความอิสระ C ไม่ได้บังคับโครงสร้างเลย B ตัดการตัดสินใจของโมเดลทิ้ง

Checkpoint 4

ทีม IT อยากให้ agent ค้น Confluence, query Postgres และโพสต์ลง Slack ได้เองตามต้องการ โดยไม่อยากเขียนและดูแลโค้ดเรียกแต่ละระบบเอง ควรใช้อะไร?

  1. เขียน flowchart ตายตัวว่าคำถามแบบไหนไประบบไหน
  2. เขียน loop เองบน Client SDK แล้วทำ handler ทีละระบบ
  3. ดึงเนื้อหาทุกระบบมาใส่ system prompt ทุกเช้า
  4. MCP server ของแต่ละระบบ
ดูเฉลย

D MCP ให้ protocol เดียวและโมเดลยังเลือกเรียกเอง B คือภาระดูแลที่ทีมอยากหลีก C ข้อมูลเก่า ไม่ scale และโพสต์ Slack ไม่ได้ A ตัดการตัดสินใจอิสระของ agent

4. เลือกขนาดของขั้น processing

โมเดลในขั้น processing คือตัวที่กินค่าใช้จ่ายและ latency มากที่สุด การเลือกโมเดลจึงเป็นการตัดสินใจเชิงสถาปัตยกรรม ไม่ใช่รายละเอียดปลีกย่อย

  1. เริ่มจากโมเดล Haiku ที่เร็วและถูก
  2. benchmark กับ input จริง ไม่ใช่ตัวอย่างที่แต่งขึ้น
  3. ขยับขึ้นไปโมเดลที่แรงกว่า เฉพาะจุด ที่ผลทดสอบชี้ว่ามีช่องว่าง

การจัดโมเดลใหญ่เกินจำเป็นถือเป็น ความผิดพลาดในการออกแบบ ไม่ใช่ "ค่าเผื่อที่ปลอดภัย" ส่วนการสุ่มสลับโมเดล หรือเอา classifier แยกมาแทน Claude ทั้งหมด ก็ไม่ตอบโจทย์ (รายละเอียด trade-off ของโมเดลอยู่ในบท 2.1)

สรุปสั้นๆ

Haiku ก่อน → benchmark ด้วยข้อมูลจริง → ส่งเฉพาะเคสยากขึ้นไปโมเดลใหญ่

Checkpoint 5

บริษัทประกันต้องอ่านใบเคลมวันละหลายพันใบ มีเพดานงบต่อเดือน เคสส่วนใหญ่ตรงไปตรงมา มีบางส่วนกำกวม ควรออกแบบขั้น processing ยังไง?

  1. ส่งทุกใบไปโมเดลใหญ่สุดเพื่อความปลอดภัย
  2. ใช้ classifier ธรรมดาแทน Claude ทั้งหมด
  3. สุ่มส่งครึ่งหนึ่งไป Haiku อีกครึ่งไปโมเดลใหญ่
  4. เริ่มจาก Haiku, benchmark กับใบเคลมจริง แล้วส่งเฉพาะเคสที่ Haiku ทำไม่ได้ขึ้นไปโมเดลที่แรงกว่า
ดูเฉลย

D A ไม่สนเพดานงบ C ไม่มีหลักการ คุณภาพคาดเดาไม่ได้ B เสียความสามารถในการตีความเคสกำกวม

  1. ใช้ classifier ภายนอกตัวเดียว ตัด LLM ออก
  2. ใช้โมเดล Opus ตั้ง effort สูงสุดตั้งแต่วันแรก

5. Feedback loop ที่แก้ทิศทางระหว่างรัน

Feedback เข้าสู่การรันได้ 3 ระดับ:

ระดับ 1: Tool result ที่ตรวจได้

ออกแบบ tool ให้รายงาน ข้อเท็จจริงที่ตรวจได้ เช่น ผลเทสต์ ผ่าน/ไม่ผ่าน, error จาก validator, schema ไม่ตรงตรงไหน ถ้า tool ตอบแค่ "done" โมเดลก็ไม่มีอะไรให้เทียบเพื่อแก้ตัว

ระดับ 2: Hooks

Hook คือโค้ดที่รัน ทุกครั้ง ที่มี tool call ตรงเงื่อนไข ไม่ว่าโมเดลจะคิดอะไร ใน Agent SDK:

  • PreToolUse รันก่อน tool ทำงาน ดักจับ แก้ หรือบล็อกการเรียกได้
  • PostToolUse รันหลัง tool ทำงานแล้ว
  • แต่ละ HookMatcher จับคู่ pattern (เช่น "Bash" หรือ "Write|Edit") กับรายการ callback และ timeout (ไม่ใส่ก็ได้)
async def audit(input_data, tool_use_id, context):
    print("edited:", input_data.get("tool_name"))
    return {}

options = ClaudeAgentOptions(hooks={
    "PreToolUse": [
        HookMatcher(matcher="Bash", hooks=[check_command], timeout=120),
        HookMatcher(hooks=[log_all]),          # ไม่มี matcher = ทุก tool
    ],
    "PostToolUse": [
        HookMatcher(matcher="Edit|Write", hooks=[audit]),
    ],
})

Matcher ที่ไม่ระบุ pattern จะครอบทุก tool และใช้ timeout ค่าเริ่มต้นของ event นั้น

ระดับ 3: Graded outcomes (Managed Agents)

ส่ง event user.define_outcome พร้อม:

  • description ผลงานที่ต้องการ
  • rubric เกณฑ์ตรวจ (เช่น {"type": "file", "file_id": ...})
  • max_iterations ไม่บังคับใส่ ค่าเริ่มต้น 3 สูงสุด 20
{
  "type": "user.define_outcome",
  "description": "สร้างรายงานยอดขายรายไตรมาสเป็น .xlsx",
  "rubric": {"type": "file", "file_id": "file_..."},
  "max_iterations": 4
}

Harness จะตั้ง grader แยก ที่ตรวจผลงานเทียบ rubric ใน context window ของตัวเอง แล้วส่ง feedback กลับให้ agent ทำรอบถัดไป grader ให้คะแนนแต่ละเกณฑ์แยกกัน เกณฑ์ที่เจาะจงและตรวจได้จึงให้ผลชัดกว่าเกณฑ์ลอยๆ นี่ก็คือ pattern evaluator-optimizer ที่ฝังมาใน harness

ผลของ outcomeเกิดอะไรต่อ
satisfiedsession เข้าสู่ idle
needs_revisionagent เริ่มรอบใหม่พร้อม feedback ของ grader
max_iterations_reachedมี turn สุดท้ายเพื่อรับทราบหนึ่งรอบ แล้ว idle โดยไม่ตรวจอีก
failedsession idle เพราะ rubric ใช้กับผลงานนั้นไม่ได้
interruptedsession ถูกขัดจังหวะระหว่างที่ outcome ยัง active

ลองกับงานตัวเอง: ใน agent ที่คุณเคยสร้าง มีการตรวจไหนบ้างที่พึ่งพาให้โมเดล "จำคำสั่งได้" และอันไหนย้ายไปเป็น tool result, hook หรือเกณฑ์ใน rubric ได้

เข้าใจผิดบ่อย

"เขียนคำสั่งใน system prompt ไว้ก็พอ" ไม่ใช่ ในการรันยาวๆ คำสั่งไม่รับประกันพฤติกรรม แต่ hook รันทุกครั้งที่ match

"ให้ agent ตัวหลักตรวจงานตัวเอง" ไม่ใช่ harness ใช้ grader แยกใน context ของตัวเอง เพื่อไม่ให้เป็นการให้คะแนนตัวเอง

สรุปสั้นๆ

Tool result บอกข้อเท็จจริง, hook บังคับทุกครั้ง, graded outcome ให้ grader แยกตรวจเทียบ rubric และวนแก้ไม่เกิน max_iterations

Checkpoint 7

ใน Managed Agents เมื่อกำหนด outcome ไว้แล้ว ใครเป็นคนตรวจไฟล์ผลงานเทียบกับ rubric?

  1. Hook PostToolUse ที่ตรวจทุก tool call
  2. Agent ตัวหลักอ่านงานตัวเองอีกรอบ
  3. แอปของเรา parse ข้อความสุดท้ายแล้วแปลงเป็น tool result
  4. Grader ที่ harness ตั้งขึ้น ทำงานใน context window แยก
ดูเฉลย

D A ทำงานระดับ tool call ไม่ใช่ผลงานทั้งชิ้น B คือให้คะแนนตัวเอง C ไม่ใช่กลไกของ outcome

Checkpoint 8

อยากจำกัดให้ agent แก้งานตาม feedback ของ grader ได้ไม่เกิน 6 รอบ ต้องตั้ง field ไหนใน user.define_outcome?

  1. max_turns
  2. max_tokens
  3. max_retries
  4. max_iterations
ดูเฉลย

D max_iterations (ค่าเริ่มต้น 3 สูงสุด 20) ตัวอื่นไม่ใช่ field ของ outcome

Checkpoint 9

ฝ่าย security ต้องการ log ทุกครั้งที่ agent แก้หรือสร้างไฟล์ โดยไม่หยุดการทำงานอิสระของ agent ควรทำยังไง?

  1. ให้คนกดยืนยันก่อนทุกการแก้ไข
  2. เขียนใน system prompt ว่า "ทุกครั้งที่แก้ไฟล์ให้รายงาน"
  3. รัน cron ทุก 5 นาทีเพื่อดูว่าไฟล์ไหนเปลี่ยน
  4. ลงทะเบียน hook PostToolUse ที่ match Edit|Write
ดูเฉลย

D Hook รันทุกครั้งที่ match B ขึ้นกับว่าโมเดลจะทำตามไหม C เดาและพลาดการเปลี่ยนแปลงได้ A เป็น approval gate ไม่ใช่ audit log และทำลายความอิสระ
