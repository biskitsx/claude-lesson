3.8 Progressive discovery vs. monolithic context: tool search and when to use it

ต้นฉบับ: CertSafari 3.8

อ่านจบแล้วควรทำได้
  • อธิบายได้ว่าการโหลด tool definition ทั้งหมดตั้งแต่แรก (monolithic) เสียอะไรบ้าง ทั้ง token และความแม่นในการเลือก tool
  • เปิดใช้ tool search ใน API ได้ และส่ง request รอบถัดไปให้ถูกกติกา
  • ตั้งค่า ENABLE_TOOL_SEARCH ใน Agent SDK ได้ทั้ง 5 แบบ และรู้ว่าแต่ละค่าทำอะไร
  • เลือกได้ระหว่างโหลดทั้งหมด, tool search, ผสมกับ non-deferred, prompt caching หรือ Agent Skills
แนวคิดหลัก: เก็บแค่ "ป้ายบอกทาง" ไว้ใน context

Progressive discovery คือเก็บแค่ทางเข้าเบาๆ ไว้ใน context เช่น tool สำหรับค้นหา หรือชื่อกับคำอธิบายของ Skill แล้วค่อยโหลดของเต็มเมื่อ request นั้นต้องใช้จริง ตรงข้ามกับ monolithic ที่ยัดทุกอย่างเข้าไปทุก request เหมือนแบกคู่มือทุกเล่มติดตัวไปทุกที่ แทนที่จะพกแค่สารบัญ

1. ราคาของการโหลด tool ทั้งก้อน

  • ตั้งค่าหลาย MCP server พร้อมกัน (เช่น GitHub, Slack, Sentry, Grafana, Splunk) อาจกิน ราว 55k token ไปกับนิยาม tool ก่อนจะเริ่มทำงานอะไรเลย เอกสาร Agent SDK ประเมินว่า tool 50 ตัวใช้ราว 10–20K token
  • ความแม่นในการเลือก tool เริ่มตกเมื่อโหลดพร้อมกันราว 30–50 ตัว การเพิ่ม server ใหม่จึงทำให้ agent เลือก tool ผิดได้ ทั้งที่ไม่มี tool ตัวไหนถูกแก้เลย
  • Context rot: ยิ่ง token เยอะ ความแม่นและ recall ยิ่งลด context window ที่ใหญ่ขึ้นแค่ให้ ที่ มากขึ้น แต่ไม่ได้แก้ปัญหาเลือก tool ผิด

นึกภาพพนักงานใหม่ที่ถูกยื่นเมนูเครื่องมือ 200 อย่างให้ดูพร้อมกัน ต่อให้โต๊ะใหญ่พอวางได้หมด ก็ยังหยิบผิดอยู่ดี

สรุปสั้นๆ

โหลด tool เยอะ = เสีย token ก่อนเริ่มงาน และเลือก tool ผิดมากขึ้นตั้งแต่ราว 30–50 ตัว window ใหญ่ขึ้นไม่ช่วยเรื่องหลัง

Checkpoint 1

Agent DevOps ต่อ 6 MCP server รวมนิยาม tool ราว 60k token ตั้งแต่เพิ่ม server ล่าสุด agent เริ่มเรียก tool ผิดตัวบ่อย หัวหน้าทีมเสนอให้ย้ายไปใช้โมเดลที่ context window ใหญ่ขึ้น ข้อเสนอนี้แก้ปัญหาไหม?

  1. แก้ได้ เพราะ tool ทั้งหมดจะมีที่อยู่ใน context เหลือเฟือ
  2. ไม่แก้ เพราะ tool ชุดใหญ่ชุดเดิมยังถูกโหลดพร้อมกัน ความแม่นในการเลือกจึงยังตกเหมือนเดิม
  3. แก้ได้บางส่วน เพราะ window ใหญ่ทำให้ context rot หายไป
  4. ไม่แก้ เพราะโมเดลที่ window ใหญ่ไม่รองรับ MCP
ดูเฉลย

B ปัญหาคือจำนวน tool ที่โมเดลต้องเลือกพร้อมกัน ไม่ใช่ที่ว่าง window ใหญ่ขึ้นไม่ได้ลดจำนวน tool และไม่ได้ทำให้ context rot หาย

Checkpoint 2

ตามแนวทางของ Anthropic ความแม่นในการเลือก tool มักเริ่มตกเมื่อโหลด tool พร้อมกันประมาณกี่ตัว?

  1. 30–50 ตัว
  2. 5–10 ตัว
  3. 200–300 ตัว
  4. มากกว่า 10,000 ตัว
ดูเฉลย

A ราว 30–50 ตัวคือช่วงที่การเลือกเริ่มพลาด ส่วน 10,000 คือเพดานจำนวน tool ที่ SDK รองรับในแค็ตตาล็อก

2. Tool search ทำงานยังไง

Tool search ใน API แทนแค็ตตาล็อกทั้งก้อนด้วยขั้นค้นหา ปกติลดพื้นที่ของนิยาม tool ได้ มากกว่า 85% เพราะโหลดเฉพาะ 3–5 tool ที่ request นั้นต้องใช้

VariantClaude เขียนอะไร
tool_search_tool_regex_20251119regex pattern
tool_search_tool_bm25_20251119query เป็นภาษาธรรมชาติ

ทั้งสองแบบค้นจาก ชื่อ tool, คำอธิบาย, ชื่อ argument และคำอธิบาย argument

เปิดใช้งาน

ใส่ variant ของ search tool ลงใน tools แล้วตั้ง defer_loading: true ให้ tool ที่ไม่อยากให้เข้า context ตั้งแต่แรก

"tools": [
  {"type": "tool_search_tool_bm25_20251119", "name": "tool_search_tool_bm25"},
  {"name": "get_ticket", "description": "...", "input_schema": {...}},
  {"name": "export_audit_log", "description": "...", "input_schema": {...},
   "defer_loading": true}
]

เกิดอะไรขึ้นระหว่างรัน

  1. ตอนแรก context มีแค่ search tool กับ tool ที่ไม่ได้ defer
  2. Claude เรียก search ซึ่ง รันฝั่ง server แล้วคืนผลเป็น block tool_reference (ค่าเริ่มต้น 5 รายการ ปรับ limit ได้ตั้งแต่ 1 ถึง 10,000)
  3. API ขยาย reference เหล่านั้นเป็นนิยามเต็มให้เอง
  4. Claude เรียก tool ที่เพิ่งค้นเจอ แล้วโค้ดของเรารันและส่งผลกลับ

กติกาของบทสนทนา

  • ส่ง content ของ assistant กลับไป แบบไม่แก้ รวมถึง block server_tool_use และ tool_search_tool_result
  • ห้ามส่ง tool_result ให้ ID ที่ขึ้นต้นด้วย srvtoolu_ เพราะเป็น server tool API จะปฏิเสธ
  • tool ที่ค้นเจอแล้วเรียก ให้ส่ง tool_result ปกติ
  • ถ้าค้นไม่เจอ จะได้ array tool_references ว่าง ไม่ใช่ error
  • tool ที่ค้นเจอแล้วยังใช้ได้ใน turn ต่อๆ ไป
  • tool ที่ defer ไม่อยู่ใน prefix ของ system prompt ดังนั้น prompt caching ยังทำงานได้ปกติ
  • ต้องมี tool ที่ไม่ defer อย่างน้อยหนึ่งตัว (ปกติคือ search tool) และ ห้าม defer ตัว search tool เอง
เข้าใจผิดบ่อย

"ค้นเจอแล้ว ก็ตัด tool ที่ defer ออกจาก tools ใน request ถัดไปได้" ไม่ได้ tool ที่ defer ยังต้องส่งไปใน array tools ทุก request defer_loading คุมแค่ว่าอะไรเข้า context ไม่ได้คุมว่าอะไรถูกส่งไป

สรุปสั้นๆ

เพิ่ม search tool + defer_loading: true ให้หาง search รันฝั่ง server คืน tool_reference ส่ง content เดิมกลับไม่แก้ ไม่ตอบ srvtoolu_ และส่ง tools ครบทุกครั้ง

Checkpoint 3

property ไหนใน tool definition ที่ทำให้ tool นั้นไม่เข้า context จนกว่าจะถูกค้นเจอ?

  1. cache_control
  2. defer_loading
  3. strict
  4. lazy_load
ดูเฉลย

B cache_control เกี่ยวกับ prompt caching, strict เกี่ยวกับการบังคับ schema ส่วน lazy_load ไม่มีอยู่จริง

Checkpoint 4

ใน turn ที่แล้ว Claude เรียก tool search (ID srvtoolu_01A) ค้นเจอ refund_payment แล้วเรียก refund_payment (ID toolu_01B) โค้ดของคุณรัน refund เสร็จแล้ว request ถัดไปต้องทำยังไง?

  1. ส่ง tool_result ทั้งให้ srvtoolu_01A และ toolu_01B
  2. ส่ง content ของ assistant กลับแบบไม่แก้, ส่ง tool_result ให้ toolu_01B เท่านั้น และส่ง tools ครบรวม tool ที่ defer
  3. ตัด block server_tool_use ออกเพื่อประหยัด token แล้วส่ง tool_result ให้ toolu_01B
  4. ส่ง tools เหลือแค่ search tool กับ refund_payment เพราะตัวอื่นไม่ได้ใช้
ดูเฉลย

B A ผิดเพราะ API ปฏิเสธ result ของ srvtoolu_ C ผิดเพราะต้องส่ง content เดิมครบ D ผิดเพราะต้องส่ง tool ที่ defer ไว้ทุกครั้ง

3. ENABLE_TOOL_SEARCH ใน Agent SDK

ใน Agent SDK ตั้งผ่าน option env:

options = ClaudeAgentOptions(
    env={"ENABLE_TOOL_SEARCH": "auto:5"},   # เปิดเมื่อนิยามที่ defer ได้ถึง 5% ของ window
)
ค่าพฤติกรรม
(ไม่ตั้ง)เปิด search และ defer นิยาม แต่จะถอยไปโหลดทั้งหมดตั้งแต่แรกถ้าใช้โมเดลรุ่นเก่า, ตั้ง ANTHROPIC_BASE_URL ที่ไม่ใช่ first-party หรือใช้ Microsoft Foundry บน Azure
trueบังคับเปิด search แม้ base URL ไม่ใช่ first-party ถ้า proxy ไม่รองรับ tool_reference request จะล้ม
autoเปิดเฉพาะเมื่อนิยามที่ defer ได้รวมแล้วถึง 10% ของ context window ถ้าไม่ถึงก็โหลดทั้งหมดตั้งแต่แรก
auto:Nเหมือน auto แต่กำหนดเกณฑ์เอง เช่น auto:5 = 5%
falseปิด โหลดนิยามทั้งหมดทุก turn
  • บน Opus 4.5, Sonnet 4.5, Haiku 4.5 และรุ่นหลังจากนั้น search เปิดเป็นค่าเริ่มต้น
  • SDK รองรับแค็ตตาล็อกได้ถึง 10,000 tool และคืน 5 อันดับแรก ต่อการค้นหนึ่งครั้งเป็นค่าเริ่มต้น
เข้าใจผิดบ่อย

"ตั้ง auto แล้วจะ defer ให้เสมอ" ไม่ใช่ ถ้านิยามรวมยังไม่ถึงเกณฑ์ (10% หรือ N%) ทุก tool จะถูกโหลดตั้งแต่แรกเหมือนปิด search

สรุปสั้นๆ

ไม่ตั้ง = เปิดแต่ถอยได้, true = บังคับเปิด (เสี่ยงพังบน proxy), auto/auto:N = เปิดเมื่อถึงเกณฑ์, false = ปิด

Checkpoint 5 (จับคู่)

จับคู่สถานการณ์กับค่า ENABLE_TOOL_SEARCH (ไม่ตั้ง / true / auto / auto:3 / false):

  1. ทีมใช้ LLM gateway ภายในเป็น base URL และยืนยันแล้วว่า gateway ส่งต่อ tool_reference ได้ อยากให้ search ทำงานแน่ๆ
  2. อยากให้ search เปิดก็ต่อเมื่อนิยามที่ defer ได้ใหญ่ถึง 3% ของ window
  3. อยากให้โหลดทุก tool ทุก turn เสมอเพื่อ debug
  4. ใช้ API ของ Anthropic ตรงกับ Sonnet 4.5 และพอใจกับพฤติกรรมมาตรฐาน
  5. อยากให้ search ทำงานเมื่อนิยามถึงเกณฑ์มาตรฐาน 10%
ดูเฉลย

1-true, 2-auto:3, 3-false, 4-ไม่ตั้ง, 5-auto ข้อ 1 ต้องบังคับเพราะ base URL ไม่ใช่ first-party (ค่าเริ่มต้นจะถอยไปโหลดทั้งหมด) และใช้ได้เพราะ gateway รองรับ tool_reference

4. เลือกกลยุทธ์ให้ตรงกับชุด tool

Tool search แลก latency เพิ่มหนึ่งรอบค้นหา กับ context พื้นฐานที่เล็กลง โดยทั่วไปคุ้มเมื่อมีราว 20 tool ขึ้นไป และส่วนใหญ่ไม่ได้ใช้ใน turn นั้นๆ

สถานการณ์กลยุทธ์
tool ไม่กี่ตัว และใช้เกือบทุกตัวในเกือบทุก requestโหลดทั้งหมดตั้งแต่แรก
ราว 20+ tool ส่วนใหญ่ว่างในแต่ละ turntool search + defer_loading กับหางยาว
แค็ตตาล็อกใหญ่ แต่มีไม่กี่ตัวที่ใช้หนักtool search โดยเก็บ 3–5 ตัวที่ใช้บ่อยสุดไว้แบบไม่ defer
ชุด tool ใหญ่ที่คงที่ ใช้ซ้ำใน request จำนวนมากprompt caching (ใช้เดี่ยวๆ หรือคู่กับ search)
  • Prompt caching ลด ค่าใช้จ่าย ของนิยามที่ส่งซ้ำ แต่ token ยังอยู่ใน context ครบ จึงไม่แก้เรื่องเลือก tool ผิดหรือ context rot
  • นั่งย่อคำอธิบาย tool ด้วยมือ ช่วยได้น้อย และอาจทำให้ search จับคู่แย่ลง เพราะ search ใช้คำอธิบายเป็นข้อมูลค้น
เข้าใจผิดบ่อย

"เปิด prompt caching แล้วปัญหา context บวมก็หาย" ไม่ใช่ caching ทำให้ถูกลง แต่นิยามยังกินที่และยังทำให้เลือก tool พลาดเท่าเดิม

"Defer ทุกตัวดีที่สุดเสมอ" ไม่ใช่ tool ที่ใช้ตลอดควรโหลดไว้ ไม่อย่างนั้นต้องเสียรอบค้นหาทุกครั้งโดยไม่ได้อะไร

สรุปสั้นๆ

ชุดเล็กใช้บ่อย = โหลดหมด, 20+ ตัวที่ส่วนใหญ่ว่าง = search, แค็ตตาล็อกใหญ่มีตัวเด่น = search + เก็บตัวเด่นไว้, ชุดใหญ่คงที่ = caching (ลดเงิน ไม่ลด token)

Checkpoint 6 (จับคู่)

จับคู่ชุด tool กับกลยุทธ์ (a) โหลดทั้งหมด (b) search + defer หางยาว (c) search + เก็บตัวที่ใช้หนักไว้แบบไม่ defer (d) prompt caching:

  1. บอตร้านกาแฟมี 5 tool (เมนู, สั่ง, ชำระเงิน, สถานะ, ยกเลิก) ใช้ครบแทบทุกออเดอร์
  2. ผู้ช่วยฝ่ายขายมี 45 tool ใน CRM แต่ละคำขอใช้แค่ 1–2 ตัว ไม่มีตัวไหนเด่นเป็นพิเศษ
  3. แพลตฟอร์มคลาวด์มี 500 tool แต่ 90% ของคำขอใช้ list_instances, get_logs, restart_service
  4. ระบบ batch ส่ง request หลายแสนครั้งด้วยชุด tool ใหญ่ชุดเดิมทุกครั้ง อยากลดค่าใช้จ่ายจากนิยามที่ซ้ำ
ดูเฉลย

1-a, 2-b, 3-c, 4-d ข้อ 4 เป้าหมายคือลดค่าใช้จ่ายจากส่วนที่ซ้ำ ซึ่งเป็นงานของ caching (จะใช้คู่กับ search ด้วยก็ได้)

Checkpoint 7

แอปจดบันทึกสุขภาพมี tool 8 ตัว นิยามรวมราว 1,500 token และเกือบทุก request ใช้หลายตัวในนี้ ควรตั้งค่ายังไง?

  1. โหลดทั้ง 8 ตัวตั้งแต่แรก
  2. เปิด tool search และ defer ทั้ง 8 ตัว
  3. เปิด tool search แบบ regex และ defer 5 ตัว
  4. ย้าย tool ทั้งหมดไปเป็น Agent Skills
ดูเฉลย

A ไม่มีปัญหา context ให้แก้ การเพิ่มรอบค้นหามีแต่เพิ่ม latency

Checkpoint 8

Agent ปฏิบัติการต่อ MCP server 5 ตัว รวมนิยามราว 55k token และเริ่มเลือก tool ผิด ข้อไหนแก้ตรงจุดที่สุด?

  1. เปิด tool search ให้นิยามส่วนใหญ่ถูก defer
  2. ย้ายไปโมเดลที่มี context window ใหญ่กว่า
  3. ให้ทีมเขียนคำอธิบาย tool ใหม่ให้สั้นลงครึ่งหนึ่ง
  4. เปิด prompt caching กับ tools ทั้งหมด
ดูเฉลย

A เป็นทางเดียวที่เอานิยามออกจาก context จริง B, C และ D ยังทิ้ง tool ชุดใหญ่ไว้ใน context เท่าเดิม (C ยังอาจทำให้ search แย่ลงอีก)

5. Agent Skills และการโหลดแบบผสม

Tool search defer schema ของ tool แต่ Agent Skills defer ความรู้วิธีทำงาน เช่น workflow, schema ของข้อมูล, สคริปต์ โหลดเป็น 3 ระดับ:

  1. Metadata (ชื่อ + คำอธิบาย) โหลดตอนเริ่ม ราว 100 token ต่อ Skill
  2. เนื้อหา SKILL.md โหลดเมื่อ Skill ถูก trigger
  3. ไฟล์ที่แนบมา โหลดเมื่อ Claude อ่านไฟล์นั้นจริง และถ้าเป็นสคริปต์ จะมีแค่ output ที่เข้า context ไม่ใช่ตัวโค้ด
  • Skills ต้องมี code execution environment ส่วน tool search ต้องใช้โมเดลที่รองรับ (Claude Opus 4.1 และรุ่นก่อนหน้าไม่รองรับ)
  • แบบผสม: Claude Code โหลด CLAUDE.md ไว้ตั้งแต่แรก แล้วใช้ glob กับ grep หาไฟล์อื่นตอนต้องใช้ การสำรวจแบบนี้ช้ากว่าการมีข้อมูลเตรียมไว้ และอาจเปลือง context ไปกับทางตัน
สรุปสั้นๆ

Tool search = defer schema, Skills = defer ขั้นตอน/ความรู้ (100 token ต่อ Skill ตอนเริ่ม) ของที่ใช้ตลอดโหลดไว้ ของที่เหลือค่อยหา

Checkpoint 9

Agent ฝ่ายบัญชีมีขั้นตอนปิดงบเฉพาะกรณีราว 80 แบบ (แต่ละแบบมีขั้นตอนหลายหน้าและสคริปต์ประกอบ) แต่ละคำขอใช้แค่ 1–2 แบบ ตอนนี้ใส่ทุกขั้นตอนไว้ใน system prompt จนบวม ควรทำยังไง?

  1. แพ็กแต่ละขั้นตอนเป็น Agent Skill
  2. เปิด tool search แล้วใส่ defer_loading
  3. เปิด prompt caching กับ system prompt
  4. ย้ายไปโมเดลที่ window ใหญ่กว่า
ดูเฉลย

A สิ่งที่บวมคือ "วิธีทำงาน" ไม่ใช่ schema ของ tool Skills โหลดแค่ metadata ไว้ก่อนแล้วค่อยดึงเนื้อหาเมื่อใช้ ส่วน C กับ D ยังทิ้ง token ไว้ใน context ครบ
