2.3 Few-shot and chain-of-thought prompting for Claude

ต้นฉบับ: CertSafari 2.3

อ่านจบแล้วควรทำได้
  • เลือกได้ว่างานไหนพอแค่ zero-shot งานไหนต้องเพิ่มเป็น one-shot หรือ few-shot และรู้ว่าทำไมต้องขยับทีละขั้น
  • ออกแบบชุดตัวอย่าง (examples) ที่ ตรงงาน หลากหลาย และมีโครงสร้าง ไม่ให้ Claude ไปจำรูปแบบที่เราไม่ได้ตั้งใจสอน
  • แยก chain-of-thought (CoT) 3 แบบ: basic, guided, structured และรู้ว่าแบบไหนเหมาะกับ pipeline
  • ตัดสินใจได้ว่าเมื่อไหร่ใช้ extended thinking เมื่อไหร่ต้องเขียน CoT เองใน tag และรู้ต้นทุนของ thinking
  • จัดวางเอกสารยาว ตัวอย่าง และคำถาม ให้ถูกลำดับใน prompt
แนวคิดหลัก: บอก → ให้ดู → ให้เห็นวิธีคิด

Instruction คือการ บอก ว่าอยากได้อะไร Example คือการ ให้ดู ว่าหน้าตา output ควรเป็นแบบไหน ส่วน chain-of-thought คือการ ให้เห็นเส้นทางความคิด ก่อนได้คำตอบ หลักคือเพิ่มเครื่องมือถัดไปก็ต่อเมื่อเครื่องมือก่อนหน้าเอาไม่อยู่แล้วเท่านั้น ไม่ใช่ใส่ทุกอย่างไว้ตั้งแต่แรก

1. Zero-shot, one-shot และ few-shot

ลองนึกถึงการสอนเด็กฝึกงานใหม่ให้กรอกฟอร์ม ถ้างานง่าย แค่อธิบายเป็นคำพูดก็พอ ถ้าอธิบายแล้วยังทำออกมาไม่ตรง ก็ยื่นตัวอย่างที่กรอกแล้วให้ดูหนึ่งใบ และถ้ายังพลาดกับเคสแปลกๆ ก็ให้ดูหลายใบที่ต่างกัน prompt ก็ทำงานแบบเดียวกัน

  • Zero-shot: มีแค่คำสั่ง ใช้ได้ดีเมื่อเราอธิบายรูปแบบ output และข้อจำกัดเป็นคำพูดได้ครบ เคล็ดลับคือ ใส่เหตุผลของแต่ละกฎ ด้วย เช่น "ตอบไม่เกิน 2 บรรทัด เพราะจะแสดงบน notification มือถือ" พอ Claude รู้ว่ากฎมีไว้ทำไม ก็จะใช้หลักเดียวกันกับเคสที่กฎไม่ได้เขียนไว้ได้
  • One-shot: คำสั่ง + ตัวอย่าง 1 ชิ้น เหมาะเมื่อรูปแบบ น้ำเสียง หรือสไตล์ "ให้ดูง่ายกว่าอธิบาย"
  • Few-shot (หรือ multishot): คำสั่ง + ตัวอย่างหลายชิ้นที่ต่างกัน ใช้เมื่อให้ดูชิ้นเดียวแล้วผลยังไม่นิ่ง หรืองานมี pattern ละเอียดและ edge case เยอะ จำนวนที่แนะนำคือ ประมาณ 3–5 ตัวอย่างที่หลากหลาย
วิธีใน prompt มีอะไรใช้เมื่อ…
Zero-shotคำสั่งชัดเจน รูปแบบ output ข้อจำกัด และเหตุผลของแต่ละข้ออธิบาย output ได้ครบด้วยคำพูด
One-shotคำสั่ง + ตัวอย่าง 1 ชิ้นรูปแบบ/น้ำเสียง/สไตล์ ให้ดูง่ายกว่าเขียนบรรยาย
Few-shotคำสั่ง + ตัวอย่างหลายชิ้นที่ต่างกันตัวอย่างเดียวแล้วผลยังแกว่ง หรืองานมี pattern ซับซ้อน

ทำไมต้องขยับทีละขั้น? เพราะตัวอย่างทุกชิ้นทำให้ prompt ยาวขึ้น และ ทุกรายละเอียดในตัวอย่าง Claude อาจลอกตามได้หมด ใส่เกินความจำเป็นก็เท่ากับเพิ่มสิ่งที่อาจถูกลอกโดยไม่ตั้งใจ

ปัญหา "label เพี้ยน" แก้ด้วยตัวอย่าง ไม่ใช่ด้วยการให้อธิบาย

อาการที่เจอบ่อย: โมเดลจัดหมวดถูก แต่เขียน label ไม่เหมือนกัน รอบหนึ่งได้ Urgent อีกรอบได้ urgent! อีกรอบได้ ด่วนมาก นี่คือปัญหา รูปร่างของ output (format drift) ไม่ใช่ปัญหาการคิด การสั่งให้ Claude "อธิบายเหตุผลเป็นย่อหน้า" ไม่ได้ทำให้ label นิ่งขึ้นเลย ทางแก้ที่ได้ผลคือใส่ตัวอย่าง input → output หลายคู่ที่ใช้ label สะกดแบบเดียวกัน และห่อแต่ละคู่ด้วย tag

ส่วนการแปะตัวอย่างเดียวไว้ท้าย prompt แบบไม่มี tag ถือเป็นการแก้ที่อ่อนที่สุด เพราะ pattern น้อยเกินไปและ Claude แยกไม่ออกว่าอะไรคือตัวอย่าง อีกทางที่ผิดคือเพิ่ม temperature เพราะยิ่งเพิ่มความสุ่ม ผลยิ่งไม่นิ่ง

ตัวอย่างใช้กับรูปภาพได้ด้วย แต่ต้นฉบับเตือนว่า few-shot กับภาพ ไม่ได้ผลเสมอไป ต้องทดสอบกับเคสของเราเอง

    <output>severity: P1 | area: payment</output>

  </example>

เข้าใจผิดบ่อย

"label สะกดไม่ตรงกัน ให้โมเดลอธิบายเหตุผลก่อนตอบก็จะดีขึ้น" ไม่ใช่ การอธิบายเป็นร้อยแก้วไม่ได้เปลี่ยนรูปร่าง output ตัวที่แก้ได้คือ few-shot examples ที่มี tag

สรุปสั้นๆ

เริ่มที่ zero-shot (พร้อมเหตุผลของกฎ) แล้วค่อยเพิ่มตัวอย่างเมื่อจำเป็น ปัญหารูปแบบ/label ไม่นิ่ง แก้ด้วยตัวอย่าง 3–5 ชิ้นที่หลากหลายและห่อด้วย tag

Checkpoint 1

ระบบสกัดข้อมูลใบแจ้งหนี้ด้วย zero-shot ดึงยอดเงินถูกทุกครั้ง แต่ช่องสกุลเงินออกมาปนกันทั้ง THB, บาท, ฿ และ thb ทำให้ระบบปลายทางพัง ควรแก้อย่างไร?

  1. เพิ่มคำสั่ง "ให้อธิบายเหตุผลที่เลือกสกุลเงินเป็นย่อหน้าก่อนตอบ"
  2. ตัดคำสั่งเรื่องสกุลเงินออก ให้โมเดลเลือกรูปแบบเองอย่างอิสระ
  3. ใส่คู่ใบแจ้งหนี้ → output หลายคู่ที่หลากหลาย ใช้ THB เหมือนกันทุกคู่ และห่อแต่ละคู่ด้วย <example>
  4. ย้ายไปใช้โมเดลรุ่นใหญ่ขึ้นโดยไม่แตะ prompt
ดูเฉลย

C ปัญหาคือรูปร่าง output ไม่ใช่การคิด ตัวอย่างหลายชิ้นที่มี tag แสดงรูปแบบที่ต้องการชัดที่สุด A ไม่เปลี่ยนรูปร่าง B ยิ่งเปิดให้แกว่งมากขึ้น D ไม่ได้บอกโมเดลเลยว่ารูปแบบที่ถูกคือแบบไหน

Checkpoint 2

prompt แปลชื่อเมนูอาหารเป็นภาษาอังกฤษสำหรับร้านอาหาร ทีมต้องการ "สไตล์" แบบเฉพาะ: ชื่ออังกฤษสั้น ตามด้วยวงเล็บชื่อไทยแบบทับศัพท์ ซึ่งอธิบายด้วยคำพูดแล้วผลยังเพี้ยนบ้าง แต่ยังไม่มีเคสขอบที่ซับซ้อน ขั้นถัดไปที่เหมาะสมที่สุดคือ?

  1. ข้ามไปใส่ตัวอย่าง 20 ชิ้นทันทีเพื่อความชัวร์
  2. ลบคำสั่งทั้งหมดแล้วใช้แต่ตัวอย่าง
  3. เปิด extended thinking
  4. เพิ่มตัวอย่าง 1 ชิ้นที่แสดงสไตล์นั้น (one-shot) แล้ววัดผลก่อน
ดูเฉลย

D สไตล์ที่ "ให้ดูง่ายกว่าอธิบาย" คือกรณีของ one-shot ควรขยับทีละขั้น เพราะตัวอย่างทุกชิ้นเพิ่มความยาวและเพิ่มสิ่งที่อาจถูกลอก ถ้าชิ้นเดียวยังไม่นิ่งค่อยขยับเป็น few-shot

2. ออกแบบตัวอย่างให้ดี

Claude ดูตัวอย่าง ละเอียดทุกจุด รวมถึงจุดที่เราไม่ได้ตั้งใจสอน เช่น ความยาวเท่ากัน โครงประโยคเหมือนกัน หรือทุกชิ้นมีอารมณ์ไปทางเดียวกัน สิ่งที่เหมือนกันทั้งชุดจะกลายเป็น "pattern" ที่โมเดลเรียนไปด้วย ชุดตัวอย่างที่ดีต้องมี 3 คุณสมบัติ:

  • Relevant (ตรงงาน): หน้าตา input และ output เหมือนของจริงที่จะเจอ
  • Diverse (หลากหลาย): ครอบคลุม edge case และต่างกันพอที่จะไม่เกิด pattern บังเอิญ
  • Structured (มีโครงสร้าง): ตัวอย่างแต่ละชิ้นอยู่ใน <example> และทั้งชุดอยู่ใน <examples>

ชุดตัวอย่างที่ "เหมือนกันหมด" อันตรายยังไง

ถ้าตัวอย่างทุกชิ้นหน้าตาคล้ายกัน ระบบจะทำงานดีเฉพาะกับ input ที่หน้าตาแบบนั้น แล้วพังกับอย่างอื่น และ การเพิ่มตัวอย่างแบบเดิมเข้าไปอีกยิ่งตอกย้ำ pattern ผิด ทางแก้คือความครอบคลุม: ทุก label ต้องมีตัวแทน มีเคสก้ำกึ่งที่ยาก และมีความยาว/การใช้คำหลากหลาย ความหลากหลายสำคัญที่สุดกับหมวดที่ก้ำกึ่ง เพราะคำนิยามที่เขียนเป็นตัวหนังสืออย่างเดียวมักจับเส้นแบ่งไม่ได้

Tag สำคัญพอๆ กับเนื้อหา

ถ้าแปะตัวอย่างปนกับคำสั่งโดยไม่มี tag จะเกิดความสับสน 2 ทาง: Claude อาจเข้าใจว่าค่าเฉพาะในตัวอย่างเป็น ข้อบังคับ หรือกลับกัน เข้าใจว่ากฎบางข้อเป็นแค่ ข้อมูลตัวอย่าง สิ่งที่บอก Claude ว่า "นี่คือการสาธิต" คือ tag ไม่ใช่ตำแหน่งใน prompt ควรใช้ชื่อ tag เดิมทุก prompt เพื่อให้ผลคาดเดาได้

อีกข้อที่น่าสนใจ: ในงาน moderation การเปลี่ยนชุดตัวอย่างอย่างเดียว (ไม่แตะกฎ) ก็เปลี่ยนได้ว่าระบบจะปล่อยหรือบล็อกอะไร ตัวอย่างจึงเป็นเหมือน "นโยบาย" อีกชั้นหนึ่ง

<examples>
  <example><comment>ร้านนี้บริการดีมาก แนะนำเลย</comment><label>ALLOW</label></example>
  <example><comment>เดี๋ยวจะไปดักรอหน้าบ้านแก</comment><label>BLOCK</label></example>
  <example><comment>ดื่มน้ำมะนาวรักษามะเร็งได้ 100%</comment><label>BLOCK</label></example>
  <example><comment>ของมาช้าไปหน่อย แต่ใช้ดี</comment><label>ALLOW</label></example>
</examples>
เข้าใจผิดบ่อย

"classifier ไม่แม่น ก็เพิ่มจำนวนตัวอย่างเข้าไป เดี๋ยวก็ดีขึ้นเอง" ไม่จริง ถ้าตัวอย่างเพิ่มยังหน้าตาเหมือนเดิม จะยิ่งตอกย้ำลักษณะผิวเผินที่ชุดเดิมมีร่วมกัน สิ่งที่แก้ได้คือความหลากหลาย ไม่ใช่จำนวน

สรุปสั้นๆ

ตัวอย่างต้องตรงงาน หลากหลาย และอยู่ใน tag ถ้าทุกชิ้นหน้าตาเหมือนกัน Claude จะเรียนความเหมือนนั้นไปด้วย เพิ่มของเดิมไม่ช่วย ต้องเพิ่มความครอบคลุม

ลองเดาก่อน

ตัวจัดหมวดอีเมลมีตัวอย่าง 6 ชิ้น ทุกชิ้นเป็นอีเมลสั้น 1 บรรทัด และทุกชิ้นเป็นหมวด "สอบถามราคา" พอเจออีเมลยาวที่เป็นการร้องเรียน ระบบตอบผิดบ่อย ควรทำอะไร?

  1. แทนตัวอย่างบางส่วนด้วยอีเมลยาว อีเมลร้องเรียน และหมวดอื่นๆ ที่โครงสร้างต่างกัน
  2. เพิ่มตัวอย่างอีเมลสั้นหมวดสอบถามราคาอีก 10 ชิ้น
  3. ย้ายตัวอย่างไปไว้ล่างสุดของ prompt
ดูเฉลย

A ชุดเดิมสอนว่า "สั้น + สอบถามราคา" คือ pattern การเพิ่มแบบเดิมยิ่งตอกย้ำ และตำแหน่งไม่ใช่สิ่งที่บอกว่าเป็นตัวอย่าง ต้องเพิ่มความหลากหลาย

Checkpoint 3

prompt คัดกรองรีวิวโรงแรมมีกฎ 6 ข้อ และมีตัวอย่าง 5 คู่ (รีวิว + ผลลัพธ์) ที่หลากหลายและตรงงาน แต่ทั้งหมดเขียนสลับปนอยู่กับกฎโดยไม่มี tag เลย ความเสี่ยงหลักคืออะไร?

  1. ตัวอย่างไม่หลากหลายพอ
  2. prompt ยาวเกิน context window
  3. ต้องเปิด extended thinking ก่อน ตัวอย่างถึงจะได้ผล
  4. Claude อาจตีความค่าในตัวอย่างเป็นข้อบังคับ หรือตีความกฎเป็นแค่ข้อมูลตัวอย่าง
ดูเฉลย

D ชุดนี้ผ่านเรื่อง relevant และ diverse แล้ว แต่ขาด structure เมื่อไม่มี tag Claude แยกการสาธิตออกจากคำสั่งได้ไม่แน่นอน

3. Chain-of-thought สามรูปแบบ

Chain-of-thought (CoT) คือให้ Claude คิดเป็นขั้นๆ ก่อนตอบ ช่วยได้มากในงานที่คำตอบต้องอาศัย "งานระหว่างทาง" ซึ่งถ้าตอบรวดเดียวจะถูกบีบหรือข้ามไป เช่น วิเคราะห์หลายขั้น คณิตศาสตร์ หรือการชั่งน้ำหนักหลายปัจจัย

แบบเพิ่มอะไรใน promptได้อะไร
Basicวลีอย่าง "think step-by-step"Claude คิดก่อนตอบ แต่เลือกเองว่าจะคิดเรื่องอะไร
Guidedระบุขั้นการคิดเป็นลำดับมั่นใจว่าปัจจัยที่เราต้องการถูกพิจารณาครบ
StructuredGuided + tag แยกส่วนคิดกับส่วนคำตอบโค้ดตัดส่วนคิดทิ้งได้ และดึงคำตอบออกมาได้สะอาด

ตัวอย่างสั้นๆ ของทั้ง 3 แบบ ในงานเขียนข้อความเสนอโปรโมชันให้ลูกค้าบัตรสมาชิก:

ทำตามขั้น (1)-(3) ข้างบนใน <thinking></thinking>
แล้วใส่ข้อความสุดท้ายใน <output></output> เท่านั้น

แบบ structured คือแบบที่ใช้ใน moderation filter: ให้เหตุผลอยู่ใน <thinking> และคำตัดสินอยู่ใน <output> โค้ดจะ parse เฉพาะคำตัดสิน ไม่ต้องเดาว่าคำตอบอยู่ตรงไหนของข้อความยาว

ในข้อสอบ

Structured CoT สำคัญที่สุดใน pipeline ที่โค้ดต้องรู้แน่นอนว่าส่วนคิดจบตรงไหน และคำตอบเริ่มตรงไหน

สรุปสั้นๆ

Basic = บอกให้คิด, Guided = บอกว่าคิดเรื่องอะไรตามลำดับ, Structured = guided + tag แยกความคิดออกจากคำตอบ เพื่อให้โค้ดแยกได้

Checkpoint 4 (จับคู่)

จับคู่สิ่งที่ใส่ใน prompt กับรูปแบบ CoT:

  1. "ก่อนประเมินสินเชื่อ ให้ดูรายได้ก่อน แล้วดูภาระหนี้ แล้วค่อยสรุป"
  2. "ลองคิดทีละขั้นก่อนตอบ"
  3. "ทำขั้นรายได้ → หนี้ → สรุป ใน <thinking> แล้วใส่ APPROVE/REJECT ใน <output>"

A = Basic, B = Guided, C = Structured

ดูเฉลย

1-B, 2-A, 3-C ข้อ 1 ระบุขั้นการคิดตามลำดับ (guided) ข้อ 2 แค่บอกให้คิด (basic) ข้อ 3 มีทั้งขั้นและ tag แยกส่วน (structured)

4. Extended thinking กับ CoT ที่เขียนเอง

Extended thinking คือ CoT ที่มีมาในตัวโมเดล เหตุผลจะมาใน thinking block ก่อนข้อความคำตอบ ถ้ารุ่นที่ใช้รองรับ โดยทั่วไปควรเลือกใช้สิ่งนี้มากกว่าเขียน CoT เอง

  • Adaptive thinking (thinking={"type": "adaptive", ...}) ให้ Claude ตัดสินเองว่าจะคิดเมื่อไหร่และคิดลึกแค่ไหน
  • บน Claude Opus 4.6 ถึง 4.8 และ Sonnet 4.6 thinking ปิดอยู่จนกว่าเราจะเปิด adaptive thinking เอง ส่วน Claude Sonnet 5 เปิดไว้เป็นค่าเริ่มต้น
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    thinking={"type": "adaptive", "display": "summarized"},
    messages=[{"role": "user", "content": "ห.ร.ม. ของ 1071 กับ 462 คือเท่าไร"}],
)

Thinking block ไม่ใช่ความคิดดิบ

  • display: "summarized" ได้ สรุป ของ thinking กลับมา
  • display: "omitted" (ค่าเริ่มต้นในหลายรุ่น) ช่อง thinking จะ ว่างเปล่า
  • ไม่มีค่าไหนที่คืน chain of thought ดิบ ทั้งหมด ถ้าต้องการร่องรอยการคิดที่ตรวจสอบได้เต็มๆ ต้องสั่ง CoT ใน tag ให้เขียนออกมาในคำตอบเอง เพราะนั่นคือสิ่งที่ Claude เขียนจริง

เมื่อไหร่ยังต้องเขียน CoT เอง

  • ใช้ extended thinking ไม่ได้ เช่น บน Claude.ai แผนฟรี
  • มีคน (เช่น auditor, reviewer) ต้องอ่านเหตุผลฉบับเต็ม
  • และใช้ทั้งสองอย่างร่วมกันได้ ไม่ต้องเลือกอย่างเดียว

ต้นทุนของ thinking

  • Thinking token คิดเงินเป็น output token แม้ไม่ได้ถูกส่งกลับมาให้เห็น
  • นับรวมใน max_tokens
  • เพิ่ม latency

ปรับระดับการคิดรายรอบ (turn-level steering): วลีอย่าง "Please think hard before responding." ทำให้คิดมากขึ้น ส่วน "Answer directly without deliberating." ทำให้คิดน้อยลง agent harness อาจใช้แบบแรกในขั้นวางแผน และแบบหลังในขั้นยืนยันงานประจำ แต่ก่อนใช้งานจริงต้องวัด trigger rate, จำนวน token, latency และคุณภาพก่อนเสมอ

เข้าใจผิดบ่อย

"เปิด extended thinking แล้วได้ audit trail ครบ เพราะ thinking block คือเหตุผลดิบ" ไม่ใช่ thinking block มีอย่างมากก็แค่สรุป (หรือว่างเปล่าถ้า omitted) ถ้าต้องตรวจสอบเหตุผลฉบับเต็ม ใช้ CoT ใน tag

ในข้อสอบ

มี extended thinking และงานต้องคิดหลายขั้น → ใช้ extended thinking. ไม่มี หรือต้องให้คนอ่านเหตุผลเต็ม → ใช้ CoT ใน tag

สรุปสั้นๆ

Extended thinking เป็นตัวเลือกแรกเมื่อมี แต่ได้แค่สรุปหรือช่องว่าง คิดเงินเป็น output และกิน max_tokens ถ้าต้องการเหตุผลเต็มเพื่อ audit ให้ใช้ CoT ใน tag

Checkpoint 5 (เติมคำ)

ทีมเปิด adaptive thinking แล้วพบว่า field thinking กลับมาว่างทุกครั้ง อยากให้มีข้อความสรุปการคิดกลับมาด้วย ต้องตั้ง thinking={"type": "adaptive", "display": "____"} เป็นค่าใด?

  1. "omitted"
  2. "verbose"
  3. "summarized"
  4. "enabled"
ดูเฉลย

C summarized ให้สรุปกลับมา omitted คือสิ่งที่ทำให้ว่างอยู่ตอนนี้ และไม่มีค่าไหนคืนความคิดดิบ ถ้าต้องการเต็มๆ ใช้ CoT ใน tag

Checkpoint 6

ฝ่าย compliance ของธนาคารต้องเก็บเหตุผลฉบับเต็มของทุกการตัดสินใจอนุมัติวงเงิน เพื่อให้ผู้ตรวจสอบอ่านย้อนหลังได้ ทางเลือกไหนเหมาะที่สุด?

  1. เปิด extended thinking แบบ display: "omitted" แล้วเก็บ field thinking
  2. เปิด extended thinking แบบ display: "summarized" เพราะสรุปคือเหตุผลดิบที่ย่อแล้ว ถือว่าครบ
  3. สั่งให้เขียนเหตุผลตามขั้นที่กำหนดใน <thinking> และคำตัดสินใน <output> แล้วเก็บทั้งสองส่วน
  4. เพิ่ม max_tokens เพื่อให้ thinking block ยาวพอจะเป็นฉบับเต็ม
ดูเฉลย

C thinking block ไม่ใช่ความคิดดิบในทุกโหมด ร่องรอยที่ตรวจสอบได้เต็มคือ CoT ที่โมเดลเขียนในคำตอบเองผ่าน tag (structured CoT) และ max_tokens ไม่ได้เปลี่ยนว่า block คืนอะไร

5. วางเอกสารยาว ตัวอย่าง และคำถามตรงไหน

เรื่องการจัดวางสำคัญมากเมื่อ input ยาวราวๆ 20,000 token ขึ้นไป (การจัดการขีดจำกัด token ดูบทที่ 2.4) หลักมี 3 ข้อ:

  1. เอกสารยาวไว้บนสุด เหนือคำถาม คำสั่ง และตัวอย่าง วิธีนี้ทำให้ผลดีขึ้นในทุกรุ่นโมเดล
  2. ห่อเอกสารแต่ละชิ้นด้วย tag: <document> ที่มี <source> กับ <document_content> ข้างใน และรวมทุกชิ้นไว้ใน <documents> อย่าแปะข้อความดิบ
  3. ให้ quote ก่อนตอบ: สั่งให้ Claude ดึงข้อความที่เกี่ยวข้องออกมาใส่ tag ของมันเองก่อน แล้วค่อยทำงาน นี่คือ CoT แบบหนึ่งสำหรับเอกสารยาว ช่วยให้ความสนใจอยู่กับเนื้อหาที่เกี่ยวข้อง
<documents>
  <document>
    <source>policy_2025.pdf</source>
    <document_content>{{POLICY}}</document_content>
  </document>
  <document>
    <source>claims_log.csv</source>
    <document_content>{{CLAIMS}}</document_content>
  </document>
</documents>

[คำสั่ง + ตัวอย่าง]

ก่อนตอบ ให้ยกข้อความที่เกี่ยวข้องมาไว้ใน <quotes> ก่อน
คำถาม: เคลมรายการไหนบ้างที่ขัดกับนโยบาย

ถ้าคำตอบพลาดรายละเอียดที่ซ่อนอยู่กลางเอกสาร ทางแก้คือ วางเอกสารไว้บนสุด + quote ก่อน ไม่ใช่ตัดให้เหลือเอกสารชิ้นเดียว เพราะโครงสร้างหลายเอกสารมีไว้เพื่องานที่ต้องเทียบข้ามแหล่งอยู่แล้ว

เข้าใจผิดบ่อย

"เอาคำถามไว้บนสุด Claude จะได้รู้ก่อนว่าจะหาอะไรในเอกสาร" ผิดทิศ เอกสารยาวต้องอยู่บน คำถามอยู่ล่าง

สรุปสั้นๆ

เอกสารยาว (ใน tag) อยู่บนสุด → คำสั่งและตัวอย่าง → คำถามอยู่ท้าย และให้ quote ส่วนที่เกี่ยวข้องก่อนลงมือวิเคราะห์

Checkpoint 7

ทีมกฎหมายส่งรายงานตรวจสอบภายใน 4 ฉบับ รวมราว 50,000 token เข้าไปพร้อมคำสั่ง ตัวอย่าง 2 ชิ้น และคำถาม โดยตอนนี้วางคำถามไว้บนสุดแล้วตามด้วยเอกสารดิบ คำตอบมักพลาดข้อค้นพบที่อยู่กลางรายงาน ควรแก้อย่างไร?

  1. เพิ่มประโยค "อ่านทุกบรรทัดอย่างละเอียด" ในคำสั่ง แต่คงลำดับเดิมไว้
  2. ย้ายคำถามขึ้นไปทั้งบนสุดและท้ายสุดเพื่อย้ำ แต่คงเอกสารดิบไว้
  3. เพิ่มตัวอย่างอีก 10 ชิ้น
  4. ห่อรายงานแต่ละฉบับด้วย document tag ย้ายไว้บนสุด แล้วให้ quote ข้อค้นพบที่เกี่ยวข้องก่อนตอบ
ดูเฉลย

D ตรงกับการจัดวางที่แนะนำทั้ง 3 ข้อ A ไม่ได้แก้ลำดับหรือโครงสร้าง B ยังเอาคำถามไว้ผิดที่และไม่แก้เรื่องข้อความดิบ C ไม่เกี่ยวกับปัญหาหาข้อมูลกลางเอกสาร

Checkpoint 8 (เลือก 3 ข้อ)

นักพัฒนากำลังสร้าง prompt ถาม-ตอบจากคู่มือภายในหลายเล่มที่ยาวมาก ข้อไหนเป็นแนวปฏิบัติที่ถูกต้อง?

  1. วางคำถามไว้บรรทัดแรกสุดของ prompt
  2. ห่อแต่ละเล่มด้วย <document> ที่มี <source> และ <document_content>
  3. แทรกตัวอย่าง few-shot ไว้ระหว่างคู่มือแต่ละเล่ม เพื่อให้อยู่ใกล้เนื้อหา
  4. วางคู่มือทั้งหมดไว้เหนือคำสั่งและคำถาม
  5. ให้ Claude ดึงข้อความที่เกี่ยวข้องมาไว้ใน tag ก่อนเขียนคำตอบสุดท้าย
  6. สั่งให้ตอบทันทีโดยไม่ต้องยกข้อความอ้างอิง เพื่อประหยัด output token
ดูเฉลย

B, D, E คือ 3 หลักของการวางเอกสารยาว A ผิดทิศ C ทำให้ตัวอย่างปนกับเอกสารจนแยกยาก และ F ตัดขั้น quote ที่ช่วยให้ความสนใจอยู่กับเนื้อหาที่เกี่ยวข้องทิ้งไป
