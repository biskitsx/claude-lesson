3.4 Run-level telemetry และการติด tag สำหรับฝูง Claude agent

ต้นฉบับ: CertSafari 3.4

อ่านจบแล้วควรทำได้
  • อธิบายได้ว่าทำไม log แบบแบนๆ ใช้ debug agent ไม่ได้ และอ่าน span tree ของ Claude Code / Agent SDK ได้
  • ใช้ attribute บน claude_code.llm_request แยก retry storm ออกจากการชน output limit ได้
  • กระจาย config ของ OpenTelemetry collector ผ่าน managed settings และรู้ว่า setting ไหนถูกล็อก setting ไหนไม่ถูกล็อก
  • ติด tag ตาม tenant, ทีม และ deployment และคุม cardinality ของ metric
  • เลือกเปิด content gate ให้แคบที่สุดตามความเสี่ยงด้าน privacy
แนวคิดหลัก: มอง run เป็นต้นไม้ ไม่ใช่รายการ

prompt เดียวของ agent แตกออกเป็น model request หลายครั้ง, tool call, การรอ permission และ subagent และเส้นทางก็ไม่เหมือนกันทุกรอบ Run-level telemetry จัดสิ่งเหล่านี้เป็น span tree (ต้นไม้ของช่วงเวลาที่ซ้อนกัน) จึงเห็นว่าอะไรเป็นลูกของอะไร และเวลาหายไปที่ไหน

1. ทำไม agent run ถึง debug แบบปกติได้ยาก

Request log แบบแบนๆ บอกได้ว่ามีการเรียก API กี่ครั้ง แต่ไม่บอกว่าแต่ละครั้งเกี่ยวกันยังไง เหมือนดูใบเสร็จร้านอาหารที่เรียงตามเวลา แต่ไม่รู้ว่าจานไหนเป็นของโต๊ะไหน

โครงสร้าง span tree ใน Claude Code / Agent SDK

claude_code.interaction                 (1 turn)
├── claude_code.llm_request
├── claude_code.hook                    (ต้องเปิด detailed beta tracing)
└── claude_code.tool
    ├── claude_code.tool.blocked_on_user   (เวลารอคนกดอนุญาต)
    └── claude_code.tool.execution         (เวลารันจริง)
        └── ... span ของ subagent ซ้อนอยู่ใต้ Agent tool call ที่สร้างมันขึ้นมา
  • แต่ละ turn คือ span claude_code.interaction
  • claude_code.hook จะมีก็ต่อเมื่อเปิด detailed beta tracing
  • แยก blocked_on_user ออกจาก execution ทำให้รู้ว่า "ช้า" เพราะ tool ทำงานช้า หรือเพราะคนยังไม่กดอนุญาต

Attribute ที่มีประโยชน์บน claude_code.llm_request

Attributeบอกอะไร
agent_id, parent_agent_idagent ตัวไหนส่ง request และใครเป็นคน spawn มัน
query_source_safesubsystem ไหนเป็นต้นเรื่อง
attemptครั้งที่เท่าไหร่ของการลอง (มากกว่า 1 = retry)
stop_reasonเหตุที่การตอบหยุด เช่น ชน output limit
error_classประเภท error เช่น api_timeout, server_overload

สามตัวหลัง (attempt, stop_reason, error_class) ช่วยแยก "retry storm" (ลองซ้ำเพราะ server ล้น) ออกจาก "ตอบไม่จบเพราะชน output limit" ซึ่งอาการภายนอกดูคล้ายกัน แต่วิธีแก้คนละเรื่อง

Managed Agents และ API-side spans

  • Session viewer ใน Console มี timeline แยก lane ละ thread และแท็บ Tools แสดงจำนวนครั้งที่เรียก, จำนวนที่ล้มเหลว และค่ามัธยฐานของเวลา
  • ตั้ง OpenTelemetry destination เพื่อ export span ฝั่ง API ได้
  • อยากให้ span ของ API ไปซ้อนอยู่ใต้ span ของแอปเรา ให้เรียก SDK ภายใน span ของเราเอง SDK จะส่ง header W3C traceparent ไปให้
  • การส่ง span เป็นแบบ at-least-once (อาจซ้ำ ให้ dedupe ด้วย trace ID + span ID) และ best-effort (span ที่หายจะไม่ถูกส่งใหม่)
สรุปสั้นๆ

interaction → llm_request / hook / tool → blocked_on_user กับ execution ใช้ attempt + error_class ดู retry, stop_reason ดู output limit และ dedupe span ด้วย trace ID + span ID

Checkpoint 1

ทีมสงสัยว่า agent ช้าเพราะ tool deploy รันนาน หรือเพราะต้องรอ on-call มากดอนุญาต ควรดู span ไหนใต้ claude_code.tool?

  1. claude_code.hook
  2. claude_code.llm_request
  3. claude_code.tool.blocked_on_user เทียบกับ claude_code.tool.execution
  4. claude_code.interaction
ดูเฉลย

C blocked_on_user วัดเวลารอคนกดอนุญาต แยกจาก execution ที่วัดเวลารันจริง span อื่นไม่ได้แยกสองอย่างนี้

Checkpoint 2

Dashboard แสดงว่า run บางตัวใช้เวลานานผิดปกติ อยากรู้ว่าเกิดจาก server overload แล้วถูก retry ซ้ำๆ หรือเพราะคำตอบชน output limit ควรดูอะไร?

  1. agent_id และ parent_agent_id
  2. query_source_safe
  3. จำนวน span claude_code.interaction
  4. attempt และ error_class (ประกอบกับ stop_reason) บน claude_code.llm_request
ดูเฉลย

D attempt มากกว่า 1 คู่กับ error_class=server_overload คือ retry storm ส่วน stop_reason บอกว่าชน limit หรือไม่ A บอกแค่ว่าใครส่ง B บอกแค่ subsystem

2. กระจาย config ของ collector ผ่าน managed settings

Claude Code export ได้ 3 สัญญาณ: metrics, log events และ traces วิธีที่ scale คือใส่ตัวแปร telemetry ไว้ใน block env ของ settings.json ที่ผู้ดูแลระบบจัดการ (managed settings) ทุกเครื่องจะได้ค่าเหมือนกันโดยนักพัฒนาไม่ต้องตั้งเอง

{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "grpc",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "https://otel.corp.example:4317",
    "OTEL_EXPORTER_OTLP_HEADERS": "Authorization=Bearer ${COLLECTOR_TOKEN}"
  }
}

Managed setting ล็อกอะไรได้บ้าง

ถ้า managed settings ตั้ง…ผลกับค่าที่นักพัฒนาตั้งเอง
endpointendpoint ทั้งแบบ per-signal และแบบ generic ของนักพัฒนาถูกลบทิ้ง
protocolprotocol ของนักพัฒนาถูกลบทิ้งเช่นกัน
headers หรือ client key/certificateendpoint ทุกตัวที่นักพัฒนาตั้งถูกลบทิ้ง เพื่อไม่ให้ credential ขององค์กรหลุดไปที่ collector ที่ไม่ได้อนุมัติ
exporter selector (OTEL_METRICS_EXPORTER, OTEL_LOGS_EXPORTER, OTEL_TRACES_EXPORTER)ใช้ลำดับความสำคัญปกติรายคีย์ ถ้า managed ไม่ได้ตั้ง นักพัฒนาเปลี่ยนเองได้
  • ช่วงเวลา export ก็ควรคุมจาก managed settings ด้วย (ค่า default ของ metric คือ 60 วินาที) ตอน debug ค่อยลดให้สั้นลง
  • สำหรับ Agent SDK ใน production ตั้งตัวแปรใน environment ของ process (shell, container หรือ orchestrator) แล้วทุก query() จะใช้ค่านั้นเองโดยไม่ต้องแก้โค้ด
ลองเดาก่อน

managed settings ล็อก endpoint ไว้แล้ว แต่นักพัฒนาคนหนึ่งตั้ง OTEL_METRICS_EXPORTER=console ใน shell ของตัวเอง metrics ของเขาไปไหน? คำตอบ: ออกที่ console ของเขา ไม่ถึง collector กลาง เพราะการล็อก endpoint ไม่ได้ล็อก exporter selector

เข้าใจผิดบ่อย

"ล็อก endpoint ใน managed settings แล้ว ข้อมูลทุกเครื่องจะไปถึง collector กลางแน่นอน" ไม่ใช่ ต้องใส่ exporter selector ใน managed settings ด้วย ไม่อย่างนั้นนักพัฒนาเปลี่ยนสัญญาณไปเป็น console หรือปิดไปเลยได้

สรุปสั้นๆ

ใส่ทุกอย่างไว้ใน managed env: เปิด telemetry, exporter, protocol, endpoint, headers และ interval การตั้ง headers/credential ใน managed จะลบ endpoint ทุกตัวของนักพัฒนา แต่ exporter selector ต้องล็อกแยกเอง

Checkpoint 3

managed settings ใส่ OTEL_EXPORTER_OTLP_HEADERS ที่มี token ขององค์กรไว้ นักพัฒนาคนหนึ่งตั้ง per-signal endpoint สำหรับ logs ชี้ไปที่ collector ส่วนตัว จะเกิดอะไรขึ้น?

  1. logs ไปที่ collector ส่วนตัวพร้อม header ขององค์กร
  2. logs ไปทั้งสองที่
  3. Claude Code ลบ endpoint ที่นักพัฒนาตั้ง เพราะ managed settings ให้ credential มาแล้ว
  4. Claude Code หยุดส่ง telemetry ทั้งหมด
ดูเฉลย

C เมื่อ managed settings ให้ headers หรือ client key/cert endpoint ทุกตัวที่นักพัฒนาตั้งจะถูกลบ เพื่อกันไม่ให้ credential ขององค์กรถูกส่งไปที่ collector ที่ไม่ได้อนุมัติ

3. ติด tag ตาม tenant, ทีม และ deployment

  • OTEL_SERVICE_NAME ตั้งชื่อ agent
  • OTEL_RESOURCE_ATTRIBUTES รับคู่ key=value คั่นด้วย comma เช่น version ของ service, deployment environment และคีย์ที่เรากำหนดเอง เช่น department, cost center
  • resource attribute ถูกแปะลงในทุก metric datapoint โดย default

Tag ต่อ run ในระบบ multi-tenant

ใน service ที่รับงานจากหลาย tenant ให้ส่ง tag เป็นราย run ผ่าน per-call options ของ Agent SDK และ URL-encode ค่าที่มาจาก request (เช่น ชื่อ tenant ที่มี comma หรือ = จะทำให้ parse ผิด)

จุดที่ต่างกันระหว่างภาษา:

  • TypeScript: options.env แทนที่ environment ที่สืบทอดมาทั้งหมด ต้อง spread process.env ใส่ก่อน ไม่อย่างนั้น agent จะเสีย PATH และ API key
  • Python: env merge ทับ environment ที่สืบทอดมา ใส่แค่ tag ก็พอ
// TypeScript
const attrs = `tenant.id=${encodeURIComponent(tenantId)},team=payments`;
query({ prompt, options: { env: { ...process.env, OTEL_RESOURCE_ATTRIBUTES: attrs } } });

# Python
opts = ClaudeAgentOptions(env={"OTEL_RESOURCE_ATTRIBUTES": f"tenant.id={quote(tenant_id)},team=payments"})

Flag ที่คุม attribute บน metric

ตัวแปรเพิ่มอะไรDefault
OTEL_METRICS_INCLUDE_RESOURCE_ATTRIBUTESคีย์จาก OTEL_RESOURCE_ATTRIBUTES บน metric datapointtrue
OTEL_METRICS_INCLUDE_SESSION_IDsession.id (และ ccr.session.id บน cloud session)true
OTEL_METRICS_INCLUDE_ACCOUNT_UUIDuser.account_uuid และ user.account_idtrue
OTEL_METRICS_INCLUDE_VERSIONapp.versionfalse
OTEL_METRICS_INCLUDE_ENTRYPOINTapp.entrypointfalse
OTEL_METRICS_INCLUDE_REPOSITORYvcs.* (ตัวตนของ repository)false

Cardinality คือจำนวนชุดค่าที่ไม่ซ้ำของ label ใน metric ทุก session ใหม่หรือนักพัฒนาใหม่ที่มี ID ไม่ซ้ำจะสร้าง time series ใหม่ ถ้า dashboard ไม่ได้ group ด้วย ID พวกนี้ ก็ควรปิด

แยก span ฝั่ง API ตาม workspace

OpenTelemetry destination ใน Console เลือกได้ว่าจะครอบคลุมทุก workspace, เฉพาะบาง workspace หรือทุก workspace ยกเว้นที่ระบุ span จะถูกส่งไปทุก destination ที่เปิดอยู่และครอบคลุม workspace นั้น ตัวอย่างเช่น ส่ง production ไป backend ราคาแพง แต่ไม่รวม staging

เข้าใจผิดบ่อย

"session ID และ account ID ต้อง opt-in ถึงจะถูกแนบไปกับ metric" ไม่ใช่ ทั้งสองเปิดเป็น default ถ้า dashboard ไม่ได้ใช้ ให้ปิดเอง ไม่อย่างนั้น time series จะงอกตามจำนวน session และนักพัฒนา

สรุปสั้นๆ

ใช้ OTEL_RESOURCE_ATTRIBUTES สำหรับ tag ทีม/tenant, ส่งต่อ run ผ่าน per-call env (TS ต้อง spread process.env), ปิด flag session/account ถ้าไม่ได้ใช้ และใช้ destination ราย workspace แยก production กับ staging

Checkpoint 4

SaaS ที่รัน Agent SDK ให้หลายลูกค้าอยากให้ telemetry ของแต่ละ run มี tenant ID และ user ID ติดไปด้วย ควรตั้งตัวแปรไหนใน per-call env?

  1. OTEL_RESOURCE_ATTRIBUTES
  2. OTEL_SERVICE_NAME
  3. OTEL_METRICS_INCLUDE_ACCOUNT_UUID
  4. OTEL_EXPORTER_OTLP_HEADERS
ดูเฉลย

A OTEL_RESOURCE_ATTRIBUTES รับคู่ key=value ที่เรากำหนดเอง B คือชื่อ agent, C แนบ account ของ Claude ไม่ใช่ tenant ของเรา, D คือ header สำหรับส่งไป collector

Checkpoint 5

Dashboard ค่าใช้จ่ายแยกตามทีม (ทีมมาจาก resource attribute team) แต่ backend เตือนว่าจำนวน time series โตขึ้นทุกวันตามจำนวน session และนักพัฒนาใหม่ จะหยุดการโตโดยยังแยกตามทีมได้ ต้องทำอะไร?

  1. ตั้ง OTEL_METRICS_INCLUDE_RESOURCE_ATTRIBUTES=false
  2. เปิด OTEL_METRICS_INCLUDE_REPOSITORY
  3. ตั้ง OTEL_METRICS_INCLUDE_SESSION_ID=false และ OTEL_METRICS_INCLUDE_ACCOUNT_UUID=false
  4. ลด export interval เป็น 10 วินาที
ดูเฉลย

C session และ account ID เป็นตัวสร้าง series ใหม่ A จะทำให้คีย์ team หายไปด้วย B เพิ่ม cardinality D ไม่เกี่ยวกับจำนวน series

Checkpoint 6 (เลือก 3 ข้อ)

บริษัทมีนักพัฒนา 400 คนใช้ Claude Code อยากได้ telemetry ที่รวมศูนย์ แยกค่าใช้จ่ายตามแผนกได้ และไม่ทำให้ backend บวม ข้อไหนคือแนวปฏิบัติที่ถูกต้อง?

  1. ส่งอีเมลให้นักพัฒนาแต่ละคน export ตัวแปร OTEL ใน shell profile ของตัวเอง
  2. ใส่ตัวแปร telemetry ใน settings.json แบบ managed ที่ผู้ดูแลระบบจัดการ
  3. ตั้ง OTEL_METRICS_EXPORTER=console ทุกเครื่องเพื่อให้เห็นผลทันที
  4. เพิ่ม resource attribute เช่น department และ cost_center
  5. ปิด flag cardinality ที่ dashboard ไม่ได้ใช้ เช่น session ID
ดูเฉลย

B, D, E managed settings กระจายค่าเดียวกันทุกเครื่องโดยไม่ต้องพึ่งคน, custom attribute ใช้แยกแผนก, ปิด flag ที่ไม่ใช้ลด series A ทำให้ค่าแต่ละเครื่องไม่ตรงกันและไม่ scale C ใช้สำหรับ debug ในเครื่อง ไม่ใช่ส่งเข้าส่วนกลาง

4. Content แบบไหนที่คุ้มจะเก็บในระดับ fleet

Content (prompt, คำตอบ, รายละเอียด tool) ถูก redact เป็น default การเปิด content gate แต่ละตัวคือการเปิดข้อมูลมากขึ้น และถ้าเปิดผ่าน managed settings ก็คือเปิดข้อมูลของวิศวกรทุกคนให้ใครก็ตามที่ query backend ได้เห็น ให้ตัดสินแต่ละ gate จาก "ใครจะเห็นอะไรบ้าง" ไม่ใช่จาก "ทำอะไรได้เพิ่ม"

Gateเปิดอะไรข้อควรระวัง
(ปิดทุก gate)ยังมี user.email เมื่อใช้ OAuthส่งแค่ไป collector ของเรา ไม่ไป Anthropic แต่ backend เก็บไว้ ถ้านโยบายไม่ให้เก็บต้อง filter ที่ backend
OTEL_LOG_USER_PROMPTSข้อความที่ผู้ใช้พิมพ์ถ้า strip ที่ collector ต้องตัดทั้ง prompt และ prompt_text ตัดตัวเดียวข้อความยังอยู่
OTEL_LOG_ASSISTANT_RESPONSESคำตอบของ assistantถ้าไม่ตั้งจะสืบทอดค่าจาก OTEL_LOG_USER_PROMPTS ถ้าอยากปิดต้องตั้ง 0 ชัดๆ
OTEL_LOG_TOOL_DETAILSรายละเอียดการเรียก tool เช่น คำสั่งfield อย่าง full_command ไม่ถูกตัด คำสั่งอาจมี secret
OTEL_LOG_RAW_API_BODIESrequest/response body ทั้งก้อน รวมบทสนทนาทั้งหมดเปิดตัวนี้ = ยินยอมกับทุกอย่างที่ gate prompt, tool detail และ tool content เปิดเผยรวมกัน แทบไม่เหมาะกับทั้ง fleet

ตัวอย่าง: ทีม security อยาก audit คำสั่งที่ agent รัน ตัวเลือกที่แคบที่สุดคือเปิด OTEL_LOG_TOOL_DETAILS แล้วส่งเป็น log event เข้า SIEM ไม่ต้องเก็บ prompt หรือทั้งบทสนทนา แต่ก็ยังต้องระวังว่าคำสั่งอาจมี secret ติดอยู่

เข้าใจผิดบ่อย

"Raw body logging เป็นสวิตช์แยกที่จำกัดขอบเขตได้" ไม่ใช่ การเปิด OTEL_LOG_RAW_API_BODIES เท่ากับยินยอมให้เปิดเผยทุกอย่างที่ content gate ตัวอื่นเปิดเผยรวมกัน

"ปิด user prompts แล้ว assistant responses ก็ปิดแน่นอน / เปิด user prompts แล้ว responses ยังปิดอยู่" ต้องระวัง responses ที่ไม่ได้ตั้งค่าจะตามค่า prompts ถ้าอยากเปิด prompts แต่ไม่เปิด responses ต้องตั้ง OTEL_LOG_ASSISTANT_RESPONSES=0

สรุปสั้นๆ

เปิด gate ให้แคบที่สุดที่ตอบโจทย์ audit คำสั่งใช้ tool details, อย่าเปิด raw bodies ทั้ง fleet และจำไว้ว่า user.email มาเสมอภายใต้ OAuth

Checkpoint 7

ทีม compliance ต้องการบันทึกว่า agent ของทุกทีมรันคำสั่ง shell อะไรบ้าง แต่ห้ามเก็บข้อความที่วิศวกรพิมพ์คุยกับ agent ควรเปิด gate ไหน?

  1. OTEL_LOG_RAW_API_BODIES
  2. OTEL_LOG_USER_PROMPTS
  3. OTEL_LOG_TOOL_DETAILS
  4. OTEL_LOG_ASSISTANT_RESPONSES
ดูเฉลย

C tool details ให้รายละเอียดคำสั่งโดยไม่ต้องเก็บ prompt A เปิดบทสนทนาทั้งหมด B เก็บข้อความที่พิมพ์ซึ่งต้องห้าม D ไม่ได้ให้คำสั่ง (และถ้าไม่ตั้งจะตามค่าของ B)

Checkpoint 8

ทีมเปิด OTEL_LOG_USER_PROMPTS=1 เพื่อวิเคราะห์คำถามที่พบบ่อย และไม่ได้ตั้งค่า OTEL_LOG_ASSISTANT_RESPONSES ไว้ ผลคืออะไร?

  1. เก็บแค่ prompt ส่วนคำตอบยังถูก redact
  2. ไม่เก็บอะไรเลยจนกว่าจะตั้งทั้งสองตัว
  3. เก็บ raw API body ทั้งหมด
  4. เก็บทั้ง prompt และคำตอบ เพราะ responses สืบทอดค่าจาก prompts
ดูเฉลย

D ถ้าไม่ตั้ง responses จะใช้ค่าเดียวกับ prompts ถ้าอยากเก็บแค่ prompt ต้องตั้ง responses เป็น 0
