6.1 Structured discovery and requirement gathering for Claude solutions

ต้นฉบับ: CertSafari 6.1

อ่านจบแล้วควรทำได้
  • รัน discovery session ที่ครอบคลุม users, needs, experience, constraints และได้ข้อเท็จจริงเรื่อง capability, speed, budget ที่การเลือกโมเดลต้องใช้
  • แปลงผล discovery เป็นโมเดลตั้งต้นที่มีเหตุผลรองรับ พร้อมแผนอัปเกรดหรือ optimize ภายหลัง
  • เขียน success criteria ที่ specific, measurable, achievable, relevant ครอบคลุม quality, latency, cost และ safety
  • เลือกเทคนิค (blind spot pass, prototype, interview, reference, ดู sample data) เพื่อขุด requirement ที่ยังไม่มีใครรู้ ก่อนลงมือสร้าง
  • เขียน acceptance test ก่อนเขียนโค้ด และไล่ย้อนหาจุดพังของผลิตภัณฑ์ผ่าน Description Chain ได้
แนวคิดหลัก: requirement ที่ testable

requirement ที่ดีต้องชัดพอที่ คนนอก เข้ามาดูระบบที่เสร็จแล้ว แล้วตัดสินได้ทันทีว่า ผ่านหรือไม่ผ่าน ถ้าไม่มีใครทำให้มัน "ตก" ได้ มันยังไม่ใช่ requirement

1. Discovery brief: users, needs, experience, constraints

จุดเริ่มต้นของทุกโปรเจกต์มักเป็นประโยคกว้างๆ เช่น "คนไข้อยากเช็กเวลารอคิวก่อนออกจากบ้าน" ประโยคนี้เป็น จุดเริ่มบทสนทนา ยังไม่ใช่ requirement งานของ discovery คือเปลี่ยนมันให้เป็นภาพที่ชัดด้วยคำถามภาษาคน 4 ข้อ:

คำถามต้องได้อะไร
Users ใครใช้เจาะจงให้ได้ รวมถึงพนักงานและทุกคนที่แตะระบบ ไม่ใช่แค่ผู้ใช้ปลายทาง
Needs ต้องการอะไรผลลัพธ์ที่เขาอยากได้ ซึ่งไม่เหมือนกับฟีเจอร์ที่เขาขอ
Experience ใช้แล้วรู้สึกยังไงบรรยายประสบการณ์ที่ดี ไม่ใช่รายการฟีเจอร์
Constraints ติดอะไรงบประมาณ ทักษะเทคนิคของคนดูแลระบบ อุปกรณ์ที่ผู้ใช้มี ข้อกำหนดด้าน privacy

Process map: ตัดสินบทบาท AI ทีละขั้น

แทนที่จะถามว่า "ระบบนี้ควรใช้ AI ไหม" ทั้งก้อน ให้แตกความต้องการออกเป็นขั้นตอน ระบุ stakeholder ของแต่ละขั้น แล้วเลือกบทบาท AI รายขั้น จากสามแบบ:

  • Automation AI ทำขั้นนั้นเอง แล้วคนตรวจทีหลัง
  • Augmentation คนกับ AI ทำขั้นนั้นด้วยกัน
  • Agency AI ลงมือได้อย่างมีอิสระ แต่อยู่ในขอบเขตที่ builder กำหนด

ผลที่ได้คือตารางเล็กๆ หนึ่งแถวต่อหนึ่งขั้น แต่ละแถวมีการตัดสินบทบาท AI ของตัวเอง เช่น ระบบคิวคลินิก:

ขั้นStakeholderบทบาท AI
รวบรวมจำนวนคนรอจากระบบลงทะเบียนเจ้าหน้าที่เวชระเบียนAutomation
ประเมินเวลารอเมื่อมีเคสฉุกเฉินแทรกพยาบาลคัดกรองAugmentation
ส่งข้อความแจ้งเตือนคนไข้เมื่อใกล้ถึงคิวคนไข้Agency (ภายในกฎที่ตั้งไว้)

สามคำถามบังคับใน session แรก

ก่อนจะแนะนำโมเดลใดๆ ต้องได้คำตอบ 3 ข้อนี้ ซึ่งทุกข้อมาจาก workload ของลูกค้า:

  1. Capabilities โมเดลต้องทำอะไรได้บ้าง
  2. Speed ต้องตอบเร็วแค่ไหนในแอป
  3. Cost งบสำหรับช่วงพัฒนาและช่วง production

ข้อมูลอย่างจำนวนพนักงาน IT, แพลตฟอร์ม social ที่ใช้ทำการตลาด หรือเวอร์ชันของระบบ ticketing ไม่ได้ช่วยตัดสิน capability, speed หรือ cost เลย

ในข้อสอบ

ถ้าถามว่าต้องรู้อะไรก่อนแนะนำโมเดล ให้เลือก capability, ความเร็วในการตอบ และงบ dev + production ข้อมูลองค์กรจุกจิกเป็นตัวหลอก แม้จะฟังดูรอบคอบ

สรุปสั้นๆ

ถาม 4 ข้อ (users, needs, experience, constraints) แตกงานเป็น process map แล้วเลือกบทบาท AI รายขั้น และอย่าออกจาก session แรกโดยไม่รู้ capability, speed, budget

Checkpoint 1 (จับคู่)

จับคู่ขั้นตอนในระบบตอบคำถามลูกค้าของร้านประกันกับบทบาท AI ที่บรรยายไว้ (A = Automation, B = Augmentation, C = Agency)

  1. AI ร่างสรุปกรมธรรม์ให้ลูกค้าทุกฉบับ แล้วเจ้าหน้าที่สุ่มตรวจตอนสิ้นวัน
  2. เจ้าหน้าที่คุยกับลูกค้า ขณะที่ AI เสนอคำตอบและข้อกฎหมายที่เกี่ยวข้องข้างจอแบบ real-time
  3. AI นัดหมายเวลาตรวจสุขภาพให้ลูกค้าเองได้ แต่ต้องอยู่ในช่วงเวลาและสาขาที่กำหนด
ดูเฉลย

1-A, 2-B, 3-C AI ทำแล้วคนตรวจทีหลัง = Automation, ทำงานไปด้วยกัน = Augmentation, AI ตัดสินใจเองในกรอบที่กำหนด = Agency

Checkpoint 2

คุณนัด discovery ครั้งแรกกับบริษัทขนส่งที่อยากใช้ Claude จัดหมวดคำร้องเรียน ก่อนแนะนำโมเดล ต้องได้ข้อมูลข้อไหนบ้าง? (เลือก 3 ข้อ)

  1. ต้องตอบเร็วแค่ไหนในหน้าจอเจ้าหน้าที่
  2. จำนวนรถบรรทุกในกองยาน
  3. งานนี้ต้องให้โมเดลทำอะไรได้บ้าง (เช่น อ่านภาษาไทยปนอังกฤษ แยกหมวดได้กี่หมวด)
  4. ชื่อผู้ให้บริการ cloud email ที่ใช้ในบริษัท
  5. งบช่วงพัฒนาและงบรายเดือนตอน production
  6. จำนวนสาขาทั่วประเทศ
ดูเฉลย

A, C, E speed, capability และ budget คือสามข้อที่การเลือกโมเดลต้องใช้ ข้อมูลองค์กรอื่นๆ (B, D, F) ไม่ได้บอกอะไรเกี่ยวกับสามข้อนี้

2. จากผล discovery สู่โมเดลตั้งต้น

ลองนึกก่อน: ทีมซัพพอร์ตส่งคำขอคัดแยก ticket สั้นๆ วันละ 50,000 รายการ ต้องตอบไม่ถึงวินาที งบ pilot จำกัด ควรเริ่มจากตรงไหน? คำตอบคือเริ่มจากโมเดลที่ เร็วและคุ้มค่า ทดสอบกับ ticket จริง และอัปเกรดเฉพาะเมื่อไม่ถึงเกณฑ์ความแม่นยำ

เส้นทางสัญญาณจาก discoveryดำเนินต่อยังไง
A: เร็วและคุ้มค่าก่อน
(ตัวอย่าง: Claude Haiku 4.5)		latency ตึง, งบจำกัด, งานง่ายปริมาณมาก, ช่วง prototypeเริ่มที่นี่ ทดสอบละเอียด เทียบกับ requirement อัปเกรดเฉพาะเมื่อเจอช่องว่างด้าน capability ที่ระบุได้
B: capability ก่อน
(ตัวอย่าง: Claude Opus 4.8)		reasoning ซับซ้อน, งานวิทยาศาสตร์, ต้องเข้าใจบริบทละเอียด, ความแม่นสำคัญกว่าค่าใช้จ่าย, coding ขั้นสูง, agentic งานที่มี autonomy สูงเริ่มจากโมเดลที่แข็งที่สุด ปรับ prompt, eval แล้วค่อยหาความคุ้มค่าด้วยการลด effort หรือลดรุ่นทีหลัง

ไม่ว่าเลือกทางไหน ต้อง ยืนยันด้วย prompt และข้อมูลจริงของลูกค้า เสมอ

Effort: ปุ่มปรับในโมเดลเดิม

Effort เป็นค่าราย request (ใน API ชื่อ output_config.effort) ที่คุมว่าโมเดลคิดมากแค่ไหนก่อนตอบ effort สูง = ฉลาดขึ้นแต่ช้าและใช้ token มากขึ้น effort ต่ำ = เร็วและถูกแต่คิดน้อยลง หลายโมเดลของ Claude รองรับ และการปรับ effort บนโมเดลที่เลือกแล้ว มักเป็นคันโยกที่ดีกว่าการเปลี่ยนโมเดล แต่ต้องทำหลังจาก eval แล้ว

{
  "model": "claude-opus-4-8",
  "max_tokens": 2048,
  "output_config": {"effort": "medium"},
  "messages": [{"role": "user", "content": "..."}]
}

ทำไม Haiku 4.5 เหมาะกับโจทย์คัดแยก ticket

Haiku 4.5 วางตำแหน่งไว้สำหรับแอปแบบ interactive และงานปริมาณสูง การเริ่มที่ reasoning สูงสุดทุก request หรือเลือกโมเดลจากขนาด context window คือการตอบคำถามที่ลูกค้าไม่ได้ถาม context window ไม่ได้อยู่ในสามเกณฑ์หลัก และ prompt คัดแยกสั้นๆ ก็ไม่ต้องใช้ window ใหญ่

กลับกัน ถ้าทีมวิจัยต้องสังเคราะห์งานวิจัยหลายขั้น ความแม่นสำคัญกว่าเงิน และเป็น agent ที่รันยาวแบบอิสระ ข้อเสนอที่เป้าหลักคือ "ประหยัด" (โมเดลถูกกว่า, ลด effort, ทำ batch pipeline) พลาดลำดับความสำคัญที่ลูกค้าบอกไว้ การจูน effort ทำได้ แต่เป็นขั้นหลัง eval

เข้าใจผิดบ่อย

"discovery ควรจบที่โมเดลแรงสุดกับ reasoning สูงสุด คุณภาพจะได้ไม่เป็นคอขวด" ผิด ถ้า latency ตึง ปริมาณสูง งบจำกัด ต้องเริ่มที่โมเดลเร็วและถูก แล้วอัปเกรดเมื่อมีหลักฐาน

สรุปสั้นๆ

สัญญาณ latency/ปริมาณ/งบ → เริ่มเส้นทาง A สัญญาณความซับซ้อน/ความแม่น/agent อิสระ → เส้นทาง B ยืนยันด้วยข้อมูลจริงเสมอ effort เป็นการจูนหลัง eval

Checkpoint 3

ทีมวิเคราะห์สัญญาทางกฎหมายเลือกเส้นทาง capability-first เพราะความแม่นสำคัญกว่าค่าใช้จ่าย อะไรคือการยืนยันว่าเลือกถูก?

  1. ดู benchmark สาธารณะว่าโมเดลนั้นอยู่อันดับต้น
  2. ลด effort ลงทันทีเพื่อดูว่ายังแม่นอยู่ไหม
  3. รัน eval ด้วยสัญญาและ prompt จริงของทีม เทียบกับ success criteria ที่ได้จาก discovery
  4. ถามฝ่าย IT ว่าบริษัทมี license โมเดลไหนอยู่แล้ว
ดูเฉลย

C การยืนยันต้องมาจาก workload จริงเทียบเกณฑ์ที่ตกลงกันไว้ A ไม่สะท้อนงานของทีม B เป็นการ optimize ที่ข้ามขั้นมาก่อน eval D เป็นข้อมูลองค์กรที่ไม่เกี่ยวกับความเหมาะสมของโมเดล

Checkpoint 4

แอปส่งอาหารต้องจัดหมวดข้อความแชตจากไรเดอร์วันละ 80,000 ข้อความ ต้องได้ผลภายในไม่ถึงวินาที งบ pilot น้อย ข้อไหนเหมาะที่สุด?

  1. เริ่มด้วย Claude Haiku 4.5 ทดสอบกับข้อความจริงจาก production และอัปเกรดเฉพาะเมื่อความแม่นไม่ถึงเกณฑ์
  2. ใช้ Opus 4.8 ที่ effort สูงสุดทุกข้อความ เพื่อไม่ให้พลาด
  3. ใช้ Sonnet 5 พร้อม extended thinking ทุก request
  4. เลือกโมเดลที่มี context window ใหญ่ที่สุดที่หาได้
ดูเฉลย

A ตรงกับสัญญาณ latency ตึง ปริมาณสูง งบน้อย B และ C เพิ่มทั้ง latency และค่าใช้จ่าย ขัดกับเป้าไม่ถึงวินาที D optimize ปัจจัยที่ลูกค้าไม่ได้พูดถึงเลย

Checkpoint 5

ศูนย์วิจัยวัสดุต้องการ agent ที่วางแผนและรันการทบทวนวรรณกรรมหลายขั้นเองเป็นเวลานาน ผู้อำนวยการย้ำว่า "ผิดไม่ได้ เงินไม่ใช่ปัญหา" ควรเริ่มที่ไหน?

  1. Haiku 4.5 รันหลายรอบเพื่อประหยัด
  2. Claude Opus 4.8 เพราะ reasoning ซับซ้อนและงาน agentic ขั้นสูงคือจุดแข็งของมัน
  3. Sonnet 5 ที่ลด effort ลงเพื่อคุมงบ
  4. ส่งผ่าน Batch API เพื่อให้ความแม่นยำสูงขึ้น
ดูเฉลย

B สัญญาณทุกตัวชี้ไปเส้นทาง capability-first A และ C ไปเน้นประหยัดซึ่งขัดกับลำดับความสำคัญ D ใช้กลไกด้าน throughput/ต้นทุนผิดที่ Batch API ไม่ได้เพิ่มความแม่น

3. เขียน success criteria ที่วัดได้

ลองนึกก่อน: เปลี่ยน "โมเดลต้องจัดหมวด sentiment ได้ดี" ให้เป็นประโยคที่ สอบตกได้ ต้องตัดสิน 3 อย่าง: ใช้ metric อะไร, threshold เท่าไร, ทดสอบกับชุดข้อมูลไหน

เกณฑ์ที่ดีมี 4 คุณสมบัติ:

  • Specific ระบุเป้าชัด
  • Measurable มี metric เชิงปริมาณ หรือ scale เชิงคุณภาพที่ใช้อย่างสม่ำเสมอ
  • Achievable อิงจาก benchmark, การทดลองก่อนหน้า, งานวิจัย หรือความรู้ผู้เชี่ยวชาญ และไม่เกินความสามารถของ frontier model ปัจจุบัน
  • Relevant ตรงกับจุดประสงค์ของแอป เช่น ความถูกต้องของการอ้างอิงสำคัญมากในแอปการแพทย์ แต่ไม่ค่อยสำคัญในแชตบอตคุยเล่น
มิติแบบคลุมเครือแบบวัดได้
Qualityจัดหมวด sentiment ได้ดีF1 อย่างน้อย 0.85 บนชุด held-out 10,000 โพสต์ที่หลากหลาย (ดีกว่า baseline 5%)
Safetyoutput ปลอดภัย99.5% ของ output ไม่ toxic หรือ น้อยกว่า 0.1% ของ output ใน 10,000 ครั้งถูก content filter ตีธง
ความรุนแรงของ errorไม่ค่อยพลาดหนัก90% ของ error เป็นแค่ความไม่สะดวก ไม่ใช่ความเสียหายร้ายแรง (นิยามทั้งสองคำไว้ชัด)
Latencyเร็ว95% ของ response ต่ำกว่า 200 ms
Costราคาไม่แพงงบที่คำนวณจาก cost ต่อ call, ขนาดโมเดล และความถี่การใช้

threshold ด้าน latency ต้องมาจาก discovery ด้วย widget แชตกับรายงานที่รันข้ามคืนยอมรับความช้าได้ต่างกันมาก และ metric เดียวแทบไม่เคยพอ โมเดลคัดแยกที่แม่นแต่ช้าหรือเกินงบ ก็ถือว่าล้มเหลวอยู่ดี

เข้าใจผิดบ่อย

"เป้าความแม่นยำตัวเดียวคือ success criterion ที่ครบแล้ว" ผิด use case ส่วนใหญ่ต้องมีหลายเกณฑ์ (quality, safety, latency, cost) แต่ละตัวมี threshold ของตัวเอง

สรุปสั้นๆ

ทุกเกณฑ์ต้องสอบตกได้: มี metric, threshold และชุดทดสอบ ครอบคลุมหลายมิติ และ threshold ด้าน latency/cost มาจาก discovery

Checkpoint 6

ผู้ช่วยตอบคำถามในแอปธนาคารมีเกณฑ์ข้อเดียว คือ accuracy ≥ 90% ผลทดสอบได้ 93% แต่ p95 latency อยู่ที่ 4 วินาที และค่าใช้จ่ายต่อ call สูงกว่างบ pilot ปัญหาคืออะไร?

  1. เกณฑ์ accuracy ไม่ achievable ตั้งแต่แรก
  2. success criteria ไม่ครบ latency และ cost ควรมี threshold ที่วัดได้ของตัวเองตั้งแต่ discovery
  3. ควรเลื่อนเรื่อง latency และ cost ไปคุยหลัง launch
  4. ควรยกเกณฑ์ accuracy เป็น 95% เพื่อบังคับคุณภาพ
ดูเฉลย

B ปัญหาคือเกณฑ์มีมิติเดียว A ผิดเพราะเกณฑ์ผ่านแล้ว C มองข้ามว่า latency/cost ก็เป็น success criteria D ยกเกณฑ์ความแม่นไม่ช่วยจับปัญหาความเร็วและเงิน

4. ขุด requirement ที่ยังไม่มีใครรู้ ก่อนเริ่ม implement

เทคนิคในหัวข้อนี้ใช้ Claude ในบท coding agent ก่อนเขียนโค้ดแม้แต่บรรทัดเดียว Claude ค้น codebase และเว็บได้เร็ว จึงช่วยดึงสิ่งที่ยังไม่รู้ขึ้นมาได้เร็วกว่าคนทำคนเดียว

สิ่งที่ยังไม่รู้มีสองแบบ:

  • Unknown unknowns คำถามที่เราไม่รู้ด้วยซ้ำว่าต้องถาม เช่น ไม่รู้ว่า "ดี" หน้าตาเป็นยังไง ไม่รู้ว่ามีใครลองอะไรไปแล้ว หรือมีหลุมพรางอะไรบ้าง
  • Unknown knowns เกณฑ์ที่คนรู้ก็ต่อเมื่อเห็น เช่น layout หรือสไตล์ภาพ ("บอกไม่ได้ แต่เห็นแล้วจะรู้")

ทำไมต้องทำแต่เนิ่นๆ: spec ที่เปลี่ยนนิดเดียวอาจได้โค้ดหน้าตาต่างกันมาก และพอ coding agent สร้างไปแล้ว การกลับลำทีหลังทำได้ยาก

เทคนิคเปิดเผยอะไรตัวอย่างการขอ
Blind spot passunknown unknowns ในเรื่องที่ไม่คุ้น"ก่อนเพิ่ม payment provider ใหม่ ช่วยหาและอธิบายสิ่งที่ฉันน่าจะไม่รู้ใน module billing"
Prototype / mockunknown knowns ที่รู้เมื่อเห็นไฟล์ HTML ไฟล์เดียว mock แถบเครื่องมือด้วยข้อมูลปลอม ไม่ต่ออะไรเลย
หลายทิศทางพร้อมกันความชอบที่คนพูดไม่ออกขอ dashboard 4 แบบที่ต่างกันมาก ให้ลูกค้าเลือก

Prototype และ mock เป็น spike คืองานทิ้งได้ที่ตอบคำถามข้อเดียว ไม่ผูกตัวเองกับ backend route หรือ state ใหม่

Interview prompt

บอก Claude ว่าจะสร้างอะไร แล้วให้มันสัมภาษณ์เราด้วย AskUserQuestion tool ครอบคลุมเรื่อง implementation, UI/UX, edge case, ข้อกังวล และ tradeoff ให้ ข้ามคำถามที่ชัดอยู่แล้ว ถามจนครบ แล้วเขียน spec ลงไฟล์ SPEC.md การเล่าให้ Claude รู้ว่าตอนนี้เราอยู่ตรงไหนช่วยให้มันโฟกัสส่วนที่ยาก

ฉันจะสร้างระบบแจ้งเวลารอคิวคลินิก ช่วยสัมภาษณ์ฉันโดยใช้ AskUserQuestion

ดู sample data จริงแต่เนิ่นๆ

input จริงเผยสิ่งที่ห้องประชุมมองไม่เห็น ขอตัวอย่างจาก production มาดูตั้งแต่ต้น แล้วมองหา:

  • ข้อมูลที่ไม่เกี่ยวข้อง หรือไม่มีอยู่จริง
  • input ยาวเกินไป
  • input คุณภาพแย่ หรือเป็นอันตราย
  • เคสกำกวมที่แม้แต่คนยังเห็นไม่ตรงกัน
สรุปสั้นๆ

unknown unknowns ใช้ blind spot pass / interview / reference ส่วน unknown knowns ใช้ prototype หรือหลายทิศทางให้เลือก ทำก่อนเขียนโค้ด และขอ sample data จริงตั้งแต่ต้น

Checkpoint 7

คุณกำลังเขียน interview prompt ให้ Claude ขุดความกำกวมที่จะเปลี่ยน design ของระบบจองห้องประชุม ประโยคหนึ่งเขียนว่า "อย่าถามคำถามที่ ____ ให้ขุดลงไปในจุดยากที่ฉันอาจยังไม่ได้คิด" ช่องว่างควรเป็นคำไหน?

  1. เชิงเทคนิค
  2. ชัดเจนอยู่แล้ว (obvious)
  3. ปลายเปิด
  4. ถามต่อเนื่อง (follow-up)
ดูเฉลย

B เป้าคือข้ามเรื่องที่ชัดแล้วเพื่อไปหาจุดยาก คำถามเชิงเทคนิค ปลายเปิด และถามต่อเนื่อง เป็นสิ่งที่ interview ควร มี ไม่ใช่สิ่งที่ห้าม

5. Acceptance test ที่กำหนดก่อนเขียนโค้ด

acceptance test คือนิยามของคำว่า "เสร็จ" ที่ตกลงร่วมกันระหว่างเรา ลูกค้า และ Claude ปกติ 5 ถึง 7 ข้อ ก็พอ แต่ละข้อต้องชัดพอให้คนแปลกหน้าตัดสินได้

  • ตก: "ระบบใช้งานง่าย" (ใครจะสอบตกข้อนี้ได้?)
  • ผ่าน: "คนไข้ที่มีสมาร์ตโฟนรุ่นพื้นฐาน หาเวลารอคิวปัจจุบันเจอภายใน 30 วินาที โดยไม่ต้องสมัครบัญชี" ข้อนี้มีผู้ใช้ อุปกรณ์ เวลา และข้อจำกัด ทุกส่วนย้อนกลับไปหา discovery ได้

จากนั้นเพิ่ม edge case เช่น คลินิกปิด, ไม่มีข้อมูล, เวลารอเป็นศูนย์ และถ้าร่างแรกเขียนไว้ให้คนตัดสิน ก็แปลงให้โค้ดตรวจได้

ขยายไปสู่ agent ที่รันยาว

ใน harness สำหรับ agent ที่ทำงานยาว มี initializer agent ที่ขยาย prompt ของผู้ใช้เป็นไฟล์ feature requirements แบบละเอียด ในตัวอย่างการสร้าง clone ของ claude.ai ได้ feature มากกว่า 200 รายการ และทุกรายการเริ่มต้นเป็น "ยังไม่ผ่าน" จากนั้น coding agent ทำทีละ feature และ แก้ได้เฉพาะ field passes เท่านั้น ห้ามลบหรือแก้ test เพราะจะกลบ feature ที่ขาดหรือมี bug

{
  "category": "functional",
  "description": "ปุ่มแจ้งเตือนส่ง SMS เมื่อเหลืออีก 3 คิว",
  "steps": [
    "เปิดหน้าคิวของคนไข้",
    "กดเปิดการแจ้งเตือน",
    "จำลองให้คิวเลื่อนจนเหลือ 3",
    "ตรวจว่ามี SMS ถูกส่ง 1 ครั้ง"
  ],
  "passes": false
}
ลองใช้กับงานจริง

หยิบ requirement จากโปรเจกต์ล่าสุดที่ไม่มีใครทำให้มันตกได้ แล้วถามว่าคนแปลกหน้าต้องเห็นอะไรถึงจะบอกได้ว่า "ไม่ผ่าน"

เข้าใจผิดบ่อย

"เขียน acceptance test หลังจาก build แรกเสร็จ" ผิด ต้องเขียนก่อนเขียนโค้ด เพราะมันคือสิ่งที่ build ถูกวัด

สรุปสั้นๆ

5-7 ข้อ ผ่าน/ตกชัด มีผู้ใช้ อุปกรณ์ เวลา ข้อจำกัด บวก edge case เขียนก่อนโค้ด ใน harness ยาวๆ ทุก feature เริ่มที่ passes: false และ agent แก้ได้แค่ field นั้น

Checkpoint 8

initializer agent กำลังเขียนรายการ feature สำหรับระบบจองคิวก่อนที่จะมีโค้ดใดๆ ค่า passes เริ่มต้นของแต่ละรายการควรเป็นอะไร?

  1. true
  2. "pending"
  3. false
  4. null
ดูเฉลย

C ทุกรายการเริ่มที่ยังไม่ผ่าน แล้วค่อยพลิกเมื่อ feature ทำงานจริง true อ้างว่าเสร็จก่อนสร้าง "pending" เป็น string ไม่ใช่ boolean ตาม schema และ null ไม่ใช่สถานะผ่าน/ตก

6. Description Chain

จากเสียงของผู้ใช้ไปจนถึงคำสั่งที่ Claude ได้รับ มี 4 ข้อต่อ และ แต่ละข้อต่อเพิ่ม judgement ที่ข้อก่อนหน้าไม่ได้ทำ:

ข้อต่อคืออะไรjudgement ที่ต้องใส่
1. User voiceความต้องการตามที่ผู้ใช้เล่าผู้ใช้กลุ่มไหน ผลลัพธ์อะไร ประสบการณ์แบบไหน
2. Requirementย่อหน้าเดียวที่วัดได้ทุกคำคุณศัพท์ต้องกลายเป็นการตัดสินใจที่ปกป้องได้ เช่น "เร็ว" ต้องกลายเป็นตัวเลข
3. Technical speccomponent และการทำงานร่วมกันคัดค้านแนวทางที่ทำลาย constraint
4. AI instructionconstraint, stack, test ที่ส่งให้ ClaudeClaude ต้องรู้อะไรบ้าง spec ถึงจะกลายเป็นโค้ดที่ใช้ได้

prompt engineering เป็นแค่ ข้อต่อสุดท้าย ข้อจำกัดที่หนีไม่พ้นคือ Claude ทำตามสิ่งที่ผู้ใช้ไม่ได้พูดไม่ได้ builder ต้องเป็นคนแปลความหมายในทุกข้อต่อ

ใช้ chain นี้วินิจฉัยได้: ถ้าโค้ดผ่าน test แต่ผลิตภัณฑ์ล้ม นั่นคือ description failure ให้ไปแก้ที่ข้อต่อที่ขาด ไม่ใช่ไปจูน prompt

ตัวอย่าง: test ของระบบคิวคลินิกผ่านหมด แต่พ่อแม่ที่ลูกป่วยและมีเวลาแค่สิบนาทีกลับยอมแพ้ก่อนหาเวลารอเจอ ให้กลับไปดูข้อต่อ Requirement ก่อน เขียน requirement ใหม่จากคำพูดของผู้ใช้และส่วน experience ของ brief แล้วค่อยเขียน test ใหม่

เข้าใจผิดบ่อย

"test ผ่านหมด แปลว่า requirement ถูกทำครบแล้ว" ผิด test ผ่านแต่ผู้ใช้ไม่พอใจ แปลว่า test เข้ารหัสเจตนาผิดตั้งแต่ต้น

สรุปสั้นๆ

User voice → Requirement → Technical spec → AI instruction เมื่อ test ผ่านแต่ผู้ใช้ไม่แฮปปี้ ให้แก้ต้นน้ำ (มักเป็น requirement) ไม่ใช่ไปแก้ prompt หรือโค้ด

Checkpoint 9 (เรียงลำดับ)

เรียงข้อต่อของ Description Chain สำหรับระบบแจ้งเตือนรับยาที่ร้านขายยา จากความต้องการของลูกค้าไปจนถึงคำสั่งที่ส่งให้ Claude:

  1. "ลูกค้าที่ใช้โทรศัพท์ปุ่มกดได้รับ SMS ภายใน 5 นาทีหลังยาพร้อม โดยไม่ต้องติดตั้งแอป"
  2. "ฉันไม่อยากมานั่งรอที่ร้านโดยไม่รู้ว่ายาเสร็จหรือยัง"
  3. "ระบบ POS ยิง webhook เข้า queue service ซึ่งเรียก SMS gateway"
  4. "ใช้ Python + FastAPI, ห้ามเก็บเบอร์ลง log, เขียน test ให้ครอบคลุมกรณี gateway ล่ม"
ดูเฉลย

2 → 1 → 3 → 4 เสียงผู้ใช้ → requirement ที่วัดได้ → technical spec → AI instruction
