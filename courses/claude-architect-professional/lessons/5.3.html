5.3 Human approval checkpoints ใน Claude Code และ Agent SDK

ต้นฉบับ: CertSafari 5.3

อ่านจบแล้วควรทำได้
  • อธิบายได้ว่าทำไมต้องวางจุดอนุมัติไว้ที่ action เสี่ยง ไม่ใช่ทุก action (approval fatigue)
  • เลือก permission mode ทั้ง 6 แบบให้เหมาะกับงาน และรู้ว่าจุดอนุมัติไหนรอดทุก mode
  • ไล่ลำดับการตัดสินสิทธิ์ใน SDK: hooks → deny → ask → mode → allow → canUseTool และทำนายผลได้
  • เขียน canUseTool ที่ส่งการเรียก tool ไปให้คนตัดสิน รวมถึงแก้ input ก่อนอนุมัติ
แนวคิดหลัก: วางคนไว้ตรงที่เสี่ยง

Agent บางครั้งทำสิ่งที่ผู้ใช้ไม่ได้ตั้งใจ เช่น ลบ remote branch หรือรัน migration ใส่ production เป้าหมายคือให้คนตรวจ action ที่เสี่ยง ไม่ใช่ทุก action เพราะถ้าถามทุกครั้ง คนจะกดอนุมัติตามความเคยชิน ข้อมูลที่บทเรียนอ้างถึงคือผู้ใช้ Claude Code กดอนุมัติ permission prompt ถึง 93%

1. ทำไม agent ต้องมีจุดอนุมัติโดยคน

ลองนึกถึงสัญญาณกันขโมยรถที่ดังทุกครั้งที่มีแมวเดินผ่าน ไม่นานทั้งซอยก็เลิกสนใจ ถึงวันที่มีโจรจริงก็ไม่มีใครหันไปดู permission prompt ก็เหมือนกัน ถ้าเด้งถามทุกการอ่านไฟล์ คนจะกด "อนุมัติ" แบบไม่อ่าน และพลาดตัวที่สำคัญจริง

หลักการออกแบบจึงเป็น: ปล่อยงานประจำ (อ่าน, แก้ไฟล์ในขอบเขตที่ตรวจแล้ว) ให้ผ่านไป แล้วเก็บ ความสนใจของคน ไว้ให้ action ที่ย้อนกลับยากหรือกระทบระบบภายนอก เช่น push, deploy, ลบข้อมูล, โอนเงิน

สรุปสั้นๆ

ถามทุกอย่าง = ไม่มีใครอ่านจริง ปล่อยงานประจำผ่าน แล้วให้คนดูเฉพาะจุดเสี่ยง

Checkpoint 1

ทีมหนึ่งตั้งให้ agent ถามอนุมัติทุก tool call รวมถึงการอ่านไฟล์ หลังผ่านไปสองสัปดาห์ น่าจะเกิดอะไร และควรแก้อย่างไร?

  1. ปลอดภัยที่สุดแล้ว ไม่ต้องแก้
  2. คนเริ่มกดอนุมัติแบบไม่อ่าน ควรปล่อยการอ่านและการแก้ไฟล์ประจำให้ผ่าน แล้วถามเฉพาะ action เสี่ยง
  3. ควรเปลี่ยนเป็น bypassPermissions ทั้งหมดเพื่อความเร็ว
  4. ควรเพิ่มคนอนุมัติเป็นสองคนต่อทุก call
ดูเฉลย

B approval fatigue ทำให้ด่านทุกด่านไร้ความหมาย C ตัดคนออกหมดแม้กับ action เสี่ยง D ยิ่งทำให้ล้า

2. Permission modes: คนต้องตรวจมากแค่ไหน

ใน Claude Code CLI สลับ mode ด้วย Shift+Tab ส่วนใน Agent SDK ตั้งผ่าน option permissionMode

Modeอะไรรันได้เลยโดยไม่ถามเหมาะกับ
defaultแค่การอ่านงาน sensitive ที่อยากดูเองทุก action
acceptEditsการอ่าน, การแก้ไฟล์ และคำสั่ง filesystem ทั่วไป (เช่น mkdir, touch, mv, cp) อย่างอื่นยังถามวนแก้โค้ดที่ตรวจทิศทางแล้ว
planการอ่าน (และคำสั่งที่ classifier อนุมัติ ถ้ามี auto mode) แต่ ไม่แตะ source file จนกว่าคนจะอนุมัติแผนอยากเห็นแผนก่อนลงมือ
autoทุกอย่าง โดยมี classifier เบื้องหลังตรวจคำสั่ง shell และ network request ว่าตรงกับสิ่งที่ผู้ใช้ขอหรือไม่งานยาวที่อยากลดการถาม แต่ยังมีตัวตรวจแทนคน (ไม่ได้ตัดคนออกทั้งหมด)
dontAskการอ่านไฟล์ใน working directory และ tool ที่อนุมัติไว้ล่วงหน้า อะไรที่จะต้องถาม จะถูกปฏิเสธทันที และไม่เรียก canUseToolCI ที่ไม่มีคนเฝ้าและต้องล็อกแน่น
bypassPermissionsเกือบทุกอย่าง ยกเว้น action ที่ไม่มี mode ไหนอนุมัติอัตโนมัติเฉพาะใน container หรือ VM ที่แยกขาดเท่านั้น

การรันแบบ headless ด้วย --dangerously-skip-permissions จะ ปฏิเสธ call ส่วนน้อยที่ยังต้องถาม (เพราะไม่มีคนให้ถาม)

จุดอนุมัติที่รอดทุก mode

  • tool ที่ตรงกับ ask rule ที่ตั้งไว้ชัดเจน
  • connector tool ที่องค์กรตั้งให้ถาม (ในกรณีที่การตั้งค่านั้นมีผลถึง Claude Code)
  • tool ที่ต้องโต้ตอบกับผู้ใช้: AskUserQuestion และ MCP tool ที่ทำเครื่องหมาย requiresUserInteraction
  • rm และ rmdir ที่ลบ path สำคัญ (critical path)
  • กลไกป้องกันของการส่งข้อความข้าม session

องค์กรปิด mode ที่หลวมที่สุดได้ผ่าน managed settings: permissions.disableBypassPermissionsMode: "disable" ปิด bypassPermissions และ permissions.disableAutoMode: "disable" เอา auto mode ออก

สรุปสั้นๆ

default (อ่านอย่างเดียว) → acceptEdits (+แก้ไฟล์) → plan (ดูแผนก่อน) → auto (classifier ช่วย) → dontAsk (ไม่ถาม = ปฏิเสธ) → bypassPermissions (เกือบทุกอย่าง, ใช้ใน sandbox เท่านั้น) ask rule, tool ที่ต้องโต้ตอบ และการลบ critical path ยังถามเสมอ

Checkpoint 2 (จับคู่)

จับคู่ mode กับพฤติกรรม:

  1. plan
  2. acceptEdits
  3. auto
  4. dontAsk
  5. bypassPermissions

ดูเฉลย

Checkpoint 3

หัวหน้าฝ่าย security ต้องการให้ทุกการรัน terraform apply ต้องมีคนอนุมัติ ไม่ว่า developer จะสลับไป mode ไหน ควรทำอย่างไร?

  1. บอกทีมให้ใช้ default mode เสมอ
  2. เพิ่ม ask rule สำหรับ Bash(terraform apply *)
  3. ใส่ Bash ใน allow rules
  4. ใช้ acceptEdits
ดูเฉลย

B ask rule รอดการเปลี่ยน mode เพราะถูกตรวจก่อนขั้น mode A พึ่งวินัยของคน C ยิ่งปล่อยผ่าน D ไม่ได้บังคับเรื่องนี้

Checkpoint 4

job ใน CI รันตอนตีสองโดยไม่มีใครเฝ้า ต้องการให้ call ที่ไม่ได้อนุมัติไว้ถูกปฏิเสธทันทีแทนที่จะค้างรอ ควรตั้งค่าอย่างไร?

  1. ตั้ง dontAsk และระบุ tool ที่ปลอดภัยสำหรับ CI ไว้ใน allowedTools
  2. ตั้ง default แล้วให้ canUseTool รอคนตอบ
  3. ตั้ง bypassPermissions บน runner ที่มี credential ของ production
  4. ตั้ง plan
ดูเฉลย

A dontAsk ปฏิเสธทุกอย่างที่จะต้องถาม และรันได้เฉพาะที่ allow ไว้ B จะค้างเพราะไม่มีคน C อันตรายบนเครื่องที่ไม่ได้แยกขาด D ไม่ได้ทำงานจริง

3. คนอยู่ตรงไหนในลำดับการตัดสินสิทธิ์

ใน Agent SDK ทุก tool call ถูกตรวจตามลำดับนี้ ขั้นแรกที่ตัดสินได้ ชนะ ขั้นหลังไม่ได้เห็นอีก:

  1. Hooks เช่น PreToolUse อนุญาต, ปฏิเสธ, ให้ถาม (permissionDecision: "ask") หรือแก้ไข input ได้
  2. Deny rules บล็อกโดยไม่ถาม และขั้นหลังยกเลิกไม่ได้
  3. Ask rules ถามทุกครั้งที่ใช้ tool นั้น
  4. Permission mode
  5. Allow rules เช่น Bash(npm test) หรือ Read ถ้าใส่ชื่อ tool เปล่าๆ อย่าง "Bash" เท่ากับอนุมัติทั้ง tool
  6. canUseTool callback ถามคนตอน runtime
ผลที่ตามมาจากลำดับนี้
  • plan mode: tool ที่เขียนไฟล์ถูกส่งไป canUseTool แม้จะมี allow rule ตรง เพราะ mode อยู่ก่อน allow
  • allow แบบชื่อเปล่า: canUseTool ไม่มีวันเห็น tool นั้น เพราะถูกอนุมัติที่ขั้น 5 ไปแล้ว
  • PreToolUse hook รอดแม้ใน bypassPermissions เพราะ hook อยู่ขั้น 1 ก่อนขั้น mode
  • dontAsk: สิ่งที่จะต้องถามถูกปฏิเสธที่ขั้น mode ไม่ไปถึง canUseTool
  • deny rule ย้อนกลับจากใน callback ไม่ได้ เพราะตัดสินไปแล้วตั้งแต่ขั้น 2

ตัวอย่าง hook ที่บังคับให้ถามก่อนเรียก tool โอนเงิน ไม่ว่า mode อะไร:

async def require_approval(input_data, tool_use_id, context):
    if input_data["tool_name"] == "mcp__bank__transfer":
        return {"hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "ask",
        }}
    return {}
เข้าใจผิดบ่อย

"ใน dontAsk mode call ที่ไม่ได้อนุมัติจะไปรอที่ canUseTool" ไม่ใช่ ถูกปฏิเสธทันที ไม่มีคนตัดสิน

"bypassPermissions ข้ามทั้ง hook และ ask rule" ไม่ใช่ สองอย่างนี้อยู่ก่อนขั้น mode จึงยังมีผล

"ใส่ tool ใน allowedTools แล้ว canUseTool ยังได้ตรวจทุก call อยู่" ไม่ใช่ allow แบบชื่อเปล่าอนุมัติทั้ง tool ก่อนถึง callback

สรุปสั้นๆ

hooks → deny → ask → mode → allow → canUseTool ขั้นแรกที่ตัดสินคือคำตอบ อยากบังคับให้คนเห็นทุก mode ใช้ hook หรือ ask rule อยากให้ callback เห็น อย่าใส่ allow แบบชื่อเปล่า

ลองเดาก่อน

agent อยู่ใน plan mode และมี allow rule สำหรับ Edit เมื่อ Claude พยายามแก้ไฟล์ call นี้จะไปจบที่ไหน?

  1. รันได้เลยเพราะมี allow rule
  2. ถูกส่งไปที่ canUseTool ให้คนตัดสิน
  3. ถูก deny อัตโนมัติ
ดูเฉลย

B plan mode ตัดสินที่ขั้น mode ก่อนถึง allow rule และส่ง write tool ไปให้ callback

ลองเดาก่อน

CI job ตั้ง dontAsk พร้อม allow Bash(pytest *) และ Read แล้ว Claude พยายามรัน git push origin main จะเกิดอะไร?

  1. รอ canUseTool จนหมดเวลา
  2. ถูกปฏิเสธทันที ไม่มีคนเกี่ยวข้อง และไม่เรียก canUseTool
  3. รันได้เพราะ git เป็นคำสั่งพื้นฐาน
ดูเฉลย

B ไม่ตรงกับ allow rule ใด และ dontAsk เปลี่ยนสิ่งที่จะต้องถามให้เป็นการปฏิเสธ

Checkpoint 5

แอป SDK ตั้ง allowedTools: ["Read", "Write"] และมี canUseTool ที่แสดงทุกการเขียนไฟล์ให้ reviewer ดู แต่ reviewer ไม่เคยเห็นการเขียนไฟล์สักครั้ง ทั้งที่ไฟล์ถูกแก้ไปแล้ว สาเหตุและวิธีแก้คืออะไร?

  1. callback เขียนผิด ต้อง return allow ก่อน
  2. "Write" แบบชื่อเปล่าอนุมัติที่ขั้น allow ก่อนถึง callback ให้เอา Write ออกจาก allowedTools
  3. ต้องเปลี่ยนเป็น bypassPermissions callback จึงจะทำงาน
  4. ต้องเพิ่ม deny rule ให้ Write
ดูเฉลย

B allow rule ตัดสินก่อน callback C ยิ่งข้ามการตรวจ D จะบล็อก Write ทั้งหมดโดยไม่ไปถึงคนเลย

Checkpoint 6

สตาร์ทอัพ HR tech มี tool delete_employee_record ที่ต้องให้คนอนุมัติทุกครั้ง แม้ทีม ops จะรัน agent ใน bypassPermissions บน sandbox ควรใช้กลไกไหน?

  1. ลงทะเบียน PreToolUse hook ที่คืนค่า "ask" สำหรับ tool นั้น
  2. ใส่ tool นั้นใน allowedTools
  3. เขียนใน system prompt ว่า "ถามก่อนลบเสมอ"
  4. ตั้ง canUseTool ให้ถามเฉพาะ tool นั้น
ดูเฉลย

A hook อยู่ขั้นแรกจึงรอด bypassPermissions B ทำให้ผ่านอัตโนมัติ C เป็นแค่คำขอที่ model อาจไม่ทำตาม D ไม่ถูกเรียกเพราะ bypassPermissions ตัดสินที่ขั้น mode ไปแล้ว

4. canUseTool: ส่ง tool call ไปให้คนตัดสิน

canUseTool ถูกเรียกเมื่อไม่มีขั้นก่อนหน้าตัดสินได้ หรือเมื่อ Claude เรียก AskUserQuestion มันได้รับ ชื่อ tool, input ของ tool และ context object เช่น input ของ Bash มี command, description, timeout ส่วน Write มี file_path และ content

ผลลัพธ์PythonTypeScript
อนุญาต (แก้ input ได้)PermissionResultAllow(updated_input=...){ behavior: "allow", updatedInput }
ปฏิเสธ (Claude อ่าน message ได้)PermissionResultDeny(message=...){ behavior: "deny", message }

context มี suggestions (รายการ PermissionUpdate) ที่ถ้าอนุมัติแล้วบันทึกเป็น rule ครั้งต่อไป call แบบเดียวกันจะไม่ต้องถามอีก ฝั่ง TypeScript context ยังมี AbortSignal ด้วย

async def review(tool_name, tool_input, context):
    if tool_name == "Bash" and "DROP TABLE" in tool_input["command"]:
        return PermissionResultDeny(message="ห้ามลบตาราง ให้สร้าง backup ก่อน")
    if tool_name == "Write" and tool_input["file_path"].startswith("/etc/"):
        safe = {**tool_input, "file_path": "/tmp/staging" + tool_input["file_path"]}
        return PermissionResultAllow(updated_input=safe)   # อนุมัติแบบแก้ไข
    return PermissionResultAllow(updated_input=tool_input)

ใน Python ถ้าใช้ can_use_tool ต้องเปิด stream ค้างไว้ วิธีที่ใช้กันคือใส่ hook หลอกที่คืน {"continue_": True}

reviewer ทำอะไรได้บ้าง (6 แบบ)

  1. อนุมัติ
  2. อนุมัติพร้อมแก้ ผ่าน updated_input / updatedInput
  3. อนุมัติและจำไว้ โดยบันทึก rule จาก suggestions
  4. ปฏิเสธ พร้อม message ที่ Claude อ่าน
  5. เสนอทางอื่น ใส่ใน message ของการปฏิเสธ
  6. เปลี่ยนทิศทางทั้งหมด ผ่าน streaming input
เข้าใจผิดบ่อย

"ส่ง tools array ไปแล้ว คำถามชี้แจงของ Claude จะมาถึง callback เอง" ไม่ใช่ ถ้ากำหนด tools เองต้องใส่ AskUserQuestion ไว้ด้วย ไม่อย่างนั้นคำถามไม่มีทางมาถึง canUseTool

"deny rule ที่ตั้งไว้ ปลดได้จากใน callback" ไม่ได้ deny ตัดสินไปก่อนแล้ว callback ไม่ได้เห็น call นั้น

สรุปสั้นๆ

canUseTool คือขั้นสุดท้ายที่ให้คนตัดสิน: allow (แก้ input ได้) หรือ deny (มี message) ใช้ suggestions จำการตัดสิน และอย่าลืมใส่ AskUserQuestion ถ้ากำหนด tools เอง

Checkpoint 7

tech lead ต้องการว่า ห้ามมีไฟล์ไหนถูกแก้ก่อนที่เธอจะอนุมัติ แม้ทีมจะมี allow rule สำหรับ Edit อยู่ใน settings ควรใช้วิธีไหน?

  1. ใช้ plan mode ซึ่งส่งการแก้ไฟล์ไปที่ canUseTool แม้มี allow rule ตรง
  2. ใช้ acceptEdits
  3. ใช้ dontAsk
  4. เพิ่ม Edit ใน allowedTools อีกรอบ
ดูเฉลย

A plan mode ตัดสินก่อนขั้น allow B อนุมัติ edit อัตโนมัติ C จะปฏิเสธหรือปล่อยตาม allow โดยไม่มีคน D ยิ่งข้าม callback

  1. PermissionResultDeny(message=...)
  2. PermissionResultAllow(updated_input=...) ที่มีคำสั่งที่แก้แล้ว
  3. {"permissionDecision": "ask"}
  4. PermissionResultAllow() แล้วส่งคำสั่งใหม่ผ่าน system prompt
ดูเฉลย

B updated_input คือ field ที่ทำให้ tool รันด้วย input ที่ reviewer แก้ (TypeScript ใช้ updatedInput) A ปฏิเสธ C เป็นรูปแบบของ hook ไม่ใช่ callback

Checkpoint 9

แอป SDK กำหนด tools: ["Read", "Grep", "Bash"] และมี canUseTool ที่จะแสดงคำถามของ Claude ให้ผู้ใช้ตอบ แต่ไม่เคยมีคำถามโผล่มาเลย เกิดอะไรขึ้น?

  1. Claude ถูกห้ามถามคำถามใน SDK
  2. ไม่ได้ใส่ AskUserQuestion ใน tools คำถามจึงไม่มีทางไปถึง callback
  3. ต้องใช้ dontAsk ก่อน
  4. ต้องเพิ่ม deny rule ให้ Bash
ดูเฉลย

B เมื่อกำหนดรายชื่อ tool เอง ต้องรวม AskUserQuestion ไว้ด้วย dontAsk ยิ่งทำให้ไม่ถึง callback
