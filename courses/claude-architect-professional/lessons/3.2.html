3.2 MCP authorization: discovery, client registration และ scoped token

ต้นฉบับ: CertSafari 3.2

อ่านจบแล้วควรทำได้
  • เลือกได้ว่า MCP server ตัวไหนควรใช้ OAuth และตัวไหนควรดึง credential จาก environment โดยดูจาก transport
  • ไล่ขั้นตอนที่ client ใช้ค้นหา (discovery) authorization server และลงทะเบียนตัวเอง (registration) ได้ พร้อมชี้จุดที่ถูกโจมตีได้
  • หาช่องโหว่เรื่อง audience ของ token ได้ รวมถึงการส่ง token ต่อไปยัง API ปลายทาง (token passthrough)
  • แยก 401 กับ 403 ออกจากกัน และออกแบบการขอ scope เพิ่มแบบแคบ (step-up authorization) ได้
แนวคิดหลัก: token ผูกกับ server ตัวเดียว

Audience-bound access token คือ token ที่ออกให้ใช้กับ MCP server ตัวเดียว ซึ่งระบุด้วย canonical URI (URI มาตรฐานที่ใช้เรียกชื่อ server ตัวนั้น) server ต้องปฏิเสธ token ที่ออกให้ server ตัวอื่น และห้ามส่ง token ที่ได้รับต่อไปให้บริการอื่นเด็ดขาด

เปรียบเหมือนบัตรผ่านงานสัมมนาที่พิมพ์ชื่อห้องไว้ ถึงจะเป็นบัตรจริงจากผู้จัดงาน แต่ถ้าชื่อห้องไม่ตรง คนเฝ้าประตูก็ต้องไม่ให้เข้า

1. Transport เป็นตัวกำหนดว่า MCP server จะยืนยันตัวตนแบบไหน

คำถามแรกที่ต้องถามเวลา audit MCP server ไม่ใช่ "ใช้ OAuth หรือยัง" แต่เป็น "server นี้คุยกับ client ผ่าน transport อะไร" เพราะ spec ของ MCP กำหนดกลไกต่างกันตาม transport:

Transportกลไกที่ควรใช้ช่องโหว่ที่ต้องมองหา
HTTP-based (server อยู่บนเครือข่าย)OAuth 2.1 ตาม MCP authorization specserver ที่รับ request โดยไม่มี token เลย หรือใช้ static key ตัวเดียวแชร์กันทุกคน
STDIO (server เป็น child process บนเครื่องเดียวกัน)ไม่ใช้ spec นี้ ให้ดึง credential จาก environment แทนprocess อื่นใน environment เดียวกันอ่าน secret พวกนั้นได้
Transport อื่นๆMCP ไม่ได้กำหนดกลไกไว้ ให้ทำตาม security best practice ของ protocol นั้นๆขึ้นกับ protocol

เหตุผลที่ STDIO ไม่ใช้ OAuth: server ตัวนั้นถูก client spawn ขึ้นมาเป็น process ลูกบนเครื่องเดียวกัน ไม่มีเครือข่ายคั่นกลาง การทำ OAuth flow เต็มรูปแบบเลยไม่มีประโยชน์ แต่ข้อแลกคือ secret ที่อยู่ใน environment variable ก็มองเห็นได้จาก process อื่นที่อยู่ใน environment เดียวกัน

เข้าใจผิดบ่อย

"MCP server ทุกตัวต้องทำ OAuth 2.1" ไม่ใช่ OAuth ใช้กับ transport แบบ HTTP เท่านั้น STDIO server ควรอ่าน credential จาก environment ส่วน transport อื่นใช้แนวทางของ protocol ตัวเอง

สรุปสั้นๆ

HTTP → OAuth 2.1, STDIO → credential จาก environment, อื่นๆ → best practice ของ protocol นั้น ดู transport ก่อนเสมอ แล้วค่อยตัดสินว่า "ขาดอะไร"

Checkpoint 1 (จับคู่)

จับคู่ MCP server แต่ละตัวกับวิธียืนยันตัวตนที่เหมาะสม:

  1. server อ่านไฟล์ในเครื่องที่ IDE ของนักพัฒนา spawn ขึ้นมาเป็น child process
  2. server ภายในบริษัทที่เปิดเป็น endpoint https://tools.corp.example/mcp
  3. server ที่ทีมทดลองต่อผ่าน message queue ของตัวเอง ซึ่ง MCP ไม่ได้นิยามกลไก auth ไว้
  1. OAuth 2.1 ตาม MCP authorization spec
  2. ดึง credential จาก environment
  3. ใช้ security best practice ของ protocol นั้น
ดูเฉลย

1-B, 2-A, 3-C STDIO คือ process ในเครื่อง จึงใช้ environment, HTTP ใช้ OAuth 2.1 ส่วน transport ที่ MCP ไม่ได้กำหนดก็ต้องพึ่งแนวทางของ protocol นั้นเอง

2. Client ค้นหา authorization server ได้ยังไง

Client ที่เพิ่งเจอ MCP server ครั้งแรกไม่จำเป็นต้องรู้ล่วงหน้าว่าจะไปขอ token จากที่ไหน มันค้นเองได้จากการลองเรียกดูก่อน:

  1. Client ส่ง request แรก โดยไม่มี token
  2. Server ตอบ 401 Unauthorized พร้อม header WWW-Authenticate ที่มี URL ของ Protected Resource Metadata (field resource_metadata) และอาจมี scope เป็นคำใบ้ว่าควรขอ scope อะไร
  3. Client ไปอ่านเอกสาร metadata นั้น ซึ่งอยู่ที่ path แบบ well-known: /.well-known/oauth-protected-resource จะอยู่ที่ root ของโดเมนหรือต่อท้ายด้วย path ของ MCP endpoint ก็ได้ ในเอกสารนี้จะมี scopes_supported ด้วย
  4. จากนั้นไปอ่าน metadata ของ authorization server ซึ่ง server ต้องมีอย่างน้อยหนึ่งแบบ: OAuth 2.0 Authorization Server Metadata (/.well-known/oauth-authorization-server) หรือ OpenID Connect Discovery (/.well-known/openid-configuration) และ client ต้องรองรับทั้งสองแบบ
  5. ตรวจว่า authorization server รองรับ PKCE หรือไม่ ถ้าไม่มี field code_challenge_methods_supported แปลว่าไม่รองรับ PKCE และ client ต้องหยุด ห้ามทำต่อ

ตัวอย่าง challenge ที่ server ส่งกลับมา (ตัวอย่างนี้เขียนเอง):

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://notes.example.com/.well-known/oauth-protected-resource", scope="notes:read"
เช็กลิสต์ตอน audit discovery
  • endpoint ของ authorization server ทุกตัวต้องเป็น HTTPS
  • redirect URI ต้องเป็น localhost หรือ HTTPS เท่านั้น
  • ไม่มี code_challenge_methods_supported = ไม่มี PKCE = client ต้องปฏิเสธ ไม่ใช่ "ลองต่อไปก่อน"
เข้าใจผิดบ่อย

"ได้ token มาใช้งานได้จริง แปลว่า flow ถูกต้องแล้ว" ไม่ใช่ ถ้า metadata ของ authorization server ไม่ประกาศว่ารองรับ PKCE แต่ client ยังเดินหน้าจนได้ token มา นั่นคือช่องโหว่ฝั่ง client ถึง token จะใช้ได้ก็ตาม เพราะ spec บังคับให้ client หยุดตั้งแต่ตอนเห็นว่าไม่มี PKCE

สรุปสั้นๆ

เรียกแบบไม่มี token → ได้ 401 พร้อมที่อยู่ของ metadata → อ่าน Protected Resource Metadata → อ่าน metadata ของ authorization server (รองรับทั้ง OAuth และ OIDC) → ไม่มี PKCE ให้หยุด

Checkpoint 2

ทีม security ตรวจ log ของ MCP client แล้วพบว่า metadata ของ authorization server ตัวหนึ่งไม่มี code_challenge_methods_supported แต่ client ยังทำ OAuth flow ต่อจนได้ access token ที่ใช้เรียก tool ได้ปกติ ควรสรุปผลการ audit ว่าอย่างไร?

  1. ไม่มีปัญหา เพราะ token ที่ได้มาใช้งานได้และยังไม่หมดอายุ
  2. แก้ได้ด้วยการลดอายุ token ให้สั้นลง
  3. เป็นปัญหาฝั่ง MCP server เพราะควรส่ง 403 แทน 401
  4. เป็นช่องโหว่ฝั่ง client เพราะเมื่อไม่เห็นการรองรับ PKCE client ต้องปฏิเสธที่จะทำ flow ต่อ
ดูเฉลย

D ไม่มี field นี้แปลว่า server ไม่รองรับ PKCE และ spec กำหนดให้ client หยุด การที่ได้ token ที่ใช้งานได้ไม่ได้แปลว่าปลอดภัย ส่วน 401/403 กับอายุ token ไม่เกี่ยวกับปัญหานี้

3. ลงทะเบียน client ที่ server ไม่เคยรู้จักมาก่อน

ก่อนจะขอ token ได้ authorization server ต้องรู้ก่อนว่า client คือใคร MCP กำหนดลำดับความสำคัญของวิธีลงทะเบียนไว้ ให้ client ไล่จากบนลงล่าง:

  1. ใช้ข้อมูล client ที่ลงทะเบียนไว้แล้ว (pre-registered) ถ้ามีความสัมพันธ์กันมาก่อน
  2. Client ID Metadata Document ถ้า authorization server ประกาศว่ารองรับ (field client_id_metadata_document_supported)
  3. Dynamic Client Registration ผ่าน registration_endpoint ซึ่งตอนนี้ deprecated แล้ว เก็บไว้เพื่อ backward compatibility เท่านั้น
  4. ให้ผู้ใช้กรอกรายละเอียด client เอง

Client ID Metadata Document ทำงานยังไง

แทนที่จะลงทะเบียนแล้วได้ client ID เป็นสตริงสุ่ม วิธีนี้ให้ client_id เป็น HTTPS URL เลย และ URL นั้นเสิร์ฟ JSON ที่บรรยายตัว client:

// https://app.example.dev/oauth/client.json
{
  "client_id": "https://app.example.dev/oauth/client.json",
  "client_name": "Example Notes Agent",
  "redirect_uris": ["https://app.example.dev/callback"]
}
  • field ที่ต้องมีคือ client_id, client_name, redirect_uris (ใส่ client_uri, logo_uri, grant_types, response_types, token_endpoint_auth_method เพิ่มได้)
  • client_id ในเอกสารต้องตรงกับ URL ที่เสิร์ฟเอกสารทุกตัวอักษร
  • authorization server ตรวจ redirect URI ที่ client ส่งมากับ redirect_uris ในเอกสารทุกครั้ง

จุดอ่อน: redirect แบบ localhost เปิดช่องให้ปลอมตัว

Metadata document เป็น URL สาธารณะ ใครก็อ่านได้ ถ้าใน redirect_uris มี localhost อยู่ ผู้โจมตีสามารถ:

  1. เอา metadata URL ของแอปจริงมาใช้เป็น client_id ของตัวเอง
  2. เปิด listener บน localhost port ที่ระบุไว้ในเอกสารบนเครื่องเหยื่อ
  3. รอดัก authorization code ที่ถูก redirect กลับมา

หน้า consent จะแสดงชื่อแอปจริง ผู้ใช้เลยกดอนุญาตโดยไม่สงสัย วิธีลดความเสี่ยง:

  • แสดง hostname ของ redirect บนหน้า consent
  • เตือนเมื่อ client มี redirect เป็น localhost อย่างเดียว
  • บังคับ attestation (การพิสูจน์ว่าเป็นแอปตัวจริง)
  • ใช้ allowlist ของโดเมน หรือตรวจ reputation ของโดเมน
เข้าใจผิดบ่อย

"Dynamic Client Registration เป็นวิธีหลักสำหรับ client ที่ไม่เคยเจอกัน" ไม่ใช่แล้ว DCR ถูก deprecate ถ้า server ประกาศรองรับ Client ID Metadata Document ให้ใช้วิธีนั้นก่อน DCR เป็นแค่ทางสำรอง

สรุปสั้นๆ

Pre-registered → Client ID Metadata Document → DCR (deprecated) → ให้ผู้ใช้กรอก ระวัง redirect แบบ localhost ที่เปิดให้คนอื่นแอบอ้าง metadata URL ของเราได้

Checkpoint 3

MCP client ตัวใหม่ต้องเชื่อมกับ authorization server ที่ไม่เคยติดต่อกันมาก่อน metadata ของ server ประกาศทั้ง client_id_metadata_document_supported และ registration_endpoint client ควรลงทะเบียนด้วยวิธีไหน?

  1. Dynamic Client Registration เพราะมี endpoint ให้ใช้และ server ออก client ID ให้ทันที
  2. ขอให้ผู้ใช้พิมพ์ client ID เข้ามาเอง
  3. Client ID Metadata Document โดยใช้ HTTPS URL ของตัวเองเป็น client_id
  4. ส่ง request โดยไม่มี client ID แล้วรอ server สร้างให้
ดูเฉลย

C ไม่มีความสัมพันธ์เดิม (pre-registered ใช้ไม่ได้) และ server รองรับ Client ID Metadata Document ซึ่งอยู่ลำดับก่อน DCR ที่ deprecated แล้ว การให้ผู้ใช้กรอกเป็นทางสุดท้าย

4. ผูก token กับ server ตัวเดียว และห้ามส่งต่อ

Parameter resource และ canonical URI

Client ต้องใส่ parameter resource ทั้งใน authorization request และ token request โดยค่าคือ canonical URI ของ MCP server ที่จะใช้ token นั้น กติกาคือ:

  • ต้องมี scheme (เช่น https://)
  • ห้ามมี fragment (ส่วน #...)
  • แนะนำให้ไม่มี slash ปิดท้าย
  • ใส่ port หรือ path ได้ถ้าจำเป็นต้องใช้ระบุตัว server
ค่า resourceใช้ได้ไหมเหตุผล
https://notes.example.com/mcpได้มี scheme, มี path ระบุ server
https://notes.example.com:9443ได้port ช่วยระบุ server
https://notes.example.com/team-a/mcpได้path หลายระดับก็ได้
notes.example.comไม่ได้ไม่มี scheme
https://notes.example.com#mcpไม่ได้มี fragment

การส่งและเก็บ token

  • ส่ง access token ใน header Authorization: Bearer ... เท่านั้น ห้ามใส่ใน query string (URL ไปโผล่ใน log, history, proxy ได้ง่าย)
  • refresh token ต้องเก็บเป็นความลับ และ client ห้ามสมมติว่าจะได้ refresh token เสมอ

Audience validation

MCP server ต้องปฏิเสธทุก token ที่ไม่ได้ออกมาให้ตัวเองโดยเฉพาะ แม้ลายเซ็นถูกต้องและยังไม่หมดอายุก็ตาม เพราะลายเซ็นบอกแค่ว่า "ใครออก" ไม่ได้บอกว่า "ออกให้ใคร"

Token passthrough และ confused deputy

สมมติ MCP server ของเราต้องเรียก API ปลายทางอีกตัว ถ้ามันเอา token ที่ client ส่งมาไปใช้ต่อทั้งดุ้น นี่คือ token passthrough และทำให้เกิด confused deputy: API ปลายทางเห็น token ที่ถูกต้อง แต่ไม่รู้ว่าถูกส่งผ่านตัวกลางมา ตัวกลางเลยกลายเป็น "ตัวแทนที่ถูกหลอกใช้" ให้ทำสิ่งที่ผู้เรียกไม่ควรทำได้โดยตรง และการควบคุม/audit ที่ server ตัวกลางก็ถูกข้ามไป

วิธีแก้มี 2 ส่วนคู่กัน:

  1. MCP server ตรวจ audience ของ token ที่รับเข้ามา (ต้องออกให้ตัวเองเท่านั้น)
  2. เวลาเรียก API ปลายทาง ให้ใช้ token แยกต่างหาก ที่ออกมาสำหรับ API นั้นโดยเฉพาะ
เข้าใจผิดบ่อย

"token ที่ authorization server ของบริษัทเซ็นมา ใช้กับ MCP server ไหนของบริษัทก็ได้ และส่งต่อไปเลยจะได้ไม่ต้องขอ token ใหม่" ไม่ใช่ token ผูกกับ canonical URI ของ server ตัวเดียว การส่งต่อคือ token passthrough ที่สร้าง confused deputy

"แก้ passthrough ได้ด้วยการลดอายุ token หรือใช้ลายเซ็นที่แข็งแรงขึ้น" ไม่ใช่ ปัญหาอยู่ที่ audience ไม่ใช่ความแข็งแรงของ token สิ่งที่แก้ได้คือ audience validation + token แยกสำหรับปลายทาง

ลองเดาก่อน

MCP server ได้รับ token ที่ลายเซ็นถูกต้อง ยังไม่หมดอายุ แต่ออกให้ MCP server อีกตัวหนึ่ง ควรรับไหม? คำตอบคือ ไม่รับ ลายเซ็นพิสูจน์แค่ผู้ออก ไม่ได้พิสูจน์ผู้รับที่ตั้งใจไว้

สรุปสั้นๆ

ใส่ resource = canonical URI ทั้งตอนขอ code และขอ token, ส่ง token ทาง header, server ตรวจ audience ทุกครั้ง และใช้ token ใหม่เมื่อเรียกบริการปลายทาง

Checkpoint 4

MCP server "expense-tools" รับ bearer token จาก client แล้วเอา token เดิมแนบไปเรียก API ระบบบัญชีภายในทันทีโดยไม่ตรวจอะไร ข้อสรุปของการ audit คืออะไร?

  1. ไม่มีปัญหา เพราะ token มาจาก authorization server ของบริษัทเดียวกัน
  2. ควรลดอายุ token เหลือ 5 นาทีเพื่อลดความเสี่ยง
  3. เป็น token passthrough ต้องตรวจ audience ที่ MCP server และใช้ token แยกตอนเรียก API บัญชี
  4. ควรย้าย token ไปไว้ใน query string เพื่อให้ API บัญชีอ่านได้ง่าย
ดูเฉลย

C การส่ง token ของผู้ใช้ต่อไปให้ API อื่นคือ token passthrough ทำให้เกิด confused deputy การลดอายุไม่แก้ต้นเหตุ ส่วน query string ห้ามใช้อยู่แล้ว

Checkpoint 5

Client กำลังขอ token สำหรับ MCP server ที่เปิดอยู่ที่ https://docs.example.org:8443/mcp ค่า resource แบบไหนถูกต้อง? (เลือกได้มากกว่าหนึ่ง)

  1. https://docs.example.org:8443/mcp
  2. docs.example.org:8443/mcp

ดูเฉลย

A, D canonical URI ต้องมี scheme (B ไม่มี) และห้ามมี fragment (C มี) และต้องใส่ resource ทั้งสอง request

5. 401 กับ 403 และการขอ scope เพิ่มเฉพาะตอนจำเป็น

StatusความหมายClient ควรทำอะไร
401ต้อง authorize หรือ token ใช้ไม่ได้ทำ discovery แล้วขอ token
403token ใช้ได้ แต่ scope ไม่พออ่าน challenge insufficient_scope แล้วทำ step-up
400request ผิดรูปแบบแก้ request ไม่ต้อง authorize ใหม่

Step-up authorization

เมื่อเจอ 403 พร้อม error="insufficient_scope" client ทำแบบนี้:

  1. รวม scope ที่เคยขอไปแล้ว กับ scope ที่ระบุใน challenge (union ไม่ใช่แทนที่)
  2. ขอ authorize ใหม่ด้วยชุด scope รวมนั้น
  3. retry request เดิม
  4. ถ้าลองไม่กี่ครั้งแล้วยังไม่ผ่าน ให้หยุดและถือว่าเป็นความล้มเหลวถาวร ไม่วนไม่รู้จบ
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope", scope="notes:write"

# client เคยขอ notes:read → ขอใหม่เป็น "notes:read notes:write"

Scope ตอนเริ่มต้น

  • ถ้า 401 แรกมีคำใบ้ scope ให้ขอตามนั้น
  • ถ้าไม่มีคำใบ้ client จะขอทุก scope ใน scopes_supported ซึ่งทำให้ได้สิทธิ์เกินจำเป็นตั้งแต่ครั้งแรก (over-grant)

เพราะฉะนั้นฝั่ง server ควรใส่ scope ใน challenge 401 เสมอ เพื่อให้ client ขอแค่ที่ต้องใช้จริง แล้วค่อย step-up ทีหลัง (หลัก least privilege)

เข้าใจผิดบ่อย

"403 แปลว่า token หมดอายุ ให้ login ใหม่" ไม่ใช่ 403 คือ token ยังใช้ได้แต่ scope ไม่พอ ถ้า login ใหม่ด้วย scope เดิม ก็จะได้สิทธิ์ชุดเดิมกลับมาและเจอ 403 ซ้ำ ต้อง step-up ด้วย scope ที่รวมของใหม่เข้าไป

สรุปสั้นๆ

401 = ไปเอา token, 403 = ขอ scope เพิ่มแบบ union, 400 = แก้ request server ควรให้คำใบ้ scope ใน 401 ไม่อย่างนั้น client จะขอทุก scope ตั้งแต่ต้น

Checkpoint 6

Agent เรียก tool "delete_note" ด้วย token ที่ยังไม่หมดอายุและผ่าน audience แล้ว แต่ token มีแค่ notes:read server ควรตอบแบบไหน และ client ควรทำอะไร?

  1. 401 แล้ว client ทำ discovery ใหม่ตั้งแต่ต้น
  2. 403 แล้ว client login ใหม่ด้วย scope ชุดเดิมจนกว่าจะผ่าน
  3. 400 แล้ว client แก้รูปแบบ request
  4. 403 พร้อม error="insufficient_scope" แล้ว client ขอ authorize ใหม่ด้วย scope เดิมรวมกับ scope ที่ขาด
ดูเฉลย

D token ใช้ได้แต่สิทธิ์ไม่พอ = 403 insufficient_scope แล้ว step-up แบบ union B ผิดเพราะ scope เดิมจะได้ผลเดิม และต้องหยุดหลังลองไม่กี่ครั้ง

Checkpoint 7

ทีมพบว่า token ที่ client ได้มาครั้งแรกมี scope admin:write ทั้งที่ผู้ใช้แค่จะอ่านเอกสาร ตรวจแล้วพบว่า challenge 401 ของ server ไม่มี scope เลย สาเหตุและวิธีแก้ที่น่าจะถูกที่สุดคือ?

  1. client ขอทุก scope ใน scopes_supported เพราะไม่มีคำใบ้ ให้ server ใส่ scope ใน challenge 401
  2. authorization server มีบั๊กออก scope เกิน ต้องเปลี่ยน authorization server
  3. token ถูกส่งต่อแบบ passthrough จาก server อื่น
  4. ควรตอบ 403 แทน 401 ในครั้งแรก
ดูเฉลย

A เมื่อไม่มีคำใบ้ client จะขอทุก scope ที่ server ประกาศว่ารองรับ จึง over-grant ตั้งแต่ต้น การใส่คำใบ้ scope ที่แคบใน 401 แก้ได้ตรงจุด
