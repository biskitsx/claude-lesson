5.4 HIPAA, BAAs and zero data retention for Claude

ต้นฉบับ: CertSafari 5.4

อ่านจบแล้วควรทำได้
  • บอกได้ว่าบน Claude แต่ละช่องทาง ใครเป็นคน process prompt กับ output และ control ไหนตามมาจากข้อนั้น
  • อธิบายได้ว่า zero data retention (ZDR) ครอบคลุมอะไร ไม่ครอบคลุมอะไร และทำไม API ยังรับ feature ที่ไม่ eligible อยู่
  • เปิด HIPAA readiness ได้ ทำนายได้ว่า request แบบไหนจะโดน API ปฏิเสธ และรู้ว่า PHI ต้องอยู่ในขอบเขตไหน
  • ตัดสินได้ว่า workflow ที่มี PHI รันที่ไหนได้ และเปิด Covered Model ใน workspace เดียวของ org ที่เป็น ZDR โดยไม่กระทบที่เหลือ
แนวคิดหลัก: ใคร process ข้อมูล คนนั้นคุมกติกา

คนที่ "จับ" prompt และ output ของเราจริงๆ ขึ้นกับว่า deploy ผ่านช่องทางไหน บน Claude API, Claude Platform on AWS และ Microsoft Foundry ผู้ process คือ Anthropic ส่วนบน Amazon Bedrock และ Google Cloud's Agent Platform ผู้ process คือ cloud provider ข้อตกลงเรื่อง retention และ BAA ของ Anthropic มีผลเฉพาะกับข้อมูลที่ Anthropic เป็นคน process เท่านั้น

1. ใคร process ข้อมูล เป็นตัวตัดสินว่า control ไหนใช้ได้

ก่อนจะคุยเรื่อง HIPAA หรือ ZDR ต้องตอบคำถามแรกให้ได้ก่อนว่า "ข้อมูลวิ่งไปที่ระบบของใคร" เพราะ Anthropic มีข้อตกลงด้านข้อมูลอยู่ 2 แบบคือ zero data retention (ZDR) กับ HIPAA readiness และทั้งสองแบบใช้ได้เฉพาะช่องทางที่ Anthropic เป็นผู้ process เองเท่านั้น ถ้าเป็นช่องทางที่ cloud provider เป็นคนรัน inference เราต้องไปดูเอกสารของ provider นั้นแทน

จุดที่คนสับสนบ่อยที่สุดคือ Claude Platform on AWS ตัวนี้ซื้อผ่าน AWS Marketplace จ่ายบิลรวมกับ AWS และเปิดจาก AWS Console ก็จริง แต่คนที่ operate service คือ Anthropic เลยใช้ retention policy เดียวกับ API ของ Anthropic เอง ต่างจาก Bedrock ที่ AWS เป็นคนรัน inference เปรียบเหมือนซื้อตั๋วเครื่องบินผ่านเว็บเอเจนซี่ คนที่บินจริงคือสายการบิน เงื่อนไขสัมภาระก็เป็นของสายการบิน ไม่ใช่ของเว็บ ช่องทางการจ่ายเงินไม่ได้บอกว่าใครเป็น processor

ค่าตั้งต้นเมื่อยังไม่มีข้อตกลงใดเลย

  • ข้อมูลที่ถูกเก็บไว้ ไม่ถูกนำไป train ถ้าลูกค้าไม่ได้อนุญาตไว้อย่างชัดแจ้ง
  • โดย default เนื้อหาบทสนทนา ไม่ถูกเก็บ
  • ข้อยกเว้นคือ Covered Models ซึ่งบังคับให้มี retention 30 วัน (ดูหัวข้อ 5)
  • feature ที่จำเป็นต้องเก็บข้อมูล (เช่นไฟล์ หรือ job) จะประกาศระยะเวลา retention ของตัวเองไว้
สรุปสั้นๆ

ถามก่อนเสมอว่าใครรัน inference ถ้าเป็น Anthropic (API, Platform on AWS, Foundry) ใช้ข้อตกลงของ Anthropic ถ้าเป็น Bedrock หรือ Google Cloud ไปดูของ provider ช่องทางบิลไม่ใช่ตัวตัดสิน

Checkpoint 1

ทีมการเงินของโรงพยาบาลเอกชนแห่งหนึ่งอยากให้ทุกอย่างจ่ายผ่านบัญชี AWS เดิม ทีม dev เลยสมัคร Claude Platform on AWS ผ่าน Marketplace แล้วเข้าใช้จาก AWS Console ทีม compliance ถามว่าต้องไปอ่าน retention policy ของใคร?

  1. ของ AWS ทั้งหมด เพราะจ่ายเงินและเข้าใช้ผ่าน AWS
  2. ของ Anthropic เพราะ Anthropic เป็นคน operate service นี้ จึงใช้ policy เดียวกับ first-party API และขอ ZDR ได้
  3. แบ่งกัน: AWS ดูแล prompt ส่วน Anthropic ดูแล output
  4. เหมือน Bedrock ทุกประการ เพราะอยู่บน AWS เหมือนกัน
ดูเฉลย

B Platform on AWS ต่างจาก Bedrock ตรงที่ Anthropic เป็นคนรัน service เอง การจ่ายผ่าน Marketplace หรือเปิดจาก AWS Console ไม่ได้เปลี่ยนว่าใครเป็น processor และไม่มีการแบ่งครึ่งข้อมูลแบบตัวเลือก C

2. Zero data retention: ครอบคลุมอะไร และไม่ได้กันอะไร

ZDR หมายความว่าหลังจากส่ง response กลับไปแล้ว Anthropic ไม่เก็บ prompt และ response ไว้ at rest (ไม่เขียนลง storage) คุณสมบัติสำคัญ:

  • ต้อง ขอผ่านทีม sales ของ Anthropic ไม่ใช่ปุ่มเปิดเองใน Console
  • เปิดเป็นราย organization ถ้าสร้าง org ใหม่ใต้ account เดิม org ใหม่ ไม่ได้รับ ZDR ตาม ต้องขอเปิดแยก
  • ZDR org ไม่รองรับ CORS แอปที่เรียก API จาก browser ตรงๆ ต้องมี backend proxy คั่นกลาง
ครอบคลุมโดย ZDRไม่ครอบคลุม
Messages API และ Token Counting API เฉพาะ feature ที่ตาราง eligibility ระบุว่า eligibleClaude Console รวมถึง playground
Claude Code ที่ใช้ API key ของ Commercial organization (ยกเว้นสถิติการใช้งานจาก metrics logging ซึ่งถ้าเปิดไว้อาจถูกเก็บ)Claude Managed Agents (transcript ของ session อยู่จนกว่าจะลบ)

หมายเหตุ: Claude Code ที่ใช้ผ่าน Claude Enterprise มี ZDR offering แยกต่างหาก ไม่ได้มาจาก ZDR ของ API org

ZDR คือ "สัญญาเรื่องการเก็บ" ไม่ใช่ "ตัวกรอง request"

ลองนึกก่อนตอบ: org ที่เปิด ZDR แล้ว ส่ง request ที่ใช้ code execution ซึ่งในตาราง eligibility เขียนว่า "No" สำหรับ ZDR จะเกิดอะไรขึ้น?

คำตอบคือ API รับ request ตามปกติ และข้อมูลของ feature นั้นจะตกอยู่ใต้ retention policy ของ feature นั้นเอง ไม่ใช่ ZDR feature ที่ไม่ eligible ส่วนใหญ่เป็นแบบ stateful (มี job, file, หรือ container state ที่ต้องอยู่ต่อ) ZDR จึงไม่ได้ช่วยกันอะไรให้ ทีมต้องมี review process ของตัวเองเพื่อคุมว่าไม่มีใครเผลอใช้ feature พวกนี้

เปรียบเหมือนร้านที่สัญญาว่า "ไม่จดเบอร์โทรลูกค้า" แต่ถ้าลูกค้าเลือกบริการส่งของถึงบ้านเอง ร้านก็ต้องจดที่อยู่ไว้ตามเงื่อนไขของบริการส่งของ ร้านไม่ได้ห้ามลูกค้าสั่งส่ง

เข้าใจผิดบ่อย

"ถ้าเปิด ZDR แล้ว API จะปฏิเสธ request ที่ใช้ feature ที่ไม่ eligible" ผิด ZDR ไม่บล็อกอะไรเลย ตัวที่ปฏิเสธ request คือ HIPAA readiness เท่านั้น

สรุปสั้นๆ

ZDR = ไม่เก็บ prompt/response at rest ขอผ่าน sales เปิดราย org ไม่ inherit ไปยัง org ใหม่ ไม่ครอบคลุม Console, Managed Agents, แผน consumer, Teams/Enterprise UI และไม่บล็อก feature ที่ไม่ eligible

Checkpoint 2

บริษัทประกันได้ ZDR บน org หลักแล้ว มีงาน 4 อย่าง งานไหนอยู่ภายใต้ ZDR จริง?

  1. ทีม data science สร้าง org ใหม่ชื่อ "analytics" ใต้ account เดิม แล้วเรียก Messages API จากที่นั่น
  2. ทีม ops ใช้ Claude Managed Agents รันงานกลางคืนจาก org หลัก
  3. developer ใช้ Claude Code ด้วย API key ของ org หลัก (Commercial) และปิด metrics logging ไว้
  4. PM ลองวาง prompt ใน Console playground ของ org หลัก
ดูเฉลย

C Claude Code ที่ใช้ key ของ Commercial org ที่มี ZDR อยู่ในขอบเขต (และปิด metrics logging แล้ว) ส่วน A เป็น org ใหม่ที่ไม่ได้ inherit ZDR, B Managed Agents เก็บ transcript ไว้, D Console/playground อยู่นอกขอบเขต

3. HIPAA readiness: BAA บวกกับการบังคับ feature ที่ระดับ API

HIPAA readiness ออกแบบมาสำหรับ org ที่ต้องจัดการ PHI (Protected Health Information ข้อมูลสุขภาพที่ระบุตัวบุคคลได้) ต้องมี 2 อย่าง:

  • BAA (Business Associate Agreement) ที่เซ็นแล้ว คือสัญญาตามกฎหมาย HIPAA ระหว่างผู้ให้บริการกับลูกค้า
  • organization ที่เปิด HIPAA

วิธีปกป้องข้อมูลของ HIPAA readiness ต่างจาก ZDR: มันไม่ได้ลบทันที แต่ใช้ safeguard ที่กว้างกว่า คือ encryption, access control และ audit logging ดังนั้น org ที่มี PHI ใช้ HIPAA readiness อย่างเดียวพอ ไม่จำเป็นต้องมี ZDR ซ้อน

ขั้นตอนเปิดแบบ self-serve

  1. เข้า Console หน้า Data retention (platform.claude.com/settings/privacy)
  2. admin ที่มีสิทธิ์ HIPAA management จะเห็นการ์ด HIPAA compliance
  3. ดาวน์โหลด BAA และ HIPAA Implementation Guide
  4. กด accept ในฐานะ ผู้แทนทางกฎหมายที่มีอำนาจ ของบริษัท

รายละเอียดที่ต้องจำ:

  • การเปิดผูกกับ เวอร์ชันของ BAA ที่ดาวน์โหลด ไป
  • control มีผล ทันทีที่ accept
  • การตั้งค่านี้ ถาวร admin ปิดเองไม่ได้
  • ถ้าต้องการ BAA แบบเจรจาเงื่อนไขเอง (negotiated BAA) ต้องไปทาง sales

API บังคับ feature eligibility ให้จริงๆ

นี่คือความต่างใหญ่จาก ZDR ถ้า org ที่เปิด HIPAA ส่ง request ที่ใช้ feature ที่ไม่ eligible API จะตอบ 400 invalid_request_error พร้อมบอกชื่อ feature วิธีแก้คือเอา feature นั้นออกแล้วส่งใหม่

HTTP 400
{"type": "error",
 "error": {"type": "invalid_request_error",
           "message": "code_execution is not available ... without Zero Data Retention ..."}}

(ตัวอย่างข้างบนแต่งขึ้นเพื่อให้เห็นภาพ) สังเกตว่าข้อความ error อาจมีคำว่า "without Zero Data Retention" อยู่ นั่นเป็นแค่สำนวนของ API การไปเปิด ZDR ไม่ได้ทำให้ request ผ่าน ทางแก้มีทางเดียวคือถอด feature ออก

ข้อยกเว้น: client-side tool บางตัวที่ในตาราง eligibility เขียนว่า "not blocked" API จะยอมรับ แต่ข้อมูลที่ผ่าน tool นั้น ยังอยู่นอก HIPAA readiness

Checkpoint 3

สตาร์ทอัปเทเลเมดิซีนเพิ่ง accept BAA มาตรฐานใน Console request ถัดมาที่แนบ tool code_execution ไปด้วย ได้ 400 ที่บอกว่า feature นี้ใช้ไม่ได้ "without Zero Data Retention" ทีมควรทำอะไร?

  1. ขอ ZDR จาก sales แล้วส่ง request เดิมอีกครั้ง
  2. ปิด HIPAA readiness ชั่วคราว ส่ง request แล้วค่อยเปิดกลับ
  3. ถอด code_execution ออกจาก request แล้วส่งใหม่
  4. retry request เดิมแบบ exponential backoff เพราะน่าจะเป็น error ชั่วคราว
ดูเฉลย

C HIPAA readiness บังคับ eligibility ที่ API ทางแก้คือถอด feature ออก คำว่า ZDR ใน error เป็นแค่สำนวน (A ไม่ช่วย) HIPAA ปิดไม่ได้เพราะถาวร (B) และส่งซ้ำแบบเดิมก็โดนปฏิเสธซ้ำ (D)

4. BAA ครอบคลุม PHI ที่ไหน และไม่ครอบคลุมที่ไหน

BAA ครอบคลุมเฉพาะ org ที่เป็นคน accept และเฉพาะ feature ที่ eligible ใน org นั้น มีที่ที่คนมักเข้าใจผิดว่าครอบคลุมแต่จริงๆ ไม่ใช่:

  • Claude Console รวม Workbench แม้จะเป็นที่ที่เรากดเปิด HIPAA ก็ตาม แต่การเอา PHI ไปพิมพ์ใน Console ไม่อยู่ใต้ BAA
  • แผน consumer (Free, Pro, Max) เช่น หมอหลายคนแชร์ account Pro กันไว้ค้นข้อมูลชาร์ต อยู่นอกสัญญาทั้งหมด
  • Claude Enterprise ที่ยังไม่ activate Primary Owner ต้องไปเปิด HIPAA compliance ในเมนู Data and privacy และ accept BAA ก่อน
  • Beta feature และ third-party integration โดยทั่วไปถูกยกเว้น ถ้า admin เปิด Enterprise Skills หรือ connector ที่ส่งข้อมูลไป third party admin ต้องรับผิดชอบเอง

pattern ที่ถูกต้องสำหรับงานอย่างการสรุปเวชระเบียน: org แยกเฉพาะที่เปิด HIPAA เรียก Claude API ด้วย feature ที่ eligible เท่านั้น แล้วปล่อยให้ 400 error ของ API เป็นด่านกันพลาดอีกชั้น

เข้าใจผิดบ่อย

"เซ็น BAA แล้ว PHI ผ่านช่องทางไหนของ org ก็ได้" ผิด BAA ครอบคลุมแค่ feature ที่ eligible ไม่รวม Console/Workbench และ Enterprise ต้อง activate ก่อน

สรุปสั้นๆ

PHI ต้องวิ่งใน org ที่เปิด HIPAA ผ่าน API ด้วย feature ที่ eligible เท่านั้น Console, แผน consumer, Enterprise ที่ยังไม่ activate และ integration ภายนอกไม่นับ Claude Code ต้องเป็น Enterprise + ต่อตรง Claude API

Checkpoint 4

เครือคลินิกทันตกรรมเซ็น BAA กับ Anthropic แล้ว มี 4 ไอเดียจะใช้ Claude กับประวัติคนไข้ ไอเดียไหนอยู่ใต้ BAA?

  1. ทันตแพทย์ copy ประวัติคนไข้ไปถามใน Workbench ของ org ที่เปิด HIPAA ไว้
  2. ระบบสรุปประวัติการรักษาที่เรียก Claude API จาก org แยกที่เปิด HIPAA ใช้แต่ feature ที่ eligible
  3. ผู้จัดการคลินิกใช้ account Max ส่วนตัวสรุปเคสยากๆ
  4. ใช้ workspace ตั้งต้นของ Claude Enterprise ที่บริษัทเพิ่งซื้อ โดยยังไม่มีใครเข้าไปตั้งค่า HIPAA
ดูเฉลย

B เป็น pattern ที่ถูกต้อง Workbench อยู่นอก BAA แม้ org จะเปิด HIPAA (A) แผน consumer ไม่ครอบคลุม (C) และ Enterprise ต้องให้ Primary Owner เปิด HIPAA และ accept BAA ก่อน (D)

Checkpoint 5

ทีม IT กำลังเขียน managed settings ให้ Claude Code ของ developer ในบริษัทประกันสุขภาพที่ใช้ Enterprise แบบ HIPAA-ready ช่อง allowedProviders ควรใส่ค่าไหนจึงจะอยู่บนเส้นทางที่ eligible?

  1. ["bedrock"]
  2. ["foundry"]
  3. ["anthropic"]
  4. ["gateway"]
ดูเฉลย

C มีแค่การต่อตรงเข้า Claude API ที่ eligible ภายใต้ Enterprise HIPAA configuration Bedrock, Foundry และ gateway ไม่ eligible ทั้งหมด

Checkpoint 6

บริษัท health-tech อยากให้ Claude ช่วยแยกข้อมูลจากแบบฟอร์มรับผู้ป่วย และให้ทีมพัฒนาใช้ Claude Code ใน repo ที่มีข้อมูลตัวอย่างเป็น PHI จริงด้วย ข้อไหนถูก? (เลือก 2 ข้อ)

  1. pipeline แยกข้อมูลแบบฟอร์มควรรันใน org แยกที่เปิด HIPAA ผ่าน Claude API ด้วย feature ที่ eligible
  2. Claude Code จะได้รับความคุ้มครองอัตโนมัติ เพราะใช้ API key ของ org ที่เปิด HIPAA เดียวกัน
  3. ถ้าจะให้ Claude Code อยู่ใต้ BAA ต้องเป็น Enterprise ที่ HIPAA-ready, login ด้วย account Enterprise และต่อตรง Claude API
  4. ให้ Claude Code วิ่งผ่าน LLM gateway ภายในบริษัทเพื่อเพิ่ม audit log จะทำให้เข้าเงื่อนไขมากขึ้น
ดูเฉลย

A, C HIPAA readiness ของ API org ไม่ครอบคลุม Claude Code (B ผิด) และ LLM gateway หรือ custom ANTHROPIC_BASE_URL ทำให้ไม่ eligible (D ผิด)

5. ใช้ Covered Model ใน org ที่เป็น ZDR

Covered Models ได้แก่ Claude Fable 5.1, Claude Mythos 5.1, Claude Fable 5 และ Claude Mythos 5 โมเดลกลุ่มนี้บังคับ retention 30 วัน เลยใช้ไม่ได้ใน org ที่เป็น ZDR เว้นแต่ Anthropic จะอนุญาตเป็นกรณีพิเศษอย่างชัดแจ้ง

สิ่งที่ต้องรู้คือ API ไม่เปิด retention ให้เองอัตโนมัติ ถ้า org หรือ workspace ยังไม่ตรงเงื่อนไข request จะได้ 400 invalid_request_error บอกว่า org หรือ workspace ต้องเปิด data retention ก่อน

วิธี pilot แบบไม่กระทบทั้ง org: override ราย workspace

  1. ใน Console หน้า Data retention เลือก workspace ที่จะ pilot จาก dropdown (ห้ามใช้ Default Workspace เพราะมันตาม setting ของ org เสมอ)
  2. เลือก Standard data retention (30-day retention) แล้วกด Save
  3. อ่านและ accept เงื่อนไขในหน้าต่างยืนยัน (retention มีผล หลัง accept เท่านั้น)
  4. ส่ง request ไป Covered Model จาก workspace นั้น เช็กว่าผ่าน ขณะที่ workspace อื่นยังเป็น ZDR ตาม default ของ org

เปรียบเหมือนตึกที่ทุกห้องตั้งให้ทำลายเอกสารทันที แต่มีห้องเดียวที่ต้องเก็บเอกสาร 30 วันตามเงื่อนไขของอุปกรณ์ใหม่ เราตั้งค่าเฉพาะห้องนั้น ไม่ต้องเปลี่ยนนโยบายทั้งตึก

อีกจุดที่สอบชอบหลอก: HIPAA readiness ไม่ใช่ทางปลดล็อกโมเดล มันมีไว้สำหรับ PHI และปิดไม่ได้ อย่างไรก็ตาม บน Enterprise ที่ HIPAA-ready และใส่ HIPAA configuration แล้ว สมาชิกใช้ Covered Models ใน Claude Code และ Cowork ภายใต้ BAA ได้

เข้าใจผิดบ่อย

"admin เปิด HIPAA readiness ลองเพื่อปลดล็อกโมเดล แล้วค่อยปิดทีหลังได้" ผิด HIPAA readiness มีผลทันทีและถาวร การ pilot Covered Model ต้องใช้ 30-day retention override ราย workspace

สรุปสั้นๆ

Covered Models ต้องมี retention 30 วัน API ไม่เปิดให้เองแต่ตอบ 400 ถ้าจะลองใน org ZDR ให้ override เฉพาะ workspace (ไม่ใช่ Default Workspace) แล้ว accept เงื่อนไข อย่าใช้ HIPAA เป็นทางลัด

Checkpoint 7 (เรียงลำดับ)

เรียงขั้นตอนเปิด Covered Model ให้ workspace "research-pilot" ใน org ที่เป็น ZDR:

  1. accept เงื่อนไขในหน้าต่างยืนยัน
  2. ส่ง request ไป Covered Model จาก research-pilot แล้วเช็กว่า workspace อื่นยังเป็น ZDR
  3. เลือก research-pilot จาก dropdown ในหน้า Data retention
  4. เลือก Standard data retention (30-day) แล้วกด Save
ดูเฉลย

3 → 4 → 1 → 2 เลือก workspace ก่อน ตั้งค่าแล้ว Save จากนั้น accept เงื่อนไข (retention เริ่มมีผลตรงนี้) แล้วจึงทดสอบ request

Checkpoint 8

บริษัทกฎหมายใช้ ZDR ทั้ง org ทีมวิจัยทีมเดียวอยากลอง Claude Mythos 5 โดยที่ทีมอื่นต้องอยู่บน ZDR ต่อไป ทางไหนถูก?

  1. ขอให้ sales ยกเลิก ZDR ทั้ง org ชั่วคราวระหว่าง pilot
  2. ส่ง request ไปเลย API จะเปิด retention 30 วันให้เฉพาะ request นั้นอัตโนมัติ
  3. เปิด HIPAA readiness เพื่อปลดล็อก Mythos 5 แล้วค่อยปิดหลัง pilot
  4. เปิด Standard data retention 30 วันเฉพาะ workspace ของทีมวิจัย (ที่ไม่ใช่ Default Workspace)
ดูเฉลย

D override ราย workspace กระทบเฉพาะทีมที่ต้องใช้ A กว้างเกินไป B ผิดเพราะ API ตอบ 400 ไม่ได้เปิดให้เอง C ผิดเพราะ HIPAA ไม่ได้ปลดล็อกโมเดลและปิดไม่ได้
