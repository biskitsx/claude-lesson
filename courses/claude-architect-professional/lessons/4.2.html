4.2 Eval datasets and graders: ออกแบบชุดทดสอบแบบผสมหลายวิธี

ต้นฉบับ: CertSafari 4.2

อ่านจบแล้วควรทำได้
  • เปลี่ยนเป้าหมายลอยๆ อย่าง "ตอบดีๆ" ให้เป็น success criteria ที่วัดผลได้จริง
  • สร้าง dataset ที่หน้าตาเหมือน traffic จริงใน production แล้วเติม edge case เข้าไปอย่างตั้งใจ
  • อธิบายได้ว่าทำไม เคสเยอะ + ตรวจอัตโนมัติ + รันหลายรอบ ถึงชนะเคสน้อยที่คนตรวจเอง
  • เลือก grader ให้เหมาะกับงาน (code / LLM / human) และรวม grader หลายตัวเข้าเป็น framework เดียวได้
แนวคิดหลัก: test case หนึ่งอันมี 4 ชิ้น

eval หนึ่งเคสประกอบด้วย input ที่ป้อนเข้าไป, output ที่โมเดลตอบออกมา, golden answer (คำตอบอ้างอิงที่ถือว่าถูก) และ คะแนน จาก grader ที่เอา output ไปเทียบกับ golden answer ถ้าขาดชิ้นไหนไป เราก็ไม่มีทางบอกได้ว่าระบบดีขึ้นหรือแย่ลง

1. ตั้ง success criteria ให้ได้ก่อน แล้วค่อยเขียน test case

ก่อนจะลงมือเขียนเคสสักเคส ต้องตอบให้ได้ก่อนว่า "ผ่าน" หน้าตาเป็นยังไง ถ้าเกณฑ์ยังลอยๆ อยู่ ต่อให้มีเคสเป็นพันก็ไม่รู้จะให้คะแนนยังไง เกณฑ์ที่ใช้ทดสอบได้ควรมีคุณสมบัติ 4 อย่าง (คล้ายหลัก SMART ที่คุ้นกัน):

  • Specific เจาะจง บอกชัดว่าวัดอะไร กับข้อมูลชุดไหน
  • Measurable วัดได้ จะเป็นตัวเลขตรงๆ หรือเป็น scale เชิงคุณภาพก็ได้
  • Achievable ทำได้จริง ไม่ใช่ตั้งเป้า 100% สมบูรณ์แบบ
  • Relevant เกี่ยวข้องกับสิ่งที่ผู้ใช้หรือธุรกิจสนใจจริงๆ

จุดที่คนมักพลาดคือคิดว่า "วัดได้" ต้องเป็นตัวเลขแข็งๆ อย่างเดียว ความจริงคือ scale เชิงคุณภาพ เช่น rubric ให้คะแนน 1–5 ก็นับว่าวัดได้ ตราบใดที่ใช้อย่างสม่ำเสมอควบคู่กับตัวเลขอื่น

ตัวอย่างการเขียนใหม่: เป้าเดิม "ระบบวิเคราะห์ sentiment ควรแม่นๆ" กลายเป็น "ได้ F1 อย่างน้อย X บน held-out test set (ชุดข้อมูลที่กันไว้ไม่ใช้ตอนจูน) และดีกว่า baseline ปัจจุบัน" แบบนี้ทุกคนในทีมตัดสินได้ตรงกันว่าผ่านหรือไม่ผ่าน

ส่วนเกณฑ์ที่ ไม่ใช่ เกณฑ์ที่ดีมักมี 3 หน้าตา:

  • ไม่มีการวัดเลย เช่น "ให้ดูเป็นมิตรขึ้น"
  • ตั้งความสมบูรณ์แบบที่ทำไม่ได้ เช่น "ทุกคนต้องให้คะแนนเต็ม"
  • เอากระบวนการมาแทนเกณฑ์ เช่น "หัวหน้าทีมเซ็นอนุมัติก่อนปล่อย" ซึ่งเป็นขั้นตอนการทำงาน ไม่ใช่เป้าที่วัดได้
สรุปสั้นๆ

เกณฑ์ที่ดีบอกได้ว่าวัดอะไร บนข้อมูลชุดไหน ด้วยเกณฑ์ตัดเท่าไหร่ rubric 1–5 ใช้ได้ถ้าใช้สม่ำเสมอ ส่วน "ดีขึ้น", "สมบูรณ์แบบ" หรือ "รอหัวหน้าอนุมัติ" ไม่ใช่ success criteria

Checkpoint 1

ทีมทำ bot ช่วยร่างอีเมลตอบผู้สมัครงาน เป้าเดิมเขียนว่า "อีเมลต้องสุภาพและให้ข้อมูลครบ" ข้อไหนเป็น success criterion ที่ทดสอบได้ดีที่สุด?

  1. อีเมลต้องฟังดูสุภาพกว่าเวอร์ชันเก่าอย่างเห็นได้ชัด
  2. ฝ่าย HR ทุกคนต้องให้คะแนนเต็มกับทุกอีเมล
  3. ค่าเฉลี่ยอย่างน้อย 4/5 บน rubric ความครบถ้วนของข้อมูล วัดจากอีเมลตัวอย่าง 250 ฉบับที่กันไว้
  4. ผู้จัดการฝ่ายสรรหาอ่านและอนุมัติก่อนปล่อยทุกเวอร์ชัน
ดูเฉลย

C เป็นข้อเดียวที่เจาะจง วัดได้ และทำได้จริง A ไม่มีการวัด B ตั้งเป้าสมบูรณ์แบบที่ทำไม่ได้ D เป็นกระบวนการอนุมัติ ไม่ใช่เกณฑ์

Checkpoint 2

ระบบแปลงบันทึกแพทย์เป็นสรุปสำหรับคนไข้ มีเป้าว่า "อ่านง่าย" ทีมอยากเขียนให้เป็นเกณฑ์ที่ใช้ทดสอบได้ ข้อไหนเหมาะสุด?

  1. สรุปทุกฉบับต้องไม่มีศัพท์แพทย์แม้แต่คำเดียว และคนไข้ทุกคนต้องเข้าใจ 100%
  2. ค่าเฉลี่ยอย่างน้อย 4/5 บน rubric ความเข้าใจง่าย จากตัวอย่าง 400 บันทึกที่ไม่ได้ใช้ตอนเขียน prompt
  3. ให้สรุปฟังดูเป็นกันเองมากขึ้น
  4. ส่งให้แพทย์หัวหน้าแผนกอ่านทุกครั้งก่อนปล่อย
ดูเฉลย

B rubric ที่ใช้สม่ำเสมอบนชุดข้อมูลที่กันไว้ถือว่าวัดได้และทำได้จริง A เป็นความสมบูรณ์แบบ C ไม่มีการวัด D เป็นการเซ็นอนุมัติ

2. test case ต้องหน้าตาเหมือน traffic จริงก่อน แล้วค่อยเติม edge case

dataset ที่ดีคือกระจกของ production ขั้นแรกให้จำลองสิ่งที่ผู้ใช้ส่งเข้ามาจริงๆ ให้ได้ก่อน ทั้ง ประเภทเอกสาร ความยาว สำนวนการพิมพ์ noise (คำผิด ฟอร์แมตเพี้ยน) และ สัดส่วนคร่าวๆ ของแต่ละแบบ ถ้าของจริงมี PDF สแกน 30% แต่ dataset มีแต่ PDF สะอาด คะแนนที่ได้ก็จะดูดีเกินจริง

จากนั้นค่อยเติม edge case อย่างตั้งใจ หมวดมาตรฐานที่ควรมีแทบทุกงาน:

  • input ไม่เกี่ยวข้องหรือไม่มีข้อมูลเลย
  • input ยาวมากๆ
  • ในงานแชต: ผู้ใช้พิมพ์อะไรที่อันตรายหรือนอกเรื่อง
  • เคสกำกวมที่แม้แต่คนก็ยังตัดสินไม่ตรงกัน

นอกจากนี้ยังมี edge case เฉพาะงาน เช่น

งานedge case ที่ควรใส่
สรุปบทความบทความที่พูดหลายเรื่องปนกัน, พาดหัวที่ชวนเข้าใจผิดไม่ตรงกับเนื้อหา
FAQ botคำถามสะกดผิด, คำถามยืดยาววกวน
ความเป็นส่วนตัวด้านสุขภาพข้อมูลสุขภาพที่พูดตรงๆ, ที่เป็นสมมติฐาน ("ถ้าผมเป็นเบาหวาน…"), และที่แฝงมาโดยนัย

ทุกเคสต้องมี golden answer ซึ่งอาจเป็นคำตอบที่ต้องตรงเป๊ะ (exact match) หรือเป็นตัวอย่างคำตอบที่สมบูรณ์แบบให้ grader ใช้เทียบก็ได้

ตัวอย่าง dataset ขนาดจิ๋ว สังเกตว่ามีเคสปกติปนกับ edge case ที่ตั้งใจใส่:

reviews = [
    {"text": "ส่งไว ของตรงปก", "label": "positive"},
    {"text": "กล่องบุบ แต่ของข้างในโอเค", "label": "mixed"},           # edge: ความรู้สึกปน
    {"text": "เยี่ยมมาก รอแค่ 3 สัปดาห์เอง 🙃", "label": "negative"},   # edge: ประชด
    # ... เติมให้ครบตามสัดส่วนจริงของ production
]

สุดท้าย dataset ไม่ใช่ของทำครั้งเดียวจบ ทุกครั้งที่เจอ failure จริงใน production ให้แปลงเป็น test case ใหม่ dataset จะได้ตามทันสิ่งที่เกิดขึ้นจริงไปเรื่อยๆ

เข้าใจผิดบ่อย

"อยากให้ eval ทำนายผล production ได้แม่นขึ้น ก็เพิ่มตัวอย่างหมวดที่ง่ายเข้าไปเยอะๆ" ไม่ใช่ การเพิ่มเคสง่ายแค่ทำให้มั่นใจในเรื่องที่รู้อยู่แล้ว พลังทำนาย (predictiveness) มาจากการทำให้สัดส่วน input ตรงกับของจริง และใส่ edge case ที่ครอบคลุม

"golden label ของ edge case ให้ตามคำที่เห็นบนผิว" ไม่ใช่ ประโยคประชดที่ใช้คำบวกต้องติด label ตามความหมายจริง (ลบ) ถ้าใส่ label ตามผิว เคสนั้นจะให้รางวัลกับความผิดพลาดที่มันถูกสร้างมาเพื่อจับ

สรุปสั้นๆ

เลียนแบบ traffic จริงก่อน (ประเภท ความยาว noise สัดส่วน) → เติม edge case ทั้งหมวดมาตรฐานและเฉพาะงาน → ทุกเคสมี golden answer → แปลง failure จาก production เป็นเคสใหม่เสมอ

Checkpoint 3

dataset จัดประเภทรีวิวร้านอาหารมีเคส "อาหารอร่อยสุดๆ ถ้าคุณชอบรอโต๊ะสองชั่วโมง" ทีมตั้งใจใส่ไว้เป็น edge case golden label ควรเป็นอะไร?

  1. positive เพราะมีคำว่า "อร่อยสุดๆ"
  2. negative เพราะความหมายจริงคือบ่นเรื่องการรอ
  3. mixed เพราะมีทั้งคำบวกและเรื่องลบ
  4. ไม่ต้องใส่ label เพราะเป็นเคสกำกวม
ดูเฉลย

B นี่คือเคสประชด จุดประสงค์คือดูว่าโมเดลอ่านความหมายจริงหรือแค่อ่านคำบนผิว ถ้าตั้งเป็น positive เท่ากับให้คะแนนความผิดพลาด ส่วน mixed เป็น edge case อีกประเภทหนึ่ง (ความรู้สึกปนกันจริงๆ) และทุกเคสต้องมี golden answer

Checkpoint 4

eval ดึงข้อมูลจากใบเสร็จได้ 96% แต่ทุกเคสเป็นรูปถ่ายใบเสร็จที่ชัดและตรง ขณะที่ของจริงมีรูปเอียง ใบเสร็จยาวหลายท่อน และใบที่ซีดจาง อยากให้ eval ทำนายผล production ได้ดีขึ้น ควรทำอะไร?

  1. เพิ่มรูปใบเสร็จชัดๆ อีก 500 ใบ
  2. ให้คนสองคนติด label ชุดเดิมซ้ำเพื่อความแม่น
  3. เพิ่มรูปเอียง ใบยาว และใบซีด ตามสัดส่วนที่เจอจริง พร้อม edge case ที่ตั้งใจใส่
  4. แปลใบเสร็จชุดเดิมเป็นหลายภาษา
ดูเฉลย

C ช่องว่างอยู่ที่ประเภท input ที่ dataset ไม่มี A เพิ่มความมั่นใจในหมวดที่ครอบคลุมแล้ว B ตรวจ label แต่ไม่เพิ่ม coverage D ทดสอบความสามารถที่งานนี้ไม่ได้ต้องการ

Checkpoint 5

ระบบดึงวันหมดอายุจากสัญญาประกันภัย ชุดทดสอบมีแต่กรมธรรม์ template มาตรฐานของบริษัทเอง แต่ลูกค้าเริ่มอัปโหลดกรมธรรม์จากบริษัทอื่น เอกสารสแกน และไฟล์ที่ฟอร์แมตเสีย ควรเพิ่มอะไร?

  1. กรมธรรม์ template มาตรฐานเพิ่มอีกหลายร้อยฉบับ
  2. ชุดตัวอย่างแบบ stratified ของเอกสารฟอร์แมตเสีย สแกน และ template ที่ไม่ใช่มาตรฐาน วางคู่กับเอกสารมาตรฐานเดิม
  3. ทดสอบว่าโมเดลตอบเป็นภาษาอังกฤษได้คล่องไหม
  4. ตรวจ label ของเอกสารชุดเดิมซ้ำอีกรอบ
ดูเฉลย

B stratified คือเก็บตัวอย่างให้ครบทุกกลุ่มย่อย จะได้ครอบคลุมประเภท input ที่ขาดไป ข้ออื่นเพิ่มความมั่นใจในหมวดเดิม ทดสอบความสามารถที่ไม่เกี่ยว หรือไม่ได้เพิ่ม coverage

3. ปริมาณ, การตรวจอัตโนมัติ และการรันหลายรอบ

ลองคิดเรื่องต้นทุน: เขียน test case จ่ายครั้งเดียว แต่ การให้คะแนนต้องจ่ายทุกครั้งที่รัน eval ถ้าทีมแก้ prompt วันละหลายรอบ แล้วทุกรอบต้องรอคนมานั่งตรวจ ต้นทุนจะพอกขึ้นเร็วมาก การตรวจอัตโนมัติจึงสเกลได้ดีกว่ามาก

ดังนั้นให้ออกแบบคำถามตั้งแต่แรกให้ตรวจแบบกลไกได้ เช่น multiple choice, string match, ตรวจด้วยโค้ด หรือให้ LLM ตรวจ เทคนิคง่ายๆ คือ บังคับ format ของ output เช่น สั่งว่า "ตอบเป็นตัวเลขอย่างเดียว" แค่นี้ก็ตรวจด้วย exact match ได้แล้ว

ลองเดาก่อน

ทีม A มี 1,000 เคสที่ตรวจอัตโนมัติ ทีม B มี 200 เคสที่ผู้เชี่ยวชาญตรวจเอง แต่รันได้แค่ครั้งเดียวต่อ release ทีมไหนรู้ปัญหาได้ดีกว่า? คำตอบคือ ทีม A เพราะรันได้ทุกครั้งที่มีการเปลี่ยนแปลง ไม่ต้องรอรอบ release ปริมาณที่รันบ่อยชนะคุณภาพการตรวจที่รันนานๆ ครั้ง

Trial: ผลรันครั้งเดียวเชื่อไม่ได้

Trial คือการลองทำ task หนึ่งครั้ง เนื่องจาก output ของโมเดลแปรผันระหว่างแต่ละรอบ (non-deterministic) คะแนนที่ขยับ 2–3% จากการรันครั้งเดียวอาจเป็นแค่ noise ไม่ใช่การปรับปรุงจริง วิธีแก้คือรันหลาย trial ต่อ task ทั้งเวอร์ชันเก่าและใหม่ แล้วเทียบผลที่รวมแล้ว (aggregated)

เข้าใจผิดบ่อย

"เคสจำนวนน้อยที่คนตรวจอย่างพิถีพิถัน ดีกว่าเคสจำนวนมากที่ตรวจอัตโนมัติ" ไม่ใช่ เพราะต้นทุนการตรวจเกิดซ้ำทุกรอบ การตรวจอัตโนมัติเลยเป็นทางเดียวที่รันบ่อยๆ ได้จริง ปริมาณชนะ

"คะแนนแกว่งเพราะ grader ไม่ดี เปลี่ยน grader ก็หาย" ไม่ใช่ ความแปรปรวนส่วนใหญ่มาจาก output ของโมเดลเอง ต้องแก้ด้วยการรันหลาย trial

สรุปสั้นๆ

เขียนเคสจ่ายครั้งเดียว ตรวจจ่ายทุกรอบ → ออกแบบให้ตรวจอัตโนมัติได้ (บังคับ format) → เคสเยอะชนะเคสน้อย → รันหลาย trial ก่อนเชื่อว่าคะแนนเปลี่ยนจริง

Checkpoint 6

ทีมแก้ prompt จัดหมวดคำร้องเรียน รันชุดทดสอบ 600 เคสครั้งเดียว คะแนนขึ้นจาก 73% เป็น 76% ก่อนจะสรุปว่า prompt ใหม่ดีกว่า ควรทำอะไร?

  1. เปลี่ยนจาก exact match เป็น LLM grader เพื่อความยุติธรรม
  2. รันหลาย trial ต่อ task ทั้งสองเวอร์ชัน แล้วเทียบผลรวม
  3. ประกาศใช้เลย เพราะ 3% บน 600 เคสถือว่าเยอะแล้ว
  4. ตัดเคสที่ตอบผิดบ่อยออกจากชุดทดสอบ
ดูเฉลย

B ผลต่างจากการรันครั้งเดียวอาจเป็น noise จาก output ที่แปรผัน การเปลี่ยน grader ไม่ได้แก้ความแปรปรวนของโมเดล และการตัดเคสยากทิ้งทำให้ eval ทำนายได้แย่ลง

4. Grader 3 แบบ: code, LLM และ human

หลักเลือกคือ ใช้ grader ที่ถูกที่สุดที่ยังตัดสินเกณฑ์นั้นได้อย่างเชื่อถือได้ ถ้าออกแบบ eval ให้ตรวจด้วยโค้ดได้ นั่นดีที่สุด และพยายามหลีกเลี่ยงการออกแบบ eval ที่ต้องพึ่งคนตรวจ

Graderวิธีที่ใช้บ่อยจุดแข็งจุดอ่อนเหมาะกับ
Code-basedstring match (exact, regex, fuzzy), binary test, static analysis, ตรวจผลลัพธ์จริง (outcome verification)เร็ว ถูก เป็นกลาง ได้ผลซ้ำเดิม debug ง่ายเปราะกับคำตอบที่ถูกแต่เขียนต่างไป จับความละเอียดอ่อนได้น้อยคำตอบเชิงหมวดหมู่ หรือคำตอบสั้นที่นิยามชัด
Model-based (LLM)ให้คะแนนตาม rubric, natural-language assertion, เทียบเป็นคู่ (pairwise), ให้หลาย judge ลงความเห็นร่วมยืดหยุ่น สเกลได้ จับความละเอียดอ่อนได้ รับคำตอบแบบอิสระได้non-deterministic แพงกว่า code ต้องให้คน calibrateน้ำเสียง คำตอบปลายเปิด การตรวจ policy ที่ซับซ้อน
Humanผู้เชี่ยวชาญ (SME) รีวิว, สุ่มตรวจ, วัดความเห็นตรงกันระหว่างผู้ตรวจ (inter-annotator agreement)คุณภาพระดับมาตรฐานทองคำ ตรงกับวิจารณญาณผู้เชี่ยวชาญแพง ช้า สเกลยากcalibrate LLM grader, output ที่เป็นเรื่องอัตวิสัย

Code grader ที่ควรรู้จัก

  • Exact match normalize ช่องว่างและตัวพิมพ์เล็กใหญ่ก่อน แล้วเทียบกับ golden answer
  • Cosine similarity เทียบ sentence embedding (เวกเตอร์ตัวแทนความหมายของประโยค) ใช้วัดว่าถามคำถามเดียวกันด้วยถ้อยคำต่างกัน (paraphrase) แล้วได้คำตอบที่ สอดคล้องกัน ไหม ไม่ได้วัดว่าคำตอบ ถูก
  • ROUGE-L วัดความทับซ้อนแบบ longest common subsequence ระหว่างสรุปที่โมเดลเขียนกับสรุปอ้างอิง
def exact_match(output: str, golden: str) -> bool:
    norm = lambda s: " ".join(s.split()).lower()
    return norm(output) == norm(golden)

LLM grader ที่ควรรู้จัก

  • Likert scale ให้คะแนน 1–5 กับคุณภาพบางด้าน เช่น ความเห็นอกเห็นใจ (empathy) หรือความเป็นมืออาชีพ
  • Binary ตอบ yes/no กับคำถามเดียว เช่น "คำตอบนี้มีข้อมูลสุขภาพส่วนบุคคลไหม" ข้อดีคือจับกรณีที่แฝงโดยนัยซึ่ง rule แบบ regex พลาดได้
  • ควร บังคับ format ของคำตัดสิน (เช่น ตอบแค่ yes/no หรือตัวเลข) จะได้ parse ต่อได้ และถ้าทำได้ ให้ใช้ โมเดลคนละตัว กับตัวที่สร้าง output มาเป็นคนตรวจ
GRADER_PROMPT = """อ่านคำตอบด้านล่าง แล้วตัดสินว่ามีข้อมูลสุขภาพของบุคคลที่ระบุตัวได้หรือไม่
รวมถึงกรณีที่บอกเป็นนัย ตอบเพียงคำเดียว: yes หรือ no

<response>{response}</response>"""
เข้าใจผิดบ่อย

"cosine similarity สูงแปลว่าคำตอบถูก" ไม่ใช่ มันวัดความสอดคล้อง ถ้าโมเดลตอบผิดเหมือนกันทุกครั้ง คะแนนก็ยังสูง

แนวข้อสอบ

bot ตอบคำถามนโยบายบริษัทที่คำตอบเป็นข้อเท็จจริงสั้นๆ (เช่น "ลาพักร้อนได้กี่วัน") และนโยบายเปลี่ยนเป็นระยะ grader ที่ถูกคือ exact match หรือ normalized string match เทียบกับ answer key ที่มีคนคอยอัปเดต ตัวเลือกหลอกที่เจอบ่อย: cosine similarity (วัดความสอดคล้อง ไม่ใช่ความถูก), ให้ LLM ให้คะแนนความเป็นมืออาชีพ (วัดน้ำเสียง ไม่ใช่ข้อเท็จจริง), ให้คนรีวิวรายสัปดาห์ (สเกลไม่ได้)

สรุปสั้นๆ

คำตอบสั้นนิยามชัด → code grader · น้ำเสียง/ปลายเปิด → LLM grader (Likert หรือ binary, บังคับ format, ใช้คนละโมเดล) · คน → ใช้ calibrate และตัดสินเรื่องอัตวิสัย ถูกที่สุดที่ยังเชื่อถือได้คือคำตอบ

Checkpoint 7

bot ภายในตอบคำถามเรื่องรหัสสาขาและเวลาเปิดปิดของแต่ละสาขา (คำตอบสั้น เป็นข้อเท็จจริง ข้อมูลเปลี่ยนเมื่อมีการย้ายสาขา) ควรใช้ grader แบบไหน?

  1. cosine similarity ระหว่างคำตอบของ bot เมื่อถามซ้ำหลายแบบ
  2. LLM ให้คะแนนความสุภาพ 1–5
  3. normalized string match เทียบกับ answer key ที่ทีมคอยอัปเดตตามข้อมูลสาขา
  4. ให้พนักงานสุ่มอ่านคำตอบเดือนละครั้ง
ดูเฉลย

C คำตอบสั้นและนิยามชัด code grader จึงถูกและแม่นที่สุด A ผ่านได้แม้ตอบผิดเหมือนกันทุกครั้ง B วัดน้ำเสียงไม่ใช่ความถูก D ช้าและสเกลไม่ได้

Checkpoint 8 (จับคู่)

จับคู่งานตรวจกับ grader ที่เหมาะที่สุด:

  1. ตรวจว่าโมเดลตอบหมวดสินค้าตรงกับ label ที่กำหนดไว้
  2. ตรวจว่าถามเรื่องเดียวกันด้วยถ้อยคำต่างกัน แล้วได้คำตอบที่ความหมายใกล้กัน
  3. ให้คะแนนความสุภาพของคำตอบ 1–5
  4. เทียบคะแนนของ LLM grader กับวิจารณญาณผู้เชี่ยวชาญเป็นระยะ

ตัวเลือก: A) Likert LLM grader · B) Human SME review · C) Exact match · D) Cosine similarity

ดูเฉลย

1-C, 2-D, 3-A, 4-B exact match เหมาะกับ label หมวดหมู่, cosine วัดความสอดคล้องระหว่าง paraphrase, Likert ให้คะแนนคุณภาพเชิงน้ำเสียง, ผู้เชี่ยวชาญใช้ calibrate LLM grader

5. รวม grader หลายตัวเป็น framework เดียว

แอปส่วนใหญ่ต้องประเมินหลายมิติพร้อมกัน เช่น ถูกต้องไหม ฟอร์แมตตรงไหม น้ำเสียงดีไหม ปลอดภัยไหม ดังนั้น task เดียวมักมี grader หลายตัว แต่ละตัวดูแลมิติเดียว แล้วค่อยเอาคำตัดสินมารวมกันด้วยหนึ่งใน 3 วิธี:

วิธีรวมกติกาเหมาะเมื่อ
Weightedถ่วงน้ำหนักคะแนนแล้วรวมกัน ต้องถึง threshold คะแนนดีด้านหนึ่งชดเชยด้านที่อ่อนได้ทุกมิติสำคัญพอๆ กัน และยอมให้แลกกันได้
Binarygrader ทุกตัวต้องผ่าน ตกตัวเดียวคือตกทั้งเคสทุกมิติเป็นเงื่อนไขบังคับ
Hybridบางตัวเป็นด่านบังคับ (hard gate) ที่เหลือถ่วงน้ำหนักรวมกันมีบางเรื่องห้ามพลาดเด็ดขาด เช่น privacy แต่เรื่องอื่นแลกกันได้

อีกเรื่องที่สำคัญคือ grader แต่ละตัว ดูหลักฐานคนละชิ้นได้ ตัวอย่าง: transcript ของ agent บอกว่า "จองห้องประชุมให้แล้ว" แต่ grader แบบ outcome verification ไปเช็กใน database ว่ามี record การจองจริงไหม คำพูดของ agent ไม่ใช่หลักฐานว่างานเสร็จ

บทบาทของคนยังไม่หายไป: คนใช้ calibrate LLM grader และตัดสิน output ที่เป็นเรื่องอัตวิสัย ตัวอย่างจริงคือ Descript ที่ทำ agent ตัดต่อวิดีโอ เปลี่ยนจากให้คนตรวจทั้งหมดมาเป็น LLM grader ที่ใช้เกณฑ์ซึ่งทีม product กำหนด แล้วให้คนช่วย calibrate เป็นระยะ

ตัวอย่างออกแบบ: chatbot การแพทย์

  1. Code check ตรวจฟอร์แมตตายตัว (เช่น มีหัวข้อครบ ความยาวไม่เกินกำหนด)
  2. Binary LLM grader ตรวจว่ามีข้อมูลสุขภาพหลุดออกมาไหม ตั้งเป็น hard gate
  3. Likert LLM grader ให้คะแนนน้ำเสียง/ความเห็นอกเห็นใจ
  4. คนสุ่มตรวจเป็นระยะ เพื่อ calibrate LLM grader ทั้งสองตัว
def score_case(c):
    if not format_ok(c.output):               # code grader
        return 0
    if llm_yes_no(PHI_PROMPT, c.output) == "yes":   # hard gate: privacy
        return 0
    tone = llm_likert(TONE_PROMPT, c.output)        # 1-5
    completeness = llm_likert(COMPLETE_PROMPT, c.output)
    return 0.4 * tone + 0.6 * completeness          # weighted ส่วนที่เหลือ = hybrid
เข้าใจผิดบ่อย

"มี LLM grader แล้ว ไม่ต้องมีคนรีวิวอีก" ไม่ใช่ LLM grader เป็น non-deterministic และอาจเพี้ยนไปจากที่คนต้องการ ต้อง calibrate กับผู้ตรวจที่เป็นคนอย่างต่อเนื่อง

"agent รายงานว่าทำเสร็จแล้ว ก็ถือว่าผ่าน" ไม่ใช่ ควรมี grader ที่ตรวจผลลัพธ์จริง (outcome) แยกจาก transcript

สรุปสั้นๆ

หนึ่ง task หลาย grader หนึ่งมิติต่อตัว รวมด้วย weighted (ชดเชยกันได้), binary (ต้องผ่านหมด) หรือ hybrid (มี hard gate + ถ่วงน้ำหนัก) ตรวจผลลัพธ์จริงไม่ใช่แค่คำพูด และให้คน calibrate LLM grader เสมอ

Checkpoint 9

bot ให้คำแนะนำด้านการเงินส่วนบุคคล ทีมต้องการว่า "ถ้ามีเลขบัญชีหรือข้อมูลส่วนตัวหลุดออกมา ต้องตกทันที" ส่วนความชัดเจนกับความครบถ้วนให้ชดเชยกันได้ ควรรวม grader แบบไหน?

  1. Weighted: ถ่วงน้ำหนักทั้งสามมิติรวมกัน
  2. Binary: ทุกมิติต้องผ่านหมด
  3. Hybrid: privacy เป็น hard gate ส่วนความชัดเจนกับความครบถ้วนถ่วงน้ำหนักรวมกัน
  4. ใช้ LLM grader ตัวเดียวให้คะแนนรวม 1–5
ดูเฉลย

C ต้องการทั้งด่านบังคับและส่วนที่แลกกันได้ A ปล่อยให้คะแนนดีด้านอื่นกลบ privacy ที่รั่วได้ B เข้มเกินสำหรับมิติที่ทีมยอมให้ชดเชย D รวมทุกมิติจนแยกไม่ออกว่าตกเพราะอะไร

Checkpoint 10

agent จัดการนัดหมายคลินิก transcript บอกว่า "ยกเลิกนัดให้เรียบร้อยแล้วค่ะ" ทีมอยากให้ eval จับกรณีที่ agent พูดว่าทำแล้วแต่จริงๆ ไม่ได้ทำ ควรเพิ่ม grader แบบไหน?

  1. LLM grader ให้คะแนนความมั่นใจของประโยคใน transcript
  2. code grader ที่ไปเช็ก record นัดหมายในระบบว่าสถานะเปลี่ยนเป็นยกเลิกจริง
  3. cosine similarity ระหว่าง transcript กับประโยคตัวอย่าง "ยกเลิกเรียบร้อย"
  4. ROUGE-L เทียบ transcript กับ transcript อ้างอิง
ดูเฉลย

B นี่คือ outcome verification ตรวจหลักฐานจริงในระบบแทนการเชื่อคำพูด ตัวเลือกอื่นยังวัดแค่ข้อความใน transcript
