7.3 Diagnose Claude Code configuration: what loaded and why

ต้นฉบับ: CertSafari 7.3

อ่านจบแล้วควรทำได้
  • ใช้ /memory, /hooks, /mcp, /permissions, /status และ /doctor ดูว่า session โหลดอะไรมาจริง ก่อน ลงมือแก้อะไร
  • อธิบายได้ว่าทำไมค่า settings, ไฟล์ memory, permission rule หรือ hook ถึงมีอยู่บน disk แต่ไม่มีผล
  • แยก MCP server ที่ failed, ที่ ยังไม่ได้อนุมัติ และที่ connected แต่ไม่มี tool ออกจากกัน และรู้วิธีแก้ที่ถูกของแต่ละแบบ
  • หาต้นเหตุของปัญหา config ด้วย safe mode หรือ config directory ที่สะอาด
แนวคิดหลัก: ดูจากสิ่งที่โหลด ไม่ใช่สิ่งที่เขียน

ไฟล์บน disk บอกแค่ว่าเรา ตั้งใจ จะให้เป็นยังไง แต่ session ที่กำลังรันบอกว่าอะไร มีผลจริง ให้ถาม session ก่อนว่าโหลดอะไรมาบ้าง และค่าจากแหล่งไหนชนะ จากนั้นค่อยปิด customization ทีละส่วนเพื่อหาตัวการ เหมือนช่างไฟที่ไม่ได้ดูแค่แบบแปลนบ้าน แต่เอามิเตอร์ไปวัดที่ปลั๊กจริง

1. เริ่มจากอาการ แล้วถามว่า "โหลดอะไรมา"

เวลามีคนบอกว่า "hook ไม่ทำงาน" หรือ "Claude ไม่สนกฎใน CLAUDE.md" สัญชาตญาณแรกมักเป็นการเปิดไฟล์ config มาแก้ ซึ่งมักเสียเวลา เพราะไฟล์อาจถูกต้องอยู่แล้ว แต่ไม่ได้ถูกโหลด หรือโหลดแล้วแต่มีค่าอื่นทับ ขั้นแรกที่ถูกคือใช้คำสั่งที่รายงาน สถานะที่ session โหลดอยู่จริง:

คำสั่งสิ่งที่แสดง
/memoryตำแหน่งไฟล์ memory (CLAUDE.md) ทั้งระดับ user และ project รวมถึงโฟลเดอร์ auto memory และสวิตช์เปิด/ปิด auto memory
/skillsskill ที่ใช้ได้ จากทั้งแหล่ง project, user และ plugin
/hookshook configuration ที่ active อยู่
/mcpMCP server ที่เชื่อมต่อ และสถานะของแต่ละตัว
/permissionsกฎ allow และ deny ที่ resolve แล้วและมีผลอยู่ตอนนี้
/statusแหล่ง settings ที่ active ทั้งหมด รวมถึงบอกว่ามี managed settings (settings ที่องค์กรบังคับ) มีผลอยู่หรือไม่
/doctorตรวจสุขภาพการตั้งค่า: ไฟล์ settings ที่ไม่ valid, extension ที่ไม่ได้ใช้, ชื่อ subagent ซ้ำ พร้อมเสนอวิธีแก้
/debug [ปัญหา]เปิด debug logging แล้วให้ Claude วิเคราะห์ปัญหาจาก log และ path ของไฟล์ settings
สรุปสั้นๆ

ก่อนแก้ไฟล์ ให้ถาม session ด้วยคำสั่ง /… ที่ตรงเรื่อง: memory, skills, hooks, mcp, permissions, status แล้วใช้ /doctor หรือ /debug ช่วยหาจุดผิด

Checkpoint 1 (จับคู่)

จับคู่คำถามกับคำสั่งที่ควรใช้ (A: /hooks, B: /permissions, C: /status, D: /mcp, E: /doctor):

  1. "องค์กรมี managed settings บังคับเครื่องนี้อยู่หรือเปล่า"
  2. "server ฐานข้อมูลที่เพิ่มไว้ ต่อติดไหม"
  3. "สรุปตอนนี้กฎ deny ที่มีผลจริงมีอะไรบ้าง"
  4. "hook ที่เขียนไว้ถูกโหลดเข้ามาไหม"
  5. "ช่วยตรวจหน่อยว่ามีไฟล์ settings ไหน syntax พัง หรือชื่อ subagent ซ้ำ แล้วเสนอวิธีแก้"
ดูเฉลย

1-C, 2-D, 3-B, 4-A, 5-E /status ดูแหล่ง settings รวม managed · /mcp ดูสถานะ server · /permissions ดูกฎที่ resolve แล้ว · /hooks ดู hook ที่ active · /doctor ตรวจไฟล์ที่ไม่ valid และเสนอวิธีแก้

2. Settings, memory และ permission rule ที่ "พลาดแบบเงียบๆ"

ปัญหากลุ่มนี้น่าหงุดหงิดเพราะไม่มี error ไฟล์ถูกอ่านแล้ว แต่ผลไม่ออกมาตามที่คิด สาเหตุหลักๆ มี 5 แบบ

2.1 ถูกอ่าน ไม่ได้แปลว่าชนะ (precedence)

ลำดับความสำคัญของไฟล์ settings จากสูงไปต่ำ:

  1. .claude/settings.local.json (ของเราคนเดียว ไม่ commit)
  2. .claude/settings.json ของ project (แชร์ทั้งทีม)
  3. ~/.claude/settings.json ระดับ user

ถ้า key เดียวกันอยู่ในหลายไฟล์ ไฟล์ที่อยู่สูงกว่าชนะ ดังนั้น /status อาจแสดงว่าไฟล์ project ถูกอ่านแล้ว แต่ค่าใน settings.local.json ของคนนั้นยังทับอยู่ นี่เป็นปัญหาเรื่องลำดับ ไม่ใช่ปัญหาการโหลด (ส่วน managed settings ขององค์กรอยู่เหนือทุกไฟล์ของ user และ project)

2.2 วางผิดไฟล์

~/.claude.json (ไม่มี /settings) เก็บ app state และสวิตช์ UI เท่านั้น ส่วน permissions, hooks และ env ต้องไปอยู่ใน ~/.claude/settings.json ชื่อคล้ายกันมาก ระวังสับสน

2.3 CLAUDE.md ไม่ได้โหลดพร้อมกันทั้งหมด

  • CLAUDE.md ใน subdirectory จะโหลดแบบ on demand คือโหลดตอนที่ Claude อ่านไฟล์ในโฟลเดอร์นั้น ไม่ได้โหลดตอนเริ่ม session
  • subagent ที่มีมาในตัว (built-in) อย่าง Explore และ Plan ข้าม CLAUDE.md ตอนเริ่ม ถ้ามีกฎสำคัญ ต้องเขียนซ้ำลงใน prompt ที่ใช้สั่งงาน subagent
  • custom subagent ที่ตั้ง omitClaudeMd ก็ข้าม CLAUDE.md เหมือนกัน

2.4 Bash rule จับแค่ข้อความคำสั่งตรงตัว

Permission rule ของ Bash เทียบกับ string ของคำสั่ง ไม่ได้ดูว่าสุดท้ายแล้วรันโปรแกรมอะไร เช่น rule Bash(rm *) จะไม่บล็อก /bin/rm -rf build หรือ find . -name '*.log' -delete และ ไม่มีคำเตือนใดๆ เหมือนป้าย "ห้ามเข้าประตูหน้า" ที่ไม่ได้ห้ามคนเดินเข้าประตูหลัง

ถ้าต้องการการันตีจริง ให้ใช้ PreToolUse hook (สคริปต์ที่ตรวจก่อน tool ทำงาน) หรือ sandbox แทน pattern ของ string

เข้าใจผิดบ่อย

"/status บอกว่าอ่าน settings.json ของ project แล้ว ค่าทุกตัวในนั้นก็ต้องมีผล" ไม่ใช่ ถูกอ่านไม่เท่ากับชนะ local ทับ project และ project ทับ user

"rule Bash(rm *) ขึ้นใน /permissions แสดงว่าการลบไฟล์ถูกบล็อกหมดแล้ว" ไม่ใช่ rule โหลดแล้วจริง แต่จับเฉพาะคำสั่งที่ขึ้นต้นด้วย string นั้น วิธีลบแบบอื่นหลุดได้หมด

สรุปสั้นๆ

ค่าไม่มีผล → ดู precedence (local > project > user) · ใส่ permissions/hooks/env ใน ~/.claude/settings.json ไม่ใช่ ~/.claude.json · Explore/Plan ไม่อ่าน CLAUDE.md ต้องบอกซ้ำ · Bash rule ไม่ใช่กำแพงจริง ใช้ hook หรือ sandbox

ลองเดาก่อน

Tech lead ตั้ง "model": "claude-opus-4-8" ไว้ใน .claude/settings.json ของ repo แต่ dev คนหนึ่งเปิดมาทีไรก็ได้ Sonnet ทุกครั้ง ทั้งที่ /status แสดงว่าไฟล์ project ถูกอ่านแล้ว สาเหตุที่น่าจะเป็นที่สุดคือ?

  1. dev คนนั้นตั้ง key model ไว้ใน .claude/settings.local.json ของตัวเอง ซึ่งมีลำดับสูงกว่า
  2. เครื่องของ dev ไม่ได้ export ตัวแปร environment ของ model ไว้ ไฟล์ project เลยถูกข้าม
  3. ค่าใน settings.json มีผลกับไฟล์ที่สร้างหลังจากแก้ settings เท่านั้น
  4. Claude Code เวอร์ชันของ dev เก่าเกินกว่าจะรู้จัก field model
ดูเฉลย

A /status ยืนยันแล้วว่าไฟล์ถูกโหลด ปัญหาจึงเป็นเรื่องลำดับ ไม่ใช่การโหลด settings.local.json ชนะ settings.json ของ project ตัวเลือกอื่นเป็นกลไกที่ไม่มีอยู่จริง

Checkpoint 2

ทีมใส่ Bash(rm *) เป็น deny rule และเห็นใน /permissions แล้ว แต่ Claude ยังล้างโฟลเดอร์ cache ได้ด้วย find ./cache -type f -delete โดยไม่มีอะไรเตือน ควรทำอย่างไร?

  1. ย้าย rule ไปไว้ใน ~/.claude.json เพื่อให้มีผลทุก project
  2. รีสตาร์ท session เพราะ rule ที่ขึ้นแต่ไม่บังคับแปลว่าโหลดไม่ครบ
  3. เปลี่ยนไปบล็อกด้วย PreToolUse hook หรือ sandbox แทนการใช้ pattern ของ string คำสั่ง
  4. เปิด debug log หา error ที่ rule โยนออกมา
ดูเฉลย

C rule โหลดครบแล้ว แต่จับได้เฉพาะ string ที่ตรง rm … และไม่โยน error ใดๆ ส่วน ~/.claude.json เป็นที่เก็บ app state ไม่ใช่ที่ใส่ permission

Checkpoint 3

CLAUDE.md ของ project เขียนว่า "ห้ามแก้ไฟล์ใน migrations/" session หลักทำตามดี แต่ตอนส่งงานให้ subagent Plan ไปวางแผน แผนที่ได้กลับมีขั้นตอนแก้ไฟล์ migration ควรแก้อย่างไร?

  1. เพิ่มกฎลงใน ~/.claude.json
  2. เขียนกฎนั้นซ้ำใน prompt ที่ใช้สั่งงาน subagent Plan
  3. สร้าง CLAUDE.md ใหม่ไว้ใน migrations/
  4. รัน /memory อีกรอบให้ subagent เห็นไฟล์
ดูเฉลย

B subagent Explore และ Plan ข้าม CLAUDE.md ตอนเริ่ม จึงต้องบอกกฎซ้ำใน prompt ที่ส่งไป ~/.claude.json ไม่ใช่ที่เก็บกฎ, CLAUDE.md ในโฟลเดอร์ย่อยโหลดก็ต่อเมื่ออ่านไฟล์ในนั้นแล้ว (ซึ่งสายเกินไปสำหรับการวางแผน) และ /memory แค่แสดงตำแหน่งไฟล์

3. Hook ที่ไม่เคยทำงานเลย

Hook ที่เขียนผิดส่วนใหญ่ ไม่ error แค่ไม่ถูกเรียกเฉยๆ สาเหตุที่พบบ่อย:

  • วางผิดที่ hook ของ project และ user ต้องอยู่ใต้ key "hooks" ใน settings.json ไฟล์แยก hooks/hooks.json ใช้ได้กับ plugin เท่านั้น ถ้าสร้างไฟล์นี้เองใน project มันจะไม่ถูกโหลด
  • matcher เป็น array จะถูก flag ว่า invalid และถ้าอยู่ใต้ PreToolUse หรือ PermissionRequest จะทำให้ hook อื่นทั้งหมดในไฟล์เดียวกันไม่ถูกโหลดด้วย
  • ตัวพิมพ์เล็ก-ใหญ่ matcher เป็น case-sensitive ชื่อ tool ขึ้นต้นด้วยตัวใหญ่ (Bash, Edit, Write, Read) ใส่ "bash" จะไม่ match อะไรเลย และไม่มี error
  • คั่นด้วย comma ก่อนเวอร์ชัน v2.1.191 matcher "Edit,Write" ถูกตีความตรงตัวทั้ง string จึงไม่ match อะไร ใช้ "Edit|Write" ซึ่งใช้ได้ทุกเวอร์ชัน
  • สะกดชื่อ tool ผิด ก็พลาดแบบเงียบๆ เหมือนกัน

ตัวอย่างโครงสร้างที่ถูก (ใน .claude/settings.json):

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "./scripts/check-protected.sh" }]
      }
    ]
  }
}

เทียบกับแบบที่พัง: "matcher": ["Edit", "Write"] (array) หรือ "matcher": "edit|write" (ตัวเล็ก)

ข้อสอบชอบถาม

matcher แบบ array ใต้ PreToolUse ไม่ได้ทำให้พังแค่ hook ตัวเดียว แต่ทำให้ hook อื่นในไฟล์เดียวกันไม่โหลดไปด้วย entry ผิดตัวเดียวเลยดูเหมือน "hook ทุกตัวเสีย"

เข้าใจผิดบ่อย

"ถ้า matcher เขียนผิด เช่น "bash" ระบบจะขึ้น error ให้เห็น" ไม่ใช่ matcher เป็น case-sensitive และ matcher ที่ไม่ match อะไรก็ไม่ error hook แค่ไม่เคยรัน

สรุปสั้นๆ

hook ไม่ทำงาน → ดูที่อยู่ (key "hooks" ใน settings.json, ไม่ใช่ hooks.json แยก) · matcher เป็น string ไม่ใช่ array · ชื่อ tool ตัวใหญ่ · ใช้ | ไม่ใช่ , แล้วยืนยันด้วย /hooks

Checkpoint 4 (จับคู่)

จับคู่ config ของ hook กับผลที่เกิดขึ้น:

  1. "matcher": "write"
  2. "matcher": ["Bash", "Edit"] ใต้ PreToolUse
  3. "matcher": "Edit,Write" บน Claude Code เวอร์ชันเก่ากว่า v2.1.191
  4. "matcher": "Edit|Write"
  5. เขียน hook ไว้ใน hooks/hooks.json ที่ root ของ project (ไม่ใช่ plugin)

ผลที่เป็นไปได้: (a) ทำงานถูกต้องทุกเวอร์ชัน (b) ไม่ match อะไร และไม่มี error (c) ถูก flag invalid และ hook อื่นในไฟล์ไม่โหลดด้วย (d) ไฟล์ไม่ถูกโหลดเลย (e) ถูกตีความตรงตัวทั้ง string จึงไม่ match

ดูเฉลย

1-b, 2-c, 3-e, 4-a, 5-d ชื่อ tool ต้องตัวใหญ่, array ใต้ PreToolUse ลากตัวอื่นพังด้วย, comma ไม่รองรับในเวอร์ชันเก่า, | ใช้ได้เสมอ และ hooks.json แยกไฟล์เป็นของ plugin เท่านั้น

4. MCP server: 3 สถานะที่พัง และวิธีแก้ของแต่ละแบบ

ดูสถานะจาก /mcp แล้วเลือกวิธีแก้ให้ตรงกับสถานะ ห้ามใช้วิธีเดียวกันแก้ทุกแบบ

สิ่งที่ /mcp แสดงความหมายวิธีแก้
failedprocess ของ server ไม่ได้เริ่มเลย สาเหตุยอดฮิตคือ path แบบ relative ใน command หรือ args ซึ่งจะ resolve จากโฟลเดอร์ที่เปิด Claude Codeใช้ absolute path สำหรับสคริปต์ในเครื่อง ส่วนโปรแกรมที่อยู่ใน PATH อย่าง npx หรือ uvx ใช้ได้ตามปกติ
ไม่ขึ้นในรายการ / disabled (server ระดับ project)หน้าต่างขออนุมัติครั้งแรกของ server ใน .mcp.json ถูกปิดทิ้งไปเข้าไปอนุมัติจาก /mcp
connected แต่ 0 toolsserver เริ่มทำงานแล้ว แต่ไม่ส่งรายชื่อ tool กลับมากด Reconnect ถ้ายังเป็นศูนย์ ให้รัน claude --debug=mcp แล้วอ่าน stderr ของ server ใน ~/.claude/debug/<session-id>.txt

ที่อยู่ของ config MCP

  • server ระดับ project อยู่ใน .mcp.json ที่ root ของ repo (ไม่ใช่ใน .claude/) ใต้ key mcpServers (ไม่ใช่ servers แบบที่ VS Code ใช้)
  • settings.json ไม่อ่าน key mcpServers ใส่ไว้ตรงนั้นก็ไม่มีผล
  • ตัวแปร environment ของแต่ละ server ใส่ไว้ใน entry ของ server นั้นใน .mcp.json
  • safe mode ปิด MCP server ทั้งหมด ดังนั้น server ที่ขึ้นว่า connected ไม่ได้รันอยู่ใน safe mode
{
  "mcpServers": {
    "tickets": {
      "command": "/Users/me/tools/ticket-mcp/run.sh",
      "args": ["--readonly"],
      "env": { "TICKET_API_URL": "https://tickets.internal" }
    }
  }
}
เข้าใจผิดบ่อย

"server ที่ connected แต่มี 0 tools ต้องแก้ path เป็น absolute หรือกดอนุมัติใหม่" ไม่ใช่ ปัญหา path ทำให้ server เริ่มไม่ได้ (failed) และการปิดหน้าอนุมัติทำให้ server ถูก disable แต่ server ที่ connected แปลว่าเริ่มทำงานแล้ว ขั้นต่อไปคือ Reconnect แล้วดู stderr ใน debug log

สรุปสั้นๆ

failed → absolute path · disabled/ไม่ขึ้น → อนุมัติใน /mcp · connected 0 tools → Reconnect แล้วดู stderr · config อยู่ใน .mcp.json ที่ root ใต้ mcpServers

Checkpoint 5 (จับคู่)

จับคู่อาการกับวิธีแก้ (A: เปลี่ยนเป็น absolute path, B: อนุมัติจาก /mcp, C: ย้าย config ไป .mcp.json ที่ root, D: Reconnect แล้วอ่าน stderr ใน debug log):

  1. server ขึ้นว่า failed และ command เขียนว่า ./scripts/mcp-server.sh
  2. เพื่อนร่วมทีม clone repo มาแล้วไม่เห็น server ของ project เลย เพราะเผลอปิดหน้าต่างถามตอนเปิดครั้งแรก
  3. ใส่ mcpServers ไว้ใน .claude/settings.json แล้ว server ไม่ขึ้นเลย
  4. server ขึ้น connected แต่จำนวน tool เป็นศูนย์
ดูเฉลย

1-A, 2-B, 3-C, 4-D path relative ทำให้เริ่มไม่ได้, approval ที่ถูกปิดต้องอนุมัติใหม่ใน /mcp, settings.json ไม่อ่าน mcpServers และ connected-0-tools ต้องดู stderr

Checkpoint 6

/mcp แสดงว่า server ค้นเอกสารภายใน "docs-search" เป็น connected แต่ Claude บอกว่าไม่มี tool สำหรับค้นเอกสาร ขั้นต่อไปที่ถูกต้องคือ?

  1. เปลี่ยน command ของ server เป็น absolute path
  2. เปิด Claude Code ใหม่ด้วย --safe-mode เพราะ server ที่ไม่มี tool ถูกปิดใน safe mode
  3. อนุมัติ server ใหม่ เพราะ approval ระดับ project หมดอายุเองแบบเงียบๆ
  4. กด Reconnect จาก /mcp ถ้ายังเป็นศูนย์ ให้รันแบบ debug MCP แล้วอ่าน stderr ของ server
ดูเฉลย

D connected แปลว่า process เริ่มแล้ว ปัญหา path และ approval จึงตัดทิ้งได้ (approval ไม่ได้หมดอายุเอง) ส่วน safe mode ปิด MCP ทั้งหมด ไม่ได้ช่วยวินิจฉัยเคสนี้

5. หาต้นเหตุด้วย safe mode หรือ config directory ที่สะอาด

ถ้าคำสั่งข้างบนยังชี้ไม่ได้ ให้ใช้วิธีตัดออกทีละส่วน (isolate) แบบเดียวกับการถอดปลั๊กทีละเครื่องเพื่อหาว่าเครื่องไหนทำไฟตก

5.1 Safe mode

เปิดด้วย claude --safe-mode หรือตั้ง env CLAUDE_CODE_SAFE_MODE

  • ปิด: CLAUDE.md, skills, plugins, hooks, MCP servers, custom commands และ custom agents
  • ยังทำงาน: การ auth, การเลือก model, built-in tools และ permissions

ถ้าปัญหาหายไปใน safe mode แปลว่าต้นเหตุอยู่ในส่วนที่ถูกปิด ใช้ได้ดีกับอาการ CPU หรือ memory พุ่งด้วย ถ้าใช้ทรัพยากรลดลงใน safe mode ให้ไล่ดู plugins, MCP servers และ hooks

5.2 Config directory ที่สะอาด

mkdir -p ~/claude-clean/empty && cd ~/claude-clean/empty
CLAUDE_CONFIG_DIR=~/claude-clean/config claude --setting-sources user
  • บรรทัดแรกสร้างและเข้าโฟลเดอร์ว่าง จะได้ไม่มีไฟล์ project ใดๆ
  • CLAUDE_CONFIG_DIR ชี้ไปที่ config directory ใหม่ที่ว่างเปล่า แทน ~/.claude เดิม
  • --setting-sources user เปิดเฉพาะแหล่ง settings ระดับ user ตัด project และ local ออก
  1. ถ้าปัญหาหาย: copy ไฟล์ของ user เดิมเข้าไปในโฟลเดอร์ใหม่ ทีละไฟล์ จนปัญหากลับมา ไฟล์ล่าสุดคือตัวการ
  2. ถ้าใส่ไฟล์ user ครบแล้วปัญหาไม่กลับมา: ลองเปิดจากโฟลเดอร์ project โดยไม่ใส่ --setting-sources user เพื่อดูว่าเป็นที่ config ของ project หรือ local
  3. ถ้าปัญหายังอยู่แม้ในสภาพสะอาด: ต้นเหตุอยู่นอก config ของ user และ project ให้ดู /status ว่ามี managed settings หรือไม่ (ไฟล์ของ user ทับไม่ได้ และปิดด้วยการทดสอบนี้ไม่ได้) แล้วค่อยดู environment variable ของ shell
สรุปสั้นๆ

safe mode = ปิด customization ทั้งหมดทีเดียว ดูว่าปัญหาอยู่ในกลุ่มนั้นไหม · clean config dir + --setting-sources user = เริ่มจากศูนย์แล้วเติมทีละไฟล์ · ถ้ายังพังในสภาพสะอาด ดู managed settings และ env ของ shell

Checkpoint 7

คุณต้องการเปิด Claude Code ด้วย config directory ใหม่ และให้โหลดเฉพาะ settings ระดับ user (ไม่เอา project และ local) ช่องว่างควรเป็นอะไร?

CLAUDE_CONFIG_DIR=~/claude-clean/config claude --setting-sources ____
  1. project
  2. managed
  3. local
  4. user
ดูเฉลย

D user เปิดเฉพาะแหล่ง user ทำให้ project และ local ไม่ถูกโหลด ส่วน managed settings ปิดจากการทดสอบนี้ไม่ได้อยู่แล้ว

Checkpoint 8

Claude Code ของ dev คนหนึ่งกิน CPU สูงผิดปกติ พอเปิดด้วย claude --safe-mode อาการหายไป ข้อสรุปไหนถูกต้อง?

  1. ต้นเหตุอยู่ที่ระบบ auth หรือการเลือก model
  2. ต้นเหตุน่าจะอยู่ในส่วนที่ safe mode ปิด เช่น plugin, MCP server หรือ hook
  3. ต้นเหตุคือ permission rule เพราะ safe mode ปิด permissions
  4. ต้นเหตุคือ built-in tools ต้องลง Claude Code ใหม่
ดูเฉลย

B safe mode ปิด CLAUDE.md, skills, plugins, hooks, MCP servers และ custom commands/agents แต่ auth, model, built-in tools และ permissions ยังทำงานตามปกติ ปัญหาที่หายไปจึงชี้ไปที่กลุ่มที่ถูกปิด
