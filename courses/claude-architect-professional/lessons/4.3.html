4.3 A/B testing prompt: baseline, segment และการ rollout ตามเวอร์ชัน

ต้นฉบับ: CertSafari 4.3

อ่านจบแล้วควรทำได้
  • ตั้ง baseline และเป้าตัวเลขไว้ ก่อน จะลองเปลี่ยนอะไร
  • เปรียบเทียบแบบ offline อย่างยุติธรรม: ชุดข้อมูลเดียวกัน grader เดียวกัน เปลี่ยนทีละตัวแปร
  • บอกได้ว่าเมื่อไหร่ live A/B test คุ้มค่า และเมื่อไหร่ offline eval ก็พอ
  • อ่านผลแยกตาม segment เพื่อจับ regression ที่ค่าเฉลี่ยรวมซ่อนไว้
  • ใช้เวอร์ชันที่ pin ไว้ (Managed Agents) ทำ canary, promote และ rollback
แนวคิดหลัก: "ดีขึ้น" ต้องเทียบกับของจริง ด้วยเกณฑ์ที่ตั้งไว้ก่อน

การเปลี่ยนแปลงหนึ่งจะนับว่าเป็นการปรับปรุงได้ก็ต่อเมื่อมัน ชนะเวอร์ชันที่รันอยู่ใน production ตอนนี้ บน metric และเป้าที่เลือกไว้ล่วงหน้า คะแนนสูงลอยๆ โดยไม่มีอะไรให้เทียบ หรือเป้าที่ขยับตามผลลัพธ์ ไม่นับ

1. Baseline และเป้าหมาย

การพัฒนา prompt คือลูปง่ายๆ: เปลี่ยนหนึ่งอย่าง → วัดเทียบ baseline → เก็บหรือทิ้ง แล้ววนต่อ baseline ในที่นี้คือผลของเวอร์ชันที่ใช้อยู่จริงบนชุดทดสอบเดียวกัน

เป้าหมาย (target) ควรยึดกับอะไรที่มีที่มา เช่น benchmark ของอุตสาหกรรม ผลการทดลองก่อนหน้า งานวิจัย หรือความเห็นผู้เชี่ยวชาญ สังเกตว่า ผลการทดลองก่อนหน้าก็คือ baseline ชนิดหนึ่ง นั่นเอง

สิ่งสำคัญคือ ตั้งเส้นชัยก่อนวิ่ง ถ้ากำหนดเป้าหลังเห็นผล คนมักขยับเป้าให้ผลที่ได้ดูผ่านโดยไม่รู้ตัว

เคล็ดลับเชิงปฏิบัติ: รัน eval suite กับเวอร์ชัน production ไว้ตั้งแต่แรก แล้วบันทึกไม่ใช่แค่คะแนนคุณภาพ แต่รวมถึง latency, token usage, ต้นทุน และ error rate พอมีผู้สมัคร (candidate) ใหม่มา ก็เทียบได้ทันทีทุกมิติ

สรุปสั้นๆ

baseline = คะแนนของ production บนชุด eval เดียวกัน · เป้าต้องมีที่มาและตั้งก่อนรัน · บันทึก latency/token/cost/error คู่กับคุณภาพตั้งแต่แรก

Checkpoint 1

prompt สกัดข้อมูลจากใบสั่งซื้อปัจจุบันได้ 91% ทีมเขียน prompt ใหม่และอยากรู้ว่ามันดีกว่าจริงไหม ต้องมีอะไรบ้างถึงจะตัดสินได้?

  1. ให้ senior engineer สามคนอ่าน output แล้วโหวตว่าชอบอันไหน
  2. คะแนนของ prompt ใหม่อย่างเดียว ถ้าเกิน 90% ก็ถือว่าดี
  3. คะแนนของ prompt production บนชุด eval เดียวกัน และ margin ที่ต้องชนะซึ่งกำหนดไว้ก่อนรัน
  4. ชุดทดสอบใหม่ที่ออกแบบมาเพื่อโชว์จุดแข็งของ prompt ใหม่
ดูเฉลย

C ต้องมีทั้งของเทียบ (baseline บนชุดเดียวกัน) และเกณฑ์ที่ล็อกไว้ก่อน A เป็นความเห็น B ไม่มีของเทียบ D ทำให้ชุดทดสอบลำเอียงเข้าข้างผู้สมัคร

2. เปรียบเทียบแบบ offline บน held-out set

วิธีพื้นฐานที่สุดคือรันทั้ง baseline และ candidate บน held-out set ที่มี label ชุดเดียวกัน และให้คะแนนด้วย grader ตัวเดียวกัน แล้วเลือก metric ให้เหมาะกับลักษณะ output:

ลักษณะงานวิธีให้คะแนนทำไม
label เชิงหมวดหมู่ (เช่น ระดับความเร่งด่วน)exact match เทียบกับ label ที่คนติดไว้ชัดเจน ไม่กำกวม รันซ้ำได้ถูกๆ
สรุปข้อความอิสระที่มีสรุปอ้างอิงROUGE-L F1ให้คะแนนการเก็บเนื้อหาสำคัญในลำดับใกล้เคียงกัน exact match ใช้ไม่ได้เพราะคำตอบถูกเขียนได้หลายแบบ
ความเร็วในการตอบresponse time (ms)เป็นเกณฑ์เชิงปฏิบัติการ ติดตามคู่กับคุณภาพ ไม่ใช่ใช้แทน

อะไรที่ ไม่ใช่ metric ที่ถูกต้อง: ความมั่นใจที่โมเดลประเมินตัวเอง (self-rated confidence) และการให้เพื่อนร่วมงานโหวต ทั้งสองอย่างไม่ได้บอกความถูกต้อง

เรื่องขนาด: เหมือนบท 4.2 คือ ชุดใหญ่ที่ตรวจอัตโนมัติชนะชุดเล็กที่คนตรวจ เพราะการตรวจเป็นต้นทุนที่เกิดซ้ำทุกครั้งที่รันใหม่

def compare(dataset, prompt_a, prompt_b, grade):
    score = {"A": 0, "B": 0}
    for case in dataset:                      # ชุดเดียวกัน
        score["A"] += grade(run(prompt_a, case.input), case.label)   # grader เดียวกัน
        score["B"] += grade(run(prompt_b, case.input), case.label)
    return {k: v / len(dataset) for k, v in score.items()}
เข้าใจผิดบ่อย

"เวอร์ชันใหม่รายงานความมั่นใจเฉลี่ยสูงกว่า แปลว่าแม่นกว่า" ไม่ใช่ ความมั่นใจที่โมเดลบอกเองไม่ได้สัมพันธ์กับความถูกต้อง

"ชุดเล็กที่คนติด label เองน่าเชื่อกว่าชุดใหญ่ที่ตรวจอัตโนมัติเสมอ" ไม่ใช่ โดยทั่วไปปริมาณ + ตรวจอัตโนมัติให้สัญญาณที่ดีกว่าและรันซ้ำได้บ่อยกว่า

สรุปสั้นๆ

ชุดเดียวกัน grader เดียวกัน · หมวดหมู่ → exact match · สรุปมีอ้างอิง → ROUGE-L F1 · latency คู่กับคุณภาพ · ห้ามใช้ความมั่นใจของโมเดลหรือโหวต

Checkpoint 2

ระบบจัดอีเมลเข้ากล่อง "ขาย / ซัพพอร์ต / สแปม" ทีมมีอีเมล 500 ฉบับที่คนติด label ไว้แล้ว อยากเทียบ prompt สองเวอร์ชัน วิธีไหนเหมาะที่สุด?

  1. ให้แต่ละเวอร์ชันบอกความมั่นใจของตัวเองแล้วเลือกตัวที่มั่นใจกว่า
  2. รันทั้งสองเวอร์ชันบน 500 ฉบับเดิม ให้คะแนนด้วย exact match เทียบ label
  3. ใช้ ROUGE-L เทียบชื่อกล่องกับ label
  4. ให้ทีมขายโหวตว่าชอบผลของเวอร์ชันไหน
ดูเฉลย

B output เป็นหมวดหมู่ exact match บนชุดเดียวกันเร็วและเป็นกลางที่สุด ROUGE-L เหมาะกับข้อความยาว ส่วนความมั่นใจและการโหวตไม่ได้วัดความถูก

Checkpoint 3

ทีมทำสรุปรายงานประชุม มีรายงาน 300 ชิ้นพร้อมสรุปอ้างอิงที่คนเขียน อยากได้ metric ที่ให้รางวัลเมื่อสรุปเก็บเนื้อหาของสรุปอ้างอิงไว้ในลำดับคล้ายกัน ควรใช้อะไร?

  1. exact match
  2. ROUGE-L F1
  3. response time
  4. ความยาวของสรุปเป็นจำนวน token
ดูเฉลย

B ROUGE-L ดู longest common subsequence จึงสะท้อนการเก็บเนื้อหาตามลำดับ exact match จะตกเกือบทุกเคสเพราะถ้อยคำต่างกัน ส่วนเวลาและความยาวไม่ได้วัดคุณภาพเนื้อหา

Checkpoint 4

ทีมมีทางเลือก: (1) ตัวอย่าง 60 เคสที่ผู้เชี่ยวชาญตรวจด้วยมือ หรือ (2) 1,500 เคสที่ตรวจอัตโนมัติด้วย exact match จะใช้ชุดไหนเป็นหลักในการเทียบเวอร์ชันที่แก้กันหลายรอบต่อสัปดาห์?

  1. ชุด 60 เคส เพราะผู้เชี่ยวชาญแม่นกว่าเสมอ
  2. ชุด 1,500 เคส เพราะปริมาณและการตรวจอัตโนมัติรันซ้ำได้ทุกรอบ
  3. ไม่ใช้ทั้งคู่ ไปทำ live A/B test เลย
  4. ใช้ชุด 60 เคสแต่ให้โมเดลตรวจแทนผู้เชี่ยวชาญ
ดูเฉลย

B ต้นทุนการตรวจเกิดซ้ำทุกรอบ ชุดใหญ่อัตโนมัติจึงใช้งานได้จริงกว่าและให้สัญญาณเสถียรกว่า live A/B test ช้าเกินไปสำหรับการเช็กทุกการแก้

3. ทำให้การเปรียบเทียบยุติธรรม

เปลี่ยนทีละตัวแปร ถ้าเปลี่ยนสามอย่างพร้อมกันแล้วคะแนนขึ้น เราไม่รู้เลยว่าอันไหนช่วย อันไหนถ่วง ตัวอย่างที่ดี: ทีมหนึ่งตรวจ prompt ของ support desk โดยสร้าง prompt 6 แบบ แต่ละแบบเพิ่ม pattern เพียงอย่างเดียวบน base ที่สะอาด แล้วรันทั้ง 6 บนชุด ticket เดียวกัน 44 ใบด้วย grader แบบ deterministic ผลคือบอกได้ชัดว่าผลแต่ละอย่างมาจากการเปลี่ยนแปลงไหน

ระวัง noise การรัน config เดิมเป๊ะซ้ำหลายรอบก็ยังได้ผลไม่เท่ากัน ต่างกันแค่ข้อเดียวอาจเป็นความบังเอิญ ให้ดูว่า margin ที่ candidate ชนะ มากกว่าการแกว่งตามปกติของ baseline เอง หรือเปล่า

Pin ทุกอย่างยกเว้นสิ่งที่ทดสอบ: eval set, grader, model, ค่า effort และ เวอร์ชันของ prompt ที่ระบุชัด

Managed Agents: bare ID กับ version

ใน Managed Agents ถ้าส่งแค่ agent ID เปล่าๆ (bare ID) ระบบจะ resolve เป็น เวอร์ชันล่าสุด เสมอ ถ้าเพื่อนร่วมทีม publish เวอร์ชันใหม่ระหว่างที่เรากำลังรัน eval ผลจะปนกันโดยไม่รู้ตัว ทางแก้คือส่งเป็น object ที่มี field version เพื่อ pin session ไว้ที่เวอร์ชันนั้นเป๊ะ

# bare ID: ได้เวอร์ชันล่าสุด ณ ตอนนั้น (เปลี่ยนได้ตลอด)
agent = "agent_support_router"

# pinned: ได้เวอร์ชัน 4 เสมอ
agent = {"id": "agent_support_router", "version": 4}

ส่วนการทดสอบ โมเดล ให้เอา prompt และข้อมูลของเราเองรันกับโมเดลแต่ละตัว อย่าอาศัยแค่ benchmark สาธารณะ

สรุปสั้นๆ

เปลี่ยนทีละอย่าง · ชนะต้องเกิน noise ของ baseline · pin eval set, grader, model, effort และเวอร์ชัน prompt · bare ID = ล่าสุดเสมอ ใช้ version เพื่อ pin

Checkpoint 5

harness ของทีม eval เรียก Managed Agent ด้วย agent ID เปล่าๆ ขณะที่ทีมอื่น publish เวอร์ชันใหม่วันละหลายครั้ง ผล eval เลยแกว่งไม่มีเหตุผล ควรแก้อย่างไร?

  1. รัน eval ตอนกลางคืนที่ไม่มีใคร publish
  2. ส่ง agent ID พร้อม version ที่ระบุชัดในทุก session
  3. เพิ่มจำนวนเคสใน eval เพื่อลด noise
  4. เปลี่ยน grader เป็นแบบ deterministic
ดูเฉลย

B ต้นเหตุคือ bare ID resolve เป็นเวอร์ชันล่าสุด การ pin version ทำให้ตัวแปรนี้นิ่ง ข้ออื่นแค่อ้อมปัญหาหรือแก้ผิดจุด

4. เมื่อไหร่ควรทำ live A/B test

Live A/B test คือการแบ่ง traffic จริงแบบสุ่มระหว่างเวอร์ชันเก่าและใหม่ ข้อดีคือการสุ่มช่วยคุมตัวแปรแทรกซ้อน (confound) และวัดผลลัพธ์จริงทางธุรกิจได้ เช่น อัตราการทำ task สำเร็จ แต่ข้อเสียก็ชัด: ช้า (เป็นวันถึงสัปดาห์) ต้องมี traffic พอ และ ผู้ใช้จริงต้องเจอเวอร์ชันที่ยังไม่พิสูจน์

วิธีบทบาทข้อจำกัด
Offline eval อัตโนมัติด่านแรกของ ทุก การเปลี่ยนแปลงวัดได้แค่สิ่งที่อยู่ใน dataset
Live A/B testยืนยันการเปลี่ยนแปลงที่สำคัญด้วยผลลัพธ์จริงช้า ต้องมี traffic ผู้ใช้เจอ candidate
Production monitoringจับปัญหาหลังเกิด (reactive)รู้ตัวเมื่อมีผลกระทบแล้ว
ปล่อยให้ทุกคนแล้วดู metricไม่ใช่ A/B testไม่มี control group จึงบอกไม่ได้ว่าผลมาจาก prompt หรือจากอย่างอื่น

อีกข้อที่ควรทำคู่กันเสมอ: เมื่อ metric ใน A/B test ขยับ ให้ อ่าน transcript ประกอบด้วย ตัวเลขบอกว่า "อะไร" เปลี่ยน transcript บอกว่า "ทำไม"

เข้าใจผิดบ่อย

"อยากเช็ก prompt ที่แก้ใหม่ให้เร็วที่สุด ให้ทำ live A/B test" ไม่ใช่ live test เป็นวิธีที่ช้าที่สุด เริ่มที่ offline eval ก่อนเสมอ

"ปล่อยเวอร์ชันใหม่ให้ทุกคน แล้ว CSAT ขึ้น แปลว่า prompt ใหม่ดีกว่า" ไม่ใช่ ไม่มี control group อาจเป็นฤดูกาล โปรโมชั่น หรืออย่างอื่นก็ได้

สรุปสั้นๆ

offline eval ทุกครั้ง → live A/B เฉพาะการเปลี่ยนสำคัญ → monitoring คอยจับหลังปล่อย · ไม่มี control group ไม่ใช่ A/B · อ่าน transcript คู่กับตัวเลข

Checkpoint 6 (จับคู่)

จับคู่วิธีกับบทบาท:

  1. Offline eval อัตโนมัติ
  2. Live A/B test
  3. Production monitoring
  4. เปลี่ยนให้ทุกคนแล้วดู metric ตัวแทน

ตัวเลือก: A) จับปัญหาหลังเกิดขึ้นแล้ว · B) ระบุไม่ได้ว่าผลมาจาก prompt เพราะไม่มี control · C) ด่านแรกของทุกการแก้ · D) ยืนยันการเปลี่ยนสำคัญด้วยผลจริง แต่ช้า

ดูเฉลย

1-C, 2-D, 3-A, 4-B แต่ละวิธีมีที่ทางของมัน ไม่ได้แทนกัน

5. อ่านผลแยกตาม segment

ค่าเฉลี่ยรวมซ่อน regression ได้เก่งมาก การแก้ที่ตั้งใจช่วย segment หนึ่ง อาจไปทำให้ segment ข้างเคียงแย่ลง ขณะที่คะแนนรวมกลับขึ้น ดังนั้นให้แยกผลตาม หมวด, ประเภท input หรือทีมปลายทาง ทุกครั้ง นอกเหนือจากดูคะแนนรวม

ในตัวอย่างนี้คะแนนรวมก็ลดด้วย แต่หลักเดียวกันใช้ได้แม้กรณีที่คะแนนรวม เพิ่มขึ้น ถ้า gain ใน segment ใหญ่มากพอ มันจะกลบ segment ที่พังได้มิด

เข้าใจผิดบ่อย

"คะแนนรวมเท่าเดิมหรือดีขึ้น แปลว่า promote ได้อย่างปลอดภัย" ไม่ใช่ ต้องดูทุก segment ก่อน

สรุปสั้นๆ

อ่านผลรวม + แยกตาม segment เสมอ กฎที่กว้างเกินมักดึงเคสของ segment ข้างเคียงไปด้วย

Checkpoint 7

  1. Promote เลย เพราะคะแนนรวมขึ้น 5 จุด
  2. Promote แล้วให้ทีมคืนเงินโอนเคสเองไปก่อน
  3. ยังไม่ promote แก้กฎให้แคบลง แล้วรันเทียบแยกตามหมวดอีกรอบ
  4. ตัดเคสคืนเงินที่มีคำว่า "ยกเลิก" ออกจาก eval

6. Promote, canary และ rollback ตามเวอร์ชัน

Managed Agents เก็บ prompt ไว้ฝั่ง server ทุกครั้งที่เรียก agents.update จะได้ เวอร์ชันใหม่ที่แก้ไขไม่ได้ (immutable) แล้ว session เลือกใช้เวอร์ชันด้วยหมายเลข ดูรายการเวอร์ชันทั้งหมดได้ด้วย client.beta.agents.versions.list(AGENT_ID)

  1. สร้างเวอร์ชัน (agents.update) เป็นงานสำรวจ ถ้าผู้เรียกทุกตัว pin ไว้ จะไม่มีผลกับ production เลย
  2. Canary ส่ง traffic ส่วนหนึ่งไปเวอร์ชันใหม่ แล้วเทียบกับเวอร์ชันเดิมก่อนขยายเต็ม
  3. Promote แก้ production config ที่ระบุว่าผู้เรียกต้องส่งเวอร์ชันไหน การแก้ config นี้คือขั้น release ที่ต้องผ่านการรีวิว
  4. Rollback ให้ผู้เรียกกลับไปใช้หมายเลขเวอร์ชันเดิม ไม่ต้อง deploy ใหม่
PROD = {"router": 7}            # config ที่ผ่าน code review = ตัว release

def agent_ref(name, canary=None, pct=0.0):
    v = canary if canary and random.random() < pct else PROD[name]
    return {"id": AGENT_IDS[name], "version": v}

# canary 10%:  agent_ref("router", canary=8, pct=0.10)
# promote:     PROD["router"] = 8   (ผ่านรีวิว)
# rollback:    PROD["router"] = 7   (ไม่ต้อง deploy prompt ใหม่)
ทำไม pin ถึงสำคัญด้านความปลอดภัย

agents.update ไม่มี approval workflow ในตัว และ API key ใดก็ได้ใน workspace เรียกได้ ถ้าผู้เรียกใช้ bare ID เวอร์ชันที่ยังไม่ผ่านรีวิวจะเข้าสู่ production ทันทีที่มีคน update การ pin เวอร์ชันอย่างชัดเจนคือสิ่งที่กันเวอร์ชันใหม่ออกจาก production จนกว่าจะถูก promote

เข้าใจผิดบ่อย

"ผู้เรียกที่ใช้ bare ID ปลอดภัย เพราะทีมรีวิว prompt ก่อน update อยู่แล้ว" ไม่ใช่ ระบบไม่ได้บังคับการรีวิว ใครถือ key ก็ update ได้ bare ID จะรับเวอร์ชันนั้นทันที

สรุปสั้นๆ

update = สร้างเวอร์ชัน immutable (ยังไม่ใช่ release) · canary = แบ่ง traffic บางส่วน · promote = แก้หมายเลขที่ pin (ผ่านรีวิว) · rollback = pin กลับ ไม่ต้อง deploy

Checkpoint 8 (จับคู่)

สมมติผู้เรียกทุกตัว pin เวอร์ชันไว้ จับคู่การกระทำกับผลที่เกิด:

  1. เรียก agents.update สร้าง v9
  2. ส่ง 5% ของ traffic ไป v9
  3. เปลี่ยนเลขใน production config จาก 8 เป็น 9 ผ่าน PR ที่รีวิวแล้ว
  4. เปลี่ยนเลขกลับเป็น 8

ตัวเลือก: A) Rollback โดยไม่ต้อง deploy · B) ไม่มีผลกับ production · C) Canary · D) Promote

ดูเฉลย

1-B, 2-C, 3-D, 4-A การสร้างเวอร์ชันเป็นงานสำรวจ ส่วนการเปลี่ยนเลขที่ pin คือ release

Checkpoint 9

นักพัฒนาคนหนึ่งเรียก agents.update เพื่อลองไอเดียใหม่ แล้วลูกค้าเริ่มได้คำตอบแปลกๆ ทันที ข้อไหนอธิบายสาเหตุและวิธีป้องกันได้ถูกที่สุด?

  1. เวอร์ชันเก่าถูกเขียนทับ ต้องเปิด backup ของ prompt
  2. production ใช้ bare ID จึงรับเวอร์ชันล่าสุดทันที ควร pin version และให้การเปลี่ยนเลขเป็นขั้น release ที่ผ่านรีวิว
  3. agents.update มี approval ในตัว แต่ถูกปิดไว้ ต้องไปเปิด
  4. ต้องเปลี่ยนไปเก็บ prompt ในโค้ดแทน server
ดูเฉลย

B เวอร์ชันเป็น immutable ไม่ได้ถูกเขียนทับ (A ผิด) และไม่มี approval workflow ในตัว (C ผิด) ปัญหาคือ bare ID ที่ resolve เป็นล่าสุด
