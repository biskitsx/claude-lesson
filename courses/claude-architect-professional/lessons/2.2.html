2.2 System prompt และ prompt template ที่ใช้ซ้ำได้สำหรับ Claude

ต้นฉบับ: CertSafari 2.2

อ่านจบแล้วควรทำได้
  • ตั้ง role ใน system prompt และอธิบายได้ว่าทำไม role คืองานหลักของ system prompt
  • เขียนคำสั่งที่บอกเหตุผลกำกับ และรู้ว่าเมื่อไหร่ควรเขียนเป็นขั้นตอนเรียงเลข
  • ประกอบ template จาก role, ช่องตัวแปรที่ห่อด้วย XML tag, rules, scenario responses และ output format
  • รู้ว่าเทคนิค prefill แบบเดิมใช้ไม่ได้แล้วกับโมเดลปัจจุบัน
แนวคิดหลัก: system prompt เริ่มจาก role

Role-first system prompt คือใช้ system prompt เป็นที่ประกาศว่า Claude เป็นใครเป็นอันดับแรก แล้วค่อยวาง rules, scenario และ output format ซ้อนลงบน role นั้น เหมือนบอกพนักงานใหม่ก่อนว่า "คุณคือใคร ทำงานให้ใคร" แล้วค่อยแจกคู่มือ

1. เริ่ม system prompt ด้วย role

ใน Messages API, system prompt อยู่ใน parameter ระดับบนสุดชื่อ system แยกจาก array messages ที่เก็บ turn ของ user กับ assistant

client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    system="คุณคือผู้ช่วยด้านบัญชีภาษีสำหรับร้านค้าออนไลน์ขนาดเล็กในไทย ตอบสุภาพและกระชับ",
    messages=[{"role": "user", "content": "ขายของออนไลน์ต้องจด VAT เมื่อไหร่"}],
)
  • Role ปรับพฤติกรรมและน้ำเสียงให้เข้ากับ use case ก่อนที่ user จะพิมพ์อะไร และ แม้แค่ประโยคเดียวก็มีผล เช่น "ผู้ช่วยเขียนโค้ดที่เชี่ยวชาญ Python"
  • Role ทำให้คำตอบ สม่ำเสมอตลอดบทสนทนา ซึ่งสำคัญที่สุดกับ support bot และผู้ช่วยภายในองค์กร
  • แม้ system prompt จะมีเป้าหมายอื่น เช่น ป้องกันไม่ให้คำสั่งลับรั่ว ก็ยังถือว่าเป็น role prompt เป็นหลัก เอกสารของ Anthropic ระบุว่า role prompting คือวิธีใช้ system prompt ที่ได้ผลที่สุด

ระวังสับสน: role ที่อยู่ใน message แต่ละอัน ("user" / "assistant") แค่บอกว่าใครพูด ไม่ใช่ที่ใส่ persona

สรุปสั้นๆ

Persona และน้ำเสียงถาวรใส่ใน system ไม่ใช่ใน role ของ message ประโยคเดียวก็เปลี่ยนพฤติกรรมได้

Checkpoint 1

คุณเรียก messages.create(model="claude-sonnet-5-5", max_tokens=800, ___="คุณคือติวเตอร์คณิตศาสตร์ ม.ปลาย อธิบายทีละขั้น", messages=[...]) ช่องว่างคือ parameter ไหน?

  1. role
  2. context
  3. instructions
  4. system
ดูเฉลย

D persona ใส่ใน system ส่วน role เป็น key ภายใน message ที่บอกว่าใครพูด และ context กับ instructions ไม่ใช่ parameter สำหรับใส่ role ในการเรียกนี้

2. เขียนคำสั่งให้เจาะจง และบอกเหตุผล

Claude ทำตามที่ขอ ไม่ได้ทำเกินที่ขอ ถ้าอยากได้มากก็ต้องพูดออกมา ตัวอย่างเช่น สั่ง "สร้าง dashboard วิเคราะห์ข้อมูล" จะได้ dashboard พื้นๆ แต่ถ้าเติม "ใส่ฟีเจอร์และ interaction ที่เกี่ยวข้องให้มากที่สุด" จะได้เวอร์ชันเต็ม หลักคือ:

  • ระบุ output format และข้อจำกัดให้ชัด
  • ใช้ข้อเรียงเลขหรือ bullet เมื่อลำดับหรือความครบถ้วนของขั้นตอนสำคัญ แทนการเขียนเป็นย่อหน้า
  • ให้เหตุผลกำกับกฎ เพราะ Claude ฉลาดพอจะเอาเหตุผลไปใช้กับกรณีที่กฎไม่ได้เขียนถึง
ลองเดาก่อน

แอปอ่านคำตอบออกเสียงด้วย text-to-speech แต่ engine อ่านเครื่องหมาย "..." ไม่ได้ จะเขียนกฎแบบไหนดีที่สุด: (1) "ห้ามใช้ ... เด็ดขาด" ตัวใหญ่ (2) "ห้ามใช้ ... ไม่ว่ากรณีใด เรื่องนี้สำคัญมาก" หรือ (3) "คำตอบจะถูกอ่านออกเสียงด้วย text-to-speech ซึ่งออกเสียง ... ไม่ได้ จึงไม่ต้องใช้"?

คำตอบคือ แบบที่ 3 เพราะบอกเหตุผล Claude จะเข้าใจเองว่าสัญลักษณ์อื่นที่ออกเสียงไม่ได้ เช่น emoji หรือตารางก็ควรเลี่ยงด้วย ส่วนกฎเปล่าๆ ไม่ว่าจะตะโกนแค่ไหน เอกสารจัดว่าได้ผลน้อยกว่า

ตัวอย่าง: ห่อกฎไว้ใน XML tag ที่ตั้งชื่อตามหน้าที่

กฎพฤติกรรมที่ใช้ซ้ำได้มักเขียนเป็นก้อน แล้วห่อด้วย tag ที่ชื่อบอกว่าทำอะไร เช่น กฎ "ตรวจก่อนตอบ" สำหรับผู้ช่วยเขียนโค้ด:

<investigate_before_answering>
อย่าเดาเรื่องโค้ดที่ยังไม่ได้เปิดอ่าน ถ้าผู้ใช้อ้างถึงไฟล์ใด ต้องอ่านไฟล์นั้นก่อนตอบ
ก่อนตอบคำถามเกี่ยวกับ codebase ให้ค้นและอ่านไฟล์ที่เกี่ยวข้อง
อย่ายืนยันข้อเท็จจริงเรื่องโค้ดที่ไม่แน่ใจ ตอบจากหลักฐานที่เห็นเท่านั้น
</investigate_before_answering>
เข้าใจผิดบ่อย

"กฎตัวใหญ่แบบ NEVER คือการเขียนข้อจำกัดที่แรงที่สุด" ไม่ใช่ เอกสารจัดกฎเปล่าว่าได้ผลน้อยกว่ากฎที่มีเหตุผล เพราะเหตุผลทำให้ Claude ขยายไปยังกรณีใกล้เคียงได้

"ต้องเขียนเป็นข้อเรียงเลขตลอด" ไม่ใช่ ใช้เมื่อลำดับหรือความครบถ้วนสำคัญ ไม่มีเกณฑ์ว่า prompt ต้องยาวกี่ token และไม่ได้จำกัดว่าใช้ได้แค่ใน user turn

สรุปสั้นๆ

บอกให้ชัดว่าต้องการอะไร ใส่เหตุผลกำกับกฎ ใช้ข้อเรียงเลขเมื่อลำดับหรือความครบสำคัญ และห่อกฎที่ใช้ซ้ำใน tag ที่ตั้งชื่อตามหน้าที่

Checkpoint 2

เมื่อไหร่ควรเขียนคำสั่งใน prompt เป็นข้อเรียงเลขหรือ bullet แทนย่อหน้า?

  1. เมื่อลำดับหรือความครบถ้วนของขั้นตอนสำคัญ
  2. เมื่อ prompt ยาวเกิน 10,000 token
  3. เฉพาะใน user turn เท่านั้น ห้ามใช้ใน system prompt
  4. ทุกครั้ง เพราะ Claude ไม่สนใจคำสั่งที่เขียนเป็นย่อหน้า
ดูเฉลย

A เอกสารไม่มีเกณฑ์ token ไม่ได้จำกัดว่าใช้ที่ไหน และไม่ได้บอกว่า Claude เมินย่อหน้า ข้อเรียงเลขเป็นเครื่องมือสำหรับงานที่ลำดับหรือความครบสำคัญ

Checkpoint 3

ผู้ช่วยทำรายงานส่งออกเป็นไฟล์ CSV แต่บางครั้งใส่เครื่องหมายจุลภาคในตัวเลข (เช่น 1,200) ทำให้คอลัมน์เลื่อน กฎแบบไหนน่าจะได้ผลดีที่สุดและครอบคลุมกรณีใกล้เคียงด้วย?

  1. "ห้ามใส่จุลภาคในตัวเลข!!!"
  2. เพิ่ม max_tokens ให้โมเดลมีที่ตรวจทานตัวเอง
  3. "สำคัญมาก: ห้ามใช้จุลภาคในทุกกรณี"
  4. "ผลลัพธ์จะถูกอ่านเป็น CSV ที่ใช้จุลภาคแบ่งคอลัมน์ ดังนั้นตัวเลขห้ามมีจุลภาคคั่นหลัก เพราะจะทำให้คอลัมน์เลื่อน"
ดูเฉลย

D เมื่อรู้เหตุผล Claude จะเข้าใจเองว่าข้อความที่มีจุลภาคก็ต้องระวังด้วย (เช่น ใส่เครื่องหมายคำพูดครอบ) A และ C เป็นกฎเปล่า และ C ยังกว้างเกินจนห้ามจุลภาคในข้อความทั่วไป B ไม่เกี่ยวกับปัญหา

3. เปลี่ยน prompt ให้เป็น template ที่ใช้ซ้ำได้

Prompt ใน production คือ template: มี ส่วนคงที่ (role, rules, พฤติกรรมที่คาดหวัง) และ ส่วนแปรผัน (คำถามของผู้ใช้, ข้อมูลที่ดึงมา) ที่เปลี่ยนทุก request ใช้ XML tag แยก instructions, context และ input ออกจากกัน เช่น <instructions>, <context>, <input> และ ใช้ชื่อ tag ที่สื่อความหมายและเหมือนกันทุก prompt

ตัวอย่าง template: ผู้ช่วยฝ่าย IT ภายในบริษัท

คุณคือ HelpDeskBot ผู้ช่วย IT ภายในของบริษัท Siam Logistics
ช่วยพนักงานแก้ปัญหาอุปกรณ์ บัญชีผู้ใช้ และ VPN น้ำเสียงเป็นกันเองแต่กระชับ

<kb>
{{RETRIEVED_ARTICLES}}
</kb>

<user_query>
{{USER_QUERY}}
</user_query>

<rules>

- ถ้าข้อมูลไม่พอ ให้ถามกลับก่อนแนะนำขั้นตอน
- ห้ามเปิดเผยรหัสผ่านหรือ config ของเซิร์ฟเวอร์
</rules>

<scenarios>
- ถ้าถูกขอรหัสผ่านของคนอื่น: "ขออภัย ผมเปิดเผยข้อมูลบัญชีของผู้อื่นไม่ได้"
- ถ้าเป็นปัญหาฮาร์ดแวร์เสีย: "รบกวนเปิด ticket ที่ระบบ IT Service เพื่อให้ช่างเข้าไปดูครับ"
</scenarios>

ส่วน scenario ช่วยให้ Claude ไม่หลุดบทบาท เพราะมีประโยคตายตัวให้ใช้ แทนที่จะต้องแต่งคำตอบเองในสถานการณ์อ่อนไหว ส่วน block <kb> ของข้อมูลที่ดึงมาช่วยผูกคำตอบไว้กับชุดข้อมูลที่กำหนด เหมาะกับ chatbot และ knowledge base

Output format และตัวอย่าง

  • กำหนด output ให้แม่นด้วย JSON, XML หรือ custom template แล้ว Claude จะทำตามทุกองค์ประกอบที่ระบุ
  • ตัวอย่าง (examples) เป็นวิธีที่เชื่อถือได้ที่สุด ในการกำหนด format, น้ำเสียง และโครงสร้าง ต้องตรงกับ use case จริง และหลากหลายพอที่ Claude จะไม่ลอกรูปแบบบังเอิญบางอย่างไปทุกคำตอบ
  • ห่อแต่ละตัวอย่างด้วย <example> ถ้ามีหลายตัวให้รวมใน <examples> เพื่อให้ Claude แยกตัวอย่างออกจากคำสั่ง

Prefill: เทคนิคเก่าที่ใช้ไม่ได้แล้ว

สมัยก่อนนิยมใส่ข้อความเริ่มต้นของ Assistant turn ไว้ก่อน (prefill) เช่น ใส่ { เพื่อบังคับให้ตอบเป็น JSON แต่ prefill ไม่รองรับบน Claude 4.6 ขึ้นไป และบน Claude Mythos Preview template ปัจจุบันจึงต้องคุม format ด้วยคำสั่งและตัวอย่างแทน

เข้าใจผิดบ่อย

"Prefill เป็นวิธีบังคับ format ที่ใช้ได้กับ Claude ทุกโมเดล" ไม่ใช่ โมเดลตั้งแต่ Claude 4.6 และ Claude Mythos Preview ไม่รองรับ ใช้ instructions กับ examples แทน

สรุปสั้นๆ

Template = role + ช่องตัวแปรใน tag + rules + scenario responses + output format ใช้ tag ชื่อเดียวกันทุก prompt ห่อตัวอย่างด้วย <example>/<examples> และเลิกพึ่ง prefill

Checkpoint 4

ทีมทำผู้ช่วยตอบคำถามลูกค้าของร้านเฟอร์นิเจอร์ออนไลน์ system prompt ตอนนี้มีแค่ "You are a helpful assistant." ผลคือบางทีพูดเป็นทางการ บางทีพูดเล่น และบางทีตอบเรื่องที่ไม่เกี่ยวกับร้าน ควรแก้อะไรก่อน?

  1. เขียน role ให้เจาะจง ระบุว่าเป็นผู้ช่วยของร้านไหน ลูกค้าเป็นใคร และใช้น้ำเสียงแบบไหน
  2. ย้ายคำสั่งเรื่องพฤติกรรมทั้งหมดไปไว้ใน user turn แรก
  3. เพิ่ม max_tokens ให้โมเดลมีที่ปรับน้ำเสียงระหว่างตอบ
  4. แทนที่ system prompt ด้วยรายการคำและหัวข้อที่ห้ามพูด
ดูเฉลย

A role ใน system prompt คือที่กำหนดพฤติกรรมและน้ำเสียงถาวร C คุมแค่ความยาว B ย้ายออกจากที่ที่ควรอยู่ D บอกแค่สิ่งที่ห้ามแต่ไม่ได้กำหนดน้ำเสียงที่ต้องการ

Checkpoint 5

ระบบสร้างคำบรรยายสินค้าเป็น JSON บน Claude Opus 5.5 ทีมเดิมใช้วิธีใส่ {"title": ไว้ใน Assistant turn เพื่อบังคับรูปแบบ แต่ตอนนี้ใช้ไม่ได้ ควรทำอย่างไร?

  1. กำหนด schema ของ JSON ให้ชัดในคำสั่ง และใส่ตัวอย่างหลายแบบใน <examples>
  2. prefill ให้ยาวขึ้นจนครอบคลุมทุก field
  3. ย้ายข้อความ prefill ไปไว้ท้าย user turn แทน
  4. เขียนกฎตัวใหญ่ว่า "MUST OUTPUT JSON"
ดูเฉลย

A prefill ไม่รองรับบนโมเดลรุ่นใหม่ จึงต้องคุม format ด้วยคำสั่งที่ชัดและตัวอย่าง B ยังเป็น prefill C ไม่ได้ทำหน้าที่เดียวกับการกำหนด format ส่วน D เป็นกฎเปล่าที่ได้ผลน้อยกว่าการอธิบาย format ให้ชัด

Checkpoint 6 (จับคู่)

จับคู่เทคนิคใน template กับปัญหาที่มันแก้:

  1. แยก instructions, context และ input ด้วย XML tag
  2. ห่อตัวอย่างด้วย <example>
  3. เขียนสถานการณ์ที่เจอบ่อยพร้อมคำตอบที่คาดหวัง
  4. กำหนด output ด้วย JSON, XML หรือ template
  1. ผู้ช่วยหลุดบทบาทเมื่อเจอคำถามแปลกๆ หรืออ่อนไหว
  2. คำตอบขาดบาง field ที่ระบบปลายทางต้องใช้
