7.2 Explore, plan, implement, commit: the Claude Code loop

ต้นฉบับ: CertSafari 7.2

อ่านจบแล้วควรทำได้
  • แบ่งงานใน Claude Code เป็น 4 ช่วง: explore → plan → implement → commit และอธิบายได้ว่าทำไมต้องอ่านและวางแผนก่อนลงมือแก้
  • เลือก permission mode ให้ตรงกับว่ายอมให้ Claude เปลี่ยนอะไรได้เองแค่ไหนโดยไม่ต้องถามเรา
  • เขียน prompt ที่ระบุชัดว่าไฟล์ไหน แหล่งข้อมูลไหน อาการเป็นยังไง แทนคำสั่งกว้างๆ
  • คุม session ให้สะอาดด้วยการขัดจังหวะ (interrupt), ย้อน (rewind), ล้าง context และโยนงานรีเสิร์ชให้ subagent
  • ให้ Claude มี "วิธีตรวจงานตัวเอง" ที่รันได้จริง เช่น test, screenshot หรือ build
แนวคิดหลัก: แยกการอ่านออกจากการแก้

ลูปนี้ตั้งใจแยกช่วง อ่านและคิด ออกจากช่วง แก้ไฟล์ ให้ Claude ทำความเข้าใจโค้ดก่อน เสนอแผนที่เรารีวิวได้ แล้วค่อยเขียนโค้ด รันเทสต์ และ commit ทีหลัง เหมือนช่างที่ต้องสำรวจหน้างานและให้ลูกค้าเซ็นแบบก่อน ถึงจะเริ่มทุบผนัง

1. สี่ช่วง: explore, plan, implement, commit

ปัญหาที่เจอบ่อยเวลาสั่ง Claude Code ว่า "ทำฟีเจอร์ X ให้หน่อย" ทีเดียวจบ คือมันอาจรีบแก้โค้ดก่อนเข้าใจว่าระบบเดิมทำงานยังไง ผลคือแก้ผิดที่ หรือสร้างของซ้ำกับที่มีอยู่แล้ว วิธีแก้คือแบ่งงานเป็น 4 ช่วง และ ส่ง prompt แยกกันในแต่ละช่วง

ลองนึกถึงงานเพิ่มการล็อกอินผ่าน OAuth (การให้ผู้ใช้ล็อกอินด้วยบัญชีจากผู้ให้บริการภายนอก) จะออกมาประมาณนี้:

  1. Explore ให้ Claude อ่านและอธิบายว่าระบบ auth, session และการเก็บ secret ตอนนี้ทำงานยังไง ห้ามแก้อะไร
  2. Plan ให้ระบุว่าต้องแก้ไฟล์ไหนบ้าง และ flow ของ session ใหม่จะเป็นยังไง แล้วเขียนออกมาเป็นแผน
  3. Implement ให้ทำตามแผนที่ตกลงกันแล้ว เขียนเทสต์ให้ callback handler รันชุดเทสต์ แล้วแก้จนผ่าน
  4. Commit ให้ commit พร้อมข้อความที่อธิบายชัดเจน แล้วเปิด PR

จุดที่ต้องสังเกตคือช่วง implement ต่อยอดจากแผน ที่ผ่านการรีวิวในช่วงก่อนหน้า ไม่ได้เริ่มคิดใหม่จากศูนย์ ถ้าแผนผิด เราจับได้ตั้งแต่ตอนที่ยังไม่มีโค้ดสักบรรทัดถูกแก้ ซึ่งแก้ง่ายกว่ามาก

บังคับให้ "ห้ามแก้" ด้วยโหมด ไม่ใช่ด้วยคำขอร้อง

การเขียนใน prompt ว่า "อย่าเพิ่งแก้นะ" เป็นแค่คำขอ Claude อาจยังแก้ได้อยู่ดี ถ้าต้องการการันตีว่าช่วงสำรวจและวางแผนจะไม่มีการเขียนไฟล์ ให้เปิด session ด้วย plan mode:

claude --permission-mode plan

ในโหมดนี้ Claude อ่านโค้ด ค้นหา และเสนอการเปลี่ยนแปลงได้ แต่ เขียนไฟล์ source ไม่ได้ จนกว่าเราจะอนุมัติให้ออกจาก plan mode ไปลงมือ

สรุปสั้นๆ

สี่ช่วง สี่ prompt: อ่าน → วางแผน → ทำตามแผน + เทสต์ → commit/PR และถ้าอยากให้ "ไม่แก้ไฟล์" เป็นกฎจริง ให้ใช้ --permission-mode plan ไม่ใช่แค่เขียนขอใน prompt

Checkpoint 1

หลังจาก Claude สำรวจโค้ดระบบแจ้งเตือนแล้วเสนอแผนเพิ่มช่องทาง LINE ที่ทีมรีวิวผ่าน ทีมส่ง prompt ถัดไปว่า "ลงมือทำ เขียนเทสต์ แล้วรันจนผ่าน" ช่วงนี้ Claude ควรยึดอะไรเป็นหลัก?

  1. ออกแบบโครงสร้างใหม่ทั้งหมด เพราะตอนนี้รู้จักโค้ดดีขึ้นแล้ว
  2. แผนที่ตกลงกันไว้ในช่วงก่อนหน้า
  3. ข้อความ commit ที่จะเขียนตอนจบ
  4. ผลเทสต์ชุดเดิมก่อนเริ่มงาน โดยไม่ต้องเขียนเทสต์ใหม่
ดูเฉลย

B ช่วง implement คือการทำตามแผนที่ผ่านการรีวิวแล้ว ถ้าเริ่มออกแบบใหม่ก็เท่ากับข้ามขั้นรีวิวที่เพิ่งทำไป ส่วนการเขียนเทสต์ใหม่และรันให้ผ่านเป็นส่วนหนึ่งของช่วงนี้ด้วย

Checkpoint 2

หัวหน้าทีมอยากให้ Claude วิเคราะห์ระบบ billing แล้วเสนอวิธี refactor โดย การันตี ว่าจะไม่มีไฟล์ไหนถูกแก้จนกว่าเขาจะอ่านแผน วิธีไหนตรงที่สุด?

  1. เขียนตัวใหญ่ใน prompt ว่า "ห้ามแก้ไฟล์เด็ดขาด"
  2. ข้ามช่วง explore ไปเลย เพื่อให้ Claude ไม่มีโอกาสแตะไฟล์
  3. เปิด session ด้วย claude --permission-mode plan
  4. เปิดด้วยโหมด Accept edits แล้วค่อย revert ถ้าไม่ชอบ
ดูเฉลย

C plan mode บังคับที่ระดับเครื่องมือว่าห้ามเขียนไฟล์ source คำขอใน prompt ไม่ได้บังคับอะไร การข้าม explore ก็ไม่ได้กันการแก้ และ Accept edits คือแก้ได้ทันที ตรงข้ามกับที่ต้องการ

2. เลือก permission mode ให้ตรงกับงาน

Permission mode คือตัวตั้งว่า Claude ทำอะไรได้เองโดยไม่ต้องถาม และอะไรต้องรอเรากดอนุมัติ ยิ่งไว้ใจงานมาก ก็ยิ่งปล่อยให้ทำเองได้มาก

โหมดทำเองได้เลยต้องรอเราเหมาะกับ
Manual (default, ถามทุกครั้ง)อ่านไฟล์ ค้นหาทุกการแก้ไฟล์และทุกคำสั่ง shellโค้ดที่ยังไม่ไว้ใจ เช่น รีวิว PR จากคนนอก
Accept editsแก้ไฟล์ และคำสั่งจัดการไฟล์พื้นฐาน เช่น mkdir, mvคำสั่ง shell อื่นๆงาน implement ที่ไว้ใจได้
Planสำรวจอย่างเดียว ไม่แก้ sourceการออกจาก plan mode เพื่อไปลงมือช่วง explore และ plan
Autoเกือบทุกอย่าง มี classifier ทำงานเบื้องหลังคอยบล็อกสิ่งที่เสี่ยงไม่มีเรื่องที่ทำเป็นประจำsession ยาวๆ

เรื่องที่ต้องจำเพิ่ม:

  • Permission allowlist ใช้อนุมัติล่วงหน้าเฉพาะคำสั่งที่ปลอดภัย เช่น npm run lint หรือ git commit วิธีนี้ปลอดภัยกว่าการเปลี่ยนทั้ง session ไปเป็นโหมดที่หลวมกว่า เพราะเปิดแค่ช่องที่ต้องใช้
  • bypassPermissions ข้ามการถามทุกอย่าง โหมดนี้ ไม่อยู่ในรอบการกด Shift+Tab ปกติ จะเลือกได้ก็ต่อเมื่อเปิด Claude Code ด้วย flag --allow-dangerously-skip-permissions
  • ใน Claude Code เวอร์ชันใหม่ๆ Auto เป็นโหมดเริ่มต้น ของ session แบบ interactive โดย classifier จะบล็อกการกระทำเสี่ยงแทนการถามเรา
เข้าใจผิดบ่อย

"Accept edits ยังถามก่อนแก้ไฟล์ทุกครั้ง" ไม่ใช่ Accept edits แก้ไฟล์ (และคำสั่งจัดการไฟล์พื้นฐาน) ได้เลยโดยไม่ถาม โหมดที่ถามก่อนทุกการแก้ไฟล์และทุกคำสั่งคือ Manual

"Accept edits อนุมัติทุกคำสั่ง shell ด้วย" ก็ไม่ใช่ คำสั่งอย่าง npm install ยังต้องรอเรากดอนุมัติ เพราะไม่ใช่การแก้ไฟล์หรือคำสั่งจัดการไฟล์พื้นฐาน

สรุปสั้นๆ

ไม่ไว้ใจ → Manual · อ่านและวางแผน → Plan · ลงมือกับงานที่ไว้ใจ → Accept edits · session ยาว → Auto · อยากปลดล็อกแค่บางคำสั่ง → allowlist ส่วน bypassPermissions ต้องเปิดด้วย flag พิเศษเท่านั้น

ลองเดาก่อน

Claude อยู่ในโหมด Accept edits กำลังเพิ่มฟีเจอร์ใหม่ แล้วต้องติดตั้งแพ็กเกจด้วย pnpm add dayjs จะเกิดอะไรขึ้น?

  1. รันทันที เพราะ Accept edits อนุมัติทุกอย่าง
  2. หยุดรอให้เรากดอนุมัติ
  3. ถูกบล็อกถาวร ไม่มีทางรันได้ในโหมดนี้
ดูเฉลย

B Accept edits ปล่อยเฉพาะการแก้ไฟล์และคำสั่งจัดการไฟล์พื้นฐาน คำสั่งติดตั้งแพ็กเกจเป็น shell command อื่น จึงยังต้องถามเรา (แต่ไม่ได้ถูกห้าม แค่ต้องอนุมัติ)

Checkpoint 3 (จับคู่)

จับคู่สถานการณ์กับ permission mode (Manual / Accept edits / Plan / Auto):

  1. อยากให้ Claude ไล่อ่านโค้ด legacy แล้วเขียนข้อเสนอ โดยยังไม่แก้อะไร
  2. ปล่อย Claude ทำ migration ยาวทั้งบ่าย ให้ตัวคัดกรองเบื้องหลังจับเรื่องเสี่ยงแทน
  3. ลองรันสคริปต์ที่ได้มาจาก repo ที่ไม่รู้จัก อยากเห็นทุกคำสั่งก่อนรัน
  4. ไว้ใจการแก้ไฟล์ของ Claude ในงานนี้ แต่อยากกดอนุมัติเองตอนมันจะติดตั้ง dependency
ดูเฉลย

1-Plan, 2-Auto, 3-Manual, 4-Accept edits Plan สำหรับสำรวจและเสนอ, Auto มี classifier สำหรับ session ยาว, Manual สำหรับของที่ไม่ไว้ใจ, Accept edits ปล่อยการแก้ไฟล์แต่ยังถามคำสั่ง shell อื่น

Checkpoint 4

ทีม security ต้องตรวจ PR ที่ contributor ภายนอกส่งมา ระหว่างให้ Claude ช่วยไล่โค้ด เขาต้องการเห็นและอนุมัติ ทุก การแก้ไฟล์และ ทุก คำสั่งก่อนเกิดขึ้น ควรใช้โหมดไหน?

  1. Auto เพราะ classifier จะบล็อกของที่อันตรายให้อยู่แล้ว
  2. Accept edits แล้วค่อยรีวิว diff ทีหลัง
  3. bypassPermissions เพื่อให้เร็วที่สุด
  4. Manual (default)
ดูเฉลย

D Manual คือโหมดเดียวที่ถามก่อนทุกการแก้ไฟล์และทุกคำสั่ง Auto ให้ classifier ตัดสินแทนเรา Accept edits แก้ไฟล์ไปก่อนเลย และ bypassPermissions ข้ามการถามทั้งหมด

3. ชี้ Claude ไปที่ context ที่แม่นยำ

Prompt กว้างๆ ทำให้ Claude ต้องเดาว่าเราหมายถึงอะไร วิธีทำให้ prompt คมขึ้นมี 4 แบบ คือระบุ ขอบเขต, แหล่งข้อมูล, แพทเทิร์นที่มีอยู่ หรือ อาการ ให้ชัด

เทคนิคแบบกว้างแบบเจาะจงต้องบอกอะไรเพิ่ม
กำหนดขอบเขตงาน"เขียนเทสต์ให้ไฟล์นี้"ไฟล์ไหน, edge case ไหน (เช่น ตอนผู้ใช้ยังไม่ล็อกอิน), และเงื่อนไข เช่น "ไม่ใช้ mock"
ชี้ไปที่แหล่งข้อมูล"ทำไม API ของคลาสนี้ถึงแปลกๆ"ให้ไปดู git history ของคลาสนั้น แล้วสรุปว่า API เปลี่ยนมายังไง
อ้างแพทเทิร์นที่มีอยู่"เพิ่ม widget ปฏิทิน"ให้ดู widget ที่มีอยู่แล้วในหน้าแรก โดยยกไฟล์ใดไฟล์หนึ่งเป็นตัวอย่างให้ทำตาม
บอกอาการ"แก้บั๊กล็อกอิน"อาการ (เช่น ล็อกอินพังหลัง session หมดอายุ), ตำแหน่ง (โฟลเดอร์ไหน), ให้เขียนเทสต์ที่ fail เพื่อจำลองบั๊กก่อน แล้วค่อยแก้

ตัวอย่าง prompt ที่ใช้เทคนิค "บอกอาการ":

ผู้ใช้กดชำระเงินซ้ำได้ถ้ากดปุ่มเร็วๆ สองครั้ง โค้ดอยู่ใน src/checkout/
เขียนเทสต์ที่จำลองการกดซ้ำแล้ว fail ก่อน จากนั้นแก้ให้เทสต์ผ่าน

@file กับ @directory ไม่เหมือนกัน

  • @ไฟล์ เช่น @src/api/orders.ts จะดึง เนื้อหาทั้งไฟล์ เข้า context
  • @โฟลเดอร์ เช่น @src/api ได้แค่ รายชื่อไฟล์ ไม่ได้เนื้อหา ถ้าอยากให้ Claude อ่านจริง ต้องอ้างไฟล์ที่ต้องการทีละตัว

ช่องทางป้อน context อื่นๆ

  • วางหรือลาก screenshot เข้ามาในแชท
  • pipe ข้อมูล เข้า Claude โดยตรง เช่น
tail -n 200 server.log | claude -p "สรุปว่า error นี้เกิดจากอะไร"
  • ให้ URL ของเอกสาร ที่เกี่ยวข้อง
  • ให้ Claude ไปหาข้อมูลเอง ผ่าน Bash, MCP tool หรือการอ่านไฟล์
เข้าใจผิดบ่อย

"ใส่ @src/services แล้ว Claude ได้อ่านทุกไฟล์ในโฟลเดอร์นั้น" ไม่ใช่ ได้แค่รายชื่อไฟล์ ถ้าต้องการเนื้อหา ให้อ้างไฟล์เจาะจง เช่น @src/services/payment.ts

สรุปสั้นๆ

prompt ที่ดีบอก "ตรงไหน ดูจากอะไร ทำตามแบบไหน อาการคืออะไร" และจำไว้ว่า @ไฟล์ = เนื้อหา, @โฟลเดอร์ = แค่รายชื่อ

Checkpoint 5

นักพัฒนาพิมพ์ว่า "อ่าน @lib/parsers แล้วหาว่าทำไม CSV ที่มี quote ซ้อนถึงพัง" Claude จะได้อะไรจาก @lib/parsers และควรทำอะไรต่อ?

  1. ได้เนื้อหาทุกไฟล์ในโฟลเดอร์ จึงใช้ prompt นี้ได้เลย
  2. ได้เฉพาะไฟล์ที่ใหญ่ที่สุดที่พอดีกับ context
  3. ได้แค่รายชื่อไฟล์ ควรอ้างไฟล์ที่เกี่ยว เช่น @lib/parsers/csv.ts เพิ่ม
  4. ไม่ได้อะไรเลย เพราะ @ ใช้กับโฟลเดอร์ไม่ได้ ต้อง copy โค้ดมาวางเอง
ดูเฉลย

C การอ้างโฟลเดอร์ให้แค่รายชื่อไฟล์ ไม่ได้โหลดเนื้อหาและไม่มีการเลือกไฟล์ใหญ่ให้อัตโนมัติ ส่วน @ ใช้กับโฟลเดอร์ได้ แค่ผลที่ได้เป็นรายชื่อ

4. หักเลี้ยว ล้าง context และโยนงานให้ subagent

ถ้าเห็นว่า Claude เริ่มออกนอกทาง ให้แก้ทันที ยิ่งรอนาน งานที่ต้องทิ้งก็ยิ่งเยอะ เครื่องมือที่ใช้มีดังนี้:

คำสั่ง / ปุ่มทำอะไรใช้เมื่อ
Escหยุด Claude กลางคัน ยกเลิก tool call ที่กำลังรัน แต่ context ยังอยู่เห็นว่าผิดทาง อยากสั่งใหม่ทันที
พิมพ์คำแก้แล้วกด Enter (ไม่ต้องหยุด)ข้อความถูกต่อคิว Claude จะอ่านหลัง tool call ปัจจุบันเสร็จ ใน turn เดียวกันอยากเพิ่มคำแนะนำโดยไม่ขัดงานที่ทำอยู่
Esc สองครั้ง หรือ /rewindย้อนกลับไปสถานะก่อนหน้า ทั้ง บทสนทนาและโค้ดเดินผิดทางไปหลายขั้นแล้ว อยากเริ่มจากจุดเดิม
/clearล้าง context ทั้งหมดเปลี่ยนไปทำงานที่ไม่เกี่ยวกับงานเดิม (context ยาวๆ ที่ไม่เกี่ยวทำให้ประสิทธิภาพตก)
/btwตอบคำถามแทรก โดย ไม่บันทึกลงประวัติบทสนทนาถามเรื่องเล็กๆ ข้างทางโดยไม่อยากให้ context รก
/compact <คำสั่ง>สรุป session ให้สั้นลง โดยเน้นตามที่เราบอกsession ยาวแต่ยังอยากทำงานเดิมต่อ

ตัวอย่าง: /compact เก็บรายละเอียดการเปลี่ยน schema ของตาราง orders ไว้ สรุปที่ได้จะรักษาเรื่องนั้นไว้เป็นหลัก

โยนงานรีเสิร์ชให้ subagent

การอ่านไฟล์เยอะๆ เพื่อหาคำตอบทำให้ context ของ session หลักบวม วิธีเลี่ยงคือสั่งประมาณว่า "ใช้ subagent ไปสืบว่า…" subagent จะอ่านไฟล์ใน context ของมันเอง แล้วส่งกลับมาแค่ ข้อสรุป เหมือนส่งเด็กฝึกงานไปค้นเอกสารในห้องเก็บของ แล้วกลับมารายงานแค่สิ่งที่เจอ

Subagent นิยามเป็นไฟล์ที่มี frontmatter 4 field คือ name, description, tools, model แล้วตามด้วยคำสั่งการทำงาน ตัวอย่าง:

---
name: perf-investigator
description: ไล่หาจุดที่ทำให้ระบบช้า โดยไม่แก้โค้ด
tools: Read, Grep, Glob, Bash
model: sonnet
---
คุณคือวิศวกร performance ไล่หา query ที่ไม่มี index,
loop ที่เรียก API ซ้ำ และการโหลดข้อมูลเกินจำเป็น
รายงานพร้อมเลขบรรทัดและข้อเสนอวิธีแก้

field tools คือรายชื่อ tool เท่านั้น ที่ subagent ตัวนี้ใช้ได้ ถ้าไม่ใส่ Edit/Write ไว้ มันก็แก้ไฟล์ไม่ได้

สรุปสั้นๆ

Esc = หยุดแต่จำไว้ · Esc Esc หรือ /rewind = ย้อนทั้งแชทและโค้ด · /clear = เริ่มงานใหม่ · /btw = ถามแทรกไม่บันทึก · /compact = ย่อแบบมีโฟกัส · subagent = ไปอ่านแทน ส่งกลับแค่ข้อสรุป

Checkpoint 7

Claude กำลังรัน refactor อยู่ คุณเห็นว่ามันเริ่มแก้ไฟล์ผิดโมดูล แต่ context ที่คุยกันมาทั้งหมดยังมีประโยชน์ อยากหยุดทันทีแล้วสั่งใหม่ ควรทำอะไร?

  1. กด Esc ครั้งเดียว แล้วพิมพ์คำสั่งที่ถูก
  2. พิมพ์ /clear
  3. พิมพ์ /btw ตามด้วยคำแก้
  4. ปิด terminal แล้วเปิด session ใหม่
ดูเฉลย

A Esc หยุด tool call ที่กำลังรันโดยเก็บ context ไว้ /clear กับการเปิด session ใหม่ทิ้ง context ที่ยังมีประโยชน์ ส่วน /btw เป็นคำถามแทรกที่ไม่เข้าประวัติ ไม่ได้ใช้หักเลี้ยวงาน (ถ้าอยากย้อนโค้ดที่แก้ผิดไปแล้วด้วย ให้ใช้ Esc สองครั้งหรือ /rewind)

5. ให้ Claude มีวิธีตรวจงานตัวเอง

ถ้าเราไม่ให้เกณฑ์ว่า "เสร็จ" หมายถึงอะไร คนที่ต้องมานั่งตรวจก็คือเรา ทางที่ดีกว่าคือให้ เกณฑ์ความสำเร็จที่จับต้องได้ เช่น:

  • ตัวอย่าง input พร้อม output ที่คาดหวัง
  • เทสต์ที่ตอนนี้ fail อยู่ และต้องทำให้ผ่าน
  • screenshot ของหน้าตาที่ต้องการ ให้เทียบกับผลจริง
  • ข้อความ error จริง ไม่ใช่คำบรรยายว่า "มันพัง"

ตัวอย่าง prompt ที่ให้ทั้งงานและวิธีตรวจในข้อความเดียว:

เขียนฟังก์ชัน isValidThaiPhone แล้วทดสอบกับ:
  "0812345678"  → true
  "081-234-5678" → true
  "12345"       → false
รันเทสต์ ถ้าไม่ผ่านให้แก้จนผ่านทั้งหมด

4 วิธีผูกการตรวจเข้ากับงาน

เลือกตาม 2 คำถาม: การตรวจนี้ต้องอยู่ นานแค่ไหน และต้อง แน่นหนาแค่ไหน

วิธีทำงานยังไงเหมาะกับ
ใน prompt เดียวบอกให้รันการตรวจและแก้วนจนผ่าน ภายในข้อความนั้นงานชิ้นเดียวจบ เช่น ฟังก์ชันที่มีตัวอย่าง input/output
เงื่อนไข /goalมี evaluator แยกต่างหากตรวจซ้ำหลังทุก turn ตลอดทั้ง session Claude ทำต่อจนกว่าเป้าจะสำเร็จเงื่อนไขที่ต้องจริงตลอด session
Stop hookสคริปต์รันการตรวจแล้ว บล็อกไม่ให้ turn จบ จนกว่าจะผ่าน เป็นด่านแบบ deterministic (ผลแน่นอน ไม่ขึ้นกับการตีความของโมเดล)กฎที่ต้องบังคับด้วยสคริปต์ ห้ามหลุด
Verification subagentโมเดลตัวใหม่ที่ไม่ได้ทำงานชิ้นนั้น พยายามหาข้อโต้แย้งว่าผลลัพธ์ผิดงานที่ไม่ควรให้คนทำเป็นคนให้คะแนนตัวเอง
ลองใช้กับงานตัวเอง

นึกถึงการเปลี่ยนแปลงล่าสุดที่คุณให้ AI ช่วยทำ มีเทสต์ build หรือการเทียบ screenshot อะไรบ้างที่มันน่าจะรันเองได้ เพื่อที่คุณจะได้ไม่ต้องมานั่งตรวจเองทีหลัง

สรุปสั้นๆ

ให้เกณฑ์ที่รันได้เสมอ แล้วเลือกวิธีผูก: งานเดียว → prompt เดียว · ทั้ง session → /goal · ต้องบังคับแน่นอน → Stop hook · ไม่อยากให้ตรวจงานตัวเอง → verification subagent

Checkpoint 8 (จับคู่)

จับคู่สถานการณ์กับวิธีผูกการตรวจ (A: ใน prompt เดียว, B: /goal, C: Stop hook, D: verification subagent):

  1. อยากได้ฟังก์ชันแปลงวันที่ พร้อมตัวอย่าง 3 คู่ input/output ในข้อความเดียว
  2. ทั้ง session นี้ coverage ต้องไม่ต่ำกว่าเดิม ให้มีตัวตรวจซ้ำหลังทุก turn
  3. ทีมกำหนดว่า turn จะจบไม่ได้ถ้า make lint ยัง fail และต้องบังคับด้วยสคริปต์ ไม่ใช่ขึ้นกับโมเดล
  4. รายงานวิเคราะห์ความเสี่ยงที่ agent เขียน ไม่ควรให้ agent ตัวเดิมเป็นคนตัดสินว่าถูก
ดูเฉลย

1-A, 2-B, 3-C, 4-D งานจบในข้อความเดียวใช้ prompt, เงื่อนไขทั้ง session ใช้ /goal, ด่านที่ต้องแน่นอนใช้ Stop hook, งานที่ผู้ทำไม่ควรตรวจเองใช้ verification subagent
