3.7 Choosing between MCP, direct tools and agent-to-agent integration

ต้นฉบับ: CertSafari 3.7

อ่านจบแล้วควรทำได้
  • เลือกได้ว่าจะต่อ Claude เข้ากับระบบหนึ่งด้วย direct tool, MCP server หรือ agent อีกตัว
  • อธิบายสิ่งที่ MCP ทำให้เป็นมาตรฐาน: primitive 3 แบบ, transport 2 แบบ และหน้าที่ของ server แบบ remote
  • ต่อ MCP server ใน Claude Code ได้ทั้งแบบ remote, local และ JSON config และรู้จุดที่มักพัง
  • เลือก surface ที่เหมาะ: Claude Code CLI, Agent SDK, Client SDK หรือ Managed Agents
  • ตั้งค่า MCP connector ใน Messages API ได้ และรู้ข้อจำกัดของมัน
แนวคิดหลัก: ส่งต่อ "การกระทำ" หรือส่งต่อ "การคิด"

Direct tool กับ MCP server ต่างกันที่ ใครใช้ซ้ำได้: tool ของแอปเดียว หรือ integration ที่หลาย client แชร์กัน แต่ทั้งคู่ยังเป็นแค่ "มือ" ที่ Claude สั่งให้ทำ ส่วนการส่งงานให้ agent อีกตัว คือส่ง "หัว" ไปด้วย ตัวรับมี prompt, tool และวิจารณญาณของตัวเอง

1. สามทางในการต่อ Claude เข้ากับระบบ

กลไกใครถืออะไรเหมาะเมื่อ
Direct toolแอปของเรานิยาม tool และ schema เอง รันทุก call เอง แล้วส่งผลกลับแอปเดียวเป็นเจ้าของระบบนั้น client อื่นไม่ต้องใช้
MCP serverintegration อยู่หลัง protocol กลาง client ไหนก็ต่อได้หลาย client ต้องใช้ร่วมกัน หรือ vendor มี server ให้อยู่แล้ว
Agent อีกตัวตัวรับมี prompt, tool, MCP server และ skills ของตัวเองระบบนั้นต้องใช้การคิดวิเคราะห์ของตัวเอง ไม่ใช่แค่เรียก API

เปรียบเทียบง่ายๆ direct tool คือเครื่องมือที่ซื้อมาใช้ในบ้านตัวเอง MCP server คือปลั๊กไฟมาตรฐานที่เสียบเครื่องใช้ไฟฟ้ายี่ห้อไหนก็ได้ ส่วน agent อีกตัวคือการจ้างช่างผู้เชี่ยวชาญมาทำงานทั้งก้อน

เรื่องสำคัญของการส่งงานให้ agent ใน Managed Agents: การ delegate ลึกได้ชั้นเดียว subagent แต่ละตัวทำงานใน session thread ของตัวเอง แล้วส่งรายงานกลับให้ตัวหลัก (lead)

เข้าใจผิดบ่อย

"Specialist agent ส่งต่องานให้ agent อีกตัวได้อีกทอด" ไม่ได้ ใน Managed Agents การ delegate ลึกชั้นเดียว lead ส่งให้ specialist ได้ แต่ specialist ส่งต่อไม่ได้

สรุปสั้นๆ

แอปเดียวใช้ = direct tool, หลาย client ใช้ร่วม = MCP server, ต้องการวิจารณญาณแยก = agent อีกตัว (delegate ได้ชั้นเดียว)

Checkpoint 1 (จับคู่)

จับคู่ความต้องการกับกลไก (direct tool / MCP server / agent อีกตัว):

  1. แอปจองห้องประชุมภายในบริษัท ทีมเดียวดูแลทั้งแอปและ schema ไม่มี client อื่นใช้
  2. ระบบ ticketing ของ vendor ที่มี server สำเร็จรูปอยู่แล้ว และต้องใช้ทั้งจากแอป production และจาก Claude Code ของนักพัฒนา
  3. งานตรวจสอบ compliance ของสัญญา ที่ต้องมี prompt เฉพาะ ชุด tool เฉพาะ และต้องใช้ดุลพินิจหลายขั้น
ดูเฉลย

1-direct tool, 2-MCP server, 3-agent อีกตัว เจ้าของเดียวไม่ต้องใช้ protocol กลาง, หลาย client + มี server จาก vendor คือจุดแข็งของ MCP, ส่วนงานที่ต้องคิดเองต้องส่งให้ agent

2. MCP ทำอะไรให้เป็นมาตรฐาน

Primitive 3 แบบ แยกกันด้วยว่า ใครเป็นคนคุม:

  • Tools: model-controlled โมเดลเลือกเองว่าจะเรียกเมื่อไหร่
  • Resources: application-controlled แอปเป็นคนเลือกว่าจะเอาข้อมูลไหนใส่ context
  • Prompts: user-controlled ผู้ใช้เลือกเอง เช่นเลือกจากเมนู slash command

Transport 2 แบบ:

  • stdio: client รัน server เป็น subprocess แล้วคุยกันด้วย JSON-RPC ที่คั่นด้วย newline ผ่าน stdin/stdout ส่วน log ต้องไปที่ stderr (ถ้าเขียน log ลง stdout จะปนกับข้อความ protocol)
  • Streamable HTTP: client ส่ง JSON-RPC ด้วย POST ไปที่ endpoint ระยะไกล server ตอบเป็น JSON หรือ SSE stream และ client อาจเปิด GET stream ค้างไว้รับข้อความจาก server

หน้าที่ของ server เมื่อเปิดเป็น remote: ต้องตรวจ header Origin, server ที่รันในเครื่องควร bind แค่ localhost และต้อง authenticate การเชื่อมต่อ ดังนั้นการเปลี่ยน stdio server ที่รันในเครื่องให้กลายเป็น hosted service เป็น งาน deploy จริงจัง ไม่ใช่แค่สลับค่า config

สรุปสั้นๆ

Tools/Resources/Prompts = โมเดล/แอป/ผู้ใช้คุม stdio = subprocess ในเครื่อง, Streamable HTTP = remote ที่ต้องตรวจ Origin และ auth

Checkpoint 2

ทีมมี MCP server ตัวหนึ่งที่รันแบบ stdio บนเครื่องนักพัฒนา ตอนนี้อยากให้ทีมอื่นทั่วบริษัทเรียกผ่านเครือข่ายได้ ต้องทำอะไร?

  1. เปลี่ยน flag transport จาก stdio เป็น http ใน config ฝั่ง client ก็พอ
  2. Deploy เป็น endpoint แบบ Streamable HTTP ที่ตรวจ Origin และ authenticate การเชื่อมต่อ
  3. แชร์ไฟล์ binary ให้ทุกคนรันเองแบบ stdio
  4. เปิด port ของ stdin ให้คนอื่นต่อเข้ามา
ดูเฉลย

B การขึ้นเป็น hosted service ต้อง deploy ใหม่พร้อมหน้าที่ด้านความปลอดภัยของ remote server แค่เปลี่ยนค่าไม่พอ

Checkpoint 3

ใน config ของ Claude Code มี server ที่ตั้งไว้ว่า "command": "npx", "args": ["-y", "@acme/notion-mcp"] server นี้ใช้ transport อะไร?

  1. Streamable HTTP
  2. SSE
  3. stdio
  4. WebSocket
ดูเฉลย

C client เป็นคนสั่งรันโปรเซส (npx) ในเครื่อง แล้วคุยผ่าน stdin/stdout นั่นคือ stdio

3. ต่อ MCP server ใน Claude Code

# remote (Streamable HTTP) พร้อม bearer token
claude mcp add --transport http billing https://mcp.example.com/mcp \
  --header "Authorization: Bearer $TOKEN"

# local stdio: ทุกอย่างหลัง -- คือคำสั่งที่ใช้รัน server
claude mcp add --env API_KEY=xyz files -- npx -y @acme/files-mcp

# จาก JSON
claude mcp add-json billing '{"type":"http","url":"https://mcp.example.com/mcp"}'
  • Remote: claude mcp add --transport http <name> <url> ใส่ --header ได้ถ้าต้องส่ง token
  • Local: claude mcp add [options] <name> -- <command> [args...] ทุกอย่างหลัง -- คือคำสั่งรัน server ไม่ใช่ option ของ claude
  • JSON config: claude mcp add-json รับ block แบบ mcpServers จุดพังคลาสสิก: entry ที่มี url แต่ ไม่ใส่ type (http, sse หรือ ws) จะถูกอ่านเป็น stdio แล้วล้ม
  • Lifecycle: พอปิด session, stdio server ที่ session รันไว้จะถูกปิดตามลำดับสัญญาณ SIGINT → SIGTERM → SIGKILL
  • ดูสถานะ: claude mcp list, claude mcp get <name> และ /mcp ในเซสชัน
  • Server ระดับโปรเจกต์จาก .mcp.json จะค้างสถานะ pending จนกว่าจะมีคนกดอนุมัติแบบ interactive ส่วนในโหมด claude -p (headless) จะต่อเฉพาะ server ที่ส่งผ่าน command line
เข้าใจผิดบ่อย

"ใส่แค่ url ใน JSON ก็พอ Claude Code รู้เองว่าเป็น HTTP" ไม่ใช่ ถ้าไม่ใส่ type จะถูกตีความเป็น stdio แล้วต่อไม่ติด

สรุปสั้นๆ

Remote ใช้ --transport http, local ใช้ -- คั่นคำสั่ง, JSON ต้องมี type เสมอเมื่อมี url และ .mcp.json ต้องอนุมัติก่อนถึงจะต่อ

4. เลือก surface ให้ตรงงาน

Surfaceเหมาะเมื่อ
Claude Code CLIมีคนนั่งทำงานแบบ interactive และคอยอนุมัติขั้นที่เสี่ยง
Agent SDKสคริปต์ต้องการ agent loop, built-in tools และระบบ permission สำเร็จรูป โดยไม่ต้องเขียนส่วนจัดการ tool เอง
Client SDKอยากคุมทุก request และทุก tool result เอง หรือใช้ beta tool runner
Managed Agentsให้ Anthropic host agent loop ให้ ตั้งค่าผ่าน Claude API
  • ใน Client SDK เมื่อ response มี tool_use โค้ดของเรา ต้องรัน tool เองแล้วส่ง tool_result กลับ จะเขียนลูปเองหรือใช้ beta tool runner ก็ได้ SDK ไม่ได้ทำ agent loop ให้
  • ใน Agent SDK ใส่การเชื่อมต่อผ่าน option mcpServers ชื่อ tool จะอยู่ในรูป mcp__<server>__<tool> และ allowedTools ใช้ชื่อแบบนี้จับคู่
  • สำหรับ CI ที่ไม่มีคนเฝ้า ใช้ headless claude -p คู่กับ --allowedTools เพื่ออนุมัติ tool ไว้ล่วงหน้า
options = ClaudeAgentOptions(
    mcp_servers={"jira": {"type": "http", "url": "https://mcp.example.com/jira"}},
    allowed_tools=["mcp__jira__search_issues", "Read", "Edit", "Bash"],
)
เข้าใจผิดบ่อย

"Client SDK ก็มี agent loop ให้เหมือน Agent SDK" ไม่ใช่ Client SDK คืน tool_use มาให้เราจัดการเอง ตัวที่มี loop สำเร็จรูปคือ Agent SDK

สรุปสั้นๆ

มีคนเฝ้า = CLI, สคริปต์อัตโนมัติที่อยากได้ loop สำเร็จรูป = Agent SDK, อยากคุมเองทุกจังหวะ = Client SDK, อยากให้ Anthropic host = Managed Agents

Checkpoint 4

คุณเรียก Messages API ผ่าน Client SDK ส่ง tool lookup_stock ไปด้วย แล้ว response กลับมาเป็น block tool_use ที่ขอเรียก lookup_stock ขั้นต่อไปคืออะไร?

  1. รอ เดี๋ยว API จะรัน tool แล้วส่งคำตอบสุดท้ายมาเอง
  2. โค้ดของคุณรัน lookup_stock แล้วส่ง tool_result กลับใน request ถัดไป (ลูปเองหรือใช้ beta tool runner)
  3. เปลี่ยนเป็น MCP server ก่อนถึงจะรันได้
  4. ส่ง request เดิมซ้ำพร้อม tool_choice: none
ดูเฉลย

B direct tool ฝั่ง client เป็นหน้าที่ของแอปเราที่จะรันและส่งผลกลับ

Checkpoint 5

ทีมต้องการงาน nightly บน CI ที่ให้ Claude แก้โค้ดและรันเทสต์วนไปจนเทสต์ผ่าน ไม่มีคนเฝ้า และไม่อยากเขียน tool handler เอง ควรใช้อะไร?

  1. Agent SDK
  2. Client SDK เขียนลูปเอง
  3. Claude Code CLI แบบ interactive
  4. MCP server อย่างเดียว
ดูเฉลย

A Agent SDK มี loop, built-in tools และ permission ให้ B ต้องเขียนเอง C ต้องมีคนนั่งอนุมัติ D เป็นแค่ช่องทางเชื่อมต่อ ไม่มี agent loop ในเครื่อง

Checkpoint 6

นักพัฒนากำลังไล่บั๊กใน service ที่รันอยู่ อยากให้ Claude ช่วยอ่าน log และลองแก้ แต่ต้องการกดอนุมัติเองก่อนทุกคำสั่งที่แตะ production ใช้อะไรดี?

  1. Claude Code CLI
  2. Managed Agents
  3. Headless claude -p พร้อม --allowedTools ครอบทุก tool
  4. Client SDK แบบ batch
ดูเฉลย

A งาน interactive ที่มีคนคอยอนุมัติขั้นเสี่ยงคือจุดแข็งของ CLI ส่วน C อนุมัติทุกอย่างล่วงหน้า ตรงข้ามกับที่ต้องการ

5. MCP connector ใน Messages API

Messages API มี MCP connector ให้ Claude เรียก tool บน MCP server ได้โดยไม่ต้องเขียน client เอง แต่มีข้อจำกัดชัดเจน:

  • ต่อได้เฉพาะ remote server (Streamable HTTP หรือ SSE ที่ URL แบบ https://) stdio server ต่อตรงไม่ได้ เพราะ API ไม่มีทางไปรัน subprocess บนเครื่องเรา
  • รองรับแค่ส่วน tool call ของ MCP ใช้ resources กับ prompts ไม่ได้
  • config แยกเป็นสองที่: mcp_servers เก็บรายละเอียดการเชื่อมต่อ (type: "url", url, name และ authorization_token ถ้ามี) ส่วน tools ใส่ mcp_toolset ที่อ้าง server ด้วยชื่อ
  • server แต่ละตัวต้องถูกอ้างด้วย toolset ตัวเดียวพอดี และ toolset เป็นตัวกำหนดว่าเปิด tool ไหนบ้าง
  • ฟีเจอร์นี้อยู่หลัง beta flag
{
  "mcp_servers": [
    {"type": "url", "url": "https://mcp.example.com/sse",
     "name": "inventory", "authorization_token": "..."}
  ],
  "tools": [
    {"type": "mcp_toolset", "mcp_server_name": "inventory"}
  ]
}
เข้าใจผิดบ่อย

"MCP connector สั่งรัน stdio server ในเครื่องได้" ไม่ได้ ต้อง deploy เป็น remote HTTPS ก่อน

"ผ่าน connector ก็อ่าน resources ของ server ได้" ไม่ได้ connector รองรับแค่ tool call

สรุปสั้นๆ

Connector = remote HTTPS เท่านั้น, tool เท่านั้น, ต่อใน mcp_servers แล้วเปิด tool ด้วย mcp_toolset หนึ่งตัวต่อหนึ่ง server

Checkpoint 7

เติมคำในช่องว่าง: ใน request ของ Messages API ที่ใช้ MCP connector, ใน array tools ต้องมี object ที่ "type" เป็น ______ เพื่ออ้างถึง server ใน mcp_servers และเลือกเปิด tool

ดูเฉลย

mcp_toolset ข้อมูลการเชื่อมต่ออยู่ใน mcp_servers ส่วนการเปิด tool อยู่ใน toolset ที่อ้างชื่อ server

Checkpoint 8

บริษัทมี MCP server ภายในที่รันแบบ stdio สำหรับค้นข้อมูลลูกค้า ตอนนี้ backend ต้องการให้ Claude ใช้ server นี้ผ่าน Messages API ทำยังไง?

  1. Deploy เป็น remote MCP server ที่ URL แบบ HTTPS แล้วใส่ไว้ใน mcp_servers
  2. ใส่ command ของ stdio ลงใน mcp_servers
  3. ใช้ connector อ่าน resources ของ server แทน
  4. เปิด .mcp.json ใน repo ของ backend
ดูเฉลย

A connector ต่อได้แค่ remote HTTPS และ .mcp.json เป็นของ Claude Code ไม่เกี่ยวกับ Messages API

6. เมื่อไหร่ "agent อีกตัว" ดีกว่า

  • ส่งงานให้ specialist agent = ส่งทั้ง วิจารณญาณและ integration ของมันไปด้วย และช่วยให้ context ของ lead ไม่รก
  • agent ใน Managed Agents session เดียวกัน แชร์ sandbox, filesystem และ credential ใน vault การส่งต่องานจึง แยกแค่ context ไม่ได้แยก permission
  • thread ของ subagent อยู่ต่อ (persist) lead ส่งคำถามตามได้ ดังนั้นถ้าการคุยกับระบบนั้นอาจต้องโต้ตอบหลายรอบ ให้เลือก agent มากกว่า MCP server
เข้าใจผิดบ่อย

"แยกเป็น subagent แล้วก็ปลอดภัย เพราะแต่ละตัวแยกกันขาด" ไม่ใช่ ใน session เดียวกัน subagent เห็น sandbox และ credential ชุดเดียวกับ lead สิ่งที่แยกคือประวัติบทสนทนาเท่านั้น ถ้าต้องการแยกสิทธิ์จริงต้องออกแบบอีกชั้น

สรุปสั้นๆ

เลือก agent เมื่องานต้องคิดเองหรือต้องคุยหลายรอบ แต่จำไว้ว่าใน session เดียวกัน isolation มีแค่เรื่อง context

Checkpoint 9

ใน Managed Agents session หนึ่ง lead ส่งงานให้ subagent "license-checker" ตรวจ license ของ dependency ข้อไหนถูกต้อง?

  1. license-checker มี session thread และประวัติของตัวเอง แต่ใช้ sandbox, filesystem และ credential ร่วมกับ lead
  2. license-checker มี sandbox แยกและ credential แยกโดยอัตโนมัติ
  3. license-checker ส่งงานย่อยต่อให้ subagent อีกตัวได้
  4. license-checker เห็นประวัติทั้งหมดของ lead
