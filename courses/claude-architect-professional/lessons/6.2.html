6.2 Communicating architecture trade-offs to stakeholders

ต้นฉบับ: CertSafari 6.2

อ่านจบแล้วควรทำได้
  • เสนอการเลือกโมเดลหรือ effort ให้ผู้บริหารที่ไม่ใช่สายเทคนิค เป็นข้อแนะนำเดียวพร้อม "ราคา" ของมัน
  • เทียบ cost per completed task แทนราคาต่อ token และแยกได้ว่าการประหยัดไหนไม่เสียคุณภาพเลย
  • บอกได้ว่าความซับซ้อนแต่ละชั้น (รวมถึง multi-agent) ซื้ออะไรและจ่ายอะไร เพื่อให้แบบเรียบง่ายเป็นค่า default
  • หนุนข้อแนะนำด้วย eval ของเราเอง ไม่ใช่ benchmark ของ vendor
  • อธิบาย residual risk แบบเจาะจง มีขอบเขต และมีมาตรการ ไม่ใช่ "ไม่มีความเสี่ยง"
  • อธิบาย context management, thinking mode และทางเลือก hosting ให้วิศวกรฟังโดยไม่ผิดทางเทคนิค
แนวคิดหลัก: trade-off ที่สื่อสารดีมี 4 ส่วน

ข้อแนะนำเดียว + ราคาที่ต้องจ่าย (cost, speed, quality หรือ risk) + หลักฐานจาก eval บน workload ของเราเอง + ขอบเขตของสิ่งที่อาจผิดพลาด ตัวเลขของ vendor บอกว่าควรทดสอบอะไร แต่ไม่ใช่หลักฐานของเรา

1. แปลง trade-off ของโมเดลเป็นข้อแนะนำภาษาคน

ทุกการตัดสินใจแลกกันระหว่าง capability, speed, cost และ risk เสมอ แต่คนฟังแต่ละกลุ่มต้องการต่างกัน: ผู้บริหาร ต้องการข้อแนะนำเดียว ราคาของมัน และเงื่อนไขที่จะทำให้เปลี่ยนใจ ส่วน วิศวกร ต้องการกลไก (รายละเอียด lineup ของโมเดลอยู่ในบท 2.1)

รูปประโยคสำหรับผู้บริหาร: โมเดลตั้งต้น + เหตุผล + เงื่อนไขที่จะเปลี่ยน เช่น

"เราเริ่มระบบคัดแยก ticket ด้วย Haiku 5.5 เพราะปริมาณสูงและอ่อนไหวเรื่องราคา
 จะขยับขึ้นรุ่นก็ต่อเมื่อ eval เจอช่องว่างด้าน capability ที่ระบุได้"

มีสองเส้นทางให้เล่า:

  • Cost-first เริ่มจากโมเดลถูก ทดสอบ แล้วอัปเกรดเฉพาะจุดที่เจอช่องว่าง
  • Capability-first สำหรับ reasoning ซับซ้อนหรืองาน agentic ที่มี autonomy สูง เริ่มที่ Opus 5.5 เพราะความแม่นสำคัญกว่าเงิน แล้วค่อยลด effort หรือลดรุ่นเมื่อ workflow นิ่ง

Effort คือปุ่มแรก

หลายโมเดลมี parameter effort ที่แลกความฉลาดกับ latency และค่าใช้จ่าย ภายในโมเดลเดิม ดังนั้นเมื่อมีคนบ่นว่าแพง คำตอบแรกควรเป็น "ลด effort แล้ววัดใหม่" ก่อน "เปลี่ยนไปโมเดลที่ถูกกว่า" เปรียบเหมือนแอร์ที่ค่าไฟแพง ลองปรับอุณหภูมิขึ้นก่อน ยังไม่ต้องรื้อเครื่องใหม่

Fast mode คือการจ่ายเงินซื้อเวลา

Fast mode บน Opus 5.5, Opus 5 และ Opus 4.8 ให้ความเร็วในการ output สูงขึ้น สูงสุด 2.5 เท่า แต่คิด ราคาพรีเมียม ให้เล่ามันว่าเป็นการจ่ายเงินเพิ่มเพื่อแลกกับ response time ไม่ใช่ทางประหยัด

ลองใช้กับงานจริง

เขียนการเลือกโมเดลครั้งที่ผ่านมาของคุณเป็นประโยคเดียว ที่บอกชื่อโมเดล เหตุผล และผลวัดแบบไหนที่จะทำให้เปลี่ยน

สรุปสั้นๆ

ผู้บริหารต้องการประโยคเดียว: โมเดล + เหตุผล + exit condition บ่นว่าแพง → ลด effort แล้ววัดใหม่ก่อนเปลี่ยนโมเดล fast mode แพงขึ้นเพื่อเร็วขึ้น

Checkpoint 1

ระบบสรุปเคสลูกค้าของบริษัทประกันรันบน Opus 5.5 คุณภาพดีจนทีมพอใจ แต่ CFO บอกว่าค่าใช้จ่ายสูงเกินไป ควรเสนออะไรเป็นอย่างแรก?

  1. ย้ายไป Haiku 5.5 ทันทีเพราะราคาต่ำสุด
  2. ลดรุ่นลงหนึ่งขั้นก่อน แล้วค่อยปรับ effort ทีหลัง
  3. ลด effort บนโมเดลเดิม แล้ววัดทั้งค่าใช้จ่ายและคุณภาพใหม่
  4. เปิด fast mode ให้งานจบเร็วขึ้นจะได้ถูกลง
ดูเฉลย

C effort คือคันโยกแรก A ข้ามการวัดและเสี่ยงเสียคุณภาพ B สลับลำดับ D fast mode แพงขึ้น ไม่ใช่ถูกลง

2. ทำไมราคาต่อ token หลอกตา และการประหยัดแบบไหน "ฟรี"

stakeholder ชอบเอาตารางราคามาเทียบกัน แต่ตัวเลขที่ถูกคือ cost per completed task (ต้นทุนต่องานที่เสร็จจริง) โมเดลที่ถูกกว่าต่อ token แต่ต้องคุยหลายรอบกว่า คิดนานกว่า หรือต้อง retry บ่อยกว่า อาจแพงกว่าต่อ ticket ที่ปิดได้ ในทางกลับกัน โมเดลที่เก่งกว่ามักใช้ turn และ thinking น้อยกว่า ต้นทุนต่องานจึงอาจต่ำกว่า โดยเฉพาะเมื่อใช้ effort ต่ำ

เหมือนจ้างช่างสองคน คนหนึ่งค่าแรงต่อชั่วโมงถูกกว่าแต่ใช้เวลาสามวันและต้องมาแก้ซ้ำ อีกคนแพงกว่าต่อชั่วโมงแต่จบในวันเดียว ที่ต้องเทียบคือค่าซ่อมทั้งงาน

การประหยัดแบ่งเป็นสองประเภท และต้องเล่าต่างกัน:

  • Free wins ลดเงินโดยไม่แตะคุณภาพ เล่าเป็นงานที่ "ทำอยู่แล้ว"
  • Trade-offs แลกคุณภาพหรือ capability กับเงิน ต้องบอกราคาด้านคุณภาพไว้ข้างๆ ตัวเลขที่ประหยัดได้
คันโยกเสียคุณภาพไหมเล่ายังไง
Prompt caching และตัด token ที่ไม่จำเป็นไม่ทำอยู่แล้ว ประหยัดล้วนๆ
Batch processing (ถูกลงราว 50%)ไม่ แต่ผลอาจใช้เวลาถึง 24 ชั่วโมงเหมาะกับงานที่รอได้หนึ่งวัน ไม่ใช่ผู้ใช้ live
Workspace spend limitsไม่เพดานงบรายเดือน ไม่ได้เปลี่ยนคุณภาพ
ลด effortอาจเสียถูกและเร็วขึ้น ถ้าคุณภาพตกก็คืนค่า effort
effort ต่ำ + รันซ้ำด้วย effort สูงเฉพาะงานที่ failpass rate เท่าเดิมในการทดสอบของ Anthropicถูกลงราว 40% ถ้าตรวจ output อัตโนมัติได้ (ต้องมี verifier)
บอกโมเดลว่าใช้เวลาไปเท่าไรแล้วเสียคะแนนไม่กี่จุดagent จบเร็วขึ้น แลกกับต้นทุนคุณภาพเล็กน้อยที่วัดได้
ใช้โมเดลเล็กลงอาจเสียทำเฉพาะเมื่อ eval ยืนยันว่ายังผ่านเกณฑ์
เข้าใจผิดบ่อย

"โมเดลที่ราคาต่อ token ต่ำสุดคือตัวเลือกที่ถูกที่สุด" ผิด ต้องเทียบ cost per completed task บน workload จริง

สรุปสั้นๆ

เทียบต้นทุนต่องานที่เสร็จ ไม่ใช่ต่อ token caching, ตัด token, spend limit, batch (สำหรับงานรอได้) คือ free wins ส่วนลด effort/โมเดลเล็ก/บอกเวลา คือ trade-off ต้องบอกราคาด้านคุณภาพด้วย

Checkpoint 2

ฝ่ายจัดซื้อเห็นว่ามีโมเดลอีกตัวที่ราคาต่อ token ถูกกว่าตัวที่ใช้อยู่เกือบครึ่ง และขอให้เปลี่ยนเลย ควรตอบยังไง?

  1. เปลี่ยนได้เลย ราคาต่อ token คือข้อมูลที่ต้องรู้ทั้งหมดแล้ว
  2. คูณราคาต่อ token กับปริมาณ request ต่อเดือนของทั้งสองตัวแล้วเลือกตัวที่ต่ำกว่า
  3. วัด cost per completed task ของทั้งสองโมเดลบน workload จริงของเราก่อนตัดสิน
  4. เทียบค่าพรีเมียมของ fast mode ระหว่างสองโมเดล
ดูเฉลย

C ต้นทุนจริงขึ้นกับจำนวน turn, thinking และ retry A และ B ยังมองแค่ราคาต่อ token (B แค่คูณปริมาณ แต่ไม่สนอัตราที่งานเสร็จ) D ไม่ใช่ตัวเปรียบเทียบที่เกี่ยวข้อง

3. ติดราคาให้ความซับซ้อนทุกชั้น

ทักษะที่ต้องการคือทำให้ราคาของแต่ละชั้นมองเห็นได้ เพื่อให้ stakeholder เลือกแบบเรียบง่ายเป็นค่า default ระบบ agentic มักแลก latency และเงินกับผลงานที่ดีขึ้น capability ที่เพิ่มเป็นของจริง บิลก็เป็นของจริงเหมือนกัน

ชั้นได้อะไรจ่ายอะไร
LLM call เดียว + retrieval + in-context examplesพอสำหรับแอปจำนวนมากถูกที่สุดทั้งรันและ debug
Workflow (เส้นทางในโค้ดกำหนดไว้ก่อน)คาดเดาได้สำหรับงานที่นิยามชัดยืดหยุ่นน้อยลง
Agent (เลือกขั้นตอนและ tool เอง)ยืดหยุ่นlatency, ค่าใช้จ่าย, พฤติกรรมคาดเดายากขึ้น
Framework ครอบอีกชั้นเขียนเร็วขึ้นอาจซ่อน prompt และ response ทำให้ debug ยาก

Multi-agent ซื้อความครอบคลุม ไม่ใช่ความเร็ว

ลองนึกก่อน: product owner ขอ research agent หลายตัวรันขนาน "จะได้เร็วขึ้น" จริงไหม?

  • agent ขนานสำรวจพื้นที่ได้กว้างกว่า agent ตัวเดียวที่ติดข้อจำกัด context window
  • ใช้ token ราว 3 ถึง 10 เท่า สำหรับงานเทียบเท่า เพราะ context ถูกทำซ้ำ และการประสานงานเพิ่ม message
  • เวลารวมมัก นานกว่า agent ตัวเดียว เพราะงานคำนวณรวมเพิ่มขึ้น
  • agent ทุกตัวที่เพิ่ม = จุดพังเพิ่ม, ชุด prompt ที่ต้องดูแลเพิ่ม, แหล่งเซอร์ไพรส์เพิ่ม
  • มีทีมที่ใช้เวลาหลายเดือนสร้าง multi-agent แล้วพบว่า prompt ที่ดีขึ้นของ agent ตัวเดียวให้ผลเท่ากัน

Multi-model: เกมต้นทุน ไม่ใช่เกมความกว้าง

อีกรูปแบบที่ต่างจาก multi-agent คือ จับคู่โมเดลถูกกับโมเดล frontier เพื่อให้ token ส่วนใหญ่คิดราคาถูก มีสองแบบ:

  • Executor + advisor โมเดลถูกทำงานหลัก แล้ว escalate การตัดสินใจยากไปหาโมเดล advisor
  • Orchestrator + workers orchestrator ส่งงานจำนวนมากให้ worker ราคาถูก

ใส่ไว้ในข้อเสนอก็ต่อเมื่อวัดแล้วคุ้มเท่านั้น

เข้าใจผิดบ่อย

"agent ขนานให้ผลเร็วกว่า" ผิด มันให้ความครอบคลุม แลกกับ token ที่มากขึ้นและเวลารวมที่มักนานขึ้น

สรุปสั้นๆ

แต่ละขั้นของบันได (call เดียว → workflow → agent → framework) มีราคา ทำให้มองเห็นเพื่อให้แบบง่ายเป็น default multi-agent = ครอบคลุม แพงกว่า 3-10 เท่า multi-model = เกมต้นทุนที่ต้องพิสูจน์ด้วยการวัด

Checkpoint 3 (จับคู่)

คุณกำลังอธิบายบันไดความซับซ้อนให้คณะกรรมการ จับคู่ชั้นกับคำอธิบาย (A–D)

  1. LLM call เดียวพร้อม retrieval และตัวอย่าง
  2. Workflow
  3. Agent
  4. Framework ครอบอีกชั้น

A: อาจซ่อน prompt/response ทำให้หาสาเหตุความผิดพลาดยาก · B: ยืดหยุ่น แลกกับ latency ค่าใช้จ่าย และความคาดเดาได้ · C: พอสำหรับหลายแอป ถูกที่สุดในการรันและ debug · D: เส้นทางกำหนดในโค้ด คาดเดาได้สำหรับงานที่นิยามชัด

ดูเฉลย

1-C, 2-D, 3-B, 4-A

4. หนุนข้อแนะนำด้วย eval ของเราเอง

ตัวเลขจาก vendor เป็นหลักฐานที่อ่อนที่สุด Anthropic เองก็บอกว่าการวัดด้านต้นทุนและคุณภาพของตัวเองเป็นข้อมูลภายในและเป็นแค่ ทิศทาง ไม่ใช่คำรับประกัน ตัวอย่าง: มีผลจาก vendor ว่าชุด Sonnet 5 ที่มี Fable 5 เป็น advisor ได้คะแนนห่างจาก Fable 5 ไม่เกิน 10% บน SWE-bench Pro ด้วยราคา 63% ตัวเลขแบบนี้เป็นเหตุผลให้ ทดสอบ pattern นี้ ไม่ใช่เหตุผลให้ ใช้ เลย

ทำไม benchmark สาธารณะใช้ไม่ได้ที่ระดับบนสุด: โมเดลแรงๆ อย่าง Opus หรือ Fable ทำข้อสอบได้เกือบหมด benchmark จึง saturate และแยกโมเดลออกจากกันไม่ได้ ส่วน custom eval ไม่ saturate เพราะใช้โจทย์จาก production ที่คัดมา รวมเคสที่เครื่องมือปัจจุบันยังทำไม่ได้ และให้คะแนนตามเกณฑ์ที่ทีมตั้งเอง

วิธี 4 ขั้น

  1. สร้าง benchmark test เฉพาะ use case ของเรา
  2. รันด้วย prompt และข้อมูลจริง
  3. เทียบโมเดลที่เป็นตัวเลือกด้าน accuracy, คุณภาพ response และการรับมือ edge case
  4. ชั่งผลงานกับ cost per completed task

ขั้นที่สำคัญที่สุดคือ evaluation set เพราะทุกขั้นที่เหลือพึ่งมัน เวลานำเสนอ ให้ผล eval เป็นเหตุผลของการตัดสินใจ โมเดลเล็กที่ผ่านเกณฑ์ชนะทั้งเรื่องราคาและความเร็ว การขยับขึ้น tier ก็ต้องมี eval รองรับเหมือนกัน เช่น ถ้า Opus ยังติดขัดบางงานใน eval ขั้นต่อไปคือ Fable

eval ยังใช้ วินิจฉัย ได้ด้วย: รันแบบ head-to-head บน harness เดียวกัน จะแยกได้ว่าปัญหามาจากโมเดลหรือจาก setup ของเรา

ลองนึกก่อน: CFO ถามว่าทำไมต้องใช้ Opus แทน Sonnet สำหรับตรวจสัญญา หลักฐานที่ควรเอาไปคือผลของ ทั้งสองโมเดลบนชุดสัญญาของเราเอง ให้คะแนนตามเกณฑ์ของเรา

เข้าใจผิดบ่อย

"ตัวเลขที่ Anthropic เผยแพร่เพียงพอจะยืนยันการเลือกโมเดลสำหรับ workload ของเรา" ผิด มันบอกว่าควรทดสอบอะไร ไม่ใช่หลักฐานแทน eval ของเรา

สรุปสั้นๆ

vendor benchmark = ทิศทาง และ saturate ที่ระดับบน หลักฐานจริงมาจาก custom eval: สร้าง test → รันด้วยข้อมูลจริง → เทียบ → ชั่งกับต้นทุนต่องาน

Checkpoint 4 (เรียงลำดับ)

คุณต้องเตรียมหลักฐานว่าควรใช้โมเดลไหนในระบบตอบคำถามภาษีของสำนักงานบัญชี เรียงขั้นตอนให้ถูก:

  1. ชั่งผลงานของแต่ละโมเดลกับต้นทุนต่อคำถามที่ตอบเสร็จ
  2. รันชุดทดสอบด้วย prompt และคำถามจริงจากลูกค้า
  3. สร้างชุดทดสอบเฉพาะงานตอบคำถามภาษี
  4. เทียบโมเดลด้านความถูกต้อง คุณภาพคำตอบ และ edge case
ดูเฉลย

3 → 2 → 4 → 1 รัน test ที่ยังไม่มีไม่ได้ และต้นทุนต้องชั่งกับคุณภาพที่วัดแล้วเป็นขั้นสุดท้าย

5. ทำให้ residual risk อ่านออกและมีขอบเขต

"ไม่มีความเสี่ยง" เป็นประโยคที่ใช้ไม่ได้เลย เพราะไม่จริงสำหรับระบบ LLM และไม่ให้อะไรผู้อนุมัติตรวจสอบ risk statement ที่ดีต้อง ระบุความล้มเหลวที่เจาะจง, กำหนดขอบเขตความรุนแรง และ บอกว่าจะตรวจพบได้ยังไง ผู้อนุมัติยอมรับความเสี่ยงที่มองเห็นขอบได้ แต่ยอมรับสิ่งที่ไม่รู้ไม่ได้

4 คำถามสำหรับตีกรอบความเสี่ยง:

  • Untrusted content input ไหนมาจากนอก trust boundary?
  • Actions ระบบเขียน แก้ ลบ หรือเรียกอะไรได้บ้าง?
  • Blast radius ผลร้ายที่สุดที่นึกออกคืออะไร?
  • Observability ถ้ามีอะไรผิดปกติ จะเห็นเร็วแค่ไหน?

ตัวอย่างของ Anthropic: incident-response agent

  • input เป็น log ภายในและ Slack ภายใน ดังนั้นการ inject ต้องมาจากคนในหรือ account ที่ถูกเจาะ
  • อ่านได้กว้าง แต่ สร้างได้แค่เอกสารและข้อความ Slack แก้ ลบ หรือเปลี่ยน permission ไม่ได้
  • กรณีเลวร้ายสุด: log ที่อ่อนไหวเล็กน้อยถูกโพสต์ลงห้อง incident ที่ล็อกไว้อยู่แล้ว
  • ทุก action ส่งเข้า SIEM ความผิดปกติโผล่ภายในไม่กี่นาที
  • สรุป: ไม่ได้ปลอดความเสี่ยง แต่ write surface ที่จำกัดพร้อม audit ครบเป็น profile ที่ยอมรับได้

อัปเกรดโมเดล = ต้องเช็กขอบเขตใหม่

agent ตัวเดียวกันถูกย้ายจาก Opus 4 ไป Opus 4.5 โดย ไม่เพิ่ม tool, permission หรือ prompt ใดๆ แต่โมเดลที่ฉลาดขึ้นกลับไปขอให้ agent อีกตัวเขียน fix ลง production ระหว่าง incident ขอบเขตยังรักษาไว้ได้เพราะมี คนรีวิว pull request ก่อนขึ้น production บทเรียนคือ การอัปเกรดโมเดลเปลี่ยน risk profile และ control อย่าง human code review เป็นส่วนหนึ่งของ design ไม่ใช่ของแถม

ความเสี่ยงด้านเงินก็ตีกรอบแบบเดียวกัน

  • session budget ของ Managed Agents จำกัดความเสียหายจาก run เดียวที่หลุด
  • workspace spend limits เป็นด่านสุดท้ายของทั้ง workspace

"เดือนที่แย่ที่สุดจะไม่เกินเพดานของ workspace" เป็นประโยคที่อนุมัติได้ ส่วน "ค่าใช้จ่ายน่าจะอยู่ในระดับสมเหตุสมผล" อนุมัติไม่ได้

แบบฝึก: เปลี่ยน "support agent ทำอะไรเสียหายไม่ได้หรอก" เป็นประโยคที่มีขอบเขต เช่น

support agent อ่านประวัติคำสั่งซื้อได้อย่างเดียว ร่างคำตอบได้แต่ไม่ส่งจนกว่าคนจะรีวิว
คืนเงินหรือแก้ข้อมูลบัญชีไม่ได้ ทุก tool call ถูก log และมีคนรีวิวทุกวัน
ค่าใช้จ่ายถูกจำกัดทั้งระดับ session และระดับ workspace
เข้าใจผิดบ่อย

"ถ้าพูดได้ว่าไม่มีความเสี่ยง แปลว่าพร้อมอนุมัติ" ผิด สิ่งที่ต้องนำเสนอคือ residual risk ที่มีขอบเขต

สรุปสั้นๆ

ห้ามพูดว่าไม่มีความเสี่ยง ใช้ 4 คำถาม (untrusted input, actions, blast radius, observability) อัปเกรดโมเดลแล้วต้องเช็กขอบเขตใหม่ ความเสี่ยงด้านเงินตีกรอบด้วย session budget + workspace spend limit

Checkpoint 5

agent ตรวจ log ความปลอดภัยของคุณได้รับอนุมัติไปแล้วด้วย risk profile ที่มีขอบเขต ทีมจะอัปเกรดไปโมเดลรุ่นใหม่โดยไม่เปลี่ยน tool, permission หรือ prompt ควรนำเสนอต่อผู้อนุมัติยังไง?

  1. เป็นเรื่องต้นทุนอย่างเดียว เพราะไม่มีอะไรเปลี่ยนนอกจากโมเดล
  2. แจ้งว่าเป็นการสลับโมเดลเฉยๆ risk profile เหมือนเดิม
  3. ถอนสิทธิ์เขียนทั้งหมดของ agent ก่อนอัปเกรดเพื่อความปลอดภัย
  4. เป็นการเปลี่ยน risk profile ต้องเช็กขอบเขตใหม่ก่อน ship และคง control อย่าง human code review ไว้
ดูเฉลย

D โมเดลที่ฉลาดขึ้นอาจทำสิ่งที่ไม่เคยทำ (ตัวอย่าง Opus 4 → 4.5) A และ B สมมติว่าพฤติกรรมไม่เปลี่ยน C เกินเหตุ เพราะขอบเขตรักษาได้ด้วย control ที่มีอยู่

6. อธิบายกลไกให้ทีมวิศวกรฟัง

กับวิศวกร ความแม่นยำสำคัญมาก ถ้าอธิบาย feature ผิด ทีมก็สร้างผิด

Compaction กับ context editing

ทั้งสองอย่างช่วยให้ session ยาวๆ ไม่ล้น context window แต่ทำงานต่างกัน:

CompactionContext editing
ทำงานที่ไหนฝั่ง serverตั้งค่าฝั่ง client
ทำอะไรเมื่อบทสนทนาใกล้เต็ม window จะสรุปบทสนทนาทั้งหมดให้อัตโนมัติ client ไม่ต้องจัดการเองล้างเนื้อหาเฉพาะจุดตามกลยุทธ์ที่ตั้ง เช่น tool result เก่า หรือจัดการ thinking block
พูดกับทีมว่า"ทำให้ context ที่ active เล็กอยู่เสมอโดยอัตโนมัติ""ทิ้ง tool output เก่าที่เราเลือกทิ้ง"

ทั้งคู่ ไม่ต้องใช้ Batch API และ ไม่ผูกกับ tier ของโมเดล ถ้ามีข้อเท็จจริงที่ต้องอยู่รอดหลังการสรุป ให้จับคู่กับ memory tool

Thinking mode ขึ้นกับรุ่นของโมเดล

  • Extended thinking โหมดแบบเก่าที่ตั้งเอง กำหนดด้วย token budget
  • Claude 4.7 ขึ้นไป (รวม Opus 4.8) ปฏิเสธ extended thinking ด้วย error 400 โหมดเดียวที่มีคือ adaptive thinking ซึ่งโมเดลตัดสินเองว่าจะคิดเมื่อไรและมากแค่ไหน
  • Claude 4.5 ลงไป ที่รองรับ thinking (รวม Haiku 4.5) มีแค่ extended thinking ใช้ adaptive ไม่ได้

ทีมที่ต้องรองรับทั้งสองกลุ่มต้องมี สอง code path และควรวางแผน migration ไว้ก่อน request แรกจะพัง

def thinking_config(model):
    if model in OLD_THINKING_MODELS:      # เช่น Haiku 4.5
        return {"type": "enabled", "budget_tokens": 8000}
    return {"type": "adaptive"}           # 4.7+ เช่น Opus 4.8, Opus 5.5

Managed Agents กับ Claude Agent SDK

เรื่องนี้คือ ใครเป็นคนดูแล infrastructure ไม่ใช่เรื่อง capability ทั้งสองมี agent, tool และ session เหมือนกัน

Claude Agent SDKManaged Agents
รันที่ไหนใน process ที่เราดูแลเองharness สำเร็จรูปที่ตั้งค่าได้ บน infrastructure ของ Anthropic
Toolcustom tool เขียนในโค้ดเรา (รองรับ MCP)ตั้งค่าใน agent definition
Sandbox / stateเราจัดการเองsandbox บน cloud ที่ Anthropic ดูแล (หรือ self-hosted sandbox ที่เราตั้ง) และ event log ต่อ session
เหมาะกับต้องการคุมทุกอย่างใน processงานรันยาวและ asynchronous

agent definition ของ Managed Agents ถูกเก็บและ version ไว้ฝั่ง server เหตุผลที่ถูกในการเลือก Managed Agents คือ "Anthropic ดูแล sandbox และ session state ให้" ไม่ใช่ "SDK ทำ X ไม่ได้" (เพราะ SDK ก็มี custom tool, MCP, subagent และ hook)

เข้าใจผิดบ่อย

"ส่ง extended thinking พร้อม budget ไปที่ Opus 4.8 ได้ มันจะใช้ควบคู่กับ adaptive" ผิด รุ่น 4.7 ขึ้นไปปฏิเสธด้วย 400

สรุปสั้นๆ

compaction = server สรุปให้อัตโนมัติ, context editing = client เลือกล้าง thinking: 4.7+ adaptive อย่างเดียว, 4.5 ลงไป extended อย่างเดียว Managed Agents vs SDK = ใครดูแล infra

Checkpoint 6

coding agent ตัวหนึ่งใช้ Haiku 4.5 กับ extended thinking ที่ตั้ง budget ไว้ ทีมจะย้ายไป Opus 5.5 โดยไม่แก้โค้ด ควรบอกทีมว่าอะไร?

  1. ไม่ต้องแก้ เพราะโมเดลระดับ Opus รองรับทั้งสองโหมด
  2. วางแผนแก้ตอนนี้: Opus 5.5 ปฏิเสธ extended thinking ด้วย 400 ต้องย้ายไปใช้ adaptive thinking
  3. ไม่ต้องแก้ budget จะกลายเป็นเพดานของ adaptive thinking เอง
  4. ถ้ากลัวพัง ให้ไปใช้ Opus 4.8 แทนเพราะยังรองรับ extended thinking
ดูเฉลย

B รุ่น 4.7 ขึ้นไปใช้ได้แต่ adaptive A ผิดเพราะไม่มีรุ่นไหนรองรับทั้งสอง C request ถูกปฏิเสธ ไม่ได้ถูกแปลง D Opus 4.8 ก็เป็นรุ่น 4.7+ เหมือนกัน

Checkpoint 7

agent รีแฟกเตอร์โค้ดที่รันนานหลายชั่วโมงเริ่มชน context window วิศวกรถามว่า compaction กับ context editing ต่างกันยังไง ข้อไหนถูก?

  1. compaction ลบ tool result ทิ้งโดยไม่สรุป ส่วน context editing ต้องเรียก API สรุปแยกเอง
  2. compaction สรุปบทสนทนาก่อนหน้าให้อัตโนมัติเมื่อใกล้เต็ม window ส่วน context editing ใช้กลยุทธ์ที่ตั้งค่าได้ เช่น ล้าง tool result เก่าหรือจัดการ thinking block
  3. ทั้งสองใช้ได้เฉพาะโมเดลระดับ Opus
  4. ทั้งสองต้องส่งผ่าน Batch API
ดูเฉลย

B A สลับและบิดกลไก C ทั้งคู่ไม่ผูกกับ tier D ไม่เกี่ยวกับ Batch API

Checkpoint 8

ทีมหนึ่งใช้ทั้ง Opus 4.8 และ Haiku 4.5 และต้องประเมินเวลาพัฒนาเรื่อง thinking ข้อไหนถูก? (เลือก 2 ข้อ)

  1. Opus 4.8 ใช้ adaptive thinking เป็นโหมดเดียว โมเดลตัดสินเองว่าจะคิดเท่าไร
  2. Opus 4.8 ใช้ได้ทั้งสองโหมดใน request เดียว
  3. Haiku 4.5 รองรับ extended thinking แต่ไม่รองรับ adaptive thinking
  4. adaptive thinking มีเฉพาะใน Haiku 4.5
  5. extended thinking ถูกยกเลิกไปแล้วในทุกโมเดล
ดูเฉลย

A, C B ผิดเพราะ 4.7+ ปฏิเสธ extended D กลับด้านความจริง E ผิดเพราะรุ่น 4.5 ลงไปยังใช้ extended อยู่

Checkpoint 9

ทีมเล็กต้องการ agent ที่รันต่อเนื่องหลายวันแบบ asynchronous และไม่มีคนดูแล sandbox หรือ session infrastructure เหตุผลที่ถูกในการเสนอ Managed Agents คือข้อไหน?

  1. Agent SDK สร้าง custom tool หรือต่อ MCP ไม่ได้
  2. มีแค่ Managed Agents ที่รองรับ subagent และ hook
  3. Managed Agents รันบน infrastructure ที่ Anthropic ดูแล มี sandbox ต่อ session และ event log ให้ ทีมจึงไม่ต้องแบกภาระ ops ส่วนนี้
  4. Agent SDK ต้องติดตั้ง CLI แยกต่างหากจึงใช้กับงานยาวไม่ได้
ดูเฉลย

C การเลือกขึ้นกับว่าใครดูแล infra A, B, D อ้างข้อจำกัดของ SDK ที่ไม่จริง (SDK มี custom tool, MCP, subagent, hook)
