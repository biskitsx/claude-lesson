7.4 Claude API keys: key types, secret storage, rotation และ leak response

ต้นฉบับ: CertSafari 7.4

อ่านจบแล้วควรทำได้
  • เลือกระหว่าง personal key, service account key, legacy workspace key และ Admin API key ได้ โดยดูว่า key ถือ identity ของใคร และ จะหยุดใช้ได้เมื่อไหร่
  • แยก 401 (authentication ล้มเหลว) กับ 403 (level ไม่พอ) และรู้ว่าแต่ละอันแก้ยังไง
  • ทายได้ว่า API ตอบอะไรเมื่อ workspace scope ของ key ไม่ตรงกับ workspace ใน request
  • เก็บ, ตั้ง expiration และ rotate key ได้ ตั้งแต่ .env บน laptop ไปจนถึง secrets manager บน production
  • รับมือ key รั่วด้วย secret scanning, การ deactivate, spend limit และ usage monitoring
แนวคิดหลัก: identity-backed API key

Personal key และ service account key "สวมตัวตน" ของ user หรือ service account ที่ organization จัดการอยู่แล้ว สิทธิ์ของ key ตามตัวตนนั้นไปตลอด และ เมื่อ identity ถูกลบ key ก็ใช้ไม่ได้ทันที เหมือนบัตรพนักงานที่ผูกกับคน ลาออกบัตรก็ดับ

1. Key แต่ละแบบถือ identity ของใคร

  • Static key หน้าตาแบบ sk-ant-api... ส่งเป็น Authorization: Bearer <key>
  • ใน Console (Settings → API keys) field Linked account เป็นตัวกำหนดชนิด key: ผูกกับตัวเรา (personal) หรือกับ service account (สำหรับงานแชร์/workload)
Key typeทำงานในนามของหยุดใช้ได้เมื่อ
Personal keyตัวเรา พร้อม role และ permission ของเราเราหลุดจาก organization (หรือจาก workspace ถ้าเป็น single-workspace key) key ที่ถูก archive ไม่ฟื้นคืน แม้จะถูก invite กลับมา
Service account keyservice accountservice account ถูก archive หรือถูกเอาออกจาก workspace (กรณี single-workspace key)
Workspace key (legacy)ไม่มีใคร เป็นของ workspaceหมดอายุ, ถูก disable/delete หรือ workspace ถูก archive ไม่เกี่ยวว่าคนสร้างจะออกไปหรือยัง

Legacy workspace key คือข้อยกเว้นที่ไม่ผูกกับ identity มันยังทำงานต่อแม้คนสร้างลาออก integration ใหม่ๆ จึงควรใช้ key แบบ identity-backed

เลือกใช้แบบไหน

  • Script ส่วนตัวและงาน dev ใช้ personal key แต่อย่าแชร์ให้ทีม เพราะพอเจ้าของออก ระบบทีมพังทันที
  • CI job และ production service ใช้ service account เฉพาะ ซึ่ง organization admin เป็นคนสร้าง

Admin API key

  • ใช้ จัดการ organization ไม่ได้ใช้เรียก model
  • สร้างได้เฉพาะสมาชิกที่มี role admin (Settings → Admin keys)
  • prefix sk-ant-admin01-... ใช้กับ Admin API, Usage and Cost API, Rate Limits API และ API อื่นในหมวด Admin
  • ใช้ข้าม organization ไม่ได้
  • Console Admin API key เลือก scope ไม่ได้ และเข้าถึงทุก endpoint ที่รับ key นี้ แต่ endpoint ของ service account และ federation รับเฉพาะ org:admin OAuth token เท่านั้น Admin API key จะโดนปฏิเสธไม่ว่าคนสร้างมีสิทธิ์สูงแค่ไหน

401 vs 403: อ่าน status code ก่อนเสมอ

Statusความหมายสาเหตุตัวอย่างแก้ยังไง
401 authentication_errorพิสูจน์ตัวตนไม่ผ่านkey ไม่รู้จัก, ถูก archive, หมดอายุแก้ credential (key หมดอายุไม่กลับมา ต้องสร้างใหม่)
403ตัวตนผ่าน แต่ level ไม่พอpersonal key ของ developer พยายามจัดการ user (ต้อง admin) หรือ Enterprise key ไม่มี scope ที่ endpoint ต้องการแก้ level: ใช้ identity ที่ role สูงพอ หรือสร้าง key ใหม่ที่มี scope ครบ
  • Key ส่งเป็น bearer token ส่วน header เก่า x-api-key ยังใช้ได้ (Admin API call ปกติใช้ตัวนี้)
  • Level ของ personal key = organization role ของเจ้าของ เช่น developer จัดการ API key ได้ แต่จัดการ user ต้องเป็น admin
  • Claude Enterprise key มี scope ชัดเจน (เช่น read:members, read:analytics) ล็อกตั้งแต่ตอนสร้าง เรียกนอก scope ได้ 403 ที่บอกทั้ง scope ที่ key มีและ scope ที่ endpoint ต้องการ อยากขยายต้องสร้าง key ใหม่
# ดู status ก่อนตัดสินใจแก้
try:
    client.messages.create(...)
except anthropic.AuthenticationError:      # 401
    rotate_credential()                     # key ผิด/หมดอายุ/ถูก archive -> ต้องได้ key ใหม่
except anthropic.PermissionDeniedError:    # 403
    escalate_role_or_scope()                # key ใช้ได้ แต่สิทธิ์ไม่ถึง
แถม: allowed_tools ไม่ใช่ allowlist

ใน Agent SDK allowed_tools แค่ pre-approve tool ที่ระบุ tool อื่นที่ไม่อยู่ใน list จะไม่ match allow rule แล้ว ตกไปที่ permission mode ถ้าตั้ง permission_mode: "bypassPermissions" ไว้ ทุกอย่างก็ผ่านหมด ถ้าอยากกันจริงให้ใช้ disallowed_tools, เลี่ยง bypass mode หรือใช้ PreToolUse hook

เข้าใจผิดบ่อย

"ลบ engineer ออกจาก org แล้ว key ทุกตัวที่เขาสร้างจะใช้ไม่ได้" ไม่ใช่ personal key ถูก archive ก็จริง แต่ legacy workspace key เป็นของ workspace ยังใช้ได้จนกว่าจะหมดอายุ ถูก disable/delete หรือ workspace ถูก archive

"ได้ 403 จาก Admin หรือ Compliance API แปลว่า key เสีย ให้เปลี่ยนเป็น key แบบเดิม" ไม่ใช่ 403 คือ key ผ่านแล้วแต่ level ไม่พอ scope ล็อกตอนสร้าง key แบบเดิมก็ได้ 403 เหมือนเดิม ต้องสร้าง key ใหม่ที่มี scope ที่ขาด

สรุปสั้นๆ

Personal = ของเรา, service account = ของ workload, legacy workspace = ของ workspace (รอดแม้คนสร้างออก), Admin key = จัดการ org และ 401 = แก้ credential, 403 = แก้ level

Checkpoint 1

Data engineer คนหนึ่งลาออก admin เอาเขาออกจาก organization วันรุ่งขึ้น job ไหนยังเรียก API ได้ปกติ?

  1. Job ที่ใช้ personal key ของเขา
  2. Job ที่ใช้ legacy workspace key ที่เขาสร้างไว้
  3. ไม่มีเลย key ทุกตัวที่เขาสร้างถูก revoke หมด
  4. ทุก job เพราะ key ไม่ผูกกับคน
ดูเฉลย

B personal key ถูก archive พร้อมเจ้าของ แต่ legacy workspace key เป็นของ workspace ไม่ใช่ของคน (และนี่คือเหตุผลที่ควรรีบย้ายไป service account)

Checkpoint 2

Agent ตั้ง allowed_tools=["Grep"] คู่กับ permission_mode="bypassPermissions" แล้วพบว่า agent ยังรัน Write ได้ เพราะอะไร?

  1. Config ผิด syntax เลยถูกเมินทั้งหมด
  2. allowed_tools แค่ pre-approve tool ที่ระบุ ส่วน Write ไม่ match allow rule จึงตกไปที่ permission mode ซึ่ง bypass อนุมัติให้
  3. เป็น bug ของ permission evaluator
  4. เพราะไม่มี PreToolUse hook เท่านั้น
ดูเฉลย

B combination นี้ valid และทำงานตามออกแบบ D ไม่ครบ เพราะ disallowed_tools หรือการไม่ใช้ bypass mode ก็กันได้เหมือนกัน

Checkpoint 3 (เรียงลำดับ)

ทีมจะเลิกใช้ legacy workspace key ใน service จ่ายบิล เรียงขั้นตอนให้ถูก:

  1. ยืนยันว่า request ผ่าน แล้วค่อยลบ key เก่า
  2. สร้าง key ใหม่สำหรับ workspace นั้น
  3. ตัดสินใจว่าจะใช้ key ชนิดไหน
  4. Deploy key ใหม่ลง ANTHROPIC_API_KEY หรือ entry ใน secrets manager
  5. ให้ admin สร้าง service account และเพิ่มเข้า workspace (ถ้าจำเป็น)
ดูเฉลย

c → e → b → d → a key เก่าต้องลบเป็นขั้นสุดท้าย เพื่อไม่ให้มีช่วงไหนที่ traffic วิ่งโดยไม่มี credential ที่ใช้ได้

2. API ตรวจยังไงว่า key ทำงานใน workspace ไหนได้

สถานการณ์ผลลัพธ์
Workspace-scoped keyใช้ได้แค่ใน workspace ของมัน ไม่ต้องส่ง workspace ID
Key ไม่ scope workspace แต่ไม่ส่ง header anthropic-workspace-id400 invalid_request_error
ส่ง ID ที่ format ผิด400
ส่ง ID ถูก format แต่ identity เข้าไม่ถึง404 not_found_error (เหมือน workspace ไม่มีอยู่จริง)
  • Key ที่ไม่ scope ต้องบอก workspace ทุก request ผ่าน anthropic-workspace-id หรือตั้งครั้งเดียวด้วย default_headers ตอนสร้าง client
  • 404 ตรงนี้ส่วนใหญ่แปลว่า ไม่ได้เป็นสมาชิก ไม่ใช่พิมพ์ผิด
  • Service account เป็นสมาชิก Default Workspace โดยอัตโนมัติ workspace อื่นต้องเพิ่มเองทีละที่
  • Admin API เช็กกลับทาง: รับ personal/service account key ก็ต่อเมื่อ key ไม่ได้ scope อยู่กับ workspace เดียว key แบบ single-workspace บน laptop ของ admin เลยใช้กับ endpoint จัดการ org ไม่ได้ แม้ role จะอนุญาตก็ตาม
import anthropic
# ตั้ง workspace ครั้งเดียว ไม่ต้องใส่ทุก request
client = anthropic.Anthropic(
    default_headers={"anthropic-workspace-id": "wrkspc_01ABC..."}
)
สรุปสั้นๆ

ไม่ส่ง/ส่ง ID ผิด format = 400, ส่ง ID ถูกแต่ไม่ได้เป็นสมาชิก = 404 และ Admin API ต้องการ key ที่ไม่ scope workspace

Script ใช้ key ที่เข้าได้หลาย workspace แล้วโดน 400 invalid_request_error ทุกครั้ง ต้องเพิ่ม header ตัวไหน?

  1. x-api-key
  2. anthropic-version
  3. anthropic-workspace-id
  4. anthropic-organization-id
ดูเฉลย

C A คือ header credential, B คือ API version, D ไม่ใช่ header สำหรับเลือก workspace

Checkpoint 5

Service account ตัวหนึ่งเพิ่งสร้าง ยังไม่เคยถูกเพิ่มเข้า workspace "analytics" ถ้าส่ง ID ของ analytics ที่ถูกต้อง 100% ไป จะได้อะไร?

ดูเฉลย

404 not_found_error เหมือน workspace ไม่มีอยู่ เพราะ identity เข้าไม่ถึง (service account อยู่แค่ใน Default Workspace โดยอัตโนมัติ) 400 จะได้เฉพาะตอนไม่ส่ง header หรือ ID ผิด format

3. เก็บ, ตั้งอายุ และ rotate key

ทางรั่วยอดฮิต: commit key แบบ plaintext ขึ้น public repo หรือ paste key ลง tool ของ third party การอัปโหลด key ไปที่ web IDE, cloud provider หรือ CI/CD platform เท่ากับให้คนทำ tool นั้นเข้าถึง Console account ของเราได้ ถ้าจำเป็นต้องใส่ ให้ใส่เป็น encrypted secret และทุกคนควรมี key ของตัวเอง

Environmentเก็บยังไง
Laptopไฟล์ .env โหลดด้วย python-dotenv และใส่ไว้ใน .gitignore
Cloudencrypted secret storage (ไม่ใช่ dotenv) ให้ secret manager inject ANTHROPIC_API_KEY ซึ่ง SDK อ่านเองอัตโนมัติ
มีหลาย keykey management system: ที่เก็บเข้ารหัสที่เดียว, access control ละเอียด, audit trail, rotate ง่าย
# laptop เท่านั้น
echo "ANTHROPIC_API_KEY=sk-ant-api..." > .env
echo ".env" >> .gitignore        # กันเผลอ commit

# โค้ด: ไม่ต้องส่ง key ตรงๆ SDK อ่านจาก env เอง
from dotenv import load_dotenv; load_dotenv()
import anthropic; client = anthropic.Anthropic()

Expiration

  • Preset: 3 ชั่วโมง, 1 วัน, 7 วัน, 30 วัน, custom duration หรือ Never (สำหรับ key ที่เรา rotate เองใน secrets manager)
  • Org ตั้ง maximum expiration policy ได้ ซึ่งจำกัดตัวเลือกและตัด Never ออก
  • Expiration ตั้งตอนสร้างและ แก้ทีหลังไม่ได้
  • Anthropic เตือนก่อนหมดอายุ: 7 วันล่วงหน้า สำหรับ key อายุ ≥ 14 วัน และ 1 วันล่วงหน้า สำหรับ key อายุ ≥ 7 วัน
  • หมดอายุแล้วได้ 401 authentication_error ทางเดียวคือสร้าง key ใหม่

Rotation

สร้าง key ใหม่ ก่อน ปลด key เก่า และทำเป็นรอบ (ต้นฉบับยกตัวอย่างทุก 90 วัน) Expiration ช่วยจำกัดว่า key ที่รั่วจะใช้ได้นานแค่ไหน แต่ ไม่ได้แทน secret hygiene ที่ดี

เข้าใจผิดบ่อย

"Key ที่หมดอายุแล้ว เข้า Console ไป reactivate หรือยืดอายุได้" ไม่ได้ expiration ล็อกตั้งแต่สร้าง หมดแล้วได้ 401 และเปิดกลับไม่ได้

สรุปสั้นๆ

Laptop = .env + .gitignore, cloud = secret manager, อายุ key แก้ไม่ได้ และ rotate แบบสร้างใหม่ก่อนลบเก่า

Checkpoint 6

ทีมสร้าง key อายุ 7 วันไว้ทดสอบ แต่โปรเจกต์ยืดเป็น 60 วัน ทำยังไงดี?

  1. แก้ expiration ใน Console เป็น 60 วัน
  2. Disable แล้ว re-enable เพื่อรีเซ็ตอายุ
  3. สร้าง key ใหม่ที่อายุยาวพอ แล้ว rotate ไปใช้ key นั้น
  4. รอให้หมดอายุแล้วค่อย reactivate
ดูเฉลย

C expiration แก้ไม่ได้ disable/re-enable ไม่รีเซ็ตอายุ และ key หมดอายุแล้ว reactivate ไม่ได้

4. ตรวจจับการรั่ว, ปิดให้ไว และเฝ้า usage

Secret scanning

  • เปิด secret scanning ใน source control provider
  • รัน SAST tool อย่าง Gitleaks กับ repo
  • ใส่ scanning ใน CI/CD เพื่อจับ secret ก่อนเข้า main branch
  • ตาข่ายรองรับจาก GitHub: ผ่าน Secret scanning partner program ถ้า Claude API key โผล่ใน public repo GitHub จะแจ้ง Anthropic ซึ่งจะ deactivate key อัตโนมัติ และ email แจ้งเจ้าของ
# CI step: fail build ถ้าเจอ secret
gitleaks detect --source . --redact --exit-code 1

ถ้าสงสัยว่าโดน: revoke ทันที, สร้าง key ใหม่ และเก็บใน secrets manager

Actionย้อนได้?ผลลัพธ์
Disableได้status เป็น inactive กด Re-enable กลับเป็น active เหมาะกับ key ที่ยังไม่แน่ใจ
Deleteไม่ได้key ถูก archive แต่ยังโผล่ใน List API Keys ด้วย status: "archived" key ที่หมดอายุทำได้แค่ delete
เข้าใจผิดบ่อย

"Delete key ต้องสงสัยก็ย้อนได้เหมือน disable" ไม่ใช่ เฉพาะ Disable ที่ Re-enable ได้ Delete คือถาวร

Spend control: จำกัดความเสียหาย

  • Org แบบ Custom Rate Limit ควรตั้ง usage limit และ spend limit
  • Org แบบ Standard Rate Limit ตั้ง auto-reload threshold ให้ระวัง เพราะทุกครั้งที่ reload คือเครดิตเพิ่มให้ attacker ใช้
  • ภาพรวมเรื่อง rate limit / spend limit / service tier อยู่ในบท 2.1

Monitoring

  • ดู log และ usage แยกตาม key ใน Console
  • แยก key ตามจุดประสงค์ (dev / test / prod) ถ้ารั่วจะได้ปิดแค่ตัวเดียว
  • List API Keys และ Retrieve API Key คืน expires_at ใช้ audit และ rotate ก่อนหมดอายุได้
  • Identity-backed key บอกได้ว่า user หรือ service account ไหนเป็นคนเรียก
import os, requests
from datetime import datetime, timedelta, timezone

r = requests.get("https://api.anthropic.com/v1/organizations/api_keys",
                 headers={"x-api-key": os.environ["ANTHROPIC_ADMIN_KEY"],   # Admin API key
                          "anthropic-version": "2023-06-01"})
soon = datetime.now(timezone.utc) + timedelta(days=14)
for k in r.json()["data"]:
    exp = k.get("expires_at")
    if exp is None:                      # null = ไม่มีวันหมดอายุ
        continue
    if datetime.fromisoformat(exp.replace("Z", "+00:00")) < soon:
        print("ใกล้หมดอายุ:", k["name"], exp)
สรุปสั้นๆ

Scan ก่อนรั่ว (Gitleaks, CI, GitHub partner program), รั่วแล้ว revoke + สร้างใหม่, Disable ย้อนได้ Delete ไม่ได้, ตั้ง spend limit และแยก key ตามจุดประสงค์

Checkpoint 7 (จับคู่)

จับคู่สถานะ/การกระทำกับผลที่ตามมา:

  1. กด Disable key
  2. กด Delete key
  3. Key ที่เลยวันหมดอายุ
  4. Key หลุดไปอยู่ใน public GitHub repo
ดูเฉลย

1 → status inactive, Re-enable กลับได้ · 2 → ถาวร ถูก archive แต่ยังอยู่ใน list · 3 → ได้ 401 และทำได้แค่ delete · 4 → Anthropic deactivate ให้อัตโนมัติและ email แจ้ง

Security team อยากได้ report รายสัปดาห์ของทุก key ทุก workspace ที่จะหมดอายุใน 14 วัน แบบ automate ควรใช้อะไร?

  1. Compliance Activity Feed
