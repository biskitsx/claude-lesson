1.2 Ways to build and host a Claude agent (Client SDK, Agent SDK, Managed Agents)

ต้นฉบับ: CertSafari 1.2

อ่านจบแล้วควรทำได้
  • เลือกได้ว่าจะใช้ Client SDK, Agent SDK หรือ Claude Managed Agents โดยดูว่าแต่ละตัวรับภาระเรื่อง agent loop, tools และ hosting ไปให้เรามากแค่ไหน
  • อธิบาย building block 4 ตัวของ Managed Agents ได้: agent, environment, session, events
  • แยก deployment model 3 แบบได้: Agent SDK ใน process ของเราเอง, Managed Agents บน cloud sandbox ของ Anthropic และ Managed Agents ที่ใช้ self-hosted sandbox
แนวคิดหลัก: ใครเป็นคนเขียนและรัน harness

Agent harness คือโค้ดที่ห่อโมเดลไว้แล้ววน agent loop ให้ ส่ง prompt ไป รัน tool ที่โมเดลขอ เอาผลป้อนกลับ และตัดสินว่าเมื่อไหร่ควรหยุด ทางเลือกในการสร้าง agent ทั้งหมดต่างกันหลักๆ แค่ตรงนี้: harness เป็นของ เราเขียนเอง, เป็น library ที่รันใน process ของเรา หรือ Anthropic รันให้

1. สี่ทางในการสร้าง Claude agent

ไม่ว่าจะสร้างด้วยวิธีไหน agent ทุกตัววนรอบเดียวกันหมด: ส่ง prompt → โมเดลขอเรียก tool → รัน tool แล้วส่งผลกลับ → วนไปเรื่อยๆ จนโมเดลตอบโดยไม่ขอ tool แล้ว (รายละเอียดลูป tool use อยู่ในบท 8.1) สิ่งที่ต่างกันคือ ใครเป็นคนหมุนลูปนี้

  • Client SDK เรียก Messages API ตรงๆ เราเขียน tool loop เอง หรือจะใช้ tool runner (beta) ช่วยหมุนลูปก็ได้ แต่ tool ยังต้องนิยามและรันเองอยู่ดี เหมาะกับคนที่อยากคุมทุกอย่างละเอียดๆ
  • Agent SDK เป็น library ภาษา Python/TypeScript ที่ไปรัน binary ของ Claude Code ใน process ที่เราดูแลเอง ได้ของแถมมาครบ: loop ของ Claude Code, built-in tools, permissions, sessions, hooks, subagents และรองรับ MCP
  • Managed Agents Anthropic host harness ให้ทั้งหมด เราแค่ config ผ่าน Claude API
  • Claude Code CLI ใช้ทำงานแบบ interactive หรืองาน one-off ใน terminal

เปรียบง่ายๆ เหมือนเรื่องร้านอาหาร: Client SDK คือทำกับข้าวเองทุกขั้น, Agent SDK คือซื้อชุดครัวสำเร็จมาตั้งในร้านเรา, Managed Agents คือจ้าง cloud kitchen ทำให้เลย

เลือกยังไงในทางปฏิบัติ

  • Client SDK เมื่อตัว loop คือ product ของเราเอง เช่น อยากมี stopping rule แบบพิเศษ หรือตัด context ด้วยวิธีของเราเอง
  • Agent SDK เมื่ออยากได้ agent สไตล์ coding ที่ทำงานได้เลยภายใน service ของเรา
  • Managed Agents เมื่องานรันนานเป็นนาทีหรือเป็นชั่วโมง และไม่อยากดูแล sandbox, การรัน tool หรือที่เก็บ session เอง
# Agent SDK แบบสั้นๆ: เราไม่ต้องเขียน tool loop เลย
from claude_agent_sdk import query, ClaudeAgentOptions

async def main():
    opts = ClaudeAgentOptions(allowed_tools=["Read", "Grep", "Bash"])
    async for msg in query(prompt="หาว่า test ไหนพังแล้วสรุปสาเหตุ", options=opts):
        print(msg)   # SDK วน loop + รัน tool ให้เอง เราแค่อ่าน message ที่ yield ออกมา
เข้าใจผิดบ่อย

"ใช้ beta tool runner ของ Client SDK แล้วก็ได้ tool สำเร็จรูปแบบ Claude Code" ไม่ใช่ tool runner แค่ช่วยหมุนลูป ส่วน tool ยังเป็นของที่เรานิยามและรันเองทั้งหมด ถ้าอยากได้ Read/Edit/Bash, hooks, sessions มาพร้อมใช้ ต้องเป็น Agent SDK

สรุปสั้นๆ

loop เหมือนกันทุกแบบ ต่างกันที่ใครหมุนและใครถือ tool: Client SDK = เรา, Agent SDK = library ใน process เรา, Managed Agents = Anthropic

Checkpoint 1

ทีม backend มี service ภาษา TypeScript อยากให้ agent อ่านไฟล์ใน repo รันคำสั่ง shell ได้ มี hook ไว้ block คำสั่งอันตราย และ resume session เดิมได้ โดยไม่อยากเขียน tool loop เอง ควรใช้อะไร?

  1. Client SDK แล้วเขียน handler ของ Read/Bash เอง
  2. Agent SDK
  3. Client SDK + beta tool runner
  4. เปิด Claude Code CLI แบบ interactive ทิ้งไว้บนเซิร์ฟเวอร์
ดูเฉลย

B Agent SDK ให้ loop, built-in tools, hooks และ sessions ของ Claude Code มาใน process ของเราเลย ส่วน A กับ C ยังต้องนิยาม tool เอง และ D เป็นการใช้งานแบบคนนั่งพิมพ์ ไม่ใช่การฝังใน service

2. Claude Managed Agents: agent, environment, session, events

Managed Agents เปลี่ยนจาก "เขียนโค้ด" เป็น "เขียน config" เป็นส่วนใหญ่ เรื่องจุกจิกอย่าง prompt caching กับ compaction ก็ harness ของ Anthropic จัดการให้ ตัวต่อหลักมี 4 ชิ้น:

Building blockคืออะไร
Agentชุด config: model, system prompt, tools, MCP servers, skills สร้างครั้งเดียว แล้วอ้างถึงด้วย ID ได้ในหลาย session
Environmentที่ที่ session ไปรัน: cloud sandbox ที่ Anthropic ดูแล หรือ self-hosted sandbox
Sessionagent หนึ่งตัวที่กำลังรันอยู่ใน environment หนึ่ง เพื่อทำงานชิ้นหนึ่ง
Eventsข้อความที่วิ่งระหว่างแอปเรากับ agent เช่น user turn, tool result, status update

คิดแบบ OOP ก็ได้: agent คือ class, session คือ instance ที่ถูก new ขึ้นมาใน environment หนึ่ง และ events คือ message ที่โยนไปมากับ instance นั้น

Flow ตอนรันจริง

  1. สร้าง session โดยอ้าง agent ID กับ environment
  2. ส่ง user event เข้าไป
  3. รับผลแบบ streaming ผ่าน server-sent events (SSE)
  4. ประวัติ event ทั้งหมดเก็บไว้ฝั่ง server ดึงย้อนหลังได้ทีหลัง
  5. ระหว่างทางส่ง event เพิ่มเพื่อ steer หรือ interrupt agent ได้
// pseudo-code แสดงลำดับความคิด (ไม่ใช่ signature จริงของ API)
const session = await createSession({ agent: AGENT_ID, environment: ENV_ID });
await sendEvent(session.id, { type: "user", text: "อัปเดต dependency แล้วรัน test" });
for await (const ev of streamEvents(session.id)) {   // มาทาง SSE
  console.log(ev.type);                               // tool result, status update ...
}
// อยากเปลี่ยนทิศ? ส่ง user event ใหม่เข้าไปได้เลย

เหมาะสุดกับ: งานที่รันนานๆ, session แบบ stateful ที่มี filesystem ค้างอยู่ได้ และงานที่ต้องรันซ้ำตามรอบด้วย scheduled deployment (cron)

เข้าใจผิดบ่อย

"Managed Agents ใช้กับ workload ที่ต้องการ Zero Data Retention (ZDR) ได้" ไม่ได้ session เก็บ history, สถานะ sandbox และ output ไว้ฝั่ง Anthropic ตอนนี้จึง ยังไม่เข้าเงื่อนไข ZDR และ HIPAA BAA แต่ยังสั่งลบ session และไฟล์ที่อัปโหลดผ่าน API ได้

สรุปสั้นๆ

Agent = config ที่ reuse ด้วย ID, Environment = ที่รัน, Session = instance ที่ทำงานอยู่, Events = ข้อความไป-กลับ (stream ผ่าน SSE และเก็บ history ไว้ server)

  4. ข้อความ "เริ่มรัน lint แล้ว" ที่แอปเราได้รับระหว่างทาง

3. Process เรา, cloud ของ Anthropic หรือ sandbox ของเรา

คำถามเดียวที่ใช้แยก deployment model คือ ฝั่งไหนรัน loop และฝั่งไหนรัน tools

  • Agent SDK: ทั้ง loop และ tools อยู่ใน process ของเรา deploy เหมือน service ทั่วไป (container หรือ serverless) จะเก็บ session ไว้ใน backend ของเราเองก็ได้
  • Managed Agents + cloud environment (default): tools รันใน sandbox ที่ Anthropic ดูแล Anthropic จัดการ egress control, การ mount ไฟล์และ GitHub repo และ lifecycle ของ sandbox ให้
  • Managed Agents + self-hosted sandbox: orchestration ยังอยู่กับ Anthropic แต่ การรัน tool ย้ายมาอยู่บน infra ของเรา ไฟล์, process และ network access อยู่ในมือเรา แต่ input/output ของ tool ยังวิ่งไปที่ control plane ของ Anthropic อยู่ เนื้อหาของ skills และ memory store ถูก copy เข้ามาใน sandbox โดย memory files ไปอยู่ที่ /mnt/memory/ แล้ว SDK worker sync การเปลี่ยนแปลงกลับไปที่ store
เรื่องCloud environmentSelf-hosted sandbox
Tools รันที่ไหนSandbox ที่ Anthropic ดูแลInfra ของเรา
Network reachตาม egress control ของ Anthropicตาม network policy ของเรา
Mount ไฟล์และ GitHub repoAnthropic จัดการเราจัดการ
Memory storesAnthropic mount ไว้ที่ /mnt/memory/ดาวน์โหลดมาที่ /mnt/memory/ แล้ว SDK worker sync กลับ
LifecycleAnthropic จัดการเราจัดการ

เมื่อไหร่ self-host ถึงคุ้ม

  • ข้อมูลต้องอยู่ใน network boundary ของเราเท่านั้น
  • agent ต้องเข้าถึง internal service ที่ไม่มี public route
  • งานต้องผ่าน compliance หรือ audit control ของเราเอง

ถ้าไม่เข้าข้อไหนเลย ใช้ cloud environment ไปเถอะ infra ที่ต้องดูแลน้อยกว่าเยอะ

เข้าใจผิดบ่อย

"Self-hosted sandbox = ทั้ง agent รวมถึงการเรียกโมเดลย้ายมาอยู่บน infra เรา" ไม่ใช่ ที่ย้ายมามีแค่ tool execution ส่วน reasoning ของ Claude และ orchestration ยังอยู่ฝั่ง Anthropic

ลองเดาก่อน

ย้าย Managed Agents session ไปใช้ self-hosted sandbox แล้ว การคิด (reasoning) ของ Claude เกิดที่ไหน?

  1. บนเครื่องของเราทั้งหมด
  2. ฝั่ง Anthropic ส่วน tool รันบนเครื่องเรา
  3. แบ่งครึ่ง: model บางส่วนรันบนเครื่องเรา
ดูเฉลย

B self-hosting ย้ายแค่การรัน tool ส่วนโมเดลกับ orchestration ยังอยู่กับ Anthropic

สรุปสั้นๆ

Agent SDK = loop + tools อยู่บ้านเรา, Managed cloud = อยู่บ้าน Anthropic ทั้งคู่, Managed self-hosted = loop อยู่ Anthropic แต่ tools อยู่บ้านเรา

Checkpoint 3

agent ต้องเรียก HR API ภายในบริษัทที่เข้าได้จาก VPN เท่านั้น และทีมอยากให้ Anthropic เป็นคนดูแล agent loop ให้ ควรเลือกแบบไหน?

  1. Managed Agents + cloud sandbox แล้วเปิด egress ให้กว้างขึ้น
  2. Managed Agents + self-hosted sandbox
  3. Client SDK + beta tool runner โดยให้ Anthropic host ให้
  4. แบบไหนก็ได้ เพราะ tool call รันบน network ของผู้เรียกเสมอ
ดูเฉลย
