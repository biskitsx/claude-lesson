8.3 Built-in tools vs custom tools, skills และ MCP: เลือกวิธีให้ Claude ลงมือ

ต้นฉบับ: CertSafari 8.3

อ่านจบแล้วควรทำได้
  • แยก Anthropic-provided client tool, server tool และ user-defined tool ได้จาก "ใครเขียน schema" และ "โค้ดรันที่ไหน"
  • ตัดสินได้ว่าเมื่อไหร่ built-in tool พอ และเมื่อไหร่คุ้มที่จะเขียน custom tool
  • อธิบายได้ว่า skill ใช้ progressive disclosure ยังไง เพื่อไม่ให้ความรู้ที่ไม่ได้ใช้มากิน context
  • เลือกได้ว่าจะใช้ MCP, skill หรือทั้งคู่ และบอก context cost ของแต่ละแบบได้
แนวคิดหลัก: connection กับ know-how

Tool และ MCP server ให้ Claude มี action ให้เรียก (connection) ส่วน skill ให้ Claude มี วิธีทำหรือเอกสารอ้างอิงให้อ่านแล้วทำตาม (know-how) ที่โหลดเข้ามาเฉพาะตอนต้องใช้ หลายระบบต้องใช้ทั้งสองอย่าง

1. ใช้ built-in ก่อน แล้วค่อยเขียน custom tool สำหรับ action เฉพาะโดเมน

การขยายความสามารถ Claude มี 4 ทาง: tool ที่ Anthropic ให้มา, tool ที่เราเขียนเอง, skill และ MCP server เลือกผิดก็จะเจอ 2 แบบ: เขียนโค้ดที่ไม่จำเป็น หรือเผา context ทิ้ง

จุดที่คนพลาดบ่อย: คำว่า "built-in" บอกแค่ว่าใครออกแบบ tool ไม่ได้บอกว่าใครรัน

ประเภทSchema ใครเขียนใครรัน callตัวอย่าง
User-defined client toolเราแอปของเราget_weather
Anthropic-schema client toolAnthropicแอปของเราbash, text_editor
Server toolAnthropicinfrastructure ของ Anthropicweb_search, web_fetch, code_execution, tool_search

Built-in ใน Claude Code และ Agent SDK

Claude Code กับ Agent SDK มี built-in มาให้แล้ว เช่น Read, Edit, Write, Bash, Grep, Glob, WebFetch ฯลฯ ใน SDK:

  • เปิดใช้ built-in ด้วยชื่อใน allowed_tools
  • ส่ง tools array ที่มีเฉพาะ built-in ที่ต้องการ เพื่อให้ตัวที่ไม่ใช้ไม่ต้องเข้ามาอยู่ใน context
  • Bash คือตัวเอนกประสงค์สำหรับงาน computer ทั่วไป
options = ClaudeAgentOptions(
    tools=["Read", "Grep", "Glob"],          # เอาเข้า context แค่ 3 ตัวนี้
    allowed_tools=["Read", "Grep", "Glob"],  # อนุมัติให้ใช้ได้โดยไม่ต้องถาม
)

เมื่อไหร่ควรเขียน custom tool

Custom tool คือ name + description + input_schema ที่โค้ดเราเป็นคนรัน ใน Agent SDK ให้ register ผ่าน in-process MCP server ควรเขียนเมื่อ action นั้นเฉพาะโดเมน และ agent ทำบ่อย เช่น agent จัดการอีเมลที่ต้องมี fetchInbox กับ searchEmails

from claude_agent_sdk import tool, create_sdk_mcp_server

@tool("lookup_shipment", "ดูสถานะพัสดุจากเลข tracking ภายในบริษัท", {"tracking_no": str})
async def lookup_shipment(args):
    status = await internal_api.track(args["tracking_no"])   # เรียกระบบภายในของเรา
    return {"content": [{"type": "text", "text": status}]}

logistics = create_sdk_mcp_server(name="logistics", version="1.0.0", tools=[lookup_shipment])

และรักษา tool set ให้เล็ก: tool PR ตัวเดียวที่มี parameter action ดีกว่ามี create_pr, review_pr, merge_pr แยกกัน

เข้าใจผิดบ่อย

"Anthropic เขียน schema ของ bash กับ text_editor ก็แปลว่า Anthropic รันให้" ไม่ใช่ สองตัวนี้เป็น client tool แอปเรารันแต่ละ call และส่ง tool_result กลับเอง มีแค่ server tool ที่รันฝั่ง Anthropic

สรุปสั้นๆ

ถามสองข้อ: ใครเขียน schema และใครรัน built-in ครอบคลุมงานไฟล์/shell/search อยู่แล้ว custom tool ไว้สำหรับ action เฉพาะโดเมนที่ทำบ่อย

Checkpoint 1

tool ไหนต่อไปนี้ Anthropic เป็นคนเขียน schema แต่แอปของเราต้องรันเอง?

  1. web_fetch
  2. bash
  3. tool_search
  4. code_execution
ดูเฉลย

B bash เป็น Anthropic-schema client tool ส่วนอีกสามตัวเป็น server tool ที่รันบน infrastructure ของ Anthropic

Checkpoint 2

ทีม QA ก๊อป checklist ทดสอบก่อน release 12 ขั้นมาแปะในแชท Claude Code ทุกรอบ และบางทีก็มีขั้นตกหล่น ควรทำยังไง?

  1. แปะ checklist ไว้ใน CLAUDE.md ให้โหลดทุก session
  2. ทำเป็น Skill แล้วเรียกด้วย slash command เช่น /release-qa
  3. เปิดเป็น MCP resource
  4. เขียน custom tool ที่ print checklist ออกมา
ดูเฉลย

B นี่คือ procedure ที่ใช้เป็นครั้งคราว เหมาะกับ skill CLAUDE.md ไว้สำหรับ convention ที่ต้องใช้ตลอดเวลา MCP ไว้ต่อระบบภายนอก และ tool ที่แค่ print ข้อความตายตัวไม่ได้เพิ่มอะไร

2. Skills: know-how ที่โหลดเฉพาะตอนต้องใช้

Skill คือ directory ที่มีไฟล์ SKILL.md (instruction + metadata) และอาจมี script, template, ไฟล์อ้างอิงอื่นๆ แนบมา Claude จะหยิบมาใช้เองเมื่อเกี่ยวข้อง ตัวอย่างการใช้: deploy checklist, ขั้นตอน code review, API style guide

---
name: invoice-reconcile
description: กระทบยอด invoice กับรายการเดินบัญชี หาเคสยอดไม่ตรงและสรุปเป็นตาราง ใช้เมื่อ user พูดถึง invoice, statement, กระทบยอด หรือ reconciliation
---
# ขั้นตอน
1. ...

Frontmatter บังคับแค่ 2 field:

  • name ยาวไม่เกิน 64 ตัว ใช้ได้แค่ตัวพิมพ์เล็ก ตัวเลข และ hyphen
  • description ยาวไม่เกิน 1024 ตัว Claude ใช้ field นี้จับคู่กับคำขอ จึงต้องบอกทั้ง ทำอะไร และ ใช้เมื่อไหร่ เขียนแค่ "ตัวช่วย invoice" ไม่พอ เพราะไม่ได้บอกว่าใช้ตอนไหน

Progressive disclosure: โหลด 3 ระดับ

ลองเดาก่อน: ติดตั้ง 20 skill แต่ละตัวมี body ราว 4,000 token ก่อนใช้งานจะกิน context เท่าไหร่? คำตอบคือแค่ราว 2,000 token เพราะตอนเริ่มโหลดแค่ metadata ตัวละประมาณ 100 token

ระดับโหลดเมื่อไหร่Token costเนื้อหา
1: Metadataตลอด ตั้งแต่เริ่ม~100 token ต่อ skillname กับ description
2: Instructionsเมื่อถูก triggerไม่เกิน 5k tokenbody ของ SKILL.md
3+: Resourcesเมื่อต้องใช้0 จนกว่าจะถูกเปิดไฟล์ที่แนบมา script รันผ่าน bash และมีแค่ output ที่เข้า context
  • Trigger ได้สองทาง: user พิมพ์ /<name> หรือ Claude เห็นว่า description ตรงกับงาน
  • ที่เก็บ: ~/.claude/skills/ (ส่วนตัว) และ .claude/skills/ (ของ project) ใน Claude Code ไม่ต้อง upload
  • บน Claude API skill รันใน container ของ code execution tool จึงต้องเปิด code execution ด้วย
  • Skill สั่งให้ Claude รัน tool หรือโค้ดได้ ให้มอง skill ที่ไม่รู้ที่มาเหมือน software ที่กำลังจะติดตั้ง ต้องตรวจก่อน
เข้าใจผิดบ่อย

"ติดตั้ง skill เยอะๆ แล้ว context จะเต็ม เพราะ instruction โหลดตั้งแต่เริ่ม" ไม่ใช่ ตอนเริ่มโหลดแค่ name กับ description body โหลดตอนถูก trigger

"script ที่แนบมากิน context ตามความยาว เพราะ Claude ต้องอ่าน" ไม่ใช่ Claude รัน script ผ่าน bash มีแค่ output ที่เข้า context ตัวโค้ดไม่เข้า

สรุปสั้นๆ

Skill จ่ายแค่ ~100 token ต่อตัวจนกว่าจะถูกใช้ description ต้องบอกทั้ง what และ when เพราะเป็นตัวที่ใช้ trigger

Checkpoint 3 (เรียงลำดับ)

มี skill invoice-reconcile ที่แนบไฟล์ FX_RULES.md ไว้สำหรับเคสหลายสกุลเงิน เรียงเหตุการณ์ให้ถูก:

  1. Claude อ่าน SKILL.md ทำให้ instruction เข้า context
  2. user ขอให้กระทบยอด invoice เดือนนี้ ซึ่งเป็นเงินบาททั้งหมด
  3. Claude ทำงานจนเสร็จตามขั้นตอนใน SKILL.md
  4. ตอนเริ่ม session system prompt มี name และ description ของ skill
  5. Claude เห็นว่าไม่มีหลายสกุลเงิน จึงไม่เปิด FX_RULES.md
ดูเฉลย

d → b → a → e → c metadata มาก่อนเสมอ body โหลดหลังมีคำขอที่ตรง และไฟล์แนบระดับ 3 ถูกข้ามได้ถ้าไม่จำเป็น

Checkpoint 4

skill ของคุณไม่เคยถูกเรียกเองเลย ทั้งที่ user ถามเรื่องที่ตรงกับมัน field ไหนใน frontmatter ที่ควรเขียนใหม่ก่อน?

  1. trigger
  2. description
  3. when_to_use
  4. summary
ดูเฉลย

B Claude จับคู่คำขอกับ description field อื่นในตัวเลือกไม่ใช่ field ที่ใช้ trigger

3. MCP ไว้เชื่อมต่อ skill ไว้สอนวิธีทำ

แยกง่ายๆ: ถ้า Claude ต้องเข้าถึงระบบที่ปกติมองไม่เห็น ใช้ MCP ถ้า Claude ต้องรู้วิธีทำอะไรบางอย่าง ใช้ skill

MCPSkill
คืออะไรprotocol สำหรับต่อกับ service ภายนอกความรู้, workflow, เอกสารอ้างอิง
ให้อะไรtool และการเข้าถึงข้อมูลความรู้, workflow, reference material
ตัวอย่างโพสต์ Slack, query database, คุม browsercode review checklist, deploy workflow, API style guide

เทสต์ในชีวิตจริง: ถ้าคุณต้องก๊อปข้อมูลจาก tab browser ที่ Claude เข้าไม่ถึงมาแปะซ้ำๆ ให้ต่อระบบนั้นด้วย MCP ถ้าคุณแปะ playbook เดิมในแชทเป็นรอบที่สาม ให้ทำเป็น skill

Context cost

  • ทุกอย่างที่ถูกอ่านใน turn นับรวมใน context budget รวมถึง tool definition ด้วย
  • MCP client ส่วนใหญ่โหลด tool definition ทั้งหมดตั้งแต่แรก agent ที่ต่อ tool เป็นพันตัวอาจกินไปหลายแสน token ก่อนจะได้อ่านคำขอของ user ด้วยซ้ำ
  • Skill กินแค่ราว 100 token จนกว่าจะถูก trigger
  • Tool search ช่วยให้ Claude โหลด tool แบบ on-demand ได้

ใช้คู่กัน

MCP ให้ connection ส่วน skill สอนให้ใช้ connection นั้นให้ดี เช่น ต่อ analytics database ผ่าน MCP แล้วมี skill ที่อธิบาย schema และ query pattern ซึ่งโหลดเข้ามาเฉพาะตอนมีคำถามเรื่อง database

เข้าใจผิดบ่อย

"MCP กับ skill เป็นทางเลือกแทนกัน ต้องเลือกอย่างใดอย่างหนึ่ง" ไม่ใช่ สองอย่างแก้คนละปัญหา และถูกออกแบบมาให้ทำงานด้วยกัน

สรุปสั้นๆ

MCP = มือที่เอื้อมไปถึงระบบภายนอก skill = คู่มือว่าใช้มือนั้นยังไง MCP มักโหลด definition ทั้งหมดตั้งแต่แรก skill จ่ายแค่ metadata

Checkpoint 5

ทีม data อยากให้ Claude query BigQuery ได้ และต้องทำตาม convention ภายใน เช่น ห้าม select * และต้อง filter ด้วย partition date ทุกครั้ง แบบไหนเหมาะที่สุด?

  1. เขียน custom tool แยกตาม table
  2. MCP server อย่างเดียว แล้วยัด convention ทั้งหมดใส่ tool description
  3. MCP server สำหรับ connection บวก skill ที่อธิบาย schema และ query pattern
  4. skill อย่างเดียว ใส่ credential ไว้ใน SKILL.md
ดูเฉลย

C ต้องการทั้ง connection และ know-how skill อย่างเดียวต่อ DB ไม่ได้ (และใส่ credential ไว้ในไฟล์คือไอเดียที่แย่) ส่วนยัดทุกอย่างใน description ทำให้ทุก request ต้องจ่าย token ก้อนนั้น

Checkpoint 6

บริษัทมี bot ที่ใช้ Linear MCP server ทางการอยู่แล้ว ตอนนี้อยากให้ Claude Code สร้าง issue ใน Linear ได้ ควรทำยังไง?

  1. ต่อ Linear MCP server ตัวเดิมเข้ากับ Claude Code เพื่อใช้ tool และ authentication ที่มีอยู่
  2. เขียน custom tool ใหม่พร้อม OAuth flow ของตัวเอง
  3. เขียน skill ที่อธิบายวิธีสร้าง issue
  4. ให้ Claude ใช้ Bash ยิง curl ไปที่ API ตรงๆ
ดูเฉลย

A B ทำงานซ้ำ, skill เรียก network เองไม่ได้, ส่วน curl ผ่าน Bash ข้ามการมี schema ที่มีโครงสร้าง และจัดการ credential ได้แย่

4. เลือกระหว่าง built-in, custom tool, skill และ MCP

ไล่ถามตามลำดับต้นทุน หยุดที่ข้อแรกที่ตอบได้:

  1. Built-in tool ทำได้แล้วหรือยัง? (อ่านไฟล์ แก้ไฟล์ shell search ส่วนใหญ่ครอบคลุม)
  2. Claude ต้องเข้าถึงระบบภายนอกไหม? ถ้าใช่ ใช้ MCP
  3. Claude เข้าถึงทุกอย่างได้ แต่ทำขั้นตอนผิด? เขียน skill
  4. เขียน custom tool เฉพาะเมื่อเป็น domain action ที่ทำซ้ำ และไม่มี tool ไหนแสดงออกได้สะอาด
  5. ถ้าต้องใช้ setup เดียวกันข้ามหลาย repo ให้แพ็กเป็น plugin
Extensionให้อะไร Claudeชนะเมื่อContext cost
Built-in tool (Read, Edit, Bash, Grep)action ทั่วไปกับไฟล์ shell searchอ่าน แก้ รัน ค้นโค้ดdefinition ของ tool ที่เปิดไว้
Custom tooldomain action ที่ backed ด้วย function/API ของเราagent ทำ action นั้นซ้ำ และไม่มี built-in ที่เข้ากันdefinition ของมัน ทุก request
Skill (SKILL.md)procedure หรือ referenceมี playbook/workflow ที่ถูกแปะซ้ำdescription ทุก session, body เฉพาะตอนใช้
MCP servertool และข้อมูลจากระบบภายนอกClaude ต้องใช้ข้อมูล/action ที่เข้าถึงไม่ได้tool definition มักโหลดหมดตั้งแต่แรก
Pluginbundle ของ feature ข้างบนrepo ที่สองต้องการ setup เดียวกันเท่ากับของที่อยู่ใน bundle

Heuristic ตอนสอบ: ไม่มีระบบภายนอกและไม่มี custom logic → built-in · โจทย์พูดถึง procedure หรือ style guide → skill · มีชื่อ service (Slack, Jira, database) → MCP · มีทั้ง service และ convention การใช้ → ทั้งคู่

สรุปสั้นๆ

ไล่จากถูกไปแพง: built-in → MCP (ถ้าต้องต่อระบบนอก) → skill (ถ้าทำขั้นตอนผิด) → custom tool (domain action ซ้ำๆ) → plugin (ใช้ข้าม repo)

Checkpoint 7 (จับคู่)

จับคู่ความต้องการกับ extension (Built-in tools / MCP server / Skill / Plugin):

  1. ส่งสรุป sprint เข้า channel ใน Microsoft Teams
  2. refactor ฟังก์ชันและรันเทสต์ใน repo
  3. ทำตามขั้นตอน incident postmortem ของทีมทุกครั้ง
  4. ทีม mobile อยากได้ setup เดียวกับที่ทีม web ใช้อยู่ใน repo ของตัวเอง
ดูเฉลย

1 → MCP server · 2 → Built-in tools · 3 → Skill · 4 → Plugin

Checkpoint 8

agent ของโรงพยาบาลต้องดึงตารางเวรแพทย์จากระบบ HR ภายในที่เข้าได้ผ่าน internal REST API ที่ต้อง auth เท่านั้น ยังไม่มี MCP server หรือ SDK ใดๆ ควรทำยังไง?

  1. เขียน custom tool ที่เรียก API นั้น แล้ว register ผ่าน in-process MCP server
  2. ใช้ WebFetch ยิงไปที่ API
  3. เขียน skill ที่บอกว่าตารางเวรอยู่ที่ไหน
  4. หา community MCP server มาใช้
ดูเฉลย

A WebFetch ไม่ได้ออกแบบมาสำหรับ API ภายในที่ต้อง auth, skill ให้ข้อมูลสดไม่ได้ และ community server ไม่มีทางรู้ schema หรือมี credential ของระบบภายในเรา
