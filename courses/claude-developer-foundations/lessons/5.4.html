5.4 Claude token pricing, token counting และ usage tracking

ต้นฉบับ: CertSafari 5.4

อ่านจบแล้วควรทำได้
  • ประมาณค่าใช้จ่ายของ request จากจำนวน input/output token กับราคาต่อ MTok ของ model
  • อธิบายได้ว่า batch discount, fast mode, US-only inference และ cache multiplier เปลี่ยนราคายังไง และตัวไหนซ้อนกันได้
  • นับ input token ด้วย count_tokens ก่อนส่งจริง รวมถึงใช้เทียบ tokenizer ตอน migrate model
  • กระทบยอดค่าใช้จ่ายจริงด้วย usage field ใน response และ Usage and Cost Admin API และอ่านมันคู่กับ rate limit ได้
แนวคิดหลัก: input แยกเป็น 3 ก้อน

เมื่อใช้ prompt caching, response จะรายงาน input แยก 3 field และแต่ละ field คิดราคาคนละเรท:

  • token ที่อ่านจาก cache (cache_read_input_tokens)
  • token ที่เขียนลง cache (cache_creation_input_tokens)
  • token ที่ไม่ได้ cache หลัง breakpoint สุดท้าย (input_tokens)

ขนาด input จริงและต้นทุนจริงต้อง บวกทั้ง 3 ตัว เสมอ

1. Input กับ output ราคาไม่เท่ากัน

Claude คิดเงินเป็น token: input คือทุกอย่างที่เราส่งไปใน request ส่วน output คือทุกอย่างที่ Claude generate ออกมา แต่ละ model ตั้งราคาแยกกันเป็น USD ต่อล้าน token (MTok)

ModelInput / MTokOutput / MTok
Claude Fable 5.1$10$50
Claude Opus 5.5$4$20
Claude Sonnet 5.5$2$10
Claude Haiku 4.5$1$5

สังเกตว่า ทุก model output แพงกว่า input 5 เท่า ดังนั้นงานที่ตอบยาวอาจแพงกว่าที่ดูจากความยาว prompt เยอะ

# คำนวณค่าใช้จ่ายคร่าวๆ (ราคาต่อ MTok)
PRICE = {"claude-opus-5-5": (4, 20), "claude-haiku-4-5": (1, 5)}

def cost(model, input_tokens, output_tokens):
    inp, out = PRICE[model]
    return input_tokens / 1e6 * inp + output_tokens / 1e6 * out

# Opus 5.5: 30,000 in + 3,000 out = $0.12 + $0.06 = $0.18
print(cost("claude-opus-5-5", 30_000, 3_000))

Tool use ก็นับเป็น input

  • parameter tools ทั้งก้อน (name, description, schema)
  • ทุก block tool_use และ tool_result ที่อยู่ในบทสนทนา
  • system prompt ที่ API แอบเติมให้เมื่อมี tools

แปลว่าถ้ามี tool catalogue ใหญ่ๆ เราจ่ายค่ามันซ้ำ ทุก turn ส่วน server-side tool อย่าง web search ยังมีค่าบริการต่อครั้งเพิ่มบนค่า token อีกที

สรุปสั้นๆ

ค่าใช้จ่าย = input × ราคา input + output × ราคา output, output แพงกว่า 5 เท่า และ tool definition / tool block นับเป็น input ทุก turn

Checkpoint 1

Request บน Opus 5.5 มี 25,000 input token และ 5,000 output token ข้อไหนถูก?

  1. input แพงกว่า output 5 เท่าเพราะมี token มากกว่า 5 เท่า
  2. input กับ output มีค่าเท่ากันพอดี (คนละ $0.10)
  3. output คิดราคาเหมาต่อ request
  4. input ฟรีถ้ายังไม่เกิน context window
ดูเฉลย

B 25,000 × $4/MTok = $0.10 และ 5,000 × $20/MTok = $0.10 output แพงกว่าต่อ token 5 เท่า แต่จำนวนน้อยกว่า 5 เท่า เลยเท่ากัน

2. Modifier ที่เปลี่ยนราคาต่อ token

Modifierผลต่อราคาข้อจำกัด
Batch APIลด 50% ทั้ง input และ outputใช้กับ fast mode ไม่ได้
Fast mode (Opus 5.5)$8 input / $40 output ต่อ MTok (2 เท่า)เฉพาะ Claude API (first-party)
US-only inference_geo×1.1 ทั้ง input, output, cache write และ cache readClaude 4.6 ขึ้นไป
Cache write 5 นาที×1.25 ของราคา input ปกติคิดเฉพาะ token ที่เขียน
Cache write 1 ชั่วโมง×2 ของราคา input ปกติคิดเฉพาะ token ที่เขียน
Cache read (hit)×0.1 ของราคา input (Opus 5.5 = ×0.05, Fable 5.1 = ×0.025)คิดเฉพาะ token ที่อ่าน

Caching ทำงานยังไงแบบย่อ

ส่วนต้นของ prompt ที่คงที่ (prefix) cache ได้ เราวาง breakpoint ด้วย cache_control เพื่อบอกว่า prefix จบตรงไหน ถ้า prefix ถึง breakpoint มีใน cache แล้ว token ส่วนนั้นจะคิดเป็น cache read ถ้ายังไม่มี ระบบประมวลผลทั้ง prompt แล้วเก็บ prefix เป็น cache write (TTL default ของ ephemeral คือ 5 นาที ตั้งเป็น "1h" ได้)

system=[{
    "type": "text",
    "text": MANUAL_40K_TOKENS,                     # เอกสารยาวที่ใช้ซ้ำ
    "cache_control": {"type": "ephemeral", "ttl": "1h"},  # breakpoint + TTL 1 ชั่วโมง
}]

อะไรซ้อนกันได้บ้าง

  • Cache multiplier ซ้อนกับ Batch discount และ data residency ได้ ดังนั้น batch ที่อ่าน cached prefix ได้ส่วนลด ทั้งสองต่อ (แต่ cache hit ใน batch เป็นแบบ best-effort)
  • Fast mode ซ้อนกับ caching และ data residency ได้ แต่ซ้อนกับ batch ไม่ได้
  • ความยาว context ไม่ใช่ modifier: Claude 4.6 ขึ้นไปคิดราคาเรทปกติตลอด window 1M token request ยาวแพงกว่าแค่เพราะมี token มากกว่าเท่านั้น
สรุปสั้นๆ

Batch −50%, fast mode ×2, US-only ×1.1, cache write ×1.25 (5m) / ×2 (1h), cache read ×0.1 (Opus 5.5 ×0.05, Fable 5.1 ×0.025) ซ้อนกันได้หมด ยกเว้น fast mode + batch

ลองเดาก่อน

งาน nightly batch ที่ทุก request ใช้ system prompt ยาวชุดเดียวกันและ cache ไว้ ส่วนลด batch กับส่วนลด cache read จะเป็นยังไง?

ดูเฉลย

ซ้อนกันได้ ได้ทั้งสองต่อ (ไม่ใช่เลือกเอาอันที่ลดมากกว่า และไม่ใช่ว่า batch ใช้ cache ไม่ได้) แค่ cache hit ใน batch ไม่การันตี 100%

Checkpoint 2

ทีมอยากลดต้นทุนให้สุดแล้วลองจับคู่ option ต่างๆ คู่ไหน ใช้ด้วยกันไม่ได้?

  1. Caching + Batch API
  2. US-only inference_geo + caching
  3. Fast mode + Batch API
  4. Fast mode + caching
ดูเฉลย

C fast mode ส่งผ่าน Batch API ไม่ได้ คู่อื่นซ้อนกันได้ทั้งหมด

Checkpoint 3

ระบบ Q&A กฎหมายใช้ cache_control: {"type": "ephemeral"} (TTL default) กับเอกสารสัญญา 60,000 token ทนายถามคำถามเป็นช่วงๆ ห่างกันราว 15 นาที ผลคือแทบไม่เคยได้ cache read และจ่ายค่า cache write ซ้ำไปเรื่อยๆ ควรแก้ยังไง?

  1. ตั้ง TTL ของ cache_control เป็น "1h"
  2. ยิง request เปล่าทุก 5 นาทีเพื่อ "อุ่น" cache
  3. แบ่งเอกสารเป็นหลาย breakpoint
  4. ใช้ model ที่ context window ใหญ่ขึ้นเพื่อให้ server จำได้นานขึ้น
ดูเฉลย

A TTL default คือ 5 นาที สั้นกว่าช่วงห่าง 15 นาที ตั้ง 1h (cache write ×2) จะครอบคลุม B ไม่ใช่กลไกที่ใช้ยืดอายุ cache, C เปลี่ยนแค่ความละเอียดแต่ทุกชิ้นยังหมดอายุใน 5 นาที, D context window เป็นขนาดสูงสุดต่อ request ไม่เกี่ยวกับการเก็บ cache

3. นับ token ก่อนส่งจริง

  • Endpoint count_tokens คืนค่า input_tokens ของ request โดยไม่รัน model
  • รับ input หน้าตาเดียวกับ messages.create: system prompt, tools, รูปภาพ และ PDF
  • ใช้ประมาณต้นทุน: นับ request ตัวแทนหนึ่งตัว แล้วคูณกับ volume ที่คาดไว้
  • ใช้ฟรี แต่มี requests-per-minute limit ของตัวเองตาม usage tier
count = client.messages.count_tokens(
    model="claude-opus-5-5",
    system="คุณคือผู้ช่วยด้านภาษี",
    messages=[{"role": "user", "content": "ลดหย่อนอะไรได้บ้าง"}],
)
print(count)   # {"input_tokens": ...} ไม่มีการ generate ไม่เสียค่า token

# ประมาณงบรายเดือน: request ตัวแทน x volume
monthly_input = count.input_tokens * 500_000

ข้อจำกัดของการนับ

  1. ไม่สนใจ caching: ใส่ cache_control ไปได้ แต่ผลที่ได้คือขนาด input ดิบ ไม่ใช่ต้นทุนหลังหักส่วนลด cache
  2. บาง input ถูก reject: server tool ส่วนใหญ่, MCP connector และ image/document block ที่อ้างแหล่งด้วย URL หรือ file ถ้าอยากให้นับรูปหรือ PDF ให้ส่งเป็น base64
  3. ขึ้นกับ model: Fable 5.1, Mythos 5.1, Fable 5 และ Mythos 5 ใช้ tokenizer ที่มากับ Opus 4.7 prompt เดียวกันจะออกมาใหญ่ขึ้นราว 30% เมื่อเทียบกับ model รุ่นเก่า ตัวเลขเก่าจึงประเมินต้นทุนต่ำไป

วิธีเช็กตอน migrate model

# นับ request เดียวกันด้วย 2 model แล้วเทียบ
for m in ["claude-sonnet-5-5", "claude-fable-5-1"]:
    n = client.messages.count_tokens(model=m, messages=msgs).input_tokens
    print(m, n)   # tokenizer ต่างกัน ตัวเลขอาจต่างกันเป็นสิบเปอร์เซ็นต์
เข้าใจผิดบ่อย

"นับ token ไว้แล้วบน model เก่า ย้ายไป model ใหม่ก็ใช้ตัวเลขเดิมได้" ไม่ใช่ endpoint นับด้วย tokenizer ของ model ที่เราส่งไป ต้องนับใหม่ทั้งสอง model แล้วเทียบกัน

สรุปสั้นๆ

count_tokens = ฟรี ไม่รัน model คืน input_tokens แต่ไม่คิด cache, ไม่รับ URL/file source และตัวเลขผูกกับ tokenizer ของ model

Checkpoint 4 (เติมคำ)

อยากรู้จำนวน input token โดยไม่ให้ model generate อะไร ใช้ client.messages.________(...)

ดูเฉลย

count_tokens (ไม่ใช่ token_count, estimate หรือ create)

Checkpoint 5

ทีมเอา prompt 80,000 token ที่มี cache_control breakpoint บน prefix ซึ่ง cache ไว้แล้ว ไปเรียก count_tokens ผลที่ได้คืออะไร?

  1. 80,000 × อัตรา cache read
  2. ขนาด input เต็มทั้งหมด เพราะการนับไม่ใช้ logic ของ caching
  3. เฉพาะ token หลัง breakpoint
  4. error เพราะ count_tokens ไม่รับ cache_control
ดูเฉลย

B count_tokens รับ cache_control ได้ แต่คืนขนาด input ดิบเสมอ ไม่ได้คำนวณราคาหลัง cache

4. ติดตามค่าใช้จ่ายจริงและ rate limit

Usage field ในทุก response

Fieldความหมาย
cache_read_input_tokenstoken ที่อ่านมาจาก cache
cache_creation_input_tokenstoken ที่เขียนลง cache ใน request นี้
input_tokenstoken ที่ไม่ได้ cache หลัง breakpoint สุดท้าย

พลาดกันบ่อยคือ log แค่ input_tokens สมมติ cache เอกสาร 200,000 token แล้วถามคำถาม 50 token, field นี้จะโชว์ 50 ทั้งที่จริงส่งไป 200,050 token

u = resp.usage
total_input = (u.input_tokens
               + u.cache_read_input_tokens
               + u.cache_creation_input_tokens)   # ต้องบวกครบ 3 ตัว
log.info("usage", total_input=total_input, output=u.output_tokens)

Usage and Cost Admin API

  • ดูยอดรวมระดับ organization ต้องใช้ Admin API key
  • /v1/organizations/usage_report/messages คืน token count เป็น bucket 1m, 1h หรือ 1d
  • filter / group ได้ตาม model, workspace, API key, service tier, inference_geo, speed
  • cost report คืนยอดเป็น USD เอาไว้กระทบยอดกับระบบบัญชีภายใน
  • หน้า Usage และ Cost ใน Console แสดงข้อมูลคล้ายกันและ export CSV ได้
# token รายวันของเดือนนี้ แยกตาม workspace
curl "https://api.anthropic.com/v1/organizations/usage_report/messages?\
starting_at=2026-10-01T00:00:00Z&ending_at=2026-10-26T00:00:00Z&\
group_by[]=workspace_id&bucket_width=1d" \
  -H "anthropic-version: 2023-06-01" \
  -H "x-api-key: $ANTHROPIC_ADMIN_KEY"   # ต้องเป็น Admin key ไม่ใช่ key ปกติ

เชื่อมกับ rate limit

  • model ส่วนใหญ่นับ input_tokens + cache_creation_input_tokens เข้า ITPM (input tokens per minute)
  • cache_read_input_tokens ไม่นับ เข้า ITPM
  • cache hit rate สูง = ประหยัดเงินและลดแรงกด ITPM ไปพร้อมกัน
  • หน้า Usage ใน Console มีกราฟ peak ITPM รายชั่วโมงเทียบกับ cache rate และ limit ปัจจุบัน
เข้าใจผิดบ่อย

"input_tokens คือขนาด input ทั้งหมดของ request" ไม่ใช่ มันคือเฉพาะ token ที่ไม่ได้ cache หลัง breakpoint สุดท้าย ยอดรวม = input_tokens + cache_read_input_tokens + cache_creation_input_tokens

สรุปสั้นๆ

Log usage ให้ครบ 3 field, ใช้ Admin API (usage_report + cost report) กระทบยอดระดับ org และจำไว้ว่า cache read ไม่กิน ITPM

Checkpoint 6 (จับคู่)

จับคู่ field กับความหมาย:

  1. cache_read_input_tokens
  2. cache_creation_input_tokens
  3. input_tokens
  1. token หลัง breakpoint สุดท้ายที่ไม่ได้ cache
  2. token ของ prefix ที่ได้จาก cache entry ที่มีอยู่แล้ว
  3. token ที่ถูกเขียนลง cache ที่ breakpoint ใน request นี้
ดูเฉลย

1 → b · 2 → c · 3 → a

Checkpoint 7

Dashboard ภายในแสดงว่าแต่ละ request ใช้ input แค่ ~100 token แต่บิลกับกราฟ ITPM ไม่สอดคล้องกันเลย แอปนี้ cache knowledge base ขนาดใหญ่ไว้ใน system prompt ปัญหาน่าจะอยู่ตรงไหน?

ดูเฉลย

Dashboard อ่านแค่ input_tokens ซึ่งเป็นแค่ส่วนที่ไม่ได้ cache ต้องบวก cache_read_input_tokens และ cache_creation_input_tokens ด้วย และตอนดู ITPM จำไว้ว่า cache write นับ แต่ cache read ไม่นับ
