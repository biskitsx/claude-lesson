8.2 MCP server primitives: tools, resources และ prompts

ต้นฉบับ: CertSafari 8.2

อ่านจบแล้วควรทำได้
  • อธิบายบทบาทของ host, client และ server ใน MCP ได้
  • อธิบายว่า server ประกาศ feature ผ่าน capability declaration ยังไง
  • นิยาม tool ด้วย inputSchema ที่ถูกต้อง และคืนผลแบบ text หรือ structured ได้
  • expose resource และ resource template ได้ และรู้วิธีป้องกัน resource แบบ file://
  • publish prompt ที่มี parameter และคืน error code ที่ถูกต้อง
  • เลือกระหว่าง stdio กับ Streamable HTTP และรู้ว่าทำไม stdout ของ stdio server ต้องสะอาด
แนวคิดหลัก: server เล็ก ทำเรื่องเดียว ให้ 3 อย่าง

MCP server คือโปรแกรมเล็กๆ ที่ให้ host 3 อย่าง: tools ที่โมเดลเรียกได้, resources ที่เป็น context และ prompts ที่เป็น message template ใช้ซ้ำได้ host เป็นคนคุมบทสนทนาเสมอ server แค่ตอบ request ที่ส่งมาถึงมัน

1. Host, client และ server

สามคำนี้สับสนง่าย ลองนึกเป็นออฟฟิศ: host คือตัวบริษัท client คือพนักงานประสานงานที่แต่ละคนดูแลซัพพลายเออร์ได้เจ้าเดียว ส่วน server คือซัพพลายเออร์

บทบาทคืออะไรหน้าที่
Hostแอปที่ user ใช้ เช่น Claude Code หรือ agent ที่เราเขียนสร้างและจัดการ client หลายตัว, บังคับใช้ security policy และ user consent, ตัดสินเรื่อง authorization, ประสานงานกับ LLM
Clientอยู่ข้างใน hostถือ connection กับ server ได้ ตัวเดียวเท่านั้น, แนบ protocol version และ capability ไปกับ request, ส่ง message ไปกลับ, กั้นไม่ให้ server เห็นกันเอง
Serverlocal process หรือ remote serviceexpose tools, resources, prompts

หลักการออกแบบ: server ต้องสร้างง่าย ต่อกันได้ (composable) และมองไม่เห็นบทสนทนาทั้งหมดหรือ server ตัวอื่น ได้รับแค่ context ที่จำเป็นต่อหน้าที่ของมัน

สรุปสั้นๆ

Host คุมทุกอย่างและถือ consent, client หนึ่งตัวต่อ server หนึ่งตัว, server เห็นแค่ส่วนของตัวเอง

Checkpoint 1 (จับคู่)

จับคู่หน้าที่กับบทบาท (Host / Client / Server):

  1. ถาม user ก่อนอนุญาตให้ลบไฟล์ และเปิด connection ไปหา server 4 ตัว
  2. ให้ tool query_sales และ resource เป็นไฟล์ schema ของ DB
  3. คุยกับ server Postgres ตัวเดียว ส่งต่อ message ไปกลับ
ดูเฉลย

1 → Host (consent + จัดการ client หลายตัว) · 2 → Server · 3 → Client

2. Capability declaration: ต้องประกาศก่อนถึงจะใช้ได้

ใน MCP feature ไม่ได้ถูก "เดา" แต่ถูก negotiate ตอนเริ่ม connection server ประกาศว่ามีอะไร เช่น รองรับ tools, resource subscription, prompt template ส่วน client ก็ประกาศของตัวเอง เช่น sampling และ elicitation

กฎสำคัญ: feature ไหนที่ server implement ไว้ ต้องประกาศ ถ้ามี handler ของ tool ครบแต่ไม่ได้ประกาศ capability tools ก็ไม่มีใครเรียก tool นั้นได้

{
  "capabilities": {
    "tools":     { "listChanged": true },              // แจ้ง client เมื่อรายการ tool เปลี่ยน
    "resources": { "subscribe": true, "listChanged": true },
    "prompts":   { "listChanged": true }
  }
}

listChanged: true คือสัญญาว่า server จะส่ง notification เมื่อชุด tool เปลี่ยน แล้ว client จะไป fetch list ใหม่ resources กับ prompts ใช้ pattern เดียวกันใต้ key ของตัวเอง

เข้าใจผิดบ่อย

"เขียน handler แล้วก็พอ capability ประกาศหรือไม่ก็ได้" ไม่ใช่ การเรียก tool ต้องมี capability tools ประกาศไว้

"stdio server พิมพ์ debug ออก stdout ได้ เดี๋ยว client ก็ข้ามข้อความที่ไม่รู้จักเอง" ไม่ใช่ stdout คือท่อของ protocol ข้อความที่ไม่ใช่ MCP จะทำให้ stream พัง ให้ log ไป stderr

Checkpoint 2

ทีมเขียน server ที่ handle tools/call ครบ แต่ใน capabilities มีแค่ resources ผลคืออะไร?

  1. ใช้ได้ปกติ เพราะ capability เป็นแค่ hint
  2. client จะเจอ tool เองผ่าน tools/list
  3. เรียก tool ไม่ได้ เพราะ server ต้องประกาศ capability tools ก่อน
  4. ใช้ได้ แค่จะไม่มี notification เมื่อ tool เปลี่ยน
ดูเฉลย

C feature ต้องถูก advertise ก่อนถึงจะถูกใช้ ไม่ใช่แค่ listChanged ที่ต้องประกาศ

Transport: stdio vs Streamable HTTP

stdio (server ที่รันบนเครื่อง)

  • client launch server เป็น child process server อ่าน JSON-RPC จาก stdin และเขียนออก stdout
  • แต่ละ message คั่นด้วย newline และห้ามมี newline อยู่ข้างใน
  • stdout ต้องมีแค่ MCP message ที่ถูกต้อง log ทั้งหมดไป stderr ซึ่ง client อาจเก็บ ส่งต่อ หรือทิ้งก็ได้ และไม่ควรถือว่า stderr คือ error โดย default
  • ตอนปิด: client ปิด input stream ของ child, รอให้ exit, ถ้าไม่ยอมจบก็ force kill
  • ฝั่ง SDK ใช้ StdioServerTransport
# คำหลัง -- คือ process ที่ Claude Code จะ spawn
claude mcp add --transport stdio inventory -- node ./inventory-server.js
// ใน stdio server: ห้าม console.log เด็ดขาด
console.error("server started");   // ไป stderr ปลอดภัย
// console.log("debug!");          // ไป stdout = ทำ protocol พัง

Streamable HTTP (remote server)

  • เป็น service ที่รันอยู่แล้ว มี HTTP endpoint เดียวรับ POST
  • ทุก JSON-RPC request หรือ notification คือ POST หนึ่งครั้ง server ตอบเป็น JSON object เดียว หรือเป็น SSE stream
  • Claude Code config ยังรับ transport sse แบบเก่า และ entry ws ด้วย
claude mcp add --transport http billing https://mcp.example.com/mcp

จำง่ายๆ: stdio = client เป็นคนเปิด server เอง ส่วน HTTP = client ไปต่อกับ server ที่รันอยู่แล้ว

สรุปสั้นๆ

ประกาศ capability ทุก feature ที่มี, stdio ใช้ในเครื่องและ stdout ต้องสะอาด, HTTP ใช้กับ remote ที่ POST ทีละ message

3. Tools

Field ของ tool ใน MCP:

  • name ต้อง unique, ยาว 1–128 ตัว, case-sensitive, ใช้ได้แค่ ASCII ตัวอักษร ตัวเลข _ - และ .
  • title (optional), description
  • inputSchema ต้องเป็น JSON Schema object ที่ valid ห้ามเป็น null ถ้าไม่มี $schema จะถือเป็น JSON Schema 2020-12
  • outputSchema, annotations, icons (optional ทั้งหมด)

Tool ที่ไม่มี parameter เลยก็ยังต้องมี schema ให้เขียนแบบนี้:

{
  "name": "get_server_time",
  "description": "คืนเวลาปัจจุบันของ server",
  "inputSchema": { "type": "object", "additionalProperties": false }   // ไม่ใช่ null และห้ามละไว้
}

Discovery, invocation และผลลัพธ์

  • tools/list ไว้หา tool (มี pagination ด้วย cursor)
  • tools/call ไว้เรียก โดยส่ง name กับ arguments
  • ผลลัพธ์มี content array ที่เป็น text, image, audio, resource_link หรือ resource แบบ embedded พร้อม flag isError
  • ถ้าประกาศ outputSchema ไว้ server ต้องคืน structuredContent ที่ตรง schema
// request
{"jsonrpc": "2.0", "id": 7, "method": "tools/call",
 "params": {"name": "check_stock", "arguments": {"sku": "TSHIRT-M"}}}

// result
{"jsonrpc": "2.0", "id": 7,
 "result": {"content": [{"type": "text", "text": "TSHIRT-M เหลือ 42 ตัว"}], "isError": false}}

Stateful tool

ถ้า tool คืน handle เช่น cart_id ให้บอก retention policy ไว้ใน description ของ tool ที่สร้าง handle นั้น (เช่น "หมดอายุใน 30 นาที") และถ้ามีคนส่ง handle ที่หมดอายุหรือไม่รู้จักมา ให้คืน tool execution error (isError: true) เพื่อให้โมเดลรู้ตัวและ recover ได้

ฝั่ง host ก็มีหน้าที่: ให้ human อยู่ใน loop ด้วยการแสดงว่ามี tool อะไรบ้าง โชว์ตอนถูกเรียก และขอยืนยันก่อนทำ operation

เข้าใจผิดบ่อย

"tool ไม่มี parameter ก็ตั้ง inputSchema เป็น null หรือไม่ใส่ก็ได้" ไม่ใช่ ต้องเป็น object schema ที่ valid เสมอ

สรุปสั้นๆ

list ด้วย tools/list เรียกด้วย tools/call ผลเป็น content array + isError และ inputSchema ห้ามว่าง

Checkpoint 3

client อยากสั่งให้ server รัน tool resize_image ต้องใส่ "method" เป็นอะไร?

  1. tools/execute
  2. tools/list
  3. tools/call
  4. tools/run
ดูเฉลย

C tools/list ไว้หา tool ส่วนอีกสองชื่อไม่มีใน spec

4. Resources

Resource คือ "ข้อมูลให้อ่าน" ไม่ใช่ "action ให้ทำ" เช่น ไฟล์ config, schema ของ DB, เอกสาร

  • Field: uri (ตัวระบุ), name, และ optional title, description, mimeType, size, icons
  • Method: resources/list, resources/read และ resources/templates/list สำหรับ URI template เช่น file:///{path}
  • ผลของ read: แต่ละรายการใน contents มีได้ทั้ง text หรือ blob ที่เป็น base64
  • Annotation: audience (user และ/หรือ assistant), priority (0.0–1.0), lastModified
  • Capability flag: listChanged (แจ้งเมื่อชุด resource เปลี่ยน) และ subscribe (แจ้งเมื่อ resource ตัวใดตัวหนึ่งถูกอัปเดต ผ่าน subscriptions/listen)
{"jsonrpc": "2.0", "id": 3, "method": "resources/read",
 "params": {"uri": "file:///project/config/app.yaml"}}

หน้าที่ของ server เรื่องความปลอดภัย

  • validate ทุก URI
  • encode binary ให้ถูก
  • ทำ access control กับ resource ที่ sensitive
  • สำหรับ file:// ต้อง sanitize path กัน directory traversal (เช่น ../../etc/passwd)
from pathlib import Path
ROOT = Path("/srv/docs").resolve()

def safe_path(user_path: str) -> Path:
    p = (ROOT / user_path).resolve()
    if not p.is_relative_to(ROOT):        # หลุดออกนอก ROOT = ปฏิเสธ
        raise ValueError("path ไม่ได้รับอนุญาต")
    return p

ถ้าหา resource ไม่เจอ ให้คืน error -32602 พร้อมใส่ URI ไว้ใน data

สรุปสั้นๆ

Resource คือ context ที่อ่านผ่าน URI ใช้ template ได้ และถ้าเป็นไฟล์ ต้อง sanitize path ทุกครั้ง

Checkpoint 4

server เปิด resource template file:///{path} ให้ client อ่านไฟล์ในโฟลเดอร์ docs ข้อไหนคือสิ่งที่ต้องทำ?

  1. ตั้ง priority เป็น 1.0 ให้ทุกไฟล์
  2. sanitize path เพื่อกัน directory traversal
  3. เปิด subscribe: true ให้ทุกไฟล์
  4. คืนทุกไฟล์เป็น base64 blob เท่านั้น
ดูเฉลย

B ข้ออื่นเป็นแค่ option หรือไม่จำเป็น text ไฟล์คืนเป็น text ได้ ไม่ต้องเป็น blob

5. Prompts

Prompt คือ template ที่มีชื่อ และมี arguments ได้ (แต่ละตัวมี name, description, required) เหมือน slash command สำเร็จรูปที่ server เตรียมไว้ให้

  • prompts/list ไว้หาว่ามี prompt อะไร
  • prompts/get ส่ง argument ไป แล้วได้ messages กลับมา
  • แต่ละ message มี role (user หรือ assistant) และ content เป็น text, image, audio, resource link หรือ embedded resource ได้
// request
{"jsonrpc": "2.0", "id": 9, "method": "prompts/get",
 "params": {"name": "summarize_incident", "arguments": {"incident_id": "INC-2041"}}}

// result
{"jsonrpc": "2.0", "id": 9,
 "result": {"messages": [{"role": "user",
   "content": {"type": "text", "text": "สรุป incident INC-2041 ให้หัวหน้าทีมอ่าน..."}}]}}

Error code ที่ต้องจำ

server ควร validate argument ก่อนทำอะไร:

  • ชื่อ prompt ไม่มีอยู่จริง หรือขาด required argument → -32602 (Invalid params)
  • พังจากข้างใน server เอง → -32603 (Internal error)

ตารางเทียบ 3 primitive

Toolstools/listtools/callnotifications/tools/list_changed
Resourcesresources/list, resources/templates/listresources/readnotifications/resources/list_changed, notifications/resources/updated
Promptsprompts/listprompts/getnotifications/prompts/list_changed
สรุปสั้นๆ

Prompt = template ที่ get แล้วได้ messages กลับมา ขาด argument หรือชื่อผิดคือ -32602 พังข้างในคือ -32603

Checkpoint 5

client เรียก prompts/get ชื่อ summarize_incident แต่ลืมส่ง incident_id ซึ่งเป็น required server ควรตอบอะไร?

  1. messages เป็น array ว่าง
  2. error -32601 Method not found
  3. error -32603 Internal error
  4. error -32602 Invalid params
ดูเฉลย

D method มีอยู่จริง และ server ไม่ได้พังข้างใน แค่ input ไม่ครบ จึงเป็น Invalid params
