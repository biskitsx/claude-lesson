5.3 Choosing a Claude model: capability, latency และ cost (tiers, effort, fast mode)

ต้นฉบับ: CertSafari 5.3

อ่านจบแล้วควรทำได้
  • จับคู่ workload กับ tier ของ Claude ที่เหมาะ โดยดูจาก latency, ราคา และ capability
  • เลือกได้ว่าจะ "เริ่มเล็กแล้วขยับขึ้น" หรือ "เริ่มเก่งแล้วลดลง"
  • ใช้ effort เพื่อแลกความละเอียดกับจำนวน token บน model ตัวเดิม
  • อธิบายได้ว่า fast mode เปลี่ยนอะไร แพงขึ้นเท่าไหร่ และ model ไหนรองรับ
แนวคิดหลัก: capability–speed–cost tradeoff

ทุกการเลือก model คือการบาลานซ์ 3 อย่าง: เก่งแค่ไหน ตอบเร็วแค่ไหน และแพงแค่ไหน เราขยับจุดบาลานซ์ได้ 2 ทาง คือ เปลี่ยน tier หรือ อยู่ model เดิมแต่ปรับ effort / เปิด fast mode

1. Lineup ปัจจุบันและบทบาทของแต่ละ tier

ทั้ง 4 model รองรับ input เป็น text + image, output เป็น text, vision และ tool use ได้หมด คำถามจริงเลยไม่ใช่ "ทำได้ไหม" แต่เป็น "ทำได้ดีแค่ไหน เร็วแค่ไหน และจ่ายเท่าไหร่"

Thinking 2 แบบ

  • Adaptive thinking: Claude ตัดสินเองทีละ request ว่าจะคิดไหมและคิดเยอะแค่ไหน ถามเรื่องง่ายๆ อาจตอบเลยโดยไม่ think
  • Extended thinking: โหมด manual เรากำหนด budget ของ thinking token เองต่อ request ผ่าน budget_tokens ในตารางนี้มีแค่ Haiku 4.5 ที่ใช้แบบนี้

แต่ละ tier เกิดมาเพื่ออะไร

  • Fable 5.1: เก่งสุด สำหรับ agent session ยาวๆ และ deep research หลายขั้นที่จบด้วยเอกสารสำเร็จรูป
  • Opus 5.5: จุดเริ่มต้นของ workload ส่วนใหญ่ เหมาะกับ coding agent ที่รันเองหลายชั่วโมง, refactor ขนาดใหญ่, งานหนัก vision และ computer use
  • Sonnet 5.5: บาลานซ์ความเร็วกับความเก่ง สำหรับ code generation ประจำวัน, data analysis, agentic tool use
  • Haiku 4.5: latency และราคาต่ำสุด สำหรับงาน real-time, ประมวลผลปริมาณมาก และงาน sub-agent

ตัวเลขที่ควรจำ: output token ของ Fable แพงกว่า Haiku 10 เท่า ($50 vs $5) และ Haiku มี context window (200K) กับ max output (64K) เล็กกว่าอีก 3 ตัว (1M / 128K)

เข้าใจผิดบ่อย

"ต้องใช้ Sonnet ขึ้นไปถึงจะทำ tool use ได้" ไม่ใช่ ทุก model ปัจจุบันรองรับ tool use ไม่ใช่ตัวแยก tier

สรุปสั้นๆ

Fable = เก่งสุด/แพงสุด, Opus = จุดเริ่มทั่วไป, Sonnet = สายกลาง, Haiku = เร็วสุด/ถูกสุด (context เล็กกว่า, ใช้ extended thinking, ไม่มี effort)

Checkpoint 1

บริษัท e-commerce ต้องติด tag ให้รีวิวสินค้าสั้นๆ วันละหลายล้านรีวิว (บวก / ลบ / กลาง) แบบ real-time งบจำกัดและ latency ต้องต่ำ ควรเลือก model ไหน?

  1. Opus 5.5 เพราะเป็นจุดเริ่มต้นของงานส่วนใหญ่
  2. Sonnet 5.5 เพราะต้องใช้ tool use
  3. Haiku 4.5
  4. Fable 5.1 เพื่อความแม่นยำสูงสุด
ดูเฉลย

C งานง่าย ปริมาณมหาศาล ต้องเร็วและถูก ตรงกับ Haiku 4.5 ส่วน B อ้างเรื่อง tool use ซึ่งทุก model ทำได้

Checkpoint 2

ทีมทำ voice assistant ในแอปธนาคาร ต้องเริ่มตอบภายในเสี้ยววินาที คนใช้เยอะมาก งบตึง แต่ยังต้องให้เหตุผลได้พอสมควร (เช่น อธิบายค่าธรรมเนียม) tier ไหนเหมาะสุด?

  1. Haiku 4.5
  2. Opus 5.5
  3. Sonnet 5.5
  4. Fable 5.1
ดูเฉลย

A เลือก tier ที่เร็วและถูกที่สุดที่ยังให้เหตุผลได้ตามโจทย์ ตัวอื่นแพงหรือช้าเกินความจำเป็น

2. สองวิธีในการเลือก model ตั้งต้น

แนวทางเหมาะกับทำยังไง
Start small, step upprototype, latency budget ตึง, งานที่ไวต่อต้นทุน, งานง่ายปริมาณมากเริ่มที่ Haiku 4.5 แล้วขยับขึ้นเมื่อเจอ capability gap ที่ชี้ชัดได้เท่านั้น
Start capable, step downreasoning ซับซ้อน, งานวิทย์/คณิต, ความเข้าใจละเอียดอ่อน, coding ขั้นสูง, ความถูกต้องสำคัญกว่าต้นทุนเริ่มที่ Opus 5.5 จูน prompt ให้เข้าที่ แล้วค่อยลด effort หรือย้ายไป model ถูกลงทีหลัง

ถ้า Opus 5.5 ที่ effort xhigh หรือ max แล้วยังไม่พอสำหรับงานหนักจริงๆ ค่อยขยับขึ้นไป Fable 5.1

ไม่ว่าทางไหน eval เป็นตัวตัดสิน

  • สร้าง benchmark จาก prompt และข้อมูลจริงของเรา
  • เทียบ model ในเรื่อง accuracy, คุณภาพคำตอบ และ edge case
  • เทียบ cost per completed task ไม่ใช่ cost per token เพราะ model ที่ต่อ token แพงกว่าอาจทำงานเสร็จในรอบเดียว ขณะที่ตัวถูกต้องวนหลายรอบ
  • ผลวัดของ Anthropic: model รุ่นใหม่แก้โจทย์ได้อย่างน้อยเท่ารุ่นก่อนเสมอ และมักมี cost per solved task ต่ำกว่า
สรุปสั้นๆ

งานง่าย/ไวต่อเงิน → เริ่ม Haiku แล้วขึ้น งานยาก/ต้องแม่น → เริ่ม Opus 5.5 แล้วลง และวัดด้วย eval ที่ดู cost per completed task

Checkpoint 3 (เรียงลำดับ)

เรียงขั้นตอนของแนวทาง start small ให้ถูก:

  1. ประเมินว่า performance ผ่าน requirement ไหม
  2. อัปเกรด model เมื่อเจอ capability gap ที่ชัดเจนเท่านั้น
  3. เริ่ม implement ด้วย Haiku 4.5
  4. เทสต์ use case ให้ทั่ว
ดูเฉลย

c → d → a → b เริ่มเล็ก เทสต์ ประเมิน แล้วค่อยขยับขึ้นเฉพาะเมื่อมีหลักฐานว่าไม่พอ

3. Effort: จูน model ตัวเดิมแทนการเปลี่ยน model

Effort คือปุ่มบอกว่าให้ model "ใช้ token ไปกับคำตอบนี้มากแค่ไหน" แลกระหว่างความละเอียดถี่ถ้วนกับความประหยัด token

  • ตั้งต่อ request ที่ output_config.effort
  • มี 5 ระดับจากต่ำไปสูง: low, medium, high, xhigh, max
  • มีผลกับ output token ทั้งหมด: text, tool call และ argument ของมัน รวมถึง thinking ถ้ามีการ think
  • effort ต่ำ = ประหยัดเวลาและเงิน แต่เสีย capability ไปบ้าง ส่วน max ให้ capability สูงสุด
resp = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=4096,
    output_config={"effort": "low"},   # ลด effort เพื่อลดค่า token
    messages=[{"role": "user", "content": "สรุป PR นี้สั้นๆ"}],
)

Default effort และจุดเริ่มต้น

  • model ส่วนใหญ่ default เป็น high (เช่น Fable 5.1 และ Opus 5)
  • Opus 5.5 default เป็น medium ให้เริ่มที่นั่น
  • บน Opus 4.8 และ 4.7 ค่าที่ แนะนำ สำหรับ coding และ agentic work ส่วนใหญ่คือ xhigh แม้จะไม่ใช่ default
  • Haiku 4.5 ไม่รองรับ effort

กฎตัดสินใจ

อาการทำอะไร
แพงไป แต่คุณภาพโอเคลด effort บน model เดิม
ลด effort แล้วคุณภาพตกคืน effort กลับระดับเดิม
คุณภาพยังไม่พอ และยังไม่เคยลด effortลอง tier ถัดขึ้นไปที่ low effort ก่อน ค่อยตัดสินใจใช้ model ใหญ่ที่ default
เข้าใจผิดบ่อย

"อยากลดค่าใช้จ่าย ให้ย้ายไป model ถูกกว่าก่อน" ไม่ใช่ ลด effort บน model ที่ใช้อยู่ก่อน แล้วย้าย model เฉพาะเมื่อ eval บอกว่าจำเป็น

"งาน autonomous coding สำคัญๆ บน Opus 4.8 ใช้ default หรือ max ไปเลย" ไม่ใช่ ค่าที่แนะนำคือ xhigh

สรุปสั้นๆ

Effort อยู่ที่ output_config.effort มี low → max คุมทุก output token Opus 5.5 เริ่ม medium, Haiku ไม่มี effort และปัญหาเรื่องเงินให้ลด effort ก่อนเปลี่ยน model

ลองเดาก่อน

Agent บน Opus 5.5 ตอบดี แต่บิลรายเดือนสูงเกินงบ ขั้นแรกควรทำอะไร: ย้ายไป Haiku, เปิด fast mode หรือลด effort?

ดูเฉลย

ลด effort บน Opus 5.5 ก่อน fast mode ทำให้ แพงขึ้น ส่วนการย้ายไป Haiku เสี่ยงคุณภาพตกโดยยังไม่มีหลักฐานจาก eval

Checkpoint 5

ทีม platform จะปล่อย agent ให้ migrate monorepo ขนาดใหญ่ไปใช้ framework ใหม่ รันเองต่อเนื่องหลายชั่วโมง ในกลุ่ม model รุ่นก่อน ตัวเลือกไหนตรงคำแนะนำที่สุด?

  1. Opus 4.8 ที่ effort xhigh
  2. Sonnet 5 ที่ effort low เพื่อความเร็ว
  3. Haiku 4.5 ปิด extended thinking
  4. Opus 4.8 แล้วปรับ temperature ให้สูงขึ้นเพื่อความสร้างสรรค์
ดูเฉลย

A งาน coding ยาวๆ แบบ agentic บน Opus 4.8 แนะนำ xhigh ส่วน D จะโดน 400 เพราะ Opus 4.8 ไม่รับค่า temperature, top_p, top_k ที่ไม่ใช่ default

4. Fast mode: model เดิม แต่ output ไหลเร็วขึ้น

  • รัน model ตัวเดิม บน inference configuration ที่เร็วกว่า weights, พฤติกรรม และ capability ไม่เปลี่ยน
  • เพิ่ม output tokens per second ได้ถึง 2.5 เท่า
  • เร่งความเร็ว output ไม่ได้เร่ง time to first token (TTFT) เลยเห็นผลชัดตอน stream คำตอบยาวๆ
  • เปิดด้วย speed: "fast" คู่กับ beta header fast-mode-2026-02-01
  • สถานะเป็น research preview
resp = client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=8192,
    speed="fast",                      # เปิด fast mode
    betas=["fast-mode-2026-02-01"],    # ต้องมี beta flag
    messages=[{"role": "user", "content": "เขียน migration script ทั้งชุดให้หน่อย"}],
)
  • Model ที่รองรับ: Opus 5.5, Opus 5 และ Opus 4.8 (Opus 4.7 จะ reject)
  • ราคา: คิดแบบ premium บน Opus 5.5 คือ $8 input / $40 output ต่อ MTok = 2 เท่าของปกติ ($4 / $20)

Effort vs fast mode: คนละขั้วกัน

EffortFast mode
เปลี่ยนอะไรปริมาณงานที่ model ทำความเร็วในการส่ง output (งานเท่าเดิม)
ผลต่อเงินลดลงได้แพงขึ้น (premium)
ใช้เมื่อปัญหาคือบิลมีคนนั่งรอ output ยาวๆ
เข้าใจผิดบ่อย

"Fast mode คือการสลับไปใช้ model ที่เบากว่า แลกคุณภาพกับความเร็ว" ไม่ใช่ เป็น model ตัวเดิม เปลี่ยนแค่ output rate กับราคา

สรุปสั้นๆ

Fast mode = speed: "fast" + beta header, output เร็วขึ้นถึง 2.5x (ไม่ใช่ TTFT), จ่าย 2 เท่า, ใช้ได้แค่ Opus 5.5 / 5 / 4.8

Checkpoint 6

ข้อไหนอธิบาย fast mode ถูกต้อง?

  1. สลับไปใช้ Opus รุ่นย่อที่เล็กกว่าเพื่อให้เร็วขึ้น
  2. เพิ่ม output tokens per second (ไม่ใช่ TTFT) และคิดราคาแบบ premium
  3. ใช้กับ Haiku 4.5 ได้เพื่อให้เร็วขึ้นไปอีก
  4. ทำให้ราคาต่อ token ถูกลงเพราะใช้เวลาน้อยลง
ดูเฉลย

B model เดิม (A ผิด), Haiku ไม่รองรับ (C ผิด) และราคาแพงขึ้น ไม่ใช่ถูกลง (D ผิด)
