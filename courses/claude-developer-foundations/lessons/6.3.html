6.3 Structured outputs และ strict tool use สำหรับ JSON ที่เชื่อถือได้

ต้นฉบับ: CertSafari 6.3

อ่านจบแล้วควรทำได้
  • อธิบายได้ว่าทำไม JSON ที่ขอผ่าน prompt อย่างเดียวทำ parser ปลายทางพัง และ constrained decoding กันปัญหานี้ยังไง
  • ส่ง JSON schema ผ่าน output_config.format ได้ ทั้งแบบตรงๆ และผ่าน client.messages.parse()
  • เปิด strict: true บน tool ได้ และรู้ว่า toolset ไหนไม่รับ
  • เลือก fallback ได้เมื่อ structured outputs ใช้กับ schema ที่ต้องการไม่ได้
แนวคิดหลัก: constrained decoding

จำกัดการ sample token ให้เลือกได้เฉพาะ token ที่ยังทำให้ output ถูกต้องตาม schema รูปร่างถูกบังคับ ระหว่าง generate ไม่ใช่ตรวจทีหลัง ผลที่ได้จึง parse ได้เสมอ มี field ครบ และ type ถูก เหมือนเขียนบนแบบฟอร์มที่มีช่องให้กรอกเท่านั้น จะเขียนนอกช่องก็ทำไม่ได้

1. ทำไม JSON ที่ขอใน prompt ถึงทำ pipeline พัง

คนที่รับ output ต่อมักเป็นโค้ด เช่น json.loads(), insert ลง database หรือ typed function พวกนี้ไม่รับของ "เกือบถูก" ปัญหาที่เจอซ้ำๆ มี 4 แบบ:

  • Parsing error JSON ไม่ valid
  • Missing required fields field ที่ต้องมีหายไป
  • Inconsistent types type ไม่ตรง
  • Schema violations ที่ต้องเขียนโค้ดจับแล้ว retry

ตัวอย่าง: tool จองตั๋วต้องการ passengers เป็น integer แต่ถ้าไม่บังคับ Claude อาจส่ง "two" หรือ "2" มา

Structured outputs รับประกันทั้ง validity, type safety และความเสถียร จนไม่ต้องมี retry ลูป มี 2 ส่วนที่แยกกันแต่ใช้ร่วมกันได้:

  • JSON outputs คุมรูปร่างของ คำตอบ ของ Claude
  • Strict tool use คุมรูปร่างของ arguments ที่ส่งเข้า tool
เข้าใจผิดบ่อย

"เขียน prompt ชัดๆ พร้อมตัวอย่างแล้ว ก็ส่งเข้า parser ได้โดยไม่ต้องกันอะไร" ไม่ใช่ prompting แค่เพิ่มโอกาสถูก มีแต่ constrained decoding ที่ตัดโอกาส output ผิดรูปออกไปได้จริง

สรุปสั้นๆ

Prompt = ขอร้อง · Constrained decoding = บังคับ ถ้าโค้ดปลายทางต้อง parse ให้เลือกแบบบังคับ

Checkpoint 1

ทีมเขียน prompt ละเอียดมาก มีตัวอย่าง JSON ครบ ทดสอบ 50 ครั้งผ่านหมด แล้วส่งตรงเข้า json.loads() ใน production โดยไม่มี try/except ความเสี่ยงคืออะไร?

ดูเฉลย

ไม่มีอะไรบังคับ format จริง prompt แค่เพิ่มโอกาส วันหนึ่งก็อาจเจอ parse error, field หาย หรือ type ผิด แล้ว pipeline ล่ม

2. JSON outputs ด้วย output_config.format

  1. นิยามโครงสร้างเป็น JSON schema (หรือเป็น type ในภาษาที่ใช้)
  2. ส่งใน output_config.format พร้อม type: "json_schema"
  3. อ่านผลจาก text content block ของ response
import json
resp = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "ดึงข้อมูลออเดอร์จากแชทนี้: ..."}],
    output_config={
        "format": {
            "type": "json_schema",
            "schema": {
                "type": "object",
                "properties": {
                    "customer": {"type": "string"},
                    "item": {"type": "string"},
                    "quantity": {"type": "integer"},
                    "express": {"type": "boolean"},
                },
                "required": ["customer", "item", "quantity", "express"],
                "additionalProperties": False,   # ห้ามมี field เกินมา
            },
        }
    },
)
text = next(b.text for b in resp.content if b.type == "text")  # ผลอยู่ใน text block
order = json.loads(text)                                        # parse ได้แน่นอน

ทางลัดใน Python: client.messages.parse()

ส่ง Pydantic model เข้าไปเป็น output_format= SDK จะแปลงเป็น schema ส่งไปเป็น output_config.format ให้ validate ผลแล้วคืน object มาใน parsed_output

from pydantic import BaseModel

class Order(BaseModel):
    customer: str
    item: str
    quantity: int
    express: bool

resp = client.messages.parse(
    model="claude-sonnet-5-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "ดึงข้อมูลออเดอร์จากแชทนี้: ..."}],
    output_format=Order,          # helper layer ของ output_config.format
)
order = resp.parsed_output        # ได้ Order object ที่ validate แล้ว

output_format (argument ของ helper) กับ output_config.format (field ใน request) คือ ฟีเจอร์เดียวกัน คนละ layer

ข้อจำกัดของ schema

  • Constraint อย่าง minimum, maximum, minLength, maxLength จะถูกถอดออกจาก schema ที่ Claude ได้รับ แล้วย้ายไปเขียนไว้ใน description ของ field
  • Helper ยังเติม additionalProperties: false ให้ทุก object และกรอง string format ให้เหลือเฉพาะที่รองรับ
  • แต่ helper ที่ validate จะยังตรวจ response กับ schema ต้นฉบับ ของเรา เช่น field ที่มี minimum: 100 จะถูกส่งเป็น integer ธรรมดาพร้อมโน้ตใน description แต่ตอนได้ผลกลับมา helper ยังเช็กว่า ≥ 100
  • ถ้ายิง request เอง ใช้ transform_schema() จาก package anthropic แปลงให้ ได้ schema ที่แก้ต่อได้ก่อนส่ง
เข้าใจผิดบ่อย

"Constraint ที่ไม่รองรับอย่าง minimum ถูกทิ้งไปเฉยๆ" ไม่ใช่ มันถูกย้ายไปอยู่ใน description และ helper ยังตรวจให้ตอน validate

"output_format= ใน parse() เป็นอีกฟีเจอร์หนึ่ง" ไม่ใช่ เป็น helper ที่ห่อ output_config.format อยู่

สรุปสั้นๆ

Schema → output_config.format → อ่านจาก text block หรือใช้ parse() กับ Pydantic ให้ SDK จัดการ constraint ที่ไม่รองรับไม่หาย แค่ย้ายไป description แล้วตรวจฝั่ง client

3. Strict tool use

ความเสี่ยงอีกจุดอยู่ที่ tool arguments เช่น handler create_booking ได้ "2" แทน 2 หรือ field ที่ required หายไป แล้วพังกลางงาน

ใส่ strict: true ไว้ ระดับบนสุดของ tool definition (ข้างๆ name, description, input_schema) ระบบจะ compile input_schema เป็น grammar แล้วบังคับการ sample ให้ได้ input ที่ตรงเท่านั้น

{
  "name": "create_booking",
  "description": "จองโต๊ะร้านอาหาร",
  "strict": true,                       // อยู่ระดับเดียวกับ name ไม่ใช่ใน input_schema
  "input_schema": {
    "type": "object",
    "properties": {
      "date": {"type": "string"},
      "passengers": {"type": "integer"}
    },
    "required": ["date", "passengers"],
    "additionalProperties": false
  }
}

สิ่งที่รับประกัน:

  • input ในทุก tool_use block ตรงกับ input_schema
  • ชื่อ tool ถูกเสมอ (เป็น tool ที่เราให้ไว้ หรือ server tool)
  • handler ไม่ต้องมีลูป validate-and-retry สำหรับ arguments อีก

ข้อจำกัดเชิงปฏิบัติ

  • computer_toolset_20260801 และ browser_toolset_20260801 ไม่รับ strict: true ใส่แล้ว request fail
  • Compiled tool schema ถูก cache ไว้นานสุด 24 ชั่วโมงหลังใช้ครั้งล่าสุด (message content ไม่ได้ถูก cache แบบนี้)
  • Strict tool use เป็น HIPAA eligible แต่ schema cache ไม่มีการป้องกัน PHI แบบเดียวกับ prompt/response ห้ามใส่ PHI ใน property names, enum values, const values และ pattern regex
ฟีเจอร์ตั้งที่ไหนคุมอะไรผลอยู่ที่ไหน
JSON outputsoutput_config.format กับ type: "json_schema"คำตอบของ Claudetext content block
Strict tool usestrict: true บน tool definitionชื่อ tool และ tool inputsfield input ของ tool_use block
เข้าใจผิดบ่อย

"ใส่ strict: true ได้กับทุก entry ใน tools" ไม่ได้ computer use และ browser use toolset ไม่รับ และทำให้ request ทั้งก้อน fail

สรุปสั้นๆ

strict: true ระดับบนสุดของ tool = arguments ตรง schema เสมอ ยกเว้น computer/browser toolset ที่ใส่ไม่ได้ และอย่าเอา PHI ไปไว้ใน schema

4. เมื่อใช้ structured outputs ไม่ได้

ก่อนอื่นเช็กว่าที่ติดเป็นแค่ constraint ที่ไม่รองรับ หรือเปล่า ถ้าใช่ transform_schema() หรือ helper ที่ validate จัดการได้ ไม่ต้องเลิกใช้ฟีเจอร์

ที่ต้อง fallback จริงๆ มี 2 กรณี:

  • โมเดลที่ใช้ไม่รองรับ structured outputs
  • schema ต้องใช้ feature ที่อยู่นอก subset ที่รองรับ

Fallback คือเทคนิคจากบทเรียน 6.2: กำหนด format ให้เป๊ะด้วย JSON, XML หรือ template, prefill assistant turn (ถ้าโมเดลรับ) และใส่ examples

แต่ตอนนี้ ไม่มีอะไรรับประกันแล้ว syntax error, field หาย, type ผิด กลับมาได้ทั้งหมด ต้องเติม:

from pydantic import ValidationError

def get_order(prompt, retries=2):
    for attempt in range(retries + 1):        # retry budget จำกัด
        text = call_claude(prompt)
        try:
            return Order.model_validate_json(text)   # parse + validate schema ในโค้ด
        except ValidationError as e:
            prompt += f"\nรอบก่อน output ผิด: {e}. ตอบใหม่เป็น JSON ตาม format"
    raise RuntimeError("ได้ JSON ที่ถูกไม่ทัน retry budget")
เข้าใจผิดบ่อย

"Fallback ไปใช้ prompt-based format แล้ว ตัด validation ออกได้" ไม่ได้ guarantee หายไปแล้ว ต้องมี parse error handling, schema validation และ retries

สรุปสั้นๆ

Constraint ไม่รองรับ ≠ ใช้ไม่ได้ · โมเดลไม่รองรับหรือ schema เกิน subset → fallback ไป prompt + ต้องมี validation และ retry

Checkpoint 6

ทีมต้องใช้โมเดลที่ไม่รองรับ structured outputs จึงเปลี่ยนไปใช้ template + examples สิ่งที่ต้องเพิ่มในโค้ดคืออะไร และเพราะอะไร?

ดูเฉลย

ต้องเพิ่ม parse error handling, schema validation และ retry ที่มี budget เพราะ output ไม่ได้ถูกบังคับด้วย constrained decoding แล้ว จึงอาจผิดรูปได้

Checkpoint 7

tool get_exchange_rate พังเมื่อ API ปลายทาง timeout และคืน tool_result ว่า "failed" พร้อม is_error: true แล้ว Claude ก็เรียกซ้ำวนไม่จบ ควรแก้ยังไง?

  1. เปลี่ยนข้อความ error ให้บอกชัดว่าเกิดอะไร เช่น "upstream timeout, ลองใหม่ได้หลัง 30 วินาที หรือใช้อัตราที่ cache ไว้"
  2. เอา is_error ออก ให้ดูเหมือนสำเร็จ
  3. ไม่ต้องส่ง tool_result กลับเมื่อ error
  4. เปลี่ยน tool นี้เป็น server tool
ดูเฉลย

A error ที่บอกรายละเอียดและสิ่งที่ทำได้ทำให้ Claude ปรับแผนได้ · B ทำให้ Claude อาจเอาข้อมูลที่พังไปใช้ต่อ · C ผิดกติกา API เพราะทุก tool_use ต้องมี tool_result ตามมา ไม่งั้น request error · D ไม่ใช่ option ที่ตั้งได้สำหรับ tool ที่เราเขียนเอง
