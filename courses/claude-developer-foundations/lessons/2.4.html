2.4 Calling the Claude API: REST, JSON และ sync vs async patterns

ต้นฉบับ: CertSafari 2.4

อ่านจบแล้วควรทำได้
  • อธิบายได้ว่า Messages API call คือ HTTPS POST ที่ส่ง JSON ไปและได้ JSON กลับ และบอกได้ว่า SDK ใส่ header อะไรให้บ้าง
  • เลือกระหว่าง blocking call, async client, streaming และ submit-and-poll ให้เหมาะกับ workload
  • เก็บประวัติบทสนทนาเป็น JSON ใน storage ของเราเองระหว่างแต่ละ request
  • อธิบายได้ว่าทำไม network call เข้ากับ async programming และหลบ race condition จาก shared state ระหว่าง coroutine ได้
แนวคิดหลัก: request เหมือนกัน ต่างกันแค่ "วิธีรอ"

ไม่ว่าจะเรียกแบบไหน ตัว request ที่ส่งไปคือ JSON ของ Messages API ชุดเดิม และสิ่งที่ได้กลับคือ Message object หน้าตาเดิม สิ่งที่ต่างกันมีอย่างเดียวคือ โค้ดของเรารอผลลัพธ์ยังไง เพราะฉะนั้นให้เลือก pattern จาก latency ที่รับได้และรูปร่างของ workload

1. Messages API คือ REST endpoint ธรรมดาที่คุยกันด้วย JSON

ลอก SDK ออกให้หมด สิ่งที่เหลือคือ HTTP request ธรรมดาตัวเดียว:

  • Base URL: https://api.anthropic.com ส่วนงานสนทนาใช้ POST /v1/messages
  • Header ที่ต้องมี: content-type: application/json, anthropic-version (เช่น 2023-06-01) และ Authorization: Bearer <token> (header เก่า x-api-key ยังใช้เป็น fallback ได้)
  • Official SDK ใส่ auth, version และ content-type ให้เอง แถมมี typed request/response, retry ในตัว, streaming และ timeout
  • Header ตัวเดียวที่เราอาจต้องใส่เองคือ anthropic-workspace-id และใส่เฉพาะตอน API key ของเราครอบคลุมหลาย workspace
# ยิงตรงด้วย curl จะเห็นชัดว่าไม่มีอะไรซับซ้อน
curl https://api.anthropic.com/v1/messages \
  -H "content-type: application/json" \
  -H "anthropic-version: 2023-06-01" \
  -H "Authorization: Bearer $ANTHROPIC_TOKEN" \
  -d '{"model":"claude-opus-5-5","max_tokens":512,
       "messages":[{"role":"user","content":"สวัสดี"}]}'

Response ที่ได้กลับมามี field หลักๆ แบบนี้:

{
  "id": "msg_01...",          // id ของ message นี้
  "type": "message",
  "role": "assistant",
  "content": [{"type": "text", "text": "..."}],  // เป็น list ของ block
  "model": "claude-opus-5-5",
  "stop_reason": "end_turn",  // ทำไมถึงหยุด
  "stop_sequence": null,
  "usage": {"input_tokens": 12, "output_tokens": 40}
}

API เป็น stateless: ความจำเป็นหน้าที่ของเรา

API ไม่จำอะไรเลยระหว่าง request ถ้าอยากให้ Claude "จำ" turn ก่อนหน้า เราต้องส่งประวัติทั้งหมดไปเองทุกครั้ง วิธีมาตรฐานคือเก็บ array messages (list ของ object ที่มี role กับ content) เป็น JSON ใน DB โดยใช้ conversation id เป็น key แล้วทำแบบนี้ทุก turn:

  1. โหลด history ของ conversation นั้น
  2. append ข้อความใหม่ของ user
  3. ส่งทั้งก้อนไปที่ API
  4. append content ของ assistant ที่ได้กลับมา
  5. save กลับลง storage
def chat_turn(conv_id, user_text):
    history = db.load(conv_id) or []          # 1. โหลดของเดิม
    history.append({"role": "user", "content": user_text})
    reply = client.messages.create(
        model="claude-opus-5-5", max_tokens=1024, messages=history)
    history.append({"role": "assistant", "content": reply.content})
    db.save(conv_id, history)                 # 5. เก็บกลับ
    return reply

เพราะ history เป็นของเรา เราจะใส่ assistant message ที่เขียนขึ้นเอง (synthetic) ลงไปก็ได้ เช่นเป็นตัวอย่างคำตอบ

ข้อจำกัดเรื่องขนาด: request ของ Messages และ Token Counting สูงสุด 32 MB ถ้าเกินจะได้ HTTP 413 พร้อม error request_too_large ดังนั้นต้องวางแผนตัด/ย่อ history ไว้ก่อนที่แชตยาวๆ จะชนเพดาน

ทำไม network call ถึงเหมาะกับ async

เวลารอ API ตอบ CPU ของเราแทบไม่ได้ทำอะไร await client.messages.create(...) จะพักแค่ coroutine ตัวนั้น แล้วปล่อยให้ event loop ไปรัน coroutine ตัวอื่นต่อ ตัว request และ Message ที่ได้เหมือน blocking call ทุกอย่าง ต่างแค่การจัดคิว

ข้อควรระวัง: ถ้าหลาย coroutine append ลง list หรือ dict ตัวเดียวกัน ก็เกิด race ได้แบบเดียวกับ thread วิธีที่ปลอดภัยคือให้แต่ละ coroutine return ผลของตัวเอง แล้วค่อยรวมทีหลัง

# ไม่ดี: ทุก task เขียนลง results ตัวเดียวกัน
# ดี: ให้ gather คืนผลเป็น list แล้วค่อยรวม
results = await asyncio.gather(*(summarize(doc) for doc in docs))

อีกระดับของ async คือ async ที่ระดับ endpoint เลย เช่น Message Batches API ที่รับ request ไปก่อนแล้วค่อยประมวลผลทีหลัง HTTP response ตอนส่งแค่บอกว่า "รับแล้ว" ยังไม่มีคำตอบ

เข้าใจผิดบ่อย

"API จำ turn ก่อนหน้าได้ ส่งแค่ข้อความล่าสุดก็พอ" ไม่ใช่ API เป็น stateless service ของเราต้องเก็บ history เองและส่งไปทั้งหมดทุกครั้ง

สรุปสั้นๆ

POST JSON ไปที่ /v1/messages พร้อม 3 header หลัก ได้ Message กลับมา history เป็นของเรา ต้องเก็บและส่งเองทุก turn และระวังเพดาน 32 MB

Checkpoint 1

ทีมเขียน wrapper ด้วย Rust ยิง HTTP เองโดยไม่ใช้ SDK และใช้ API key ที่ผูกกับ workspace เดียว header ตัวไหนที่ต้องใส่เองทุก request แน่ๆ?

  1. anthropic-workspace-id
  2. anthropic-version
  3. request-id
  4. x-batch-id
ดูเฉลย

B anthropic-version ต้องมีทุก request ปกติ SDK ใส่ให้ แต่ถ้ายิงเองก็ต้องใส่เอง ส่วน workspace id ใช้เฉพาะ key ที่ครอบหลาย workspace และ request-id เป็น header ฝั่ง response

Checkpoint 2

ทุกเดือนต้องแปะ tag หมวดหมู่ให้รีวิวสินค้าเก่า 80,000 รายการ แต่ละรายการไม่เกี่ยวกัน อยากประหยัดที่สุด ได้ผลภายในวันรุ่งขึ้นก็พอ ควรใช้อะไร?

  1. Streaming ผ่าน connection เดียวแล้วยัดรีวิวทั้งหมดใน prompt
  2. ลูป messages.create ทีละรายการ
  3. Message Batches API
  4. เปิด session เดียวแล้ว resume ไปเรื่อยๆ
ดูเฉลย

C งานปริมาณมาก แยกกันอิสระ และไม่มีใครรอผลทันที คือโจทย์ของ Batch API ซึ่งประมวลผลแบบ async และราคาประมาณครึ่งหนึ่ง

2. Blocking call กับ async client

client.messages.create(...) บน client แบบ sync (Anthropic) จะรอจนได้ Message ครบก่อนค่อยไปบรรทัดต่อไป เหมาะกับ script, CLI tool และ worker ที่ทำทีละ request

แต่ถ้า service รันบน event loop (เช่น FastAPI) การเรียกแบบ blocking จะไปแช่ทั้ง loop ทำให้ coroutine อื่นค้างไปหมด ทางแก้คือใช้ AsyncAnthropic ซึ่งมี method messages.create ชื่อเดียวกัน แค่ต้อง await ภายใน async function (Python SDK ยังเลือกใช้ aiohttp เป็น backend ได้ถ้าอยากได้ throughput แบบ async ดีขึ้น)

import asyncio
from anthropic import AsyncAnthropic

client = AsyncAnthropic()

async def main():
    # await = พัก coroutine นี้ระหว่างรอ ไม่ block loop
    msg = await client.messages.create(
        model="claude-opus-5-5", max_tokens=1024,
        messages=[{"role": "user", "content": "ช่วยสรุปไฟล์นี้หน่อย"}])
    print(msg.content)

asyncio.run(main())   # จุดเริ่ม event loop ระดับบนสุด
สรุปสั้นๆ

Script/CLI ใช้ Anthropic แบบ blocking ได้เลย service ที่อยู่บน asyncio ใช้ AsyncAnthropic + await method เหมือนกันทุกอย่าง

Checkpoint 3

ใน handler async def ของ web service มีคนเขียน reply = client.messages.create(...) โดย client เป็น AsyncAnthropic แล้วได้ coroutine object แทน Message ต้องเติมอะไร?

ดูเฉลย

เติม await หน้า call เพราะ messages.create ของ async client คืน awaitable ส่วน asyncio.run ใช้แค่เริ่ม loop ที่ระดับบนสุด ไม่ใช่ใส่ใน handler

3. Streaming: เมื่อ output ยาว หรือมีคนนั่งดูอยู่

ลองเดาก่อน: job ตอนดึกขอ max_tokens=128000 และไม่มีใครนั่งดู ควรเรียกยังไง? คำตอบคือ messages.stream(...) แล้วเรียก get_final_message() ไม่ใช่ blocking call ธรรมดา และไม่ต้องหั่นงานเป็นหลาย call

Streaming คือ response ทยอยมาเป็นชิ้นๆ ผ่าน HTTP connection เดียวที่เปิดค้างไว้ มันช่วยใน 2 กรณี:

  • มีคนรออยู่ และได้ประโยชน์จากการเห็นข้อความค่อยๆ โผล่
  • Response ยาวมากจนเสี่ยงโดน HTTP timeout ซึ่ง SDK บังคับ ให้ใช้ streaming เมื่อ max_tokens สูงๆ แม้เราจะอยากได้แค่ผลสุดท้าย
with client.messages.stream(
    model="claude-opus-5-5", max_tokens=128000,
    messages=[{"role": "user", "content": "เขียนรายงานฉบับเต็ม"}],
) as stream:
    final = stream.get_final_message()   # ได้ Message หน้าตาเดียวกับ create
print(final.usage.output_tokens)

Error กลาง stream

Error ที่ blocking call รายงานเป็น HTTP status อาจมาเป็น error event ระหว่าง stream ได้ ตัวหลักคือ overload: overloaded_error ใน stream เทียบเท่ากับ HTTP 529 ใน call ปกติ ถ้าเขียน error handling ครอบแค่ response แรก จะพลาดเคสนี้ไป ทั้ง sync และ async stream รองรับหมด

try:
    with client.messages.stream(**req) as stream:
        for text in stream.text_stream:
            ui.push(text)
except anthropic.APIStatusError as e:
    # ต้องมี path นี้แยก: overload อาจมาหลังจาก stream เริ่มไปแล้ว
    handle_retry(e)
เข้าใจผิดบ่อย

"Streaming มีไว้สำหรับ UI งาน backend ใช้ blocking เสมอ" ไม่ใช่ ถ้า max_tokens สูง SDK บังคับให้ stream อยู่แล้ว และ get_final_message() ก็คืน Message ครบเหมือน create

สรุปสั้นๆ

Stream เมื่อมีคนดูหรือ output ยาว ใช้ get_final_message() ถ้าอยากได้แค่ผลรวม และต้องจัดการ error event กลาง stream แยกจาก HTTP status

Checkpoint 4

แชตบอทมีโค้ด retry เมื่อได้ HTTP 529 แต่ช่วง peak ผู้ใช้ยังเห็นคำตอบขาดกลางประโยคบ่อยๆ น่าจะเป็นเพราะอะไร?

  1. max_tokens ต่ำเกินไป
  2. Overload มาเป็น error event หลัง stream เริ่มไปแล้ว ซึ่งการเช็ก 529 ตอนเริ่มจับไม่ได้
  3. API ตัด history ทิ้งเพราะเกิน 32 MB
  4. ต้องเปลี่ยนเป็น Batch API
ดูเฉลย

B ใน stream, overload โผล่มาเป็น overloaded_error event กลางทาง ต้องมี error path สำหรับ stream โดยเฉพาะ

4. Submit-and-poll: งานที่ไม่มีใครรอ

แยกการส่งงานกับการเก็บผลออกจากกัน: ส่งงานไป ได้ ID กลับมา แล้วค่อยมาเช็กสถานะทีหลัง ตัวอย่างมาตรฐานคือ Message Batches API ซึ่ง batch เริ่มที่ processing_status = in_progress แล้วเปลี่ยนเป็น ended เมื่อทุก request เสร็จและผลพร้อม

import time

while True:
    batch = client.messages.batches.retrieve(batch_id)
    if batch.processing_status == "ended":
        break                       # ผลพร้อมแล้ว ไปดึง results ได้
    print("ยังไม่เสร็จ รอก่อน...")
    time.sleep(60)                  # เช็กทุก 60 วินาที
  • Job ID ต้องอยู่นานกว่า process ที่ส่งงาน ให้เก็บ batch id ลง DB พร้อมข้อมูลที่ใช้ map ผลกลับไปหา record ของเรา
  • ตัว poller รันเป็น scheduled job ได้ ถ้า restart ก็ไม่เสียงาน
  • ใช้เมื่อ throughput และต้นทุนสำคัญกว่า latency เช่น classification หรือ evaluation ตอนกลางคืน ห้ามใช้เมื่อมี user รออยู่
Patternโค้ดรอยังไงเหมาะเมื่อ
Blocking messages.createthread รอจนได้ Message ครบScript, worker ที่ทำทีละ request
AsyncAnthropic + awaitcoroutine ยอมถอยระหว่าง request วิ่งService ที่รันบน event loop อยู่แล้ว
messages.streamอ่าน event ผ่าน connection เดียวมีคนดู output หรือ max_tokens สูงจนเสี่ยง timeout
Message Batches (submit-and-poll)เก็บ ID แล้วเช็ก processing_status ทีหลังงานปริมาณมากที่ไม่มีใครรอผลทีละชิ้น
สรุปสั้นๆ

Submit-and-poll = ส่งงาน เก็บ ID ให้ทนทาน แล้ว poll จน ended เหมาะกับงานกลางคืนปริมาณมาก ไม่เหมาะกับงานที่ user รอ
