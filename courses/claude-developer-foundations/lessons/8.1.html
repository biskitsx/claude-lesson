8.1 Defining Claude tools: schemas, descriptions และ tool set design

ต้นฉบับ: CertSafari 8.1

อ่านจบแล้วควรทำได้
  • แยก tool ได้ 3 ประเภท: user-defined client tool, Anthropic-schema client tool และ server tool และบอกได้ว่าแอปเราต้องทำอะไรกับแต่ละแบบ
  • เทียบ client tool กับ server tool ได้: ใครรันโค้ด ใครขับ loop และอะไรถูกส่งกลับมา
  • เขียน tool definition ด้วย name, description, input_schema และใช้ input_examples กับ strict เป็น
  • เขียน description ที่พา Claude ไปเลือก tool ถูกตัว
  • ออกแบบ tool set ที่โตได้: consolidation, namespacing และ response ที่ high-signal
  • ตั้งค่า tool_choice และ server tool entry ได้ รวมถึงรู้ข้อจำกัดของการ force tool
แนวคิดหลัก: tool use คือสัญญา

เราประกาศว่ามี operation อะไรบ้างและ input หน้าตาแบบไหน Claude เป็นคนตัดสินว่าจะเรียกเมื่อไหร่ แล้วส่ง request แบบมีโครงสร้างออกมา Claude ไม่เคยรันโค้ดเอง คนรันคือแอปของเรา หรือ server ของ Anthropic

1. Tool รันที่ไหน ตัดสินว่าเราต้องสร้างอะไร

คำถามแรกก่อนเขียน tool คือ "โค้ดของ tool นี้รันที่ไหน" เพราะคำตอบจะบอกเลยว่าฝั่งเราต้องเขียนอะไรบ้าง แบ่งได้ 3 กลุ่ม:

กลุ่มใช้เมื่อแอปเราต้องจัดการ
User-defined client toollogic เฉพาะของเรา, internal API, ข้อมูล proprietaryเขียน schema เอง, รันโค้ดเอง, ส่ง tool_result กลับ
Anthropic-schema client tool (memory, bash, text_editor, computer, browser)งานทั่วไปที่ Anthropic มี schema มาตรฐานให้แล้วรันโค้ดเองและส่ง tool_result กลับ แต่ไม่ต้องคิด schema
Server-executed tool (web_search, web_fetch, code_execution, tool_search)อยากได้ความสามารถพวกนี้โดยไม่ต้องเขียน handlerแค่เปิดใช้ใน request ไม่ต้องสร้าง tool_result

ทำไมควรใช้ schema ของ Anthropic ถ้ามีให้? เพราะ Claude ถูก train มากับ trajectory ที่ใช้ signature พวกนี้ เลยเรียกได้แม่นกว่า และ recover จาก error ได้ดีกว่า schema ที่เราคิดขึ้นเอง

Client tool: เราเป็นคนขับ loop

Claude ตอบกลับมาด้วย stop_reason: "tool_use" พร้อม tool_use block โค้ดเรารัน tool แล้วส่ง tool_result block กลับ วนแบบนี้ไปเรื่อยๆ ตราบใดที่ stop_reason ยังเป็น tool_use ถ้า tool พังให้ส่งผลกลับพร้อม is_error: true

while resp.stop_reason == "tool_use":
    results = []
    for block in resp.content:
        if block.type == "tool_use":
            try:
                out = run_tool(block.name, block.input)   # โค้ดเรารันเอง
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": out})
            except Exception as e:
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": f"ล้มเหลว: {e}", "is_error": True})
    messages += [{"role": "assistant", "content": resp.content},
                 {"role": "user", "content": results}]
    resp = client.messages.create(model=MODEL, tools=TOOLS, messages=messages, max_tokens=1024)

Server tool: Anthropic ขับ loop ให้

ใน response จะเห็น server_tool_use block (และผลของมัน) อยู่แล้ว เราไม่ต้องสร้าง tool_result และไม่ต้องจัดการ is_error ยกเว้น 2 กรณีพิเศษ:

  • stop_reason: "pause_turn" แปลว่า loop ฝั่ง server ชน iteration limit ให้ส่ง conversation กลับไปใหม่ โดยรวม response ที่ pause ไว้ และใช้ tools ชุดเดิม เพื่อให้ทำต่อ
  • Mixed turn ถ้า Claude เรียก server tool กับ client tool ใน parallel group เดียวกัน server tool จะยังไม่มีผล ให้เราส่งแค่ tool_result ของ client tool กลับไป โดยใช้ tools array เดิม แล้ว API จะไปรัน server tool ที่ค้างไว้ให้เอง
เข้าใจผิดบ่อย

"Server tool ก็ต้องส่ง tool_result และจัดการ is_error เหมือน client tool" ไม่ใช่ งานนั้นมีแค่ client tool ส่วน server tool มีแค่กรณี pause_turn กับ mixed turn ที่ต้องทำอะไรเพิ่ม

สรุปสั้นๆ

Schema ใครเขียนไม่สำคัญเท่า "ใครรัน" ถ้าเรารัน (client tool) เราต้องวน loop และส่ง tool_result ถ้า Anthropic รัน (server tool) เราแค่เปิดใช้ แล้วระวัง pause_turn กับ mixed turn

Checkpoint 1

Response หนึ่งมี server_tool_use ของ web_search ที่ยังไม่มีผล กับ tool_use ของ lookup_order (client tool ของเรา) ในรอบเดียวกัน ควรทำยังไง?

  1. สร้าง tool_result ปลอมให้ web_search ก่อน แล้วค่อยส่งพร้อมผล lookup_order
  2. รัน lookup_order แล้วส่งเฉพาะ tool_result ของมันกลับไป โดยใช้ tools array ชุดเดิม
  3. ส่ง conversation เดิมกลับไปเฉยๆ แบบเดียวกับ pause_turn โดยยังไม่รัน lookup_order
  4. ตัด web_search ออกจาก tools แล้วค่อยส่งผล lookup_order
ดูเฉลย

B นี่คือ mixed turn เราตอบเฉพาะส่วนที่เป็นของเรา (client tool) และต้องคง tools ชุดเดิมไว้ API จะรัน server tool ที่ค้างอยู่เอง ห้ามสร้างผลให้ server tool

Checkpoint 2

แอปของคุณรัน shell command อยู่แล้ว จะใช้ custom tool ชื่อ run_shell หรือใช้ bash tool ของ Anthropic ก็ได้ ข้อไหนคือเหตุผลที่ถูกที่สุดที่ควรใช้ของ Anthropic?

  1. Anthropic จะรัน command ให้บน server ไม่ต้องรันเอง
  2. ไม่ต้องส่ง tool_result กลับ
  3. Claude ถูก train มากับ schema นี้ จึงเรียกได้แม่นกว่าและ recover จาก error ได้ดีกว่า
  4. bash tool ไม่กิน token ใน context
ดูเฉลย

C bash ยังเป็น client tool แอปเราต้องรันและส่ง tool_result เองเหมือนเดิม ข้อดีอยู่ที่ schema ที่ Claude คุ้นเคย

2. Anatomy ของ tool definition

Client tool ใส่ไว้ใน parameter tools ระดับบนสุดของ request แต่ละตัวมี field หลัก 3 ตัว:

  • name ต้องตรง regex ^[a-zA-Z0-9_-]{1,128}$
  • description เป็น plaintext ตรงนี้สำคัญมาก เพราะ API เอา tool definition ทั้งหมดไปพับรวมเป็น system prompt พิเศษ ทุกตัวอักษรที่เขียนจึงกลายเป็น context ให้ Claude อ่าน
  • input_schema เป็น JSON Schema object
{
  "name": "book_meeting_room",
  "description": "จองห้องประชุมในออฟฟิศกรุงเทพฯ ... (ดูหัวข้อถัดไปว่าควรเขียนยาวแค่ไหน)",
  "input_schema": {
    "type": "object",
    "properties": {
      "room":   {"type": "string", "description": "รหัสห้อง เช่น BKK-12A"},
      "start":  {"type": "string", "description": "เวลาเริ่ม ISO 8601"},
      "seats":  {"type": "integer", "description": "จำนวนคน"},
      "layout": {"type": "string", "enum": ["boardroom", "classroom"]}
    },
    "required": ["room", "start", "seats"]
  },
  "input_examples": [
    {"room": "BKK-12A", "start": "2026-11-02T14:00:00+07:00", "seats": 6}
  ],
  "strict": true
}

Field เสริม: input_examples และ strict

  • input_examples คือตัวอย่าง input ช่วยได้มากกับ object ซ้อนหลายชั้นหรือ parameter ที่ format จุกจิก (เช่น วันที่) แต่มีเงื่อนไข: ทุกตัวอย่างต้อง validate ผ่าน input_schema ไม่งั้นได้ 400, ตัวอย่างกิน prompt token, และใช้ไม่ได้กับ server tool และ toolset ของ computer use / browser use
  • strict: true เปิด grammar-constrained sampling ทำให้ input ที่ Claude สร้างตรง schema แน่นอน เช่น ได้ integer 2 ไม่ใช่ string "two"
สรุปสั้นๆ

name + description + input_schema คือขั้นต่ำ examples ช่วย "เพิ่มโอกาส" ให้เรียกถูก แต่ strict เป็นตัวเดียวที่ "การันตี" ว่า type ตรง schema

Checkpoint 3

tool จองโต๊ะร้านอาหารมี field party_size เป็น integer แต่บางครั้ง Claude ส่งมาเป็น "สี่" อยากให้ได้ integer ทุกครั้งแบบรับประกัน ต้องแก้ตรงไหน?

  1. เพิ่ม input_examples ที่ party_size เป็นตัวเลข
  2. เขียน description ให้ชัดว่าต้องเป็นตัวเลข
  3. ตั้ง strict: true
  4. ย้าย party_size ไปไว้ใน required
ดูเฉลย

C examples กับ description แค่ทำให้โอกาสดีขึ้น ส่วน strict ใช้ grammar-constrained sampling บังคับให้ตรง schema

3. เขียน description ให้ Claude เลือก tool ถูก

ลองนึกเคสนี้: มี tool ดูราคาหุ้น แล้ว Claude ดันเรียกกับหุ้นที่ระบบไม่รองรับซ้ำๆ จะแก้ที่ไหน? คำตอบคือ description ไม่ใช่ strict mode และไม่ใช่การเพิ่ม required parameter

Claude เลือก tool จากสองอย่าง: สิ่งที่ user ขอ กับ description ของแต่ละ tool Anthropic เองบอกว่า description ที่ละเอียดคือปัจจัยที่สำคัญที่สุดต่อ performance ของ tool use

Description ที่ดีควรตอบ:

  • tool นี้ทำอะไร
  • ควรใช้เมื่อไหร่ และไม่ควรใช้เมื่อไหร่
  • แต่ละ parameter หมายถึงอะไร
  • ข้อจำกัด เช่น อะไรที่ tool นี้ไม่คืนให้

ความยาวขั้นต่ำประมาณ 3–4 ประโยคต่อ tool ถ้า tool ซับซ้อนก็เขียนยาวกว่านั้น

{
  "name": "get_fx_rate",
  "description": "คืนอัตราแลกเปลี่ยนล่าสุดระหว่างสกุลเงินคู่หนึ่ง โดยใช้รหัส ISO 4217 เช่น USD, THB, JPY. รองรับเฉพาะสกุลเงินหลัก 30 สกุลเท่านั้น ถ้าเป็นคริปโตห้ามเรียก. ใช้เมื่อ user ถามอัตราปัจจุบัน ไม่ใช่อัตราย้อนหลังหรือการพยากรณ์. คืนค่าเป็นตัวเลขอย่างเดียว ไม่มีกราฟหรือข่าว.",
  "input_schema": {
    "type": "object",
    "properties": {
      "base":  {"type": "string", "description": "สกุลเงินต้นทาง ISO 4217"},
      "quote": {"type": "string", "description": "สกุลเงินปลายทาง ISO 4217"}
    },
    "required": ["base", "quote"]
  }
}
เข้าใจผิดบ่อย

"Claude เลือก tool ผิด เปิด strict หรือเพิ่ม parameter ก็หาย" ไม่ใช่ strict คุมแค่รูปร่างของ input ไม่ได้ช่วยเรื่องการเลือก tool ให้ไปเขียน description ใหม่

สรุปสั้นๆ

เลือกผิดตัว = แก้ description ส่ง type ผิด = เปิด strict สองปัญหานี้คนละเรื่องกัน

Checkpoint 4

ใน flow ปิดเคสลูกค้า คุณต้องการให้ Claude เรียก close_ticket ทุกครั้งแบบไม่มีข้อยกเว้น (บนโมเดลที่รองรับการ force tool) ควรตั้ง tool_choice แบบไหน?

  1. {"type": "tool", "name": "close_ticket"}
  2. {"type": "any"}
  3. {"type": "auto"}
  4. {"type": "none"}
ดูเฉลย

A any บังคับแค่ว่าต้องใช้สัก tool อาจเป็นตัวอื่นได้ auto ให้ Claude เลือกเอง ส่วน none ห้ามใช้ tool เลย

Checkpoint 5

ข้อไหนไม่จำเป็นต้องใส่ใน description ของ tool?

  1. เคสที่ไม่ควรใช้ tool นี้
  2. ความหมายของแต่ละ parameter
  3. ว่า tool นี้เขียนด้วย Go และ deploy บน Kubernetes
  4. ข้อมูลที่ tool นี้ไม่คืนให้
ดูเฉลย

C Claude เห็นแค่ schema กับผลลัพธ์ implementation ข้างหลังไม่ช่วยอะไรในการตัดสินใจ แถมกิน token เปล่าๆ

4. สร้าง tool set ที่ scale ได้

พอ tool เริ่มเยอะ ปัญหาไม่ได้อยู่ที่ tool ตัวใดตัวหนึ่ง แต่อยู่ที่ "ทั้งชุด" มี 3 หลักให้จำ:

  • Consolidate รวม tool ที่ทำงานเรื่องเดียวกันเป็นตัวเดียวที่มี parameter action เช่น แทนที่จะมี create / review / merge แยก 3 ตัว ก็มี tool PR ตัวเดียว tool น้อยลง = ความกำกวมตอนเลือกน้อยลง
  • Namespace ใส่ prefix ชื่อ service เช่น github_, slack_ ช่วยมากโดยเฉพาะเมื่อใช้ tool search
  • คืนผลที่ high-signal ส่ง stable identifier (slug, UUID) และเฉพาะ field ที่ขั้นต่อไปต้องใช้ ผลที่บวมเต็มไปด้วย field ภายในคือการเผา context ทิ้ง
// แทน create_pr / review_pr / merge_pr
{
  "name": "github_pull_request",
  "description": "จัดการ pull request ใน repo ... action=create เปิด PR ใหม่, review ส่ง review, merge รวม PR ...",
  "input_schema": {
    "type": "object",
    "properties": {
      "action": {"type": "string", "enum": ["create", "review", "merge"]},
      "pr_id":  {"type": "string", "description": "ไม่ต้องใส่ถ้า action=create"}
    },
    "required": ["action"]
  }
}

เมื่อไหร่ควรเป็น tool เมื่อไหร่ไม่ควร

ควรเป็น toolไม่ต้องเป็น tool
มี side effect (ส่งเมล, เขียน DB)สรุปความ
ต้องการข้อมูลสด/ข้อมูลภายนอกQ&A ครั้งเดียว
ต้องการ output รูปร่างตายตัวงานง่ายๆ ที่โมเดลทำได้เอง
เรียกเข้าระบบที่มีอยู่แล้ว

Rule of thumb: ถ้าคุณกำลังเขียน regex เพื่อแกะ "การตัดสินใจ" ออกจากข้อความที่โมเดลตอบ การตัดสินใจนั้นควรเป็น tool call ตั้งแต่แรก

เมื่อ tool ล้มเหลว

อย่าเงียบ และอย่าส่ง error body กลับไปเหมือนเป็นข้อมูลปกติ ให้ส่ง tool_result ที่มี tool_use_id ตรงกัน, content อธิบายว่าพังเพราะอะไรและแนะนำให้ retry ได้ไหม, และ is_error: true

{
  "type": "tool_result",
  "tool_use_id": "toolu_01abc",
  "content": "Inventory API ตอบ 504 timeout ลองใหม่ได้ในอีกสักครู่",
  "is_error": true
}
สรุปสั้นๆ

Tool น้อยแต่ชัด ชื่อมี namespace ผลลัพธ์กระชับ และ error ต้องติดธง is_error เสมอ

Checkpoint 6

tool check_stock เรียก inventory API แล้วได้ HTTP 502 อยากให้ Claude รู้ว่ามันพัง และไม่เอา HTML error page ไปตีความเป็นข้อมูลสต็อก ควรส่งอะไรกลับ?

  1. tool_result ที่มี tool_use_id ตรงกัน, content บอกว่า API ล่มและลองใหม่ได้ และ is_error: true
  2. ส่ง HTML error page ทั้งหน้ากลับไปใน content โดยไม่ใส่ is_error
  3. ไม่ส่ง tool_result เลย ข้ามไปเรียก API รอบหน้า
  4. ส่ง content ว่า "สต็อก = 0" และ is_error: false
ดูเฉลย

A ต้องมี tool_result ทุก tool_use และต้องติดธง error ให้ชัด ข้อ D อันตรายที่สุดเพราะโกหกว่าเป็นข้อมูลจริง

Checkpoint 7 (จับคู่)

จับคู่ปัญหากับวิธีแก้:

  1. มี tool จัดการ invoice แยก 8 ตัวตาม action แล้ว Claude เลือกผิดบ่อย
  2. tool ของ Jira กับ Notion ชื่อคล้ายกันจนสับสน
  3. ผลของ tool มี field ภายในเป็นร้อยตัว
  4. โค้ดใช้ regex หาคำว่า "APPROVE" ในคำตอบของ Claude
ดูเฉลย

1 → consolidate เป็น tool เดียวที่มี action · 2 → namespace ด้วย prefix ชื่อ service · 3 → คืนเฉพาะ field high-signal และ stable ID · 4 → ทำการตัดสินใจนั้นให้เป็น tool call

5. ตั้งค่า request: tool_choice และ server tool

ค่า default ของ tool_choice คือ auto (เมื่อมี tools) ถ้าอยากให้ Claude ใช้ tool บ่อยขึ้น ลองเขียนใน prompt เช่น "ใช้ tool ตรวจสอบก่อนตอบ" ก็ช่วยได้ ส่วนถ้าอยากให้เรียกได้ทีละไม่เกิน 1 tool ต่อ turn ให้ตั้ง disable_parallel_tool_use: true

ค่าความหมาย
autoClaude ตัดสินเอง (default เมื่อส่ง tools มา)
anyต้องใช้ tool สักตัวใน list แต่ไม่ระบุตัว
toolต้องใช้ tool ที่ระบุชื่อ
noneห้ามใช้ tool (default เมื่อไม่ได้ส่ง tools)

ราคาของการ force tool

  • เมื่อใช้ any หรือ tool API จะ prefill assistant turn ให้ ผลคือ Claude ไม่เขียนคำอธิบายใดๆ ก่อน tool_use block
  • Manual extended thinking ไม่รับ any และ tool
  • Claude Opus 5.5, Sonnet 5.5, Fable 5.1 และ Mythos 5.1 จะตอบ 400 ถ้าใช้ any หรือ tool ให้ใช้ auto คู่กับ strict tool use หรือใช้ structured outputs แทน

Server tool และ MCP connector

เปิด server tool ด้วย entry เดียว มี type ที่มีวันที่เป็น version และ name ไม่ต้องเขียน handler ใดๆ

resp = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    tools=[{"type": "web_search_20250305", "name": "web_search"}],  # type มีวันที่เป็น version
    messages=[{"role": "user", "content": "ข่าวล่าสุดเรื่อง ..."}],
)

ส่วน remote MCP server ต่อเข้ากับ Messages API ได้ตรงๆ ผ่าน MCP connector ไม่ต้องมี MCP client แยกต่างหาก

เข้าใจผิดบ่อย

"tool_choice: tool ใช้ได้ทุกที่" ไม่ใช่ บางโมเดลและ manual extended thinking จะตอบ 400

สรุปสั้นๆ

auto คือ default, any/tool คือการบังคับที่แลกกับการไม่มีคำอธิบายและใช้ไม่ได้บนบางโมเดล server tool เปิดด้วย entry เดียวที่มี type แบบมีวันที่

Checkpoint 8

ส่ง request ไป Sonnet 5.5 พร้อม tool_choice: {"type": "tool", "name": "lookup_invoice"} จะเกิดอะไรขึ้น และควรแก้ยังไง?

  1. ทำงานปกติ Claude เรียก lookup_invoice ทันที
  2. ได้ 400 ให้เปลี่ยนเป็น auto คู่กับ strict tool use (หรือ structured outputs)
  3. API เปลี่ยนเป็น any ให้อัตโนมัติ
  4. Claude ไม่สนใจ tool_choice แล้วตอบเป็นข้อความ
ดูเฉลย

B Sonnet 5.5 อยู่ในกลุ่มที่ไม่รับ any/tool ทางออกคือ auto + strict
