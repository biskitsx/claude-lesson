2.3 Claude Messages API: requests, vision, tools, streaming และ thinking

ต้นฉบับ: CertSafari 2.3

อ่านจบแล้วควรทำได้
  • อ่าน response ของ Messages API ออก: content blocks, stop_reason และ usage
  • เก็บ conversation state ในโค้ดเราเอง ส่งซ้ำทุกครั้งโดยไม่ทำ prompt cache พัง
  • เขียน client-side tool loop ที่ส่ง thinking block กลับไปแบบไม่แตะต้อง
  • อ่าน streaming response ทีละ event หรือให้ SDK รวมให้
  • ส่งรูปแบบ inline (base64), URL หรือ Files API file_id
  • บอกได้ว่า request เปลี่ยนตรงไหนเมื่อเรียก Claude ผ่าน Google Cloud หรือ Amazon Bedrock
แนวคิดหลัก: API ความจำสั้นเป็นศูนย์

Messages API เป็น stateless ฝั่ง app ของเราเป็นคนถือ conversation ทั้งหมด และต้องส่งทั้งก้อนใหม่ทุก request ทั้ง turn เก่า, tool result และรูป

1. หน้าตาของ request และ response

request ขั้นต่ำมี 3 อย่าง:

  • model
  • max_tokens เพดานความยาวของคำตอบ
  • messages list ที่แต่ละตัวมี role (user หรือ assistant) และ content

คำสั่งที่อยากให้มีผลตั้งแต่ turn แรก ใส่ใน field system ระดับบนสุด ไม่ได้อยู่ใน messages

{
  "id": "msg_01AbC...",
  "type": "message",
  "role": "assistant",
  "model": "claude-sonnet-5-5",
  "content": [{"type": "text", "text": "สวัสดีครับ"}],
  "stop_reason": "end_turn",
  "stop_sequence": null,
  "usage": {"input_tokens": 12, "output_tokens": 6}
}
  • content เป็น array ของ typed block ไม่ใช่ string คำตอบธรรมดาคือ text block เดียว แต่ถ้าเปิด tool หรือ thinking จะมี tool_use และ thinking block ปนมา โค้ดที่อ่าน content[0].text ตรงๆ จะพังทันที
  • usage บอก input_tokens และ output_tokens ใช้คิดเงินและติดตามขนาด context
# อ่านเฉพาะ text block อย่างปลอดภัย ไม่สมมติว่าอยู่ index 0
text = "".join(b.text for b in resp.content if b.type == "text")

stop_reason บอกอะไร

ค่าความหมาย
end_turnตอบจบตามธรรมชาติ
max_tokensชนเพดาน คำตอบถูกตัด ยังไม่ใช่คำตอบที่จบ
stop_sequenceเจอ custom stop string ที่เราตั้งไว้
tool_useClaude อยากเรียก tool
refusalClaude ปฏิเสธ มี stop_details บอก policy category ให้ log ได้โดยไม่ต้อง parse ข้อความ
สรุปสั้นๆ

ส่ง model + max_tokens + messages (และ system ถ้ามี) ได้กลับมาเป็น block array พร้อม stop_reason กับ usage อย่าสมมติว่า content มีแค่ text

Checkpoint 1

ทีม trust & safety อยากเก็บสถิติว่า Claude ปฏิเสธคำขอแต่ละครั้งเพราะ policy หมวดไหน ควรอ่านจากตรงไหน?

  1. ใช้ regex หาคำว่า "ขออภัย" ใน text
  2. object stop_details ที่มากับ stop_reason: "refusal"
  3. field stop_sequence
  4. object usage
ดูเฉลย

B stop_details บอก category มาเป็น structured data ส่วน regex เปราะ stop_sequence บอกแค่ stop string ที่ match และ usage มีแค่จำนวน token

2. Conversation state อยู่ในโค้ดเรา

หลังได้คำตอบทุกครั้ง: append assistant message → append user turn ถัดไป → ส่งทั้ง list อะไรก็ตามที่อยากให้ Claude เห็นใน turn นั้น (เอกสาร, screenshot, tool result) ต้องอยู่ใน request ของ turn นั้น msg_ ID เอาไปดึงประวัติไม่ได้

history = []

def ask(question):
    history.append({"role": "user", "content": question})
    resp = client.messages.create(model=MODEL, max_tokens=1024,
                                  system=SYSTEM, messages=history)  # ส่งทั้งก้อนทุกครั้ง
    history.append({"role": "assistant", "content": resp.content})
    return resp

assistant turn ไม่จำเป็นต้องมาจาก Claude จริง จะเขียน few-shot exchange ขึ้นมาเองก็ได้

Prefill และ system message กลางบท

  • Prefill: บน model เก่าอย่าง Sonnet 4.5 ถ้า message สุดท้ายเป็น assistant Claude จะเขียนต่อจากตรงนั้น (เช่น prefill "คำตอบคือ (" คู่กับ max_tokens: 1 เพื่อได้ตัวอักษรเดียว) แต่ ไม่แนะนำสำหรับโค้ดใหม่: Opus 4.6 ปฏิเสธ prefilled assistant turn และ checklist การย้ายไป Opus 5.5 บอกให้เอาออก
  • Mid-conversation system message: บน model ใหม่ (Opus 5.5, Sonnet 5.5) ใส่ role: "system" ต่อท้าย user turn เพื่อเพิ่มคำสั่งกลางทางได้ แต่ห้ามเป็นตัวแรกของ messages และเพราะมันต่อท้าย จึงไม่ทำให้ cached prefix ก่อนหน้าเสีย

Prompt caching กับ breakpoint

ใส่ cache_control บน content block = ตั้ง cache breakpoint ทุกอย่างตั้งแต่ต้นจนถึง block นั้นกลายเป็น prefix ที่ reuse ได้ cache key คือ hash ของ prompt จนถึง breakpoint ถ้ามีอะไรเปลี่ยนก่อนหน้า (timestamp ใน system prompt, สลับลำดับ tool, แก้ turn เก่า) จะ miss ทันที ของที่เปลี่ยนบ่อยให้ไว้ท้ายสุด

system = [
    {"type": "text", "text": MANUAL_40K,                   # เนื้อหานิ่ง
     "cache_control": {"type": "ephemeral", "ttl": "1h"}},  # breakpoint ตรงนี้
    {"type": "text", "text": f"เวลาปัจจุบัน: {now}"},        # ของที่เปลี่ยน อยู่หลัง breakpoint
]
  • usage.cache_read_input_tokens = token ที่อ่านจาก cache, usage.cache_creation_input_tokens = token ที่เขียนใหม่ ถ้า read ค้างที่ 0 ตลอดแปลว่า prefix ไม่เคยซ้ำ
  • TTL default 5 นาที refresh ฟรีทุกครั้งที่ใช้ นับจากตอนเริ่ม request (response ที่ stream นานๆ จะกินอายุไปด้วย)
  • TTL 1 ชั่วโมง: ใส่ "ttl": "1h"
  • ค่าเขียน: แบบ 5 นาทีแพงกว่า base input 25% แบบ 1 ชั่วโมงแพงเป็น 2 เท่า ของ base input คุ้มเมื่อ request ห่างกันเกิน 5 นาที หรือ response ยาว
เข้าใจผิดบ่อย

"Claude เห็นรูปหรือเอกสารไปแล้วใน turn ก่อน turn หลังอ้างถึงได้เลยไม่ต้องส่งซ้ำ" ไม่ได้ API ไม่จำอะไรข้าม call ต้องมีตัวเนื้อหาหรือ file_id ในทุก request ที่ต้องใช้

สรุปสั้นๆ

เราถือ history เองและส่งทั้งหมดทุกครั้ง วาง breakpoint หลังของนิ่ง ก่อนของที่เปลี่ยน เลือก TTL ตามความถี่ของ request

ลองเดาก่อน

backend เก็บ msg_ ID จาก turn แรกไว้ แล้วใน turn ที่สองส่งแค่คำถามใหม่ Claude จะเห็นอะไร?

ดูเฉลย

เห็นแค่คำถามใหม่ API ไม่เก็บ history และ message ID ไม่ได้ใช้ดึง turn เก่า

Checkpoint 2

ผู้ช่วย HR cache คู่มือพนักงาน 50,000 token ไว้ แต่พนักงานถามห่างกันประมาณ 15–40 นาที ทำให้ cache หมดอายุแทบทุกครั้ง ควรปรับยังไง?

  1. เพิ่ม breakpoint อีกจุด
  2. ตั้ง ttl: "1h" บน block คู่มือ ยอมจ่ายค่าเขียนแพงขึ้นเพื่อไม่ต้องเขียนใหม่บ่อย
  3. ตัดคู่มือให้เล็กกว่าขนาดขั้นต่ำที่ cache ได้
  4. เปลี่ยนไปใช้ automatic caching
ดูเฉลย

B ช่วงห่างเกิน 5 นาทีคือเคสที่ TTL 1 ชั่วโมงคุ้ม breakpoint เพิ่มหรือ automatic caching ไม่ได้ยืดอายุ 5 นาที และถ้าเล็กกว่าขั้นต่ำก็ cache ไม่ได้เลย

Checkpoint 3

system prompt มี 2 block: block แรกเป็น style guide 8,000 token ที่ไม่เปลี่ยน block ที่สองเป็น "วันที่วันนี้: …" และ cache_control อยู่บน block ที่สอง cache_read_input_tokens เป็น 0 ตลอด แก้ยังไง?

  1. เพิ่ม TTL เป็น 1h
  2. ย้าย cache_control ไปไว้บน block style guide ให้ breakpoint อยู่ก่อนวันที่
  3. ใส่ cache_control เพิ่มบน block วันที่อีกอัน
  4. ย้ายวันที่ไปไว้ใน block แรก
ดูเฉลย

B ตอนนี้ prefix ที่ cache รวมวันที่ซึ่งเปลี่ยนทุกวันเข้าไปด้วย hash เลยไม่เคยซ้ำ ต้องให้ breakpoint จบก่อนส่วนที่เปลี่ยน

3. Tool call และ thinking block ใน request loop

Client-side tools

Claude ไม่ได้รันอะไรเอง ถ้าอยากใช้ tool response จะมี stop_reason: "tool_use" พร้อม tool_use block (ชื่อ tool + argument เป็น JSON) โค้ดเราเป็นคนรัน แล้วส่ง tool_result กลับใน user message ใหม่ต่อจาก assistant turn วนไปเรื่อยๆ ตราบใดที่ stop_reason เป็น tool_use ค่าอื่นแปลว่าจบลูป (เรื่องออกแบบ tool schema อยู่ในบทหลัง)

while True:
    resp = client.messages.create(model=MODEL, max_tokens=16000,
                                  tools=TOOLS, messages=messages)
    # append ทั้ง content ตามที่ได้มา รวม thinking block และ signature
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":
        break
    results = [{"type": "tool_result", "tool_use_id": b.id,
                "content": run_tool(b.name, b.input)}
               for b in resp.content if b.type == "tool_use"]
    messages.append({"role": "user", "content": results})

Server tools

  • web_search, web_fetch, code_execution, tool_search รันฝั่ง Anthropic เราไม่ต้องสร้าง tool_result เอง
  • ใน response จะเห็นเป็น server_tool_use block
  • ถ้า server loop ชน iteration cap จะได้ stop_reason: "pause_turn" ให้ส่ง conversation ใหม่โดยรวม response ที่ pause ไว้ เพื่อให้ทำต่อ

Thinking blocks

Extended และ adaptive thinking จะเพิ่ม thinking block ที่มี signature ใน tool loop ต้อง ส่งกลับแบบเดิมเป๊ะ รวมถึง block ที่ข้อความ thinking ว่างเปล่า วิธีที่ปลอดภัยสุดคือ append assistant message ตามที่ได้รับ ไม่ filter ตาม type ไม่ประกอบใหม่ ถ้าแก้ สลับลำดับ หรือตัดบางส่วนทิ้ง จะได้ 400 error

พฤติกรรมของ Claude Opus 5.5

  • Thinking ทำงานทุก request response จึงอาจขึ้นต้นด้วย thinking block
  • Thinking token คิดเงินเป็น output token แม้ไม่ได้ส่งข้อความกลับมา และนับรวมใน max_tokens (hard limit ของ thinking + คำตอบ) ค่าที่จูนไว้สมัยไม่มี thinking อาจทำให้คำตอบถูกตัด migration guide แนะนำเริ่มที่ราว 64k เมื่อใช้ effort xhigh หรือ max
  • คุมความลึกด้วย effort (ผ่าน output_config) ไม่ใช่ thinking budget default คือ medium ลดลงถ้าอยากใช้ thinking token น้อยลง
  • รูปแบบเก่า {"type": "enabled", "budget_tokens": N} ถูกแทนด้วย {"type": "adaptive"} + effort หรือไม่ใส่ field thinking เลย
  • thinking.display default เป็น "omitted" block จะมา thinking ว่างพร้อม signature ตั้งเป็น "summarized" ถ้าอยากได้สรุปที่อ่านได้ ถือว่าเป็น display text เท่านั้น

บน model ที่ยังใช้ manual extended thinking: budget_tokens ขั้นต่ำ 1,024, นับรวมใน max_tokens และต้อง น้อยกว่า max_tokens

# model รุ่นเก่าที่ยังใช้ manual budget
client.messages.create(
    model=OLDER_MODEL,
    max_tokens=20000,
    thinking={"type": "enabled", "budget_tokens": 12000},  # ต้อง >= 1024 และ < max_tokens
    messages=messages,
)
เข้าใจผิดบ่อย

"Thinking block เป็นแค่ข้อความโชว์ ตัดทิ้งเหลือแค่ tool_use ก็ได้" ไม่ได้ ต้องส่งกลับครบพร้อม signature ตัดหรือแก้ = 400

สรุปสั้นๆ

วนลูปตราบที่ stop_reason เป็น tool_use, server tool ไม่ต้องทำ tool_result เอง (ระวัง pause_turn), thinking block ส่งกลับครบทุกตัว และบน Opus 5.5 คุมด้วย effort ไม่ใช่ budget_tokens

Checkpoint 4

dev อยากประหยัด token เลยเขียนให้ agent สร้าง assistant turn ใหม่จากแค่ tool_use block ก่อนส่งกลับ ทั้งที่เปิด thinking อยู่ จะเกิดอะไรขึ้น?

  1. ทำงานได้และประหยัด token จริง
  2. Claude จะ thinking ใหม่ตั้งแต่ต้นโดยไม่มี error
  3. API ตอบ 400 เพราะ thinking block ถูกตัดทิ้ง
  4. ได้ stop_reason: "pause_turn"
ดูเฉลย

C การตัด thinking block ทิ้งนับเป็น partial drop ซึ่ง API ปฏิเสธ ต้อง echo assistant message กลับไปทั้งก้อน

Checkpoint 5

request บน model ที่ใช้ manual thinking ตั้ง max_tokens: 8000 และ budget_tokens: 10000 แล้วไม่ผ่าน validation แก้ยังไง?

  1. ลด budget_tokens ให้ต่ำกว่า max_tokens (และไม่ต่ำกว่า 1,024)
  2. ลบ max_tokens ออก
  3. ตั้ง max_tokens ให้เป็น 2 เท่าของ budget เป๊ะ
  4. ใส่ budget เป็นค่าติดลบ
ดูเฉลย

A budget ต้องอยู่ภายในเพดาน output ข้ออื่นไม่ใช่กฎของ API (max_tokens เป็น field บังคับ และไม่มีกฎอัตราส่วน 2 เท่า)

4. Streaming แบบ server-sent events

ใส่ "stream": true จะได้ server-sent events (SSE) UI โชว์ข้อความระหว่าง generate ได้ ถ้า max_tokens สูงมาก SDK จะ บังคับ ให้ stream เพื่อกัน HTTP timeout และ SDK มี helper ที่ stream ภายในแล้วคืน Message object ตัวเดียวกับที่ messages.create() คืน

Eventมีอะไร
message_startMessage object ที่ content ยังว่าง
content_block_start / content_block_delta / content_block_stopสร้าง block ทีละชิ้นจาก delta โดย index ตรงกับตำแหน่งใน content array สุดท้าย
message_deltaการเปลี่ยนระดับบน เช่น stop_reason และ output usage
message_stopจบ stream
ping, errorkeep-alive โผล่ได้ทุกจังหวะ และ error เช่น overloaded_error กลาง stream

ประเภท delta:

  • text_delta ชิ้นส่วนข้อความ
  • input_json_delta ชิ้นส่วน string ของ JSON สำหรับ input ของ tool_use ต้องเก็บต่อกันแล้ว parse ตอน content_block_stop (หรือใช้ helper ของ SDK)
  • thinking_delta ข้อความ thinking และมี signature_delta มาก่อน block ปิด signature นี้ต้องส่งกลับใน tool loop

overloaded_error กลาง stream เทียบเท่า HTTP 529 และ parser ควร ข้าม event type ที่ไม่รู้จัก แทนที่จะ crash เพราะอาจมี type ใหม่เพิ่มในอนาคต

# ให้ SDK รวม event ให้ แล้วเอา Message ตัวเต็มตอนจบ
with client.messages.stream(model=MODEL, max_tokens=128000,
                            messages=messages) as stream:
    for chunk in stream.text_stream:      # โชว์ข้อความทีละชิ้น
        print(chunk, end="", flush=True)
    final = stream.get_final_message()    # Message เต็ม เหมือน create()
เข้าใจผิดบ่อย

"input_json_delta แต่ละตัวเป็น JSON object ครบ parse ได้เลย" ไม่ใช่ มันเป็นแค่เศษ string ต้องต่อให้ครบก่อน

สรุปสั้นๆ

message_start → (block start/delta/stop)* → message_delta → message_stop มี ping กับ error แทรกได้ เก็บ JSON delta ให้ครบก่อน parse และข้าม event ที่ไม่รู้จัก

Checkpoint 6 (เติมคำ)

ใช้ with client.messages.stream(..., max_tokens=128000) as s: แล้วต้องการ Message object ตัวเต็มตอนจบ เพื่อเอาไป append ลง history ต้องเรียก method อะไร?

ดูเฉลย

s.get_final_message() รวมทุก event เป็น Message ที่สมบูรณ์ ส่วน text_stream ให้แค่ชิ้นส่วนข้อความ ไม่ใช่ message ทั้งก้อน

5. รูปภาพและไฟล์

รูปคือ content block ใน user turn มี source 3 แบบ:

  • base64 ฝัง byte ลงไปเลย ต้องระบุ media_type
  • url รูปที่ host ไว้
  • file ไฟล์ที่อัปโหลดผ่าน Files API อ้างด้วย file_id

media type ที่รองรับ: image/jpeg, image/png, image/gif, image/webp และควรวาง image block ก่อน text ที่ถามถึงรูป

{"role": "user", "content": [
  {"type": "image", "source": {"type": "base64",
     "media_type": "image/png", "data": "iVBORw0KGgo..."}},
  {"type": "text", "text": "ในรูปนี้มี error อะไร"}
]}

ต้นทุนของ stateless และทางออก: Files API
