4.1 Claude API error types และ recovery strategies

ต้นฉบับ: CertSafari 4.1

อ่านจบแล้วควรทำได้
  • ดู status code กับ error type แล้วแยกได้ทันทีว่า "ต้องแก้ request" หรือ "retry ได้"
  • รู้ว่า SDK retry อะไรให้เองอัตโนมัติ และตั้ง max_retries อย่างตั้งใจ
  • แก้ 413 และ timeout ด้วยการลดขนาด payload หรือเปลี่ยน transport ไม่ใช่ retry
  • แยก 429 จาก rate limit, จาก acceleration limit, จาก spend cap และ 400 จาก spend limit ที่เราตั้งเองได้ พร้อมวิธีรับมือแต่ละแบบ
  • เลือกระหว่าง แก้ request / รอ SDK retry / เปลี่ยน transport / escalate จากหลักฐานใน call ที่ fail
  • อ่าน status, error type, request ID และ headers เพื่อบอกว่าปัญหาอยู่ที่ integration layer หรือที่ output ของโมเดล
แนวคิดหลัก: ต้นเหตุของ error กำหนดวิธีแก้

4xx = request, key, account หรือ payload ต้องเปลี่ยนก่อน ถึงจะผ่าน ส่ง request เดิมซ้ำกี่รอบก็ไม่ผ่าน
5xx หรือ 429 แบบชั่วคราว = ส่ง request เดิมซ้ำพร้อม backoff แล้วมีโอกาสผ่าน
จัดกลุ่มผิดเมื่อไหร่ จะเจออย่างใดอย่างหนึ่ง: retry วนไม่จบ หรือไปนั่ง debug โค้ดที่ไม่ได้พัง

1. แยก error: แก้ request หรือ retry

Error body ของ Claude API หน้าตาเหมือนกันหมด คือ JSON ที่มี object error (ข้างในมี type กับ message) และมี request_id ID เดียวกันนี้อยู่ใน header request-id ของทุก response ด้วย ส่วนใน Python/TypeScript SDK อ่านได้จาก _request_id ให้ log ค่านี้ทุกครั้งที่ fail

{
  "type": "error",
  "error": {
    "type": "not_found_error",
    "message": "model: claude-foo-9 ไม่มีอยู่จริง"
  },
  "request_id": "req_011CExample..."
}
Status / typeสาเหตุทำยังไง
400 invalid_request_errorformat หรือเนื้อหาของ requestแก้ request ห้าม retry แบบเดิม
401 authentication_errorkey ผิดรูปแบบ ถูก revoke หรือหมดอายุแก้ key
402 billing_errorปัญหา billing/การจ่ายเงินเช็ก payment ใน Claude Console
403 permission_errorkey ไม่มีสิทธิ์เข้าถึง resourceเช็กสิทธิ์ใน org และ workspace
404 not_found_errorหา resource ไม่เจอเช็ก endpoint path และ ID
409 conflict_errorชนกับ state ปัจจุบันของ resourceแก้ conflict ก่อน แล้วค่อย retry
413 request_too_largerequest ใหญ่เกิน byte limitลด payload ให้ต่ำกว่า limit
429 rate_limit_errorชน rate limit หรือ spend capขึ้นอยู่กับว่า limit ไหน (หัวข้อ 4)
500 api_errorerror ฝั่ง server ที่ไม่คาดคิดretry + exponential backoff ถ้ายังเป็นอยู่ แจ้ง support พร้อม request ID
504 timeout_errorประมวลผลนานจน timeoutใช้ streaming Messages API กับ request ยาวๆ
529 overloaded_errorAPI overload ชั่วคราวretry + backoff
  • 409 เป็น 4xx ตัวเดียวที่ retry เองได้ แต่ต้อง แก้ต้นเหตุก่อน เช่น มีสอง process แก้ resource เดียวกันพร้อมกัน หรือค่าที่ต้อง unique ถูกใช้ไปแล้ว ถ้า retry โดยไม่จัดให้ทำทีละตัว ก็ชนซ้ำเหมือนเดิม
  • 500 ไม่ได้เกิดจาก request ของเรา backoff แล้ว retry ถ้ายังไม่หายค่อยเปิด ticket แนบ request ID
  • อาจมี type ใหม่ๆ โผล่มาในอนาคต ให้ branch ตาม type ที่รู้จัก แล้วจัดการ type ที่ไม่รู้จักตามกลุ่ม status (4xx/5xx)

อ่าน trace ของ call ที่ fail

  • Status + error.type บอกว่าอยู่กลุ่มไหน
  • message มักบอกต้นเหตุตรงๆ เช่น 400 เรื่อง thinking block จะขึ้นต้นด้วยตำแหน่งของ block ที่ผิด อย่าง messages.1.content.0
  • Headers ถ้ามี retry-after แปลว่ารอแล้วผ่าน ถ้าเป็น 429 ที่ ไม่มี retry-after และ error.details.error_code เป็น enforced_spend_limit_reached แปลว่ารอไปก็ไม่ช่วย
  • request_id ผูก log ของเรา, error body และ support ticket ให้ชี้ไปที่ call เดียวกัน

ดู pattern จากหลายๆ trace ก็ช่วยได้:

  • call เดิม fail เหมือนเดิมทุกครั้ง → สงสัย request, key หรือ account
  • 5xx ที่ retry รอบถัดไปก็หาย → ฝั่ง server
  • 429 ที่ผ่านไปหลายชั่วโมงยังไม่หาย → spend cap ไม่ใช่ limit รายนาที

จุดแบ่งแรกที่ต้องดู: ถ้าได้ error body แปลว่า integration layer พังและไม่มี output เลย แต่ถ้าได้ 200 สะอาดๆ แต่ผลผิด คำถามจะย้ายไปที่ output ของโมเดล (ดูบทเรื่อง stop reason)

ระวัง streaming: error อาจมาระหว่าง stream หลังจากที่ API ตอบ 200 ไปแล้ว ดังนั้น 200 ไม่ได้การันตีว่าสำเร็จ

เข้าใจผิดบ่อย

"ได้ 200 แล้ว ถ้ามีอะไรผิดก็ต้องเป็นที่ output ของโมเดล" ไม่เสมอ ตอน streaming error เกิดกลาง stream หลัง 200 ได้ และไม่ผ่าน error handling แบบปกติ

สรุปสั้นๆ

4xx แก้ request (ยกเว้น 409 แก้ conflict แล้ว retry), 5xx/429 ชั่วคราว retry พร้อม backoff log request_id ทุกครั้ง และอย่าเชื่อ 200 ตอน streaming

Checkpoint 1

คุณใช้ Python SDK ได้ msg = client.messages.create(...) กลับมา แล้วอยากเก็บค่าที่ใช้ทำ support ticket กับ Anthropic ได้ ควรอ่าน attribute ไหน?

  1. msg.id
  2. msg._request_id
  3. msg.stop_reason
  4. msg.request_id
ดูเฉลย

B SDK เก็บ request ID ไว้ที่ _request_id ส่วน id คือ message ID ซึ่งเป็นคนละตัวกัน

Checkpoint 2

cron job สองตัวเริ่มพร้อมกันพอดีและแก้ resource เดียวกัน ตัวหนึ่งได้ 409 conflict_error ควรทำยังไง?

  1. เพิ่ม max_retries ให้ SDK จัดการ
  2. ถือว่าเป็นปัญหาฝั่ง server แล้วแจ้ง support
  3. จัดให้สอง job ทำงานทีละตัว แล้วค่อย retry
  4. ไม่ retry เลย เพราะเป็น 4xx
ดูเฉลย

C 409 retry ได้ แต่ต้องแก้ต้นเหตุ (การชนกัน) ก่อน ถ้า retry เฉยๆ ก็ชนซ้ำ และ SDK ไม่ retry 4xx ให้อยู่แล้ว

Checkpoint 3

สคริปต์ ingest เอกสารได้ 429 เป็นพักๆ และ response มี header retry-after แต่โค้ด retry ของทีมยิงซ้ำทันทีแบบ tight loop ควรแก้ยังไง?

  1. สลับ API key หลายตัวเพื่อให้ได้ bucket ใหม่
  2. อ่าน retry-after แล้วรออย่างน้อยเท่านั้น และเพิ่ม backoff ถ้าเจอ 429 ซ้ำ
  3. ลด max_tokens
  4. เปลี่ยนไปใช้ batch แล้ว poll
ดูเฉลย

B rate limit คิดระดับ organization การสลับ key ไม่ได้ bucket ใหม่ และ max_tokens ไม่เกี่ยวกับ limit จำนวน request

2. สิ่งที่ SDK จัดการให้ก่อนถึงโค้ดเรา

SDK แปลง error JSON เป็น typed exception ให้ เช่นใน Python 404 จะ raise anthropic.NotFoundError ให้ branch ด้วย exception class ไม่ใช่ไปจับข้อความใน message และ catch class ที่เจาะจงที่สุดก่อน (ส่วน Go ใช้ type เดียวคือ *anthropic.Error แล้ว branch ด้วย StatusCode)

SDK retry ให้เอง 2 ครั้งโดย default พร้อม exponential backoff สำหรับ connection error, rate limit (429) และ 5xx และเคารพ retry-after ถ้ามี ปรับจำนวนหรือปิดได้ด้วย max_retries

import anthropic

client = anthropic.Anthropic(max_retries=0)   # หน้าจอผู้ใช้: ไม่อยากให้รอนาน

try:
    msg = client.messages.create(...)
except anthropic.BadRequestError as e:        # 400: แก้ request ไม่ต้อง retry
    log.error("bad request %s", e.request_id)
except anthropic.RateLimitError as e:         # 429: ดูต่อว่าเป็น limit แบบไหน
    handle_429(e)
except anthropic.APIStatusError as e:         # กลุ่มที่เหลือ จัดการตาม status
    log.error("status=%s id=%s", e.status_code, e.request_id)

สิ่งที่ต้องคิดตอน debug:

  • error ที่ retry ได้แต่หลุดมาถึงโค้ดเรา แปลว่ามันผ่าน backoff ของ SDK มาแล้ว ปัญหาค่อนข้างถาวร
  • เอา retry loop ของเราไปครอบอีกชั้น = จำนวนครั้งคูณกัน (เช่น ลูป 3 รอบ × SDK 3 ครั้ง = 9 call)
  • ตั้ง max_retries ให้เท่ากับที่อยากได้จริง และจัดการ 4xx เอง เพราะ SDK ไม่ retry 4xx

4 ทางเลือกในการ recover

Moveใช้กับ
1. แก้ request400, 401, 402, 403, 404, 413 (ส่งซ้ำยังไงก็ไม่ผ่าน)
2. รอให้ SDK retry429 ที่มี retry-after, 500, 529
3. เปลี่ยน transport504 หรือ call ยาวแบบ non-streaming → ย้ายไป streaming หรือ Message Batches API

  • request ที่ผู้ใช้รออยู่ (latency-sensitive) ลด max_retries หรือตั้งเป็น 0 แล้วแสดง fallback ให้เร็ว
  • batch job ตอนกลางคืน รอ backoff นานได้ ใช้ default หรือเพิ่มขึ้น
  • error ที่รอดจาก retry มาได้ถือเป็นหลักฐาน ให้ log request ID แล้ว escalate อย่าวนต่อ
  • 409 คือ 4xx ตัวเดียวที่ควร retry เอง และต้องหลังแก้ conflict แล้วเท่านั้น

SDK retry connection/429/5xx ให้ 2 ครั้ง ไม่ retry 4xx อย่าครอบ loop ซ้ำ ตั้ง max_retries ตามบริบท และเลือก 1 ใน 4 move ตามหลักฐาน

  1. 403 permission_error

Checkpoint 5

service หนึ่งได้ 429 rate_limit_error หลัง SDK retry ครบแล้ว response ไม่มี retry-after และ error.details.error_code = enforced_spend_limit_reached ทางไหนเหมาะสุด?

  1. ครอบด้วย backoff loop ของตัวเองอีกชั้น
  2. เพิ่ม max_retries เป็น 10
  3. หยุด retry แล้ว escalate: ขอขึ้น tier หรือรอจนสิทธิ์กลับมา
  4. ตัด prompt ให้สั้นลงแล้วส่งใหม่
ดูเฉลย

C นี่คือ spend cap ไม่ใช่ limit รายนาที retry กี่รอบก็ไม่ผ่าน และขนาด request ไม่เกี่ยว

3. Request ใหญ่เกิน และ call ที่ใช้เวลานาน

413 request_too_large คือ limit เรื่อง ขนาดเป็น byte โมเดลไม่เคยเห็น request นี้เลย บน direct API มันถูก Cloudflare ตีกลับก่อนถึง API server ด้วยซ้ำ เปลี่ยนคำใน prompt, เปลี่ยน model หรือปรับ max_tokens ไม่ช่วยอะไร ทางเดียวคือทำ payload ให้เล็กลง

Endpointขนาด request สูงสุด
Messages API32 MB
Token Counting API32 MB
Batch API256 MB
Files API500 MB

504 timeout_error เป็นปัญหาแบบเดียวกันแต่วัดเป็นเวลา วิธีแก้คือใช้ streaming Messages API กับ request ที่ยาว

อีกเคสคือ idle connection: บาง network ตัด connection ที่เงียบนานๆ ทิ้ง ถ้ายิง non-streaming พร้อม max_tokens สูงๆ อาจค้างหรือ fail โดยไม่มี response จาก Anthropic เลย

  • SDK ตั้ง TCP keep-alive ให้ และเช็กว่า non-streaming request ไม่น่าจะเกิน 10 นาที ถ้าเช็กไม่ผ่านให้เปลี่ยนไป streaming
  • ใช้ streaming แล้ว SDK รวม stream ให้ได้ Message ตัวเต็มเหมือน non-streaming ได้ โค้ดฝั่งเราแทบไม่ต้องเปลี่ยน
  • อีกทางคือ Message Batches API ที่ส่งไปแล้วค่อย poll ผล ไม่ต้องถือ connection ค้างไว้
# เปลี่ยนเป็น streaming แต่ยังได้ Message ตัวเต็มเหมือนเดิม
with client.messages.stream(model=MODEL, max_tokens=64000, messages=msgs) as s:
    msg = s.get_final_message()
เข้าใจผิดบ่อย

"413 คือ capacity เต็ม retry หรือเปลี่ยนไปใช้ model ที่ context ใหญ่กว่าก็หาย" ไม่ใช่ 413 ถูกตีกลับด้วยขนาด byte ก่อนถึง server ต้องลด payload อย่างเดียว

สรุปสั้นๆ

413 = ใหญ่เกิน byte → ลดขนาด, 504 / call ยาว → streaming หรือ Batches ไม่ใช่ retry

Checkpoint 6

ทีมแนบ PDF สแกนความละเอียดสูงหลายไฟล์ไปใน Messages API call เดียว แล้วได้ 413 วิธีไหนแก้ได้?

  1. เปลี่ยนไปใช้ model ที่มี context window 1M
  2. ลดขนาด body ให้ต่ำกว่า 32 MB เช่น ลดความละเอียดหรือแบ่งเป็นหลาย call
  3. ลด max_tokens
  4. retry พร้อม exponential backoff
ดูเฉลย

B ปัญหาคือ byte ของ request ซึ่งไม่เกี่ยวกับ token window, output limit หรือจังหวะเวลา

4. แยก 429 แต่ละแบบ และ 400 ที่หน้าตาเหมือน quota

ลองเดาก่อน

ทุก request จาก worker ตัวหนึ่งได้ 429 rate_limit_error และ SDK retry ก็ fail ต่อเนื่องเป็นชั่วโมง น่าจะเป็นเพราะอะไร?

ดูเฉลย

น่าจะชน monthly spend cap ของ usage tier ไม่ใช่ limit รายนาที (ซึ่งหายเร็ว) และไม่ใช่ spend limit ที่เราตั้งเอง (อันนั้นตอบ 400)

  • limit รายนาทีอาจถูกบังคับในช่วงเวลาที่สั้นกว่านั้น เช่น 60 RPM อาจถูกคุมเป็น 1 request/วินาที ยิงเป็นชุดพร้อมกันก็ชนได้แม้ค่าเฉลี่ยดูไม่เกิน
  • acceleration limit เกิดจาก usage ที่ เพิ่มขึ้นแรงๆ ไม่ใช่จาก rate ที่คงที่ ค่อยๆ ramp up จะช่วยได้
  • spend-cap 429 ใช้ type เดียวกับ rate limit (rate_limit_error) ต้องดูที่ retry-after ที่หายไปและ error_code

เข้าใจผิดบ่อย

"400 invalid_request_error ทุกตัวแปลว่า body ผิด ต้องแก้ body" ไม่เสมอ spend limit ที่เราตั้งเองก็ตอบ 400 ทั้งที่ body ถูกต้อง สิ่งที่ต้องทำคือปรับ limit

"429 rate_limit_error ทุกตัว ปล่อย SDK retry ไปเรื่อยๆ เดี๋ยวก็หาย" ไม่ใช่ spend-cap 429 ไม่มี retry-after และ fail จนกว่าสิทธิ์จะกลับมา ต้องเช็ก error_code

สรุปสั้นๆ

มี retry-after → รอ, ไม่มี + enforced_spend_limit_reached → หยุดแล้ว escalate, 400 "specified API usage limits" → ไปปรับ limit ของเราเอง

จับคู่ response กับสิ่งที่ควรทำ:

  1. 429 มี retry-after: 20 และ message บอกว่าเกิน OTPM
  2. 429 ไม่มี retry-after, error_code = enforced_spend_limit_reached
  3. 400 message ขึ้นต้น "You have reached your specified API usage limits"
  4. 500 api_error
ดูเฉลย

1 → รอ 20 วินาทีแล้ว retry · 2 → หยุด retry ขึ้น tier หรือรอสิทธิ์กลับมา · 3 → เพิ่มหรือเอา spend limit ที่ตั้งเองออก · 4 → retry + backoff ถ้าไม่หายแจ้ง support พร้อม request ID

Checkpoint 8

agent มี tool query_inventory ที่รันฝั่ง client วันหนึ่ง database ล่ม executor โยน exception โค้ดส่ง tool_result ที่มี is_error: true พร้อมข้อความ error กลับไป Claude ตอบผู้ใช้ว่า "ขออภัย ตอนนี้เช็กสต็อกไม่ได้ ระบบฐานข้อมูลอาจมีปัญหา" ต้นเหตุจริงอยู่ที่ไหน?

  1. Claude ควร retry tool เองอัตโนมัติ เลยเป็นความผิดของโมเดล
  2. Integration layer: executor fail ก่อนที่โมเดลจะได้คิดอะไร Claude ตอบสนองต่อสัญญาณ error ได้ถูกต้องแล้ว
  3. is_error ใช้ได้แค่ตอนชื่อ tool ผิด จึงใช้ผิดที่
  4. ควรจูน prompt ไม่ให้ Claude พูดถึง error
ดูเฉลย

B การ retry tool เป็นหน้าที่ของ application, is_error เป็น flag สำหรับ failure ทั่วไป และการซ่อน error จะทำให้ปัญหาจริงไม่มีใครเห็น
