1.3 Agent patterns, frameworks, subagents และ memory

ต้นฉบับ: CertSafari 1.3

อ่านจบแล้วควรทำได้
  • จับคู่งานกับ pattern ได้: prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer หรือ autonomous agent
  • บอกได้ว่าใครหมุน tool-use loop (โค้ดเรา, server ของ Anthropic, Agent SDK หรือ framework) และเมื่อไหร่ควรเรียก API ตรงๆ
  • ใช้ subagent เพื่อกันงานสำรวจไม่ให้ไปรก context window หลัก
  • resume subagent ข้าม query() ได้ด้วย session ID และ agent ID
  • แยก memory file ที่อยู่ข้าม session ออกจาก context window ที่อยู่แค่ session เดียว
แนวคิดหลัก: เริ่มจากโครงที่ง่ายที่สุดที่ใช้ได้

ใน workflow โค้ดเราล็อกเส้นทางของการเรียก LLM ไว้ ใน agent โมเดลเลือกขั้นต่อไปเอง ใช้ agent ก็ต่อเมื่อ รู้ขั้นตอนล่วงหน้าไม่ได้จริงๆ เท่านั้น

1. Workflow pattern 5 แบบ (+ autonomous agent)

Patternหน้าตาใช้เมื่อ
Prompt chainingลำดับตายตัว แต่ละ call ใช้ output ของ call ก่อน คั่นด้วย code gate ตรวจระหว่างขั้นได้งานแตกเป็นขั้นที่รู้ล่วงหน้า เช่น ร่าง → แปล
Routingclassifier ส่ง input ไปที่ prompt หรือ model เฉพาะทางinput แบ่งเป็นหมวดชัดเจน
Parallelizationsectioning (งานย่อยอิสระรันพร้อมกัน) หรือ voting (งานเดียวกันรันหลายรอบ)งานย่อยไม่พึ่งกัน, อยากได้ความเร็ว หรืออยากได้ความมั่นใจเพิ่ม
Orchestrator-workersLLM ตัวกลางแตกงานตอนรันแล้วส่งให้ workerเดางานย่อยล่วงหน้าไม่ได้
Evaluator-optimizerตัวหนึ่ง generate อีกตัว critique แล้ววนซ้ำมีเกณฑ์ประเมินชัด และการ refine ช่วยได้จริงแบบวัดผลได้
Autonomous agentโมเดลเลือก tool call เองใน feedback loopจำนวนขั้นเปิดกว้าง และแต่ละขั้นเช็กกับความจริงได้
  • Sectioning vs orchestrator-workers: sectioning งานย่อยถูก hardcode ไว้ในโค้ด ส่วน orchestrator-workers โมเดลเป็นคนคิดงานย่อยตอนรัน
  • Voting: ให้หลาย prompt ทำงานเดียวกัน เช่น ตรวจโค้ดหาช่องโหว่ด้วย prompt คนละแบบ แล้วรวมคำตัดสิน
  • เรื่องความเร็ว: subagent ที่รันพร้อมกันเสร็จเมื่อตัวที่ช้าที่สุดเสร็จ ไม่ใช่เวลาของทุกตัวบวกกัน
  • Trade-off: ระบบ agentic โดยทั่วไปเอา latency กับ cost ไปแลกกับผลงานที่ดีขึ้น
# voting: ส่ง diff เดียวกันให้ prompt หลายแบบ แล้ว flag ถ้ามีตัวไหนเจอปัญหา
import asyncio

PROMPTS = ["หา SQL injection", "หา XSS", "หา secret ที่หลุดในโค้ด"]

async def vote(diff):
    verdicts = await asyncio.gather(*(llm(p, diff) for p in PROMPTS))
    return any(v.found_issue for v in verdicts)   # กฎการรวมผลอยู่ในโค้ดเรา
เข้าใจผิดบ่อย

"งานซับซ้อนหลายขั้น ต้องใช้ autonomous agent เสมอ" ไม่ใช่ เริ่มจากง่ายก่อน workflow ตายตัวหรือการเรียก LLM ครั้งเดียวมักชนะทั้งเรื่องต้นทุนและความคาดเดาได้

2. ใครหมุน tool-use loop

ลูปพื้นฐาน: Claude ขอ tool → tool ทำงาน → ผลกลับไปหา Claude คำถามออกแบบคือ ใครเป็นคนหมุนลูปนี้

ตัวบอกว่าลูปควรทำอะไรต่อคือ stop_reason:

stop_reasonความหมาย / ต้องทำอะไร
tool_useClaude ขอเรียก client tool → เรารันแล้วส่ง tool_result กลับ
end_turnได้คำตอบสุดท้ายแล้ว
max_tokensชนเพดาน token ของ response
stop_sequenceเจอ stop sequence ที่ตั้งไว้
refusalโมเดลปฏิเสธ
pause_turnserver tool วนครบ iteration limit → ส่ง conversation กลับไปใหม่ รวม response ที่ถูก pause ด้วย เพื่อให้ Claude ทำต่อ
# ลูปที่เราหมุนเองบน Messages API
while True:
    resp = client.messages.create(model=MODEL, messages=msgs, tools=TOOLS, max_tokens=2048)
    msgs.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason == "tool_use":
        msgs.append({"role": "user", "content": run_client_tools(resp.content)})  # เราสร้าง tool_result เอง
    elif resp.stop_reason == "pause_turn":
        continue          # server tool ยังไม่เสร็จ ส่ง conversation (รวม response ที่ pause) กลับไปใหม่
    else:
        break             # end_turn / max_tokens / stop_sequence / refusal

ดูเฉลย

C web_fetch เป็น server tool ที่ Anthropic รันให้ เราไม่ต้องสร้างผลของมันเลย

คนหมุนลูปโค้ดเราทำอะไรTrade-off
โค้ดเราบน Messages APIวนตาม tool_use, รัน tool, ส่ง tool_result, จัดการ stop อื่นๆเห็นและคุมทุกอย่าง แต่ต้องเขียนลูปเองทั้งหมด
Server ของ Anthropic (web_search, web_fetch, code_execution)เปิด tool และส่งซ้ำเมื่อเจอ pause_turniteration เกิดนอกสายตาเรา
Claude Agent SDK query()วนอ่าน message ที่ถูก yield (AssistantMessage, UserMessage, ResultMessage)ได้ built-in tools, subagents, hooks, session ID และไม่ต้องเขียนลูปเอง
Third-party frameworks (Strands Agents SDK ของ AWS, LangGraph, PydanticAI)config agent object ของ frameworkเริ่มได้เร็ว แต่ prompt ถูกซ่อน debug ยาก
  • Agent SDK รัน tool และวนไปจนไม่เหลือ tool call แล้ว yield ResultMessage ที่มี final text, token usage, cost และ session ID
  • Frameworks ช่วยให้เรียกโมเดล นิยาม tool และต่อ call ง่ายขึ้น แต่แลกกับ abstraction ที่บัง prompt จริง
  • เรียก API ตรงๆ เมื่อ: pattern นั้นเขียนไม่กี่บรรทัดก็ได้ หรือเราต้องเห็นแบบเป๊ะๆ ว่า Claude ได้รับอะไรไป
เข้าใจผิดบ่อย

"Server tool อย่าง web_search ต้องให้โค้ดเราเป็นคนรัน" ไม่ใช่ Anthropic รันให้ หน้าที่เรามีแค่เปิดใช้งานและจัดการ pause_turn

Client tool = เรารันเอง, server tool = Anthropic รัน, Agent SDK = SDK รันให้แล้วจบด้วย ResultMessage, framework = สะดวกแต่มองไม่เห็น prompt

3. Subagent เป็นกลยุทธ์จัดการ context window

Context window บรรจุทุกอย่าง: system prompt, messages ทั้งหมด, tool results และ tool definitions ยิ่งเต็มยิ่งแย่ ความแม่นและการจำรายละเอียดลดลง เรียกว่า context rot และตัวที่ทำให้เต็มเร็วที่สุดคือ tool results

Subagent แก้ปัญหานี้ด้วย isolation: แต่ละตัวมีบทสนทนาของตัวเอง tool call ระหว่างทางอยู่ในนั้น และส่งกลับไปหาตัวแม่แค่ ข้อความสุดท้าย เหมือนส่งเด็กฝึกงานไปขุดเอกสาร 100 หน้า แล้วกลับมาเล่าให้ฟัง 5 บรรทัด

ประโยชน์อื่น: รันขนานได้, มี system prompt เฉพาะทาง และจำกัด tool ต่อ subagent ได้

  • นิยาม subagent ได้ทาง option agents ของ query() หรือเป็นไฟล์ markdown ใน .claude/agents/
  • Claude ยังเรียก general-purpose subagent ที่ built-in มาได้ผ่าน Agent tool
  • Compaction เป็นอีกเครื่องมือสำหรับบทสนทนายาวๆ เส้นเดียว: server แทนที่ turn เก่าๆ ด้วยสรุปที่ Claude เขียนเอง (เรื่อง context discipline อยู่บท 6.1)
# นิยาม subagent ด้วย AgentDefinition
from claude_agent_sdk import AgentDefinition, ClaudeAgentOptions

opts = ClaudeAgentOptions(agents={
    "log-digger": AgentDefinition(
        description="ใช้เมื่อต้องค้นและสรุป log ขนาดใหญ่",   # Claude ใช้ตรงนี้ตัดสินว่าจะ delegate เมื่อไหร่
        prompt="คุณเชี่ยวชาญการอ่าน log หา error pattern และสรุปสาเหตุแบบสั้น",
        tools=["Read", "Grep", "Bash"],                    # Bash ไว้รัน jq/zcat ได้
    )
})
สรุปสั้นๆ

tool results คือตัวการทำ context เต็ม ส่งงานขุดข้อมูลไปให้ subagent แล้วรับกลับมาแค่ข้อความสุดท้าย context ของตัวแม่จะสะอาด

4. Resume subagent ข้าม query

โดย default ทุก query() เปิด session ใหม่ ถ้าถามต่อโดยไม่ resume ก็เท่ากับให้ทำงานเดิมซ้ำตั้งแต่ศูนย์ ต้องใช้ ID สองตัว:

IDหาได้จากเอาไปใช้ยังไง
Session IDResultMessageใส่เป็น resume ใน options ของ query ถัดไป เพื่อกู้ transcript
Agent IDข้อความใน result ของ Agent tool (agentId: ...)ใส่ไว้ใน prompt เพื่อบอกให้ Claude ทำงานต่อกับ subagent ตัวนั้น
import re
from claude_agent_sdk import query, ClaudeAgentOptions, ResultMessage

def find_agent_id(text):
    m = re.search(r"agentId:\s*([\w-]+)", text)   # ดึง agentId จากข้อความผลของ Agent tool
    return m.group(1) if m else None

session_id = agent_id = None
async for msg in query(prompt="ใช้ subagent endpoint-finder หา endpoint ที่ไม่มี auth"):
    # ... ตรงที่เจอ ToolResultBlock ของ Agent tool: agent_id = find_agent_id(text)
    if isinstance(msg, ResultMessage):
        session_id = msg.session_id

# รอบสอง: resume session เดิม + ระบุ agent ID ใน prompt
async for msg in query(
    prompt=f"ให้ subagent {agent_id} ไล่ต่อว่า endpoint ไหนเข้าถึง PII ได้",
    options=ClaudeAgentOptions(resume=session_id),
):
    ...

maxTurns: ถ้า subagent ชนเพดาน turn ผลที่ส่งกลับจะถูกมาร์กว่าเป็น partial การ resume ทำให้มันทำต่อจนจบได้โดยใช้ context ที่สะสมไว้แล้ว ไม่ต้องเริ่มขุดใหม่

เข้าใจผิดบ่อย

"เรียก query() รอบใหม่ แล้วมันจะคุยกับ subagent ตัวเดิมได้เอง" ไม่ได้ ต้อง resume session ด้วย ID และระบุ agent ID ใน prompt ทั้งสองอย่าง

สรุปสั้นๆ

session ID (จาก ResultMessage) → resume, agent ID (จาก Agent tool result) → ใส่ใน prompt ทั้งสองตัวมีหลังรอบแรกจบเท่านั้น

5. Memory ที่อยู่ได้นานกว่า session

Context window คือ working memory ที่หายไปพร้อม session การ resume แค่ต่อ transcript เดิมไปข้างหน้า และ compaction แค่ทำให้บทสนทนาเส้นเดียวไม่ล้นลิมิต ทั้งสองอย่าง ไม่ได้ทำให้เกิดการเรียนรู้ข้าม session

ตัวที่ทำได้คือ memory tool: Claude สร้าง อ่าน แก้ และลบไฟล์ใต้ /memories ได้ และไฟล์พวกนี้อยู่ข้าม session

  • Workflow: เมื่อเปิดใช้ Claude จะเช็ก memory directory ก่อนเริ่มงาน แล้วจดสิ่งที่เรียนรู้ลงไประหว่างทำ
  • Just-in-time retrieval: โหลดไฟล์เฉพาะตอนที่ต้องใช้ context ที่ active อยู่เลยเล็ก
  • Client-side execution: Claude แค่ ขอ file operation ส่วนแอปเราเป็นคนทำจริงบน storage ที่เราคุม แล้วส่ง tool_result กลับ เราจึงเป็นคนกำหนดว่าข้อมูลอยู่ที่ไหนและใครเข้าถึงได้
  • Schema: Anthropic เผยแพร่ schema ไว้ และ Claude ถูก train มากับมัน เลยเรียกได้แม่นกว่า tool ที่เราทำเลียนแบบเอง

from pathlib import Path
ROOT = Path("/srv/agent-memories")   # เราเลือกเองว่าเก็บที่ไหน

def handle_memory(cmd):
    p = (ROOT / cmd["path"].removeprefix("/memories/")).resolve()
    if not p.is_relative_to(ROOT):    # guardrail: ห้ามออกนอกโฟลเดอร์
        return "error: invalid path"
    if cmd["command"] == "view":
        return p.read_text() if p.is_file() else "\n".join(x.name for x in p.iterdir())
    if cmd["command"] == "create":
        p.parent.mkdir(parents=True, exist_ok=True)

เข้าใจผิดบ่อย

"ให้ long-term memory ด้วยการโหลดทุกอย่างที่เคยเจอเข้า context ตั้งแต่เริ่ม session" ไม่ใช่ memory file ถูกอ่าน on demand การยัดทุกอย่างเข้าไปตั้งแต่แรกคือการเร่ง context rot

สรุปสั้นๆ

context window = สมุดทดที่ทิ้งเมื่อจบ session, memory tool = แฟ้มถาวรที่ Claude เปิดเฉพาะหน้าที่ต้องใช้ และแฟ้มนั้นอยู่บน storage ของเรา
