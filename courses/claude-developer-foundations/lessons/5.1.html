5.1 How LLMs work: tokens, context window และ sampling

ต้นฉบับ: CertSafari 5.1

อ่านจบแล้วควรทำได้
  • อธิบายได้ว่า token คืออะไร และประมาณจำนวน token จากความยาวข้อความได้
  • อธิบายว่าการ generate ทีละ token ทำให้ข้อความลื่นไหลแต่แต่งเรื่องขึ้นได้ และรู้ว่าการแต่งมักไปกองอยู่ตรงไหน
  • บอกได้ว่าอะไรนับเข้า context window บ้าง และ model ไหนรับ input ขนาดเท่าไหร่ได้
  • อธิบายว่าทำไมตัวอย่างใน prompt ถึงคุมผลลัพธ์ได้โดยไม่ต้อง retrain
  • อธิบายว่าทำไม prompt เดิมได้ผลต่างกัน และ temperature, top_k, top_p คุมอะไร
  • ออกแบบ test, cache และงบค่าใช้จ่ายที่ทนต่อ non-determinism ได้
แนวคิดหลัก: autocomplete ที่เก่งมาก

LLM อ่านและเขียนเป็น token ทีละตัว แต่ละขั้นเลือก token ถัดไปจากความน่าจะเป็น โดยมองเห็นได้แค่สิ่งที่อยู่ใน context window เรื่องอื่นในบทนี้ ทั้ง hallucination, few-shot และผลที่ไม่เหมือนเดิมทุกครั้ง ล้วนมาจากกลไกนี้ทั้งนั้น

1. Token: หน่วยที่โมเดลอ่านและเขียน

โมเดลไม่ได้มองเป็นตัวอักษรหรือคำ แต่มองเป็น token ซึ่งอาจเป็นทั้งคำ เศษของคำ ตัวอักษรตัวเดียว หรือแม้แต่ byte

  • กฎคร่าวๆ: ภาษาอังกฤษ 1 token ≈ 3.5 ตัวอักษร ภาษาอื่น (รวมถึงไทย) อาจได้จำนวนต่างออกไป
  • token เป็นหน่วยของทุกอย่าง: ขนาด context window, เพดาน max_tokens, การคิดเงิน และตัวเลขใน usage ของ response
# ประมาณ token แบบหยาบๆ (ภาษาอังกฤษ)
chars = 14_000
print(chars / 3.5)   # ≈ 4,000 tokens

# ตัวเลขจริงดูจาก response
print(msg.usage.input_tokens, msg.usage.output_tokens)
สรุปสั้นๆ

คิดเป็น token เสมอ ภาษาอังกฤษหาร 3.5 จากจำนวนตัวอักษรได้ค่าประมาณ

2. Next-token generation และทำไมถึง hallucinate

ลองนึกถึง autocomplete บนมือถือที่เก่งขึ้นเป็นล้านเท่า โมเดลเลือก token ถัดไปจากสิ่งที่ "มักจะตามมา" และในลูปนี้ ไม่มีขั้นไหนตรวจสอบข้อเท็จจริง เลย

ความลื่นไหลกับการแต่งเรื่องจึงมาจากกลไกเดียวกัน งานที่มี pattern ชัดและพบบ่อย เช่น สรุป จัด format ใหม่ อธิบายแนวคิดที่คนรู้กันทั่วไป จะเชื่อถือได้ ส่วนเรื่องที่ข้อมูลน้อยหรือแปลกใหม่ คือที่ที่โมเดลเริ่มแต่ง

การแต่งมักไปกองอยู่ที่ รายละเอียดเจาะจง: ชื่อคน วันที่ ตัวเลขสถิติ citation URL และคำพูดที่ยกมา ส่วนเนื้อความอธิบายทั่วไปมักไม่ค่อยเพี้ยน

สรุปสั้นๆ

โมเดลเขียนสิ่งที่ "ฟังดูน่าจะถูก" ไม่ใช่สิ่งที่ "ถูก" ตอนตรวจงาน ให้ไล่เช็กชื่อ ตัวเลข วันที่ และลิงก์ก่อน

Claude ช่วยร่างบทความเกี่ยวกับประวัติภาษา Python ให้บล็อกบริษัท ถ้ามีเวลาตรวจแค่ส่วนเดียว ควรตรวจอะไรก่อน?

  1. ย่อหน้าที่อธิบายว่า dynamic typing คืออะไร
  2. ปีที่ออกแต่ละเวอร์ชัน ชื่อคนที่ยกคำพูดมา และลิงก์อ้างอิง
  3. ไวยากรณ์และการสะกด
  4. ย่อหน้าบทนำ
ดูเฉลย

B ข้อมูลเจาะจงอย่างวันที่ ชื่อ และ URL คือจุดที่การแต่งมักเกิด ส่วนการอธิบายแนวคิดที่คนรู้กันทั่วไปมักเชื่อถือได้

3. Context window = working memory

Context window คือ ทุกอย่างที่โมเดลอ้างอิงได้ในการตอบครั้งหนึ่ง รวมถึงคำตอบที่กำลังเขียนด้วย ซึ่งแยกจาก training data

สิ่งที่นับเข้า window:

  • system prompt
  • messages ทั้งหมด รวม tool result, รูปภาพ และเอกสาร
  • tool definitions
  • output รวมถึง extended thinking

ใน multi-turn conversation turn เก่าๆ ถูกส่งซ้ำทุกครั้ง window เลยค่อยๆ เต็มขึ้นเรื่อยๆ

ModelContext window
Claude Opus 5.5, Opus 4.8, Opus 4.71M tokens
Claude Sonnet 5.5, Sonnet 5, Sonnet 4.61M tokens
Claude Sonnet 4.5, Haiku 4.5200k tokens
  • 1M เป็นค่า default ของ flagship รุ่นปัจจุบัน ไม่ต้องใส่ beta header
  • ตัวอย่าง: เอกสาร 500,000 token ใส่ใน Sonnet 4.6 ได้ แต่ใส่ใน Haiku 4.5 ไม่ได้
  • Context rot: ยิ่ง token เยอะ ความแม่นและการดึงข้อมูลกลับมาใช้ยิ่งลดลง ดังนั้น "ใส่อะไร" สำคัญพอๆ กับ "ใส่ได้เท่าไหร่"
เข้าใจผิดบ่อย

"เปิด prompt caching แล้วจะได้พื้นที่ context window คืน" ไม่ใช่ caching เปลี่ยนแค่ ราคา ของ prefix ที่ cache ไว้ แต่ token พวกนั้นยังนั่งอยู่ใน window เต็มๆ

สรุปสั้นๆ

window = system + messages + tools + output (รวม thinking) ใหญ่ได้ถึง 1M แต่ยิ่งยาวยิ่งเสี่ยง context rot และ cache ไม่ได้ลดขนาด

Checkpoint 3

agent ตัวหนึ่งใช้ prompt caching กับ system prompt ยาว มี tool 12 ตัว และคุยมาแล้ว 40 turn ข้อไหนถูกเกี่ยวกับ context window?

  1. ส่วนที่ cache ไว้ไม่นับใน window แล้ว
  2. tool definitions ไม่นับ เพราะไม่ใช่ข้อความ
  3. prefix ที่ cache, tool definitions, messages ทั้ง 40 turn และ output ที่กำลังเขียน นับรวมทั้งหมด
  4. นับเฉพาะ turn ล่าสุด เพราะ turn เก่าถูกจำไว้แล้ว
ดูเฉลย

C ทุกอย่างที่ส่งไปและทุกอย่างที่โมเดลเขียนออกมานับหมด turn เก่าถูกส่งซ้ำทุกครั้ง และ cache เปลี่ยนแค่ราคา

4. ทำไมตัวอย่างใน prompt ถึงคุมโมเดลได้โดยไม่ต้อง retrain

เรื่องวิธีเขียน zero-shot / single-shot / multi-shot อยู่ในบท 6.2 ตรงนี้จะคุยแค่ว่า ทำไม มันได้ผล

คำตอบคือ ตัวอย่างอยู่ใน context window ซึ่งเป็น working memory ชั่วคราวของ request นั้น โมเดลเห็นตัวอย่างแล้วต่อ pattern ตาม เหมือนเราโชว์ฟอร์มที่กรอกเสร็จแล้วให้คนดูก่อนกรอกใบใหม่ ไม่ได้ไปเปลี่ยนสมองเขาถาวร

  • Fine-tuning คือการเทรนโมเดลที่ pretrain แล้วต่อด้วยข้อมูลใหม่ ซึ่ง Claude API ตอนนี้ ยังไม่มีให้ใช้
  • ผลของตัวอย่างอยู่แค่ใน request นั้น request ถัดไปต้องใส่ใหม่ทุกครั้ง และกินพื้นที่ window ทุกครั้ง
  • ตัวอย่างควร หลากหลายและครอบคลุม edge case ไม่งั้นโมเดลจะลอก pattern ที่เราไม่ได้ตั้งใจ เช่น ความยาวเท่ากันทุกข้อ หรือขึ้นต้นด้วยคำเดิมทุกครั้ง
สรุปสั้นๆ

few-shot = ข้อมูลใน context ไม่ใช่การเรียนรู้ถาวร เอาออกเมื่อไหร่ผลหายทันที

Checkpoint 5

ระบบจัดหมวด ticket ใส่ตัวอย่าง 6 ข้อใน prompt มาหลายเดือน มีคนเสนอให้ตัดออกเพื่อประหยัด token เพราะ "Claude เห็นมาเป็นแสนรอบแล้ว น่าจะจำได้" จะเกิดอะไรขึ้น?

  1. ไม่มีผล เพราะโมเดลเรียนรู้จากการใช้งานไปแล้ว
  2. ประโยชน์จากตัวอย่างหายไป เพราะตัวอย่างมีผลเฉพาะตอนอยู่ใน context ของ request
  3. คุณภาพดีขึ้น เพราะ window ว่างขึ้น
  4. ต้องสั่ง fine-tune ผ่าน API ก่อนจึงตัดได้
ดูเฉลย

B แต่ละ request เริ่มจากศูนย์ ไม่มีอะไรถูกเรียนรู้ข้าม request และ Claude API ไม่มี fine-tuning ให้ใช้

5. Sampling: ทำไม prompt เดิมได้คำตอบต่างกัน

ทุกขั้นของการ generate มี token ที่เป็นไปได้หลายตัว โมเดล สุ่มเลือก (sample) หนึ่งตัวตามความน่าจะเป็น ผลต่างกันระหว่างรอบจึงเป็นเรื่องปกติ

Parameterคุมอะไร
temperatureระดับความสุ่ม default 1.0 ช่วง 0.0–1.0 ใกล้ 0 เหมาะกับงานวิเคราะห์/ตัวเลือก ใกล้ 1 เหมาะกับงานสร้างสรรค์
top_kสุ่มจาก K token ที่น่าจะเป็นที่สุดเท่านั้น (ตัดตามจำนวน)
top_p (nucleus sampling)ตัดตัวเลือกตาม cumulative probability แทนที่จะตัดตามจำนวน

ข้อจำกัดใน model รุ่นใหม่:

  • Claude 5 ทุกตัว และ Opus 4.7 ขึ้นไป: ส่ง temperature, top_p หรือ top_k ที่ไม่ใช่ default จะได้ 400 error ไม่ว่าจะเปิด thinking หรือไม่
  • model รุ่นเก่า: ข้อห้ามนี้มีผลเฉพาะตอนเปิด thinking
# โค้ดเก่าที่ย้ายมา Opus 5.5 แล้วจะพัง
client.messages.create(model="claude-opus-5-5", temperature=0, ...)   # → 400

# ให้ลบ temperature ทิ้ง แล้วไปคุมความสม่ำเสมอด้วย prompt / validation แทน
client.messages.create(model="claude-opus-5-5", ...)
เข้าใจผิดบ่อย

"ตั้ง temperature 0 แล้ว output จะเหมือนเดิมเป๊ะทุกครั้ง" ไม่ใช่ มันเอียงไปทางตัวเลือกที่น่าจะเป็นที่สุด แต่ไม่การันตีว่าจะได้ผลเหมือนกันทุกรอบ

"อยากได้ผลสม่ำเสมอ ก็ลด temperature ได้เสมอ" ไม่ใช่ บน Claude 5 และ Opus 4.7+ ค่าที่ไม่ใช่ default จะถูกปฏิเสธด้วย 400

สรุปสั้นๆ

temperature = ความสุ่ม, top_k = ตัดตามจำนวน, top_p = ตัดตามความน่าจะเป็นสะสม และรุ่นใหม่ห้ามแตะทั้งสามตัว

จับคู่การตั้งค่ากับพฤติกรรม (สมมติว่าเป็น model รุ่นเก่าที่ยังปรับได้):

  1. temperature ต่ำ
  2. temperature สูง
  3. top_k = 5
  4. temperature = 0

  3. ใช้คำที่หลากหลายและคาดไม่ถึงมากขึ้น
  4. ใช้สำนวนที่น่าจะเป็นที่สุด ค่อนข้างระมัดระวัง

6. Non-determinism: ออกแบบระบบให้รับผลที่ไม่เหมือนเดิมได้

Non-determinism คือ input เดียวกันอาจได้ output ต่างกันข้าม call ซึ่งกระทบ regression test, cache ที่ใช้ output เป็น key และ audit ที่ต้องการให้ตัดสินใจซ้ำได้ผลเดิม

  • เกิดทั้งบน first-party API ของ Anthropic และบน cloud provider อื่น ไม่มีเจ้าไหนให้ผลเหมือนเดิมเป๊ะ
  • ไม่เคยมี setting ไหนกำจัดมันได้ โค้ดที่ย้ายไป model ใหม่แล้วลบ temperature=0 ทิ้ง ไม่ได้เสียอะไรจริงๆ
  • จำนวน token ก็ไม่คงที่: เมื่อใช้ adaptive thinking Claude จะเลือกปริมาณ thinking เองในแต่ละ request และ thinking token คิดเงินเป็น output ดังนั้นประมาณค่าใช้จ่ายเป็น ช่วง จากการรันหลายๆ รอบ

แนวปฏิบัติ:

  • ตรวจ โครงสร้างและความหมาย (JSON parse ได้, label ถูก, field ครบ) ไม่ใช่เทียบทีละ byte
  • รัน eval แต่ละเคสหลายรอบ แล้วดูว่าส่วนไหนนิ่ง ส่วนไหนแกว่ง
  • ถ้าต้อง audit ได้ ให้ เก็บ response ที่ใช้ตัดสินใจจริงไว้ เพราะรันใหม่ก็คือ sample ใหม่
def test_classify_refund():
    out = json.loads(classify("ขอคืนเงิน order #123"))   # parse ได้ไหม
    assert out["label"] == "refund"                      # label ถูกไหม
    assert "order_id" in out                             # field ครบไหม
    # ไม่ assert ว่าข้อความ reason ตรงกับไฟล์ที่เก็บไว้ทุกตัวอักษร
เข้าใจผิดบ่อย

"Non-determinism เป็นเรื่องของ API ของ Anthropic เท่านั้น ถ้าเรียกผ่าน cloud provider อื่นจะได้ผลเหมือนเดิมทุกครั้ง" ไม่จริง เกิดทุกที่ที่รันโมเดล

สรุปสั้นๆ

อย่าสู้กับ non-determinism ให้ออกแบบรอบมัน: test ตามโครงสร้าง, eval หลายรอบ, เก็บ response จริงไว้ audit และตั้งงบเป็นช่วง

Checkpoint 7

pipeline สรุปข่าวรันบน Claude ผ่าน cloud provider มี snapshot test ที่เทียบ output กับไฟล์ที่เก็บไว้ทุกตัวอักษร แล้ว fail ทุก 2–3 วัน ควรแก้ยังไง?

  1. ย้ายมาใช้ first-party API เพราะ cloud provider ไม่ deterministic
  2. ตั้ง temperature=0
  3. เปลี่ยนไปตรวจโครงสร้างและ field ที่จำเป็น แทนการเทียบข้อความเป๊ะ
  4. อัปเดต snapshot ใหม่ทุกครั้งที่ fail
ดูเฉลย

C non-determinism เกิดทุก platform, temperature 0 ไม่ได้การันตี (และรุ่นใหม่ตอบ 400) ส่วนการอัปเดต snapshot ทุกครั้งทำให้ test ไม่มีความหมาย
