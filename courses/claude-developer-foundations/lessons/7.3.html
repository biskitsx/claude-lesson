7.3 Claude hooks as guardrails: events, matchers and handlers

ต้นฉบับ: CertSafari 7.3

อ่านจบแล้วควรทำได้
  • บอกชื่อ hook event ที่ fire รอบ tool call, รอบ turn และรอบ session ได้
  • แยกได้ว่า event ไหน หยุด action ได้ และ event ไหนแค่ สังเกตหลังเกิดเหตุ
  • เขียน matcher แบบชื่อตรงตัว (exact) หรือ regular expression เพื่อเล็ง tool ที่ต้องการ
  • เลือก handler type และที่เก็บ settings ที่เหมาะกับ guardrail hook
แนวคิดหลัก: hook = policy ที่รันทุกครั้ง

Hook คือ handler ที่ลงทะเบียนไว้กับ lifecycle event Claude Code จะรันมันทุกครั้งที่ event นั้นเกิด ไม่ว่า model ตั้งใจอะไร ถ้า event fire ก่อน action มีผล hook ก็ปฏิเสธ action นั้นได้ นโยบายที่เคยเป็นแค่ตัวหนังสือจึงกลายเป็นด่านตรวจที่ไม่มีวันข้าม

1. Hook คือชั้นที่รันกับทุก tool call

ความต่างแบบสั้นที่สุด: คำสั่งใน prompt Claude เอาไปชั่งน้ำหนัก ส่วน hook Claude Code เอาไปรัน hook ไม่พึ่งว่า model จะเชื่อฟังหรือเปล่า มันจึงทำงานแม้กับ tool call ที่ model ถูก injected content หลอกให้เรียก

ความถี่Event
ครั้งเดียวต่อ sessionSessionStart, SessionEnd
ครั้งเดียวต่อ turnUserPromptSubmit, Stop, StopFailure
รอบทุก tool callPreToolUse, PostToolUse (ยกเว้น call EndConversation ที่ข้ามทั้งคู่)

Guardrail ส่วนใหญ่เล็งไปที่คู่ PreToolUse/PostToolUse เพราะ tool call คือจุดที่ agent แก้ไฟล์ รัน shell และเรียก service ภายนอก

นอกจาก block แล้ว hook ยังใช้ได้อีกหลายอย่าง เช่น audit ทุกคำสั่ง Bash ลง log, บังคับให้มนุษย์ approve ก่อนเขียน database, หรือ rewrite tool input ก่อนรัน (Agent SDK docs ยกเคส approval และ blocking ไว้)

สรุปสั้นๆ

Prompt = ขอร้อง, hook = บังคับ และ tool call คือสนามหลักของ guardrail

  1. Bash ที่รันเกิน 2 นาที
  2. Call ไปยัง MCP tool
  3. EndConversation
  4. Write ที่สร้างไฟล์ใหม่
ดูเฉลย

C tool event fire กับทุก tool call ยกเว้น EndConversation ที่ข้ามทั้ง PreToolUse และ PostToolUse ส่วน MCP tool ก็โดน * จับเหมือน tool อื่น

2. Event ไหนหยุด action ได้

ลองเดาก่อน: PostToolUse hook บน Bash เห็นคำสั่ง rm -rf build/ แล้ว exit 2 จะเกิดอะไรขึ้น? คำตอบ: ไม่มีอะไรถูกย้อนกลับ Claude แค่เห็น stderr เพราะคำสั่งรันไปแล้ว

กฎหลัก

Hook หยุด action ได้ ก็ต่อเมื่อ event ของมัน fire ก่อน action มีผล เหมือนยามที่ยืนหน้าประตูกันคนเข้าได้ ยามที่ยืนหลังประตูทำได้แค่จดว่าใครเข้าไปแล้ว

  • PreToolUse fire ก่อนรัน ยกเลิก call ได้
  • UserPromptSubmit fire ก่อน Claude ประมวลผล prompt block แล้ว prompt ไม่ถึง Claude
  • UserPromptExpansion block การ expand คำสั่งที่พิมพ์ให้กลายเป็น prompt ได้
  • PreModelSwitch veto การขอเปลี่ยน model ได้
  • PostToolUse และ PostToolUseFailure fire หลังสำเร็จหรือล้มเหลว เหมาะกับ audit, lint, report กลับ แต่สายเกินจะกันอะไร
Hook eventBlock ได้?Exit code 2 ทำอะไร
PreToolUseได้block tool call
UserPromptSubmitได้block prompt ก่อน Claude เห็น
UserPromptExpansionได้block การ expand
Stopได้ไม่ให้หยุด ให้ conversation ทำต่อ
ConfigChangeได้block การเปลี่ยน config ยกเว้น policy settings
PostToolUseไม่ได้โชว์ stderr ให้ Claude, tool รันไปแล้ว
PermissionRequestไม่ได้ (ด้วย exit 2)exit 2 ถูกเมิน ต้อง deny ผ่าน JSON decision object
  • "Block" ไม่ได้แปลว่าห้ามของอันตรายเสมอ บน Stop และ SubagentStop การ block คือ บังคับให้ Claude ทำงานต่อ เช่น ห้ามหยุดจนกว่า test จะผ่าน
  • PermissionRequest fire ตอน tool call ต้องขอ approval แต่ exit 2 ไม่มีผล ต้องคืน decision ใน JSON output
เข้าใจผิดบ่อย

"PostToolUse ที่ exit 2 หยุด call ทำลายล้างได้" ไม่ได้ มัน fire หลัง tool สำเร็จแล้ว การกันต้องอยู่ใน PreToolUse

"PermissionRequest hook exit 2 = deny" ไม่ใช่ event นี้เมิน exit 2 ต้องตอบ decision เป็น JSON

สรุปสั้นๆ

อยู่ก่อน action = กันได้ (PreToolUse, UserPromptSubmit, UserPromptExpansion, PreModelSwitch, Stop, ConfigChange) อยู่หลัง = แค่สังเกต (PostToolUse, PostToolUseFailure) และ PermissionRequest ต้อง deny ด้วย JSON

3. เล็งเป้าด้วย matcher และ if condition

Config มี 3 ระดับ: เลือก event → ใส่ matcher group เพื่อกรองว่าจะ fire เมื่อไหร่ → ระบุ handler หนึ่งตัวหรือมากกว่า

  • Tool event (PreToolUse, PostToolUse, PostToolUseFailure, PermissionRequest, PermissionDenied) match กับ ชื่อ tool
  • Event อื่นกรองด้วย field อื่น เช่น SessionStart กรองตามวิธีที่ session เริ่ม, PreCompact กรองว่า compaction เป็นแบบ manual หรือ automatic
  • บาง event ไม่รองรับ matcher fire ทุกครั้ง เช่น UserPromptSubmit, Stop, PostToolBatch

Claude Code อ่าน matcher string ยังไง

รูปแบบถูกตีความเป็นตัวอย่าง
*, string ว่าง, หรือไม่ใส่ matchermatch ทุกอย่าง*
มีแค่ตัวอักษร, ตัวเลข, _, -, ช่องว่าง, comma, |ชื่อ exact หรือ list ของชื่อ exactEdit|Write = Edit หรือ Write เท่านั้น
มีอักขระอื่นปนJavaScript regex แบบ unanchored^Notebook = tool ที่ชื่อขึ้นต้นด้วย Notebook

MCP tool ตั้งชื่อแบบ mcp__<server>__<action> regex อย่าง mcp__memory__.* จึงครอบทั้ง server ได้ในทีเดียว

if condition: กรองลึกถึง argument

Matcher เห็นแค่ชื่อ tool ถ้าอยากให้ handler รันเฉพาะ argument บางแบบ ใส่ field if บน handler ด้วย permission-rule syntax เช่น Bash(rm *) จะได้ไม่ต้องปลุก script ทุกครั้งที่มี Bash call

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",                       // ระดับ 1: ชื่อ tool
        "hooks": [
          {
            "type": "command",
            "if": "Bash(rm *)",                  // ระดับ 2: เฉพาะคำสั่งที่ขึ้นต้นด้วย rm
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh",
            "args": []
          }
        ]
      }
    ]
  }
}
#!/usr/bin/env bash
# block-rm.sh: อ่าน event JSON จาก stdin
cmd=$(jq -r '.tool_input.command')
if [[ "$cmd" == *"-rf"* ]]; then
  echo "ห้าม rm -rf ใน repo นี้" >&2   # stderr จะถูกส่งกลับให้ Claude
  exit 2                                  # exit 2 = blocking error
fi
exit 0
เข้าใจผิดบ่อย

"Edit|Write เป็น regex เลย match ชื่ออะไรก็ได้ที่มีคำว่า Edit หรือ Write" ไม่ใช่ string ที่มีแค่ตัวอักษรกับ | เป็น exact list จะกลายเป็น regex ก็ต่อเมื่อมีอักขระอื่นปน

สรุปสั้นๆ

event → matcher (ชื่อ tool, exact หรือ regex) → if (argument) → handler → Claude Code ทำตามผลของ handler

Checkpoint 4 (เรียงลำดับ)

Claude เรียก Bash ด้วย rm -rf dist/ เรียงลำดับสิ่งที่เกิดขึ้นในระบบ hook:

  1. Handler script รัน
  2. Matcher เทียบชื่อ tool กับ Bash
  3. Claude Code ทำตามผลที่ handler คืนมา
  4. Event PreToolUse fire พร้อมชื่อ tool และ input
  5. เช็ก if ว่าเข้ากับ Bash(rm *) ไหม
ดูเฉลย

d → b → e → a → c event มาก่อน แล้วกรองสองชั้น (ชื่อ tool แล้วค่อย argument) จากนั้นค่อยรัน handler

Checkpoint 5 (จับคู่)

จับคู่ matcher กับสิ่งที่มัน match:

  1. Read|Grep
  2. mcp__github__.*
  3. (ไม่ใส่ matcher)
  4. Web.*
ดูเฉลย

1 → Read หรือ Grep เท่านั้น (exact list) · 2 → ทุก tool ของ MCP server ชื่อ github · 3 → ทุกครั้งที่ event fire · 4 → regex แบบ unanchored จึง match ทุก tool ที่มี "Web" ตามด้วยอะไรก็ได้ เช่น WebFetch, WebSearch

4. Handler type และที่เก็บ config

Typeทำอะไร
commandรัน local script ที่รับ event data
httpส่ง event data ไปที่ URL
mcp_toolเรียก tool บน MCP server ที่ config ไว้
promptให้ LLM ประเมินแบบ single-turn
agentverification แบบ multi-turn ที่ใช้ tool ได้ (experimental)
  • กฎแข็ง ให้ใช้ command เพราะ input เดิมได้ decision เดิมทุกครั้ง (deterministic)
  • prompt กับ agent เอา judgment ของ model มาช่วย เหมาะกับ policy ที่คลุมเครือจน regex เขียนไม่ได้
  • Admin จำกัด HTTP handler ได้ด้วย allowedHttpHookUrls พอตั้งไว้ที่ settings ระดับไหนก็ตาม จะรันได้เฉพาะ URL ที่อยู่ใน allowlist ที่ merge แล้ว

Config อยู่ที่ไหน = คุ้มครองใคร

LocationScopeแชร์ได้?
~/.claude/settings.jsonทุกโปรเจกต์ของเราไม่ อยู่แค่เครื่องเรา

Hook ในไฟล์ user คุ้มครองแค่เรา ส่วน hook ในไฟล์โปรเจกต์คุ้มครองทุกคนที่ clone repo ไป

Exit code ที่ต้องจำ

  • 0 = สำเร็จ (และอ่าน JSON บน stdout ได้)
  • 2 = blocking error, stderr ถูกส่งกลับให้ Claude ใช้ block ได้โดยไม่ต้องมี JSON
  • 1 หรือ non-zero อื่น = non-blocking error, ไม่ block
สรุปสั้นๆ

กฎแข็งใช้ command + exit 2, policy เบลอใช้ prompt/agent, อยากให้ทั้งทีมได้ใส่ .claude/settings.json, อยากบังคับทั้งองค์กรใช้ managed policy
