3.1 Claude Code project configuration: CLAUDE.md, rules, auto memory และ settings.json

ต้นฉบับ: CertSafari 3.1

อ่านจบแล้วควรทำได้
  • เลือกได้ว่า instruction แต่ละข้อควรอยู่ใน CLAUDE.md scope ไหน: managed, user, project หรือ local
  • ใช้ /init เริ่มต้น repo ใหม่ และใช้ .claude/rules/ ทำ rule ที่โหลดเฉพาะบางไฟล์
  • แยก CLAUDE.md ออกจาก auto memory ได้ และรู้วิธีย้ายหรือปิด auto memory
  • เลือก scope ของ settings.json ถูก และบอกได้ว่าถ้า key เดียวกันถูกตั้งหลายที่ ค่าไหนชนะ
แนวคิดหลัก: context แบบซ้อนชั้นที่อยู่บน disk

Claude Code ไม่ได้จำแชทเมื่อวาน ทุก session เริ่มใหม่จากไฟล์บน disk ล้วนๆ เราเขียนคำสั่งไว้ใน CLAUDE.md หลายระดับ Claude จดสิ่งที่เรียนรู้เองไว้ใน auto memory ส่วน settings.json เป็นตัวคุมว่า tool ทำอะไรได้บ้าง จำง่ายๆ: CLAUDE.md = "ควรทำอะไร" ส่วน settings.json = "อนุญาตให้ทำอะไร"

1. ลำดับชั้นของ CLAUDE.md

CLAUDE.md คือไฟล์ instruction ที่เราเขียนเอง และถูกโหลดเข้าไปทุก session คำถามที่ต้องตอบให้ได้มีแค่สองข้อ: ใครควรได้คำสั่งนี้ และ ควร commit เข้า git ไหม ตอบสองข้อนี้ได้ก็รู้ scope แล้ว

Scopeที่อยู่ไฟล์ใครได้รับ
Managed policy/Library/Application Support/ClaudeCode/CLAUDE.md (macOS)
/etc/claude-code/CLAUDE.md (Linux / WSL)		ทุกคนในองค์กร
User~/.claude/CLAUDE.mdเราคนเดียว ทุกโปรเจกต์
Project./CLAUDE.md หรือ ./.claude/CLAUDE.mdทั้งทีม ผ่าน source control
Local./CLAUDE.local.mdเราคนเดียว เฉพาะโปรเจกต์นี้
  • CLAUDE.local.md เหมาะกับของส่วนตัวในโปรเจกต์ เช่น URL ของ sandbox ตัวเอง อย่าลืมใส่ใน .gitignore
  • ไฟล์ project คือตัวที่ทีมใช้ร่วมกัน
  • AGENTS.md: Claude จะอ่าน AGENTS.md ก็ต่อเมื่อ ไม่มี CLAUDE.md, .claude/CLAUDE.md หรือ CLAUDE.local.md อยู่ใน working directory หรือ directory แม่เลย (ไฟล์ระดับ user และ managed ไม่นับในเงื่อนไขนี้)

เขียนยังไงให้ได้ผล

  • เจาะจง "ใช้ indent 2 space" ดีกว่า "จัด format โค้ดให้ดีๆ" เยอะ
  • ยาวไม่เกินประมาณ 200 บรรทัดต่อไฟล์ และจัดกลุ่มเป็นหัวข้อ
  • ถ้าสองคำสั่ง ขัดกัน Claude อาจทำตามข้อไหนก็ได้ ไม่มีกฎว่าอันไหนชนะ ดังนั้นอย่าปล่อยให้ขัดกัน
  • แยกไฟล์ยาวด้วย @path import ได้ แต่ ไม่ได้ประหยัด context เพราะไฟล์ที่ import ก็โหลดตอนเปิด session เหมือนกัน
# CLAUDE.md ของโปรเจกต์
ภาพรวมดูที่ @README และคำสั่งที่รันได้ดูที่ @package.json

# Workflow
- วิธีแตก branch ดู @docs/branching.md   <!-- ไฟล์นี้โหลดตอนเริ่ม session ด้วย -->

ถ้าสงสัยว่าไฟล์ไหนถูกโหลดจริง ใช้ /context ดูรายการ memory file ที่โหลดอยู่ และใช้ /memory เปิดไฟล์พวกนั้นขึ้นมาแก้

อีกเรื่องที่ควรรู้: ตัว parser ของ import ข้าม code span และ fenced code block ถ้าเขียน @docs/x.md ไว้ใน backtick มันจะเป็นแค่ข้อความธรรมดา ไม่ถูก import

เข้าใจผิดบ่อย

"ย้ายเนื้อหา CLAUDE.md ไปไว้ในไฟล์ @import จะช่วยประหยัด context" ไม่จริง ไฟล์ที่ import โหลดตอนเริ่มเหมือนเดิม กิน context เท่าเดิม ถ้าอยากประหยัดจริงต้องใช้ path-scoped rules (หัวข้อถัดไป)

สรุปสั้นๆ

ทั้งองค์กร → managed, ตัวเราทุกโปรเจกต์ → ~/.claude/CLAUDE.md, ทั้งทีม → ./CLAUDE.md, ตัวเราโปรเจกต์เดียว → CLAUDE.local.md (gitignore) และ import ไม่ได้ลด context

Checkpoint 1

คุณอยากให้ Claude รู้ว่าใน repo นี้คุณชอบรันเทสต์ด้วย database container ส่วนตัวที่ port 55432 แต่เพื่อนในทีมไม่ได้ใช้แบบนี้ ควรเขียนไว้ที่ไหน?

  1. ~/.claude/CLAUDE.md
  2. ./CLAUDE.md แล้ว commit
  3. ./CLAUDE.local.md และใส่ใน .gitignore
  4. Managed policy CLAUDE.md
ดูเฉลย

C เป็นของส่วนตัวและใช้แค่ใน repo นี้ ถ้าใส่ใน user file จะไปติดทุกโปรเจกต์ ถ้าใส่ใน project file เพื่อนทั้งทีมจะได้ไปด้วย

Checkpoint 2

ใน CLAUDE.md มีประโยค "ขั้นตอน release ดูได้ที่ `@docs/release.md`" (ครอบ path ด้วย backtick) ตอนเริ่ม session จะเกิดอะไรขึ้น?

  1. import ไฟล์ตามปกติ เพราะ @ ถูก resolve ก่อน markdown
  2. ไม่ import เพราะ path อยู่ใน code span ซึ่ง parser ข้ามไป
  3. เกิด parse error แล้วไฟล์ทั้งไฟล์ไม่ถูกโหลด
  4. import แค่ย่อหน้าแรกของไฟล์
ดูเฉลย

B import parser ไม่มองใน code span และ code block ถ้าอยาก import จริงต้องเขียน @docs/release.md แบบไม่มี backtick

2. เริ่ม repo ด้วย /init และใช้ path-scoped rules

repo ใหม่ไม่ต้องนั่งเขียน CLAUDE.md เองตั้งแต่ศูนย์ พิมพ์ /init แล้ว Claude จะสำรวจ codebase และร่าง CLAUDE.md ให้ ซึ่งปกติจะมีคำสั่ง build/test ภาพรวมโครงสร้าง และ convention ที่มันเจอ

  1. พิมพ์ /init ในโปรเจกต์
  2. Claude สำรวจ codebase แล้วร่างไฟล์
  3. เรารีวิว ลบส่วนที่ไม่ถูกต้องออก (อย่าเชื่อร่างแรก 100%)
  4. commit ให้ทีมใช้ร่วมกัน

Rules: instruction ที่โหลดเฉพาะตอนจำเป็น

คำสั่งที่ใช้กับแค่บางส่วนของ codebase ให้แยกเป็นไฟล์ markdown ใน .claude/rules/ ถ้าใส่ frontmatter paths ไว้ rule นั้นจะโหลดก็ต่อเมื่อ Claude ทำงานกับไฟล์ที่ match เท่านั้น เช่น กฎของ database migration จะไม่กิน context ตอนกำลังแก้ CSS อยู่ rule ส่วนตัวก็ใส่ใน ~/.claude/rules/ ได้

---
paths:
  - "db/migrations/**/*.sql"
---

# Migration rules
- ทุก migration ต้องมี down script คู่กัน
- ห้าม DROP COLUMN ในไฟล์เดียวกับที่เพิ่ม column ใหม่

paths รับ glob pattern ได้ทั้งแบบ YAML list และแบบ string คั่นด้วย comma และเป็น field เดียวที่ rules รองรับสำหรับเรื่องนี้ (ไม่ใช่ include, files หรือ globs)

สรุปสั้นๆ

/init → รีวิว → commit ส่วนคำสั่งเฉพาะไฟล์ให้ไปอยู่ใน .claude/rules/ พร้อม paths ซึ่งเป็นวิธีที่ประหยัด context ได้จริง

Checkpoint 3 (เรียงลำดับ)

เรียงขั้นตอนตั้งค่า CLAUDE.md ใน repo ใหม่:

  1. commit ไฟล์
  2. Claude สำรวจโค้ดแล้วร่างไฟล์
  3. พิมพ์ /init
  4. อ่านร่างแล้วลบส่วนที่ผิด
ดูเฉลย

c → b → d → a ต้องรีวิวก่อน commit เสมอ เพราะร่างอาจเดา convention ผิด

Checkpoint 4

ทีมอยากให้กฎการเขียน Storybook โหลดเฉพาะตอนแก้ไฟล์ *.stories.tsx ต้องใส่ glob ไว้ใน frontmatter field ชื่ออะไร?

  1. globs
  2. files
  3. paths
  4. include
ดูเฉลย

C paths เป็น field เดียวที่ rules ใช้กำหนดว่าจะโหลดกับไฟล์ไหน

3. Auto memory: สมุดจดของ Claude เอง

CLAUDE.md คือสิ่งที่ เราบอก Claude ส่วน auto memory คือสิ่งที่ Claude เรียนรู้เอง จากการที่เราแก้มัน หรือยืนยันว่าวิธีไหนใช้ได้ เหมือนพนักงานใหม่ที่มีคู่มือบริษัท (CLAUDE.md) กับสมุดโน้ตส่วนตัวที่จดเองระหว่างทำงาน (auto memory)

CLAUDE.mdAuto memory
ใครเขียนเราClaude
เนื้อหาinstruction และกฎสิ่งที่เรียนรู้และ pattern
Scopeproject, user หรือ orgต่อ repo (ใช้ร่วมกันข้าม worktree)
โหลดเข้าทุก sessionทุก session แต่แค่ 200 บรรทัดแรก หรือ 25KB

ที่เก็บคือ ~/.claude/projects/<project>/memory/ มีไฟล์ MEMORY.md เป็น index ชี้ไปยังไฟล์ memory แยกทีละเรื่อง แต่ละ memory มี type หนึ่งในสี่แบบ:

  • user บทบาท ความถนัด และความชอบในการทำงานของเรา
  • feedback สิ่งที่เราเคยแก้ให้ และวิธีที่เรายืนยันว่าโอเค
  • project งานที่กำลังทำ deadline และการตัดสินใจที่ดูจากโค้ดไม่ออก
  • reference ไปหาข้อมูลภายนอกได้ที่ไหน เช่น issue tracker

ตั้งค่าใน settings.json ได้สองตัว: autoMemoryDirectory ย้ายโฟลเดอร์ และ autoMemoryEnabled เปิด/ปิด

{
  "autoMemoryEnabled": false   // ปิด auto memory ทั้งหมด
}
เข้าใจผิดบ่อย

"ทุกอย่างที่ auto memory จดไว้ถูกโหลดเข้า session ใหม่ทั้งหมด" ไม่ใช่ โหลดแค่ส่วนต้นของ index คือ 200 บรรทัดแรกหรือ 25KB

สรุปสั้นๆ

CLAUDE.md = เราเขียน, auto memory = Claude เขียน เก็บใน ~/.claude/projects/<project>/memory/ มี 4 type และโหลดแค่หัว index

Checkpoint 5 (จับคู่)

จับคู่ข้อความที่ Claude จดไว้กับ memory type:

  1. "bug ของ payment ถูก track อยู่ใน Linear project PAY"
  2. "ผู้ใช้เป็น backend dev ถนัด Go ไม่ค่อยเขียน frontend"
  3. "ผู้ใช้บอกว่าอย่าใช้ mock DB ใน integration test"
  4. "ต้อง freeze โค้ดก่อนวันที่ 15 เพราะมี audit"
ดูเฉลย

1 → reference · 2 → user · 3 → feedback · 4 → project

4. settings.json: scope และใครชนะ

settings.json คุมพฤติกรรมของตัว Claude Code: permissions, hooks, plugins, env vars และ model ไม่ใช่ที่สำหรับเขียนคำแนะนำให้โมเดลอ่าน

Scopeไฟล์ใช้กับ
User~/.claude/settings.jsonความชอบส่วนตัวทุกโปรเจกต์
Shared project.claude/settings.jsonpermissions, hooks, plugins, env vars ของทีม (commit)
Project local.claude/settings.local.jsonoverride ส่วนตัวในโปรเจกต์นี้ (ไม่เข้า git)
Managedmanaged-settings.json และ managed source อื่นนโยบาย security/compliance ขององค์กร
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": ["Bash(make build)", "Bash(pytest *)"],     // รันได้เลยไม่ต้องถาม
    "deny":  ["Read(./secrets/**)"]                      // ห้ามอ่านโฟลเดอร์ secrets
  }
}

Precedence: สูงไปต่ำ

  1. Managed settings ไม่มีอะไรของเรา override ได้
  2. Command-line arguments เช่น --settings ที่ส่ง JSON มาใช้แค่ session เดียว
  3. Project local .claude/settings.local.json
  4. Shared project .claude/settings.json
  5. User ~/.claude/settings.json
  • Claude Code สร้าง .claude/settings.local.json เองเมื่อเรากดอนุมัติแบบถาวรตอนมัน prompt ขอ permission และกันไม่ให้ไฟล์นี้เข้า commit
  • ถ้า ~/.claude.json parse ไม่ได้ การรันแบบ -p (print mode) จะแสดง error แล้ว exit
สรุปสั้นๆ

Managed → CLI args → local → shared project → user ยิ่งใกล้ "ตัวเราใน session นี้" ยิ่งชนะ ยกเว้น managed ที่อยู่บนสุดเสมอ

Checkpoint 6 (เรียงลำดับ)

key model ถูกตั้งไว้ 3 ที่: .claude/settings.json ของทีม, --settings ตอนรัน และ managed settings ขององค์กร เรียงจากชนะมากไปน้อย

ดูเฉลย

managed → --settings → .claude/settings.json CLI argument อยู่เหนือไฟล์ของเราทุกไฟล์ แต่แตะ managed key ไม่ได้
