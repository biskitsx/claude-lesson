2.1 Choosing a Claude model from functional requirements (เลือก model จาก requirement)

ต้นฉบับ: CertSafari 2.1

อ่านจบแล้วควรทำได้
  • แปลง business requirement ให้เป็นเกณฑ์เลือก model 4 ข้อ: capability, speed, cost และ effort
  • ตัด model ที่ context window หรือ max output ไม่พอกับงานทิ้งได้ก่อนจะไปดูราคา
  • ใช้ eval ที่สร้างจาก functional requirement มาเทียบ model ที่เหลือ ด้วยตัวชี้วัด cost per completed task
แนวคิดหลัก: requirement คือตัวเลือก model ไม่ใช่ความชอบ

ทุก requirement จะกลายเป็นเกณฑ์ด้าน capability, speed หรือ cost หรือไม่ก็เป็น hard limit ด้านขนาด model ที่ถูกต้องคือตัวที่ผ่านทุกเกณฑ์ โดยมี cost per completed task ต่ำที่สุด

1. จาก business requirement สู่ selection criteria

ฝั่ง business มักพูดเป็นภาษาคน เช่น "ต้องตอบได้ระหว่างที่ลูกค้ายังถือสายอยู่" หรือ "งบห้ามโตกว่านี้" งานแรกของเราคือแปลงประโยคพวกนี้ให้เป็นตัวเลขที่วัดได้ เช่น latency target กี่วินาที หรือ cost per request เท่าไหร่ที่ volume จริง

จากนั้นถาม 4 คำถาม:

  • Capabilities: งานนี้ต้องใช้ feature อะไรจริงๆ บ้าง
  • Speed: app ต้องตอบเร็วแค่ไหน
  • Cost: งบช่วง development กับงบช่วง production เท่าไหร่
  • Effort: model ตัวเดียวกันแต่ปรับ effort ขึ้นหรือลง พอจะผ่าน requirement ไหม

Effort คืออะไร

Effort เป็น setting รายครั้ง (per-request) ใน Messages API อยู่ที่ output_config.effort คิดง่ายๆ ว่าเป็นปุ่มหมุนระหว่าง "คิดละเอียด" กับ "ประหยัด token" ใน model ตัวเดิม

resp = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=4096,
    output_config={"effort": "low"},   # ลด effort ให้ตอบเร็วและถูกลง
    messages=[{"role": "user", "content": "สรุปตั๋ว support นี้ให้หน่อย"}],
)
  • Fable 5.1, Opus 5.5 และ Sonnet 5.5 รองรับ effort โดยมี default เป็น high, medium, high ตามลำดับ
  • Haiku 4.5 ไม่รองรับ effort
  • การเปลี่ยน effort ทำให้ cached prefix ของ prompt caching ใช้ไม่ได้ (invalidate) เพราะฉะนั้นเปลี่ยนแล้วต้องวัด cost ใหม่ทุกครั้ง

Requirement หลักบอกว่าควรเริ่มที่ model ไหน

ถ้า requirement หลักคือ…เริ่มที่งานแบบที่เจอบ่อย
Capability สูงสุดที่มีClaude Fable 5.1Agent session ที่รันเป็นชั่วโมง, deep research หลายขั้น, agentic coding ที่ซับซ้อนและงาน enterprise
Autonomy หลายชั่วโมง + capabilityClaude Opus 5.5Autonomous coding agent ที่รันยาว, refactor ขนาดใหญ่, computer use
Speed + capability สำหรับงานทั่วไปClaude Sonnet 5.5Code generation, data analysis, agentic tool use
Latency และราคาต่ำสุดClaude Haiku 4.5Real-time app, high-volume processing, งานของ sub-agent
  • ถ้า requirement ไม่ได้ชี้ไปสุดทางใดทางหนึ่ง ให้เริ่มตรงกลาง งานส่วนใหญ่เริ่มที่ Opus 5.5
  • เริ่มที่ Haiku 4.5 เมื่อมีครบสามอย่าง: volume สูง, latency budget แน่น และกดดันเรื่อง cost
  • เริ่มที่ Fable 5.1 เมื่องานต้อง reasoning หนักและรันยาวเป็นชั่วโมง

Batch: อีกคันโยกด้าน cost

ถ้างานไม่ต้องได้ผลทันที (เช่นรันตอนกลางคืน เช้าค่อยดู) Message Batches API ประมวลผลแบบ asynchronous ในราคา ถูกกว่าการเรียกปกติ 50% ส่วน streaming แค่ทำให้ รู้สึก ว่าเร็ว ไม่ได้ลดราคาต่อ token

เข้าใจผิดบ่อย

"ตอบช้าและแพงไป ก็ต้องเปลี่ยน model" ไม่เสมอไป ถ้าคุณภาพผ่านแล้ว ลองลด effort บน model เดิมก่อนแล้ววัดใหม่ มักได้ผลดีกว่าการย้าย model

สรุปสั้นๆ

แปลง requirement เป็นตัวเลข → ตอบ 4 คำถาม (capability / speed / cost / effort) → เลือกจุดเริ่มจากตาราง โดย default คือ Opus 5.5 และอย่าลืมว่า effort กับ batch เป็นคันโยกที่ไม่ต้องเปลี่ยน model

Checkpoint 1

Chatbot ตอบคำถามพนักงานใช้ Sonnet 5.5 คุณภาพคำตอบผ่านเกณฑ์แล้ว แต่พอขึ้น production ค่าใช้จ่ายสูงและ latency เกินเป้า ควรลองอะไรก่อน?

  1. เปลี่ยนไปใช้ Fable 5.1 เพราะฉลาดสุด จะได้ตอบจบในรอบเดียว
  2. ลด effort บน Sonnet 5.5 แล้ววัด latency และ cost ใหม่
  3. เพิ่ม max_tokens ให้สูงขึ้น
  4. ย้ายไป cloud provider อื่น
ดูเฉลย

B effort แลก thoroughness กับ latency/cost ภายใน model เดียวกัน เมื่อคุณภาพผ่านอยู่แล้วนี่คือคันโยกแรกที่ควรลอง ส่วน A แพงและช้ากว่าเดิม C ไม่ได้ลดอะไร D ไม่เกี่ยว

Checkpoint 2

ทีม finance ต้องจัดหมวดรายการธุรกรรม 5 ล้านรายการทุกสิ้นเดือน ขอผลภายใน 24 ชั่วโมง และเน้นประหยัดที่สุด ควรใช้อะไร?

  1. เรียก Messages API แบบ synchronous ทีละรายการ
  2. เปิด stream: true ทุก request
  3. Message Batches API
  4. อัปโหลดไฟล์ผ่าน Files API ใหม่ทุกครั้งที่เรียก
ดูเฉลย

C งานใหญ่ ไม่รีบ เน้น cost = Batches API (ถูกกว่า 50%) แบบ synchronous จ่ายราคาเต็ม streaming ช่วยแค่ perceived latency และการอัปโหลดซ้ำเพิ่ม overhead เปล่าๆ

2. Context window กับ max output คือ hard limit

Context window คือเพดาน input ต่อ request ส่วน max output คือเพดานสิ่งที่ model เขียนได้ใน response เดียว สองตัวนี้ ไม่ได้ trade-off กับราคาหรือความเร็ว ถ้าใส่ไม่พอดีก็ตกรอบทันที ไม่ต้องไปดูราคาเลย เหมือนรถที่ถูกแค่ไหนก็ไร้ประโยชน์ถ้าของที่จะขนใส่ท้ายไม่ได้

ตัวอย่าง: requirement บอกว่า "วิเคราะห์เอกสารที่ merge แล้วทั้งชุดใน request เดียว ห้าม chunking" แบบนี้ต้องกรองด้วยขนาด window ก่อน

ModelContext windowMax outputLatency (เทียบกัน)ราคา input / output ต่อ MTok
Claude Fable 5.11M tokens128K tokensช้ากว่า$10 / $50
Claude Opus 5.51M tokens128K tokensปานกลาง$4 / $20
Claude Sonnet 5.51M tokens128K tokensเร็ว$2 / $10
Claude Haiku 4.5200K tokens64K tokensเร็วที่สุด$1 / $5
  • input ที่ใหญ่เกิน 200K แต่ไม่เกิน 1M จะเหลือ 3 ตัวเลือก แล้วค่อยใช้ราคาและ latency ตัดสิน
  • ถ้าต้อง generate รายงานยาวก้อนเดียว output ต้องไม่เกิน 64K บน Haiku 4.5 หรือ 128K บนตัวอื่น
  • ไม่ต้องจำตัวเลขใส่โค้ด Models API คืนค่า limit ของแต่ละ model มาให้ (max_input_tokens, max_tokens และ capabilities object)
# ดึง limit ของ model มาเช็กก่อนส่งงานจริง
m = client.models.retrieve("claude-haiku-4-5")
if doc_tokens > m.max_input_tokens:
    print("input ใหญ่เกิน window ของ Haiku ตัดทิ้งจาก candidate")
เข้าใจผิดบ่อย

"input ใหญ่มากๆ ต้องใช้ model ที่เก่งที่สุดเท่านั้น" ไม่ใช่ Fable 5.1, Opus 5.5 และ Sonnet 5.5 มี window 1M เท่ากันหมด ตัวที่ตกรอบมีแค่ Haiku 4.5 (200K)

สรุปสั้นๆ

กรองด้วย hard limit ก่อนเสมอ: window ไม่พอ หรือ max output ไม่พอ = ตกรอบ ไม่ว่าจะถูกแค่ไหน ตอนนี้มี 3 ตัวที่ได้ 1M/128K และ Haiku 4.5 ได้ 200K/64K

ลองเดาก่อน

ใน lineup ปัจจุบัน มีกี่ model ที่มี context window 1M tokens?

ดูเฉลย

3 ตัว คือ Fable 5.1, Opus 5.5 และ Sonnet 5.5 มีแค่ Haiku 4.5 ที่เป็น 200K

Checkpoint 3

ระบบตรวจ codebase ต้องส่ง source code รวมประมาณ 450,000 tokens ใน request เดียว และอยากได้ราคาถูกที่สุดเท่าที่ทำได้ ข้อไหนถูก?

  1. Haiku 4.5 เหมาะสุดเพราะถูกที่สุด
  2. มีแค่ Fable 5.1 ที่รับ input ขนาดนี้ได้
  3. Sonnet 5.5 รับได้และถูกที่สุดในกลุ่มที่รับได้ ส่วน Haiku 4.5 รับไม่ได้
  4. ไม่มี model ไหนรับได้ ต้อง chunk เท่านั้น
ดูเฉลย

C 450K เกิน window 200K ของ Haiku 4.5 ซึ่งเป็น hard limit ราคาถูกแค่ไหนก็ไม่ช่วย ในบรรดาตัวที่มี 1M Sonnet 5.5 ถูกที่สุด

3. ใช้ eval เทียบ candidate ก่อนตัดสินใจ

หลังกรองด้วย hard limit มักเหลือหลายตัว ตัวตัดสินคือ eval ที่สร้างจาก functional requirement: แปลงแต่ละ requirement เป็น test case รวมถึง edge case ที่ business สนใจ แล้วให้ทุก candidate รันชุดเดียวกัน (รายละเอียดเรื่อง eval loop อยู่ในบทเรื่อง eval-driven iteration)

  1. สร้าง benchmark test เฉพาะ use case ของเรา
  2. รันด้วย prompt และข้อมูลจริงของเรา
  3. เทียบ accuracy, response quality และการรับมือ edge case ข้าม model
  4. ชั่งน้ำหนัก performance กับ cost (ทำเป็นขั้นสุดท้าย)

ทำไมต้องเป็น cost per completed task

ราคาต่อ token ไม่ได้บอกต้นทุนจริง ถ้า model ถูกแต่ทำพลาดบ่อยจนต้อง retry หรือต้องให้คนแก้ ต้นทุนรวมต่องานที่ สำเร็จจริง อาจแพงกว่า model ที่ราคาต่อ token สูงกว่า

# เทียบต้นทุนต่องานที่สำเร็จจริง ไม่ใช่ราคาต่อ token
def cost_per_completed_task(total_cost_usd, tasks_passed):
    return total_cost_usd / max(tasks_passed, 1)

# model A: ถูกต่อ token แต่ผ่าน 60/100 ข้อ
# model B: แพงกว่า แต่ผ่าน 97/100 ข้อ
print(cost_per_completed_task(3.0, 60))   # 0.050
print(cost_per_completed_task(4.5, 97))   # 0.046  B คุ้มกว่า
เข้าใจผิดบ่อย

"model ที่ราคาต่อ token ต่ำสุดคือตัวเลือกที่ถูกที่สุด" ไม่ใช่ ต้องเทียบด้วย cost per completed task เพราะการทำพลาดและการทำซ้ำมีต้นทุน

ในข้อสอบ: ถ้าโจทย์ถามว่าจะเลือก model ยังไง คำตอบคือสร้าง eval set จาก prompt และข้อมูลจริง ตัวเลือกที่ให้เทียบแค่ list price คือตัวหลอก

สรุปสั้นๆ

Eval ก่อน ราคาทีหลัง สร้าง benchmark → รันกับข้อมูลจริง → เทียบคุณภาพ → ค่อยชั่ง cost โดยดู cost per completed task

Checkpoint 4 (เรียงลำดับ)

ทีมกำลังพิจารณาว่าจะย้ายจาก Opus 5.5 ไป Sonnet 5.5 ดีไหม เรียงขั้นตอนให้ถูก:

  1. เอา prompt และข้อมูลจริงจาก production มารัน
  2. ชั่งน้ำหนัก performance ที่วัดได้กับ cost
  3. สร้างชุด benchmark test สำหรับ use case นี้
  4. เทียบ accuracy, คุณภาพคำตอบ และ edge case ระหว่างสอง model
ดูเฉลย

c → a → d → b eval set ต้องมาก่อนเพราะการเทียบทุกอย่างหลังจากนั้นอิงกับมัน ส่วน cost ชั่งเป็นขั้นสุดท้ายเทียบกับ performance ที่วัดได้จริง

Checkpoint 5

Opus 5.5 กับ Sonnet 5.5 ผ่าน hard limit ทั้งคู่สำหรับงานสกัดข้อมูลจากใบแจ้งหนี้ ควรใช้ตัวชี้วัดไหนตัดสิน?

  1. ราคาต่อล้าน input token
  2. ตัวไหนออกมาใหม่กว่า
  3. Cost per completed task จาก eval ที่สร้างจาก requirement ของเรา
  4. Latency อย่างเดียว
ดูเฉลย

C ราคาต่อ token ไม่นับงานที่ล้มเหลวหรือต้องทำซ้ำ cost per completed task รวมเรื่องว่าแต่ละ model ผ่าน requirement บ่อยแค่ไหนไว้แล้ว
