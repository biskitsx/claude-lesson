2.6 Configuration management: CLAUDE.md, settings.json scopes และ precedence

ต้นฉบับ: CertSafari 2.6

อ่านจบแล้วควรทำได้
  • วาง instruction ให้ถูก scope ของ CLAUDE.md และบอกได้ว่า AGENTS.md กับ path-scoped rule โหลดเมื่อไหร่
  • เรียง scope ของ settings.json ตาม precedence และรู้ว่าอะไรบังคับได้เฉพาะจาก managed settings
  • แยก model ID ที่ pin ไว้กับ alias และไล่ได้ว่า Claude Code session เริ่มด้วย model ไหน
  • Pin, promote และ rollback prompt version แยกตาม environment
  • ประกาศ plugin dependency ด้วย version range และ pin แบบ exact ได้
แนวคิดหลัก: pin vs pointer

Pin ชี้ไปที่ของชิ้นเดียวที่ตายตัว (snapshot model ID, plugin version แบบ exact, prompt version ที่มีเลข) และจะทำงานเหมือนเดิมจนกว่าเราจะแก้เอง Pointer (alias, version range, default ที่ไม่ระบุ) จะ resolve ไปหา "ตัวล่าสุด ณ ตอนนั้น" พฤติกรรมเลยเปลี่ยนได้โดยที่เราไม่ได้แก้อะไรเลย ทั้งบทนี้คือการถามว่า "ตรงนี้เราถือ pin หรือ pointer อยู่"

1. CLAUDE.md scopes, AGENTS.md และ path-scoped rules

Scopeที่อยู่ไฟล์ใครเห็น
Managed policymacOS: /Library/Application Support/ClaudeCode/CLAUDE.md
Linux/WSL: /etc/claude-code/CLAUDE.md		ทุกคนในองค์กร (IT deploy ให้)
User~/.claude/CLAUDE.mdเราคนเดียว ทุก project

  • Scope ของ CLAUDE.md บวกกัน ไม่ได้ override กัน ถ้าสองไฟล์ขัดกัน Claude อาจทำตามข้อไหนก็ได้ ต้องเคลียร์เอง
  • Import แบบ @path ช่วยหั่นไฟล์ยาวให้อ่านง่าย แต่ ไม่ได้ประหยัด context เพราะ import ก็โหลดตอน launch เหมือนกัน
  • claudeMdExcludes ใช้ข้ามไฟล์ที่ match glob (มีประโยชน์ใน monorepo)
  • จังหวะการโหลด: ไฟล์ใน working directory และ directory แม่ทั้งหมดโหลดตอน launch (เรียงจาก root ลงมา) ส่วน CLAUDE.md ใน subdirectory และไฟล์ใน .claude/rules/ โหลดเมื่อ Claude อ่านไฟล์ในนั้นเท่านั้น

Path-scoped rules

ไฟล์ใน .claude/rules/ ที่มี frontmatter paths จะโหลดเฉพาะเมื่อ Claude แตะไฟล์ที่ match ช่วยให้ CLAUDE.md หลักไม่บวม (เป้าคือแต่ละไฟล์ไม่เกินราวๆ 200 บรรทัด) rule ส่วนตัวใส่ใน ~/.claude/rules/

---
paths:
  - "src/api/**/*.ts"
---
# กฎสำหรับ API layer (โหลดเฉพาะตอนแตะไฟล์ใน src/api)
- validate input ทุก endpoint
- ใช้ error format มาตรฐานของทีม
- ใส่ OpenAPI comment ทุก handler

AGENTS.md เป็นแค่ fallback

โดย default, AGENTS.md จะโหลด ก็ต่อเมื่อไม่มี CLAUDE.md, .claude/CLAUDE.md หรือ CLAUDE.local.md อยู่ใน working directory หรือ directory แม่เลย (ไฟล์ระดับ user, managed และ rules ไม่นับในเงื่อนไขนี้)

ถ้าอยากโหลดทั้งคู่ มี 2 ทาง:

  • เพิ่มบรรทัด @AGENTS.md ใน CLAUDE.md (บน Windows ให้ใช้วิธี import นี้ อย่าใช้ symlink)
  • ตั้ง option instructionFiles ของ plugin agents-md ที่มากับระบบเป็น claude-md-and-agents-md
เข้าใจผิดบ่อย

"AGENTS.md โหลดคู่กับ CLAUDE.md เสมอ" ไม่ใช่ มันเป็น fallback ที่โหลดเฉพาะตอนไม่มี CLAUDE.md ในสาย directory

สรุปสั้นๆ

4 scope บวกกัน, ไฟล์สาย parent โหลดตอนเริ่ม, subdirectory กับ rules โหลดเมื่อแตะไฟล์, AGENTS.md มาเฉพาะตอนไม่มี CLAUDE.md

2. settings.json scopes, precedence และ managed settings

ต่างจาก CLAUDE.md ตรงที่ settings resolve ทีละ key: scope ที่สูงกว่าซึ่งตั้ง key นั้นไว้ชนะ ส่วน key ที่ไม่ได้ตั้งจะ inherit จาก scope ที่ต่ำกว่า

Scope (แรงสุดก่อน)ไฟล์ใช้ทำอะไร
Managedmanaged-settings.json, MDM policy หรือ server-managedSecurity และ compliance
Project local.claude/settings.local.jsonOverride ส่วนตัวราย project
Shared project.claude/settings.jsonPermission, hook, plugin, env var ของทีม
User~/.claude/settings.jsonค่าส่วนตัว, model default, rule ของตัวเอง

ลำดับเต็มคือ Managed → command-line args (รวม --settings JSON) → local → shared project → user

  • ไฟล์ local ถูกเพิ่มเข้า global git excludes อัตโนมัติตอนเขียนครั้งแรก และการกด "Don't ask again" จะถูกบันทึกเป็น allow rule ในไฟล์นี้
  • permissions.allow merge ข้าม scope ได้ แต่ allow ใน local ไม่ได้ชนะ ask rule จาก project หรือ managed
// .claude/settings.json (แชร์ทั้งทีม)
{
  "permissions": {
    "allow": ["Bash(npm run lint)", "Bash(npm run test *)"],
    "deny":  ["Read(./.env)", "Read(./.env.*)"]   // กันอ่าน secret
  }
}

สิ่งที่บังคับได้จริงจาก managed เท่านั้น

  • permissions.deny, sandbox.enabled, env สำหรับ provider routing
  • forceLoginMethod, forceLoginOrgUUID
  • allowManagedPermissionRulesOnly

คำแนะนำเชิงพฤติกรรมให้ใส่ใน managed CLAUDE.md ส่วนกฎอย่าง "ห้าม push เข้า main" ต้องมี ทั้ง คำสั่งใน managed CLAUDE.md และ deny rule ใน managed settings เพราะอันแรกแค่บอก อันหลังบล็อกจริง

Security key บางตัวเป็นแบบ "strictest wins" จาก scope ไหนก็ได้ เช่น project ตั้ง disableClaudeAiConnectors: true แม้ managed ตั้ง false ก็ยังปิดอยู่

Clone-time trust

ตอน clone repo มาใหม่ permissions.allow, extraKnownMarketplaces และ env ส่วนใหญ่จะรอจนกว่าเพื่อนร่วมทีมจะ trust โฟลเดอร์ ส่วน deny กับ ask มีผลทันที และ permissions.defaultMode: bypassPermissions ตั้งได้จาก user หรือ managed เท่านั้น (repo แปลกๆ เลยเปิด bypass ให้เราเองไม่ได้)

เข้าใจผิดบ่อย

"ตั้ง model ใน managed settings แล้ว user จะเปลี่ยน model ไม่ได้" ไม่ใช่ ถ้าอยากจำกัดตัวเลือกต้องใช้ availableModels

สรุปสั้นๆ

Settings ชนะกันทีละ key ตามลำดับ managed → CLI args → local → project → user แต่ allow merge กัน, บาง security key strictest wins และ deny/ask มีผลก่อน trust

Checkpoint 3 (เรียงลำดับ)

เรียงจาก precedence สูงไปต่ำ: (a) ~/.claude/settings.json (b) claude --settings '{...}' (c) managed-settings.json (d) .claude/settings.json (e) .claude/settings.local.json

ดูเฉลย

c → b → e → d → a Managed → command-line args → project local → shared project → user

Checkpoint 4

ระหว่าง session ที่เปิดค้างอยู่ เพื่อนแก้ .claude/settings.json เพิ่ม permissions.allow หนึ่งตัว และเปลี่ยน model ด้วย อะไรมีผลทันที?

  1. ทั้งสองอย่างมีผลทันที
  2. ไม่มีอะไรมีผลจนกว่าจะ restart
  3. allow entry ใหม่ hot-reload ทันที แต่ model ต้อง restart
  4. model มีผลทันที แต่ allow ต้อง restart
ดูเฉลย

C permission rule reload ระหว่าง session ได้ แต่ model ของ session ถูกเลือกตอนเริ่ม

3. Model ID, alias และ model ตอนเริ่ม session

ลองเดาก่อน: production ตั้ง claude-sonnet-4-6 (ไม่มีวันที่) ไว้ พอมีรุ่นใหม่ออก มันจะอัปเกรดเองไหม? ไม่ ID ไม่มีวันที่ คือ snapshot ตัวนั้นเลย ยังรันตัวเดิม

  • ตั้งแต่รุ่น 4.6 เป็นต้นมา ID ไม่มีวันที่ (เช่น claude-opus-4-6, claude-sonnet-5) และแต่ละ ID คือหนึ่ง snapshot
  • รุ่นเก่ามีวันที่ (เช่น claude-sonnet-4-5-20250929) และมี API alias (เช่น claude-sonnet-4-5) ที่ชี้ไป dated snapshot ล่าสุดของ minor version นั้น
  • แต่ละ ID มีตาราง deprecation และ retirement ของตัวเอง ถ้า ID ที่ pin ไว้ทำตัวเปลี่ยนไป ให้สงสัยเรื่อง infrastructure ก่อน
  • ข้าม provider: ID ไม่มีวันที่ใช้ชื่อเดียวกันบน Claude API กับ Google Cloud ส่วน Bedrock มี prefix anthropic. สำหรับ ID มีวันที่ ตัวคั่นต่างกัน (เช่น @ บน Google Cloud, ต่อท้าย -v1:0 บน Bedrock)
Claude Code aliasพฤติกรรม
opusOpus ล่าสุด สำหรับงาน reasoning หนักๆ
sonnetSonnet ล่าสุด สำหรับเขียนโค้ดประจำวัน
opusplanOpus ตอน plan mode, Sonnet ตอนลงมือ
defaultล้าง override กลับไปใช้ default ของ runtime (ตัวมันเองไม่ใช่ alias)
  • opus resolve ต่างกันตาม provider เช่น Opus 5.5 บน Anthropic API แต่เป็น Opus 4.6 บน Microsoft Foundry
  • อยาก freeze alias: ตั้ง ANTHROPIC_DEFAULT_OPUS_MODEL, ANTHROPIC_DEFAULT_SONNET_MODEL, ANTHROPIC_DEFAULT_HAIKU_MODEL หรือ ANTHROPIC_DEFAULT_FABLE_MODEL เป็น full ID ถ้ามี availableModels ตัวแปรพวกนี้จะพา alias ที่อนุญาตไปหา model นอกลิสต์ไม่ได้

Session เริ่มด้วย model ไหน

  1. flag --model
  2. env ANTHROPIC_MODEL
  3. ค่า model ใน settings ใดๆ (รวมค่าที่ /model บันทึกไว้)
  4. default ขององค์กร / account
  • model ที่ตั้งใน project หรือ managed มีผลทุกครั้งที่ launch และชนะค่าที่ /model บันทึกไว้ header ตอนเริ่มจะบอกว่ามาจากไฟล์ไหน
  • Session ที่ resume มักใช้ model เดิม และถ้า model ไม่อยู่ใน availableModels จะถูกสลับตอนเริ่มพร้อม warning
  • default อาจ resolve ไปที่ตัวเลือกเก่าที่บันทึกไว้ เว้นแต่ข้อจำกัดตัดมันออก ก็จะ resolve เหมือนไม่เคยบันทึกอะไร
  • /model มีผลทันที ไม่ต้อง restart
# pin model สำหรับ run เดียว ด้วย full ID
claude --settings '{"model": "claude-opus-4-6"}' -p "รีวิว diff นี้"
เข้าใจผิดบ่อย

"ID ที่ไม่มีวันที่คือ pointer ที่อัปเดตตลอด" ไม่ใช่ Anthropic ปล่อยของใหม่ภายใต้ ID ใหม่ ID เดิมคือ snapshot เดิม

4. Prompt version: pin, promote, rollback

ปฏิบัติกับ prompt เหมือน model: แต่ละ version immutable, แต่ละ environment pin ไว้ที่ version เดียว และการเปลี่ยนคือการย้าย version อย่างตั้งใจ ข้อดีคือพอเกิด regression เราบอกได้ว่าเพราะ prompt หรือเพราะ model

  • Managed Agents เก็บ agent (รวม system prompt) ไว้ฝั่ง server
  • agents.update สร้าง version ใหม่ที่ immutable
  • sessions.create เริ่ม session บน version ที่เลือก
# pointer: ส่ง agent id เปล่าๆ = ได้ version ล่าสุดเสมอ
client.sessions.create(agent="agent_abc")

# pin: ส่ง object ระบุ version = ได้ version นั้นเป๊ะ
client.sessions.create(agent={"type": "agent", "id": "agent_abc", "version": 3})

Caller ใน production ที่ส่ง ID เปล่า จะได้ prompt ใหม่ทันทีใน session ถัดไป และ agents.update ไม่มี approval gate key ไหนใน workspace ก็เรียกได้ การ review จึงต้องไปเกิดที่การ pin: config production ใส่เลข version ชัดๆ แล้วผ่าน review ตามปกติ

  1. สร้าง v1
  2. Evaluate v1 กับ test set ที่ label ไว้
  3. Ship v2 แล้ว evaluate
  4. เจอ regression → ชี้ caller กลับไป v1

Rollback ไม่ต้อง deploy อะไรเลย เพราะ v1 ยังอยู่เหมือนเดิม

เข้าใจผิดบ่อย

"ส่ง agent ID เปล่าๆ ก็ยังอยู่ที่ version ที่ test แล้ว" ไม่ใช่ มีแค่ object ที่ระบุ version เท่านั้นที่ pin

สรุปสั้นๆ

Prompt version immutable + production pin เลข version ผ่าน review = rollback ได้ทันทีโดยไม่ deploy

Checkpoint 7 (เรียงลำดับ)

เรียง release cycle ของ prompt: (a) พบ regression (b) evaluate v1 (c) ship v2 (d) สร้าง v1 (e) rollback ด้วยการ pin session กลับไป v1

ดูเฉลย

d → b → c → a → e

5. Plugin dependency: version range และ exact pin

Plugin ประกาศ dependency ใน array dependencies ของ plugin.json แต่ละรายการเป็นชื่อเปล่าๆ หรือ object ที่มี name, version (semver range) และ marketplace (optional)

{
  "name": "my-reviewer",
  "dependencies": [
    "lint-helpers",                                   // ชื่อเปล่า
    { "name": "test-runner", "version": "^2.0" },     // range: รับ fix อัตโนมัติ
    { "name": "secrets-scan", "version": "=2.1.0" }  // exact pin
  ]
}
  • Claude Code ติดตั้ง git tag ที่สูงที่สุด ที่เข้า range โดย range resolve กับ git tag ไม่ใช่ string version ใน plugin.json
  • ใครเป็นคน tag: plugin ที่มี repo ของตัวเอง author เป็นคน tag ส่วน plugin แบบ relative-path ผู้ดูแล marketplace เป็นคน tag
  • claude plugin tag --push validate plugin, สร้าง tag และปฏิเสธถ้า tag มีอยู่แล้ว

ถ้าไม่มี tag ไหนเข้า range:

  • Dependency ที่มี repo ของตัวเอง: ติดตั้ง fail พร้อมข้อความประมาณ "no tag satisfies range"
  • Dependency แบบ relative-path: ติดตั้ง copy ปัจจุบันของ marketplace แล้วเช็ก range ตอนโหลด ถ้าไม่เข้า plugin ที่พึ่งพามันจะถูกปิดไว้ และ claude plugin list แสดง range ที่ต้องการ
Plugin A ต้องการPlugin B ต้องการผลลัพธ์
^2.0>=2.1ติดตั้งตัวเดียวที่ tag 2.x สูงสุดที่ ≥ 2.1.0 โหลดได้ทั้งคู่
~2.1~3.0ติดตั้ง B fail เพราะ requirement ขัดกัน
=2.1.0ไม่มีค้างที่ 2.1.0 และ auto-update ข้ามเวอร์ชันใหม่ตราบที่ A ยังติดตั้งอยู่

ใช้ exact pin ("=2.1.0") เมื่ออยากล็อก build ที่ test แล้ว ใช้ caret (^) หรือ tilde (~) เมื่ออยากได้ fix อัตโนมัติ

เข้าใจผิดบ่อย

"range resolve กับ version ใน plugin.json" ไม่ใช่ มัน resolve กับ git tag release ที่ไม่ได้ tag จะไม่ถูกเลือกเลย

สรุปสั้นๆ

dependencies + semver range → ได้ git tag สูงสุดที่เข้า range อยากล็อกใช้ =x.y.z และอย่าลืม tag ทุก release

Checkpoint 8

Plugin ต้องการ formatter เฉพาะ patch release ของ 3.4 เท่านั้น ต้องเขียน key อะไรใน plugin.json และใช้ range แบบไหน? ถ้า author bump version ใน plugin.json เป็น 3.4.2 แต่ลืม tag จะเกิดอะไร?

ดูเฉลย

ใช้ key dependencies กับ {"name": "formatter", "version": "~3.4.0"} (tilde = รับแค่ 3.4.x) ส่วน 3.4.2 ที่ไม่ได้ tag จะไม่ถูกเลือก เพราะ range ดูจาก git tag ไม่ใช่ string ใน plugin.json
