6.1 Context window budget และ tool output pruning

ต้นฉบับ: CertSafari 6.1

อ่านจบแล้วควรทำได้
  • ไล่ได้ครบว่าใน request หนึ่งของ Claude API มีอะไรบ้างที่กิน context window รวมถึง cached prefix และ thinking
  • อธิบายได้ว่าทำไม context rot ทำให้การ "คัดของเข้า window" สำคัญพอๆ กับขนาดของ window
  • ตั้งค่า tool result clearing และ thinking block clearing ผ่าน context editing ได้ และบอกได้ว่าแต่ละแบบกระทบ prompt caching ยังไง
  • เลือกระหว่าง tool search, programmatic tool calling, prompt caching และ context editing ได้ตามต้นเหตุที่ทำให้ context บวม
แนวคิดหลัก: context rot

ยิ่ง context window เต็ม ความแม่นและความสามารถในการดึงข้อมูลกลับมาใช้ (recall) ของโมเดลก็ยิ่งตก เพราะฉะนั้นอย่าคิดว่า "ที่ยังเหลือ ก็ยัดเข้าไปเถอะ" ให้คิดแบบภัณฑารักษ์ คือเลือกเฉพาะของที่ควรอยู่ใน window จริงๆ (ใน exam guide จะเรียกอาการนี้ว่า context drift)

1. อะไรบ้างที่กินพื้นที่ใน context window

มอง context window เป็น working memory ของ Claude สำหรับ request เดียว และอย่าลืมว่า คำตอบที่โมเดลกำลังเขียนก็ใช้พื้นที่ในนั้นด้วย

ใน conversation ปกติผ่าน API จะไม่มีอะไรถูกทิ้งเองอัตโนมัติ ทุก turn ถูกเก็บไว้ครบ แปลว่าทุก request เราส่ง history ทั้งก้อนกลับไปใหม่หมด คุยยิ่งยาว request ยิ่งอ้วน

  • โมเดล 1M token: Claude Opus 5.5, Claude Sonnet 5.5, Claude Fable 5.1
  • โมเดล 200k token: เช่น Claude Sonnet 4.5
  • อยากรู้ว่า request ที่ส่งไปแล้วใช้ไปเท่าไหร่ ให้ดู field usage ใน response ส่วนถ้าอยากประมาณก่อนส่ง ใช้ token counting API
ส่วนประกอบนับใน window ไหมหมายเหตุ
System prompt และ tool definitionsนับถูกส่งไปทุก request
Tool results, รูปภาพ, เอกสารใน messagesนับสะสมเพิ่มขึ้นเรื่อยๆ ทุก turn
Output ของ turn ปัจจุบัน รวม extended thinkingนับthinking tokens เป็นส่วนหนึ่งของ max_tokens
Thinking blocks ของ turn ก่อนๆขึ้นกับโมเดลถูกเก็บไว้บน Opus 4.5+, Sonnet 4.6+, Fable และ Mythos แต่ถูกตัดทิ้งบน Opus/Sonnet รุ่นก่อนหน้า และ Haiku ทุกรุ่น
Cached prompt prefixนับทั้ง cache_read_input_tokens และ cache_creation_input_tokens นับเต็ม

Context awareness: โมเดลรู้ตัวว่าเหลืองบเท่าไหร่

  • Claude Sonnet 5, Sonnet 4.6, Sonnet 4.5 และ Haiku 4.5 มี context awareness ตัว API จะแทรก tag <budget:token_budget> เข้าไปใน system prompt และส่ง usage system_warning หลัง tool call แต่ละครั้ง ให้โมเดลคุมจังหวะเองได้ เราไม่ต้องส่งของพวกนี้เอง
  • Claude Opus 4.7+, Claude Sonnet 5.5, Fable และ Mythos ไม่ได้ของพวกนี้ ถ้าอยากกำหนดงบ ให้ใช้ฟีเจอร์ beta task budgets ตั้ง budget แบบ explicit
เข้าใจผิดบ่อย

"เปิด prompt caching แล้ว prefix ใหญ่ๆ จะกินพื้นที่ window น้อยลง" ไม่จริง cached tokens ยังนับเต็มจำนวนใน window caching แค่ทำให้ ราคา ถูกลง ไม่ได้ทำให้ ขนาด เล็กลง

สรุปสั้นๆ

ทุกอย่างที่ส่งไป (system, tools, history, cache) บวกกับสิ่งที่โมเดลกำลังเขียน (รวม thinking) อยู่ใน window เดียวกันหมด และ API ไม่ตัดอะไรทิ้งให้เอง

Checkpoint 1

ทีมหนึ่งมี system prompt + tool definitions รวม 60k token และ cache ไว้ ทุก request หลังจากนั้นเป็น cache hit หมด ถามว่า prefix 60k นี้กิน context window ไปเท่าไหร่ต่อ request?

  1. ไม่กินเลย เพราะอ่านจาก cache
  2. ประมาณ 10% ตามอัตราลดราคาของ cache read
  3. ครบ 60k
  4. เฉพาะตอนที่เป็น cache write ครั้งแรก
ดูเฉลย

C caching เปลี่ยนแค่ต้นทุน ไม่ได้เปลี่ยนว่า token พวกนั้นยังนั่งอยู่ใน window หรือไม่

2. ตัด tool output เก่าทิ้งด้วย context editing

ใน agentic workflow ของที่บวมเร็วที่สุดมักเป็น tool results เช่น ผลอ่านไฟล์เมื่อ 20 รอบก่อน หรือผล search ที่ใช้เสร็จไปแล้ว มันยังนั่งกินทั้งพื้นที่และ "ความสนใจ" ของโมเดลอยู่

Context editing คือการให้ API ลบเนื้อหาบางส่วนออกจาก history ตามกฎที่เราตั้ง แนวคิดเบื้องหลังคือ context มีจำกัด ใส่เพิ่มแล้วได้ผลตอบแทนลดลงเรื่อยๆ และของที่ไม่เกี่ยวยังทำให้โฟกัสเสียด้วย

  • เปิดใช้: ใส่ beta header context-management-2025-06-27 และส่ง object context_management ที่มี list edits
  • ทำที่ฝั่ง server ก่อน prompt ไปถึง Claude ฝั่ง client ยังถือ history เต็มไม่ถูกแก้ ไม่ต้อง sync อะไร

พฤติกรรมเมื่อ trigger ทำงาน

  1. พอ input เกินเกณฑ์ trigger ระบบเริ่มเคลียร์ tool results จากเก่าสุดไปใหม่
  2. result ที่ถูกเคลียร์จะถูกแทนด้วยข้อความ placeholder บอก Claude ว่าตรงนี้ถูกลบไปแล้ว
  3. โดย default ลบแค่ result ส่วน tool call (ว่า Claude เรียก tool อะไร) ยังเห็นอยู่ ถ้าตั้ง clear_tool_inputs: true จะลบ parameter ของ call ด้วย
# เปิด tool result clearing แบบปรับค่าเอง
resp = client.beta.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=4096,
    betas=["context-management-2025-06-27"],
    messages=history,                      # client ส่ง history เต็มเหมือนเดิม
    tools=TOOLS,
    context_management={
        "edits": [{
            "type": "clear_tool_uses_20250919",
            "trigger": {"type": "input_tokens", "value": 40000},   # เริ่มเคลียร์เมื่อ input เกิน 40k
            "keep": {"type": "tool_uses", "value": 4},             # เก็บคู่ use/result ล่าสุด 4 คู่
            "clear_at_least": {"type": "input_tokens", "value": 8000},  # ถ้าเคลียร์ได้ไม่ถึง 8k ก็ไม่ทำ
            "exclude_tools": ["web_search"],                       # ผลของ tool นี้ห้ามลบ
        }]
    },
)
Option ของ clear_tool_uses_20250919Defaultคุมอะไร
trigger100,000 input tokensเริ่มเคลียร์เมื่อไหร่ (นับแบบ input_tokens หรือ tool_uses)
keep3 tool usesเก็บคู่ use/result ล่าสุดไว้กี่คู่
clear_at_leastไม่มีต้องเคลียร์ได้อย่างน้อยกี่ token ไม่ถึงก็ข้ามไป
exclude_toolsไม่มีtool ที่ห้ามลบทั้ง use และ result
clear_tool_inputsfalseลบ parameter ของ tool call ด้วยหรือไม่

ทำไมต้องมี clear_at_least: เรื่องของ cache

การลบเนื้อหากลาง history ทำให้ cached prefix invalid ตั้งแต่จุดที่ลบเป็นต้นไป request ถัดไปต้องจ่าย cache write ใหม่ ถ้าลบทีละนิด (ไม่กี่ร้อย token) ก็เท่ากับจ่าย cache write บ่อยๆ แลกกับพื้นที่นิดเดียว clear_at_least เลยเป็นตัวกันว่า "ถ้าได้ไม่คุ้ม ไม่ต้องลบ" ถ้าเคลียร์ไม่ถึงขั้นต่ำ edit นั้นจะไม่ถูกใช้

Thinking block clearing

  • Strategy คู่กันคือ clear_thinking_20251015 ใช้ keep เช่น {"type": "thinking_turns", "value": 2} หรือ "all"
  • เก็บ thinking turns ไว้ = cache ยังอยู่ · ลบทิ้ง = ได้พื้นที่คืน แต่ cache invalid ตั้งแต่จุดนั้น
  • ใส่ทั้งสอง strategy ใน array edits เดียวกันได้
"context_management": {
  "edits": [
    {"type": "clear_thinking_20251015", "keep": {"type": "thinking_turns", "value": 2}},
    {"type": "clear_tool_uses_20250919"}   // ใช้ค่า default ทั้งหมด
  ]
}
เข้าใจผิดบ่อย

"เปิด context editing แล้ว client ต้องลบ result ที่ถูกเคลียร์ออกจาก history ของตัวเองด้วย" ไม่ต้อง การแก้เกิดฝั่ง server ทั้งหมด client ถือ history เต็มต่อไปได้เลย

"Tool result clearing ไม่กระทบ cache เพราะแค่ลบ token ออก" ผิด การลบทำให้ cached prefix พังตั้งแต่จุดที่ลบ ทุกครั้งที่เคลียร์ต้องจ่าย cache write

ลองเดาก่อน

ตรงที่ tool result ถูกเคลียร์ไปแล้ว Claude จะเห็นอะไร?

ดูเฉลย

เห็นข้อความ placeholder ที่บอกว่า result ตรงนี้ถูกลบออกแล้ว ส่วน tool call เดิมยังเห็นอยู่ (ถ้าไม่ได้ตั้ง clear_tool_inputs)

สรุปสั้นๆ

Context editing = server ลบ tool result เก่าสุดก่อน ใส่ placeholder แทน client ไม่ต้องทำอะไร แต่ทุกการลบคือ cache write ใหม่ เลยต้องตั้ง clear_at_least ให้คุ้ม

Checkpoint 2

อยากเปิด tool result clearing แบบค่า default ทั้งหมด ใน edits ต้องใส่ type เป็นอะไร?

  1. clear_thinking_20251015
  2. clear_tool_uses_20250919
  3. compact-2026-09-04
  4. context-management-2025-06-27
ดูเฉลย

B A ใช้เคลียร์ thinking, C เป็น beta header ของ compaction ไม่ใช่ strategy ของ context editing และ D เป็น beta header ที่ต้องใส่เพื่อเปิดฟีเจอร์ ไม่ใช่ชื่อ strategy

Checkpoint 3

agent ตัวหนึ่งเปิด tool result clearing ไว้ แล้วพบว่าการเคลียร์เกิดแทบทุก turn แต่ละครั้งได้คืนแค่ 200–400 token และ cache hit rate ตกฮวบ ควรแก้ที่ไหน?

  1. ลด trigger ให้เคลียร์เร็วขึ้นอีก
  2. ตั้ง clear_tool_inputs: true
  3. ตั้ง clear_at_least ให้ข้ามการเคลียร์ถ้าได้พื้นที่คืนไม่คุ้มกับการทำ cache พัง
  4. เปลี่ยนไปใช้ thinking clearing แทน
ดูเฉลย

C ปัญหาคือเคลียร์ถี่แต่ได้น้อย clear_at_least ถูกออกแบบมาแก้ตรงนี้ ข้ออื่นไม่ได้แตะต้นเหตุ (A ยิ่งทำให้ถี่ขึ้น)

3. เลือกวิธีแก้ให้ตรงกับต้นเหตุที่ทำให้บวม

Context editing เป็นแค่ 1 ใน 4 เครื่องมือ แต่ละตัวทำงานคนละจุดใน pipeline ก่อนเลือก ให้ถามก่อนว่า ที่บวมมาจาก tool definitions หรือจาก tool results ที่สะสม

เครื่องมือทำอะไรแก้ปัญหาไหน
Tool searchไม่โหลด tool definitions เข้ามาจนกว่า Claude จะขอ ใช้ tool tool_search ตัวเดียวแทน schema หลายสิบอัน แลกกับ turn เพิ่มหนึ่งรอบdefinitions เยอะเกินตั้งแต่ต้น
Programmatic tool callingรัน chain ของ tool calls เป็น script เดียวใน code execution sandbox ของ Anthropic ผลระหว่างทางไม่เข้า historytool_result ไปกลับหลายรอบจาก call ย่อยๆ ต่อกัน
Prompt cachingไม่ลดจำนวน token เลย แค่ทำให้ prefix ที่คงที่ถูกลงต้นทุนของการส่ง toolset เดิมซ้ำๆ
Context editingลบ result เก่าหลังจากใช้เสร็จแล้วtool_result เก่าที่ไม่เกี่ยวแล้ว

ใช้ร่วมกันได้ ลำดับที่แนะนำสำหรับ agent ที่ traffic สูง:

  1. Cache tool definitions ตั้งแต่วันแรก
  2. เพิ่ม tool search เมื่อ toolset เกินราว 20 ตัว
  3. เพิ่ม context editing เมื่อ conversation ยาวจน result ช่วงแรกๆ ไม่มีความหมายแล้ว
  4. พิจารณา programmatic tool calling เมื่อเห็น pattern เรียก tool เล็กๆ ต่อกันเป็นสายซ้ำๆ
เข้าใจผิดบ่อย

"Tool search, programmatic tool calling และ context editing ลด token แบบเดียวกัน ใช้ตัวไหนก็ได้" ไม่ใช่ แต่ละตัวเล็งต้นเหตุคนละแบบ ส่วน caching ไม่ได้ลด token เลย

สรุปสั้นๆ

Definitions บวม → tool search · chain call บวม → programmatic tool calling · result เก่าบวม → context editing · แพง → caching (ซึ่งไม่ลดขนาด)

Checkpoint 4 (จับคู่)

จับคู่อาการกับเครื่องมือ:

  1. agent มี tool 45 ตัว schema ทั้งหมดถูกโหลดเข้ามาทุก request
  2. agent ดึงราคาสินค้า 30 รายการทีละตัว แต่ละรอบมี tool_result กลับเข้า history
  3. toolset คงที่ ส่งซ้ำทุก request ค่าใช้จ่ายสูง แต่ขนาด window ยังไม่มีปัญหา
  4. log ที่อ่านตอนต้น session ยาวมากและไม่เกี่ยวกับงานตอนนี้แล้ว
ดูเฉลย

1 → tool search · 2 → programmatic tool calling · 3 → prompt caching · 4 → context editing

Checkpoint 5

ทีม compliance ต้องการเก็บ transcript ฉบับเต็ม (ก่อนถูกสรุป) ไว้ตรวจสอบทุกครั้งที่ session ยาวๆ กำลังจะถูก compact ควรใช้อะไร?

  1. SessionEnd hook
  2. PreCompact hook
  3. PostToolUse hook
  4. อ่านจาก system message compact_boundary
ดูเฉลย

B PreCompact hook รันก่อน compaction (รับ field trigger เป็น manual หรือ auto) จึงเซฟ transcript ได้ก่อนถูกแทนด้วย summary · SessionEnd สายเกินไปเพราะ compaction เกิดกลาง session · PostToolUse ทำงานหลัง tool call แต่ละครั้ง ไม่เกี่ยวกับ compaction · compact_boundary แค่บอกว่ามี compaction เกิดขึ้น ไม่ได้มี transcript เต็มมาด้วย
