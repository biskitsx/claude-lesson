Workflow vs Agent

Workflow หรือ Agent: จะเลือกสถาปัตยกรรมแบบไหนดี

อธิบายเป็นภาษาไทยแบบเข้าใจง่าย ว่าระบบที่ใช้ LLM ควรออกแบบเป็น workflow หรือเป็น agent เมื่อไหร่ควรมี subagent และแต่ละแบบต้องจ่ายอะไรบ้าง

เรียบเรียงจากบทเรียน Workflows vs Agents (CertSafari) และเอกสารของ Anthropic ที่บทเรียนนั้นอ้างถึง เนื้อหาเขียนใหม่ด้วยภาษาของเราเอง แบบทดสอบก็แต่งขึ้นใหม่

อ่านจบแล้วควรทำได้
  • แยก workflow กับ agent ออกจากกันได้ ด้วยคำถามข้อเดียว: ใครเป็นคนตัดสินว่าขั้นต่อไปคืออะไร โค้ดของเราหรือโมเดล
  • เลือกระดับความอิสระ (autonomy) ที่ต่ำที่สุดที่ยังตอบโจทย์ได้ และบอกได้ว่าการให้อิสระเพิ่มต้องแลกกับอะไร
  • อธิบายได้ว่า orchestrator ส่งงานให้ subagent ยังไง และอะไรถูกส่งกลับมา
  • บอกได้ว่ามี 3 สถานการณ์ที่ subagent ดีกว่าการใช้ agent ตัวเดียว และประเมินต้นทุนเรื่อง token กับเวลาได้คร่าวๆ
แนวคิดหลัก: ใครถือพวงมาลัย

ใน workflow ลำดับการเรียก LLM และ tool ถูกเขียนตายตัวไว้ในโค้ดของเรา ส่วนใน agent โมเดลเป็นคนเลือกเองตอนรันว่าจะทำอะไรต่อและจะเรียก tool ไหน

1. ความต่างอยู่ที่ว่า "ใครคุม control flow"

Anthropic เรียกระบบทั้งหมดในกลุ่มนี้รวมๆ ว่า agentic systems แล้วแบ่งย่อยเป็น 2 แบบ:

  • Workflow คือ LLM กับ tool ทำงานตามเส้นทางที่เราเขียนโค้ดกำหนดไว้ล่วงหน้า
  • Agent คือ LLM เป็นคนกำหนดขั้นตอนและเลือกใช้ tool เอง โดยคุมทั้งกระบวนการว่างานจะเสร็จด้วยวิธีไหน

เปรียบง่ายๆ workflow เหมือนสูตรอาหารที่เขียนไว้ทีละขั้น ใครทำก็ทำตามลำดับเดิม ส่วน agent เหมือนเชฟที่เปิดตู้เย็น ดูว่ามีอะไร แล้วค่อยคิดว่าจะทำอะไรต่อ

ดูจากโค้ดจะเห็นชัด

Workflow: ลำดับขั้นอยู่ในโค้ด อ่านโค้ดแล้วรู้เลยว่ามีกี่ขั้น

def localize(brief):
    draft = llm("เขียนข้อความจาก brief นี้", brief)
    checked = llm("ตรวจข้อความตามเกณฑ์", draft)
    return llm("แปลเป็นภาษาไทย", checked)

Agent: โค้ดเป็นแค่ลูป ในแต่ละรอบ Claude ตัดสินเองว่าจะตอบเลย จะเรียก tool หรือทำทั้งสองอย่าง ลูปจบเมื่อ Claude ตอบกลับมาโดยไม่ขอเรียก tool แล้ว

messages = [{"role": "user", "content": task}]
while True:
    reply = claude(messages, tools=TOOLS)
    messages.append(reply)
    if not reply.tool_calls:          # ไม่ขอ tool แล้ว = งานเสร็จ
        break
    messages.append(run_tools(reply.tool_calls))

สังเกตว่าในโค้ด agent ไม่มีตรงไหนบอกว่าจะวนกี่รอบ หรือจะเรียก tool ไหนก่อนหลัง ทุกอย่างโมเดลเป็นคนเลือก

แต่ละแบบได้อะไร เสียอะไร

  • Workflow คาดเดาได้ ผลลัพธ์สม่ำเสมอ เทสต์ได้ทุกเส้นทาง และรู้ต้นทุนล่วงหน้า
  • Agent ยืดหยุ่น เหมาะกับงานที่บอกขั้นตอนล่วงหน้าไม่ได้ ตัวอย่างคลาสสิกคืองานรีเสิร์ช ที่จะค้นอะไรต่อขึ้นอยู่กับว่าผลค้นครั้งก่อนเจออะไร
สรุปสั้นๆ

อย่าดูแค่ว่ามี LLM ตัดสินใจอะไรบางอย่างหรือเปล่า ให้ดูว่า เส้นทางที่เป็นไปได้ทั้งหมด ถูกเขียนไว้ในโค้ดหรือไม่ ถ้าใช่ ก็คือ workflow

Checkpoint 1

ระบบตอบอีเมลลูกค้าให้ LLM อ่านอีเมลแล้วบอกภาษา (ไทย / อังกฤษ / ญี่ปุ่น) จากนั้นโค้ด match เลือก template ตอบตามภาษานั้น ระบบนี้คืออะไร?

  1. Agent เพราะ LLM เป็นคนตัดสินว่าเป็นภาษาอะไร
  2. Workflow เพราะทางเลือกทั้งหมดถูกเขียนไว้ในโค้ดแล้ว LLM แค่ชี้ว่าไปทางไหน
  3. Agent เพราะมีหลาย template
  4. ไม่ใช่ทั้งคู่ เพราะไม่มีการเรียก tool
ดูเฉลย

B ผลลัพธ์ของ LLM แค่เลือกหนึ่งในเส้นทางที่โค้ดเตรียมไว้แล้ว โมเดลสร้างเส้นทางใหม่เองไม่ได้ เลยยังเป็น workflow (แบบ routing)

2. เริ่มจากขั้นล่างสุดของ "บันไดความอิสระ"

กฎการออกแบบข้อแรกคือ ทำสิ่งที่ง่ายที่สุดที่ใช้ได้ก่อน แล้วค่อยเพิ่มความซับซ้อนเมื่อมีโจทย์บังคับจริงๆ บางครั้งคำตอบที่ถูกคือไม่ต้องมี agentic system เลย แค่เรียก LLM ครั้งเดียวที่ทำ retrieval และใส่ตัวอย่างใน prompt (in-context examples) ดีๆ ก็มักจะพอ

ยิ่งขึ้นบันไดสูง ก็ยิ่งยก control flow ไปให้โมเดลมากขึ้น ระหว่างการเรียก LLM ครั้งเดียวกับ agent เต็มรูปแบบ มี workflow pattern คั่นอยู่ 5 แบบ: prompt chaining, routing, parallelization, orchestrator-workers และ evaluator-optimizer (รายละเอียดอยู่ในบทเรียน 1.3)

ขั้นบันไดใครตัดสินขั้นตอนใช้ขั้นนี้ก็พอ เมื่อ…
เรียก LLM ครั้งเดียว + retrieval + ตัวอย่างใน promptไม่มีใคร (มีขั้นเดียว)prompt ดีๆ ครั้งเดียวก็ได้คุณภาพตามเป้า
Workflow แบบตายตัว (chaining, routing, parallelization)โค้ดของเรางานแบ่งเป็นงานย่อยที่รู้ล่วงหน้าได้ชัดเจน
Orchestrator-workersLLM ตัวกลางเลือกงานย่อย ส่วนโครงสร้างโค้ดเป็นคนรันเดางานย่อยล่วงหน้าไม่ได้ เช่น ไม่รู้ว่าการแก้ครั้งนี้จะกระทบกี่ไฟล์
Agent อิสระเต็มตัวโมเดล ตัดสินทีละรอบงานต้องการความยืดหยุ่นและให้โมเดลตัดสินใจเองในสเกลใหญ่

การขึ้นบันไดมีราคาที่ต้องจ่าย

การเปลี่ยนจาก workflow ที่เทสต์ผ่านแล้วไปเป็น agent ไม่ได้มีผลแค่เรื่องคุณภาพ:

  • Agent กำหนดจำนวนรอบเอง ดังนั้น ค่า token และเวลาตอบไม่ได้ถูกล็อกไว้ในโค้ดอีกต่อไป อาจถูกหรือแพง เร็วหรือช้าก็ได้
  • Framework บางตัวซ่อน prompt และ response จริงไว้ ทำให้ debug ยากขึ้น
เข้าใจผิดบ่อย

"Orchestrator-workers ก็คือ parallelization ที่มี LLM ครอบอีกชั้น" ไม่ใช่ ใน orchestrator-workers โมเดลเป็นคนคิดงานย่อยตอนรันโดยดูจาก input ส่วน parallelization งานย่อยถูกกำหนดไว้ตั้งแต่แรก

"Agent อิสระคือเวอร์ชันอัปเกรดของ workflow เสมอ" ไม่ใช่ ระบบแบบ agent เอาเวลาและค่าใช้จ่ายไปแลกกับประสิทธิภาพ ถ้างานนิยามได้ชัด workflow หรือการเรียก LLM ครั้งเดียวที่จูนดีแล้วมักดีกว่า

สรุปสั้นๆ

ถามตัวเองว่า "ขั้นที่ต่ำกว่านี้ทำได้ไหม" ถ้าทำได้ ให้หยุดที่ขั้นนั้น ความอิสระที่เกินความจำเป็นคือค่า token กับเวลาที่เสียไปฟรีๆ

Checkpoint 2

ทีมมี pipeline สรุปรายงานประชุม (ดึง action items → จัดหมวด → เขียนสรุป) ที่ได้คุณภาพตามเป้าแล้ว มีคนเสนอให้เปลี่ยนเป็น agent อิสระ "เพื่อความทันสมัย" ข้อโต้แย้งไหนหนักแน่นที่สุด?

  1. Agent ให้ผลคุณภาพแย่กว่า workflow เสมอ
  2. Agent ใช้ tool อย่าง retrieval ไม่ได้
  3. ระบบเดิมตอบโจทย์อยู่แล้ว การเปลี่ยนเป็น agent จะเสียความคาดเดาได้ และเพิ่มเวลากับต้นทุนที่งานนี้ไม่ต้องการ
  4. Workflow ใส่การตรวจด้วยโค้ดระหว่างขั้นไม่ได้
ดูเฉลย

C ข้ออื่นเป็นข้อกล่าวอ้างที่ไม่จริง Agent ไม่ได้แย่กว่าเสมอ ใช้ tool ได้ และ workflow ก็ใส่ด่านตรวจระหว่างขั้นได้

Checkpoint 3

ระบบรับคำขอคืนสินค้าแบ่งเคสได้ 4 ประเภทที่รู้แน่นอน แต่ละประเภทมีขั้นตอนดำเนินการตายตัว ควรใช้สถาปัตยกรรมไหน?

  1. Orchestrator-workers ให้ LLM ตัวกลางคิดตอนรันว่าจะเรียกระบบไหน
  2. Routing workflow: จัดประเภทคำขอ แล้วรันขั้นตอนตายตัวของประเภทนั้น
  3. Agent อิสระที่เลือก tool และจุดหยุดเอง
  4. เรียก LLM 4 ครั้งตามลำดับเดิมทุกครั้ง ไม่ว่าเคสจะเป็นประเภทไหน
ดูเฉลย

B งานย่อยรู้ล่วงหน้าหมดแล้ว A จึงเพิ่มความยืดหยุ่นที่ไม่จำเป็น C ทำให้ขั้นตอนคาดเดาไม่ได้ ส่วน D ไม่มีการจัดประเภท เลยแยกเส้นทางตามประเภทไม่ได้

3. ลำดับชั้นแบบหัวหน้า–ลูกทีม: orchestrator กับ subagent

Orchestrator–subagent pattern คือระบบ multi-agent ที่มี agent หัวหน้า (lead) หนึ่งตัว ทำหน้าที่แตกงานเป็นส่วนๆ สร้าง subagent เฉพาะทางขึ้นมาทำแต่ละส่วน แล้วคอยดูแล แต่ละ agent เป็น LLM instance แยกกัน มี context ของตัวเอง และมีโค้ดเป็นตัวประสาน ในบรรดา multi-agent pattern ทั้งหมด แบบนี้ประสานงานง่ายที่สุด จึงมักเป็นจุดเริ่มต้น

ข้อเท็จจริงสำคัญ

tool call ระหว่างทางและผลลัพธ์ของ subagent อยู่ในบทสนทนาของ subagent เอง สิ่งที่ส่งกลับไปให้ตัวแม่มี แค่ข้อความสุดท้าย หัวหน้าเลยทำงานจากภาพที่ถูกย่อแล้ว เหมือนผู้จัดการที่อ่านแค่รายงานสรุป ไม่ได้นั่งดูลูกทีมทำงานทุกขั้น

ตัวอย่างโค้ดแบบย่อ

async def research_topic(query):
    facets = await lead_plan(query)                    # 1. หัวหน้าแตกคำถามเป็นประเด็นย่อย
    findings = await asyncio.gather(                   # 2. ปล่อย subagent ประเด็นละตัว พร้อมกัน
        *(run_subagent(f) for f in facets))
    return await lead_synthesize(query, findings)      # 3. หัวหน้ารวมผล

ตัวอย่างจริง: ฟีเจอร์ Research ของ Anthropic

  1. LeadResearcher วางแผนแล้ว บันทึกแผนลง memory เพราะถ้า context ยาวเกิน 200,000 token จะถูกตัดทิ้ง
  2. สร้าง subagent แต่ละตัวพร้อมโจทย์รีเสิร์ชเฉพาะ
  3. subagent แต่ละตัวค้นข้อมูลแยกกันเอง แล้วส่งสิ่งที่เจอกลับมา
  4. หัวหน้ารวมผลแล้วตัดสินว่าต้องค้นเพิ่มอีกไหม (ถ้าต้อง ก็วนกลับไปข้อ 2)
  5. เมื่อจบลูปรีเสิร์ช ผลทั้งหมดถูกส่งให้ CitationAgent แยกต่างหาก เพื่อผูกแต่ละข้อความเข้ากับแหล่งอ้างอิง

ผลลัพธ์: ใช้ Claude Opus 4 เป็นหัวหน้าและ Sonnet 4 เป็น subagent ทำคะแนนใน eval รีเสิร์ชภายในได้ดีกว่า Opus 4 แบบ agent ตัวเดียวถึง 90.2%

ทางเลือกเชิงโครงสร้าง 2 เรื่อง

  • รอแบบ synchronous: หัวหน้ารอ subagent ทั้งชุดเสร็จก่อนค่อยไปต่อ ประสานงานง่าย แต่ถ้ามีตัวไหนช้า ทุกอย่างก็ช้าตาม
  • ส่งทุกอย่างผ่านหัวหน้าทำให้รายละเอียดหาย: อีกทางคือให้ subagent เขียนผลลงที่เก็บภายนอก (ไฟล์, DB) แล้วส่งกลับแค่ reference สั้นๆ
เข้าใจผิดบ่อย

"Orchestrator เห็นทุก tool call และทุกไฟล์ที่ subagent ทำผ่านมา" ไม่ใช่ ตัวแม่ได้แค่ข้อความสุดท้าย ซึ่งปกติเป็นสรุปสั้นๆ

สรุปสั้นๆ

หัวหน้าแตกงาน → ลูกทีมทำใน context ของตัวเอง → ส่งกลับแค่สรุป → หัวหน้ารวมผลและตัดสินว่าจะไปต่อหรือหยุด

Checkpoint 4 (เรียงลำดับ)

เรียงขั้นตอนของลูป orchestrator ในระบบ Research ให้ถูก:

  1. CitationAgent ผูกข้อความกับแหล่งอ้างอิง
  2. หัวหน้าสร้าง subagent พร้อมโจทย์เฉพาะ
  3. หัวหน้าวางแผนและบันทึกแผนลง memory
  4. หัวหน้ารวมผลและตัดสินว่าต้องค้นเพิ่มไหม
  5. subagent แต่ละตัวค้นข้อมูลเองแล้วส่งผลกลับ
ดูเฉลย

c → b → e → d → a การทำ citation เป็นขั้นแยกที่เกิดหลังจากลูปรีเสิร์ชจบแล้ว

Checkpoint 5

ระบบสร้างคำบรรยายสินค้าทำงานแบบนี้ทุกครั้ง: เขียนร่าง → ตรวจคำต้องห้ามตามเกณฑ์ตายตัว → ย่อให้สั้นสำหรับมือถือ แต่ละขั้นรับ output ของขั้นก่อนหน้าไปทำต่อ เป็น pattern ไหน?

  1. Orchestrator-workers
  2. Evaluator-optimizer
  3. Routing
  4. Prompt chaining
ดูเฉลย

D ลำดับตายตัวและส่งต่อ output ทีละขั้น ไม่มีการเลือกเส้นทาง (routing) ไม่มีการวนแก้จนผ่าน (evaluator-optimizer) และไม่มี LLM คิดงานย่อยตอนรัน (orchestrator-workers)

4. เมื่อไหร่ subagent คุ้ม และต้องจ่ายเท่าไหร่

Subagent ช่วยได้จริงแค่ใน 3 สถานการณ์ นอกจากนั้นต้นทุนการประสานงานมักแพงกว่าสิ่งที่ได้กลับมา หลายทีมพบว่าแค่ปรับ prompt ของ agent ตัวเดียวให้ดีขึ้นก็ได้ผลพอๆ กับ multi-agent แล้ว

สถานการณ์ปัญหาเมื่อใช้ agent ตัวเดียวsubagent ช่วยยังไง
Context pollution (context รก)ผลจากงานย่อยหนึ่ง เช่น ประวัติคำสั่งซื้อยาว 2,000+ token ไปเบียดพื้นที่คิดของงานถัดไปมี context สะอาดแยกต่างหาก แล้วส่งกลับแค่สรุปสั้นๆ
งานขนานagent ตัวเดียวค้นทีละขั้น ครอบคลุมได้น้อยหลาย subagent สำรวจคนละมุมพร้อมกัน
ความเชี่ยวชาญเฉพาะtool เยอะเกินไป (มักเกิน 20 ตัว) ข้ามหลายโดเมน ทำให้เลือก tool ผิดแต่ละตัวมีชุด tool และ system prompt เฉพาะหน้าที่ของตัวเอง
  • การแยก context คุ้มที่สุดเมื่องานย่อยสร้าง output เกินประมาณ 1,000 token และส่วนใหญ่ไม่เกี่ยวกับงานหลัก
  • การแยกความเชี่ยวชาญยัง ช่วยเรื่องความปลอดภัย ด้วย ใน Agent SDK แต่ละ subagent กำหนด system prompt และจำกัด tool ของตัวเองได้ เช่น ถ้าให้ reviewer มีแค่ tool อ่าน ก็วิเคราะห์ไฟล์ได้แต่แก้ไฟล์ไม่ได้

ต้นทุนที่ต้องรู้

  • ระบบ multi-agent มักใช้ token มากกว่า agent ตัวเดียว 3–10 เท่า ส่วนที่เพิ่มมาจาก context ที่ซ้ำกัน ข้อความที่ agent ส่งหากัน และสรุปตอนส่งต่องาน
  • subagent ที่รันขนานกันเสร็จพร้อมตัวที่ช้าที่สุด แต่ เวลารวมของงานทั้งหมดมักนานขึ้น เพราะปริมาณการคำนวณรวมเพิ่มขึ้นมาก
  • สิ่งที่ได้จริงจากการรันขนานคือ ความครอบคลุม ไม่ใช่ความเร็ว
  • งานที่ไม่เหมาะ: งานที่ทุก agent ต้องใช้ context ชุดเดียวกัน หรือ agent ต้องพึ่งพากันมาก งานเขียนโค้ดส่วนใหญ่มีส่วนที่แยกทำขนานได้น้อยกว่างานรีเสิร์ช
  • ความล้มเหลวที่เคยเกิด: ระบบ Research รุ่นแรกๆ ปล่อย subagent 50 ตัวกับคำถามง่ายๆ บางทีมแยก วางแผน / ลงมือ / รีวิว เป็นคนละ agent แล้วเสีย context ทุกครั้งที่ส่งต่อ จนใช้ token ไปกับการประสานงานมากกว่าการทำงานจริง

จำกัด tool ของ subagent ใน Agent SDK

agents: {
  "code-reviewer": {
    description: "รีวิวโค้ดโดยไม่แก้ไฟล์",
    prompt: "คุณคือ reviewer ...",
    tools: ["Read", "Grep", "Glob"],   // subagent ตัวนี้ใช้ได้แค่ tool เหล่านี้
    model: "sonnet"
  }
}
  • tools (อยู่ในนิยามของ agent) คือรายชื่อ tool ที่ subagent ตัวนั้นใช้ได้
  • allowedTools เป็น option ระดับบนสุด ใช้อนุมัติ tool อัตโนมัติสำหรับทั้ง query ไม่ได้จำกัดเฉพาะ subagent
  • disallowedTools ใช้ตัด tool ที่ระบุชื่อออก ไม่ได้เป็นรายชื่อ tool ที่อนุญาต
เข้าใจผิดบ่อย

"แบ่งงานให้ subagent รันขนานกันแล้วจะเสร็จเร็วกว่า agent ตัวเดียว" ไม่ใช่ การรันขนานซื้อความครอบคลุม แต่ปริมาณงานรวมก็เพิ่มขึ้นมาก

สรุปสั้นๆ

ใช้ subagent เมื่อเจอ 1 ใน 3 ปัญหานี้: context รก, ต้องสำรวจหลายมุมพร้อมกัน หรือ tool เยอะจนเลือกผิด และต้องยอมจ่าย token 3–10 เท่า

ลองเดาก่อน

งานรีเสิร์ชที่ agent ตัวเดียวทำได้ ถ้าเปลี่ยนเป็น subagent 4 ตัวรันขนาน เวลาจริง (wall-clock) จะเป็นยังไง?

  1. ลดเหลือประมาณ 1 ใน 4
  2. ลดลงนิดหน่อย เพราะการประสานงานกินเวลาไปบ้าง
  3. หลายครั้งกลับนานขึ้น เพราะปริมาณการคำนวณรวมเพิ่มขึ้นมาก
ดูเฉลย

C สิ่งที่ได้คือความครอบคลุม ไม่ใช่ความเร็ว

  2. tools
  3. disallowedTools
  4. permissionMode
ดูเฉลย

B tools ในนิยาม agent คือรายชื่อ tool ที่ตัวนั้นใช้ได้ ส่วน allowedTools เป็นการอนุมัติอัตโนมัติระดับทั้ง query และ disallowedTools ใช้ตัด tool ออก

Checkpoint 7 (จับคู่)

จับคู่อาการของ agent ตัวเดียวกับประโยชน์ของ subagent:

  1. ดึง log ระบบมาหมื่น token ก่อนวิเคราะห์ แล้ว agent วิเคราะห์ประเด็นหลักพลาด
  2. คำถามเปรียบเทียบคู่แข่ง 6 เจ้า แต่ agent ค้นทีละเจ้าแล้วไม่ทั่วถึง
  3. เพิ่ม tool ฝั่ง billing เข้าไปแล้ว agent กลับเลือก tool ผิดในงานซัพพอร์ตที่เคยทำได้ดี
ดูเฉลย

1 → แยก context (context isolation) · 2 → สำรวจขนาน (parallel exploration) · 3 → แยกความเชี่ยวชาญด้วยชุด tool เฉพาะ (specialization)

Checkpoint 8

ทุกครั้งที่มีการอัปโหลดสัญญา ระบบให้ LLM 3 ตัวตรวจพร้อมกันคนละเรื่อง (ข้อกฎหมาย / ตัวเลขการเงิน / วันที่สำคัญ) แล้วรวมผลเป็นรายงานเดียว เป็น pattern ไหน?

  1. Parallelization แบบ sectioning: แบ่งงานย่อยอิสระมาตรวจ input เดียวกันพร้อมกัน แล้วรวมผล
  2. Parallelization แบบ voting: รัน prompt เดียวกันหลายรอบแล้วเอาเสียงข้างมาก
  3. Evaluator-optimizer: ตัวหนึ่งหาปัญหา อีกตัววิจารณ์วนไปเรื่อยๆ
  4. Orchestrator-workers: LLM ตัวกลางเลือกตอนรันว่าจะตรวจเรื่องไหนบ้าง
ดูเฉลย

A หมวดการตรวจถูกกำหนดตายตัว (ไม่ใช่ D) แต่ละตัวทำคนละเรื่อง (ไม่ใช่ voting) และไม่มีการวนแก้ (ไม่ใช่ C)
